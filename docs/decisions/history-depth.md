# 订阅的历史深度(kb/feeds/history.py + registry.py + sync.py)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束(原 CLAUDE.md「订阅的历史深度(kb/feeds/history.py + registry.py + sync.py)」)

- **新订阅只收最近 `reg.HISTORY_DAYS`(5)天的内容**(`sync._within_history`)—— 一个刚添加的源常常把整个存档一次交
  出来,这些旧文随后逐批翻译、逐批重新导出,每重新导出一次 `indexed_at` 就刷新一次,于是**连着十几天以「补录」的形
  态占满当天日报**。
- **下界是订阅创建(或改链接重置)那一刻钉死的一个日期**(`subscriptions.history_floor`),**不是「距今 N 天」的滑动
  窗口**(滑动窗口会在源站停更几天后恢复时把那几天静默丢掉)。**也不能只拦「第一次抓取」**:第一次之后 etag 命中
  304,等源站下次更新时整份 feed 又回来了,那时闸门早撤了。
- **老库里的订阅补成空串 = 不设下界,行为逐字不变。**
- **没有发布时间的条目照收**(身上没有任何「很旧」的证据),日报那边按「补录」接住。
- **区间补抓(`scope.ranged`)不受这道闸限制** —— 那是唯一的逃生口。
- **`_within_history` 只管往后,存量要单独清**(`scripts/feed_trim_history.py`)。清理**同时会钉上 `history_floor`**。
  顺序:备份 → 钉下界 → 删 feeds.db 行 → 删 vault md → `remove_missing_documents`;**feeds.db 要先删**(它是「要不要
  重新导出」的事实来源)。**被别的订阅共享的条目只摘归属、不删行**,而且要**连文件和索引一起算**(`_live_paths`)。
  **收藏保护只按真要删的那些判。**
- **另一条筛选口径 `--pending-translation`** 直接取 `translate.queued_sql()`。**这一路不钉 `history_floor`**(筛的维
  度不是日期)。它和 `--floor` 不能一起用,**而这道互斥检查必须排在所有副作用之前,「续上没做完的那一份」和取锁都算
  副作用** —— 口径在 `cmd_run` 的第一句,**不在 `_run_locked` 里**。**有没做完的计划时,这一趟只续它、续完就
  `return 0`。**
- **「给了 `--floor` 没有」问的是 `args.floor is not None`,不许问真值**(`--floor ""` 是变量没赋值那种最常见的 shell
  事故,而这是不可逆删除)。
- **下界先校验再用**(`norm_floor`),非规范写法在备份和任何删除之前就拒掉:比较是**字符串**比较,`2026-10-1` 少写一
  个零就既大于当天那篇、又大于第二天那篇。
- **删除分三步、每一步做完记一笔**(`progress.json`),各步幂等,重跑先把没做完的续完。
- **清理和同步、索引之间有一把跨进程锁**(见维护锁那节),锁之外还要**「下界现读」**(`sync._stored_floor`)—— 两道各
  管一段,缺任何一道都会复发。
- **问不到管道状态一律拦下,只有连接被拒才放行**(连接被拒 = 服务没起 = 没有管道在跑,这是唯一能证明空闲的那种)。
- **`--source` 是纯数字时只按 id 查,不许退回名字**(`trim.find_source`)。**名字命中多条时拒绝执行、要求改用 id。**
- **备份目录要原子地占一个唯一名字**(`tempfile.mkdtemp`,前缀带订阅 id)。
- **续跑不是「接着执行上次批准的那件事」,收藏那道护栏要按此刻的事实再查一遍**,而且**必须和删除在同一个写事务里**
  (`_apply` 在 kb.db 上 `BEGIN IMMEDIATE`,最终复查、unlink、`remove_missing_documents` 全在这一个事务里)——
  **索引能从 vault 重建,收藏和备注不能**。配套:**删索引必须用持锁那条连接**;`--allow-favorites` 放行时把要毁掉的那
  几行另存 `favorites.json` 进备份。
- **没有旧文可清 ≠ 不用钉下界**;**没带 `--yes` 一个设置都不改**。
- **测试样本的发布日期必须跟着今天走**(`_FRESH`/`DAY`),写死日期过几天就被这道闸挡住。
- 详细见 `docs/decisions/history-depth.md`。

## 事故形态与实测证据

- **新订阅只收最近 `reg.HISTORY_DAYS`(5)天的内容**(`sync._within_history`)。一个刚
  添加的源常常把自己的整个存档一次交出来:实测 `Hugging Face Blog` 的 feed 一口气给了
  500 条、最早到 2024-04-10。这些旧文随后逐批翻译(一轮 40 条)、逐批重新导出,每重新
  导出一次 `indexed_at` 就刷新一次,于是**连着十几天以「补录」的形态占满当天日报**——
  而它们并不是那几天发生的事(2026-10-01 那份日报 46 条素材里补录占了 30 条,其中 29
  条是这一个源 7 月的旧文)。
- **下界是订阅创建(或改链接重置)那一刻钉死的一个日期**(`subscriptions.history_floor`,
  由 `reg.history_floor()` 算),**不是「距今 N 天」的滑动窗口**。两个写法都试得通,
  但另外两种写法各自漏一头:
  ①**滑动窗口**会在源站停更几天后恢复时,把那几天的内容静默丢掉——而那正是最该补回来
    的一批;钉死的下界对一个已经建立起来的订阅永远是过去式,只在它自己最前面那几次
    抓取起作用。
  ②**只拦「第一次抓取」**挡不住任何事:第一次之后 etag 命中 304、什么都不返回,等源站
    下次更新时整份 feed(连同那 500 条存档)又回来了,那时闸门早撤了。按固定日期判则与
    抓第几次无关,也不必像区间补抓那样放弃 etag 缓存。
- **老库里的订阅补成空串 = 不设下界,行为逐字不变**(`_ADDED_COLUMNS` 的 ALTER 默认值)。
  它们的存档早就抓完了,回头给它们钉一个下界只会在源站补发旧文时静默丢内容,挡不住
  任何已经发生的事。
- **没有发布时间的条目照收**:它身上没有任何「很旧」的证据,丢掉是不可恢复的静默损失,
  而日报那边本来就按「补录」接住这一档(只会出现一次)。
- **区间补抓(`scope.ranged`)不受这道闸限制**,那是用户点名要的那段日期——想把某个源的
  存档整段捞进来就走它,这是唯一的逃生口。
- 下界按 **Asia/Shanghai** 算,因为被比较的 `published` 就是 `fetching.parse_feed` 按这
  个时区格式化出来的;两头不同时区的话每天有 8 小时窗口会差一整天。
- **`sync._within_history` 只管往后,存量要单独清**(`scripts/feed_trim_history.py`,
  `scan` 只读 / `run --source <id|名字>` 真清)。RSS 这 9 个订阅是 2026-09-29 同一天建的,
  在下界这件事存在之前就已经把各自的存档拉进来了。清理**同时会给那个订阅钉上
  `history_floor`**——不钉的话下一次同步按空下界把整个存档原样再拉一遍,这一趟白做。
  顺序:备份 → 钉下界 → 删 feeds.db 行 → 删 vault md → `store.remove_missing_documents`。
  **feeds.db 要先删**:它是「要不要重新导出」的事实来源,后删会留下「文件没了、
  `exported_hash` 还在」那种既不重建也不存在的半状态。**被别的订阅共享的条目只摘归属、
  不删 `feed_items` 行**(聚合源和单号源常常收同一篇)。命中收藏、或条目被共享时默认
  拒绝执行,要 `--allow-favorites` / `--allow-shared` 显式放行。备份是
  `data/backups/feedtrim-*`(manifest + feed_items JSON + vault md 的 tar);kb.db 那一侧
  不用备份,它本来就是能从 vault 重建的索引。**清理口径和那道闸必须同一个**
  (`below_floor` 与 `_within_history` 互为补集,回归里对过),两处各判各的话,清掉的和
  以后拦掉的不是同一批。
  2026-10-01 已对 `Hugging Face Blog` 执行过一次(497 条,2024-04-10 ~ 2026-09-22),
  其余 7 个订阅扫出 1155 条待定 —— **低频长文那几个(Lilian Weng / Karpathy / Sam Altman)
  的存档很可能正是订阅它们的理由,不要默认清掉**。
- **另一条筛选口径 `--pending-translation`:清掉某个源还排在翻译队列里的条目**
  (`trim.pending_translation`,判据直接取 `translate.queued_sql()`,不在清理脚本里
  另写一遍 —— 两处各判各的话,清掉的和翻译那头还排着的不是同一批)。给**服务已经
  停掉**的源用:内容不会再更新,排着的那些译了也没人看,可它们每一轮都占着
  `translate.MAX_ITEMS` 的额度,把还活着的源挤到后面去。2026-10-08 对
  `HN Top 100 Blogs`(源站已停,订阅早已 enabled=0)执行过一次:284 条,队列从 896
  降到 612;那个源**已经译完的 196 条一个字没动** —— 它们不在队列里。
  **这一路不钉 `history_floor`**(`_cut_feeds` 认 `plan['mode']`):筛的维度不是
  日期,顺手钉一个就是做了没被要求的事 —— 这个源将来真要重新启用时,那条下界会把
  它自己的存档永久挡在门外。`--floor` 和它不能一起用(一个筛日期、一个筛队列,凑
  在一起没有定义),同时给直接拒掉。备份、维护锁、三步续跑、收藏护栏全部照旧走原来
  那条路,一行都没有另写。
  **这道互斥检查必须排在所有副作用之前,「续上没做完的那一份」也算副作用**
  (口径在 `cmd_run` 的第一句,不在 `_run_locked` 里)。它原来排在续跑后面,于是
  同一个订阅存在一份**已经备份、还没删完**的计划时(备份落盘之后进程被杀或 I/O
  异常,是这个脚本明确支持的恢复场景),带两个开关重跑会先把那份计划**续完** ——
  feeds 行、vault md、`documents`、全文索引和 `history_floor` 全动了 —— 然后才
  打印「不能一起用」并退 2:用户看到的是一句拒绝,加一篇再也读不到、搜不到的文章
  (2026-10-08 审查实测:退出码 2,而 `feed_row`/`file`/`documents`/`searchable`
  四处同时归零)。取锁同理算副作用:非法参数不该先去等满 `KB_MAINT_LOCK_WAIT`。
  **判据是「有旧计划时也不许动」,不是「提示对不对」** —— 原来那条回归只摆了
  「没有未完成计划」的局,那条路上两种实现都是绿的,所以 24 项全绿照过。
  回归在 `tests/test_feed_trim_pending.py` 的 `PendingTranslationTests`(9 条):口径与
  `queued_sql()` 逐字相同、队列里那条三处都没了而已译完的那条一个字没动、
  **已经钉着下界的订阅下界不变**(空下界的订阅看不出区别 —— 不管走哪条路写回去的
  都是空串,所以用例必须先钉一个)、两个开关同时给时一个字节都不动、队列为空时真的
  无事可做(连备份目录都不建)、**有一份没做完的计划时非法组合照样一个字节不动**
  (在 `_apply` 入口注入中断攒出那份计划,再带两个开关重跑:退 2、`state()` 逐字
  相同、下界还是空的,而且**计划留着**能接着续 —— 留着是「拒绝」和「删一半」的
  分界)。反向验证定点注入四版各红 1 条:新模式照样钉下界、筛选退回 `below_floor`、
  两个开关允许同时用、**把检查挪回 `_run_locked`**(红的是那四处从 1 变 0,正是
  审查报告里那份证据)。
  **有没做完的计划时,这一趟只续它、续完就结束,不许接着按这次的口径再开一轮**
  (`_run_locked` 里续跑那个 `if left:` 块末尾 `return 0`)。续跑原来只是这一趟的
  第一步:续完之后它照样往下走,按**这次命令行**上的筛选开关新建第二份计划再删
  一轮 —— 而 `cmd_scan` 给出的恢复提示是 `run --source N --yes`,**不带任何筛选
  开关**。于是「照工具自己的提示恢复一份 `--pending-translation` 的计划」=
  续完该续的那一份,紧接着按**默认的日期口径**又清一轮:已经译好、还读得到搜得到
  的旧文章连 feeds 行、中文 md、`documents` 和全文索引一起没了,`history_floor`
  也被钉上,而命令以 0 退出(2026-10-08 第 2 轮审查实测,独立复现三次;恢复时手动
  补上 `--pending-translation` 则只删该删的那一篇 —— 可那个选项压根不在提示里)。
  **日期口径自己撞不上这件事**(续跑已经把 floor 钉成同一个值,第二份计划筛出来
  是空的),所以它是新口径**不钉下界**带出来的,上一条那次挪位置管不着它:那条管
  的是非法参数组合,这条走的是一条完全合法、而且由工具自己打印出来的命令。
  判据是**授权的范围**:`--yes` 批准的是「把那份已经备份、删了一半的计划做完」,
  不是「再启动另一种清理」——**一次调用只做一件事**,要再清一轮就重新跑一次(那时
  没有未完成计划,走的是正常的确认流程)。这样续跑压根不需要「继承口径」或者
  「比对口径」:计划自带它要删的 keys 和 paths,`_apply` 认计划里的 `mode`,筛选
  开关只用来**建**新计划 —— 所以那条恢复提示不带开关本来就是对的,**光把提示写全
  修不了这件事**(续完之后那一轮照样会开)。提示里另外写出这份计划当初的口径
  (翻译队列 / 下界 X),那是人判断「要不要续」的依据。
  回归两条:**照提示恢复之后已译那篇四处都还在**(feeds 行、中文正文读得出来、
  `documents`、检索命中)、下界还是空的、**备份目录只有一个**(「没开第二轮」最直接
  的痕迹),外加提示里写出了口径那一条。反向验证定点注入两版各红 1 条:把 `return 0`
  退回旧的「重读 source 接着往下走」(红的是 `feed_row: True != False`,正是审查
  报告里那份证据)、只把提示退回旧写法(红的只有提示那条 —— 这正说明两件事得各自
  钉住,提示写全了也防不住误删)。
- **「给了 `--floor` 没有」问的是 `args.floor is not None`,不许问真值。** argparse
  本来就把两件事分得清:没写这个开关是 `None`,写了 `--floor ""` 是空字符串。拿真值
  判的话空串和「压根没给」长得一模一样,而 `cmd_run` 开头**两条判断都在这上面**:
  ①互斥检查放行,于是 `--floor "" --yes --pending-translation` 这条本该一个字节都不
  动的命令,把那份没做完的**日期**计划续完了(文章四处归零、`history_floor` 被钉上、
  退 0);②`norm_floor` 压根没被调用,于是**没有**未完成计划时单给 `--floor "" --yes`
  也不报错,而是悄悄按订阅自己那个默认下界新建一轮清理把旧文删掉,同样退 0
  (2026-10-08 第 3 轮审查用真 argparse + 真子进程复现,前者独立三次一致)。
  **空串不是一种顺手的写法**,它是 `--floor "$CUTOFF"` 而 `CUTOFF` 还没赋值这种最
  常见的 shell 事故 —— 而这是不可逆删除。口径收成两句:显式给了就必须过 `norm_floor`
  (`''` 不是 `YYYY-MM-DD`,它自己会拒),显式给了就算「给了日期」(于是和
  `--pending-translation` 互斥)。**三种显式写法都该报互斥那句话**,不是先被
  `norm_floor` 当成一个写错的日期拒掉:后者在「只修了 `norm_floor` 那一处」的实现上
  同样是绿的、也同样不动数据,只有文案能把两者分开。
  回归三处:非规范下界那张名单里加上 `''` 和 `' '`(判据是那一篇三处都还在、下界没动、
  **连备份目录都没建**)、互斥那条用例按 `'2026-08-01'` / `''` / `' '` 各走一遍(有一份
  没做完的计划、断言 `state()` 逐字相同且计划仍留着,外加报的是互斥那句话)、另有一条
  **走真 argparse**(`patch sys.argv` 调 `main()`):两种空写法都拒且一个字节不动,
  **不写这个开关的那条照旧清掉旧文** —— 后半句不能省,给 `--floor` 配一个 `default=''`
  同样会让「没提供」变成空串、把每一条普通的 `run --source N --yes` 都拒掉,而所有拿
  Namespace 喂 `cmd_run` 的用例(传的是 `floor=None`)照旧全绿。反向验证定点注入三版:
  只把互斥那道退回真值红 1 条(红的是 `2 != 0`,也就是那份计划被续完了)、只把
  `norm_floor` 那道退回真值红 4 条、两处都退回(第 3 轮被审的那一版)红 6 条 —— 其中
  那条互斥用例红的是 `{'feed_row': True, …} != {'feed_row': False, 'memberships': 0,
  'exported': False, …'documents': 0}`,正是审查报告里那份证据。
- **「共享条目只摘归属」要连文件和索引一起算,不能只在 `feed_items` 那一句上成立。**
  待删路径按「不在 `_shared_keys` 里」筛出来(`_live_paths` 再兜一道)。原来是拿整份待清
  集合去删 md 和 `documents`,而 `feed_items` 行连同 `exported_hash` 是留着的 —— 另一个
  订阅仍然列着这篇文章,点进去读不到、搜不到,**再同步也不恢复**(导出按
  `exported_hash==content_hash` 直接跳过它),2026-10-01 审查实测。**收藏保护也只对真
  要删的那些判**:共享条目压根不删文件,拿它把整趟拦下是假阳性。
- **下界先校验再用,非规范写法在备份和任何删除之前就拒掉**(`norm_floor`,`--floor` 和
  库里存着的那一份都过它)。比较是**字符串**比较:`2026-10-1` 既大于当天那篇
  `2026-10-01 08:00`(本该留着、实测三处全删),也大于第二天的 `2026-10-02`(本该收、
  实测被钉死的下界挡在门外)。少写一个零只是最顺手的那种写法,任意无效字符串同理。
- **删除分三步、每一步做完记一笔**(`progress.json` 落在备份目录里,`_apply` 按
  feeds → vault → index 往下做,各步幂等,重跑先把没做完的那几步续完)。feeds.db 是
  **先提交**的,后面 unlink 或 kb.db 清理抛异常时,重跑按 feeds 查出来的待清集合已经
  空了 —— 命令打印「无事可做」、以 0 退出,而 md 文件、`documents` 行和 FTS 命中全都
  还在,没有任何一条路把这趟清理做完(2026-10-01 审查两种中断各实测一次)。没做完的
  那一份 `scan` 会单独列一行;续跑同样要 `--yes`。
- **清理和同步、索引之间有一把跨进程锁**(`kb.maintenance.maintenance_lock()`,
  `sync._save_result` 的存盘整段、`sync.export` 整段、索引的整趟扫描写库、条目化的
  就地入库和提取的 tag 回写都认它 —— 那把锁本身见下一节「kb.db 的维护互斥锁」)。开工时问一次管道状态
  只能回答"那一刻忙不忙",答不了"接下来会不会有人起跑":备份期间起跑的一轮同步能拿着
  **空下界的旧快照**在清理收尾之后存结果,刚删掉的旧文连文件带归属一起回来
  (2026-10-01 审查实测重新入库 1 条)。导出那一侧是另一个形态 —— 清理删掉行之后它按
  自己那份行快照照样把文件写回去,而 `feed_items` 里已经没有这一条,vault 里从此躺着
  一篇谁也管不着的旧文(索引照样收,下一次清理也找不到它)。
- **锁之外还要「下界现读」**(`sync._stored_floor`,`_within_history` 用它而不是快照里
  那一份)。两道各管一段:锁管住持锁双方的交错,现读连不持锁的旁路一起挡住 —— 缺任何
  一道,上面那条都会按原样复发。
- **问不到管道状态一律拦下,只有连接被拒才放行**(`_pipeline_busy` 返回拦下的原因)。
  连接被拒 = 服务没起 = 没有管道在跑,这是唯一能证明空闲的那种;超时、HTTP 错、回包不
  是 JSON 都只说明问不到,而这是不可逆删除,问不到就别猜(原来这三种一律当空闲放行)。
  真正的互斥是那把维护锁,这里只是**早一道**:管道正忙时当场说清楚,而不是让人对着
  一个一声不响等满 `KB_MAINT_LOCK_WAIT` 的终端等下去。
- **`--source` 是纯数字时只按 id 查,不许退回名字**(`trim.find_source`)。原来是
  `id=? OR name=?` 再 `fetchone()`:一个**名字恰好叫「62」**的订阅会抢在 id=62 前面被
  取走 —— 实测清掉的是那个名叫「62」的订阅,真正点名的 62 号一个字节没动,而且是确定性的
  (2026-10-01 第 2 轮审查实测)。**名字命中多条时拒绝执行、要求改用 id**:注册表允许重名
  (同名不同链接是正当形态),挑哪一条都可能是错的那一条,而这是不可逆删除。
- **续跑不是「接着执行上次批准的那件事」,收藏那道护栏要按此刻的事实再查一遍**
  (`_apply` 按 `_live_paths` 算出此刻真要删的那几篇再 `_favorites`,续跑那一趟由
  `_run_locked` 调它 —— 整段在维护锁里,所以 `cmd_run` 只剩取锁那几行)。它原来排在新计划
  的后面,续跑从旁边绕过去了:失败之后用户把那篇还读得到的文章收藏起来,重跑(没加
  `--allow-favorites`)照样把文件、`documents` 和收藏一起删掉,退出码还是 0(同轮实测)。
  拦下时计划留在盘上,带 `--allow-favorites` 能接着续。
- **备份目录要原子地占一个唯一名字**(`_backup` 走 `tempfile.mkdtemp`,前缀带订阅 id)。
  原来是「slug + 秒」加 `exist_ok=True`:两个同名订阅在同一秒里清理会复用同一个目录,
  manifest / `feed_items.json` / md 压缩包 / `progress.json` 全被后一个覆盖 —— 前一个清掉
  的内容从此既不在库里也不在备份里,它那份没做完的计划也一起没了,重跑只会说「无事可做」
  (同轮实测)。slug 截断和非字母数字归一化还会让**不同**名字撞到一起,所以唯一性不能靠
  名字:`mkdtemp` 由内核保证这个目录是我们新建的(`_plans()` 的 glob 照旧命中)。
- **收藏那道护栏必须和删除在同一个写事务里**(`_apply` 在 kb.db 上 `BEGIN IMMEDIATE`,
  最终复查、unlink、`remove_missing_documents` 全在这一条连接的这一个事务里)。原来是
  「查完就关连接」,从那一刻到真正删除之间还有确认、备份打包、进度落盘、逐个 unlink
  一整段:用户在这段时间里收藏一篇还读得到的文章(整篇或带备注的片段),收藏 API 返回
  200、库里真有那一行,随后 `documents` 行一删、`favorites` 的 `ON DELETE CASCADE` 把它
  连同刚写的备注一起带走,命令还以 0 退出(2026-10-01 第 3 轮审查实测,整篇和片段各
  复现三次)。**索引能从 vault 重建,收藏和备注不能** —— 备份里压根没有它们。
  `BEGIN IMMEDIATE` 当场拿到写锁,于是这期间的收藏写入只有两种结局:赶在取锁之前提交
  (那就会被这次复查看见、把这一轮拦下,计划留着可续),或者等/报错
  (`store.connect` 的 `timeout=30`)—— 不再有「成功了又被静默删掉」这一档。
  **`reg.trim_lock()` 管不了这件事**:收藏 API 不认它,只有 kb.db 自己的写锁挡得住。
  两件配套的事:①**删索引必须用持锁那条连接**(`_drop_index` 收外部 conn),另开一条
  去删就是跟自己抢写锁、当场自锁;②`--allow-favorites` 显式放行时,把要毁掉的那几行
  (备注、片段锚、状态、行动卡)另存 `favorites.json` 进备份 —— md 压缩包重建不出它们。
  开工前那次 `_favorites` 留着,但它只是「早一点给提示」(省掉建备份目录),不是闸门。
- **没有旧文可清 ≠ 不用钉下界**。空集合提前返回的话这一趟什么都没改变、命令还以 0 退出,
  而那个老订阅(空下界)等源站下次补发 7 月的东西照样整批收(2026-10-01 审查实测)。
  所以 `--yes` 确认过就把合法下界存下来;**没带 `--yes` 一个设置都不改**(退 1 并打印
  要做什么)。已经钉着同一个下界时才是真的「无事可做」。
- **测试样本的发布日期必须跟着今天走**(`tests/test_feed_sources.py` 的 `_FRESH`/`DAY`)。
  写死 `2026-09-28` 的 feed 样本过几天就被这道闸挡住,红的却是一堆跟历史下界毫无关系
  的用例。回归 7 条(`test_feed_sources.py`):首次抓取只收窗口内(含边界当天)、**第一次
  之后照样受限**、钉死的下界不吃停更恢复、空下界不受限、无日期照收、区间补抓放行、改
  链接重算下界。反向验证定点注入过三版:整道闸去掉红 2 条、改成滑动窗口红 2 条、只拦
  首次抓取红 1 条。
