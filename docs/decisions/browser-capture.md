# 从已打开的浏览器标签补正文

人已经在浏览器里打开了那篇文章,由他在那个标签上点一下扩展,正文补回原条目。
这一侧的界面是主页面**左侧滑出的采集抽屉**(外壳 `capture_drawer.js`、状态机
`browser_capture.js`);怎么装、怎么用写在 `docs/browser-capture.md`。

**入口有两处,都是逐条的,而且叫同一个名字**:
- 「我的订阅」展开来源文章列表后、条目页脚上那个小文字链「从浏览器采集」
  (`source_reader.js`,只在 `body_from_link` 为真时露面);
- 「问题与待办」详情动作区里那颗**「从浏览器采集」**(正文那三档,排在「手动补正文」
  **前面**且是那两者里的主项)—— 理由见下面那条硬约束。
抽屉**只能从这两处开**(没有自己的地址了);原来那个独立页 `/browser-capture?item=<key>`
连同它的路由一起退役,理由见下面那条硬约束。

## 硬约束

- **这几块界面不加次级标题,也不描述屏幕上看得见的东西。** 抽屉和扩展弹窗原先每块都
  顶着一行标题(「这次补哪一篇」「这篇文章正在等待的采集」),每个输入框下面还跟一句
  说明它行为的小字(「默认匹配原网址」—— 那一栏本来就是预填好的),建议里还逐颗复述
  下面排着的按钮(「用『从浏览器采集』最省事,否则试『换链接』」)。**留下来的只有屏幕
  上看不出来的那些**:15 分钟的有效期、「继续导出与索引」那一下的真实射程、再试一轮
  会不会还是同一个结果、这一下要不要花模型的钱。
  **两处例外不许删**:①「继续导出与索引」那段射程必须和确认框、回执三处对得上
  (`tests/test_browser_capture.py` 钉着 `条目化提取不在这一步`);②「从浏览器采集」
  旁边那句前提(文章开着 + 扩展装好)—— 那是点下去之前唯一能知道它为什么不动的地方
  (`tests/intake_diag_probe.mjs` 钉着 `开着` / `扩展` / `手动补正文` 三个词)。

- **「从浏览器采集」和「手动补正文」是一道闸上的一对,不许一颗开一颗关。** 它们写的是
  同一列、过的是同一份准入(`_admit_body`),所以「问题与待办」里这两颗按钮共用后端那
  一个答案(`intake_diag_api.item` 的 `can_paste` = `permits_link_body`,「换链接」也在
  同一道闸上)。开着的那一颗点下去只会在服务端被拒,而**屏幕上看不出是为什么** ——
  那正是这块面板最该答出来的事。禁掉时那句理由也只有一份
  (`source_types.link_body_refusal`,**空串 ⇔ 许可**,前端一个字都不自己编),而且
  **既进 `title` 也就地显示一行**:`title` 在触屏上压根出不来,「按钮灰着、旁边什么都
  不说」正是人会反复点它的形态。人手敲 `/browser-capture?item=<key>` 绕过界面时,
  `target()` 那句拒绝也带着同一句理由。
  **顺序和主次是约定,不是排版**(`lanes.Lane.exits` 的顺序就是屏幕上的顺序):会落到
  正文那三档的多半是「页面上没有识别出正文,可能需要登录或由脚本渲染」「这一页要求先
  完成验证或登录」「HTTP 403」—— 那些页人**已经在浏览器里开着、登录态也在**,从那个
  标签抓比手工全选复制粘贴顺得多,也不容易粘坏。读不出主次,人就会先去点那颗兜底的。
  **批量栏里不给这一颗**:一个浏览器标签就是一篇文章,勾 20 条采不了 20 篇。
- **交接只带 key,「是不是这一世」由这条路自己认。** 面板上那颗按钮只拼
  `/browser-capture?item=<真实 feed_items.key>`(和 `/body`、`/requeue` 发出去的是同一个
  值,不是展示编号),**刻意不捎一份 `life` 过去** —— 身份这件事由 `_same_life`
  (`fetched_at` + `content_rev`)一处回答,而面板自己那几个写入口按 `feed_items.life` 认
  (`kb.intake_diag.warrant`)。两份判据的洞不一样(见下面 `_same_life` 那条和
  `intake-diagnostics.md` 的「还没做的」),**在交接处再判一遍只会多出第三份口径**;
  判错的方向两边都是安全那一侧(认不出来一律当「没有回执」)。详情抽屉把
  `fetched_at` 和 `content_rev` 两个值如实摆在详情末尾那块灰框里,人对着它就能看出
  「这一世变没变」。
- **准入判据只有一份,在服务端。** 「这一次写不写得了」由 `kb/browser_capture` 的
  `_admit_body`(正文够不够)、`_admit_page`(是不是指定的那一页、来源允不允许、请求
  还在不在)、`_admit_item`(条目还是绑定的那一版吗)回答;`precheck` 和 `save` 调的是
  **同一组**。**扩展一处都不判** —— 它只负责展示结论。
  事故形态(实测三种):扩展自己 `new URL()` 比网址、自己数原始字符数、信上一次刷新
  下拉时缓存的那份清单,于是「服务端会拒」的三类都要等人**把整篇文章读完、点下
  提交**才被 409 拒 —— 白读一整页。其中网址带中文那一类是
  **每一次都失败**,怎么重来都一样。往扩展里补一张规范化表、再抄一遍去重算法只会
  开出第四第五个实例,所以判据整个退回服务端。
- **`page_url()` 是文章网址的唯一规范形。** 口径跟着浏览器的 `new URL().href`:
  scheme / 主机小写、非 ASCII 主机转 punycode、默认端口去掉、非 ASCII 与不安全字符
  百分号编码、**已有转义原样透过**、点段折叠、片段丢掉。空 query(末尾那个 `?`)两边
  都丢 —— 比浏览器宽一格,宽的那头只会多认一个同页地址。**不许在别处再写一份,也
  不许拿原始字符串比**。`%2e` 这种编码过的点段不折叠(浏览器会),后果止于「人自己
  填了个点段地址」→ 读之前就被告知网址不同,可改可重发。
- **拒绝那一刻手上的真实网址不许丢 —— 出路开在待办那一行里。** `_admit_page` 判出
  「不是这一页」时把浏览器交回来的规范网址记进 `intent['seen_url']`(`_seen_elsewhere`,
  **只在 pending 的那个上记**),采集抽屉把它摆出来并给一颗「改用这个地址」—— 点下去走的
  是同一个 `create`(旧待办由服务端顶掉),不是先取消再发起。
  事故形态:站点按浏览器语言跳转(`openai.com/index/x` 在中文浏览器里落到
  `/zh-Hans-CN/index/x`),这一类订阅**每一次**都被拒,而人只看到一句「网址不同」;
  原来那句拒绝语指向的操作(「回知识库核对最终网址并重新发起」)在页面上**当场做不到**
  —— 有待办时那一栏和「发起」都是禁用的(上面那条约束要的就是这个),得先在下面取消
  待办。**记下来不等于放行**:原请求照旧只写得了它绑定的那一页,改用要人点,所以
  「扩展不会用另一篇文章静默覆盖」一个字都没松。
  **不许顺手剥掉语言前缀来「认成同一页」**:那是站点自己的约定,`/zh-Hans-CN` 在别的
  站完全可能是路径的真身,剥错一次就是把**另一篇**的正文写进这一条 —— 而 `page_url`
  那份口径的底线正是「宽的那头只会多认一个同页地址,不会把另一篇认成这一篇」。
- **`precheck` 一个字都不落库,也不顶替事务内那一道。** 真正的互斥待在 `save` 那条
  UPDATE 自己的 WHERE 里(key / 来源 / 原网址 / 正文指纹 / 修订号 / 非 X 观点 / 未排除,
  `rowcount != 1` 即拒);`precheck` 和 `save` 开头那次 `_refresh_status` 都只是**早一道**。
- **采集抽屉那一栏网址:人动过就不许被轮询填回去。** 自动填入只认「框里还是上一次
  自动填进去的那一份」(`autofillUrl`);已有请求时强制显示服务端记下的那一份并禁用。
  事故形态:本页每 2 秒重画一次,原来的判据是「框是空的就当还没填过」—— 人清空、
  切出去复制浏览器里真正的地址、切回来一粘贴,贴的那一截接在被填回的原网址后面,
  拼成一个谁也打不开的地址(实测 2.6 秒后变回原值),之后扩展只会一直说「当前标签
  网址与指定文章不同」。**两个触发点**:平常那一次,和点过「重新采集正文」进草稿态
  之后 —— 这道闸不能只挡首次渲染。
- **回执按文章恢复,不靠标签的 `sessionStorage`。** 服务端按文章 key 返回当前待办和
  最近一条有效审计回执(`browser_capture_audit`),关页、换标签、超过 15 分钟、服务
  重启之后都找得回来。已保存请求无论命中内存还是从审计恢复,都走 `saved()` 同一套
  校验(来源、排除状态、修订号、正文摘要);旧回执失效时隐藏成功区、禁用继续按钮
  并给出原因。
- **回执记的是「哪一世」的那篇文章,认不出来就当「没有回执」。** `item_key` 按网址
  算:存量清理(`scripts/feed_trim_history.py`)删掉一条、下一轮又从同一个链接收回来,
  key 一个字都没变,而库里那是另一行、另一份正文。判据只有 `_same_life` 一份 ——
  `item_fetched_at`(只在 INSERT 时写,换内容的几个写入方一个都不碰它)+ `content_rev`
  不许倒退(一行的生命里只增,新插进来的从 0 起),两条各补对方的洞:同一秒里删掉又
  收回来时 `fetched_at` 会撞上(它只记到秒),那一下由倒退的 `content_rev` 认出来。
  **认不出来一律当「没有回执」,不是「正文被改过」**:后者会在那篇文章的采集抽屉上
  常驻一句假红字,还连带藏掉回执区、禁掉继续处理那颗按钮,而重抓一次也去不掉(审计
  那一行记的是上一世,怎么比都不等)。老库里没记身份的回执行同样按「没有回执」办。
  新回执落库时顺带收掉这个 key 上前一世的审计行,判据**特意比 `_same_life` 窄**(只
  认身份那一半),这样删掉的一定是认领不了的行。
- **同一文章只留一个 pending。** 在锁内比正文版本、来源、原网址和指定最终网址:
  匹配就复用原请求和有效期,不匹配把旧的标 `superseded` 再建新的。额度只算 pending
  (`MAX_PENDING`),保存 / 取消 / 陈旧不占。不同文章各自排队。
- **额度撞满的那一下不拒人,顶掉最老的那个。** 取消的出口只开在**各自那篇文章的
  采集抽屉**上,而额度是全局的:拒了就得让人挨个翻完那 100 篇才发得出第 101 次。等待
  中的请求手上没有任何产物(正文还没读),顶掉最老的(它也最接近过期)只值一次重新
  点击,扩展那边收到的话正是「被新的采集请求替代」。**已保存的回执压根不在池子里**,
  顶不掉。
- **进入「重新采集」不撤销已保存的正文和回执**,退出也不清审计;只有再次预览确认
  提交才替换。
- **「继续导出与索引」那颗按钮的射程只有 `CONTINUE_STAGES`,而且页面、确认框、回执
  三处的话必须跟它对得上。** `extract`(条目化提取)**不在里面**:它的队列
  (`kb.extract.pending_docs`)压根没有来源参数,按全库取数 —— 一颗开在某一篇文章页上
  的按钮不该顺手买下全库那一轮模型调用(原来的话写着「该来源其他待办」,而实际射程
  是全库)。`export` 这一段认 `crawl_filter`(只有这一类来源),`index` 是整个 vault 的
  增量比对、不调模型,这两件事页面上明写着。要提取就到同步中心起跑弹窗里勾;这一篇的
  `extract_stale=1` 还在,下一轮同步自己会重新提一遍。
- **`fulltext_at` 一写上,这条就退出自动补抓队列**(`fulltext.queued_sql()` 要求它为空)。
  好处是刚补的正文不会被自动补抓再盖一遍;代价是万一采到的是一张过得了去重门槛的
  会员说明页,出路只剩人工「重新采集正文」。
- **`api.js` 住在扩展目录**(`kb/static/browser-extension/knowbase-capture/api.js`),因为
  下发的 ZIP 要带上它、扩展取不到 `kb/static/js/` 下的文件。页面在 `ui.js` **之前**加载
  它;全站十来个脚本的 `apiFail` / `toastIfFail` 都是它那一份。
- **扩展的 `popup.css` 另抄一份色板**(扩展装在浏览器里,取不到 `kb/static/css/base.css`)。
  改 `base.css` 的 `:root` 色值要连它一起改 —— 两份文件各写了一行互指注释(`base.css`
  那行就在 `:root` 上面)。CLAUDE.md 的「视觉语言」里数的那**三处**是脱离 kb-web 的
  独立产物,各抄色值 + 箭头几何;popup 只抄色板、没有箭头,所以单记在这一份里。
- **`plainUrl()`(两处,各三行)只是显示** —— 把百分号编码过的中文地址显示成人能对着
  地址栏核对的样子。它不是判据,回填给服务端时会被重新规范化成同一份。

- **「我站着这一页,此刻能做什么」只有 `here()` 一份口径,popup 里也只有一块。**
  扩展开起来就问这一次(`POST /api/browser-capture/here`),服务端答四档
  (`fill` / `absent` / `complete` / `refused`)连同那句给人看的话;popup 那张
  `PLANS` 表只把它摆成按钮,**一个字都不自己编、一处都不自己判**。
  原先这里是两块:一块问 `/api/grab/state`「这一页在不在库里」,另一块是「补回哪个
  待办」的下拉框。**两块必须并成一问,理由不是好看**:两边查条目的方式不一样
  (`grab.normalize` 一份规范形 vs `here` 两份),于是同一页能同时得到「不在库里,
  收录吧」和「在库里」两个答案 —— 屏幕上互相打脸,而点下收录就是库里多一行。
  - **下拉框连同「从清单里挑一个待办」整套退场。** 「这一页是哪一条」地址栏里就
    写着,让人再答一遍的代价是跨三个界面走七步(知识库面板 → 补抓页复制密钥 →
    核对最终网址 → 发起待办 → 回文章标签 → 挑出刚才那个 → 读取)。而那个下拉框
    信的是上一次刷新时缓存的清单 —— 那正是 `precheck` 当初要补的事故形态。
  - **待办没被取消,它退到了幕后。** `fill` 那一档由 `here()` 自己 `_create`,于是
    `precheck` / `save` 那一整套准入、CAS、回执与审计**一个字都没改**;新增的只有
    「谁来建待办」。`_create` 是从 `create` 里拆出来的**同一段**(复用、顶替、额度
    那三段),两个发起方共用 —— 各写一遍的话「同一篇文章会不会同时挂两个待办」就有
    两个答案。
  - **只在正文还欠着的时候自动建**(`_OWED` = `fulltext._eligible()` 原样转手 +
    `fulltext_at=''`,正是三档正文待办的共同前缀,不是第四份口径)。正文已经齐的那
    一条照旧要人在采集抽屉上明说「重新采集正文」:那是另一件事(「我手上这份是错的」),
    它自带警示和回执,挤成同一颗按钮会让人分不出点的是哪件。顺带也挡住一类浪费 ——
    随手逛过的页面如果也建待办,全局额度(`MAX_PENDING`)会被它们占满,而它们手上
    没有任何产物,真要补正文的那一条反倒被顶掉。
  - **按两份规范形找那一行**(`_page_aliases`:`page_url` 和 `grab.normalize`)。库里
    那一行的 `url` 是**收它的那条路**存下来的 —— 订阅类原样存 feed 给的地址,手动收录
    存的是去掉 `utm_*` 之后那一份。只按一份问,另一条路收的那一半永远答「不在库里」,
    而那一句的下一步是收录。**这不是模糊匹配**:两个候选都是这一页自己的规范形,一个
    字符都不猜;**绝不剥语言前缀、也不读网页自报的 canonical**(剥错一次就是把另一篇
    的正文写进这一条)。
  - **`elsewhere` 是承重的,不是提示。** 它交回「等着的、但指着另一个地址的那些待办」。
    事故形态:站点按浏览器语言跳转(`openai.com/index/x` → `/zh-Hans-CN/index/x`),
    人从采集抽屉发起的待办指着前者、浏览器停在后者,按地址一问这一页**确实**不在库里 ——
    只凭这一句请他收录,库里立刻多出第二行同一篇文章,两行各有各的 key、各导出一篇 md。
    把那个待办摆在他眼前、给一颗「改用这一页的地址」(`/here/adopt`,和采集抽屉上那颗
    「改用这个地址」同一个 `create`),他一眼就看出是同一篇。**要在建完待办之后才算它**
    (`answered()` 里那一句):`_create` 会把同一条目上指着别处的旧待办标成
    `superseded`,先算就会把刚作废的那个摆出来请人改用,而点下去只会被拒。
    `elsewhere` 过的是 `_pending()`(和 `/pending` **同一段**),所以条目在这期间被改过、
    被排除、被删掉的照旧当「没有待办」—— 自己再过一遍 `_intents` 就会漏掉那一道。
  - 共用的还有两样:那条连接和配对密钥(`call()`)、在标签上读一次正文(`extractFrom`)。
    原先还有第三样 —— 预览区和那道「我已核对」,由 `collecting` 标记决定提交走 `/upload`
    还是 `/from-page`;那块界面撤掉之后(见下面那条),**分路改由 `situation` 自己答**
    (`fill` → `read`/`/upload`,`absent` → `collect`/`/from-page`),少一个要和服务端那
    一答保持同步的本地标记。收录那一头自己的硬约束在 `link-grab.md`,端点是 `/api/grab*`。
  - **配对密钥用一次不依赖当前标签的调用验**(`/pending`)。拿 `/here` 验不行:人在扩展
    管理页或知识库页面上配对时 `currentTab()` 先拒,于是密钥对不对一个字都没验、还因为
    没抛出而被当成连上了,密钥照旧存进本地。`/pending` 因此不是死端点 —— 它是那道
    连接自检。
  - **提示语指向的按钮必须真的在**(`extract.js` 那两句)。按钮改名时它要跟着改 ——
    改名之前那两句写着「读取所选文字」,而弹窗上已经没有这颗了。

- **补抓页退役成抽屉,而抽屉关掉要真的停、重开要能用。**
  原来那个独立页从「我的订阅」或「问题与待办」点进去要跳出当前页面,补完正文还得自己
  找回刚才看的那一条。现在它贴在左边,底下那一页原样留着。搬家牵出三件**回退之后界面
  上一点都看不出来**的事,各有一条红(`tests/capture_drawer_shell.mjs`):
  - **关掉要把轮询一起停了**(`stopCapture`:清 timer **并且** `loadVersion += 1`)。
    独立页关掉标签就什么都没了;抽屉关掉之后底下那一页还活着,`setTimeout` 链不停就会
    一直每 2 秒打一次 `/target/<key>`,开过几次之后变成几条并行的链。只清 timer 不够 ——
    已经发出去的那一次会在自己的 `finally` 里再排下一轮。
  - **建了就 append、关了就 remove,不是切 `display`。** `workspace.js` 的
    MutationObserver 只盯**页面初始那批**浮层的 style 变化,后来挂上去的那个改 display
    它看不见;而 body 的 childList 它盯着(先例是 `egress.js`)。焦点陷阱、inert、Esc
    关闭链全靠 `syncOverlays`,所以 `#cap-drawer` 也进了它的收集口径,并在打开时注册
    `overlayClosers['cap-drawer']`。**Esc 不自己再挂一个 keydown**:两处都关的话,叠在
    抽屉之上的确认框按一次 Esc 会连抽屉一起带走。
  - **因此每次打开拿到的是一套全新元素,事件必须重绑。** 那个「只绑一次」的标志会让第
    二次打开起每一颗按钮都没有监听器:界面完整、数据也在、点下去什么都不发生。同理
    **模块级状态要跟着条目换** —— `urlAuto` 留着上一篇的网址时,这一次 `autofillUrl`
    会被自己那道「人动过就不填」的闸挡掉(新框是空的,和基准对不上),网址栏**空着**,
    人点发起就是拿一个空地址去发。
  - **DOM 由 JS 建,不写进 `index.html`**(那份已经顶着 700 行上限),**每个 id 带
    `cap-` 前缀** —— 独立页那会儿用的是 `title`、`message`、`create`、`pending` 这类
    裸名字,搬进主界面就会跟别人撞上,而 `getElementById` 撞车不报错,只是安静地拿到
    另一个元素。样式同理**整份锁在 `#cap-drawer` 里**:那份 CSS 原先写的是裸标签
    (main / header / h1 / button / input / details / summary),搬进来会命中全站。
  - **首次使用那一块要摆在看得见的地方。** 没采成过时它在最上面且摊开,采成过之后收进
    底部折叠块 —— **位置和折叠状态一起变**。只把 `<details>` 默认打开的话它还是在整屏
    最下面,而扩展没装、密钥没配的人恰恰最需要先看到它:那一栏网址和「发起采集」对他
    毫无意义,他只会点下发起,然后等一个永远不来的采集。判据是
    `GET /api/browser-capture/setup` 的 `used_before`(审计表里有没有过一行 —— 那张回执
    只有扩展真的采成一次才写得进去),**边界落在安全那一侧**:配对了、还没采成过的人
    照旧看到摊开的那一块,而他确实还没走完首次流程。
  - **装扩展给的是仓库里那个目录的绝对路径,不是只给一个 ZIP。** 它是「加载已解压的
    扩展程序」装的,而仓库里本来就躺着那份 —— 下载再解压等于把同一份代码在磁盘上放两
    处,之后改了代码,装着的还是解压出来那一份,**而人不会知道自己装的是旧的**。指到
    仓库里这一份,改完点一次「重新加载」就生效。ZIP 留着,给「浏览器不在这台机器上」
    那种情形。

- **预览区和那道「我已核对」撤了:读完直接写进去。**(产品决定。)人就站在那一页上,
  他比屏幕清楚自己要的是哪一篇,再把同一份正文塞进 450px 宽的弹窗里请他重读一遍,
  **拦不住任何服务端拦不住的东西**。
  - **撤掉的只有事前那一问,准入一道都没少**:长度(`_admit_body`,按行去重之后的
    字数)、是不是指定的那一页(`_admit_page`)、条目还是绑定的那一版吗
    (`_admit_item`),连同 `save` 那条 UPDATE 自己 WHERE 里的 CAS,全在服务端原样判。
    `precheck` 也留着 —— 它还答出那个字数,写完要摆给人看。
  - **`/upload` 的 `confirmed_complete` 跟着撤。** 界面不再问人,却照旧报一句「人已经
    核对过了」,那是**扩展签给自己的证词**;何况它从来挡不住非界面调用,随手填个 `true`
    就过。回归钉住「把它加回来会被 422 拒掉,而不是被当真」
    (`test_a_self_signed_confirmation_field_is_refused_not_believed`)。
  - **`body_provenance.confirmed` 改成如实记。** 它记的是「有没有人逐字看过这份正文」:
    扩展那两条路(`browser_article` / `browser_selection` / `browser_grab`)现在记
    `False`,**只有「手动补正文」那条还记 `True`** —— 那一段是人自己粘进来的,断言它
    属于这篇文章的就是他。两者在知识库里要分得出来,这就是分得出来的地方
    (红:`test_who_vouched_for_this_body_is_recorded_as_it_actually_happened`,正反都钉)。
  - **代价是真的,知情留下**:登录墙、摘要页只要过得了那道去重 400 字符就会被写进去,
    原先指望那道勾挡一手。出路是事后的 —— 写完就把标题和字数摆出来,不对就到知识库里
    那一条上「重新采集正文」。`fulltext_at` 一写上这条就退出自动补抓队列,所以**那是
    唯一的出路**。
  - **发起采集时可以顺带打开那一页**(抽屉上那个勾)。`window.open` **先开再发起** ——
    一旦离开这次点击的同步调用栈就不再算用户手势,会被弹窗拦截挡掉。发起失败时多开一个
    标签不要紧:勾它的意思本来就是「我这就要去那一页」。
  - **改了扩展就升 `manifest.json` 的版本号**,并且**版本号摆在弹窗头部**。这个扩展是
    「加载已解压的扩展程序」装的,改了代码要人去扩展管理页点一次「重新加载」——
    装的是哪一版只有那里看得出来,没有它,「我到底重载过没有」只能靠猜。

## 知情的代价

- 抽屉开着时固定 2 秒轮询,切到后台也不停(关掉就停);每轮 `item_state()` 开三次数据库连接。
- `save()` 持 `_lock` 期间执行 `BEGIN IMMEDIATE`,库被别的进程占着时 `item_state` /
  `pending` 一起等。TTL 内最多 100 个 pending,影响有界。
- `precheck` 让每次读页多两次本机往返,换的是「不让人白读一整页」。
- 请求队列在单个 web 进程的内存里,不支持多 worker;重启丢未完请求,不丢已保存
  正文和审计回执。
- `save()` 不取维护锁,与手动收录 `grab_store.replace()` 对称 —— 判据待在 UPDATE
  自己的 WHERE 里,见元规则「并发与数据安全」。
- 审计表每成功补抓一次长一行(一次人的动作),前一世那些在下一次补抓时收掉,没有
  按时间的留存策略。**同一秒里删掉又收回来、而且两世的修订号正好对齐**的那一档,
  旧回执仍可能按它自己的请求 id 读出来 —— 那时两份正文的摘要也相同,所以它说的话
  不假;那一页上显示的始终是这一世最后那张。
- 「继续导出与索引」不买提取,所以**图鉴条目要等下一轮同步**(或人自己到同步中心勾
  一次)。换来的是:这颗按钮的射程和钱都可预测。
