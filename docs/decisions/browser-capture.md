# 从已打开的浏览器标签补正文

人已经在浏览器里打开了那篇文章,由他在那个标签上点扩展、预览确认,正文补回原条目。
页面是 `/browser-capture?item=<key>`,怎么装、怎么用写在 `docs/browser-capture.md`。

**入口有两处,都是逐条的**:
- 「我的订阅」展开来源文章列表后、条目页脚上那个小文字链「从浏览器补抓」
  (`source_reader.js`,只在 `body_from_link` 为真时露面);
- 「问题与待办」详情动作区里那颗**「从浏览器采集」**(正文那三档,排在「手动补正文」
  **前面**且是那两者里的主项)—— 理由见下面那条硬约束。
`/browser-capture` **本身还没有一个正经的导航入口**(只能从这两处点进去,或者记住
地址),见「还没做的」。

## 硬约束

- **「从浏览器采集」和「手动补正文」是一道闸上的一对,不许一颗开一颗关。** 它们写的是
  同一列、过的是同一份准入(`_admit_body`),所以「问题与待办」里这两颗按钮共用后端那
  一个答案(`intake_diag_api.item` 的 `can_paste` = `permits_link_body`,「换链接」也在
  同一道闸上)。开着的那一颗点下去只会在服务端被拒,而**屏幕上看不出是为什么** ——
  那正是这块面板最该答出来的事。禁掉时那句理由也只有一份
  (`source_types.link_body_refusal`,**空串 ⇔ 许可**,前端一个字都不自己编),而且
  **既进 `title` 也就地显示一行**:`title` 在触屏上压根出不来,「按钮灰着、旁边什么都
  不说」正是人会反复点它的形态。人手敲 `/browser-capture?item=<key>` 绕过界面时,
  `target()` 那句拒绝也带着同一句理由。
  **顺序和主次是约定,不是排版**(`lanes.Lane.exits` 的顺序就是屏幕上的顺序):会落到
  正文那三档的多半是「页面上没有识别出正文,可能需要登录或由脚本渲染」「这一页要求先
  完成验证或登录」「HTTP 403」—— 那些页人**已经在浏览器里开着、登录态也在**,从那个
  标签抓比手工全选复制粘贴顺得多,也不容易粘坏。读不出主次,人就会先去点那颗兜底的。
  **批量栏里不给这一颗**:一个浏览器标签就是一篇文章,勾 20 条采不了 20 篇。
- **交接只带 key,「是不是这一世」由这条路自己认。** 面板上那颗按钮只拼
  `/browser-capture?item=<真实 feed_items.key>`(和 `/body`、`/requeue` 发出去的是同一个
  值,不是展示编号),**刻意不捎一份 `life` 过去** —— 身份这件事由 `_same_life`
  (`fetched_at` + `content_rev`)一处回答,而面板自己那几个写入口按 `feed_items.life` 认
  (`kb.intake_diag.warrant`)。两份判据的洞不一样(见下面 `_same_life` 那条和
  `intake-diagnostics.md` 的「还没做的」),**在交接处再判一遍只会多出第三份口径**;
  判错的方向两边都是安全那一侧(认不出来一律当「没有回执」)。详情抽屉把
  `fetched_at` 和 `content_rev` 两个值如实摆在「这一条的身份」里,人对着它就能看出
  「这一世变没变」。
- **准入判据只有一份,在服务端。** 「这一次写不写得了」由 `kb/browser_capture` 的
  `_admit_body`(正文够不够)、`_admit_page`(是不是指定的那一页、来源允不允许、请求
  还在不在)、`_admit_item`(条目还是绑定的那一版吗)回答;`precheck` 和 `save` 调的是
  **同一组**。**扩展一处都不判** —— 它只负责展示结论。
  事故形态(实测三种):扩展自己 `new URL()` 比网址、自己数原始字符数、信上一次刷新
  下拉时缓存的那份清单,于是「服务端会拒」的三类都要等人**把整篇文章读完、核对完
  预览、勾完确认、点下提交**才被 409 拒 —— 白读一整页。其中网址带中文那一类是
  **每一次都失败**,怎么重来都一样。往扩展里补一张规范化表、再抄一遍去重算法只会
  开出第四第五个实例,所以判据整个退回服务端。
- **`page_url()` 是文章网址的唯一规范形。** 口径跟着浏览器的 `new URL().href`:
  scheme / 主机小写、非 ASCII 主机转 punycode、默认端口去掉、非 ASCII 与不安全字符
  百分号编码、**已有转义原样透过**、点段折叠、片段丢掉。空 query(末尾那个 `?`)两边
  都丢 —— 比浏览器宽一格,宽的那头只会多认一个同页地址。**不许在别处再写一份,也
  不许拿原始字符串比**。`%2e` 这种编码过的点段不折叠(浏览器会),后果止于「人自己
  填了个点段地址」→ 读之前就被告知网址不同,可改可重发。
- **拒绝那一刻手上的真实网址不许丢 —— 出路开在待办那一行里。** `_admit_page` 判出
  「不是这一页」时把浏览器交回来的规范网址记进 `intent['seen_url']`(`_seen_elsewhere`,
  **只在 pending 的那个上记**),补抓页把它摆出来并给一颗「改用这个地址」—— 点下去走的
  是同一个 `create`(旧待办由服务端顶掉),不是先取消再发起。
  事故形态:站点按浏览器语言跳转(`openai.com/index/x` 在中文浏览器里落到
  `/zh-Hans-CN/index/x`),这一类订阅**每一次**都被拒,而人只看到一句「网址不同」;
  原来那句拒绝语指向的操作(「回知识库核对最终网址并重新发起」)在页面上**当场做不到**
  —— 有待办时那一栏和「发起」都是禁用的(上面那条约束要的就是这个),得先在下面取消
  待办。**记下来不等于放行**:原请求照旧只写得了它绑定的那一页,改用要人点,所以
  「扩展不会用另一篇文章静默覆盖」一个字都没松。
  **不许顺手剥掉语言前缀来「认成同一页」**:那是站点自己的约定,`/zh-Hans-CN` 在别的
  站完全可能是路径的真身,剥错一次就是把**另一篇**的正文写进这一条 —— 而 `page_url`
  那份口径的底线正是「宽的那头只会多认一个同页地址,不会把另一篇认成这一篇」。
- **`precheck` 一个字都不落库,也不顶替事务内那一道。** 真正的互斥待在 `save` 那条
  UPDATE 自己的 WHERE 里(key / 来源 / 原网址 / 正文指纹 / 修订号 / 非 X 观点 / 未排除,
  `rowcount != 1` 即拒);`precheck` 和 `save` 开头那次 `_refresh_status` 都只是**早一道**。
- **补抓页那一栏网址:人动过就不许被轮询填回去。** 自动填入只认「框里还是上一次
  自动填进去的那一份」(`autofillUrl`);已有请求时强制显示服务端记下的那一份并禁用。
  事故形态:本页每 2 秒重画一次,原来的判据是「框是空的就当还没填过」—— 人清空、
  切出去复制浏览器里真正的地址、切回来一粘贴,贴的那一截接在被填回的原网址后面,
  拼成一个谁也打不开的地址(实测 2.6 秒后变回原值),之后扩展只会一直说「当前标签
  网址与指定文章不同」。**两个触发点**:平常那一次,和点过「重新采集正文」进草稿态
  之后 —— 这道闸不能只挡首次渲染。
- **回执按文章恢复,不靠标签的 `sessionStorage`。** 服务端按文章 key 返回当前待办和
  最近一条有效审计回执(`browser_capture_audit`),关页、换标签、超过 15 分钟、服务
  重启之后都找得回来。已保存请求无论命中内存还是从审计恢复,都走 `saved()` 同一套
  校验(来源、排除状态、修订号、正文摘要);旧回执失效时隐藏成功区、禁用继续按钮
  并给出原因。
- **回执记的是「哪一世」的那篇文章,认不出来就当「没有回执」。** `item_key` 按网址
  算:存量清理(`scripts/feed_trim_history.py`)删掉一条、下一轮又从同一个链接收回来,
  key 一个字都没变,而库里那是另一行、另一份正文。判据只有 `_same_life` 一份 ——
  `item_fetched_at`(只在 INSERT 时写,换内容的几个写入方一个都不碰它)+ `content_rev`
  不许倒退(一行的生命里只增,新插进来的从 0 起),两条各补对方的洞:同一秒里删掉又
  收回来时 `fetched_at` 会撞上(它只记到秒),那一下由倒退的 `content_rev` 认出来。
  **认不出来一律当「没有回执」,不是「正文被改过」**:后者会在那篇文章的补抓页上
  常驻一句假红字,还连带藏掉回执区、禁掉继续处理那颗按钮,而重抓一次也去不掉(审计
  那一行记的是上一世,怎么比都不等)。老库里没记身份的回执行同样按「没有回执」办。
  新回执落库时顺带收掉这个 key 上前一世的审计行,判据**特意比 `_same_life` 窄**(只
  认身份那一半),这样删掉的一定是认领不了的行。
- **同一文章只留一个 pending。** 在锁内比正文版本、来源、原网址和指定最终网址:
  匹配就复用原请求和有效期,不匹配把旧的标 `superseded` 再建新的。额度只算 pending
  (`MAX_PENDING`),保存 / 取消 / 陈旧不占。不同文章各自排队。
- **额度撞满的那一下不拒人,顶掉最老的那个。** 取消的出口只开在**各自那篇文章的
  补抓页**上,而额度是全局的:拒了就得让人挨个翻完那 100 篇才发得出第 101 次。等待
  中的请求手上没有任何产物(正文还没读),顶掉最老的(它也最接近过期)只值一次重新
  点击,扩展那边收到的话正是「被新的采集请求替代」。**已保存的回执压根不在池子里**,
  顶不掉。
- **进入「重新采集」不撤销已保存的正文和回执**,退出也不清审计;只有再次预览确认
  提交才替换。
- **「继续导出与索引」那颗按钮的射程只有 `CONTINUE_STAGES`,而且页面、确认框、回执
  三处的话必须跟它对得上。** `extract`(条目化提取)**不在里面**:它的队列
  (`kb.extract.pending_docs`)压根没有来源参数,按全库取数 —— 一颗开在某一篇文章页上
  的按钮不该顺手买下全库那一轮模型调用(原来的话写着「该来源其他待办」,而实际射程
  是全库)。`export` 这一段认 `crawl_filter`(只有这一类来源),`index` 是整个 vault 的
  增量比对、不调模型,这两件事页面上明写着。要提取就到同步中心起跑弹窗里勾;这一篇的
  `extract_stale=1` 还在,下一轮同步自己会重新提一遍。
- **`fulltext_at` 一写上,这条就退出自动补抓队列**(`fulltext.queued_sql()` 要求它为空)。
  好处是刚补的正文不会被自动补抓再盖一遍;代价是万一采到的是一张过得了去重门槛的
  会员说明页,出路只剩人工「重新采集正文」。
- **`api.js` 住在扩展目录**(`kb/static/browser-extension/knowbase-capture/api.js`),因为
  下发的 ZIP 要带上它、扩展取不到 `kb/static/js/` 下的文件。页面在 `ui.js` **之前**加载
  它;全站十来个脚本的 `apiFail` / `toastIfFail` 都是它那一份。
- **扩展的 `popup.css` 另抄一份色板**(扩展装在浏览器里,取不到 `kb/static/css/base.css`)。
  改 `base.css` 的 `:root` 色值要连它一起改 —— 两份文件各写了一行互指注释(`base.css`
  那行就在 `:root` 上面)。CLAUDE.md 的「视觉语言」里数的那**三处**是脱离 kb-web 的
  独立产物,各抄色值 + 箭头几何;popup 只抄色板、没有箭头,所以单记在这一份里。
- **`plainUrl()`(两处,各三行)只是显示** —— 把百分号编码过的中文地址显示成人能对着
  地址栏核对的样子。它不是判据,回填给服务端时会被重新规范化成同一份。

- **这个扩展现在管两件事,它们在 popup 里是分开的两块,判据也各归各家。**
  「补回哪个待办」那一块是本文件说的补正文;上面「这一页」那一块是**收录一条新链接**
  (硬约束在 `link-grab.md`,端点是 `/api/grab*`)。共用的只有三样:那条连接和配对密钥
  (`call()`)、在标签上读一次正文那一步(`extractFrom`)、以及预览区和那道「我已核对」
  (`collecting` 标记决定提交走哪一头)。**不许把两套判据混在一处** —— 补正文认的是
  待办绑定的那一页和那一版条目,收录认的是「这条 url 库里有没有」,两者的洞完全不同。

## 知情的代价

- 补抓页固定 2 秒轮询,切到后台也不停;每轮 `item_state()` 开三次数据库连接。
- `save()` 持 `_lock` 期间执行 `BEGIN IMMEDIATE`,库被别的进程占着时 `item_state` /
  `pending` 一起等。TTL 内最多 100 个 pending,影响有界。
- `precheck` 让每次读页多两次本机往返,换的是「不让人白读一整页」。
- 请求队列在单个 web 进程的内存里,不支持多 worker;重启丢未完请求,不丢已保存
  正文和审计回执。
- `save()` 不取维护锁,与手动收录 `grab_store.replace()` 对称 —— 判据待在 UPDATE
  自己的 WHERE 里,见元规则「并发与数据安全」。
- 审计表每成功补抓一次长一行(一次人的动作),前一世那些在下一次补抓时收掉,没有
  按时间的留存策略。**同一秒里删掉又收回来、而且两世的修订号正好对齐**的那一档,
  旧回执仍可能按它自己的请求 id 读出来 —— 那时两份正文的摘要也相同,所以它说的话
  不假;那一页上显示的始终是这一世最后那张。
