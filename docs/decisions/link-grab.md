# 手动收录:给一条链接,内容抓进知识库(kb/feeds/grab.py + grab_page.py)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是落点的取舍、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束

- **抓不到正文一律不入库,一个字节都不写。** `registry.put_items` 是
  `ON CONFLICT(key) DO NOTHING` —— 空正文一旦落库就**再也改不回来**(重投同一条链接只会被
  `DO NOTHING` 挡住),而这一步失败的代价只是用户再点一次。所以 `grab.py` 里所有「拿不准」
  都抛 `GrabError`,`save()` 开头那道 `entry['body']` 非空检查是构造上的最后一道。口径同
  `x_article` 那条「判不准一律抛」。
- **「提取出了一段长文字」证明不了拿到了那篇文章。** 网页那条路的准入只有**一道**判据
  (`grab_page.gate_reason(final, html, body)`),**成功和失败两条路共用它**,而且排在
  「拿 `body` 做任何事」之前 —— `grab._grab_web` 里只有一个调用点。不变量一句话:
  **已经认出是关卡的响应,既不许落库、也不许被说成「这一页没找到正文」**。
  判据分两类,**六样**,一条成立就算 —— 前五道是「认出了对方的拦截」,第六道是
  「**我确认不了手里这篇是正文**」。**第六道是这一道判据的底**:没命中拦截证明不了
  拿到了正文,三轮审查各实测到至少一例漏放,最后那一例把前五道全绕过去了。
  前五样一律是**这一次响应/这一页自己的身份**:
  ①**路由**(`_GATE_ROUTES`,按最终地址的 path + query 比);②**页面真挂着的关卡组件**
  (`_gate_assets`:只看 `script/iframe/link/form/img` 那几个会被浏览器真去加载或提交的
  属性值,外加**无 `src` 的 `<script>` 自己的内联代码**);③**标题自己就是一句关卡提示**
  (`_GATE_TITLES`,**祈使句或状态播报**)且正文里也在说同一件事;④**正文通篇就是那几句
  提示**(命中句占比 ≥ `_GATE_SHARE`);⑤**正文挡在一道登录/订阅墙后面**(`_wall_reason`)。
  提取不出正文时(`body` 为空)③ 不再要正文佐证,另外加一道宽词表(`_GATE_WORDS`)——
  那时已经没有正文可言,宁可多认一道关卡。
  第六道 ⑥是**内容质量**:`body_confirmed(body)` —— 正文里**不重复的**字数要过得了提取
  器那道 `MIN_CHARS`(`readable.substance`:按行去重再数)。
  **生效性和位置要分开各判一次,DOM 里有某个片段不等于它在阻挡正文**:
  `<template>` 里的密码框、`type="application/json"` 里的示例参数都不算这一页挂着什么
  (`_live`,两问合一:`<template>` 之外还要看 `<script>` 那个 `type` 执不执行,带 `src` 的和
  内联的同一道);`nav` / 页眉页脚侧栏里的登录框不算拦在正文上(`readable.in_furniture`,
  它和提取器那三类剔除规则一一对齐:`nav` 无条件、`_DROP_OUTSIDE` 看位置、其余按
  `_noisy`)。
  **不许再靠「字数上限」和「命中几个词」来修这块**,两个方向的事故都付过账:
  - **字数上限 = 漏报,而漏报不可恢复。** 上一版是「≤1200 字且命中两句强措辞」,
    第二轮审查实测一张 **1782 字**的验证页(标题「请完成验证后继续」、地址干净)
    一路过关、`SAVED added=1`、导出和索引全成功 —— `DO NOTHING` 之下再投一次同一条链接
    也换不回真文章。
  - **通用英文词进路由表 = 误拒,而这一道在成功路径上也生效。** 上一版把
    `challenge` / `checkpoint` 整段相等算进地址判据,第二轮审查实测一篇 650 字的正经文章
    (标题「挑战：一次研究记录」、地址 `/blog/challenge/`)被拒;同一个形状的真实样本是
    developers.cloudflare.com 那篇 1277 字的文档(`/waf/reference/cloudflare-challenges/`)。
    所以**路由表里一个通用英文词都不许有**。
  - **通用验证码小组件不算页面身份。** reCAPTCHA / hCaptcha / Turnstile 的 `api.js` 正常
    文章页的评论框就挂着;Cloudflare 的 `challenge-platform/scripts/jsd/main.js` 在普通
    页面上也会被注入 —— 所以 `_GATE_ASSETS` 只收**编排**路径(`challenge-platform/h/`)
    这种只出现在关卡页上的串。
  - **标题判据只收祈使/播报措辞,话题词一个都不许进。** 「人机验证是怎么坏掉的」是文章,
    「请完成验证后继续」是关卡 —— 进了话题词,这一道就从「拦住关卡」变成「拦住一类话题」。
  - **页面上的文字不算页面身份,一个字都不算。** 组件那一道早先在**整份原始 HTML** 上做
    子串匹配 —— 一篇讲这类关卡的教程会把 `<script src="…/challenge-platform/h/g/…">` 原样
    转义印在 `<pre>` 里,于是 731 字的正经文章被拒(审查实测)。那是**内容**,不是身份:
    所以只问 DOM 里那几个真会被加载/提交的属性值,再加无 `src` 的内联脚本。**这一条不许靠
    「给样例多加几个词」绕过去** —— 词表怎么调都分不开「挂着它」和「印着它」。
  - **「没命中拦截」证明不了「拿到了正文」—— 最后一道判据落在内容自己身上。**
    复审拿**原始证据**把登录墙那一条打回来过:那张「Sign in to continue reading /
    subscribe to unlock this story」的提示页**连 `<form>` 都没有**(上一版的用例给它
    补了个密码表单,于是守住的是那个变形),提取器交出 1832 字,份额判据不成立、措辞
    不在关卡表里、结构判据也无从下手。分得开它的只有**内容自己**:整页是同一段铺了
    7 遍,按行去重只剩 260 字 —— 连 400 的门槛都过不了。所以第六道按
    `readable.substance` 算,**不许退回原始长度**(那张墙比正常文章长得多),也
    **不许改成又一张措辞表**(每家的说法都不同,那就是逐个堵组合)。
    误拒形状如实记着:**整页复读同一段**的真实页面会被拒(夹具里 `'…' * 12` 那种省事
    写法也会,所以沙箱那一页改成了八段各不相同)。
  - **登录/订阅墙按结构判,不按词。** 判据两样:**正文区里有个密码框**
    (`input[type=password]` 的 `<form>`,**且这个表单不长在页面家具里** ——
    位置借 `readable.in_furniture`,和正文提取器丢页眉页脚那一份同一个口径),或者
    **页面自己在 JSON-LD 里说 `isAccessibleForFree: false`**(schema.org 的标准键,
    付费墙站点普遍带)。先有的那张词表办不到:审查实测一张登录墙(标题是文章标题、
    正文段落被重复铺了 7 遍)提取出 **1832 字**、`saved=1` —— 它的正文看起来跟文章一样,
    唯一分得开的是**它要你登录**这件事本身。
    **已知的误拒形状如实记着**:一篇在**正文区**渲染真实、**已生效**的密码框的教学文章
    会被拒(页眉、页脚、`nav`、侧栏里的登录框不会 —— `in_furniture` 那一道就是为它留的;
    `<template>` 里的 demo 也不会 —— `_live` 那一道)。两个方向差一个量级:误拒的代价是
    用户自己复制一次正文,错存的代价是 `DO NOTHING` 把登录墙永久钉成这一篇。
- **`canonical_url(social=True)` 只给 X 自己的域,这一句是承重的。** 那一档的判据只有路径
  (`/某人/status/数字`),域名一概不看 —— 它本来服务的是「这条 feed 是 X 的镜像桥接」那个
  上下文(`SocialAdapter`:nitter / xcancel 给出的链接**正是**要被改写成 x.com,
  `tests/test_feed_sources.py` 钉着)。手动收录拿到的是用户随手粘的任意一条地址,没有这个
  上下文:无条件开着它,`https://notx.com/alice/status/12345` 在分流**之前**就变成了
  `https://x.com/alice/status/12345`,然后拿一个陌生站点的地址去问 FxTwitter、把**另一条
  推文**的内容收成「用户要的那一篇」(2026-10-16 审查实测三例)。`classify` 的域白名单那时
  已经无从谈起 —— 原域名没了。**所以这道约束待在调用方 `grab.normalize`,不在共享层里**:
  共享层那一档对它唯一的老消费方是真话,改成「只认 X 域名」会把桥接镜像的规范化一起停掉。
- **「`feed_items` 里有这一行」和「知识库里搜得到」是两件事,不许混成一句话。**
  `grab.known()` 返回的 `done` 要**四**件事同时为真:导出过(`path` 在)、**导出的是库里
  现在这一版**(`exported_hash == content_hash`)、**vault 里那一篇还在**(`_stored`)、
  而且 **vault 里当前那一份进了索引**(`_indexed`:只读打开 kb.db,口径借
  `scanner.file_hash` + `store.doc_needs_reindex` —— 索引自己判「这一篇要不要重建」用的就是
  这一对)。**四件事要分开交出去,不许只回一个布尔**:调用方据此决定「还欠哪一步、那一步
  能不能靠补跑一轮补上」(`owing` 把它说成一句人话,**所有消费方共用这一份口径** ——
  重复投递那句提示、`/api/grab/state`、界面收尾那句话)。**「以前走完过」不算完成事实**:
  一次正文补抓、一轮翻译回写都会把 `content_hash` 推新,那时 vault 和索引里都还是上一版,
  而按「`documents` 里有这条路径」答就会把它当成走完了 —— 面板说「已经在知识库里了」,
  用户搜到的是旧内容,后半条链再也没人补(2026-10-16 第二轮审查)。重复投递时
  `grab_api._duplicate` 据此分档:走完整条链的那一条是幂等的一句「已经在知识库里了」、不占
  管道;只暂存下来的那一条**要把后半条链再跑一次**,并如实说「还没写进知识库」。放过去的
  后果是用户搜不到,而再投一次只会再得到同一句话 —— **后半条链永远没人补**。
  **补跑那一轮要挂在真正拥有那一行的来源名下**(`_write_through(…, seen['kind'])`):
  export 阶段是按通道筛的(`pipeline_stages._per_channel`)—— 一条推文已经被「大V观点」收过
  但还没导出时,起一轮 `inbox` 的 export 一个字都不会动它,而回答里却写着「正在写入知识库」。
  `_indexed` 判不准一律答「没进」(代价是多跑一轮空转的 export/index),而且**不许走
  `store.connect()`** —— 那一路建表、跑迁移,是写 kb.db 的入口(要先取维护锁,见
  `maintenance-lock.md`),而这里只要回答一句「搜得到吗」。
- **「补跑一轮」不等于「它会被选中」:欠的那一步要先落实成 export 认得的形状。**
  `sync._export` 的待办判据是 `exported_hash<>content_hash`。vault 里那一篇被拿走(清理
  脚本、同步盘、手动删)而两个 hash 还相等时:那一轮 export 一个字都不会写、index 反而
  正确地把它那行旧索引收掉 —— **两个阶段都 ok,而那一篇从此搜不到**,再投一次又得到同一句
  话,反复补跑永远撞不到它(审查实测:`exported_hash == content_hash` 而文件不在,导出队列
  选中它 0 次)。所以重复投递走到这一档时先 `grab.reclaim_export(seen)` 把水位清掉、再起
  那一轮。两条配套:
  - **判据待在那条 UPDATE 自己的 WHERE 里**(元规则),`rowcount == 0` 不是失败 —— 它说明
    别人已经动过它、或者两个 hash 本来就不相等(那时 export 自己就会选中它)。
  - **清水位不是固化终态,所以这一笔可以放心写**:最坏的后果是把一篇其实还在的 md 重写
    一遍(内容由库里那一行算出来、逐字节相同,`content_hash` 没变,索引也不会重做);反过来
    「不清」的代价是那一篇**永久**搜不到。
- **「写进去了」和「写进去的是一篇文章」是两件事,不许混成一句「已经在知识库里了」。**
  `known()` 另交一件事实 `content_ok`(`grab_page.body_confirmed` 拿库里那一份正文**随时
  重算**,所以不必在表上多存一列,老库里那些以前漏放存下的条目一样认得出来);`owing()`
  把它排在**最前面** —— 它欠的不是哪一步,导出、文件、索引全齐也只是把一段不是正文的
  文字写进了知识库。**「已导出、已索引」不是内容质量证明。**
  - **这一问只对「我们按文章正文收下的网页」成立**(`kind` 是 `inbox` 且 `content_kind`
    是 `content`)。那道判据的门槛借的是提取器的 `MIN_CHARS`(400),而推文、动态、订阅源
    给的摘要本来就短 —— 不限类型的话,一条三十个字的推文每次重复投递都先被判成坏内容:
    白跑一次重抓,面板上还写着「收下的那一份看不出是正文」。别的来源各有自己的「壳 / 空
    正文」判据(`body-gap.md`、`fulltext`),这里不替它们判。反过来钉一边:手动收录按网页
    正文收下的那一条,通篇复读就是坏内容。
- **错存的内容只有一条出路:受控重抓 + 条件替换**(`grab.replace`,端点那一侧是
  `_recover`)。`put_items` 是 `DO NOTHING`,再投一次同一条链接一个字节都不会动那一行,
  于是一份错存的内容永远留在库里、用户每次只得到同一句「已经收过了」。所以**查重命中
  「看不出是正文」那一档时发一次 HTTP**(这是那道早检查唯一发请求的一档,**也不看
  `done`** —— 走完整条链的坏内容更该换),新内容过完那六道才替换。五条配套:
  - **恢复出口不许以「看不出是正文」为前提 —— 人说「重新抓一次」就重抓**
    (`GrabRequest.refetch`,界面上是投递栏里那颗按钮,只要库里有这一行就露面)。
    那道质量判据只认得出**我们认得出的**坏内容(通篇复读那一类);而「五段各不相同的
    会员说明、一个 `<form>` 都没有」的提示页过得了全部六道,从此 `content_ok` 恒真 ——
    恢复要是也架在同一道判据上,**最该换的那些恰好一辈子换不回来**(实测:原站后来恢复
    可读,重投仍回「已经在知识库里了」,HTTP 发出 0 次;历史那些 `content_kind='post'`
    的 X 残片同理)。两个入口判据独立,**都不看 `done`**。反过来钉一边:不带 refetch 的
    重复投递照旧连 HTTP 都不发(不然每次重复投递都要去对方站点跑一趟)。
  - **判据待在 UPDATE 自己的 WHERE 里**:`content_hash` 要还是我们读到的那一版;
    `rowcount == 0` 说明这期间别人已经动过它(一轮正文补抓、一次存量复查、另一条并发
    投递),不覆盖是对的,不是失败。
  - **「变了没有」和「这是哪一版」用同一套列,而且那套列就是整份导出负载**
    (`grab_store._VERSION_FIELDS` = 标题 / 正文 / 作者 / 发布时间,也就是 vault 里那一篇的
    frontmatter 加正文;口径只有一份:`item_version`)。少算一列的两头都不报错:**早退**
    少算会把一次真实更新说成「和它一样」(作者、日期单独改就是),**hash** 少算会把一次真实
    更新藏在导出闸门外面 —— 只改标题那一次 `content_hash` 不变、`exported_hash` 仍然相等,
    导出一条都选不中,文件和索引**永远**停在旧标题,而 `known` 按两个 hash 相等报 done、
    面板照旧说「全文检索里搜得到了」(实测顺序执行即复现:列表里是新标题,真实 FTS
    搜新标题 0 条、搜旧标题 1 条)。
  - **「一样」按内容比,不按 hash 比**:三处的 hash 口径算的是不同的东西(`put_items` 哈希
    整份 entry、`fulltext.body_hash` 只哈希正文、`item_version` 哈希导出负载),拿它们相等当
    「没变」会让每次重抓都白推一轮导出和索引。**CAS 比的是库里那一列的原值**,不是重算一遍
    再比。顺带一提:正因为三份口径不同,**第一次** `replace` 必然改变 `content_hash` ——
    「少算一列」要到**第二次**重抓才显形,回归要照那个序列写。
  - **写哪几列照 `fulltext._save` 那一份口径**(元规则「口径只有一份」):`content_hash`
    跟着正文变(导出闸门因此自然成立),**`exported_hash` 不许清**(它是「这一篇入没入过
    库」的事实来源,清掉会让面板上一篇正读得好好的内容连标题一起消失),`extract_stale=1`
    留一个待办,译文整组作废重排(旧译文译的是那张墙)。`content_kind` 不动 —— 一条推文
    换了正文还是推文。
  - **重抓还是确认不了就什么都不动**(库里那一份原样留着、不占管道、不谎报换好了),
    并且**把「没换成」如实交到前端**(`replaced=False`):界面据它落可恢复的那一档、
    那颗按钮继续在,而不是照「回包里没有 pipeline 这个字段」把这一次当成「早就走完
    整条链了」。
- **导出确认的是「刚落盘的那一份」,不是「UPDATE 跑到时库里那一份」**(`sync._export`
  收尾那一句 `UPDATE feed_items SET exported_hash=?,path=? WHERE key=? AND
  content_hash=?`)。**这条不变量是 `replace` 带来的**:在它之前,改正文的那几条路
  (`fulltext._save`、`x_article.fill`)全跑在同一轮管道的 crawl 阶段里、与 export 串行;
  而 `replace` 跑在 HTTP 请求里、**不持导出这把维护锁**,于是真实可达的交错是「导出渲染
  好旧那一份 → 用户重抓换成新正文 → 导出落盘旧文件」。右侧原先写 `exported_hash=
  content_hash` 取的是 SQL 跑到时行上的值,那一笔会把**新正文**的 hash 盖成旧文件的完成
  回执:导出欠账(`exported_hash<>content_hash`)当场消掉,`known` 从此报 done、重复投递
  按成品返回、补导一轮也选不中它 —— **vault 和全文检索里永远是旧那一份,而且没有任何
  路径回来重试**。`fulltext.retire_stale` 按同一个相等关系清提取待办,所以它也会跟着把
  一份旧摘要确认成新的。两条配套:
  - **`written` / `done` 的口径不动**:回执仍排在确认之前(文件进了 vault 是既成事实,
    见 `daily.md` 的「已经落进 vault 的文件不许因为后面那次确认失败而消失」),确认没成
    只是说「它已经不是最新那一版了」,下一轮导出自己会再来一次。
  - **这条不变量不止 export 一处 —— 它是「所有异步交付」那一类。** `replace` 跑在 HTTP
    请求线程里、不持任何同步的维护锁,所以每一个「先取样 → 等网络/等模型 → 再写回」的边界
    都要带判据:正文补抓的 `_save`/`_fail`、提取待办的 `retire_stale` 在 `fulltext.py`
    里(**那几条写在 `fulltext.md` 第一节**,事故形态是旧正文盖回新正文、失败记在新正文头上、
    新版本的提取待办被清掉),语种补标的 `_label_unknown` 在 `translate.py` 里(那一条写在
    `translate.md` 第一节 —— 它写的那一列 `replace` 自己也写)。只给 export 补一处的话,同一条
    恢复链上另外几处照旧会倒退(审查复现了其中两处,另一处按同一口径一并补上)。
  - **判据要能表达「这是哪一版」,「正文还一样」不算,「内容逐字相同」也不算。**
    `_VERSION_FIELDS` 是四列,所以一次**只改标题**的重抓换了 `content_hash`、正文一个字没动 ——
    补抓那边按 `AND body=?` 判的话,它会把这一版当成「还是我取样那一版」照旧写回去。而**内容
    指纹本身可以重复**:标题改成 BETA 再改回 ALPHA 之后 `content_hash` 逐字回到取样那一版,
    这期间两次更新却都已经被接受过(两种形态都用 Event 卡在补抓返回处复现过:用户重抓到的那
    一版被换成补抓那一轮的旧内容,md 和 FTS 跟着落了它,再贴同一链接只说「已经在知识库里
    了」)。所以 `replace` 每次都把 `content_rev` 加一 —— 一个**只增不复用**的代次,异步交付拿
    它当「我取样那一版」的身份(口径在 `grab_store.work_version`,它那边还留着 `content_hash`
    当冗余带)。**一边按四列认定「新版本」、另一边按单列相等认定「还是旧那一版」就是两套口
    径**(元规则:口径只有一份);而「指纹相同」和「这期间没接受过更新」压根是两个问题。
  - **「重新抓一次」自己就是这个模式的第二个入口 —— 它也得消费取样代次。**
    `_recover` 先拿一份 `known()` 快照,再去原文链接抓几十秒,最后才把结果交给 `replace`:
    和补抓逐字同形。**只在写入侧把代次加一、不在判据里核对它,等于只修了一半** —— 实测形态
    是两个页面先后重抓同一条链接,一个还在等,另一个把标题改成 BETA 又改回 ALPHA(两次都换成
    了);等第一个回来时指纹已经复原,它那份更早的抓取照旧被接受,文章换成旧内容而面板报
    「已经在知识库里了」,md 和 FTS 跟着落了它。所以 `known` 把 `content_rev` 一起交出去、
    `replace` 的 WHERE 带 `AND content_rev=?`。**`seen` 缺这一列就当场抛**,不许退回「只比
    指纹」—— 这条链上所有 `replace` 的调用方拿的都是 `known()` 那份快照。
  - **WHERE 里那一道 `content_hash` 是冗余带,别删**:光把右侧换成我们那一版的 hash 就
    已经挡住丢数据了(反向注入实测红 0 条,见那一节),它多挡的是「慢导出把一个更新的
    回执盖回旧值」那种交错 —— 代价只是多导一轮。判据待在写语句自己的 WHERE 里是元规则,
    留着它比日后重新推一遍便宜。
- **`replace` 不写 `fulltext_at` —— 手动拿到的全文不顶替补抓待办。** 那一条原来属于开了补抓
  的订阅、还没补抓成功时,手动换上来的正文仍排在补抓队列里,下一轮导出会**再抓一次**(旧结果被
  版本判据拒掉的那次同理:它留在队列里等下一轮)。代价是多抓一轮;反过来写上 `fulltext_at` 是
  **固化终态** —— 那等于宣布「这一条的全文已经拿到了」,而手动那一份只过了准入门槛
  (`substance(body) >= MIN_CHARS`)、未必是整篇,之后再没有任何路径回来补它(元规则:拿不准
  就别固化终态)。补抓真在之后落进来也不丢东西:它带着取样版本,能盖的只有它取样那一版。
- **`/api/grab/state` 是只读的那一问,写一个字节都不行。** 它只回答「这一条此刻在知识库里
  是什么状态」(`known` / `done` / `owing` / 三件事实 / 那颗按钮的名字):不发 HTTP、不起
  管道、也**不清水位**(那是投递那颗按钮的事)。面板收尾每隔一秒问一次,顺手占一轮同步会
  把用户自己的同步挤掉。
- **失败要分档,一档一句话,而且**必须**说清下一步。** 登录墙 / 验证页 / 这后面不是网页 /
  推文被删 / 账号主页不是一篇内容 —— 它们的下一步完全不同(在浏览器里打开一次、换个地址、
  去「大V观点」加订阅),折叠成「抓取失败」等于把人留在原地。
- **这一类来源 `pollable=False`,crawl 阶段对它空转**(`sync.collect` 开头那一道)。
  **必须在那儿拦住,不许靠「它没有启用的订阅」** —— 收件桶是**启用着的**订阅(面板要显示它、
  `put_items` 要挂在它身上),放过去就会拿站点首页去发一次 HTTP,而 `fetching.ADAPTERS` 里
  压根没有 `manual` 这个适配器。`adapter='manual'` 是刻意的:哪条路漏了这道闸,报出来的是
  一个说得清的 KeyError,而不是拿一个假地址去抓。
- **收件桶按站点一个,`extract=1`、`fulltext=0`、`enabled=1`。** `fulltext` 必须是 0 ——
  那个开关会把条目扣在导出闸门外等「去原文补正文」,而正文此刻已经在手里了(实测后果:
  vault 里那一篇根本不出现)。`extract=1` 是因为手动收录正是「谁值得买一次提取」的肯定
  答案(口径见 `extract-optin.md`)。
- **桶的并发创建靠 `UNIQUE(kind,url)`,不靠「先查一次有没有」**(元规则:判据待在写语句
  自己的约束里)。撞上了就重查一次拿赢的那一条。
- **时间一律换算到 Asia/Shanghai**(`grab_page.as_published`、`grab._as_published`)。
  网页上的时间戳大多是 `…T10:02:37Z`,照字面取就比真实时刻**早 8 小时**,而日报按
  `published` 做字符串比较筛窗口 —— 差这 8 小时足够把一篇内容推到前一天。不带时区的写法
  按项目时区补齐,**不按宿主机**。
- **「改动时间」不许混进发布时间那张表**(`_TIME_META` / `_MODIFIED_META` 分开)。它排在
  所有发布时间来源之后,只在一个都没有时才用 —— 否则每次对方改一个错别字,这一篇的发布
  时间就跟着变一次。
- **元信息一律按纯文本处理**(`oneline(..., 'text')`)。bs4 交出来的属性值已经把 `&lt;`
  解码成 `<` 了,再过一遍 HTML 解析会把标题里的 `<T>`、`<Button>` 整段吃掉(口径同
  `fetching._is_plain` 那段注释)。
- **推文正文的换行一个都不许压掉**(`body_text(raw, 'text')`,走 `_plain_lines`),标题
  那一头反过来必须是单行(`oneline`)。分行就是作者的分段。
- **回包里那个结构化的长文信号先收下,不许先丢掉、再凭展示文本去推断。**
  `tweet.article` 是生产者自己的签名「这条推文是一篇长文」,而 `needs_article` 的三条判据
  全是**间接**信号(正文里写着文章地址 / 时间线上那张卡片 / 正文是空的)。长文推文的
  `text` 完全可能是文章标题或一句介绍(上游 FxEmbed 的渲染器自己就按 `text === article.title`
  处理),再配一张图连「空正文」那条也被挡住 —— 于是我们连问一次都不会问,随后 `DO NOTHING`
  把这份只有标题/只有图的正文**永久**钉成那一篇(审查实测三种形态各一例,后续调用 0 次)。
  收下的办法是把它挂成已有的那个键(`x_article.HINT`,口径同浏览器通道 `x_browser._entry`
  读那张卡片),**「要不要去取长文」仍然只有 `needs_article` 这一份判据**,这里不新增第二个
  问法。三条配套:
  - **形状认不出来也算信号**(非空的非 dict):那是回包在说「有长文」而我们读不懂它,按
    「没有长文」放过去就是放行一条残缺正文;去问一次接口,问不到就拒。
  - **确认是长文、正文又没拿到:一个字都不许写**(抛 `GrabError` 说清「稍后再点一次」)。
    手动收录**没有浏览器后路**(不持有 CDP 会话,同 `bridge` 那一档)。
  - **接口那一跳没成、而手里这份回包自己带着文章内容时用它**(`x_article.from_payload`
    —— 就是 `fetch` 的尾段,渲染、标题、「只有标题不算补到了」那一道全是同一份代码)。
  这个信号键**不进 `feed_items`**:`put_items` 把整份条目哈希成 `content_hash`,多一个只在
  抓取期间有意义的键会让同一条推文从采集通道和手动收录两条路进来算出两个哈希(剥离口径同
  `fill`,共用 `x_article._strip_hint`)。
- **长文正文的拼接口径只有 `x_article.merge` 一份**,定时采集(`fill`)和手动收录都过它。
  各写一份的话同一篇长文从两条路进来会长出两种正文,而先到的那一份被 `DO NOTHING` 钉死。
- **地址规范化只有 `fetching.canonical_url` 一份**(它顺手去掉 utm_*/fbclid/gclid、把推文
  地址收成 `x.com/<handle>/status/<id>`)。`put_items` 的键是 `sha256(kind + ':' + url)`,
  两处规范化不一致时同一篇内容会变成两条记录、两篇 md、检索里两份结果。
- **X 的域判据是「等于名单里某一个」,不是 `endswith`** —— 后者会把 `notx.com` 一起圈进来,
  然后拿一个陌生站点的地址去问 FxTwitter(口径同 `x_login_import` 那条域判断)。
- **抓好了才发现存不下去 = 一个没有原因的 500。** 保存那一步的输入都来自对方的页面,所以
  收件桶的地址和名字要自己兜住:IPv6 的 `hostname` 是脱了方括号的(拼回去是畸形地址)、
  合法域名最长 253 字节而 `save_subscription` 的名字上限是 120。同一条口径也管推文那边的
  可选容器(`media.photos/videos` 不是数组就当没有媒体,文字那一半照旧收得下)。
- **形状对不等于是个日期。** `2026-99-99`、`2026-02-30`、`10:77` 都过得了那个 ISO 正则 ——
  一律留空(`_real_clock`)。假时刻会一路进列表排序和日报的时间窗口(两处都按 `published`
  做字符串比较),而「没有发布时间」是一句真话。
- **作者:人名 meta → JSON-LD 作者 → 站点名兜底。** 两个名单不许合成一张表 —— 同时给了
  `og:site_name` 和 Article JSON-LD 作者的页面很常见,合起来的话站点名会在 JSON-LD 还没问过
  的时候先占掉位置,已知的真实作者被丢掉。
- **绿泡泡的文章不许按域名先拒,它和别的站点走同一条路。** 发一次请求,读到正文就收下,
  **只有实际响应表明撞上了关卡、或者读不到正文**才拒 —— 而且那一句要指向「公众号」那一类
  (`_next_step`,**下一步这半句话只有这一份口径**,`_gate` 和「读不到正文」那一档共用)。
  按域名先拒等于替对方的服务器回答:转载页、镜像、以及对方哪天放开,都会被一句「这条路
  抓不到」挡在外面(2026-10-16 用户提出,第二轮审查判定要改)。**不绕那道关卡**照旧:不带
  登录态、不去过验证。代价如实记着:真能直接读到的那一篇会在收件桶和公众号树下各留一份 ——
  `documents.url` 没有唯一约束,跨树重复本来就有(实测同一条 url 已经同时躺在 rss / web /
  digest 三棵树下),两处都搜得到,不是丢数据。
- **占不到管道不是失败。** 内容已经在 feeds.db 里,写进 vault 由任何一轮 `inbox` 的 export
  兜住(面板那颗按钮、下一次收录、定时同步都算),所以端点照旧回 200、只是如实说「还没写
  进知识库」。反过来谎报成功的代价是用户以为检索里搜得到,而 vault 里还没有这一篇。
- **慢请求的回包落地前先对一次归属,但归属是「这次动作自己的身份」,不许借列表的代次。**
  身份 = `grabAction`(发起一次就 ++)+ `grabNav`(打开来源模块就 ++)+ `sourceKind`;
  **只有导航和新动作能让旧动作过期,轮询不能**。借 `sourceVersion` 的后果:那个数每次自动
  刷新都 ++(闲时 15 秒、管道跑时 4 秒),而这颗按钮允许抓 40 秒 —— 等于「慢回包一律当成
  过期丢掉」,正常成功的那一次既不清输入框也不收敛提示,面板永远停在「正在抓这一篇的
  正文…」(2026-10-16 审查实测 18 秒那一例:条目已经进列表了,提示还在进行中)。过期之后
  toast 照发(那是用户自己的动作),但**一个字都不往面板上写**。
- **不许许一个不存在的自动排队。** 别人的同步在跑时后端会**拒绝**起跑这一轮(如实回「稍后
  点一次」),没有任何机制替用户把它排进去 —— 提示里那句话必须跟着说「等它跑完再点一次」。
- **每个终态都要落在提示上,写进行中的那句话必须自己收敛 —— 而且「已写入知识库」只许由
  这一篇自己的事实支撑。** 成功、重复、失败、占不到管道各有一句;「正在写入知识库」由
  `grabConverge()` 收尾,**身份认那一轮的 id,结论问这一篇自己**:
  ①**身份**:`/api/grab` 把 `start_pipeline` 发的 run id 原样交给前端(`out['run']`;
  那个函数返回 id 而不是 True,正是为了让调用方**原子地**拿到「我起的是哪一轮」),快照里的
  `run_id` 跟它相等才算看到了同一轮。**不认 `running` 的跳变**(这条路一次模型都不调,整轮
  可能几百毫秒,面板一次都没见过 `running=true`;口径同 `sources.js` 的 `sourceRunFinished`),
  也**不许按「run_id 变了就算跑完」猜** —— 别人插在中间的一轮同步会被认成自己的。
  ②**结论**:那一轮 `stages.export` / `stages.index` 的状态**只是旁证,不是结论** ——
  整轮双 `ok` 只证明那两个阶段跑完了,证明不了**这一篇**进了知识库(文件被拿走而两个 hash
  还相等那一档正是双 `ok` 而它搜不到;队列把这一条暂扣在导出闸门外也是同一形状)。所以收尾
  去问一次 `/api/grab/state`(`grabCheckItem`,只读),按**这一篇**的事实落终态;阶段的红只
  用来给失败那句话**补上原因**(extract 是打标那一步,红了照样搜得到,所以不在内)。
  **核不上(快照已经是别的一轮、后端没给 run)也走同一问** —— 「这一篇在不在知识库里」是
  一个随时问得出的事实,比追一轮已经过去的运行可靠;别人那一轮的红**不许**被当成这一篇的
  原因(那会指着一个毫不相干的毛病让用户去修)。
  **没进去就落可恢复的那一档**(说出欠哪一步 + 指回那颗按钮),**那一问本身没答上来就如实说
  「没核到」**(元规则:判不准不许返回一个确定结论)—— 谎报已完成的话用户搜不到,再投一次
  只会得到「已经收过了」。**反过来钉一边两处**:快照还停在起跑之前那一轮(`grabRunAt`)时只是
  轮询还没回来,继续等、不许提前收尾;而这一篇真查得到时就要说「已写入知识库」。
- **界面那句「已写入知识库」只许由这一篇自己的两件事实同时支撑**:写进去了
  (`done`)**而且**写进去的看得出是正文(`content_ok`)。后者为假时说的是「收下的内容
  看不出是正文;再投一次这条链接,会重抓并在确认得了时把它换掉」—— 谎报的后果是用户以为
  检索里有一篇文章,而他搜到的是一页登录提示。
- **回包没送达不等于后端没存下来。** 保存排在起管道之前,断线可能发生在它之后,所以
  `fetch` 抛异常时**不许断言「这条没存下来」** —— 去问一次 `/api/grab/state`(只读),
  问得到就照事实说(库里真有就说已写入)、库里确实没有才说没存下来、那一问也没答上来就
  说「结果未知」。重投是安全的(`DO NOTHING` 挡着,不会变成两份)。
- **「稍后点一次」那句里的按钮名按归属来源给。** 来源页工具栏那颗按钮在可轮询的来源里写
  「同步全部」,只有手动收录写「写入知识库」(判据就是 `pollable`,和 `sources.js` 的
  `manual` 分支同一个)—— 一条推文被「大V观点」收过、这一轮又没占到管道时,照手动收录那套
  说就是指着一颗那一页上不存在的按钮。
- **写 `#grab-hint` 只有 `updateGrabControls()` 这一条路**(文案由 `grabHintText()` 算)。
  各处就地赋值的话,轮询那一次会把动作的终态盖掉,而动作那一次会把「其他同步正在运行」
  盖掉 —— 两种盖法都只在特定时序下出现。
- **未提交的草稿留着。** 切去别的来源看一眼再回来是常见动作,替用户清掉等于让他重新粘一次;
  只有本次收录**成功**才清输入框。

### 非网页入口(`./kb.sh grab`、skill `kb-grab`)

- **收录不只能在面板上做,但判断只有一套。** 命令行那一层(`scripts/grab_cli.py`)和 skill
  (`.claude/skills/kb-grab/`)**打的就是 `/api/grab` 与 `/api/grab/state` 这两个接口** ——
  抓取、查重、重抓替换、起哪一轮全在服务端。**不许进程内 `import kb.feeds.grab` 自己抓**:
  ①那套判断于是在两处各写一遍,其中一处迟早把「暂存下来了」说成「已经在知识库里了」(元规则
  「口径只有一份」);②**管道跑在 kb-web 进程内** —— 进程外抓完只能把内容留在 feeds.db 里,
  用户检索不到而他以为收进去了。所以 `kb.sh` 的 `cmd_grab` 第一件事是 `web_start`(同
  `./kb.sh sync`)。
- **「已存下」和「搜得到」在终端上同样要分开说,一档一句话。** `/api/grab` 回的是「那一轮
  起跑了」,所以收尾去问 `/api/grab/state`(只读)、按**这一篇自己**的事实落终态 —— 和界面
  那一侧 `grabCheckItem` 同一条口径。终态词十个(`saved` / `duplicate` / `pending` /
  `bad_content` / `unchanged` / `gone` / `failed` / `unknown` / `absent` / `not_tried`),**不许几档共用一句**:把 `pending` 说成「已写入
  知识库」,用户去检索里找不到,而再投一次只会得到同一句「已经收过了」,后半条链永远没人补。
  **`pending` 也不许报成失败**(退出码 0):内容已经在库里了,写进知识库那一步由任何一轮
  `inbox` 的 export 兜住 —— 报成失败会让调用方去重投,而重投被按 URL 去重挡住,一个字节
  都不会动。
- **「重抓换成了」不许按 `content_ok` 判。** 后端那一档(`_recover` 的成功分支)只更新
  `replaced` / `done` / `title`,回包里的 `content_ok` 仍是**库里旧那一份**的判断 —— 照它
  先判就把一次**成功的**替换说成「看不出是正文」,而且不去等它写进知识库,用户那一次重抓
  于是永远停在「没换成」。所以档位的优先级是:明确没换成 → 起跑了(含换成了那一档,它起
  的是同一条后半链)→ 没起任何一轮且内容不对。
- **这条不变量要在归并层写全,不是给某一种快照组合打补丁** —— `verdict` 的说明里是五句话,
  成立的依据各不相同:
  - **`res` 说得出「这一次做了什么」,说不出「现在是什么」。** 回包里的 `content_ok` 是
    **请求开始那一刻**的质量;`replaced=false` 的典型成因正是**别人在这中间刚换好**,那时
    它带的是人家换**之前**的判断。所以「库里现在是不是正文」只认 `state` —— 还没查过
    `state` 的 `bad_content` **不算终态**(`_settled` 挡着,它会先去只读查一次)。拿回包那个
    旧字段收口的后果是让人去 `--refetch` 一份**已经好了**的正文,而重抓要动库里那一份。
  - **「这一次换没换正文」说不出「这一篇交付完了没有」。** `replaced=false` 只回答了
    **动作**那一问(抓到的内容相同 / 别人刚换过 / 重抓撞上关卡而旧正文完好 —— 后端
    `_recover` 三种结果都回这一个值),而那一篇**可能还欠导出和索引**。实测形态:真端点 +
    临时库,`content_ok=true`、`done=false`,终端说一句「库里那一份没动」就收口,盘上一个
    Markdown 文件都没有、恢复请求 0 次 —— 不是「等完还没索引」,是**压根没人去起那一步**,
    而那一条在界面上和 `--state` 里照旧欠着。所以好正文这一档**只有 `done` 之后**才用
    `unchanged` 收口,欠着的照旧报 `pending`(动作那个事实留在那句话里),由 `settle` 走
    `/api/grab/restore` 把后半条链补上。相应地 `_settled` 的 `unchanged` 也要 `done` 作证
    (同 `bad_content` 那条:**终态要有当前事实撑着**),而自动补写只挑 `pending` 这件事
    本身没错 —— 错的是把一条欠着的条目归成了终态,于是它永远走不到补写那一步。
  - **`state` 说得出「现在是什么」,说不出「这一次结束了没有」。** 没拿到回包(`acked=False`)
    时,库里那一份**旧坏内容**不许终结这一条 —— 后端可能正停在取页中间、随后把它换掉。
    这一支和 `--refetch` 无关:普通重复提交撞上坏内容,后端也会进受控重抓。
  - **`state` 也否认不了已经确认发生过的写入。** 确认 `added`/`replaced`/`duplicate` 之后
    再查到「库里没有这一行」,那是**之后被删了**(`gone`),不是「一个字节都没写」(`failed`)。
    两者的下一步不同:后者会让人原地再抓一篇,而删掉它的可能正是用户自己。
  - **反过来,「那一篇目前存在且可检索」也证明不了「本次替换完成」** —— 显式重抓的回包丢了
    而库里旧那一版本来就 `done`,只能停在不确定。
- **这几句的次序本身也是约束:「这一行还在不在」排在所有质量/替换的结论之前。**
  库里已经没有它了,那么「这次没换成」「库里那一份是正文」全都是在描述一篇**不存在**的
  文章(实测:重抓等待期间同一篇被清理掉,终端照旧说「库里那一份没动」)。
  判「它当时在不在库里」时判据要**宽**:`replaced` 这个键**存在**本身就证明后端对它做过
  替换尝试,哪怕值是 `false` —— 漏判的代价是把「收下过、现在没了」说成「一个字节都没写、
  再投一次」,而反过来顶多多说一句。
- **缺当前证据时不发布质量结论,而且这条要落在所有最终输出路径上,不只是等待那一条。**
  `--no-wait` 提前收口、通道断了没等、只读那一问失败 —— 这几条都直接走到输出
  (实测:「证据约束只落实在部分等待分支」)。所以 `verdict` 里 `replaced=false`
  且 `state is None` 那一档停在 `unknown`,`_settled` 也不把「还没拿 `state` 核过」的
  `unknown` 当终态 —— 等得到就按事实说,等不到留在不确定,**不许回头用回包里那个旧
  `content_ok` 收口**。
- **回包的语法有效性不等于接口有效性,「是个对象且 ok=true」也还不够。** 通道层每一条
  路径都要确认「这是这个服务对它的回答」(`grab_http._checked`:必须是个对象、该带 `ok` 的
  要为真、**那条路所有分支都给的那几个承重键必须在而且类型要对** —— `/api/grab` 和
  `/api/grab/restore` 要 `url`/`added`/`duplicate`/`done`/`content_ok`,`/api/grab/state` 要
  `url`/`known`/`done`/`content_ok`,管道那一问要 `running`;`replaced` 只有重抓那几档才带,
  所以**出现时**才校验、一旦出现就必须是真布尔 —— 归并层对它做的是三态判断,一个字符串
  `"false"` 会被当成「做过替换尝试、只是没换成」)。判不准一律归到 `ApiDown`(那一档会去问
  事实、如实停在「结果不确定」)。**类型判断不能用 `isinstance`**:`True` 是 `int` 的实例,
  而 `added: true` 不是一个计数。
  `--api` 指错地方(反代插了一页、另一个应用、异常网关)时回来的可能是一段**合法 JSON**,
  而 `.get()` 一路拿到 `None` 之后每一档都读得下去 —— 实测:`[]` / `null` 让 CLI 当场崩在
  `AttributeError` 上(同一批**第二条压根没被处理**);`{"ok": false}`、以及只看「是对象且
  ok=true」那一版下的 `{"ok": true}` 和 `{"ok": true, "duplicate": false, "done": false}`,
  都让两条输入被说成「早就在知识库里了」而 `done=false`、一次核实都没发生;
  `{"ok": true, "known": true}` 被说成「看不出是正文」,`{"ok": true, "known": null}` 被说成
  「还没收进来」—— 后者是**「确定没有」**这个结论,照它重投会原地再抓一遍。
  **不在各个调用点补 `.get` 兜底**,那是同一个问题在四处各判一遍。

  **清单按「归并层实际消费哪几个键」列,不是只列「下业务结论」的那几个。** 拼在人读的
  那句话里的几个(`detail`/`title`/`kind`/`owing`/`resume`)同样要校验:实测一份**承重字段
  齐全、类型也全对**、只有 `owing` 是个数字(或 `resume` 是个列表)的回包,会让 `--state`
  在**第一条**上抛 `TypeError` / `AttributeError` —— 整批到不了输出,后面几条连一行结果都
  没有,而「一条输入一行结果」本来是这条路在所有失败路径上的承诺。**不许只在拼接处补
  `str()` 兜底**:那是把「这个回包可信吗」这一问散到每个拼接点上各判一遍,而判不准该停下来。
  反过来钉一边:这几个键**缺着**不算坏回包(旧版服务可能压根不带),那时按兜底文案走。
  **`pipeline` / `exported` / `stored` / `indexed` 刻意不在清单里**:前者只被当真值读
  (类型不对也只是多去问一次事实,那一问会给出真结论),后三个原样进 `--json`、不参与任何
  运算,而它们在库里是 0/1 —— 校验成布尔反而会把**正常回包**判成坏的,误判的代价是整批
  停在「结果不确定」,比漏校验这三个重得多。
- **打不出去的 `--api` 是参数错,不是「投出去了而结果未知」。** 请求行只能是 ASCII,所以
  地址里带没编码的非 ASCII 字符(`…:8787/知识`、IDN 主机名)会在 urllib 组装请求那一步抛
  `UnicodeEncodeError` —— 它和 `ValueError: unknown url type` 一样发生在通道那套归一化
  **之前**。实测那一版:退出 1、stdout 一个字都没有、stderr 一段 traceback,**本地服务压根
  没收到请求**。所以 `bad_api` 在参数层就拦掉它(退出 2 + 一句人话),而请求构造/发送那两步
  另有一道**兜底** catch 归到 `ApiDown`(挡参数层没想到的组合;归 `ApiDown` 而不是
  `ApiRefused`,因为「库里那一行是什么样」照旧该去问一次)。**这一层不替用户编码** ——
  改写他给的地址等于替他决定打到哪儿去,而 `%E7%9F%A5%E8%AF%86` 和 `知识` 在反代后面可能
  是两条路由。
- **「早就在知识库里了」这句话要正面证据**:`duplicate` 和 `done` 都为真(`grab_api._duplicate`
  的幂等分支)。按「少了 `pipeline` 这个字段就是幂等」推不行 —— 那不是证据,一个语义自相
  矛盾的回包(或者端点将来多一个分支)会被说成已完成而 `done=false`,用户去检索里找不到、
  再投一次还是同一句话。拿不出证据时**不下结论**:走 `verdict` 的 `unknown`,由只读那一问
  定档(通道层挡得住缺字段的那种,这一道兜的是字段齐、语义却说不通的那种)。
- **外壳只替「本机托管那一份」服务起/拦。** `./kb.sh grab` 那道 worktree 闸门和 `web_start`
  管的是 `$API` 那个地址;`--api` 指到别处(另一台机器、自己另起的一份)时它们管的是**另一个**
  服务 —— worktree 里会在连上用户给的地址之前就 die,主检出则多起一份他压根不需要的守护
  进程。实际目标由 `--parse-only` 那一步报回来(它和真正那次调用用同一个 `--api` 默认值,
  装配口径只有一份),而**认不出、或者没报回来时照旧按本机走**:管道跑在 kb-web 进程内,
  静默不起服务的代价是内容留在 feeds.db 里、检索不到(那比多起一份服务坏)。
- **只有 4xx 说得出「没收下」。** 那六道准入排在写库之前,拒了就一个字节都没写。**5xx 和
  断线一律不算** —— 保存排在起管道之前,那时写没写进去我们并不知道,所以那一档去问一次只读
  的事实:问得到就照事实说,问不到才停在「结果不确定」(同界面那条「回包没送达不等于后端
  没存下来」)。
- **保真是按「这一行是不是整个就是一条地址」判的,不是按「它从哪儿进来」判的。**
  显式参数、**以及标准输入里整行就是一条地址的那些**,一个字符都不动交给后端 ——
  地址合不合法只有 `grab.normalize` 那一份口径说得准,而在命令行这一层做有损的改写,
  代价是把一个**合法**地址改坏:`…/wiki/Function_(mathematics)` 在第一个 `)` 处被
  截掉、`…/wiki/函数（数学）` 被截成 `…/wiki/函数`、末尾带 `;` `,` `:` 的被剥掉最后
  一个字符,而截断后的地址**可能照样存在** —— 收进来的于是是另一篇文章,比抓不到更坏;
  `--refetch` 和 `--state` 走同一条解析,所以还会连带认错「要替换哪一篇」「要查哪一
  篇」。按入口分(「`-` 来的就是文章、参数来的就是地址」)不成立:`-` 同样用来喂
  「一行一条」的清单,`pbpaste | ./kb.sh grab -` 两种内容都有(实测四组
  整行地址被改写)。
- **「保真」的判据是「这条地址的边界是给定的吗」,不是「它在哪一行的什么位置」。**
  边界给定的有两类:①整行就是一条地址;②**行内明确圈出来**的 —— `<地址>`(RFC 3986
  附录 C 那个写法)、双引号或单引号包起来的、以及 Markdown `[文字](目标)`。这几种的
  分隔符本身一定不属于地址(`< > "` 在 URI 里必须编码,Markdown 的圆括号由语法自己
  配平),所以边界不是猜的。
  实测的五组正是这一类被漏掉的后果:`<…/post;>` 剥成 `…/post`、
  `[原文](…/post:)` 剥成 `…/post`、`<…/函数，性质>` 截成 `…/函数` —— 后端 `normalize`
  对原地址本来是收下并保留的,而「这一行里还有别的文字」推不出「圈出来的那一段可以
  截断」。
- **前四种原样交出去,Markdown 那一种按语法取目标 —— 这两件事要分清。**
  `<…>`、引号、整行给的是地址**原文**,解码它们等于改写用户给定的边界(CommonMark 的
  autolink 本身也不处理转义)。Markdown 给的是**源码**,整套语法都得认:
  - **反斜杠转义**:`[原文](…/part\(one\))` 里 `\(` 是字面的 `(`,目标是 `…/part(one)`;
  - **字符实体**:`…/A_&#40;B&#41;` 的目标是 `…/A_(B)`(实测点名)。只认**带分号**
    的严格写法 —— `html.unescape` 本身宽松到连 `&amp` 都解,那会改写用户真写了 `&amp`
    的地址。**两种解码在同一遍扫描里完成,顺序定死**:`\&#40;` 里的 `&` 先被转义那一档
    吃掉,剩下的 `#40;` 只是普通文字(反过来会把五个字符变成一个 `(`);
  - **目标里的括号数深度**(`A_(B_(C))` 是维基那一类的真实条目名),实体和转义解出来的
    括号**不参与配平**(它们是字面字符,不是语法);
  - **显示文字整段跳过**,而且**代码跨度里的方括号不算语法** —— ``[看 `](x)` 这个](目标)``
    里那对 `](` 夹在反引号中间(同一类的另一半:把它当收尾会让整段结构认不出来,
    于是一条好端端的链接要么被说成没有链接、要么被拼成另一个地址);
  - 目标后面那个**可选的 title** 也要跳过,`[文字](<目标>)` 那种写法单独认。
- **认边界要「先消费结构、剩下的才抽裸地址」,不能靠一个正则的几个分支排优先级。**
  正则交替只在**同一个起点**上比优先级,管不了「后面那个结构分支该赢过前面已经匹配上的
  裸地址」。实测的三组就是这一点的后果(每组 9 次:收录 / `--state` /
  `--refetch` 各三次,全部认错):`[https://a/label](https://a/target)` 被裸地址那一档从
  `label` 起手、一路吃到 `…label](https://a/target)`;`[原文](…/A_(B_(C)))` 的结构分支
  因为只认一层括号而失配、退回裸地址,把 Markdown 自己的收尾 `)` 也带走;`\(` 没还原,
  收上去的地址里留着反斜杠。所以 `grab_input._scan` 是**从左到右扫一遍**:结构化区域
  整段消费掉,裸地址只认没被结构盖住的那些文字。
- **结构认出来了就由它说了算:不支持的目标明确拒绝,不许退回裸地址拼一条出来。**
  `[看 https://…/real 很好](#锚点)` 指向的是锚点,显示文字里那条地址是**文字** ——
  从显示文字里把它挖出来收录,收进来的是**另一篇**(用户要的是锚点那一篇)。所以这一段
  **整段消费、一条都不产出**。
  (早先那一版反着写:协议筛不过就不消费、让裸地址去捡显示文字里那条。实测
  指出那正是「退回拼出另一个地址」—— 同一类问题的另一个出口。)
  **反过来钉一边**:`[备注] 看 https://…` 里那个方括号**压根不是链接结构**(后面没有
  `(`),那时不消费,裸地址照常认出来 —— 不然一行好端端的文字会因为开头有个方括号就
  整行丢掉。
- **一条链接的边界只由它自己那一段语法决定,邻近的文字说不上话。** 这条栽过两次,两次
  都是**先独立判一遍某种配对、再让另一套扫描去用那张表**:
  - 「一个 `[` 扫到末尾都没配平,后面的 `[` 也一样配不平」—— 推论**是错的**:
    `备注里有个 [,见 [原文](目标) 这篇` 里外层那个 `[` 的确配不平(`]` 被内层用掉了),
    而内层那条链接语法完整;
  - 预先独立判「哪儿是代码跨度」—— 那份表**不知道哪一段属于目标或 title**:
    ``见 [一](… "反引号 ` 的用法") 和 [二](…) 后文 `尾`` 里前一条 title 的反引号会跟后文
    那个配成一对,把中间那条完整链接整个盖掉(`markdown-it-py` 按 CommonMark 渲染出来的是
    两条正常链接 —— 真正的行内解析不会在 title 里认代码跨度)。

  两次的后果一样:那条链接被跳过、退回裸地址,发出去的地址**多带一个右括号**(收录、
  `--state`、`--refetch` 三个动作一起认错对象,而 `DO NOTHING` 之下换不回来)。
  **出路是两趟,不是再补一张表**:`_links` 第一趟**只认结构**、按 CommonMark 的行内解析
  从左到右走一遍(谁的起点先出现就先归谁,认成的那一段整段消费,所以 title 里的反引号
  压根不会被当成起点;反过来 ``[看 `](x)` 这个](目标)`` 里那个反引号先出现,它那段代码
  跨度先成立、里面的 `](` 是字面文字),`_scan` 第二趟才在**没被结构盖住**的那几段文字上
  抽 `<…>`、引号、裸地址 —— 显示文字里那条地址于是压根没机会被抽出来。

  **两趟之后还栽过第三次,根因是第一趟认的结构不全。** `见 [看 <span title="]">标签</span>](目标) 这篇`
  —— 行内 HTML 的**属性值**里那个 `]` 弹掉了显示文字的开括号,真正的 `]` 来时已经没有配对,
  于是整条链接退回裸地址、发出 `目标)`;而 `target-normalization` 实测:多一个右括号的那个
  地址能通过后端的 `grab.normalize`、真的落进库(**不能靠「它多半抓不到」兜着**)。
  所以第一趟要认全**CommonMark 里能盖住 `[` `]` 的那几种行内结构**:代码跨度、autolink、
  行内 HTML 的开/闭标签、注释、`<?…?>`、CDATA、declaration。
- **这一类的统一判据是:发出去的每个地址,都得是它那一段结构真正表达的目标。**
  上面三次栽的都是它的实例,所以回归也按这一条建(一组输入 × 三条动作),不是给每种
  字符组合加一条排除项。推论有两条,都要照着办:
  - **第一趟认出来的那一段,不许再交给第二趟去抽裸地址。** 跳过去但不记一笔是不够的 ——
    实测 `` `[不是](…/no)` `` 发出 `…/no)` 再加一个反引号、`<!-- [注释里的](…/no) -->`
    发出 `…/no)`。「字面文字」不等于「该从里面抽一条裸地址」:那一段的 `)` 是 Markdown 的
    收尾,不是地址的一部分。
  - **认成结构、但不该成立为链接的那一段,整段消费、一个字都不产出**(嵌套作废掉的外层
    `](B)`、筛不过协议的 `[文字](ftp://…)`)。认不出来就**失败关闭**,不许退回去拼一条。
  反过来钉一边(都在「多收一条」那一侧,代价是多抓一篇而不是收错一篇):**边界给定的那几档
  照旧收** —— 标签的属性值(`href="https://…"`,用户粘一段 HTML 源码进来时他要的正是它)、
  反引号圈起来而整段就是一条地址的(`` `https://…` ``,判据和「整行就是一条地址」共用
  `_WHOLE_LINE` 那一份)、以及 label 里那条 autolink **不作废**包着它的链接
  (「不许再有链接」管的是内联/引用链接的嵌套,autolink 在 bracket matching 里不参与;
  作废掉的那一版**漏掉外层那一篇**,而漏是静默的)。
- **链接里不许再有链接**(CommonMark 的「Links may not contain other links」):
  `[outer [inner](A)](B)` 成立的是 inner 那一条,包着它的那几个 `[` 随之作废。不作废的话
  选出来的是 B —— 那是**另一篇文章**,不是「多带了一个字符」那种错(实测:三条动作都只
  处理了 B)。**外层剩下的那段 `](B)` 整段消费、一个字都不产出** —— 交给第二趟的那一版
  发出 `B)`,而实测它能通过后端的规范化、真的落进库(见上一条的统一判据)。
- **代码跨度的「起点」和「收尾」在 CommonMark 里判据不同,一份表只能当收尾那一侧的
  索引。** 收尾**不**受转义影响:`` `foo\` `` 的收尾就是那个被反斜杠挡着的反引号
  (spec 的「Backslash escapes do not work in code spans」)—— 所以 `_tick_runs` 那份表
  不跳转义。起点反过来:`` \`` `` 里第一个反引号已经被转义吃掉了,剩下的那个才是起点、
  **宽度按剩下的算**,所以起点的宽度由主扫描**就地数**,不借那份表的切分。借表的那一版
  在这种输入上直接 `KeyError` —— 一行带 `` \`` `` 的文字让整条命令崩掉,而且同一批后面
  几条压根没被处理。反过来让那份表也跳转义,收尾那一侧就错了(`` `](y)\` `` 盖不住里面
  那个 `](`,于是它变成一段链接结构,最后发出去的地址多带一个右括号)。两边各有一条用例。
- **认边界不许随输入长度平方级变慢,而且不许拿正确性换速度。** 方括号按栈一遍配平,
  反引号串**一遍扫出来、按宽度分组查表**(`_tick_runs` / `_code_span_end`),收尾还必须
  落在起点那一串**之后**(同一串的后半截不许当自己的收尾)。「某个起点
  配不平、或者找不到等长收尾」只说明它自己 —— 据此剪掉后面的起点就是上面那条错推论。
  时间用例要钉**四类**输入,一类换一个判据:未闭合的方括号(`[` 两万次)、**全部配平却
  不是链接**的(`[[[[…]]]]`)、一长串未闭合反引号(判的是「找不到收尾时跳过整串」——
  旧版在串里每个字符处都重找一遍,那才是平方级的来源)、以及**很多个短反引号串**
  (`` `x`x`x… ``:这一类串的数量才多,判的是「配对查表」,而一长串那一档只调用一次配对、
  多慢都看不出来)。

  **有一类快不起来,因为「答不上来」本身就要扫到行尾**:`](目标)` 的括号一路不配平、
  title 没有收尾引号、`<?` 找不到 `?>`。一行里塞上千个这种残片,同一段余文就被反复扫
  (实测 500/1000/2000 个 `[](`:0.019/0.065/0.258 秒,长度翻倍耗时四倍;`](a (` 同理)。
  **出路是一份累计预算 + 失败关闭**(`_Budget`):按行长的倍数给(正常一行里每段结构只被
  它自己那一次探测扫过,加起来不超过行长,所以合法输入碰不到),超了抛 `TangledInput` ——
  **退出 2、一句人话、一个请求都不发**。不许「扫到一半放弃、把剩下的按裸地址拼一条」,
  那正是保真那一类要堵的事;也不许报「这一行没有链接」,那是**「确定没有」**这个结论,
  而我们只知道没认全。时间用例按四类损坏输入各钉一条(`[](`、`[](a (`、`<?`、`<!--`)。
- **「顺序去重」用集合判在不在、列表保顺序,而且这个判据只有一份**(`grab_input.dedupe`,
  行内抽取和整批参数两个调用点共用)。`not in 列表` 那一版每条都跟前面所有条比一遍 ——
  实测两万条互不相同的地址 0.62 秒、四万条 2.62 秒(长度翻倍耗时四倍)。回归按四万条
  钉,两万条那个规模把集合换回列表**一条都不红**。
- **裸写在行文里的那些:按空白断,一个标点都不剥、一个括号都不切。** 它的边界本来就
  不确定,而剥短之后那个地址**可能照样存在** —— 收进来的于是是**另一篇文章**(静默,
  而 `put_items` 的 `DO NOTHING` 之下换不回来);留着整串顶多抓不到,终端上那一行
  `failed` 用户看得见、改写了再来。**两害取轻,所以这一层不做任何「这个字符是行文」
  的推断**(包括全角句读:它在裸地址里少见,但 IRI 允许,后端也真的收下 ——
  「它没有来源」那个说法不成立)。代价写在 skill 和 `--help` 里:要精确就把地址放进
  `<…>`,或者一行一条。
- **协议名不分大小写。** `HTTPS://…` 是合法写法(后端收下并规范化成小写),两档判据
  都得认得它 —— 漏掉的后果不是「少收一条」,是这一行既不算整行、也抽不出链接,
  **整条输入连一行结果都没有**(当时直接以 2 退出,说「没给出要收录的链接」)。
- **恢复要让服务端按那一条自己的归属去做,命令行不许另写一份带固定来源的补链。**
  批量投递时后面几条必然撞上前一条起的那一轮(后端如实回 `busy`),它们的内容在库里
  却没人替它们跑 export —— 补这一步打的是 **`POST /api/grab/restore`**(下一条:
  它是独立路径,不是 `/api/grab` 加一个字段),服务端那条路现查一次归属、先落实
  `reclaim_export`、再按 `seen['kind']` 起那一轮,不发任何对外 HTTP。**写死 `inbox` 在跨来源的那一刻就错了**:一条推文被
  「大V观点」收过时,起一轮 `inbox` 的 export 一个字都不会动它(`_per_channel` 按
  通道筛;真库 + 真 `sync.export` 实测:`export('inbox')` 之后 `exported=false`,
  换 `export('social')` 才为真)。
- **恢复是一条独立路径(`POST /api/grab/restore`),不是 `/api/grab` 上的一个字段。**
  字段那种写法只在**同版**服务上成立:`kb.sh grab` 每次跑磁盘上的新 CLI,而撞见已经
  跑着的服务就直接用它(代码比进程新只提示一句 `code_stale`,按约定不代劳也不拦)——
  那个没重启的进程用的是旧 `GrabRequest`,而 **Pydantic 默认忽略不认识的键**,于是
  这道安全约束静默消失,它照旧走「不在就抓一篇新的」。实测形态(实测,拿
  `git show 5b70036:kb/web/grab_api.py` 的真模块当那个没重启的进程):等待期间历史清理
  把那一行删掉之后,旧端点实发 1 次对外取页、把一条清理掉的 `rss` 文章**重建成
  `inbox`**、标题换掉,而命令行照旧退出 0。
  **独立路径在那种服务上回 404** —— 客户端据此到此为止:不再试、档位照旧(内容在库里,
  一个字节没动)、那句话里说清「跑着的那个 kb-web 比代码旧,`./kb.sh restart` 之后再
  `--state` 查一次」。**不许退回那条会创建内容的路**,也不代劳重启(重启会打断正在跑的
  管道,口径同 `code_stale`)。
- **两个请求体都 `extra='forbid'`:多余的键当场 422,不许被忽略。** 「静默丢掉不认识
  的键」正是上面那个故障的机制 —— 哪天又有人想拿一个字段表达「只恢复」/「顺便重抓」,
  他要立刻拿到拒绝,而不是一个会动内容的 200。(面板只传 `url` / `refetch`,
  `kb/static/js/grab.js` 那一处。)
- **恢复那条路本身的约束(落在服务端的写入边界上):**
  命令行手里只有一张旧快照 —— 「刚才那次 state 查到它还在」不是写入那一刻它还在的
  保证(那是 TOCTOU,靠「再查一次 state」堵不住)。所以 `known` 为空就 **409 到此为止**,
  抓取 + 新建那条路径在这条端点上**压根不存在**(实测:不收窄时它会把一条清理掉
  的 `rss` 文章重建成 `inbox`)。它还**不走重抓**:库里那一份看不出是正文时也只如实说欠
  在哪儿,**不替人做「换掉它」这个决定**(出路是人明确要求的 `refetch`)。反过来钉一边:
  `/api/grab` 的初次收录照旧抓取并创建,那一行还在且内容没问题时照旧把后半条链补起来。
- **重投的预算在发请求之前就扣,不按「收到 200 没有」事后数。** 用客户端收不收得到
  ACK 判断远端那次写发生没有是不可靠的 —— 请求已经生效而回包丢了的那次照样起了一轮
  同步(那一轮带 extract、要调模型),不扣预算就等于上限不成立。这和「回包没送达不
  等于后端没存下来」是同一条远端事实边界。
- **一条输入对一行结果,失败路径上也成立。** 结果对象**先建好、放进列表,再去打
  接口** —— 少了这一步,通道断在半路时单条命令的 stdout 一个字都没有、批量时出问题
  那一条连同后面几条**一声不响地消失**,而 skill 被告知「只按 status 汇报」时手里压根
  没有 status。断线之后不再投的那几条如实说「还没投」(`not_tried`),不混进「失败」。
  **反过来,`--state` 那一问失败了不许说成「还没投」** —— 只读地问「这篇我存过吗」压根
  没有投递这个动作,第一条就打不通时留着 `not_tried` 那句默认文案(「前面那一条就打不通
  服务了」)是在说一件不存在的事,而且那句话指的是**别人**。那一档是 `unknown`:「现在查
  不到,不能确定这篇存过没有」。`not_tried` 和 `unknown` 都算非 0 退出,skill 的退出码
  一节要同时列上它们。
- **「这一刻库里没有这一行」证明不了「那次投递不会写入」。** 收敛层要记住**本次那个
  动作终结了没有**(`acked`:拿到 200 回包、或者被 4xx 明确拒了),而不只是档位那个词:
  - 没拿到明确回答(回包丢了 / 5xx / 断线)而只读那一问答 `known=false` → **不是终态**,
    在预算内接着核实;预算到期仍然停在「不确定」,**不许改口说「确定没存下」**。
  - 拿到了明确回答之后答 `known=false` → 那才说得出「库里没有这一行,再投一次」。
  实测形态(实测):后端已经进入取页、投递那条连接断掉,此刻 `known=false`,
  原先据此输出 `failed`「没收下，再投一次」并退出 1 —— 而那次动作随后**真的保存成功**、
  真实导出在 vault 里生成了 1 篇。skill 对 `failed` 的承诺是「一个字节都没写」,所以
  那是谎报;照它重投还会多抓一次(重抓那一档更会动库里那一份)。
  **`--state` 那条纯查询的 `absent` 语义照旧保留** —— 它压根没有投递这个动作。
- **「没换成」和「内容不合格」是两个事实,分两档说。** 重抓到的内容和库里那一份一样
  (或者这期间已经有人换过、或者又撞上关卡)时,库里那一份**本来是正文、一个字节没坏**:
  那是 `unchanged`(「库里那一份没动」)。只有库里那一份**自己**过不了那道质量判据时
  才是 `bad_content` —— 把前者说成后者,是把一次无害的空转报成质量问题。
- **本次动作的证据和库里当前的事实分开,不许互相顶替。** 「那一篇目前存在且可检索」
  证明不了「本次替换完成」,旧那一版的质量也否定不了新那一版。两处落点:①`settle`
  里**问不出来的那一轮不重算档位**(拿 `state=None` 去重算,会让「已经换成、只是这次
  没问到」被旧 `content_ok` 判成「看不出是正文」并当场停止等待);②显式重抓的**回包
  丢了**而库里旧那一版本来就 `done` 时,如实停在「换没换成核不出来」——照 `done` 报
  「已写入知识库」是把一件不知道的事说成已完成,而用户要的是新那一篇。
- **读 HTTP 会在三个层面上断,归一化只在 `_request` 这一层做。** 网络层是
  `URLError`/`OSError`/`TimeoutError`,而**正文读到一半对方关连接**抛的是
  `http.client.IncompleteRead`(`HTTPException` 的子类,**不是** OSError);错误回包的
  `e.read()` 同样会断。四个端点共用这一层,在某一个调用点补 catch 只修得了那一处。
- **说出去的那个秒数要是**轮询的**上限,而且是整个等待阶段共用的一份预算。** 超时
  是逐请求的,所以这件事只有这一层做得到,三处都要算:①剩余预算传进**每一次** state 查询,而且
  **每次请求之前**都看一眼 —— 整批查完才看的话,一批 N 条慢查询会各等满自己那一份;
  ②「管道在不在跑」那一问**也吃预算**(它自己的上限是 15 秒),返回之后**再确认一次**
  才允许发出那次恢复写(那是写,而且带 extract 的那一轮要调模型);③**不抬底** —— 抬到
  「至少 1 秒」等于预算耗尽之后每条还能再发一个一秒的请求,N 条就是 N 秒。预算 ≤ 0 时
  **不发**那一次请求,当场收尾。
  **这份预算管得到的是「还发不发下一个请求」,管不到「一个已经发出的请求读多久」** ——
  传下去的那个数是 socket 超时,而那是**两次收包之间**的空闲上限:对方每次都在超时之前
  喂一点数据,那一次读取就能跨过预算的终点才返回(按代码推断,未实测)。
  所以对外的措辞一律是「轮询的预算」,不许写成「整段等待的硬上限」(SKILL.md 和
  `--timeout` 的帮助行同口径)。真要硬上限得让读取本身也盯同一个绝对终点。
- **帮助和参数校验排在任何副作用之前**(`--parse-only`):`./kb.sh grab --help`、
  拼错的选项、少给链接都不该先起一个守护进程,而 worktree 那道闸门还抢在它前面 ——
  连帮助都拿不到(实测:usage 之后紧跟一句「工作树不能起服务」,退出 1)。
  **帮助那一档得由 wrapper 自己短路,不能押在子进程的退出码上**:argparse 的 `--help`
  让子进程以 0 退出,和「参数校验通过」一模一样,`|| return` 分不开这两件事 —— 于是帮助
  打完 shell 照旧往下走:起服务、再把帮助打第二遍。两种拼写(`-h` / `--help`)、任何位置
  都认;skill 那个 wrapper 是 `exec kb.sh grab "$@"`,所以这一处管得住它。
- **本机请求一律不走代理。** 这台机器上常设 `*_proxy`,而 urllib 默认会把 `127.0.0.1:8787`
  也交给代理 —— 拿回一个跟知识库毫无关系的 502,于是被说成「这条没收下」,而服务其实好好
  跑着。所以那个 opener 固定带一个空 `ProxyHandler`。
- **`--state` 是只读的:一个 POST 都不许发。** 「这篇我存过吗」是随时问得出的事实;悄悄替
  用户抓一次,等于他只想查一眼却动了库里那一份。
- **worktree 里只许借用已经跑着的那份服务。** 端口上还没人时 `web_start` 会起一份用
  **本检出自己** `data/` 的服务,真文章于是收进一个测试库,而命令行说「已写入知识库」——
  比 `cmd_graph` 那道闸门挡的更隐蔽(那边是拿空库覆盖好页面,这边是用户以为存下了)。判据
  同那一道(git 的 common-dir),出路给两条(去主检出跑、或者先显式 `./kb.sh start`),
  **提示而不代劳**。
- **skill 总是对主检出动手。** 它的文件随仓库走,所以可能正躺在一个 worktree 里,而真数据
  (feeds.db / kb.db / vault)只在主检出那一份 —— `scripts/grab.sh` 探到自己所在的仓库之后
  再用 common-dir 换一次。找不到检出就让人设 `KB_HOME`,不猜。

## 落点:为什么是第六类来源,而不是「往某条订阅里塞一条」

三条路都想过:

1. **塞进 `rss` / `social` 的某条订阅** —— 那条内容从此混在订阅内容里,检索按来源筛的时候
   分不出「我自己存的」;而且订阅是有身份的(水位、etag、退避、定时),一条文章地址不是一个
   可以轮询的源。
2. **自己建一张表 + 自己一条链** —— 那要重写翻译、导出 vault、索引、提取、检索、图鉴、日报
   这一整条,每一处都多一份口径。
3. **第六类来源 `inbox`(选它)** —— `kb.source_types` 里加一条 `SourceType`,于是 vault 树、
   索引扫描范围、`SOURCE_GROUPS`/`SOURCE_ALIASES`、采集器注册、「我的订阅」页那排胶囊、
   同步中心的通道、日报素材范围**全部自动派生**(`kb/config.py`、`kb/collectors/__init__.py`)。
   新来源只需要回答一件新事:内容从哪儿来。

代价只有一处:这一类**没有可以轮询的源**,所以 `SourceType` 多了一个 `pollable` 字段,
`sync.collect` 开头多一道闸。换来的是后半条链一个字都不用改。

界面上同样是复用:投递栏是「我的订阅 → 手动收录」页头下面**一行**(输入框 + 按钮 + 一行
提示),条目列表、阅读器、搜索、翻译状态全是既有部件。**刻意只有一行** —— 这一页不许再长出
整页一份的大卡片(来由见 `subs-layout.md`),而阅读区高度是锁在可用视口上的。侧栏「信息来源」
里那颗「存链接」是它的快捷入口。

## 实测证据

- **自带括号的地址会被文本抽取改坏**(命令行那条入口):
  `https://en.wikipedia.org/wiki/Function_(mathematics)` 作为**显式参数**给进去,
  实际 POST 出去的是 `…/Function_(mathematics`(截断在第一个 `)`);`--refetch` 投的
  也是截断后那一条、还带着 `refetch: true`,`--state` 查的同样是它。
  `https://example.org/post!` 变成 `…/post`。
- **按入口分保真/抽取,`-` 那一侧照旧会改坏整行地址**(实测,假服务记录真
  CLI 发出的请求;后端 `normalize` 对这四条都原样收下):

  | 标准输入原文 | CLI 实际 POST |
  | --- | --- |
  | `https://zh.wikipedia.org/wiki/函数（数学）` | `https://zh.wikipedia.org/wiki/函数` |
  | `https://example.org/post;` | `https://example.org/post` |
  | `https://example.org/post,` | `https://example.org/post` |
  | `https://example.org/post:` | `https://example.org/post` |

  同一个中文地址作为**显式参数**的对照组保持完整 —— 所以是输入模式的差异,不是后端
  规范化造成的。
- **圈出来的地址照旧被改写**(实测,真 CLI + 真本地 HTTP,服务端记下收到的
  URL;后端 `normalize` 对这五个原地址都接纳并保留;收录 / `--state` / `--refetch`
  三种动作各跑一遍,15 次全部改写到同一个错目标):

  | 标准输入 | 应保留 | 当时实发 |
  | --- | --- | --- |
  | `见 <https://example.org/post;> 这篇` | `…/post;` | `…/post` |
  | `见 "https://example.org/post," 这篇` | `…/post,` | `…/post` |
  | `见 [原文](https://example.org/post:) 这篇` | `…/post:` | `…/post` |
  | `见 <https://example.org/函数，性质> 这篇` | `…/函数，性质` | `…/函数` |
  | `见 <https://example.org/post)> 这篇` | `…/post)` | `…/post` |

  同一批目标**一行一条**喂进去全部原样提交 —— 所以那次整行修复是有效的,
  漏的是「行内也有明确边界」这一类。另外 `HTTPS://example.org/post` 当时两档判据
  都漏掉,CLI 以 2 退出、一行结果都没有,而后端接纳并规范化成小写。
- **Markdown 的边界还是被改写**(实测,真 CLI 子进程 + 真本地 HTTP,服务端
  记下收到的 URL;同环境的 `markdown_it.MarkdownIt('commonmark')` 对三组都解析到「应
  处理」那一列,后端 `normalize` 也接纳这些目标;收录 / `--state` / `--refetch` 各跑
  一遍,9 次全部不符):

  | 标准输入 | 应处理 | 当时实发 |
  | --- | --- | --- |
  | `见 [https://example.org/label](https://example.org/target) 这篇` | `…/target` | `…/label](https://example.org/target)` |
  | `见 [原文](https://example.org/A_(B_(C))) 这篇` | `…/A_(B_(C))` | `…/A_(B_(C)))` |
  | `见 [原文](https://example.org/part\(one\)) 这篇` | `…/part(one)` | `…/part\(one\)` |

  三组的机制是同一个:**正则交替只在同一个起点上比优先级**。第一组里裸地址那一档从显示
  文字的 `https` 起手(位置更靠左),Markdown 那一档的起点 `](` 永远轮不到;第二组是结构
  分支只认一层括号、失配之后退回裸地址,把 Markdown 自己的收尾 `)` 一起带走;第三组是
  `\(` 没还原。**所以修的是层级,不是再加一个括号种类的分支** —— 改成从左到右扫一遍、
  结构化区域整段消费。
- **没拿到回包时,库里那一份旧坏内容被当成了终态**(实测,真 `grab_link` +
  真准入/正文处理 + 真替换与 CAS + 临时 feeds.db + 真 `sync.export`,只把外部取页换成
  由事件控制的固定页、起管道打桩成 busy):①库里先有一份旧的登录提示内容,真实
  `content_ok=false`;②CLI 发起重抓,真实端点进入取页;③取页未完成时切断那条 POST 连接,
  端点线程继续执行;④CLI 的只读查询拿到的是**动作之前**那一版;⑤预算给了 2 秒,CLI 却在
  约 0.056 秒(显式 `--refetch`)和 0.047 秒(普通重复提交)以 **0** 退出,输出
  `status=bad_content`、`收下的那一份看不出是正文`,并劝「加 --refetch 会重抓一次」;
  ⑥CLI 返回之后放行原请求,真实后端两次都返回 `replaced=true`,库里新正文
  `content_ok=true`,真实导出各生成 1 篇。**所以那句话把一件正在成功的事说成了需要再来
  一次**,而重抓会再动库里那一份。这一支和 `--refetch` 无关:普通重复提交撞上坏内容,
  后端也会进受控重抓。
- **Markdown 的语法还有两处没认全**(实测,同环境的 `markdown_it` 对两组都
  解析到「应处理」那一列):`见 [原文](https://example.org/A_&#40;B&#41;) 这篇` 实际用到的
  是 `…/A_&#40;B&#41;` 而不是 `…/A_(B)`(字符实体没解码);显示文字里带代码跨度的那种
  ——``[看 `](x)` 这个](目标)`` —— 整段结构认不出来,于是退回裸地址,**有些正常链接还会被
  说成没有链接**。两处都落在「收录 / `--state` / `--refetch` 共用的那条解析」上。
- **已删除或已换好的文章被说成旧状态**(实测):①重抓等待期间把同一篇清理掉,
  终端照旧说「库里那一份没动」—— 那是在描述一篇不存在的文章;②另一处已经换好正文,终端
  仍说「看不出是正文」并提示再抓一次 —— 那个结论来自回包里**请求开始那一刻**的
  `content_ok`。根因是「存在性和质量的证据约束只落实在部分等待分支」:提前收口
  (`--no-wait`)、无需等待、查询失败这几条路径仍会用过时判断收口。
- **不完整的 IPv6 服务地址仍是 traceback**(实测):`--api http://[::1` 在
  `urlsplit` 这一步就抛 `ValueError: Invalid IPv6 URL`,而上一轮只把取端口那一步包了起来。
- **一段带大量未闭合 `[` 的文字会让解析耗时明显增长**(实测):每个 `[` 各自
  扫到末尾找配对,复杂度随长度平方涨。
- **`--api` 写错会变成 traceback**(实测):
  `scripts/grab_cli.py --api not-a-url --json --state https://example.org/post` 退出 1、
  **stdout 一个字都没有**、stderr 是 `ValueError: unknown url type` 的 traceback ——
  它发生在 `urllib.request.Request` 构造那一步,排在通道层那套异常归一化**之前**。
  而「一条输入对一行结果」是这条入口的契约,所以这档归**参数错**(退出 2、一个请求都不发)。
- **断线之后那次保存随后成功,而命令行已经说了「没收下」**(实测,真
  `grab_link` + 真准入/正文处理 + 临时 feeds.db + 真 `sync.export`,只把外部取页换成
  由事件控制的固定页、起管道打桩成 busy):①后端进入取页;②投递那条连接断开,动作仍在

  `status=failed`、`label=没收下`、`detail=库里没有这一行，这条没存下来；再投一次`;

  1 篇。**skill 对 `failed` 的承诺是「一个字节都没写」**,所以那是谎报,而照它重投会
  多抓一次。
- **可选字段表达的安全约束,在没重启的服务上静默消失**(实测,拿

## 还没做的

- **公众号链接照旧多半收不到** —— 不是因为我们按域名拒它(那一版已经改掉了),而是对方

  (`wechat_local` 的射程)。**真能直接读到的那一篇会在两棵树下各留一份**,下面那条说的就是
  这件事。
- **查重只问 `feed_items`**,不问 kb.db 的 `documents`。前者覆盖全部订阅类来源;公众号那棵树
  在后者 —— 所以一篇真能直接读到正文的绿泡泡文章,这里答不出「公众号那边收过了」,它会在
  收件桶里再落一份(跨树重复在这个库里本来就有:实测同一条 url 同时躺在 rss / web / digest
  三棵树下,`documents.url` 没有唯一约束)。要跨到 vault 全库查重再说。(kb.db 那一侧现在只被
  问「vault 里当前这一份索引进去了没有」—— 那是 `done` 的判据,不是查重。)
- **「还没写进知识库」只在用户再投一次、或者他自己点一次「写入知识库」时才被发现**。没有后台
  巡检去扫「暂存了但没导出」的条目 —— 定时同步那一轮的 export 会顺手兜住它们,所以那是一个
  时间问题而不是一个会永久卡住的状态。
- **没有「批量从文件导入」这一档**。入口有三个:面板、`POST /api/grab`、以及
  `./kb.sh grab`(skill `kb-grab` 打同一条)。命令行那条认 `-`(标准输入),所以
  `pbpaste | ./kb.sh grab -` 和 `./kb.sh grab - < links.txt` 够用了,没有再做一个
  读文件的子命令。
- **收件桶在通用订阅编辑器里仍然能改地址、停用、开「补抓原文」**,而这三样对这一类都不适用
  (开了补抓会让已经拿到正文的条目重新排队、X 那条还会转去走普通网页提取)。界面上要主动点
  进订阅管理、而且那颗开关自带「全文订阅不要开启」的警告,所以这一轮没动它;真要钉死得同时
  改 `source_forms.js`(按 `pollable` 隐藏不适用字段)和后端约束,那是「订阅编辑器」那一块
  的射程。
- **两种形状会被准入那一道误拒**:①正文区里渲染真实、**已生效**的密码框的教学文章
  (页眉、`nav`、页脚、侧栏里的登录框不会,`<template>` 里的 demo 也不会);②**整页复读
  同一段**的页面(真实站点里少见,夹具里那种 `'…' * 12` 的省事写法会中)。两样都是刻意选
  的那一边:误拒的代价是用户自己复制一次正文,错存的代价是 `DO NOTHING` 把登录墙永久钉成
  这一篇 —— 而且现在误拒之外还多了一条出路,错存的那些点一下「重新抓一次」就能换回来。
- **结构上与文章不可分的纯文字登录提示页**(不复读、段段各不相同、带着文章标记)**仍可能
  被收下**,而且它过得了质量那一道、`content_ok` 恒真。这一档没有打补丁:它的出路是投递栏

  判据认不出的东西恰恰最需要换,所以只要库里有这一行,人就随时能要求重抓(审查实测过「出路
  架在同一道判据上」的后果:原站恢复可读之后重投仍回「已经在知识库里了」,HTTP 发出 0 次)。
