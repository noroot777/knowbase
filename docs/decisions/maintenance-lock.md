# kb.db 的维护互斥锁(kb/maintenance.py)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束(原 CLAUDE.md「kb.db 的维护互斥锁(kb/maintenance.py)」)

- **写 kb.db + vault 的几条路共用一把跨进程独占锁**(`maintenance_lock()`,flock 在 `data/feeds-trim.lock` 上):存量清
  理脚本、订阅同步的存盘与导出、索引的两条入口(`pipeline_stages._run_index`、`cli.cmd_index`)、条目化的就地入库、提取
  的 tag 回写(**四个**调用方:管道 `_extract_pass`、`kb extract --writeback`、`scripts/extract_parallel.py`、软广补判经
  `sync_promo_tag` 进来的)、提取结果的交付(`commit_extraction`)。
- **口径是「凡是写 kb.db 或 vault 文件的入口」,不是「两条索引入口」** —— 条目化那条自称「只增不删」,可它末尾照样调
  `embed_pending_chunks`,而那个函数补的是**全库**待编码的 chunk。判据只能是**写哪张表** + **写不写 vault 里的文章文
  件**。
- **粒度是整趟,不是只圈写的那几句**(竞态的那一半在「读」),所以 scan → upsert → remove 一整段都在锁里。**向量编码也
  在锁里**:`chunk_vec` 是 sqlite_vec 虚表、**没有外键级联**,清理在中间删掉那些 chunk 的话后面几批会按不存在的 chunk
  id 插回向量,而这些孤儿行**照样占着语义检索的候选名额**。代价是一轮大编码会攥着锁几分钟,这是统一互斥的标价。
- **等待有上限,而且等的时候要出声**(`KB_MAINT_LOCK_WAIT`,默认 900 秒;`on_wait` 立刻一次、之后每 60 秒一次)。超时抛
  `LockBusy`,三处一律「什么都没动」收场。**无限等更坏**:管道是单例,一个卡住的持锁者会把面板同步、定时同步和日报一起
  冻死。
- **等锁期间还认「停止」,而且认它的回调跟出声那个分开**(`on_poll` 每 0.25 秒一次,抛 `_StopWhileWaiting` 让阶段落
  `stopped` 而不是红)。**`flock` 一成功就返回,所以拿到锁之后还要再认一次**,但**只在真等过锁时才补这一次**(无条件检
  查会把刚放进 index 的那一轮当场顶成 stopped)。
- **提取的 tag 回写也在锁里,而且锁内要先确认这一篇还在**(`_still_indexed`,不在就返回 False、**不抛异常**)——
  `writeback_tags` 是整份读改写,清理在中间把这一篇删干净的话那次写回**把 md 文件重新创建出来**,比 index 那条更糟(文件
  回来之后谁也收不掉)。**回写的粒度是「每篇各取一次」,不是整趟提取**,模型请求留在锁外。
- **取锁之前必须先把写事务落盘,而这件事由共用入口自己负责**(`if conn.in_transaction: conn.commit()`)—— **SQLite 的写
  锁不认这把维护锁**,攥着没提交的写事务去等锁,持锁的清理就卡在自己的 DELETE 上。判据是**两层**:共用入口自己 flush +
  调用点时序照旧写明白,另有一条回归把全仓调用点的名单钉住。
- **补判等不到锁时 `LockBusy` 照常抛出去、整轮中止**(`_flag_in_vault` 只接 `OSError`)。
- **「改一篇已索引 md 的展示层」只有一个入口:`kb.doc_rewrite.rewriting()`**(读原文 → 变换 → 写回 → 登记
  `content_hash` → 提交,整段在锁里、全程**同一份快照**)。`wiki_daily.step_linkify` 和
  `scripts/backfill_youtube_summaries.py` 两条旁路都走它;绕过去自己 `write_text` + 刷 hash 就等于绕过下面那两道证明。
- **登记 `documents.content_hash` = 声明「这份文件已经索引过了」,要三样证明,而且三样都在
  `doc_rewrite.register_written` 这一个边界上 —— 不许在某个调用者里自证。**
  ①**登记的是调用方本次真正写出去的那一份**(交付写出快照,退出前再读一次磁盘比对;管「别人插进来改了这个文件」);
  ②**这一份现在重新索引一次,库里那些从文件来的东西不会变**(`doc_rewrite.index_projection_matches`,管「变换自己越界
  改了索引看得见的东西」);③**库里记的还是动手之前那个 hash**(条件 UPDATE 自己的 WHERE)。
  **不满足就保留待索引,不是认证**(0 行正是想要的末态)。
- **③ 的 `expect` 不是独立参数,就是 `hash(before)`,而 `before` 交的是「索引消费的那一份原文」本身、不是它的 hash。**
  两个值分开传时它们可以对不上,而一旦对不上,② 拿着一份**不是索引消费的**原文去判「文件这句话动没动」,判出来的每个
  结论都没有依据。`register_written(conn, path, before, written)` 里 `before=None`(调用方连动手之前那一份都读不出来)
  一律拒绝 —— 那时 ③ 本来也必然 0 行,两道一致。
- **「刚读到」不许充当「刚写出」。** 登记用的 hash 和 ① 比的那一份都**取自调用方交付的写出快照**,不是退出时重读磁盘
  的那一份。所以写 md 的那几个函数一律**返回写出去的整文**(`writeback_tags`、`remove_writeback_tag`、
  `align_promo_tag`、`Rewriting.write` 存的 `new_text`),`refresh_content_hash` 也要求必传 `written`、自己不读磁盘
  (`tests/test_extraction_body_version.py` 钉着这条签名和「函数体里不许出现 read_text」)。
- **② 比的是整份索引投影,不是模型输入那三样。** `index_input_matches`(标题/账号/拼接正文)**只给软广补判用** —— 它判
  的是「能不能固化一个判定」。拿它签「已索引」会漏掉 `doc_tags`/`url`/`published`/`source`/`chunk.heading`,还会把**分块
  边界**不同当成相同:审查按字段逐个用独立子进程实测,五种外来编辑全被盖了章,连跑两趟 `kb index` 都报「未变 1」。
  投影本身走 `scanner.doc_from_text`(**和索引同一个函数**),比的是真实索引从这一份文件派生出来的每一样;
  `tests/test_doc_rewrite_roster.py` 按它的 SQL 枚举列名,索引哪天多写一列就在那儿红。
- **索引不是 `upsert_document` 完就完了 —— ② 要连 upsert 之后那一步一起比。** 三个真实索引入口
  (`cli._index_pass`、`pipeline_stages._index_pass`、`pipeline_stages._ingest_pass`)都在 upsert 之后接着跑
  `parse_pretagged` → `save_extraction`,把 frontmatter 里的 `summary` 和 `project`/`kind` 写进 `documents.summary` 和
  `entities`,而 `content_hash` 跳过的是**整趟**。这两样也是用户查得到的东西(`aggregate` 的实体枚举按 `entities.kind`
  筛、把 `documents.summary` 返回出去),不是展示层:漏掉它们的实测后果是外来编辑改了 md 里的 summary 或 kind,收据照
  签,连跑两趟 `kb index` 都报「未变 1」,库里和枚举一直是旧值,**只有强制重建才纠正得了**。名单那一侧另有一条红钉住
  「这一趟都调了我们哪些函数」——多一步写库就在那儿红,而不是等某天有人报「那一列永远是旧值」。
- **这一层只许问「文件自己这句话动没动」,不许问「库里和文件一样吗」。** 后者会把一个合法末态判成不一致:模型提取
  (`kb extract`,带不带 `--writeback` 都一样)会把自己那句摘要和 kind 写进库,而 md 里可能压根没有
  `summary:`/`project:`/`kind:` 那几行(走 `--writeback` 回写的普通文章就是这样)、或者仍写着条目化来源 frontmatter 里
  旧的那句。**那种 md 重新索引一次,`parse_pretagged` 会拿 `""` 和 `other` 把库里那两样盖掉,所以「不等」在那一篇上是
  常态**;拿它当拒绝理由等于给主回写判死刑 —— 拒绝 → 下一轮重建 → 模型摘要和 kind 当场没了,`extracted_at` 非空也不会
  重提。**「文件没指派的实体一律 other」这个默认档同理不算「文件说过的话」**(`_extraction_claims` 只收下非默认的那
  几个):把它算进去,`--writeback` 连 `entity/*` 一起回写的那一步就永久登记不上。**撤回也算动**(文件原来说了一句、
  现在不说了),所以比的是两份快照而不是「现在说了什么」—— 只看现在的话,撤回之后新值是空串,一句假的「一致」就把旧值
  永久留在库里。
- **标签这一样不是集合全等,分三段判 —— 这是 ② 最容易判错的地方。**
  - **文件上有的,库里得都有**(一个方向)。反方向不能按全等判:`kb extract` 不带 `--writeback` 时提取结果只落
    `doc_tags`、不回写文件,那是**合法状态**。按全等判它,代价**不是**「白重建一次」——
    `upsert_document` 重建 `doc_tags` 是 `DELETE` 全部再**只从文件**重建,所以那次「保守地留待下一轮」恰好触发了把这批
    标签永久删掉的那一次重建,而 `extracted_at` 非空、这一篇不会被重新提取回来。实测:一次双链化(或一次软广回写)之后
    连跑两轮索引,库里只剩 `source/*`,按主题和实体过滤全空,再同步也不恢复。
  - **文件上刚删掉的,库里得也没了。这一段要「索引消费的那一份原文」(`before`)才判得出来。** 末态上「库里有、文件
    没有」的两种来源长得一模一样 —— 上面那个合法状态,和「外来编辑刚把 md 上那行删了」;**没有原文就只能二选一地放过
    一种**,而两种的代价都是永久丢数据(放过前者吞掉一批提取标签,放过后者让删掉的标签永远筛得到)。拿 `before` 比
    就分得开:它在不在原文里。实测只有单向那一段时的后果:删掉的标签收据照签,两轮索引之后库里那行还在,按它过滤照旧
    命中这一篇,再同步也不恢复。
  - **`flag/软广` 那一行按落库那份判定归一化,规则和索引自己用的是同一份**(`store.promo_tag_wanted`):hard 该有、
    none/soft 该没有、**还没判过(`''`)就跟着文件**(那时 md 那行是提取阶段写进去的唯一记录,索引不覆盖它)。无条件把它
    从两边排除是错的:还没判过的那一篇上,外来编辑增删它判据完全看不见,而真实索引这时跟着文件 —— 按这个标签筛选从此
    停在旧结果上。那条规则有**两份实现**(纯函数 + `_align_promo_tag` 的两句 SQL,后者的判据必须待在自己的 WHERE 里),
    所以有一条回归真跑 `upsert_document` 再和纯函数对账,四档判定 × 文件有/无八个组合全覆盖。
- **「判据误报顶多白重建一次」这个假设只对一部分字段成立,别再按它推理。** 重建对 `documents` 的列是覆盖(无害)、对
  `chunks` 是重切(无害),但对 `doc_tags` 是**先删全部再只从文件重建** —— 库里专有的那批标签(提取只落库那种)当场永久
  没了。所以「拿不准就保守拒绝」在标签这一样上不是安全侧:判据得先分清差异的**方向**和**归属**,而「归属」只有拿
  原文(`before`)比才问得出来 —— 不是靠在两种误报里挑一种认下来。
- **①② 对大多数外来编辑互为备份,所以「某一道还在不在」看不出来 —— 想分辨得让另一道闭嘴,而那取决于**注入时点**。
  外来进程插在**写回之后**那一瞬:① 当场拦下,② 压根轮不到说话;插在**写入函数读文件之前**:那个改动被带进了我们自己
  写出去的全文,① 合法通过,只有 ② 拦得住。**两种时点在回归里各要有一组**(夹具里是
  `rival_slips_in_after_the_main_writeback` 和 `rival_slips_in_before_the_main_writeback_reads`)—— 只有后一种时点才
  分辨得出 ② 的那几条规则还在不在。自测踩过两次:注入拿掉其中一道,整组绿着。
  ① 独有的那一档是「外来编辑没动索引投影」(② 对它没意见,可收据不该盖到别人那一份上);② 独有的那几档是「变换自己写
  进去的东西还没落库」、「越界改了索引看得见的东西」、「还没判过软广时外来增删那行 flag」、「外来编辑删掉了一行标签 /
  改了 summary / 改了 kind」。**①-独有那一档的摆盘要挑「索引压根不读的 frontmatter 键」**(`note:` 那类)—— 原来挑的是
  `summary:`,它现在进投影了,② 对它有意见,那就不是那一档了。
- **「注入全绿先怀疑用例」在这里的具体形态是:夹具摆出来的是不是生产那个形状。** 本轮两条注入(把「没指派就是 other」
  也算成文件说过的话、`kinds` 只看现在指派的)第一次都是全绿,而注入确实落地了 —— 原因是夹具的主回写只写 `topic/`
  从不写 `entity/*`,而生产里 `--writeback` 两样都写(`extraction_tags`);以及「撤回指派」那个方向压根没有用例。
  补上那两个形状之后两条各红一条。**所以 `run_main_writeback` 带了 `entity=` 参数** —— 只写 topic 的摆盘对「实体 kind
  这一段判错了」是瞎的。
- **「动了」不等于「该拒」:动了而且**已经进库**的那一档必须照旧登记得上。** 摘要回填就是这一档(同一个协调区间里把
  `summary:` 写进 frontmatter **并且**更新 `documents.summary`),写成「动了就拒」的话它从此一次都登记不上,而症状只是
  「每轮索引都在重建这批文章」。**kind 那一段同一个取舍,但它这半边目前没有消费方** —— 仓库里没有哪条路会合法地移动
  `project:`/`kind:`,所以把它换成「动了就拒」整组全绿(实测)。**不删它**的理由不是「有人在用」,而是误报在这里不是
  安全侧:一次拒绝就是一次破坏性重建(`DELETE` 掉库里专有的那批提取标签)。那一半因此按**单元**的形状钉着
  (`test_a_kind_change_that_already_landed_is_certified`),用例自己写明「这一半没有端到端的红」。
- **合法回写必须照旧登记得上。** 真实链路是**落库 → 提交 → 回写 md**(`save_extraction` 先把 topic/entity 插进
  `doc_tags`),所以登记那一刻两边本来就一致。判据误报的代价不是「白重建一次」而是**永久拦住**:主回写从此一次都登记不
  上,每轮索引把回写过的整批文章重切 chunk、重编码向量,而外面一点看不出来。所以两边各有一条反向钉
  (`test_a_legitimate_writeback_still_gets_certified`、`test_the_normal_path_still_refreshes`);手工摆盘的夹具要把 md 上
  那组 tag 一起插进 `doc_tags`,不然每条用例拒绝的理由都悄悄变成「标签还没进库」。
- **写 `documents.content_hash` 的语句全仓只许有两处**:索引自己的 upsert(`store.upsert_document`)和那道带三样证明的
  登记(`doc_rewrite.register_written`)。`extract_writeback.refresh_content_hash` 只是转发。
- **`register_written` 里读几张表 + 那句条件 UPDATE 要在同一个事务里**(`BEGIN IMMEDIATE`;调用方已经在写事务里就沿用
  它那一个,再 BEGIN 会抛)。跨四张表(documents / doc_tags / chunks / entities)没法把判据塞进某一句的 WHERE,所以靠
  事务给一个快照;锁序仍是维护锁 → SQLite 写锁。
- **投影判据里的来源名按路径推**(`source_name_of`:`source/<name>/...`),**不去遍历 `config.SOURCES` 比 root** —— 那张表
  在模块加载时按当时的 `VAULT_ROOT` 把 root 算死了,而夹具一律打桩 `extract.VAULT_ROOT`,比 root 会在测试里全部失配、判据
  退化成「永远不一致」。路径不是那个形状时退回库里那个值(漏的是「fm 原来写的 source 和 `src.name` 不同、这次又被外来
  编辑删掉那行」这一窄档;宁可漏它,也不能把合法回写永久拦住)。`scanner.doc_from_text` 也因此接受 `rel_path`:让它
  `relative_to(scanner.VAULT_ROOT)` 等于把判据押在「两个模块级 `VAULT_ROOT` 在每个夹具里都一起被打桩」上。
- **分界线改了:「管道自动跑的写 vault 入口都该取这把锁,手工一次性运维脚本留在外面」这条分法对「登记已索引」不成立。**
  「人在边上看着」挡不住**另一个进程**里正在跑的定时同步 —— `backfill_youtube_summaries.py` 就是按手工脚本放在外面的,
  实测它和一个真·独立子进程交错时照样把一份未索引的新正文认证成「已索引」。**取不取锁按「写不写 vault 里的文章文件 +
  写不写 kb.db」问,不按「谁来按回车」问。**
- **给原来不取锁的路新加取锁,它自己就是一个新失败口子,各自收住、都不许把「什么都没做」报成成功。**
  **等的时候默认出声**(`rewriting(..., on_wait=)` 默认打一行「等维护锁」,要静默得显式传)—— 这两条脚本的输出是直接给
  人看的,一声不出地等满 15 分钟和卡死长得一模一样。**`step_linkify` 等不到锁只收住这一步**:打一行 + `break`,**退出码
  还是 0、pages/index/两张图谱照跑**(双链化按 GRAPH_MARK 幂等,下一轮原样补回来;后面几步压根不碰这把锁)——让
  `LockBusy` 冒上去等于一次锁超时就把整条 wiki 阶段标红。**`backfill_youtube_summaries.py` 把已补上的那几篇提交掉再退
  2**:它幂等可重跑,「补了一半」是合法中间态、回滚掉反而白干;但退 0 不行 —— 一次性运维脚本,人看完那行就走,报 0 等
  于说「244 篇都补齐了」而实际可能一篇没补。
- **不会抱死**:这是唯一一把跨进程维护锁,没有任何路径持着它再去取别的锁;同线程重入直接放行(flock 认的是 open file
  description)。锁的是 `data/` 下**单独的 lockfile**,只创建不删除;**文件名沿用 `feeds-trim.lock`**,改名等于在升级窗
  口里让两个持锁者同时写。
- **`test_feed_translate.ColumnBackfillTests.test_two_first_accesses_both_succeed` 是一条已知的负载敏感 flaky,红了先别当
  回归。** 判据是它自己的报错内容:`duplicate column name` 才是它要抓的回归,`database is locked` 是 `reg.db()` 在
  `BEGIN IMMEDIATE` 之前那两句 DDL/PRAGMA 上的争锁窗口。
- **测试里必须把 `maintenance.DATA_DIR` 指到 tmp**,不指的话会去 flock **生产**那个 lockfile。
- 详细见 `docs/decisions/maintenance-lock.md`。

## 事故形态与实测证据

- **写 kb.db + vault 的几条路共用一把跨进程独占锁**(`maintenance_lock()`,flock 在
  `data/feeds-trim.lock` 上):存量清理脚本、订阅同步的存盘(`sync._save_result`)与
  导出(`sync.export`)、索引的两条入口(`pipeline_stages._run_index`、`cli.cmd_index`)、
  条目化的就地入库(`pipeline_stages._ingest_pretagged_sources`)、提取的 tag 回写
  (`extract.writeback_extraction`,**四个**调用方共用它这一份:三条提取路径 +
  软广补判经 `sync_promo_tag` 进来)、**提取结果的交付**(`extract.commit_extraction`
  把校验 → 落库 → 提交 → 回写圈成一个协调区间,三条读正文的提取路径一律走它 ——
  详见「聚合源的正文补抓」那条「一次提取的结果要和它基于的那份正文绑在一起」)。
  每一条都是「先把一份快照读进内存 → 过一会儿再按它写盘」,两两不互斥就能用**删除
  之前**那份快照把另一边刚删掉的东西复活。**索引那两条是 2026-10-01 第 2 轮审查补上
  的**:清理把一篇旧文从三处删干净、进度标成完成之后,一轮并发的 index 拿它删除之前
  读到的那个 `Doc` 完成 upsert —— `documents=1`、FTS 命中 1,而 vault 里那个文件已经
  不存在:搜得到、点开没有原文,重跑清理也只会说「无事可做」(feeds 行早没了)。
- **口径是「凡是写 kb.db 或 vault 文件的入口」,不是「两条索引入口」。** 条目化
  那条是紧接着的第 1 轮审查抓出来的:它自称「只增不删」,看着跟清理没关系,可它末尾
  照样调 `embed_pending_chunks` —— 而那个函数补的是**全库**待编码的 chunk、不限于本轮
  自己写进去的那些,所以清理删掉的 chunk 会被它按旧快照插回向量(实测 151 行孤儿向量,
  语义检索当场返回空)。判据因此只能是**写哪张表**:全仓 `upsert_document` 三处
  (`_index_pass` / `_ingest_pass` / `cli._index_pass`)、`insert_vectors` 只有
  `embed_pending_chunks` 一个入口而它有三个调用点,现在全在锁里。**写 vault 文件那一半
  是第 2 轮审查补的**(见下面「tag 回写」那条):md 文件本身也是被清理删掉的东西之一,
  按「写哪张表」问压根问不到它。再添一条写入方时照这两个判据走(写不写 kb.db、写不写
  vault 里的文章文件),别照「它是不是索引」。
- **粒度是整趟,不是只圈写的那几句。** 竞态的那一半在「读」:scan 读到的是删除之前
  的文件内容,只把 upsert / `remove_missing_documents` 圈起来的话,旧快照照样写得
  进去。所以 scan → upsert → remove 一整段都在锁里(`pipeline_stages._index_pass`、
  `cli._index_pass`)。
- **向量编码也在锁里。** `embed_pending_chunks` 先把「还没有向量的 chunk」整份读出来
  (id + 正文),再分批写回 `chunk_vec`;而 `chunk_vec` 是 sqlite_vec 的虚表、**没有
  外键级联**(`remove_missing_documents` 是按 chunk id 显式删它的),清理在这中间删掉
  那些 chunk 的话,后面几批会按已经不存在的 chunk id 把向量插回去 —— 这些孤儿行谁也
  不会再来收(「孤儿向量 0」是生产审计在看的一条不变量),**而且它们照样占着语义检索
  的候选名额**(`search` 无来源过滤时先取全局 top-150、再 JOIN 当前 chunks/documents,
  孤儿候选先占名额再被 JOIN 丢弃):于是清理之后**仍然留着**的文章被一批指向不存在
  chunk 的向量挤出结果,重跑索引也不恢复(2026-10-01 第 1 轮审查实测)。代价是一轮大
  编码会把锁攥上几分钟(`--reembed` 更久),**被它挡住的不止那个一次性清理脚本**:另一
  个进程的订阅存盘与导出也在等同一把锁。这是统一互斥的标价,接受它的理由是这几条路写
  的本来就是同一个库,串起来跑才是对的。
- **等待有上限,而且等的时候要出声**(`KB_MAINT_LOCK_WAIT`,默认 900 秒;`on_wait`
  立刻一次、之后每 `NOTIFY_EVERY`(60)秒一次,第一次就拿到锁时压根不调)。超时抛
  `LockBusy`,三处一律「什么都没动」收场:index 阶段标红写明原因(漏跑一轮下一轮自己
  补 —— 扫描是全量比对)、`kb index` 退 2、清理脚本退 2 且一个字节没改。**无限等更坏**:
  管道是单例,一个卡住的持锁者会把面板上的同步、定时同步和日报一起冻死,而「拿旧快照
  写回去的那行假结果」要等到下一次索引才被收掉。不出声也不行:面板那张卡片会一直停在
  「扫描 vault」,看着像卡死。
- **等锁期间还认「停止」,而且认它的回调跟出声那个分开**(`_lock_waiter` 给
  `on_poll` + `on_wait` 两个:前者每 `_POLL`(0.25)秒一次、只问「还要不要等」,抛
  `_StopWhileWaiting` 让阶段落 `stopped` 而不是红;后者只管低频出声)。挂在同一个回调
  上的话,等锁期间按下的那一下最坏要 `NOTIFY_EVERY`(60)秒后才被看见 —— 第 1 轮审查
  把等待上限缩成 2 秒实测,那一轮等满超时、落的是 `error / 索引没做`。
- **`flock` 一成功就返回,所以拿到锁之后还要再认一次**(`waited["on"] and
  stop_requested`)。循环是「试 flock → 没拿到才问一次」,锁正好在这两步之间松开的话
  下一轮直接 return、再也不问,这一轮会照常索引到底。**但只在真等过锁时才补这一次**:
  无条件检查会把管道编排刚放进 index 的那一轮当场顶成 stopped,而按钮承诺的是「当前
  阶段结束后停止」,不是取消刚开跑的这个阶段(回归里正反两条各钉一边)。
- **提取的 tag 回写也在锁里,而且锁内要先确认这一篇还在**(`extract.writeback_extraction`)。
  这条原来被显式**排除**在外,依据是「`chunks`/`doc_tags`/`entities` 对 `documents(path)`
  都是 `ON DELETE CASCADE`,给一个已删 path 写标签会被外键当场拒掉,所以提取这条路上
  没有复活可言」—— **那个依据只看了库、没看文件,是错的**(2026-10-01 第 2 轮审查两种
  合法时序各实测一次:`kb extract --writeback` 与同步的并行存量提取)。`writeback_tags`
  是「`read_text` 拿一份全文快照 → 改 frontmatter → `write_text` 整份写回」,清理在这中间
  把这一篇从 feeds.db / vault / kb.db 三处删干净的话,那次写回**把 md 文件重新创建出来**,
  下一轮索引合法地扫到它、upsert 回库,旧文从此搜得到点得开。外键级联挡不住:标签是在
  删除**之前**写进去并提交的,级联删除照样全部成功,它管的是那几张表,管不着谁在之后
  重建文件。**而且这一条比 index 那条更糟**:index 复活的只是一行 `documents`,下一轮
  `remove_missing_documents` 自己就收掉了;文件真的回来之后谁也收不掉 —— feeds.db 里
  已经没有这一条,重跑清理只会说「无事可做」。
- **回写的粒度是「每篇各取一次」,不是整趟提取**,而且模型请求留在锁外。竞态窗口只有
  单篇的 read→write 那一下(提取那一趟里真正读磁盘的就只有这一步),把整轮圈进去等于
  攥着锁等几十次 LLM 往返,面板上的同步、定时同步和日报一起冻住。index 必须整趟是因为
  它竞态的那一半是「把整个 vault 读成一份快照」,两件事不一样。
- **锁拿到手之后先复查「这一篇还在吗」**(`_still_indexed`:文件在 + `documents` 有行),
  不在就什么都不做、返回 False(「没改文件」),**不抛异常**。等锁的这段时间里清理很
  可能正是把它删掉了;而 `_extract_pass` 把回写和 `save_extraction` 包在同一个 try 里,
  抛出去就是把这一篇记成提取失败、面板标红 —— 文章是用户主动清理掉的,那是谎报一次
  故障。判定本身早就落库了,随后被外键级联一并删掉,末态干净。
- **取锁之前必须先把写事务落盘,而这件事由共用入口自己负责**
  (`writeback_extraction` 里那句 `if conn.in_transaction: conn.commit()`)。
  **SQLite 的写锁不认这把维护锁**:攥着 `save_promo` / `save_extraction` 留下的那个
  没提交的写事务去等锁,持锁的清理就卡在自己的 DELETE 上,两边互等到 SQLite 的 busy
  超时(默认 30 秒)把清理打断 —— 清理抛 `database is locked` 退出,feeds 行和 md 都
  删了、`_drop_index` 那一步没做完:**搜索里还留着刚删掉的旧文**(2026-10-01 第 3 轮
  审查跨进程实测 32.5 秒后报错,末态 `documents=1`、全文命中 1,要再跑一次清理才收得
  干净)。提前提交不新增副作用 —— 改了文件本来也要在锁内 `conn.commit()`,这只是把
  同一个提交挪早;四个调用方的判定都是逐篇独立、可重跑的,组内那次提交没有「要么全
  要么全不」的语义。
- **这条原来只写在调用方那一侧,于是漏掉了第四个调用方。** 第 2 轮定的契约是「三条
  提取路径先 commit 再回写」(管道 `_extract_pass`、`kb extract --writeback` 本来就是,
  `scripts/extract_parallel.py` 跟着改),可软广补判经 `sync_promo_tag` 进的是同一个
  入口,它在 `save_promo` 之后、整组提交**之前**回写 —— 而那一轮的回归**按名单枚举了
  三条路径**,名单本身就是缺口,16 项定向回归和全量测试全绿照过(2026-10-01 第 3 轮
  审查发现)。所以判据换成**两层**:共用入口自己 flush(锁序正确性不取决于「每个调用
  方都记得先提交」),调用点的时序照旧写明白(`promo_backfill.cmd_run` 整组判定先
  `conn.commit()`、再逐篇 `_flag_in_vault`),各有一条回归钉着;另有一条**把全仓调用
  点的名单也钉住**,多一处会在那里红,而不是等某次清理报 `database is locked`。
- **补判等不到锁时 `LockBusy` 照常抛出去、整轮中止**(`_flag_in_vault` 只接 `OSError`)。
  那说明另一头正在做维护,而这个脚本按 `promo_level=''` 本来就可重跑;把它接住继续,
  后面每篇还要各等一次 `KB_MAINT_LOCK_WAIT` 才是更坏的一种。
- **两条旁路后来闭合了,而且把原来那条分界线证伪了。**
  `scripts/wiki/wiki_daily.step_linkify` 和 `scripts/backfill_youtube_summaries.py` 也是
  「读一篇 vault 文章 → 改 → 整份写回 → 刷 `content_hash`」,原来按「管道自动跑的取锁,
  手工一次性脚本留在外面(人在边上看着、不会和定时清理撞上)」分到了两边:前者该补、
  后者不必。**后者那半句是错的** —— 审查用真·独立子进程在两条上都复现了:在
  「写完文件 → 刷 hash」之间让子进程取到真实维护锁并换掉整篇正文,
  `WHERE content_hash=expect` 合法命中、登记下去的却是那份未索引新文件的 hash;随后连跑
  两趟 `kb index` 都报「新增/更新 0,未变 1」,再走一轮同步的索引+提取也一样 —— 页面上
  搜新正文里的词「没有找到相关内容」、搜旧正文里的词仍命中旧片段,点开文章却是新正文。
  「人在边上看着」挡得住的是**这个**进程里的并发,挡不住另一个进程里的定时同步。
  现在两条都走 `kb.doc_rewrite.rewriting()`:整段在锁里、一份快照,登记之前还要自己证
  那两样(见上面硬约束那两条)。
- **反向验证踩的那一脚:注入必须自己证明「替换真的落地了」。** 第 1 道那次注入先报了「整组照旧全绿」,看上去就是「这道
  防线是冗余的」;真因是 `str.replace` 的目标串缩进写错了 4 个空格、**静默没匹配**,被测文件压根没改。补一句
  `assert old in s` 之后同一条注入红 3 条(两条跨进程交错 + 只改 frontmatter 那条)。所以「红 0 条先怀疑用例」要往前再
  推一格:**先怀疑注入本身有没有落地** —— 一次没落地的注入和一道真冗余的防线,输出一模一样,而据它下的结论会把一道
  有射程的防线写成「可以删」。换个角度钉同一件事:按**原缺陷的形状**注入(不核对 + 按磁盘那一份登记)只红 1 条,正是
  「只改 frontmatter 的外来编辑」那一档 —— 两道射程交叠,换掉整篇正文那一档谁都抓得住。
- **这次闭合自己带进来一档新东西:两条旁路从此会等锁、会超时。** 原来它们压根不取锁,也就从来不会停下来等;现在管道
  正在同步或索引时,它们最长等 `KB_MAINT_LOCK_WAIT`(默认 900 秒)然后抛 `LockBusy`。三件事各有一条回归钉着(出声、
  linkify 只收住这一步、回填退 2,口径见上面硬约束那条),反向验证也各有自己的定点注入:入口不把 `on_wait` 传给锁、
  两处各把 `except LockBusy` 换成接不住的异常 —— 每一条都只带出它对应的那条红。
- **回归清单**(摆盘 `tests/doc_rewrite_fixture.py`;行为与那三样证明 `tests/test_doc_rewrite.py`;**标签那一样**单列 `tests/test_doc_rewrite_tags.py`,三段规则各有定点注入 + 一条和真实索引的对账;**upsert 之后那一步派生的 summary / 实体 kind** 单列 `tests/test_doc_rewrite_derived.py`,两个方向各一条红、外加一条「判据读到的那句话 = 索引真写进去的」对账和两条「合法回写照旧登记得上」的反向钉;名单 `tests/test_doc_rewrite_roster.py`):子进程认锁时
  在协调区间里取不到锁(窗口关着);子进程不认锁、换掉整篇正文时不许被认证,而且下一趟
  索引要把新正文补上;只加一行 tag 的外来改动同样不许被认证(② 对它是瞎的)。反过来钉的
  那一边是**「只改展示层的那一次照旧登记得上」** —— 不钉的话「从此一次都不登记」也全绿,
  代价是每轮索引把双链化过的整批文章白重建一遍(chunk 重切 + 向量重编码)。
  还钉着「一个协调区间只许写回一次」和清理那两半:**md 已经没了**那半有两道挡
  (`_still_indexed` + 锁内那次读),**库里那行先没了、md 还在**那半只有 `_still_indexed`
  答得出来 —— 而清理正是先删库里那行,所以第二半才是那道检查的后果式红;名单那一侧还
  单独钉了「名单取好之后清理才动手」时真走一遍 `step_linkify` 也不许把 md 写回来。
  存量提取那条并发路径在 index 之前就被 join 掉了(见 `pipeline._run_pipeline`)。
- **`linkify_doc` 因此拆成了两个形状**:`wikilib.linkify_text(u, p, text)` 接受**调用方给
  的那一份文本**,`linkify_doc(u, p)` 仍自己读文件(留给只要「这篇装饰完长什么样」的调用
  方,比如 `tests/test_extract_no_body.py`)。`step_linkify` 必须用前者 —— 用后者就又是**两份
  快照**:它自己读一次算新文本,外面再读一次算 `before`,两次读之间别人的一次写入就让
  「动手之前那份 hash」指向一份我们压根没变换过的内容。
- **不会抱死**:这是系统里唯一一把跨进程维护锁,没有任何路径持着它再去取别的锁;同
  线程重入直接放行(flock 认的是 open file description,同进程换一个 fd 再锁会把自己
  锁死)。
- 锁的是 `data/` 下**单独的 lockfile**,只创建不删除(unlink 会让「A 持锁 → B 删文件
  → C 新建再持锁」出现两个持锁者,理由同 `secrets.json` 那把锁)。**文件名沿用 feeds
  那一版的 `feeds-trim.lock`**:改名等于在升级窗口里让老进程锁 A、新进程锁 B,两个持
  锁者同时写同一个库 —— 名字只是一个路径,不值这个风险。
- **`test_feed_translate.ColumnBackfillTests.test_two_first_accesses_both_succeed`
  是一条已知的负载敏感 flaky,红了先别当回归。** 它测的是补列那把写锁,却会被
  另一件事绊倒:`reg.db()` 在 `BEGIN IMMEDIATE` **之前**还有
  `executescript(SCHEMA)` 和 `PRAGMA journal_mode=WAL`,两个连接同时首访同一个
  新库时就在这两句上争锁(DDL 和切 journal 都要锁,而 PRAGMA 不走 busy handler,
  `timeout=30` 管不着它),于是偶发 `database is locked` —— 跟补列毫无关系。
  **判据是它自己的报错内容**:`duplicate column name` 才是这条用例要抓的那个
  回归,`database is locked` 是这个窗口。单独跑或只跑两三个模块时稳定绿,整组
  一起跑、机器负载上来才出现(2026-10-08 实测:HEAD 版 0/11,前面多一条带 tar
  打包的用例之后 2~3/8;把屏障超时从 1 秒压到 0.2 秒仍然 2/10,**所以诱因不是
  屏障**,压它没用)。**并发首访那个 locked 窗口是真实的产品行为**(生产里两个
  请求同时首访老库就会撞上,只是 `_migrate` 是毫秒级、窗口极窄),要修得动
  `reg.db()` 的锁序 —— 那是核心路径,得单独立项、单独审查,别挂在别的修复里顺手改。
- **测试里必须把 `maintenance.DATA_DIR` 指到 tmp**(`tests/feed_trim_fixture.py`,以及
