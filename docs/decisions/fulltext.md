# 聚合源的正文补抓(kb/feeds/fulltext.py + readable.py)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束(原 CLAUDE.md「聚合源的正文补抓(kb/feeds/fulltext.py + readable.py)」)

- **feed 只给一个跳转壳时(标题 + 域名 + 得分),顺着原文链接把正文抓回来** —— 按壳入库的话 vault 里那篇 md 没
  有内容:检索搜不到、打标判不出实体、日报里只剩一行标题。
- **开关是订阅级的、默认关**(`subscriptions.fulltext`):对本来就给全文的源再抓一次是纯粹的降级。
  `defaults.json` 里**只标了 HN Buzzing** 一条;那段只对新库跑,存量库要在面板上点一下。**给 defaults.json 加字
  段必须同时改那条 INSERT。**
- **独立一列,不放 `config`** —— 换链接时 `save_subscription` 的 `reset` 会把 config 整个清空。
- **这一步排在翻译之前。还排在补抓队列里的条目既不翻译也不导出**,两边各认一次本模块的 `queued_sql`。队列判据:
  属于某条开了补抓的订阅、`fulltext_at` 空、`fulltext_tries < MAX_TRIES`;**出口就是第三条**(试满仍抓不动的按
  feed 原本那份壳走完翻译和导出)。`sync._export` 里收窄 base 那一句**必须排在所有统计之后**。
- **「在队列里」和「没入库」是两件事,按 `exported_hash` 分两态**(4 `fetching` / 5 `refetching`)—— 打开这个开
  关最常见的时机正是「几百条壳已经在 vault 里了」。已导出那一档如实显示库里那份壳、照旧能展开,顶上那句计数也只
  数还没入库那一档。**待补抓的条目标题照显示**,换掉的只有正文那一段。
- **提取器自己写,不装 readability/trafilatura**(我们要的输出是**纯文本**,而块级边界已经由 `fetching.plain` 定
  死;而且 `pyproject.toml` 一动 `uv run` 就要重建 editable 包)。
- **明确的 Markdown 原文先于网页提取**(`markdown_source`):GitHub README/Markdown 文件、直接 Markdown 链接与明确的
  Markdown 响应保留源格式。优先请求和 HTML 回退共用单次预算,二进制或 HTML 冒充的 Markdown 不接收;通用 HTML 提取契约不变。
- **`find_all` 是快照,`decompose()` 之前必须先问「这个节点还在吗」**(`_gone`;bs4 把被销毁节点的 `attrs` 置成
  None)。
- **`header`/`footer`/`aside` 要看位置,不能无条件删** —— 只有落在 `<article>`/`<main>` **外面**的才是站点部件
  (`_DROP_OUTSIDE`)。按 class 名剔噪声只对 `div`/`section` 做。
- **「这一页可以被确认为正文、写进库里」那一道两条链路共用一份**(`grab_page.admit`:提取 + 判据,**连先后顺序
  一起**;手动收录那边的判据表、误拒史和每一道的理由在 `link-grab.md` 第一节)。原先这道准入只接在手动收录那一头,
  补抓这一头直接拿 `extract_or_reason` 的结果当正文 —— **八道一道都不过**。事故形态:一张验证页/登录墙自己也有
  文字、够长就一路过关,被 `_save` 写进 `feed_items.body`、写上 `fulltext_at`、**退出重试队列**,而这一档
  **不可恢复**(后面任何一轮同步都不会再碰它,面板那颗「重试失败项」是订阅级的、不碰 `fulltext_at`)。实测
  (2026-10-21 审查第 1 轮,`tests/test_feed_fulltext.FullTextCase` + 三个样本:无脚本 / 2.9 MB 脚本 / 3 MB+ 脚本):
  一张 **1453 字节、一行脚本都没有**的 Cloudflare 关卡页跑 `fetch_pending('rss')` 得到 `done=1`、正文被换成
  「Verify you are human…」、`pending` 归零 —— **`62a0531` 基线上就是这个结果**。
  - **结论分三档,不是「收 / 不收」两档**(`grab_page.Admission`:**确认为正文 / 确定关卡 / 证据不足**)。
    **把后两档合成一档就是上一版两个洞的共同根** —— 它等于同时断言了两件没有证据的事:「份额未达线 ⇒ 这就是
    正文」和「份额达线 ⇒ 对方拦着你」。两侧都实测到过后果,见下面那两条。
    - **确定关卡**(①-⑤:关卡响应头、路由、页面真挂着的关卡组件、生效的登录墙、页面自己的标题)说得出
      「对方拦着你」,抛 `fetching.Gated`,**留在原重试语义里**:`fulltext_tries` 照旧计次,试满 `MAX_TRIES`
      按壳入库 —— 和「这一页我们读不懂」那一档完全一样的出口。一道验证页后面的链接不该让这条订阅的内容永远
      进不了知识库。
    - **证据不足**(⑥-⑧:份额、拒绝说明样板、内容确认不了)只说得出「我没能确认这一页哪一段是正文」,抛
      `fulltext.Unconfirmed`。**写库那一下两档一样严(都不写)**,差别在落地:这一档把那半句话记进
      `feed_items.fulltext_hold`,**一次就挂起**(`queued_sql` 把 hold 非空的排除),等人看一眼。
    - **挂起这一档不扣确定失败那份预算,`queued_sql` 的 ③ 和 ④ 是两件不同的事。** ④(`fulltext_tries<MAX_TRIES`)
      是「对方真的拦着/真的连不上,试到第三次就认了」的预算;③(`fulltext_hold=''`)是「我**没能判断**这一页是
      不是正文」。**合成一件就是审查第 1 轮的第 2 条**:再敲同一扇门不会让我们知道得更多(同一张页面、同一套
      判据,答案不会变),而扣掉预算的后果是三轮之后**静默**退回摘要 —— 审查四轮 `materialize` 实测的末态是
      `tries=3 / pending=0 / 原摘要按 summary 导出 / 第四轮一次请求都不发`,而面板上只有一句「订阅摘要」。
      回归按**请求次数**钉:连跑 `MAX_TRIES + 1` 轮同步,原文只该被请求 **1** 次。
    - **`fulltext_hold` 那一列只有三件事动得了它,`_fail` 的 `hold` 参数就是这三值。** 这是审查第 1 轮的
      第 3 条:上一版每次都写(空串也写),理由写的是「它记的是最后一次的结论」—— 那个判据是错的。
      - **非空**(`Unconfirmed`)= 判出证据不足,写进去、挂起;
      - **`''`**(`Gated`)= **查清了**,待办跟着清掉。否则 `held()` 里会攒下一堆「其实已经查清是对方拦着」
        的行,而那正是让人不再看那个列表的东西。`_save` 成功时一起清掉(留着会把一条**已经补到全文**的条目
        列成待办);
      - **`None`(缺省)** = 超时、连不上、对方 500、提取器交白卷 —— **什么都没查清,那一列原样不动**。
        **一次尝试的结果不能充当正文身份的最终结论。** 上一版把它们当成「先前那个问题已经判清」,实测后果:
        超时和空页面两种第三次,hold 都归空、`held()` 变空列表、站点恢复之后第四轮一次请求都不发。
    - **「证据不足」照旧计进 `summary['failed']`,另外多记一笔 `summary['held']`。** 它确实没补到正文,面板那句
      「N 条抓取失败」要如实含着它、失败明细照旧列出它(人要看的就是那半句话);`held` 是**加一个说明**
      (「其中 N 条看不出是不是正文,已挂起等人看一眼」),不是换一种分类。
    - **拒绝的那一下一个字节都不改**(两档都一样):壳留着、`content_kind` 还是 `summary`、`fulltext_at` 不写。
  - **人工出口得是人真点得到的东西,落了盘的状态不算出口。** 审查第 1 轮的第 2 条另一半:上一版
    `held()`/`release()` 只是两个 Python 函数,全仓 `rg` 找不到任何生产调用者 —— 状态写进了库,而人既看不到也
    恢复不了。现在两条路都通,**判据只有一份**(`fulltext.held` / `fulltext.release`),两处都过它:
    - `GET /api/intake/{kind}/held` 列出来、`POST /api/intake/{kind}/held/release` 放回队列(`keys` 空 = 全部);
    - `./kb.sh held [来源]` / `./kb.sh held --release <key>...` / `--release-all`(只读库,不起服务、不发请求)。
    **恢复那一下不抓,下一轮同步才抓**:立刻跑一轮要占住 `pipeline`,而这一下承诺的只是「再给它一次机会」;
    绑在一起只会让 409 把恢复一起拒掉。**报实际写入结果**(元规则):给了 5 个 key 只放回 3 条就说 3。
    - **`./kb.sh held` 要用主项目那个解释器,不许用 `BOOT_PY`。** `BOOT_PY` 是给**只用标准库**的引导脚本准备的
      (解析一段 JSON、`grab_cli.py` 的参数预解析),它指向采集器那个 venv(只声明 lxml / requests / zstandard),
      取不到时退到 PATH 上的系统 python。而这个脚本 import `kb.feeds.fulltext` → bs4 / httpx / feedparser:实测在
      正常的双环境安装上 `./kb.sh held rss` 直接 `ModuleNotFoundError: No module named 'bs4'` —— 帮助里承诺的
      命令在用户那儿压根跑不起来。**而开发机的 worktree 恰好没有 `collector/.venv`、系统 python 恰好装着那几个
      包**,于是用 `sys.executable` 直接跑脚本的回归全绿,真实的 shell 用户路径没人走过。入口是 `proj_py`。
    - **那条命令不许套 `env -i`**(`CLEAN_ENV` 那一族是起服务用的):那会把 `KB_DATA_DIR` 一起清掉,于是它
      **静默**去读仓库内的 `data/` —— 显式隔离过数据目录的人看到一句「没有挂起」,而他那个库里躺着一堆。
    - **范围要约束写入本身。** HTTP 那个端点把路由上的 `kind` 传给 `release(keys, kind=)`:路由名过了合法性校验
      不等于请求体里每个 key 都属于它(实测把网页专栏那一条的 key 提给 RSS 端点,它照样被恢复)。**CLI 那一侧
      刻意不传** —— `--release <key>` 文档写明按 key 跨来源,那是有意的契约。
    - **`release` 的 WHERE 里要有 `fulltext_hold<>''`**,否则返回那个数是句谎话:同一个 key 给三次会报
      `released=3`(那几列已经是目标值了,UPDATE 照样算 1 行),已经恢复过的、压根没挂起过的也一律报成功。
      同一个 key 在一次调用里重复出现也先去掉 —— 那是**同一行**。
    - **面板上还没有这一档的按钮。** 现在的出口就是上面那两条(HTTP 端点和命令行);界面接线另算一件事(结构性
      的界面改动先给可点的 demo 再定夺),所以代码注释和文档里都不要写成「面板那颗按钮」。
  - **「这一条现在还该不该等全文」只有一份判据**(`fulltext._eligible`),补抓队列、挂起待办、人工恢复、翻译闸门
    四处都过它。一条内容可能同时属于聚合源和单号源,**任意一条开着补抓就算有资格**;关掉最后一条、或者把订阅整条
    删掉(删订阅刻意保留已收录的条目),这一条就再也不该等全文了。**也不许反过来替用户把那个开关打开。**
    - **这件事被分别回答过四遍,于是漏了第四处。** 前三处补上之后,翻译那道闸门(`unsettled_sql`)只在「还排着
      队」那半边问了资格、挂起那半边没问 —— 实测后果:关掉补抓(或删掉最后一条归属)之后那一条落进一个**没有
      出口的夹缝**:翻译那边永久当它「正文还没定下来」,英文摘要再也不译成中文;待办那边按资格排除它,面板上
      看不见;人点恢复以 `released=0` 拒绝。浏览器里走完真实的「关掉补抓 → 保存 → 同步 → 刷新」也一样:页面
      上仍是英文原文、`translated_at` 空。所以资格那一道要排在**整个并集外面**,不是排在某一半边。
    - **修法不是「关掉开关就把那一列清掉」。** 那样只盖住了某一条 PATCH 路径,删订阅那条路照旧把条目留在夹缝
      里;而且两条归属只关掉一条时会把还要正文的那一条也清掉。资格是**读的时候问**,不是写的时候固化。
    - 回归在 `tests/test_admit_three_ways.py` 的 `EligibilityIsOneQuestionTests`:判据落在「摘要到底译不译」,
      两条路(关开关、删订阅)各一条,**反过来钉一边**(还有别的归属开着就照旧等全文)也在同一组里。
  - **翻译那道闸门问的是「正文定下来了吗」(`unsettled_sql`),不是「还排着队吗」(`queued_sql`)。** 两者差一个
    挂起态:挂起的条目不在补抓队列里,但它手里那份正文仍然是 feed 给的跳转壳。拿 `queued_sql` 当闸门的后果就在
    把挂起做出来的那一轮实测到了 —— 条目一挂起当场进翻译队列,壳被译一遍、按文章导出,人点恢复、正文真补上
    之后 `_save` 把那份译文丢掉重译,**同一条内容买两次模型调用**。**导出那一侧刻意不用它**:挂起的照旧按壳
    导出,和「试满额度降级出队」一个待遇,正文后来补上时 `content_rev`/`extract_stale` 会让它重新导出。
  - **`release` 挡不住已经在路上的那一轮,这是知情的取舍。** `_fail` 比的是内容身份(`work_version`:hash + rev),
    而 `release` 不碰内容,所以一个在它之前就发出去的请求回来之后照旧写得进去 —— 它会把 hold 重新写上。要挡住
    得给「人发起的这一轮」一个不可复用的代次,那是一列新字段加一道新不变量;而它的后果只是「那一条又挂回去
    了,人再点一次」,不丢任何数据。**第 3 条那个缺陷在挂起语义下也只剩这一个形态**(挂起的条目不会被自动
    抓,所以不会有第二、第三轮),回归就钉在这个形态上。
  - **两档都抛,但抛的不是同一个异常**(`FeedError` / `Unconfirmed`)。口径同 `html_problem`:那半句话明确得多,
    而「抛」这条路保证走 `_fail`,失败明细连同「不再抓取」的句柄一起进面板(`sync._export` 的 `fetch_bad`)。
    **`Unconfirmed` 做成 `FeedError` 的子类这件事当前没有可观测后果,别把它当成一道判据** —— `fetch_one` 眼下
    唯一的生产消费方是 `fetch_pending`,那里捕 `except Exception`。它是给将来 `except FeedError` 地消费它的人
    留的安全默认(漏掉这一档退化成「当成普通失败」,而不是让异常逃出去带掉整轮),所以**不给它单独写一条只验
    `issubclass` 的红** —— 那正是元规则说的「只验过程」。
  - **误拒那一侧的代价在这条链路上更重,所以该放行的必须照旧放行**:讲关卡的正经文档(地址里带
    `cloudflare-challenges`、`<pre>` 里印着那段编排脚本)、评论区挂通用验证码小组件的文章、`<template>` 里的登录
    demo、页眉常驻的登录框、正文里引一句那种提示的文章 —— 手动收录那边误拒一次用户当场看得见、还能点「重新抓一
    次」,**这条批量链路没人在旁边看着**,误拒一次就是几百条订阅内容集体按壳入库。
  - **① 这一次响应自己的身份是唯一一道不靠页面文字的判据,而它住在传输层**(`fetching.request` 一拿到响应就问
    `page_gate.response_reason`,认出来抛 `Gated`)。表只有关卡**决策**响应头这一张:`cf-mitigated` /
    `cf-chl-bypass` / `x-amzn-waf-action` / `x-sucuri-block`。
    - **放在格式分派的下游就等于没有 —— 这是审查第 1 轮的第 1 条。** 原先它只接在 HTML 那条路上,而两条链路
      各有**两个更早的成功出口**:专用原文抓取(`.md`/GitHub 地址,`markdown_source.fetch`)和 `Content-Type`
      协商(`text/markdown`,`from_response`)。实测后果:一个 status=200、带 `cf-mitigated: challenge`、正文
      就是那段「访问被拒绝、请启用脚本和 Cookie」的响应,**两个收录入口都把 492 字拒绝说明收成了正文** ——
      补抓那边 `done=1`、`fulltext_at` 写上、`pending` 归零;手动收录那边阅读区完整展示那段拒绝说明。
      **出路不是在那四个出口各补一次判断**(那就是「两头各拼一遍、其中一头迟早漏掉」的同一个形状),而是
      上提一层:**响应身份与正文是什么格式无关,格式声明不该撤销更硬的证据。**
    - **关卡必须穿透「换条路试试」那一层。** `markdown_source.fetch` 把普通失败吞成 `None`(专用原文抓不到就
      走通用 HTML 那条路),但 `Gated` 要 `raise` —— 吞掉只会让主路拿同一个站点再敲一次门,而那两次之间任何
      一次「恰好没带关卡头」都会把拒绝说明收成正文。手动收录那一侧同理,**专用抓取那一行要和通用抓取共用同一
      道错误转换**:它原先落在 `try` 外面,于是一个 `Gated` 会直接逃出 `grab()`,前端收到纯文本 500。
      **这一道要钉的是敲门次数,不是「最终被拒」。** 传输层那一道还在的前提下,吞掉 `Gated` 之后主路再敲
      一次门**照样**会被拦,于是一切只验「最后拒没拒」的用例对这一道完全不敏感(实测红 0 条)。有效的判据是
      「只敲了一次门」加上「第二次响应是什么都不影响结论」—— 回归里第二次故意给一篇读起来完全正常的文章:
      穿透时它压根没被请求,吞掉时它会被整条写进 `body`、写上 `fulltext_at`、条目离开重试队列,而我们手里
      唯一的硬证据说的是「这一次被拦住了」。
    - **一个「CDN 在场」的证据都不许进那张表。** `cf-ray`、`server: cloudflare`、`x-datadome: protected`、
      `server: AkamaiGHost` 在**正常文章**的响应上也常态出现 —— 被 Cloudflare 代理的站点占了一大片互联网,它们
      进表等于按「这站挂在 CDN 后面」整批拒稿。判据和 `_GATE_ROUTES` 同一条:只收「对方这次真的拦了才会发」的。
      值只要求非空,不枚举 `challenge` / `captcha` / `block`(枚举等于留一个「新值没进表就漏放」的洞)。
    - **状态码一个都不算关卡身份,`response_reason` 只问响应头。** 曾经把 `401/403/429/503/511` 也当成「这个
      状态码本身就是一句你过不去」,审查第 1 轮指出那是另一类判据混进来了:**没有关卡头的 429 是限流、503 是
      对方不可用,它们说得出下一步**(稍后重试),而说成「要过一道验证」会把人指向一件他做不了也不需要做的
      事 —— 顺带还让 `request` 原来那句准确的「服务限流,请稍后重试」变成**不可达**。状态码的分类留在
      `request` 自己那段话术里;关卡头认出来时话术换成 `page_gate.SAY_REPLY`(**表和话术只有一份**),4xx/5xx
      那一类后面附上 `（HTTP nnn）`。
    - **`verdict` 里那一道是冗余带,不是唯一一道。** 「谁交进来一份 HTML 加一份响应头」这件事不该假设它一定
      经过了传输层(浏览器通道、测试夹具、将来的别的传输)。两处同一张表、同一句话,不是两份判据。
  - **⑥ 那道份额判据原先随排版翻转,根在句界而不在阈值 —— 而且两侧都漏。** 上一版 `_SENTENCE` 刻意不切 `. `
    (理由是域名、缩写、小数点会把份额抖散),代价是英文的「一个自然段」被当成「一句」:同一批文字连成一段
    → 1.0(拒)、三个自然段各提一次 → 仍是 1.0(拒)、按英文句号分成七段 → 1/7(放行)。
    - **误拒那一侧**:提到那几个强措辞的正常英文文章(典型是「怎么启用 JavaScript」这类设置教程)在两端都收不
      进来,补抓那边连抓三轮耗尽额度、永久退回摘要。
    - **漏放那一侧**(2026-10-22 审查实测):**把同一张拒绝说明页的六句话各自分段就够了** —— 份额从 1.0 掉到
      **1/6**,当时那六道一道都不命中,**496 字拒绝说明当正文入库**、`fulltext_at` 写上、退出重试队列、送进
      翻译并按文章导出;手动收录那一侧同样收下,阅读区展示的就是那段「访问被拒绝」。
    - **出路是切 `. ` 并要求它后面跟空白**(`(?<=[.!?;])\s+`;CJK 句读不要求空白,因为中文句子之间没有空格)。
      实测份额从此与排版无关:拒绝说明页原样/分段都是 **0.167**,设置教程原样/分段都是 **0.143**,三个自然段
      各提一次的那篇 **0.333**。代价如实记着:那张 1782 字的英文验证页从 0.667 掉到 **0.500** 落到线下 ——
      它由 ⑤(标题「请完成验证后继续」)接住,而标题是页面自己的身份、本来就比正文份额硬。
    - **份额按句数算,不许换成字数占比。** 量过:基线钉着必须放行的那篇「正经讲 captcha 的文章」按句数是 0.50、
      按字数是 **0.681** —— 它命中的那几句刚好比不命中的长,换成字数当场越过 `_GATE_SHARE` 误拒。
      (⑦ 反过来按字数,因为那一道问的是「样板占了多少篇幅」,不是「有几句在说别的」。)
    - **也别反过来把 `_SENTENCE` 里的 `\n` 去掉**想让它「与排版无关」:英文正文没有 CJK 句读,去掉换行之后整篇
      算一句、份额二值化,凡提到一次那几个强措辞的英文文章就**全部**被拒 —— 比误拒面最大的那一版还大。
  - **⑦「这一页是一张访问被拒绝的说明」那张表,口径和理由同 `readable._LEGAL`(版权区那一档):小而极稳,而且
    按占比算不按命中次数。** 拒绝页的份额(0.167)比那篇必须放行的文章(0.50)**低**一倍,所以 ⑥ 对它压根不成
    立 —— 分得开它们的不是一条更准的线,是**另一道判据**。
    - **进这张表的必须是「这一次请求被拒了」那句状态播报本身,不是话题词。** `denied`、`security policy`、
      `captcha` 这类单词一个都不许进(⑤ 明令禁止的「话题词进表」)。整句的样板措辞不一样:正常文章写的是
      「a managed rule can block requests」,拒绝页写的是「your request was blocked by the security policy
      configured for this website」。
    - **两侧都量过**(回归钉着):那张纯文字拒绝说明页原样和六句分段都是 **0.833**(与排版无关);而一篇**真·讲
      拦截页**、正文里原样引着「your request was blocked …」和「If you think this is a mistake, contact the
      site administrator」两整句的英文技术文章是 **0.322**,照旧收下。其余被钉住的正常样本(两篇设置教程、讲
      captcha 历史的长文、引一句提示的文章、普通文章、两份 Markdown)**全部 0**。
    - **它的结论是「证据不足」而不是「确定关卡」,这一条不许松。** 那篇技术文章和一张真的拒绝说明页在**文字上
      只差一个占比** —— 把「我确认不了」说成「对方拦着你」,面板上那句话就是在替用户下一个我们并不知道的判断,
      而他照着去「在浏览器里打开一次」只会发现那一页好得很。误判一次的代价因此是一次重抓加一条待人看的记录,
      不是把一篇正常正文永久换成一段拒绝说明。
  - **不许用文字量、去重长度或段落形态给 ⑥ 开豁免。** 那三样只证明得了「这里有多少字」,证明不了「这一页没在
    拦正文」。实测否过两次:①「最长那句占一半以上 + 按细句去重仍有 400 字」这道豁免,当场把一张 **491 字、句句
    不同的纯文字拒绝说明页**收成了正文:`fulltext_at` 写上、退出补抓队列、整段拒绝说明送进翻译并按文章导出;
    ②同一道豁免对「三个自然段各提一次」的正常教程又不成立 —— **它只修好了「一整段」这一个特例**。
    那一类页面现在由 ⑦ 接住,而不是由一道字数豁免的反面接住。
  - **回归按「期望正确的结果」写,不许把误判写成预期。** 上一版那两条 `expectedFailure`(分段拒绝页不该入库、
    提到一次强措辞的正常教程该补到全文)在这一版报 **unexpected success**,标记跟着删掉;原先那组「三种排版
    三个结论」的缺陷形状快照换成了它的反面 ——
    `tests/test_admit_three_ways.py` 的 `LayoutDoesNotChangeTheVerdictTests`(同一批文字换排版不换结论,**判据
    那一层也钉**:只验结论的话,哪天份额又开始随排版抖、而两种排版恰好落在同一侧,它照旧全绿而缺陷已经回来)、
    `ResponseIdentityTests`(① 的两侧:关卡决策头算、CDN 指纹不算、普通 404/500/304 不算)、
    `EvidenceTooThinTests`(第三档本身:不写库、记成「我没能判断」、额度用完之后出现在 `held()` 里、人点一次
    `release()` 回到队列并真的再抓一次)。**按形状拆成独立文件**:并进
    `tests/test_fulltext_admit.py` 会越过 700 行硬上限,脚手架和夹具从那一份 import。
  - **反向验证:五处定点注入,四组独占的红**(136 条,基线全绿)。① `response_reason` 恒返空 → 6 条;
    ② `_SENTENCE` 回到不切 `. ` 的旧版 → 8 条;③ `_refusal_share` 恒 0 → 11 条;④ `unsure` 退回
    `FeedError` → 4 条;⑤ `held_say` 恒空 → **和 ④ 同一组 4 条,一条不差**。
    **④⑤ 红名单相同不是用例不敏感,是实现上只有一条信息通路**:`admit` 把「证据不足」编码成异常类型,
    `fetch_pending` 用 `isinstance` 解码成 `fulltext_hold`,打断哪一端 hold 都不写。元规则那条「两份实现
    各有自己的回归」说的是主路和后路**两份独立实现**,这里是一条链的两段 —— 真要分开钉,得先有第二个按
    异常类型分流的消费方,而眼下没有(见上面那条)。
    ③ 那一轮里 `test_an_article_about_block_pages_is_still_stored` 也红,看着像误伤、其实正是该红:那条
    用例**连判据层一起钉**(`_refusal_share(body) > 0`,「它真的引了样板、只是占比不够」),恒 0 之后那条
    前提当场不成立。只验「它被收下」的话这一轮会绿,而 ⑦ 已经整道失效。
  - **Markdown 那条路不过这道准入**(`markdown_source`:只认 GitHub README/`.md` 地址,或响应自己声明
    `text/markdown`)。关卡页回的是 HTML,落不到那条路上;这是显式的边界,不是漏掉的一道。**但它和存量复查那条
    接得上**:那一列 `fulltext_at` 底下躺着两条路的产物,「报过补抓成功」答不出「过了这道准入」—— 见下面第二条。
  - **调用方那道长度上限必须在 `admit` 里面生效(`limit=`),不许拿到正文之后再截。** 判据要落在**最后真写进库的
    那一份**上:准入之后还改正文,原来那个结论就不再是对最终内容的保证。事故形态(2026-10-21 审查第 1 轮实测,
    手动收录那一侧):一张开头把同一段复读了几万字、真内容排在 6 万字之后的页面,全文 69133 字过得了 ⑥(后面那段
    各不相同),截到 `MAX_CHARS` 之后落库那 60000 字**不重复的只有 202 字** —— 收录当场完成、页面紧接着提示
    「这一篇收下的内容看不出是正文」,阅读时后面的真内容也没了,而重抓只会截出同一个前缀。**基线那一版
    (`page_body` 先截、`verdict` 后判)是直接拒掉这一页的**,所以这是把判据下沉时把顺序颠倒了。补一道事后
    检查不算修:那样上限和判据就在两处各写一遍。补抓那一侧 `limit=None`(原样入库)—— 顺手给它加一刀 60000 字
    截断是另一件事,而写进去是终态。
  - 存量那一半见下一条。回归 `tests/test_fulltext_admit.py`(正反两侧 + 面板那句 + 出队出口 + 那段文字有没有进
    vault 和模型请求 + 截断那一道的两头 + 「准入放行的那一份就是存进去的那一份」);定点注入(`fetch_one` 原样
    装回审查那一版)红 8 条,全落在「该拦的」那一组。
- **判据只管未来 —— 存量那些已经被写死的,复查脚本救不回来**(`scripts/feed_fulltext_recheck.py`:它只认
  `readable.boilerplate_reason`,**上面那八道一道都不借**)。这是能力边界,不是漏掉的一道:认出一张关卡页要的是
  最终地址、DOM 里那几个组件、响应头,**落库之后这些全没了**,库里只剩那份纯文字。
  - **误拒的代价按路分三档,一档都不轻**:手动收录那边用户当场看得见、还能点「重新抓一次」;补抓那边没人在看、
    三次额度用完就**永久退回摘要**(2026-10-21 审查实测:`fulltext_tries` 1→2→3、`fulltext_at` 始终空、第四轮
    `pending=0`,vault 里只剩摘要还按摘要翻译导出);存量复查那边是把**已经在库里的**正文换成壳、译文作废、重导
    出一轮。前两条是「这一次没拿到」,第三条是「把拿到的毁掉」。同一个启发式担不起这三种后果 —— 两次借过来都当场
    借出了事故:
  - **借 ⑥(`body_confirmed`,不重复的字数要过 `MIN_CHARS`)判坏了正常的 Markdown 原文**(2026-10-21 审查第 1 轮
    实测):`fulltext.fetch_one` 有两条出口交出 **Markdown 原文**(`markdown_source.fetch` 认 `.md`/GitHub 地址、
    `from_response` 认 `text/markdown` 响应),而 Markdown 本来就允许重复 —— 一份 646 字、按行去重 254 字的正常
    quick-start README(几个平台各一段同样的安装命令)被判坏、正文换成「标题 + 链接」、`fulltext_at` 清空、译文
    作废;重抓把同一份内容再写回来,下一轮又选中,**没有终点**。按 `.md` 后缀跳过没用:无后缀地址只要声明
    `text/markdown` 也走那条路。
  - **借 ④(`_gate_share`,关卡句的份额)判坏了正常的英文设置教程**(2026-10-21 审查第 2 轮实测):`_gate_share`
    **刻意不按 `. ` 分句**(域名、缩写、小数点会把份额抖散,那个取舍本身是对的),于是一整段英文只算**一句** ——
    正文里提一次「enable JavaScript」份额就是 **1.0**;那份 Markdown 教程连标题带正文两行都提到它,同样 1.0。
    **把同样这些字分成段落,份额降到 1/7** —— 一个随排版翻转的判据担不起「销毁这份正文」。连 feed 自己给的、
    **还没补抓过**的 158 字摘要都会被选中。
  - **不是「再调一调就能用」。** ③④ 那套措辞/份额判据判的是「这一页在拦正文」,而库里那份文字答得出的只有
    「它提到过那几个词」。补英文句号分句、换一张措辞表、跳一个扩展名、把「报过补抓成功」那道守卫加回来,四样都
    不解决这件事:短摘要仍然只有一句,走 Markdown 的仍然成功之后被清掉。
  - **补一列来源凭据也是死重。** 这次之后 ⑥ 判坏的 HTML 正文**压根写不进来**(`admit` 当场拒掉),凭据只会盖在
    「⑥ 永远不会成立」的那些行上。实测核对过:一条「⑥ 不合格的 HTML 正文」和一条真走 markdown 路写进来的 README,
    `feed_items` 里**所有列都分不开它们**(相同:`kind`/`content_kind`/`fetch_round`/`body_provenance`/
    `fulltext_tries`…;不同的只有 key、url、正文和几个时间戳)。
  - **出路是人点「重新抓一次」**(`grab.replace`),不是让脚本去猜。生产只读实测(2026-10-21,`data/feeds.db`)说
    这不是损失:开了补抓的订阅名下 1021 条 = 352 条壳(`substance` 全落在 37~133)+ 669 条报过成功,那 669 条里
    **关卡句份额最高的是 0.0** —— 存量的**文字里**找不出一条可识别的关卡提示,借 ④ 过来一条也收拾不到、只会误伤。
    **但这推不出「存量里没有关卡页」**:身份证据多半在 DOM 上,而库里只剩文字 —— 只靠编排脚本认出来的那一类
    (`COMPONENT_ONLY`),正文和一篇普通文章逐字相同、份额同样是 0。已经丢掉的身份追认不回来;⑥ 那一档当时挑出
    2 条(Meta 产品落地页 934 / 393、英国地方报面包屑 473 / 392),不动它们。**认不出来的代价是库里留着两条瘦
    正文,认错的代价是把正常正文写死。**
  - 回归 `tests/test_fulltext_admit.py` 的 `RecheckTests`:射程之外那五类一个字节都不许动(正常 README、正常英文
    教程、feed 给的重复摘要、还没补抓的壳、补抓成功的真正文 —— 前两类**走真的补抓**写进去,连译文一起钉),外加
    那条能力边界本身(关卡提示页 / 纯文字登录墙都收拾不了)。样板区那一档的正反两侧、连同备份恢复那四条,在
    `tests/test_fulltext_failures.py` 的 `StaleRecheckTests` 里**基线就钉着**。
- **那份「这不是文章正文」的标准在复查脚本里只有一处(`_not_article`),两边消费:挑哪几行要收拾(`_suspect`)、
  以及从备份里挑哪一份内容当壳(`_from_backup`)。** 只在前一处加判据、后一处留着旧标准的后果实测过(2026-10-21
  审查第 1 轮):一份同样不合格的**较新**备份被当成有效原摘要装回来,`_downgrade` 紧接着清掉 `fulltext_at` ——
  这一条从此连扫描都选不中,而正确的**较旧**备份明明还在。两处的标准现在是同一个函数,**往里加东西之前先读它头上
  那两份事故**。
- **提取不出来不是故障,是「这一页我们读不懂」**:保留原本那份壳、条目照旧入库、`fulltext_tries` 计次(不计次的
  话这条永远排在队首)。宁可少补一篇,也不能把导航栏当正文译了写进知识库。
- **「抓到了一页东西」不等于「拿到了正文」:版权声明和作者简介块要当成没拿到**(`readable.boilerplate_reason`,
  两道:授权措辞句子占比 ≥ `MAX_LEGAL_SHARE`(0.5),或开头是作者简介区抬头而整块 ≤ `MAX_BYLINE_CHARS`)—— 这两
  种页面**结构上完全正常**,于是补抓报成功、离开重试队列、接着买一次翻译,**这一档不可恢复**。
- **署名不是作者简介,`_BYLINE_HEAD` 只认「这一块是作者简介区」的抬头**(`about the author(s)` / `author bios?`
  / `作者简介` / `关于作者`)。`written by` 一度在名单里,而它是正常文章的标准开头。**判据是措辞,不是段落数。**
- **原文链接后面不是网页时按抓取失败处理,绝不把文件语法当成正文**(`readable.html_problem`)。**三道,各管一类
  撒谎方式**:①**声明的类型**不在 `_TEXT_TYPES` 里;②**文件头**命中已知魔数(PDF 的首个压缩流常在几十 KB 之后,
  RTF/PostScript 整份都是 ASCII);③头部有 **NUL 字节**,**而且拿 `decode` 真解一次之后它还在**(UTF-16/32 的
  **正常文本**每隔一个字节就是 `\x00`)。**判据是「拿真正会用的那个解码器解一次」,不是另开一张编码白名单。** 配套
  `decode` 自己要认 BOM(`_BOM_CODECS` 排在 HTTP charset 和 meta 前面,**UTF-32 必须排在 UTF-16 前面**)。
  `text/plain` 留在放行名单里。
- **存量复查要连那份 body 一起换掉**(`scripts/feed_fulltext_recheck.py`)—— 光清三个标记的话,重抓三轮失败后它离
  开补抓队列,那段版权声明会被**重新翻译一遍、重新导出**。换完它就是一条「从没补抓过」的普通条目
  (`content_kind='summary'`、`content_hash` 重算),**是正确的降级**。壳从备份库恢复(`--backup`,显式给了就只认
  那一个)或按标题链接重建;恢复回来的要**再过一遍判据**。`content_hash` 的口径抽成 `fulltext.body_hash`。**射程
  是「属于开了补抓的订阅」,不是「报过补抓成功」**(`_suspect`;后者漏掉的恰恰是这个脚本自己制造的中间态)。写回
  按元规则带 `AND body=?`(**这个脚本自己的 CAS 就是这一道**,不是 `content_hash`)—— 它问的是**「我判坏的那份
  正文还在吗」**,不是补抓交付那一条的「这一行还是我取样那一版吗」;两问不同口径,别跟着下面那条一起改。
- **失败过的优先**(`ORDER BY fulltext_tries DESC, fetched_at DESC, key`)。
- **`_save` 要把旧译文一起清掉**(旧译文译的是那份壳),`translate_tries` 归零。**但不许清 `exported_hash`** —— 导出闸门是
  `exported_hash<>content_hash`,正文一换前者就自然成立;而它同时是「这一篇入没入过库」的事实来源,清掉会让一篇**已经能展开阅读**的旧条目标题连同入口一起消失。
- **这一轮的结果只许写回它取样的那一版 —— 所有异步交付边界都带判据,而判据是「那一版的身份」,不是「正文还一
  样」。** 补抓是「先 SELECT、再等网络、最后写回」,而**同一行此刻可能被另一个线程换掉**:手动收录那颗「重新抓
  一次」跑在 HTTP 请求线程里、**不持这一轮同步的维护锁**(`grab.replace`,见 `link-grab.md`)。所以
  `fetch_pending` 按 `grab_store.work_version` 取样(**不取 `body`**;那份口径摆在「库里那一条」
  那个模块里,因为**手动重抓那条链用的是同一份** —— 见 `link-grab.md` 第一节),`_save` / `_fail` 的 WHERE 带那一版的
  **代次 + 指纹**(`AND content_hash=? AND content_rev=?`),`retire_stale` 带 `AND content_hash=?`。三道判据各答
  一个问题,别互相代入:
  - **`AND body=?` 不够,它是另一套口径**:替换那条路的版本身份是**整份导出负载**
    (`grab_store._VERSION_FIELDS` —— 标题、正文、作者、发布时间),于是一次**只改标题**的手动重抓换掉了
    `content_hash` 却留着同一份正文,按正文相等判的补抓照旧获得覆盖权(实测:用户重抓到的那一版标题还在、正文
    换成了补抓那一轮抓回来的另一份内容)。一边按四列认定「这是新的一版」、另一边按单列相等认定「还是旧那一
    版」就是两套口径(元规则:口径只有一份)。
  - **内容指纹也不够,它可以重复**:标题改成 BETA 再改回 ALPHA 之后 `content_hash` 逐字回到取样那一版,而这期间
    **两次更新都已经被接受过** —— 迟到的补抓又拿回交付权,末态和上一条一样坏(实测:md 和 FTS 里都是旧正文,再
    贴同一链接只说「已经在知识库里了」)。**指纹不碰撞也会自然重复,所以不是"再哈希一列"能解决的**:换内容的两
    个写入方(`grab_store.replace`、`_save`)各自把 `content_rev` 加一,那个代次**只增不复用**,所以「我取样之后
    这一行接受过更新吗」有了一个答得准的判据。`content_hash` 留着当冗余带(多挡不碰代次的 `_downgrade` 和
    `scripts/x_article_backfill`;**如实记一笔:去掉它一条用例都不红**),而 `reclaim_export` 清导出回执、
    `translate._save` 写译文两列都不动 —— 不会把「不是内容的变动」误判成换了版。
  - **提取待办那一处比内容就够**(`retire_stale`):它做的事是按 path 清知识库里那份旧提取,与代次无关;内容回到
    原值时那笔待办确实是它清掉的那一份(替换不导出,所以 vault 里那一篇还是取样那一刻的渲染)。
  三处的 `rowcount == 0` **都不是失败**,是「那一版已经不在了,这次结果作废」(元规则)。无条件
  按 key 写的后果都实测过(Event / 定点回调各复现一次):①迟到的 `_save` 把用户刚换回的正文又盖成旧内容,导出和索引
  跟着落盘,面板最后说「这条已经在知识库里了」;②迟到的 `_fail` 把一句「抓取失败」记在新正文头上、还扣掉一次重试
  额度;③迟到的 `retire_stale` 清掉的是**新版本**那笔待办,于是下一轮导出不再摘旧的 `topic/`、`entity/`,索引按
  残留标签走 `parse_pretagged`、`extracted_at` 跟着非空 —— **新正文永远不进重新提取队列,旧主题永久留在那一篇
  上**,再同步多少轮都不变。配套两条:**统计按实际写入结果报、跳过的如实列出**(`summary['stale']`,`summarize`
  里单独一句「N 条在补抓期间已被换新、这次结果作废」;算进进度回调,不然面板那一行永远停在 N-1/N),以及
  **`_drop_extraction` 照旧对整批做**(清掉知识库里那份按旧内容算的摘要,对已经换版的那几篇也只是让它们重新提取
  一次 —— 多花一次,反过来留着是永久错)。回归 `tests/test_item_version_race.py`。
- **导出确认那一句认的是「刚落盘的那一份」**(`sync._export` 收尾的 `SET exported_hash=?,path=? WHERE key=? AND
  content_hash=?`)。`_save` 跑在 crawl 阶段、和 export 同一轮里串行,所以撞不上它;但只要有谁能在导出进行中改正文
  (手动收录那条恢复链就是 —— `grab.replace` 跑在 HTTP 请求里、不持这把维护锁),右侧写成 `exported_hash=content_hash`
  就会把**新正文**的欠账消在旧文件上,**永久漏导出**。要动那一句先读 `link-grab.md` 第一节里的同名约束。
- **`subscription_items` 要一条按 `item_key` 的索引**(主键是复合的,按 item_key 查用不上)。
- **正文从壳换成全文之后,按旧壳算出来的提取结果要作废**(`fulltext.retire_stale`,由 `sync._export` 在导出之后调
  一次)—— 不作废不是「晚一点更新」:`extracted_at` 非空意味着这一篇**永远**不进 `pending_docs`。四件事:①**时点
  是「新正文真的落了盘」**(`extract_stale=1 AND exported_hash=content_hash`),不是「网络抓到了」;②**做完才把标
  记放下**,顺序不能反;③**异常要接住**;④**摘哪些 tag 只有一份口径**(`STALE_TAG_PREFIXES` + `keep_tags`,只摘
  `topic/` 和 `entity/`,`flag/软广` 和人工 tag 留着)。不清 `promo_level`,也不动 `store.upsert_document` 的
  `extracted_at` 语义。
- **一次提取的结果要和它基于的那**组**输入绑在一起 —— 标题 + 账号 + 正文,不只是正文**
  (`extract.input_fingerprint` + `save_extraction(..., input_seen=)`)。那两样同样进 prompt(软广判定按「这个号在
  卖什么」读文末那段),换掉任何一样这个结论就不再是针对当前那篇文章的。
  **两道判据各管一种时序、缺一不可**:①**索引还没扫到当前这份 md**(`store.doc_needs_reindex`);②**索引里那组输
  入已经不是我读到的那一组**。判据待在 `save_extraction` 里,**读 chunks 正文 + 有模型往返的那三条路径**必须传指纹
  (`kb/cli.py`、`kb/pipeline_stages.py`、`scripts/extract_parallel.py`),不读正文的两条不传。**`StaleBody` 不是故
  障**,三条路径一律归到「跳过」。
- **那三条路的模型输入一律从 `extract.model_input` 一个口子取,四样同属一条语句的快照。** 原先标题和账号是从待提取
  名单里带过来的、正文稍后另读一次 —— 两次读之间另一条连接的索引可以把这一篇整篇换掉,于是**模型收到旧标题配新正文**,
  判出来的结论落在一份没人写过的东西上,而按正文比的那道判据看不出任何异常(正文确实是当前那一份)。软广那一档的后果
  最重:一篇已经改成普通教程的文章被判 hard 永久隐藏,`extracted_at` 一落就掉出所有待办。**account 也必须传进模型** ——
  原来只有管道那条路传了,另两条没传,同一篇文章在三条路上判出不同结果(口径只有一份)。
- **校验本身给不了保证,它必须和写入在同一个协调区间里**(`extract.commit_extraction`:维护锁 → `BEGIN IMMEDIATE`
  → 锁内校验 → 落库 → 提交 → 回写),锁内还要先问一次「这一篇还在吗」。**粒度仍然是每篇各取一次锁、模型请求留在锁
  外。** **「真的不在了」和「这一刻读不出来」是两档,不是一档**:文件真被清理掉(`FileNotFoundError`)不算「版本不对」
  照旧放行(由锁内那道「这一篇还在吗」和外键级联管);**别的读取失败一律拒** —— 文件还在、只是没权限或正被别人换着
  写,那一刻答不出「索引扫到当前这份 md 了吗」,而**「没读到」不等于「证明了没变」**。**索引指纹那一道(②)要问在读
  磁盘那一道(①)前面**:它只读库、一定问得出结果,反过来排的话一次读取失败会把这道**能**答出来的判据一起跳过。
- **判「还是不是同一组输入」那一族住在 `kb/extract_version.py`**(`input_fingerprint` / `model_input` / `_input_moved` /
  `_require_current_input` / `_still_indexed` / `StaleBody`,700 行上限逼出来的第四次拆分)。`kb.extract` **原样再导出**它们,
  所以 `extract.model_input`、`extract._input_moved` 这些写法和打桩一个字不用改。**要用 `VAULT_ROOT` 一律函数内
  `from kb.extract import VAULT_ROOT`** —— 夹具打桩的是 `extract.VAULT_ROOT`,在新模块里绑成模块级全局就等于在测试里读真实
  vault(理由同 `kb.extract_writeback`)。
- **`documents.content_hash` 的口径抽成了 `scanner.file_hash`。手摆 `documents` 行的测试摆盘必须按它算
  `content_hash`**,否则摆出来的是一个生产里不存在的状态。`_extract_pass` 的 `stats` 一律用 `_new_extract_stats()`
  构造。
- 详细见 `docs/decisions/fulltext.md`。

## 事故形态与实测证据

- **feed 只给一个跳转壳时,顺着原文链接把正文抓回来。** HN Buzzing 那类来源每条
  正文长这样 —— 标题、域名、发帖时刻、`↑ 101 HN Points`,一共几十个字符。按它
  入库的话 vault 里那篇 md 没有内容:全文检索搜不到文章里的任何一句话,提取打标
  拿这几十个字判不出实体,日报素材里只剩一行标题。订阅了它等于只订阅了一份链接
  清单(2026-10-09 用户指着面板说「都像个跳转似的」)。
- **开关是订阅级的、默认关**(`subscriptions.fulltext`)。只有链接聚合源需要它:
  Lilian Weng、Karpathy 那类 feed 本来就给全文,对它们再抓一次是拿一份启发式提取
  的结果去换作者亲手给的全文,纯粹的降级。`defaults.json` 里**只标了 HN Buzzing**
  一条(那是唯一有正文形态证据的);`AI Hub Today` 没有证据、`HN Top 100 Blogs`
  源站已停,一个都没顺手打开 —— 这个开关改变的是采集行为和模型开销,不是我们该
  替用户决定的事。而 defaults 那段只对**新库**跑(`defaults-v1` 一写上就不再碰),
  存量库要在面板上点一下。**给 defaults.json 加字段必须同时改那条 INSERT**:它
  原来压根没有这一列,JSON 里那个 true 会一声不响地丢掉(回归里真起一个空库验)。
- **独立一列,不放 `config`。** 换链接时 `save_subscription` 的 `reset` 会把 config
  整个清成 `'{}'` —— 那是采集进度(水位、etag)该有的下场,而这是用户对这条订阅的
  配置,不该因为改一次链接就被静默关掉。
- **这一步排在翻译之前**(`FeedCollector.materialize`)。反过来写的代价是实打实的:
  先按壳译一遍、补上正文再译一遍,同一条内容买两次模型调用,而第一份译文随后就被
  `_save` 丢掉。翻译是这条链上最贵的一步。
- **还排在补抓队列里的条目既不翻译也不导出**,两边各认一次本模块的 `queued_sql`
  (`translate.queued_sql` 里 `AND NOT (...)`、`sync._export` 里收窄 base)。
  队列判据只有这一份:①属于某条开了补抓的订阅(一条内容可能同时属于聚合源和单号
  源,任意一条开了就抓 —— 补到的正文对另一条同样有用);②`fulltext_at` 空;
  ③`fulltext_tries < MAX_TRIES`。
  **出口就是第三条**:试满仍然抓不动的离开队列,按 feed 原本那份壳走完翻译和导出
  (口径同 `translate`)。一个付费墙后面的链接不该让这条订阅的内容永远进不了知识库。
  **这里不像翻译那样留一个「整个被跳过」的开关**:翻译没配 key 时扣着就等于永久
  扣着,而补抓不需要任何配置、抓不动会自己计次出队。
- **`sync._export` 里收窄 base 的那一句必须排在所有统计之后。** `queue`/`cond` 那
  几条统计语句各自只带 `kind` 一个占位符,拼参数时用的是 `(*args, *extra)` —— 在
  它们之前往 `args` 里追加,绑定数当场对不上,整个导出阶段抛 `ProgrammingError`
  (写这段时就是这么先红的一次)。
- **「在队列里」和「没入库」是两件事,按 `exported_hash` 分两态**(`registry.items`
  的 4 `fetching` / 5 `refetching`),口径同翻译那边的 `translating` /
  `retranslating`,理由也一模一样。**打开这个开关最常见的时机正是「这个源已经同步
  过、几百条壳就摆在眼前」**,那一批全是 `exported_hash == content_hash`:它们早就
  在 vault 里了。对它们说"抓到之后才写进知识库"和文件、索引的事实正相反,而那句
  文案配着"不给展开阅读",等于把一批本来读得到的条目一起藏起来。已导出那一档如实
  显示库里那份壳、照旧能展开,只在页脚说清正文还在补;**顶上那句计数也只数还没
  入库那一档**(同 `waiting`)—— 另一档已经读得到了。
  这个缺口是浏览器回归抓出来的(第一版把两种合成一档,沙箱里恰好一条已导出的壳
  都没有,后端单测全绿)。
- **待补抓的条目标题照显示,换掉的只有正文那一段。** 标题是这条内容的标题、不是
  占位文字,用户正是靠它认出这一条;而正文此刻是那个跳转壳,照显示等于让人以为
  这条内容就只有这些。
- **提取器自己写,不装 readability/trafilatura。** 两条理由缺一条都不够:①我们要的
  输出是**纯文本**,而块级边界的口径已经由 `fetching.plain` 定死(索引、翻译切块、
  vault md 的分段全按它来),那些库输出的是 HTML 片段,拿回来还得再过一遍 `plain`
  —— 真正用得上的只是"选出正文那个容器"这一步,也就是那几十行打分;②
  `pyproject.toml` 一动 `uv run` 就要重建 editable 包,而那一步会去 pypi 问
  hatchling 的最新版(见上面「起服务那条命令一律 `uv run --offline`」那次事故)。
- **`find_all` 是快照,`decompose()` 之前必须先问「这个节点还在吗」**(`_gone`)。
  bs4 把被销毁节点的 `attrs` 置成 None,于是列表里排在后面的那些后代再被碰一下就是
  `AttributeError: 'NoneType' object has no attribute 'get'` —— 一个
  `<div class="sidebar">` 里套着另一个 `<div class="share">` 就够了,而这在真实页面
  上是常态:实测 ken.arneson.name 和 frontiersin.org 那两篇当场抛出来,整条补抓记成
  失败、重试三轮之后按壳入库,而页面本身好好的。
- **`header`/`footer`/`aside` 要看位置,不能无条件删。** `<article><header>` 里装的
  是文章自己的标题、作者和日期(实测这一条会让「By Carson Gross, February 2026」
  整行消失);`<article><aside>` 多半是题外话或引文块,也是内容。只有落在
  `<article>`/`<main>` **外面**的那些才是站点页眉、页脚和侧栏(`_DROP_OUTSIDE`)。
  同理按 class 名剔噪声只对 `div`/`section` 那几种容器做:`<article class="post-header">`
  说的是"这是文章的开头",不是"这是站点页眉"。
- **提取不出来不是故障,是「这一页我们读不懂」**:调用方保留 feed 原本那份壳、
  条目照旧入库,`fulltext_tries` 计次。宁可少补一篇,也不能把导航栏当正文译了写进
  知识库 —— 后者要花模型钱,还会污染检索。抓到页面但认不出正文的那一档**按失败
  计次**(不计次的话这条永远排在队首,每一轮都重抓同一个读不懂的页面)。
- **「抓到了一页东西」不等于「拿到了正文」:版权声明和作者简介块要当成没拿到**
  (`readable.boilerplate_reason`,两道内容判据 —— 授权措辞句子占比 ≥
  `MAX_LEGAL_SHARE`(0.5),或开头是作者简介区抬头而整块 ≤ `MAX_BYLINE_CHARS`(1500))。
  这两种页面**结构上完全正常**(有 `<article>`、有段落、字数轻松过 `MIN_CHARS`),
  提取器眼里和一篇真文章没有区别 —— 于是补抓**报成功**、`fulltext_at` 落下、条目
  离开重试队列,接着买一次翻译、覆盖掉 feed 原本那份壳。**这一档不可恢复**:后面
  任何一轮同步都不会再碰它(2026-10-09 审查在生产库里抓到两条,Fortune 那篇 455 字
  版权声明、Stripe 那篇 474 字作者简介)。口径同上一条「宁可少补一篇」。
- **署名不是作者简介,`_BYLINE_HEAD` 只认「这一块是作者简介区」的抬头。**
  `written by` 一度在那张名单里,而它是**正常文章的标准开头**(`<article><header>`
  里那行署名)—— 加上 `boilerplate_reason` 只凭开头和一个长度上限就整篇拒绝,
  一篇有署名、标题和三段正文的 580 字短文被判成「只有作者简介」,连抓三轮只留下
  链接(2026-10-09 第 2 轮审查实测)。本文件硬约束一节里早就记着
  「`<article><header>` 里那行『By Carson Gross, February 2026』」要留住,这是同
  一条规矩的另一面。剩下那几项(`about the author(s)` / `author bios?` /
  `作者简介` / `关于作者`)都在声明"下面是作者简介",Stripe 那页开头逐字是
  `About the authors`,照旧挡得住。**判据是措辞,不是段落数** —— Stripe 那块三位
  作者各一段,按"有几段正文"分不开它。
- **存量复查要连那份 body 一起换掉,光清标记是把已知错误内容又放回正文消费链**
  (`scripts/feed_fulltext_recheck.py`)。第一版只清三个标记(`fulltext_at` /
  `fulltext_error` / `fulltext_tries`)和译文、body 原样留着 —— 于是重抓三轮都失败
  之后它**离开补抓队列**,而 `translate.queued_sql` 这时不再排除它:那段版权声明
  被**重新翻译一遍、重新导出**,阶段还报「已保存 1 条到知识库」,用户点阅读看到的
  是版权声明的中文译文(2026-10-09 第 2 轮审查三轮实测)。
  **换完它就是一条「从没补抓过」的普通条目**(body 是壳、`content_kind='summary'`、
  `content_hash` 跟着重算),于是三轮失败后按壳入库 —— 和一条压根没开过补抓的条目
  待遇完全一样,**是正确的降级**,不需要任何新列、新标记或新的排除条件。
  **壳从哪儿来,两条路**:①备份库(`--backup`,或自动扫 `<data>/backups/*/feeds.db`
  按新旧倒序)—— 第一版断言"原始那份壳救不回来"**是错的**,回填前自己做的那份备份
  里就有(审查实测 Stripe 68 字、Fortune 118 字,生产上两条都从这里恢复)。恢复
  回来的要**再过一遍判据**:备份可能是在某一轮错误补抓之后做的,里面那份同样是
  样板文字,那就不算有效壳,继续往更早的找。②按标题和链接重建(兜底,不编造内容)。
  **显式给了 `--backup` 就只认那一个**,指错了不许悄悄回落到自动发现(口径同
  `x_channels` 那条)。
  **`content_hash` 的口径抽成 `fulltext.body_hash`**,脚本和 `_save` 共用:两处各
  写一遍 sha256 的话,哪天这里改了口径,换出来的 hash 和重抓之后的对不上,一条内容
  白白多导出一轮。
- **复查的射程是「属于开了补抓的订阅」,不是「报过补抓成功」**(`_suspect`)。
  后者(`fulltext_at<>''`)漏掉的恰恰是这个脚本自己制造的中间态:第一版跑过一次
  之后,那两条生产条目的 `fulltext_at` 和 `fulltext_tries` 都归了零、body 还是那段
  样板文字 —— 和「从没补抓过」长得一模一样,**再跑一次复查一条都选不中**(第 2 轮
  审查点名的就是这个:「不再被复查选中」)。**在这个射程里「body 是样板文字」就是
  充分判据**:聚合源的 feed 原本给的是跳转壳(标题 + 域名 + HN 得分),过得了判据,
  真正文同理 —— 一条 body 是版权声明或作者简介的,只能是补抓这条路写进去的。
  **没开补抓的订阅一个都不碰**,它们的正文是 feed 自己给的,不在这个脚本的射程里。
- **写回那一刻必须确认「这一条还是我扫到的那份 body」,而且判据待在 UPDATE 自己的
  WHERE 里(`_downgrade` 的 `AND body=?`)。** 这条原来写着「不取维护锁也不问管道
  忙不忙:改的是一条条目的正文和几个标记,幂等、可重跑,最坏的交错后果是某一条被
  多抓一次」—— **那句话是错的**。第 1 轮版本只改几个标记(那些确实幂等、谁盖谁都
  一样),第 2 轮加上 `body=?` 之后这条写回就变成了「拿一份旧快照覆盖正文」,而
  `_suspect` 的读事务读完到真写回之间还隔着一段备份库 I/O:同步在这期间把这一条
  补抓成功、翻译好、导出到 vault 之后,这份旧计划照样按 `key` 盖回去 —— 914 字
  完整正文连同中文译文和补抓成功时间一起变回 29 字的标题加链接,后面三轮再抓不到
  就永久停在壳上,而**下一次抓取未必还能拿到它**(2026-10-09 第 3 轮审查双线程实测,
  独立复现三次)。
  **维护锁对这件事压根不适用**:补抓那一侧的 `fulltext._save` 自己就不持维护锁,
  这边取了也挡不住它 —— 所以换的是条件更新,不是加锁。
  **比的是旧 body 本身,不是 `content_hash`**:那一列在这张表上有两个写入方、两套
  口径(`registry.put_items` 写整个 entry 的 JSON 摘要,`fulltext.body_hash` 写
  `sha256(body)`),而这里要回答的恰恰是"我读到的那份正文还是当前那一份吗" ——
  直接比正文没有第二份口径可漂。
  **0 行不是失败,是我们想要的末态**(同步刚把正文补上了),所以成功/跳过**按实际
  更新结果统计**、跳过的那几条如实报出来:按计划条数报的话,这一趟会说「已收拾 1 条」
  而库里一个字节都没改,人看完就以为处理过了。**也不就地重判** —— 重判会变成一个
  没有终点的循环,而上一条那个射程让「body 是样板文字」成为与 `fulltext_at` 无关的
  充分判据:新内容要是又一份样板文字,下一次 scan 自己就会再选中它。
  **「先 SELECT 一次比对、再无条件 UPDATE」那一版在这套用例下是绿的,如实记着。**
  它把窗口从"永远"缩成了"两条 SQL 之间"(中间没有任何 I/O),而这套回归没有能打开
  那个窗口的手段 —— 选 WHERE 的理由因此是**构造上的**(判据和那次写入同生共死,
  不必论证窗口有多窄),不是靠某一条用例钉住的。口径同 collector 那条「判据就在
  UPDATE 自己的 WHERE 里,不许在 Python 那边先 SELECT 一次」和 `sync._claim_write`。
- **复查作废译文之后,一份在途的旧翻译回包不许把它写回来。** 判据和这里是同一条
  规矩,只是换了个写入方向 —— 实现在 `translate._save` / `_fail`(`WHERE key=? AND
  title=? AND body=?`),口径写在「英文内容翻译」那一节。两个方向的回归摆在同一个
  文件里(`tests/test_fulltext_recheck_race.py`)。
- **失败过的优先**(`ORDER BY fulltext_tries DESC, fetched_at DESC, key`),理由同
  `translate.translate_pending`:按升序排的话重试永远排在"从没试过"的后面,几百条
  积压下要几十轮同步才轮得到一次重试。`key` 收尾是为了定序 —— `fetched_at` 只精确
  到秒,一批抓回来的条目时间戳一模一样。
- **`_save` 要把旧译文一起清掉。** 旧译文译的是那份壳,正文一换它就作废了 —— 留着
  的话导出会把"壳的译文"当成这篇文章的中文正文写进 vault,而 `translated_at` 非空
  意味着再不会有人去订正它。`translate_tries` 同理归零,新正文值得一份新的重试额度。
- **`subscription_items` 要一条按 `item_key` 的索引。** 它的主键是
  `(subscription_id, item_key)`,按 item_key 查用不上;而队列判据正是"这个条目属不属
  于某条开了补抓的订阅",它对每一行各查一次 —— 没有这条索引就是逐行全表扫,面板翻
  一页、导出选一次待导出集合都要付这笔钱。
- **`scripts/feed_trim_history.py` 的 `pending_translation` 要把那段 SQL 真的拿去查,
  不在 Python 里照着抄一遍**(所以它收一个 `conn`)。原来是只取重试上限、再用三个
  Row 字段把条件复写一遍 —— 注释里那句"直接取 `translate.queued_sql()`"当时就只
  兑现了一半,而判据一加条件就当场漂:补抓那一档问的是"这个条目属不属于某条开了
  补抓的订阅",Row 上压根没有对应字段,照抄的那一版会把**还在等正文**的条目当成
  "排在翻译队列里"**不可逆删除**,而它们一次模型调用都还没花过。
- **原文链接后面不是网页时按抓取失败处理,绝不把文件语法当成正文**
  (`readable.html_problem`,`fetch_one` 抛 `FeedError`)。原文是 PDF 论文时,
  `decode` 按 `errors='replace'` 把那堆字节解成一段 `%PDF-1.4 1 0 obj << /Type
  /Catalog …` 加几百个替换字符,而**提取器眼里它只是一份没有标签的文档、整篇就是
  "正文"**,长度又轻松越过 `MIN_CHARS` —— 于是补抓报成功、`fulltext_at` 落下、
  条目**离开重试队列**,接着拿这堆乱码去买一次翻译(2026-10-09 审查实测:1149 字
  正文、364 个替换字符,论文一个字都没有)。**可以不支持 PDF,但不能把"没读到
  论文"说成"已取得正文"** —— 后者是不可恢复的:那一条再也不会重试。
  **三道,各管一类撒谎方式,而且各有自己那条用例**:①**声明的类型**不在
  `_TEXT_TYPES` 里(站点自己说了这不是网页);②**文件头**命中已知魔数;③头部有
  **NUL 字节**,**而且拿 `decode` 真解一次之后它还在**。②不是①③的冗余:
  **PDF 的首个压缩流常常在几十 KB 之后**(前面是一长串 ASCII 对象定义和 xref),RTF、PostScript 整份都是 ASCII —— 这一档 NUL
  那道完全是瞎的,而 content-type 又正好配错成 `text/html` 时(小站常态)只剩魔数
  那一道。**这件事是反向验证逼出来的**:第一版的 PDF 样本头部带着压缩流(有 NUL),
  于是去掉魔数那一道整套测试照旧全绿 —— 现在另有一条头部全 ASCII 的样本钉着它。
  `text/plain` **留在放行名单里**:实践中大量小站把 HTML 页配成了它,而真纯文本页
  经提取器出来仍是可读文字(只是段落按 HTML 规则折叠),比一个跳转壳强;真要挡的
  二进制由②③管。抛异常而不是返回空串,是因为空串那条路的提示写的是"可能需要登录
  或由脚本渲染",而这里的原因明确得多 —— 面板上要说得出是哪一类。
  **③那条不能裸着问「有没有 NUL」。** UTF-16/32 的**正常文本**每隔一个字节就是
  `\x00`,裸着问等于把编码本身的产物当成罪证:一篇正常 HTML 编成 UTF-16、响应
  明确声明 `charset=utf-16`,`decode`+`extract` 本来取得 914 字正文,却被判成二进制
  (`done=0 / failed=1`,2026-10-09 第 2 轮审查)。
  **判据是「拿真正会用的那个解码器解一次,NUL 还在才算二进制」,不是另开一张
  「哪些编码放行」的名单。** 第 2 轮开的那个口子(`_wide_text`:BOM 或声明的
  charset 命中就放过)**和 `decode` 不是一份东西** —— 后者压根没有 BOM 分支,
  只试 HTTP charset、原始字节上的 ASCII meta charset 和 UTF-8。两张名单一漂,
  **只有 BOM、不声明 charset** 的 UTF-16/32 页面就从「安全失败」变成了
  「错误覆盖 + 成功退出队列」:放行之后按 UTF-8 解成乱码、NUL 留在里面,HTML
  解析认不出结构,`plain` 清掉 NUL 之后反倒把整段 HTML 源码当成了正文,长度轻松
  过 `MIN_CHARS` —— 补抓**报成功**、`fulltext_at` 落下、这一篇**永远**离不开壳
  (2026-10-09 第 3 轮审查实测 UTF-16/UTF-32 各一次:中文标题丢失、导航和评论
  全混进正文、7 个替换字符;同内容声明了 charset 的对照组 0 个替换字符、导航
  正确剔除)。**可以不支持某种编码,但不能把"没读对"说成"已取得正文"** ——
  后者是不可恢复的,那一条再也不会重试。直接调 `decode` 就没有"两张名单"可言:
  解对了没有 NUL,解不出来 NUL 还在 —— 一致性从一条约定变成了结构。
  **配套的是 `decode` 自己要认 BOM**(`_BOM_CODECS`,排在 HTTP charset 和 meta
  前面,照 WHATWG 那套嗅探顺序 —— BOM 是内容自己带上来的,最可信)。**UTF-32
  必须排在 UTF-16 前面**:`\xff\xfe\x00\x00`(UTF-32 LE)以 `\xff\xfe`(UTF-16 LE)
  开头,反过来排的话每一篇 UTF-32 页面都被当成 UTF-16 解。顺带认 UTF-8 的 BOM:
  不认的话正文开头多一个 `﻿`,而 `plain` 的空白折叠不吃它。
  **六档的末态**(BOM 有/无 × charset 有/无):BOM 在就按它解(两格都对)、只声明
  charset 的按它解、**两样都没有的那一格照旧安全失败**(按 UTF-8 解、NUL 还在,
  拦下并计次重试);魔数和声明类型那两道照旧跑在前面,所以"content-type 撒谎成
  `text/html` 的 PDF"仍然被魔数挡住 —— 真要挡的二进制一个都没放过去。
  **没有改成「解出来替换字符太多就判失败」**:那是一道新的启发式(多少个算多?),
  而这一轮的根因明确是"放行判据和解码器不是一份东西",修一致就够了 —— 对照组
  实测替换字符是 0。
- **重导出靠 `content_hash` 变了,`_save` 不许清 `exported_hash`。** 导出闸门是
  `exported_hash<>content_hash`,正文一换前者就自然成立;而 `exported_hash` 同时是
  **「这一篇入没入过库」的事实来源**(`registry.items` 的两态、`sync._export` 的四档
  都读它)。清掉它的代价实测过:一篇**已经能展开阅读**的旧条目补抓成功之后,面板上
  标题连同「展开阅读」一起消失、换成一句"译成中文之后才写进知识库",而 vault 里那份
  md 好好地躺着 —— 而且**不是一瞬间的事**:补抓之后这一条重新排进翻译队列,翻译排队
  或失败时它会一直这样(2026-10-09 审查实测 + 截图)。这和上面那条「两态」是同一个
  病换了个位置:上一轮按 `exported_hash` 把**补抓**那两档分开了,而补抓成功之后判它
  的是**翻译**那两档,清掉 `exported_hash` 正好把它从 `retranslating` 打回
  `translating`。`translate._save` 清它是对的 —— 它不改 `content_hash`(译文另存
  `title_zh`/`body_zh`),没有别的办法触发重导出,而译完之后这一条压根不在队列里、
  两态判定不适用。
- **正文从壳换成全文之后,知识库里那份按旧壳算出来的提取结果要作废**
  (`fulltext.retire_stale`,由 `sync._export` 在导出之后调一次)。不作废的后果不是
  "晚一点更新":`documents.extracted_at` 非空意味着这一篇**永远**不进
  `extract.pending_docs`,而 `sync._kept_meta` 又把旧 `tags` 原样写回 frontmatter、
  索引照它重建 `doc_tags` —— 于是摘要、主题、实体永久停在那条链接上,正文里的项目
  一个都不会出现在检索、图鉴和日报里(2026-10-09 审查实测:新中文正文确实进了
  chunk,而 summary 还是「OLD SHELL: only a link and HN points.」、tags 还是
  `topic/link-only`,`pending_docs` 是空的)。既有那条「同一篇换个语言、保留提取
  结果」的策略对这里不成立:**几十字的链接变成整篇文章,标签口径没变但内容全换了。**
  四件事:
  ①**时点是「新正文真的落了盘」,不是「网络抓到了正文」**(判据
    `extract_stale=1 AND exported_hash=content_hash`)。补抓成功之后这一条要先排队
    等翻译成功，翻译失败或同步被停止时 vault 里还是旧壳 —— 在补抓
    那一刻就清掉 `extracted_at` 的话,提取阶段会拿**旧壳**再买一次提取、写回一个
    同样过时的结论,而 `extracted_at` 跟着又非空了:等正文译完导出之后,摘要和主题
    照旧是壳的。
  ②**做完才把 `extract_stale` 放下,顺序不能反。** 这一步失败(kb.db 连不上、磁盘
    满)时标记留在原处,下一轮导出再来一次;反过来写的话这几篇**永久**停在「摘要
    还是那个跳转壳」的状态 —— 它们的 `exported_hash` 已经等于 `content_hash`、压根
    不在待导出集合里,没有任何路径回来重试。所以它查的**不限于本轮刚落盘的那几篇**。
  ③**异常要接住**(`sync._export` 里那个 try)。这一步失败只是"摘要还是旧的",让它
    冒上去会把 `materialize` 连同后面的 index/extract 一起带掉 —— 成功的文章已经
    落盘、`exported_hash` 也更新过了(同 `is_zh` 那次事故)。记进 `errors` 让阶段
    说得出来。
  ④**摘哪些 tag 只有一份口径**(`STALE_TAG_PREFIXES` + `keep_tags`,`sync._export`
    摘 frontmatter 和 `_drop_extraction` 删 `doc_tags` 共用它)。两处各写一遍的话,
    md 里摘掉的和库里删掉的不是同一批,而下一轮索引按 frontmatter 重建 `doc_tags`
    —— 差额会被原样补回去。摘的只有 `topic/` 和 `entity/`:**`flag/软广` 和人工 tag
    留着**(promo 由重新提取自己重判,改判时 `sync_promo_tag` 会摘掉 md 里那行),
    要作废的是"按旧链接算出来的结论",不是别人写进这篇 md 的东西。
  **不清 `promo_level`**:重新提取时 `save_extraction` 会拿新判定覆盖它。
  **不去动 `store.upsert_document` 的 `extracted_at` 语义**(让它按 content_hash
  变化自动失效):那是全库行为,公众号文章改一个字就要重买一次提取。
  kb.db 的连接现开现关、`config.DB_PATH` 现读(`connect` 的默认参数在函数定义时就
  绑死了,测试没法把它指到临时库上去);常态下那条查询是空集合,一次连接都不开。
  **测试里 `config.DB_PATH` 必须指到 tmp**,理由同 `maintenance.DATA_DIR` 那条。
- **一次提取的结果要和它基于的那份正文绑在一起**(`extract.body_fingerprint` +
  `_require_current_input`,`save_extraction(..., input_seen=)`)。上面那条作废只负责
  「把这一篇排回待提取队列」,它管不住**此刻正在提取的那一轮**读的是哪一份正文 ——
  而补抓把「几十字的跳转壳」换成整篇文章,正是把「模型读走旧壳 → 期间正文换新并
