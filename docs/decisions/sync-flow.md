# 同步中心那几行「按类型排的线」(kb/pipeline_flow.py + pipeline_sources.py + pipeline_lanes.py +
# pipeline._sources / _run_pipeline + pipeline_payload.py + daily_run / daily_sync / daily_library +
# web/pipeline_api.py + static/js/pipe_flow.js / pipe_flow_rows.js / pipe_log.js / pipe_matrix.js)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是形态说明和回归清单。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束

- **计划只记「要求了什么、走到了哪、各跑了多久」,不记成败**(`pipeline_flow`)。成败照旧在阶段卡片和结果账里
  (`pipeline_state` / `pipeline_results`),节点的红绿由前端从那两份里读。唯一的例外是「生成日报」:它不是管道阶段,
  没有卡片可挂,结论由日报那一轮在 `leave(..., result)` 交进来。
- **谁的计划由谁收尾,所有入口都带 owner**:手动同步是那一轮的 run id,日报是那一批的 batch 身份(一批里好几轮管道共用
  一份计划)。对不上的一律当「这份计划管不到你」:`enter`/`advance` 放行,`request` 拒(`STALE`),`end` 不动。
  **计划按 owner 各存一份(`pipeline_flow._plans`),谁开张都只写自己那一格,一份计划只在它自己的 owner 收尾时(`end`)
  才消失。** 原来全局只有一格:手动同步正在抓、刚受理了「结束本类型」,定时日报这时开张(它在等管道空出来之前就建计划),
  那一格被换掉,手动那一轮回头再问时找不到自己的计划、被当成「本来就不受控」放行 —— 导出照跑,受理过的那一下作废。
  所以日报那份还在时挤进来的手动同步也拿它自己的计划(两份互不相碰)。面板画哪一份由 `flow.live(state)` 答:管道在跑
  画这一轮自己的(没有就不画,不拿别人那份顶),空着画日报那一批的。`cutting()` 同理,只看此刻这轮管道自己那一份。
  「这一轮已经要停了」(`flow.stopping(owner, kind)`)同样只认归属相符的停止标记:另一轮手动同步被要求停止时,日报那份
  计划里还没轮到的几类照样能跳过 / 撤回。`flow.end` 只在 `_end_run` **之前**判定「这一轮是不是我的」(之后 run id 可能已经换成下一轮)。
- **锁序:`pipeline_state._lock` → `pipeline_flow._lock`**(批次合并发布在那把锁里读 `record`);日报那边同理,
  `daily_state._lock` 在外。持着 `pipeline_flow._lock` 时不许碰会取那两把锁的函数,**写日志一律在锁外**。
  `request` 要读的「停没停」(`stopping`)也在锁外问,问完再进锁核一遍其余条件。
- **「受理提前结束」和「换下一步」在同一把锁里**(`advance`)。分成「问一句」+「换步」两次的话,请求正好落在两步之间
  时会被受理、而下一步照样开跑 —— 那一步要是导出,翻译 / 正文补抓读的是只认整轮停止的判据,会整步跑完。提前结束
  只在手上那一步**不是这一类最后一步**时受理;来源那一类只认抓取那一步(导出是最后一步,受理了也兑现不了);「生成日报」
  不受理,而且**整轮停止在那一档同样不受理**(`daily_run.request_stop`),所以文案和按钮都不许把人指到「停止整轮」上
  (按钮在生成期间置灰并说「停不下来」)。
- **采集器里「该停了吗」只有一份口径:`pipeline_flow.halted()`**(整轮停止,或者正在跑的这一类被提前结束)。抓取期的
  那几处(`feeds/sync.py` 抓取循环、`feeds/prefetch.py` 两遍整批预取的 `should_stop`、`youtube/collector.stopped`)都过它。**导出期的那几处(翻译、正文
  补抓、`feeds/sync.py` 导出段)照旧只认整轮停止**:提前结束在抓取那一步受理之后,导出根本不会开跑(上一条),那几处
  永远碰不到「被提前结束」这一档。**`cutting()` 还要核一遍这份计划是不是此刻这轮管道的**(owner 等于
  `pipeline_state._state` 的 run id 或 batch,而且管道在跑):日报那一批进了某一类、却还排在别人起的手动同步后面等时,
  那一类上的提前结束不许让别人那一轮的采集器读成「该停了」。
- **终止命令一律带着它要停的那一轮的身份,核对和落笔在同一把锁里**:类型按钮带 `owner`(`flow.request`);「停止整轮」
  带 `run_id`(`/api/pipeline/stop` → `pipeline_state.request_stop(run_id)`)或日报那一批的 `batch`
  (`/api/daily/stop` → `daily_run.request_stop(batch)`,批次身份记在 `daily_state._state['batch']`)。确认框开着时那一轮
  可能已经收尾、下一轮接上了 —— 前端确认之后先比一次身份(变了直接作废、说「没有停止」),后端在锁里再比一次(确认
  之后、请求落地之前那道缝前端管不到)。不带请求体的老调用照旧停此刻那一轮。
- **进了门却没起得来的来源也要留下它自己那一格失败**(`pipeline_results.failed`,`pipeline_sources._broken`):采集器
  取不到、建账那一下(`channel_run` 进门)就炸、账本开轮被拦,都只写了合并卡片 —— 几个来源合在一张卡上时,同步中心
  按类型看这个来源念的是它自己那一格,没有就无从说起。那一格红记在点名范围上,**覆盖范围一律记零**(不许拿它清任何
  旧账),已经有自己那一格的不动。**前端反过来钉一边**:进过门、走完了却没有自己那一格的来源步骤念「结果未知」,
  不许推成「已完成」(那是别的来源的绿),也不许推成「没跑」(老留档没有逐来源结果、而那一步整体跑过的同理)。
- **没跑的那一段也要建账,但不交覆盖范围**(`pipeline_sources._settle`):被跳过的、被停掉没轮到的、提前结束没导出的那
  几格记成 `skipped` / `stopped`,当日账本把它们按「没执行过」读 —— 零覆盖,旧欠账原样留着。**一格都不建是错的**:没有
  自己那一格时折账退回整步那张合并卡片,而只要别的来源都成了那张卡片就是绿的,没跑的这个来源的旧失败会被它结清。
- **账本上的这一轮等真有来源进门时才开**(`Lanes.start` 的 `opened`)。全被跳过、或者起跑时已经被停的那一轮不是一次
  抓取,开了就是凭空多出一次「确定 0 条」的抓取。开轮和空回执**在主线程上、各路起跑之前**做(开轮那道闸抛出去的异常
  照旧穿到编排层)。「交完了」(`note_end`)只在开过轮、而且**每一路都走完**(`Lanes.join`,含停止那一档)之后记;
  有一路的异常穿出了它自己的隔离(`Lanes.broken`)的那一轮不记。
- **多来源各来源同时跑:每个来源一条线程,各自 抓取 → 导出**(`pipeline_sources.Lanes`);全库那几步(入库处理 →
  生成日报 → 整理)照旧一次一组、排在来源后面。**单来源一行不动地走老路**(`pipeline._sources` 调
  `_run_crawl(crawl_filter)` / `_run_export(crawl_filter)`,既有回归钉着这两个入口和参数),只是也绑上它的通道。
  计划里来源那几类各自走到哪一步记在 `lanes`({节点: 那一步}),全库那几组照旧用 `running` / `step`;老留档没有
  `lanes`,前端 `pipeFlowRunning` 两样都认。**采集器整条路上每个来源只取一次、按来源顺序在主线程上取。**
- **全库那几步前面有一道门**(`Lanes.wait_gate`,计划里的 `gate` / `gate_at` / `late`):入库处理要等所有来源跑完 ——
  新导出的文件不进索引,日报就取不到它们。门在等的时候用户可以点「不等了，继续」(`request(owner, 'ingest', 'go')`,
  只在 `gate == 'wait'` 时受理、来源那几类不受理);日报超预算时由 `flow.release` 代按 —— **代按是一个待消费的意思**
  (计划里的 `release`),还没走到门口时按下也作数,门一开始等就放行(只试一次的话,预算恰好在各路起跑前取采集器那段
  时间里用完,放行就落空了,日志写着「接着入库处理」、实际一直在等)。门打开那一刻**还没跑完的那几路一律记进 `late`,
  已经在导出的也算**:「进了导出这一步」证明不了「这一轮的入库看得到它的文件」—— 订阅那几类的导出先补正文、翻译
  (网络和模型,可能好几分钟),最后才拿维护锁写 vault,索引可以先拿到锁扫完。拿不准往「没等它」那边记(误记顶多
  日报里多一句「没等它」,漏记是那几篇静默缺席)。`late` 那几路**照常跑完、照常记账,只是这一轮的入库和日报不等它**;
  还没开始导出的,导出**挪到全库那几步之后**(`Lanes.hold`,手上那一步收掉、`lanes` 里记空串,面板上念「抓取做完了，
  导出排在入库处理之后」)—— 订阅那几类的导出整段攥着维护锁,跟入库处理抢锁的话索引最坏要干等十几分钟;已经在导出的
  照常导完。「没等它」和「开始导出」在同一把锁里读写(`Lanes._lock`)。整轮被停时谁都不算没等。
  **整轮收尾之前等所有来源跑完**:管道是单例,没跑完的那一路还在写库,不许宣布空闲。**起到一半起不动了**(线程开不
  出来)也一样:句柄还没交给编排层,它的 `finally` 里没有 `join` 可调,所以 `Lanes.start` 自己等已经起跑的那几路跑完
  再往外抛(`Lanes._abort`;没起来的那几路各留一格「没有起跑」,这一轮不记「交完了」)。
- **阶段卡片「改一段 → 合并 → 发布」在同一把锁里做**(`pipeline_segments.publish_lock`;两个发布口 `stage_segment`
  收尾、`fold` → `_stage` 共用,失败名单那一笔同锁)。线程局部的归属只答「这句是谁的」,答不了「谁的快照后发布」:A 刚合
  并出「B 还在跑」就被抢占,B 发布了「全都好了」,A 回来再把旧的盖上去 —— 两段都是 ok,合并卡片却停在 running,收尾时
  被判成「流程中断，未完成」。锁序:`pipeline_state._lock` 在外,这把在里;锁里只有内存里那几行。
- **归属按线程认**(`pipeline_lanes.bind`):每条来源线程进门时绑上自己的通道,阶段卡片的分段(`pipeline_segments`
  的 `_mine`)、结果账(`pipeline_results` 的 `_mine`)、日志标记都据此知道一句话是谁说的。原来三处都假定同一时刻只有一个
  来源在跑(「当前那一段 / 当前那个来源」各只记一格),两路同时跑时 RSS 的结论会写进公众号那一段、记到公众号那一格账上
  —— 当日账本拿 RSS 的绿去结清公众号的旧失败(静默丢数据)。**没绑过的线程只在此刻只有一路开着时算它的**,几路同时
  开着就谁也不记(结果账)、退回最后那一段(分段)、日志归「全库」—— 宁可归到全库,不许归到另一个来源头上。眼下所有
  往面板报进度的调用都在来源那条线程上(采集器自己的线程池只在调用方那条线程上汇总)。**来源那一路不许把「当前阶段」
  从全库那几步抢回抓取 / 导出**(`_stage` 那一句;日报按它念进度)。
- **`cutting()` 按线程认那一路**:绑着通道的线程只看自己那一类有没有被提前结束;没绑的线程(管道主线程)只在只有一路
  开着时认它,或者认全库那一组的提前结束 —— 几路同时开着时别的来源的「结束本类型」不许让主线程读成「该停了」。
- **日志按来源各留最近 40 条**(`pipeline_lanes.trim`,每行带 `<通道>` 标记;合并发布、写盘失败那几处同口径)。总数
  80 行的老口径在几路同时跑时,刷得最快的那一路(YouTube 元数据进度、X 逐账号进度)会把别的来源仅有的几行挤出去,
  而那几行常常正是它的失败原因。
- **大V观点存条目那把维护锁排队等,不再零等待**(`x_intake_store.LOCK_WAIT`,缺省 300 秒,`KB_X_LOCK_WAIT` 可调;
  `feeds/sync._save_result` 同口径)。几路同时跑时它会撞上 RSS 导出正攥着那把锁,零等待就是整批静默不存。**`set_block`
  照旧零等待**(它的契约和回归在同一条线程里先攥着真锁)。**300 秒是单次上限,不是边界**:这几笔逐账号调,每笔各拿一份
  完整等待的话,锁被长期占着时 51 个账号光准备就是四个多钟头,按了停止也照等。所以一轮 X 采集共用一个「该停了吗」和一个
  截止(`x_intake_store.bounded`,`Intake.run` 套上;最后那次存盘走 `save_lock`,停止读 `flow.halted`):每笔只等到截止、
  按了停止当场放弃(`LockBusy`,按本机故障记待续)。截止分两档 —— **还没联网的准备**(`prepare`)只等到联网截止;**已经
  做完的成品**(暂存、确认、收尾、存盘)可以晚交,截止是整轮预算之后再宽限一个 `LOCK_WAIT`(整轮最多多等这么久)。等锁的
  时间算在整轮预算里,不另补。
- **计划建不起来不许拦住同步**:`begin` / `open_daily` 抛了就按「没有计划」跑(只是这一轮点不了跳过),日志里说一句。
  `_keep_flow` 同理不许抛。
- **前端只认身份对得上的那一份计划**:跑着的认 `flow_live`(owner 等于这一轮 run id 或它所在那一批),留档那一轮认它自己
  的 `flow`(`flow.run === run_id`)。都对不上就按计划阶段和来源推一排**只读**节点 —— 宁可点不了,不许把别人那份计划的
  跳过名单念到这一轮头上。
- **「停止整轮」在日报那一批里停的是整批**(`/api/daily/stop`,它顺手停掉手上这一轮管道)。只停管道的话日报接着出报、
  整理,按钮上那句「后面排着的类型都不再跑」就是空话。
- **「不再抓取」的过滤要连结果账一起过**(`pipeline_failures.strip`):按类型看某一个来源时念的是它那一格结果账,只过卡片
  的话删掉的那条在「点开这一类」时又回来了。返回值只数卡片那一处(同一条在两处各有一份)。**状态接口要等回包拼完了
  才过滤**(`pipeline_status` 最后一句):跑着时那份实时结果账是后挂上去的,先过滤再挂就是没过滤。
- **整轮的结论按整个业务轮次数:管道那几个阶段 + 「生成日报」**(`pipe_flow.js` 的 `pipeRoundSteps`)。概况的标题、
  进度、页头、历史那一行都过它。只数管道阶段的话,日报还在生成(管道早空了)、或者生成失败时,这一轮照样写「已完成」。
  生成失败不归「重试失败项」管,所以那一档不说「已不用补」、也不指那颗按钮。
- **类型计划跟着终态那份契约走**(`pipeline_payload.run_payload` 带 `flow`,`_restore_once` 恢复它):只进历史那一份
  的话,重启之后最新那一轮的类型耗时就没了。**历史里标着「最新」的那一行画活的那一份**(`pipe_matrix.js` 的
  `pipeMatrixModelOf`,结论配的计划同理 `pipeRoundPlan`):留档那份是子轮收尾那一刻抄下的,日报那一批还要接着生成,
  而点它回到的正是活的那一份。
- **同一轮的结论更新了,版本也要变**(`pipeline_batch` 的 `_batch_rev` → 合并结果的 `revision`,
  `pipeline_payload.own_revision` 只认身份对得上的那一份,`result_version` 带上它)。日报那一批的身份在出报前后是同一个,
  而出报的结论是最后一个子轮收尾**之后**才发布的(`batch_note`):版本不动的话前端那份历史缓存永远停在出报之前,点它看到
  的是「生成日报」没有结论、整行写「已完成」。修订号随批次每一次发布进一版(被拒、写盘炸了也进),状态和历史两边
  一起变;**选中那一行的键(`row_key`)和「是不是这一轮」(`same_event`)只认身份**,不带修订号。重启要恢复它
  (`_restore_once`),不然状态那份比历史那一行少一截,两边永远对不齐。
- **历史清单整份另有一个版本:文件指纹(`pipeline_history.history_rev`,inode + 修改时刻纳秒 + 大小),状态和历史两个
  端点各带一份**。被另一轮接替的那批日报,结论是原位补进它自己那一行的(`update_history_round`):最新那一轮的版本不动,
  前端那份缓存和正在看的那一轮就一直停在出报之前,刷新整页才出来。前端历史那一块的凭据是「最新那一轮**已经收尾的**
  版本(`settled_version`)+ 清单指纹」(`pipe.js` 的 `pipeHistoryVersion`,回包那一侧 `pipeHistoryVersionOf` 同一种拼法)。
  **历史那一块跑不跑都对齐,只有待处理数等空闲**:正在跑的那一轮不在历史里,所以不拿 `result_version`(跑着时它说的是
  这一轮);原来跑着时把历史的目标整个清空,另一轮同步跑多久,被它接替的日报补上的失败原因就得在页面外面等多久。历史端点**先取指纹再读清单**:读的间隙里又写了一次,回包带的是旧指纹,下一次轮询会再取(反过来就是拿新指纹给
  旧清单盖章)。指纹只比相等不比先后;写入一律原子替换,所以每写一次都是一个新文件,换哪个写入口、跨不跨重启都不用另记账。
- **收了尾的记录里「生成日报」没有结论,念「结果未知」,不念「已完成」也不念「没跑」**(`pipeFlowGenerate` 的 `live`
  那一档、`pipeFlowState` 那句「没进过门」要让它先)。日报那边不管停在哪一步都会交结论(`daily_run` 收尾那一笔),所以
  缺它只能是那份记录拍在结论之前、或者那一笔没落下。计划还在后端手里时缺结论才是「还没轮到」。
- **跳过 / 提前结束只管「还没做的那部分」,已经发生的失败照实留着**(后端 `pipeline._skip_step` → `_settle_skipped`)。
  意图不许改写事实:存量提取是抓取期间并行跑的,它那一格可能早就红了,收尾一句「本次跳过」盖掉之后那条红只剩在日志
  里,面板和历史都只写「已跳过」,**重试也捞不回来**(实测形态:先点「入库处理 本次跳过」,随后那边队列读失败
  发布了 error,收尾把它刷成 skipped)。两处判据分开写、不许混用:**「留下过什么」问 `pipeline_stages.extract_told`**
  (队列压根没读出来也算,它一篇都没经手却已经红了),**「做过几篇活」才问 `_pre_worked`**(只给那句「存量已提取 N 篇」
  用,它必须判 False 才不会把那条 error 刷成 pending)。`_settle_skipped` 是整个编排层的兜底:哪一步已经发布过红,
  跳过 / 提前结束都不许改写它(阶段卡片每轮起跑时重置,所以看到的红只会是这一轮的)。
- **前端那一层:`state` 只答「走到哪了」,`issues` 答「有没有出问题」,两样正交、谁也不许代表谁**
  (`pipeFlowState`:生命周期一律按计划推 —— running / times / done / skips;失败只是跟着的一枚标记)。两个方向都坏过:
  - 生命周期盖住失败 → 跳过余下几步把已经发生的红抹掉,四处**一致地**念「本次跳过」,红一个字都看不见;
  - 失败冒充生命周期 → 还没轮到的一类因为并行那一步红了就念「已完成」,「本次跳过」那颗按钮当场消失、后面那一类也
    不再把它算成前面要跑的(它其实仍要执行),跟后端 `pipeline_flow.request` 的可跳过判据两端对不上。
  归约只有这一层,四个消费方(那一行此刻那句话与行上那颗按钮 `pipeFlowSay`/`pipeFlowRowAct`、展开那一块的说明
  `pipeFlowHead`、历史格 `pipeMatrixTip`/`pipeMatrixCells`、「连着几轮卡在同一处」`pipeMatrixRepeats`)都要把两件事
  各说一遍,**不许在消费方给某个按钮补特例**。
  配套口径:**动作准入与「排在谁后面」只认生命周期**;**红的颜色跟着 `data-issues` 走、不跟着 `data-s` 走**(CSS 里
  那两条排在状态规则之后);
  **「连着几轮卡在同一处」数的是红本身**,不是「这一轮念的是哪个状态名」。反过来钉一边:没有失败的跳过照旧念
  「本次跳过」,好好跑完的那一轮照旧把连续失败断开。

## 形态

- **节点**:每个来源一个(`src:<通道>`,挂抓取、导出两步),全库那几步按组(`ingest` 索引+提取、`daily` 生成日报、
  `tidy` 整理工具+Wiki),组里有任何一步在计划里这一组才算这一轮的一类。
- **一类一行**(`pipe_flow_rows.js`):名字 | 一根细条 | 此刻那句话 | 耗时 | 动作。细条**全轮共用一个比例尺**(计划里
  各类的时刻):位置是它什么时候开始、长短是跑了多久,末端在闪的还在跑;同时跑的那几路细条并排,更早逐个跑的那几轮
  自然排成阶梯。来源和全库之间一条细分隔线。不要再加分组标题、轨道和尖角。
- **按钮(行上只放一颗)**:正在跑的来源「结束本类型」(带确认;抓完在等导出的那一路不给);门在等时入库处理那一行
  「不等了，继续」,那一行写着「等 X、Y 跑完 · 已等 N 分」;还没轮到的一类「本次跳过」(门在等时挪进展开那一块),
  轮到之前可以「恢复执行」;没等的那一路那句话前面带「本轮不等 · 」。整轮「当前步骤结束后停止整轮」(带确认)。
  翻留档那一轮时一律只读,停止按钮也藏起来。
- **点一行在它下面展开那几步**:`#pipe-stages` 那六行挂在展开那一块里(失败明细、「不再抓取」、待处理数都挂在上面),
  那一块始终在文档里,只挪到被点开那一行后面(重建会丢掉焦点和明细的展开状态)。几个来源合在一张卡片上时,行上念的是
  那个来源自己那一格结果账。还在跑的那一轮默认一行都不展开,收了尾的那一轮默认展开第一个出问题的那一类;「看第一个」、
  点历史格都会把它展开。展开那一块里有「只看这一类的日志」。
- **运行日志一行三格**(`pipe_log.js`):时间 | 谁说的 | 正文,上面一排按来源筛(全部 / 各来源 / 全库)。下载的是原样那
  一份(带标记、不受筛选影响)。
- **历史运行是一张表**:一行一轮、一列一类,同一类从最新那一轮往下连着两轮以上卡在同一处(数字抹掉之后比原因),表底
  点一句「连着 N 轮都是…，不像偶发，重试多半不顶用」。行本身(选中、「最新」那一枚、点击核验、`#pipe-history-live` 在
  列表外面)的口径没变,还在 `pipe_history.js`。

## 已知的限制

- **公众号(本机绿泡泡库)没法在抓取中途停下**:它那一步是一个采集器子进程整步跑完,提前结束要等这一整步做完才生效
  (导出照旧不跑)。确认框里那句「有的来源要等这一整步做完」说的就是它。
- **「入库处理」本次跳过只管之后的那一遍**:存量提取是抓取期间就并行开跑的,跳过这一类时它已经做了的照实收进卡片,
  不会被抹掉 —— 「跳过」不等于这一类一点额度都没花。
- **日报出报之后那段整理要等管道空出来**(`daily_library.library_tail` 照旧借 `_sync_round`,最多等 15 分钟):没等的那一路
  在后台跑得比这更久,这一天的整理就记成「同步管道一直被占用」跳过。图鉴和图谱晚一天更新,下一轮照常补上。
- **大模型调用没有全局限流**(几路同时跑时翻译、YouTube 深加工、X 正文补全会同时调模型)—— 仓库主人明确不要,别加回来。
- **「重试失败项」那一轮没接这条线**(`pipeline_retry` 沿用老编排):节点按计划阶段推出来、只读,没有类型级的跳过、
  提前结束和本轮各类耗时。
- **两条既有回归把 `sync._state` 打成了 `{'stop_requested': False}`**(`tests/test_feed_targets.py`、
  `tests/test_feed_budget.py`),而 `halted()` 读的是 `pipeline_state._state` 本身。默认值同为 False,所以那两条照旧成立;
  要在那两处模拟「停止」得改打 `pipeline_state._state`。
