## 硬约束(原 CLAUDE.md「X 的采集通道(kb/feeds/x_channels.py + x_browser / x_feedgrab / x_cdp / cdp_attach)」)

- **时间线上的「显示更多」是残文信号,不是完整正文**。`x_post` 为 `browser`/`attach` 收到的这类条目
  打临时标记,在同一会话打开它自己的详情页补全,再交给 Article 补全和入库。详情页路由和正文所属推文
  的 status id 必须同时匹配,引用推和回复不能冒充原推;详情仍折叠、登录墙、超时或停止时扣留该条,
  水位保持原下界以便下轮重试。短推不额外导航;转推上下文保留;补全后的标题只取正文首行,不把后续
  段落塞进 Markdown 标题再次输出。文本按 DOM 文本节点读,恢复图片表情
  的 alt 与完整链接,不能把链接中隐藏的协议/路径当成换行。已入库残文不会被 `put_items` 去重更新,
  修复存量应走 `grab_store.replace` 的版本化替换,同时作废旧译文与提取结果,由正常导出重写正文。
- **读数稳定不代表正文完整**。`x_post.merge` 统一要求新正文严格长于原预览(不把转推前缀算进预览),
  采集端相等或更短一律不合并。存量的普通扩写仍共用此不变量,不能因「读两次一致且还没显示展开按钮」放行。
  **仅存量回填可清理已知旧链接产物**:详情页通过身份/展开检查后,识别 URL 任意字符位置的折行,
  不枚举视觉断口,不要求存在省略号。疑似项排序与替换判断共用 URL 游程识别,排序可宽、不能据此直接写回。
  替换时先按详情中的连续 URL 确认哪些换行确实位于 URL 内部,仅容许该 URL 紧邻的尾部省略号或前置独立
  省略号行作为可选排版标记;原页真实存在的省略号必须保留。除这些标记和空白外,存量全部字符仍须按序
  构成详情正文前缀,才允许等长或更短替换。URL 后的正常段落换行、URL 路径内的真实省略号不能冒充旧产物。
  不能只因含省略号或折行就放行任意短正文;转推上下文照留,采集端判据不放宽。
- **折叠推文带 Article 信号时,详情页失败不切断文章补全后路**。`x_post.complete` 统一编排:
  带折叠欠账的条目可移交 `x_article.fill`,只有确实取得文章正文并经过 `x_article.merge` 才清除欠账。
  接口答没有文章、全部后路关闭或取不到正文时,最后一道仍扣留条目并冻结水位,不许原样放行残文。
  **明确不存在与临时失败必须分开**:时间线和详情页共用 `x_page_state` 的状态判据,识别「该页面不存在」。
  详情页身份匹配、加载完成且连续两次明确不可用时跳过该条,不存残文,不为它冻结水位;水位仍只能推进到
  这一轮确实见过的推文时间。空白、加载中、登录失效、身份不匹配等未知状态照旧扣留重试。
  **临时请求出错不等于限流或不存在**:CDP 只观察当前页面会话、当前导航 loader、同源核心 GraphQL
  请求的 HTTP 状态,429 才是接口限流证据;普通 4xx/5xx 不能据此宣布推文不存在。非核心接口、其他来源、
  上次导航的迟到回包不参与判定;同一接口成功重试覆盖旧错误。主内容区重试按钮的图标结构是无响应时
  的语言无关错误信号,实测中英文错误文案仅作兜底。加载完成且连续两次同类错误才收口;详情页另须
  路由身份匹配。普通请求错误扣留该条并在同步说明里报出原因,不扩大成整轮限流;带 Article 信号时
  仍允许既有补全后路。
  明确限流连续两次才抛出批次级错误,剩余账号或回填条目不再逐条打开,已完成账号结果保留,未完成
  账号不报水位。通用「出错了」「请稍后再试」不能证明 HTTP 429,不据此固化限流结论。
- **存量不能只靠同步去重修复,本地形状也不能证明未截断**。`scripts/x_post_backfill.py scan` 默认列出
  有可靠短推文来源的存量,不因无省略号、无 URL 或空正文而排除;省略号或链接折行只用于排序。
  `x_post_meta` 保存正文来源、精确转推前缀及标题/正文指纹,随首次入库与版本化替换保存;已合并 Article
  的行在筛选和数量限制之前排除,不会再打开短推文详情。元数据与内容不匹配时保守跳过,不能沿用旧前缀。
  列迁移只增不减,旧行默认空串代表未知,不追认来源;其他路径换正文却没更新元数据时,指纹检查仍会拦下。
  **没有来源的旧行一律不能凭标题形状放行**,即使标题等于正文首行也可能是整篇 Article。旧空正文及
  仅含上下文块的旧行也先记来源不明,不承诺默认已审计;标题不同同样不能证明已取得完整 Article。
  此类行记 `skipped_ambiguous`,附 URL/原因,默认不耗浏览器预算、不改内容、不宣称完成全文审计。
  `run --resolve-legacy` 同时接收来源缺失与损坏行,但不沿用损坏的类型或前缀,也不是强制放行:
  先问长文接口,完整远端文章精确匹配存量正文
  或其独立尾段时才标 Article;远端没有 Article 时,还必须由通过身份检查的详情逐字覆盖存量预览。
  上下文边界来自正文/详情对齐,不来自标题:整段正文可匹配时优先把作者的引用留在正文内;否则只有
  保留独立引用块后,余下正文可对齐才保留该块为前缀。接口关闭、请求失败、文章或详情不能对齐时
  保持未知,不写正文。`--yes` 才用版本化 CAS 保存核实来源,仅来源变化也递增 content_rev,
  不动内容指纹或导出回执;已确认 Article 下一轮直接排除,不会反复请求。默认仍是只读核实。
  明确合并过的长文记 `skipped_article`;两类跳过均输出 URL 和原因。`--all` 和 `--url` 不能绕过资格检查。
  收尾与 JSON 报告必须列出两类跳过、来源核实/保存及实际核对数;全部排除也不能提前报成功。
  checked 只数已取得详情并完成比较或已确认远端不可用的行,失败、扣留、来源核实后判成 Article
  不算短推文核对;total 是本批受 limit 限制的候选加排除,不冒充整库存量。scan 明示未访问详情。
  scan/run 只要存在资格排除即非零退出;run 并发换版同样非零,不得用失败数为零掩盖跳过。
  `run` 默认只读核对,`run --yes` 才逐条用详情页全文及 `grab_store.replace` 写回。
  `--url` 限定目标,`--all` 仅兼容旧命令,`--limit`/`--budget` 限制本批而不宣称全量已核对。
  并发换版记为跳过,失败/停止/预算用完不动原行;远端明确不可用记 `unavailable`,不删除已有存量。
  脚本只写 feeds.db,保留原导出回执,清旧译文并留提取作废待办;翻译、vault 重导出和索引由正常管道接手。
  报告区分 `identical`(逐字相同,不宣称完整)、`blocked_length`(长度拦截)、`blocked_artifacts`(有旧产物但
  无法安全对齐)和 `normalized`(旧产物可修复);写入结果另记 updated/stale,被拦下不再混称 unchanged。
- **来源记录必须贯穿生产快照与生产入口**。`known` 与回填候选交出的 seen 都必须带 content_hash、
  content_rev 和 x_post_meta;版本化替换拒绝缺少来源字段的快照,不以空串冒充「沿用原值」。
  browser/attach、feedgrab 和被用于显式重抓的 X 接口都在产出 post 条目时盖来源标记;
  新正文用新来源,仅作者等变化保留原绑定来源,后续 Article 合并统一改为 article。
  盖戳时必须显式给出 prefix,不能用默认空串代替边界;三条生产路径共用 context_prefix,
  只从来源已声明的引用上下文计算前缀。正文以引用块开头但 prefix 为空时,还须带 AuthorText
  独立来源证据(tweetText、tweet.text 或详情原文字段);不能用正文自身的一份字符串冒充证据。
  feedgrab 只有 Markdown,不具备这份独立原文证据:按 quote_lines 口径提取开头的完整独立引用块
  保留为上下文;边界不明或仅有上下文时留成来源待核实,不盖 authored_quote。其他通道的作者自写
  引用由独立原文字段证明,仍留在正文。旧的同类不安全来源不再放行,可用显式来源核实恢复。
  x_article_backfill 换写 title/body 时同一 UPDATE 写入最终文章的来源章,不能遗留空正文的旧章。
  stamp/context_prefix 的证据不足统一抛共享 PostUnavailable,不以未处理的 ValueError 中断批次。
  存量核实与正文提案都在逐行失败边界内:该行失败、保留原文,继续后续行并写报告;时间线来源
  无法证明时只跳过该条,其余推文照常收录,继续后续账号。incomplete 提示账号、跳过数量及示例
  URL,说明保留原水位并在下次同步重试;首轮也保存实际下界,不因跳过条目而滑动窗口。
  省略号词干匹配不替代独立作者证据。
- **连接检查与登录导入共用请求错误结论**。`verify_timeline` 通过 `x_page_state.read/problem` 判
  `failed` 与 `limited`,不耗满账号预算再误报登录失效;明确登录墙仍优先。HTTP 错误另带
  http_problem 证据来路,不受 DOM 加载门槛影响。正常页面的 DOM 不存在、限流、请求错误文字
  只读 primaryColumn,不读侧栏。主列整个缺失且没有侧栏、导航、页眉页脚或文章时,允许把整页的
  明确错误文字作为分类兜底,不作为成功读到正文的证据;含侧栏或普通文章的缺主列页面仍不能据此分类。
  无正向病因证据时,超时出口只说明未加载完/未读到推文、未能判出原因并指向检查连接,不推断
  登录失效、网络或代理故障;连接检查、登录导入和账号采集共用此约束。
  普通文案须加载完成,主内容无进度指示且明确显示限流,或显示 Retry/错误 alert 时可提前给出
  dom_problem。加载中“暂时还没有推文”本身不是失败证据。
  同一次导航只让同 operation 的后到响应覆盖先前状态;其他页面、loader、操作或会话的成功
  不能撤销当前错误。账号采集与首页检查均先认登录墙,
  再认已完成渲染的推文,最后处理请求错误。详情已取得路由/推文身份匹配、未折叠且连续两次
  相同的作者正文时按内容成功;没有可用正文时才确认 HTTP/DOM 错误,不能靠兄弟接口的 200 代替正文。
  检查连接、首次导入验证和重开验证均通过共享导航观察当前首页的核心 HomeTimeline/HomeLatestTimeline
  请求,429 与普通失败分开。普通失败只提示稍后检查连接,不要求重新登录;重开失败仍不宣布导入成功,
  文案明确失败发生在重开验证阶段。加载中的明确错误不再被误报网络不通,采集与详情页仍须连续
  两次相同结论,详情页仍须路由身份匹配;同一共享判据覆盖三个消费方。

- **同一批大V账号,三条互斥的取法,选哪条是一个设置**(`social` 的 `x_channel`,默认 `browser`):`feedgrab`
  一份 X cookie 调 X 自己的接口(子进程调用用户装好的 CLI)、`browser` 复用**独立 profile** 里的登录态
  (我们起的无头 Chrome,CDP over 管道)、`attach` 直连用户**已经开着**的日常浏览器(CDP over WebSocket)。
  **口径只有 `x_channels` 一份。**
- **`bridge`(第三方 RSS 桥接)那一档已经整条删掉**(公共实例常年不稳,而三条登录态通道都能无人值守跑)。
  **它必须以退役别名活着**(`_RETIRED = {'bridge': BROWSER}`)—— 存量 `feed_settings` 里写着 `bridge` 的,
  认不出来就当成"没配"退回默认,那是在用户没动过任何设置的情况下静默换档。连同它一起删掉的有:
  `fill_bridge`(桥接那条路上的长文补全钩子)、`sync` 里那道「同一组桥接连续失败就暂停本轮剩余」的熔断、
  `needs_article(links_only=)`、设置里的 `bridges` 模板列表和面板上那个输入框。
- **通道只管「没填专用订阅链接的那些 X 账号」**(判据 `registry.uses_channel`,原名 `uses_bridge`):填了
  `feed_url` 的和非 X 的 social 订阅照旧走 HTTP。
- **后两条不是 HTTP feed,不走 adapter 的 `endpoints()/parse()`**,而是在 `sync.collect` 开头**整批预取**一
  次(`x_channels.prefetch`),由 `fetch_source` 顶上那道分派按订阅各取自己那一份(`take`)——**同一个浏览器
  profile 同时只能被一个实例打开**。
- **HTTP 那一侧的采集预算要在预取之后才开始算。** 登录态通道另算一份串行预算(`X_LOCAL_SECONDS`,1200 秒)。
- **「停止」要在起浏览器之前就认**(两条 harvest 开头各一道,每个账号之间再问一次)。
- **水位按订阅存在 `subscriptions.config` 里,`attach` 和 `browser` 共用 `x_watermark_browser`,feedgrab 必
  须另记 `x_watermark_feedgrab`**(它的下界只到天)。判据是「精度和语义一不一样」,不是「是不是浏览器」。
- **没读到上次的位置,水位一步都不许动**(抓到的照旧入库)—— 推到「这一轮见过的最新」或「退到最老那条」都
  会让那一段从此任何一轮增量都选不到。**首轮存回这一轮真正用过的那个下界**(`x_browser.started`、
  `x_feedgrab.since`),**交空值回去等于什么都没存**。**读完的那一轮照旧 `_newest(...)`,不许一律存下界。**
- **「滚不出新东西」要连着 `_BOTTOM_TRIES`(3)次、而且每次都停在页面底部,才算真到底了。**
- **「翻到底」按页面出现顺序数,连续 `_OLD_STREAK`(3)条自己发的推都老于下界才算**(`_old_enough`):
  ①**不能按时间排序数**(转推显示的是原推时间);②**只有原创推的时间能当证据**(`_own_tweet`)。
  **任何一条新于下界的条目都把计数重置。**
- **「算不算这条时间线的内容」(入库)和「它的时间算不算证据」(翻到底)是两个判据**(`_in_timeline` /
  `_own_tweet`),别合成一个。入库排除推广位、以及作者不是这个号又没有转推那行 socialContext 的(推荐位);
  **转推一定带着那行上下文,所以不会被丢掉**,正文里保留它。
- **置顶要入库,只是不参与「翻到底」的证明**(旧置顶被 `put_items` 去重,而刚发就被钉上去的推文丢掉永久补
  不回来)。
- **「有推文卡片却一条都解析不出来」是 X 改版,不是「这个号今天没发推」**(`_harvest_one` 里
  `if seen_articles and not parsed: raise`)。登录失效 / 账号打不开 / 限流同理各一句话,不许折叠。
- **feedgrab 是子进程调用,环境变量白名单 + 显式清场,`OBSIDIAN_VAULT` 必须清掉** —— 它的输出目录**优先**认
  这个变量,而这台机器上它指的正是知识库那个 vault。每个账号一个干净的输出目录。
- **它的产物路径不许写死,只能整棵扫**(`_read_output` 走 `rglob('*.md')`;路径是「平台目录 + category」拼
  的,**猜不出来**)。递归不放松归属:判据是 `_entry` 按推文 URL 里的 handle 过滤。
- **它的退出码 0 不代表这一批抓全了,所以没抓全就不许推进水位**(`_incomplete` / `_batch_failures`)。两档各有独立
  证据源,谁命中都算漏、同时命中就两句话都说,只有 `fetched`/`skipped` 算没问题:①**翻页半途中断**只有一行
  `logger.error`(`_PAGE_ABORT`),判据要连「第 N 页」「M 个账号」一起认、**逐行看而不在整份输出上 `search`**,还要和
  **回显了用户内容的日志**分开(三道各有射程);②**逐条失败**两道判据:批量记录**认形状不认路径**、收尾摘要里的
  「失败: N」**必须带上「成功: N」那半截上下文**。放宽任何一道的后果见决策文档。
- **不要把 feedgrab 抄进 kb**(它要 X 内部 GraphQL + 登录态 manifest 里的签名算法,为此背着 60 多个 fetcher
  和 playwright)。模式同 `collector/`:kb 只知道一条命令行,升级是 `git pull` 的事。
- **登录提示里的可执行文件必须就是采集时会调的那一个**(`x_feedgrab.login_command` 过一遍 `find_binary`;
  `x_channels.login_command` 因此收**整份 settings**)。两头都 `shlex.quote`;配了路径但当下不可执行时照它
  **原样显示**。
- **拿到一个浏览器有两条路,各自是一条通道,不是一个实现细节**(`x_cdp.Chrome` 管道 / `cdp_attach.Attached`
  WebSocket)。**不引入 playwright。**
- **`attach` 那条的三条硬口径**:①**那个开关只能由用户自己去开**(`chrome://inspect` 勾一次),我们不代劳也
  不绕开,「没就绪」那档给的下一步就是这句话(`ENABLE_HINT`);②**端口是读出来的,不是我们指定的** —— 读
  user-data-dir 下的 `DevToolsActivePort` + TCP 探活,固定敲 9222 只作回落;出路是 `KB_CDP_ENDPOINT`,**显式
  指定了就不再去猜别的**(写错了也不回落,而且要说出是哪儿错了),`parse_endpoint` **一个异常都不许抛出来**
  (它坐在面板每次刷新那条路上;范围另用 `_ok_port` 卡住,`urlsplit` 本身也在 try 里);③**探活必须 TCP
  connect,不能拿 WebSocket 去试**(每次 WebSocket 连接都会弹授权窗,见下一条)。
- **那个授权弹窗按连接弹、而且刻意不可持久化;「开关」那一半反过来已经是持久的。** 两半分清,文案别混:
  - **开关**(`chrome://inspect` 那一勾)写在 `Local State` 的 `devtools.remote_debugging.user-enabled`,
    **跨 Chrome 重启、跨系统重启都在**,下次启动时端口自动开(2026-10-15 实测:Chrome 主进程 15:20:38 起、
    `DevToolsActivePort` 15:20:39 写出,差一秒,不可能是手点的)。所以**不许再说「浏览器一关就没了」**。
  - **每条连接的「允许」弹窗**不存在任何偏好键、策略或 flag。上游那个「让授权能记住」的请求
    (chrome-devtools-mcp#825)已 **closed as not planned**,理由是「没有一个简单方案能同时做到不让本机任何
    程序轻松拿到你 Chrome 里的数据」;`RemoteDebuggingAllowed` 只是个二元闸门,企业用途只有**禁掉**。
    2026-10-15 实测三条独立连接三次都弹。**所以这条通道结构上答不了无人值守**(定时那一轮没人点,90 秒后
    整批记失败)—— 出路是 `x_login_import`,见下面那条,别再去找「持久化授权」的办法。
  - **`/json/version` 在这个模式下返回 404**(Chrome 把 HTTP 目标列表整个关了)。主路不受影响(端口文件第二
    行给了 ws 路径),但 `_browser_ws_path()` 是 `FALLBACK_PORTS` 那条回落**唯一**的取路径手段 —— 于是扫端口
    那条路在这个模式下必然失败,它只对「用户自己带 `--remote-debugging-port` 启动」那一种还成立。
  - 顺带:那一勾开的端口**本机实测是固定 9222,不是随机的**(`cdp_attach` 注释里那句已订正)。读端口文件仍然是对的做法(手动指定端口
    那种模式也靠它),但别再用「因为随机」当唯一论证。
- **「把登录态搬进独立 profile」是上一条的唯一出路,不是一个便利功能**(`kb/feeds/x_login_import.py`,面板
  `browser` 那一块里那颗「从日常浏览器导入登录态」;结论码 → 人话那一层在 `x_login_words.py`,
  留痕和 `state()`/`summary()` 留在前者 —— 它们有模块状态,而测试是对那个模块打桩的)。它用一次 attach 会话读出 cookie、写进 `browser` 通道那个
  独立 profile,之后定时走 `browser`:零弹窗、跨重启持久。几条硬口径:
  - **只搬 `SCOPE` 里那个域(`x.com`)的 cookie,一个别的站点都不碰。** 远程调试一开,这个浏览器里**所有**站点的
    登录态都在一条命令的射程内(银行、邮箱、公司后台都在里面)—— 射程写死在一处、而且窄到只有这件事要用的那
    个域,是这个功能敢于存在的前提。**判据是「等于那个域、或者是它的子域」,不是 `endswith`** —— 后者会把
    `notx.com`、`evilx.com` 一起圈进来。扩域必须由用户点名。
  - **读用户那个浏览器时,范围由浏览器来卡,不由我们过滤。** 这条跟上一条是两回事,而且是上一条的**实现要
    求**:`Storage.getCookies` 没有任何按站点筛选的参数(唯一的可选参数是 `browserContextId`,那是按 profile
    分),它一开口就把整杯 cookie 解密好、交到我们进程里;之后 `in_scope` 再怎么过滤,能证明的也只是「我们没有
    **保存**授权外的数据」,证不了「没有**读取**」—— 而页面上对用户说的是「只读 x.com」。所以**那一侧**的读取
    一律走页面级的 `Network.getCookies` + 显式 `urls`(`read_scoped`),`in_scope` 退居第二道。**用「最终返回/
    保存的数据过滤过」去证明「没读取权限外的数据」是个不可靠判据**,这一类判断都要下沉到最靠近浏览器的那一层。
    2026-10-15 实测(自己的无头 Chrome,合成数据):种入 `x.com` + `bank.example` + `mail.example.org`,
    `Storage.getCookies` 回五个域,`Network.getCookies` 带 `urls` 只回 `x.com` 那两个。
  - **我们自己那个 profile 必须反过来:整杯读(`read_all`)。** `urls` 卡得住域,卡掉的却还有**路径** ——
    `Network.getCookies` 交的是「对这几个地址适用的」,`ct0@/i/api` 那一族整条不出现,而且是**两次读同时漏掉**,
    于是「集合相等」什么都证明不了。审查实测(真 Chrome + 离线替身站点):验证页真正选中的就是 `ct0@/i/api`,
    第二次加载把它换发成**会话 cookie**,浏览器正常关闭之后它随进程消失,三次读一次都看不见它 —— 差异为空,
    产品报 `ok` 并承诺「以后不用点弹窗」,而下一次打开同一个 profile,生产分类器判 `login`。
    **出路不是再补一个 URL**(路径不可枚举,补一条只是把同一个盲区挪个位置),而是这一侧改成整杯读:
    **盲区是路径,不是名字** —— 整杯读之后「所有路径上的 `auth_token`/`ct0`」都进了判据。
    这一侧敢整杯读的理由很窄:那个 profile 是我们建的、除了 x.com 哪儿都没去过,所以「整杯」和「x.com 那几条」
    本来是一回事(`in_scope` 再钉一道)。**两侧的射程写在两个函数里,不许互相借用**,守法靠三道:`read_all`
    自带运行时闸(开在别人浏览器里的后台标签页、或者不是我们起的 profile,一条命令都不发出去)、结构性那条
    回归(整个 `kb/` 下 `Storage.getCookies` 这个调用形式只许出现在 `read_all` 里)、以及它的另一头(`read_all`
    的调用点只有目标侧那三处)。**源侧的射程一点都不许放宽。**
  - **为了那个范围参数要开一张页,那张页必须 `hidden` + `background`。** `Network.getCookies` 是页面域的命令,所
    以这一步比原来多开一张标签页 —— 「一张标签页都不开」那条是**我们自己**定的卫生规矩,而数据范围是**用户**
    定的约束,冲突时后者赢,不许拿自定约束去换掉它。代价用两个标志压到最小:`background` 管「不抢前台」,
    `hidden` 管「不进标签栏」(它的生命周期还跟着这条连接,断开即消失,连漏关一张空白页都不会有);导航目标是
    `about:blank`,一个网络请求都不发。协议规定 `hidden` 只能和 `background: true` 同时给。
    **老浏览器不认 `hidden` 时只许退到「后台标签页」这一档,绝不退到前台** —— 抢掉用户正在看的窗口比标签栏多
    一行严重得多,宁可整件事失败。余下的规矩一条不松:不列、不碰、不接管他已有的任何标签,绝不 `Browser.close`。
  - **缺了 `ESSENTIAL`(`auth_token` / `ct0`)就一个字都不往 profile 里写。** 写进去的后果是那个 profile 里躺着
    一份残缺的登录态,而它**盖掉了原来那份可能好着的**,`readiness` 看到 Cookies 文件照旧报「登录过」,真相要
    等到真抓的时候(口径同元规则「拿不准就别固化终态」)。
  - **交给 `Storage.setCookies` 的字段走白名单,不许原样回灌。** `getCookies` 多给的那几个(`size`、`session`、
    `sourcePort`……)不是 `CookieParam` 的合法字段,原样交回去会让这条命令整条失败,而表现只是一句「导入失败」。
    会话 cookie 的 `expires` 是 -1,**要省掉这个字段**,交回去等于说「1969 年就过期了」。
    **但 `partitionKey` 反过来必须带上**:它在 `Cookie` 和 `CookieParam` 里是**同一个**类型
    (`CookiePartitionKey`,协议原文核对过),所以省掉它不是「少给一个无用的响应字段」,而是**把一条分区 cookie
    改写成非分区的**,同名、分属不同分区的两条还会被压到同一个键上(可能连普通那条一起盖掉)。
  - **搬完立刻在目标 profile 里验证一次,而且 `ok` 之外一律不许说成「可以用了」。** cookie 换一个浏览器实例之后
    X 认不认,是这条路唯一真正的未知 —— 认不认当场就该知道,而不是等到第二天早上那一轮报「登录态已失效」。
    没验成的那几档照旧留痕:cookie 已经落进 profile 了,不留痕的话那份不可用的登录态就成了一句看不出来的假话。
  - **「当场能用」证不了「下次还在」,而对外承诺的是后者 —— 所以收尾之后要重开同一个 profile 再读一次。**
    当场那次验证读的是**浏览器进程内存里**的状态;这个功能承诺的却是「以后定时同步不用再点弹窗」,那要求
    cookie **落到磁盘上**。两件事中间隔着 `Chrome.__exit__`:它先发 `Browser.close`(让浏览器存盘)再 kill,而
    **怎么失败都不往外抛**(它必须把 fd 和进程收干净)—— 于是「被 kill、cookie 一个都没落盘」这件事从调用方
    看跟成功**一模一样**,而面板会照旧说「不再需要点授权弹窗」。`Chrome.closed_cleanly` 把那次关闭的结果交出
    来(**只是事实报告,不是异常**),但**判据不押在它身上**:判据是重开之后**这一轮写进去的那一代**还在不在,
    拿不到就按「没留下」算(拦不住的代价是用户第二天早上才发现,误拦的代价只是再点一次)。
    2026-10-15 实测:① 持久 cookie → 重开还在 → `ok`;② 把 `ct0` 换成会话 cookie → **当场验证照旧通过、重开
    就没了** → `unsaved`,并说清「多半是会话 cookie」。审查那一轮另外在只注入 `Browser.close` 失败的真浏览器上
    复现过同一形态(`after_reopen = []` 而旧代码记 `ok`)。
    **不许替会话 cookie 编一个未来的 `expires`**:那是把用户的会话凭证悄悄变成永久凭证,还把「下次还在不在」
    的答案伪造成「在」。
  - **判据是比指纹,不是比名字 —— 「磁盘上存在同名的东西」证不了「这一轮验证过的内容已经保存」。** 这是上面
    那条的要害,也是它第一次只修了一半的地方:把重开结果压成名字集合之后,**重导入最常见的那一档**就漏了 ——
    cookie 过期后用户再点一次,目标 profile 里早就躺着同名的旧凭证,于是一次**什么都没存进去**的导入照旧判
    `ok`,面板还写上「重新打开确认过它们留在了磁盘上」(2026-10-15 审查拿真浏览器实测:目标先放
    `synthetic-old-*`,写入 `synthetic-new-*`、当场验证读到的确实是新值,只在 `Browser.close` 注入失败走 kill
    分支,重开后盘上仍是 `synthetic-old-*`,而返回 `ok`)。正解是 `fingerprint()`:**身份
    (name/domain/path/partitionKey)+ 值**,sha256 截断,**只活在内存里、绝不落盘**(账本照旧只记名字和条数)。
    两次读都是**整杯**(`read_all`),所以这个比较是对称的、而且没有路径盲区 —— `ct0@/home`、`ct0@/i/api`
    这类路径受限的条目一样进得来。按 URL 读的那一版漏的正是它们,而且是**两侧同时漏**(实测 `ct0@/home`:
    只给根 URL 时它压根不出现;那条路后来还是在 `/i/api` 上被反例推翻,见上面「整杯读」那条)。
    **三档原因不许折叠**:关闭没能存盘 / 盘上还是上一次那一代 / 本来就是会话 cookie,下一步各不一样(中间那档
    还要让用户知道他此刻用的仍是过期那份)。
    **夹具也要能表达这件事** —— 上一轮 `FakeChrome.persisted` 收的是名字列表,压根表达不了「名字一样、值是旧
    的」,所以它全绿**核销不了**这条;现在它收整条 cookie。
  - **被比的那一方是「验证结束那一刻浏览器里的状态」,不是我们交进去的那份输入;而且要比完整的那一组。**
    前两轮都拿入参当基准 —— 那是条假判据,三种形态都在 2026-10-15 的真浏览器上复现过(合成 cookie、临时
    profile、`/tmp/gap_probe.py` 那一支):
    ① **Chrome 写入时把有效期削到 400 天**(交 5 年进去,盘上存的是 `400.0` 天整)。X 的 `auth_token` 正是多年
    有效期,所以拿入参比的话**每一次**导入都判「没存上」—— 一个把整个功能判死的假阴性。
    ② **站点在验证期间合法换发凭证**:导航到 `x.com/home` 那一下 X 自己就会下新 cookie(实测见 `guest_id`、
    `__cf_bm`,`ct0` 同理)。于是一次**完整存好了**的导入被报成「ct0 还是旧值」,用户照着那句话反复重导。
    ③ **同名多条只留住一条也算过**:`auth_token@x.com` 和 `auth_token@.x.com` 是两条不同的 cookie,旧判据
    `mine & prints`(任意一条对上就行)在盘上丢了 `.x.com` 那条时照旧报成功 —— 这一个是假阳性。
    一次实测跑下来,旧判据报 `stale: [auth_token, ct0]`,新判据报空。正解:`install` 在**关掉浏览器之前**
    再读一次(`verified = read_scoped(page)`),拿它跟重开结果比,**每条指纹都要在**(`mine - on_disk`)。
  - **指纹里必须带「还能用多久」(`expires` + `session`)。** 「cookie 过期了再导一次」正是这个功能存在的理由
    之一,而那一档是**同名、很可能同值、只有有效期是新的**:少了这两个字段,一次「续期压根没落盘」跟成功长得
    一模一样 —— 盘上那条过几十秒自己就没了,面板却说「以后不用再点弹窗了」。
    实测这几个字段经「写进去 → 正常关 → 重开读出来」**逐位原样往返**(持久 cookie 的 `expires` 两边完全相同;
    会话 cookie live 报 `expires=-1, session=true`、盘上直接消失,正是该报的那一档),所以带上它们不会引入
    新的假阴性。**反过来钉一边:关键凭证之外的 cookie 增减不影响结论**(浏览器和站点一直在动它们)。
  - **投影里还要带「还读得到、还发得出去吗」(`httpOnly` / `secure` / `sameSite`)。**
    这三个不是元数据:`httpOnly` 决定页面脚本还能不能读 `ct0`(X 前端靠
    `document.cookie` 取它拼 `x-csrf-token`),`sameSite` 决定跨站请求带不带它,
    `secure` 决定它只跟 HTTPS 走 —— 它们决定这条 cookie 下一次**到不到得了该到的
    地方**。而 `_PARAMS` 写入时本来就一个不少地带着,凭什么核验时丢掉。
    事故形态(2026-10-15 审查,真浏览器 + 同 origin 的真实 `document.cookie`):
    旧目标里 `ct0` 是 `httpOnly=true`,导入的那份把它改回脚本可读;验证时
    `document.cookie` 读得到 `ct0`,重开后是空串 —— 而名/值/有效期/session 全同,
    判 `ok` 并声称「重新打开确认过」。本轮自己复跑同一形态:新判据报 `stale: [ct0]`,
    把 `_PRINT_FIELDS` 换回上一轮那六个字段则报 `{}`。
    **这三个实测也逐位原样往返**(连「没指定」都原样缺席),所以带上它们不造假阴性;
    **但不许顺手把元数据也混进来**(`size`、`priority` 跟「下一次还能不能用」无关,
    比它们只是多一种被 Chrome 规范化掉、于是永远判「没存上」的方式)。
    **指纹里「没这个字段」要用一个占位符,不能让 `str()` 统一** —— `sameSite` 的合法
    取值里正好有一个叫 `None`,而「没指定」要么键缺席、要么键在值为 `null`,后者
    `str()` 出来就是 `'None'`,于是「跨站不带它」和「带它」指纹相同。实测 CDP 今天是
    整键缺席,所以那一道是备手。
  - **这一维是怎么一轮一轮补齐的,本身就是条口径:判据从比名字 → 比值 → 比有效期 →
    比读写属性,每一步都是同一个「局部相同即证明完整保存」的类问题只修了一半。**
    所以**往投影里加一维之前先问它影不影响「下一次还用得上」** —— 影响就必须在里面,
    不影响就别混进来。回归 `tests/test_x_login_state.py`(那一族从 `test_x_login_persist.py`
    拆出来,只因为 700 行上限)。
  - **反过来也要卡住:盘上不许多出验证时没有的那一组(`extra`)。** 子集不等于同一份
    状态 —— 上一次导入留下的同名条目(domain/path 任一不同就是另一条 cookie,
    `Storage.setCookies` 按 name+domain+path 覆盖、压根不会动它)会跟着请求一起发
    出去,而到底哪条被站点选中我们答不了;答不了就不该宣布「保存下来的是验证过的
    那一份」(口径同元规则「判不准一律扣留」)。真浏览器实测:盘上多一条
    `ct0@x.com` 报 `extra: [ct0]`,两边都有那条则照旧放行。
  - **已经查明的验证失败是主结论,保存差异接在后面,不许顶掉它。** 原来只要重开对不上
    就无条件改成 `unsaved`,而那句文案无条件写「当场也能用」。站点拒绝登录时它多半
    顺手清掉了凭证,于是盘上确实也对不上 —— 一次**登录被拒**就被报成一次**存盘故障**:
    真原因没了,还多了一句假话,而两者的下一步完全不同(前者该去点「打开登录窗口」,
    后者是再导一次)。五档验证结果一视同仁(`login`/`limited`/`not-loaded`/`no-tweets`
    都只在 `verdict == 'ok'` 时才让位给 `unsaved`);**「当场也能用」只许出现在 `unsaved`
    那一档**,因为只有那一档是从 `ok` 来的(`relogin`/`unconfirmed` 同理)。保存差异那半句
    **口径只有一份**(`_gap_why`),两条路都过它。
  - **「盘上那几条对得上」证不了「这份登录态还成立」—— 重开之后还要把真的那套登录验证再跑一次。**
    指纹相等只说明「那几条还在、还是那一代」,它答不了「X 那头还认不认」:账号被下线、风控、分区 cookie 这类
    快照里**压根没有身份**的东西,都能让一份逐位相同的凭证当场不好用。
    事故形态(审查在隔离的真浏览器里实测,`path-state-reproduce.json`):`/home` 下那条 `ct0` 重开后退回旧值,
    生产那个分类器对着首页判 `login`(未登录),而产品报 `ok` 并承诺「以后不用点弹窗」—— 快照那一侧一个差异
    都没有,因为**按 URL 读的那一版**两次都没看见那一条。**那条具体路径后来由整杯读堵住了**(见上面
    「整杯读」那条),所以这一道现在的射程不是「读不到的那部分」,而是「读到了也不代表站点还认」。
    正解:`_reopened` 重开之后**先读盘、再导航到 `VERIFY_URL` 跑一次 `verify_timeline`**(就是采集侧明早
    第一件事),`ok` 要求**两道都过**。读在导航之前这个顺序是判据的一部分:反过来的话那次加载里站点自己轮换
    出的新凭证会被当成「盘上本来就有的」,把「写进去那一份存上没有」顺手答成「存上了」。
    **两道闸谁都替代不了谁**:快照那道管「现在一样、将来还一样吗」(有效期、读写属性、同名多条 —— 重开那一刻
    真验一次看不出来,28 秒后才过期的 cookie 此刻照样能用),真验那道管「对得上也可能不好用」。所以
    **快照有差异时仍然报 `unsaved`,哪怕重验通过**。
    两档新结论码:`relogin`(X **明确说**未登录 = 当场能用那一份没完整留下)/ `unconfirmed`(重验**没跑成**:
    限流、首页没加载完、一条推文都没读到 = **判不准,一律扣留**,既不许宣布成功、也不许说成「没存上」——
    说成成功的代价是明早那一轮静默缺一段,说成「没存上」的代价是用户照着那句话一遍遍重导,而问题不在那儿)。
    修完之后在真 Chrome(独立无头、临时 profile)上逐步量过:只给根 URL 读到 `[auth_token@/, ct0@/]`、
    **`ct0@/home` 压根不出现**;把 `VERIFY_URL` 加进读取范围后三条都在、不重复;重开之后(**导航之前**)照旧
    读回同样三条,`_persistence_gap` 为空(不造假阴性);只把 `/home` 那条换成旧值则报 `stale: ['ct0']` ——
    那一条从此真的进了判据。端到端那一遍也跑了真 Chrome:第一次验证打桩成 `ok`(没有真登录态,「当场验证
    通过」造不出来)、第二次走真的 `verify_timeline`,而 x.com 对无头 Chrome 直接回 **HTTP 403**,于是重验落在
    「没跑成」那一档 → 产品报 `unconfirmed`、文案说「点检查连接再确认一次」,**没有**宣布成功。
    回归 `tests/test_x_login_persist.py`。**反向验证按两道闸分别注入**:目标侧退回按 URL 投影、重开之后不再
    真验、重开那次先导航再读盘、重验没跑成也说成「没存上」、重验通过就顶掉快照那道闸、当场没验过也让重开
    那次改写结论 —— 六处各自都有红,其中「重验通过就顶掉快照那道闸」会把前面那一整族用例一起带红,
    所以这两道确实是互相独立的两组判据。
    路径盲区那一族的回归在 `tests/test_x_login_state.py`(投影那一组的第五档:漏掉的不是某一维,是整整一条
    cookie);夹具那边 `FakeChrome` 照真浏览器的语义**整杯答**,而 `Network.getCookies` 一侧**故意不答** ——
    目标 profile 上再出现按 URL 读的写法,当场红在「一条都没留下」上,不会再静默。
  - **被证明的那一份,必须就是最后留下的那一份 —— 判据只能落在最后一个写者之后。**
    重开那次验证本身就是个写者:站点在那一下可以合法地下发、删除、轮换 cookie,而
    **明早采集要用的正是换来的那一份**。拿导航之前那份盘上快照去宣布成功,证的是最后
    一个写者**之前**的状态,它过得去不代表函数跑完之后盘上还有一份能用的。
    事故形态(审查用隔离 Chrome 确定性复现,`final-validation-reproduce.json`):第二次
    首页响应下发 `Set-Cookie: ct0=…; Domain=.x.com; Path=/; Secure; SameSite=Lax`
    ——**没有有效期,就是一条会话 cookie**;第二次验证照样读到推文、浏览器也**正常关闭**
    (`closed_cleanly` 两次都是 true),那条 `ct0` 随进程一起没了。两道旧闸全过(导航前
    的盘上快照跟首次快照一个字不差),产品报 `ok`、落账 `ok`、承诺「以后不用点弹窗」,
    而下一次打开同一个 profile,同一个生产分类器判 `login`。
    正解:`_reopened` 验完**再读一次浏览器**(`live`),收尾之后再开一次 `_settled`
    **只读盘、一步都不导航**,两者相等才算成功。
    **最后那次不许导航是判据的一部分**:再导航就又多一个写者,同一个缺口只是被推到
    下一次关闭之后,永远证不完(审查原话:「不能仅再添一次仍然允许站点改写状态的重开」)。
    **反过来钉一边,这一头更要紧**:站点在最后那次加载里换发凭证是**常态**,只要换来的
    那一份真落了盘就是一次完整的成功 —— 这一道要是写成「最后那次验证之后不许有变化」,
    每一次正常导入都会被判死。
    结论码沿用 `unsaved`,但**文案分得出是哪一刻的那一份没留下**:这一档说的是「最后那次
    验证用的那一份关掉之后没留在盘上」,说成「没有这一轮写的那一份」会把人指错方向
    (他写进去的那份其实好好地留着)。
    回归 `tests/test_x_login_persist.py` 的 `TheLastWriterHasToBeProvenTests`;夹具按
    「四次读各问各的」摆(验完一次 / 重开读盘 / 重开验完 / 最后只读盘),**四份答案不许
    混成一个**,否则这道闸没有射程。
  - **缺法分五档,不许折叠**:`vanished`(验证刚结束时浏览器里就没有它了 —— 重导一次没用,得去看那个账号)/
    关闭没能存盘(再导一次多半就好)/ `stale`(盘上有同名的,但不是验证通过那一份)/ `absent`(盘上压根没这个
    名字 —— 多半是会话 cookie,再导一百次也一样)/ `extra`(盘上多出验证时没有的同名条目)。
    **话只说得出来的那一句**:`stale` 现在涵盖「值不同 / 有效期不同 / 读写属性变了 / 同名少了一条」四种,
    所以不许再声称「还是上一次那份旧值」,也不许声称是其中具体哪一种。
  - **收尾那两步(`flock(LOCK_UN)`、`os.close`)自己抛错不许盖掉业务结果。** 它们跑在 `finally` 里,而
    `finally` 里冒出来的异常会**替换掉**那条 `return`:一次已经成功的导入于是在接口上变成一个没有原因的 500,
    用户看到「导入没跑完」而登录态其实已经搬好了 —— 他会再点一次、再弹一个授权窗。两步照旧都试一次、失败咽掉
    (锁和 fd 的归宿不依赖这两句:进程退出时内核一并收走)。**反过来钉一边:咽掉异常不等于不解锁** —— 判据落在
    「换个 fd 还抢得到同一把锁」,不在「调过那一句」。
  - **账本永远不比 profile 旧:改之前先登记,每条退出路径都更新。** 原来是「正常走完时记一条」,于是写完 cookie
    之后导航或验证一抛异常就直接返回、跳过留痕 —— 而 profile **已经被改了**,面板上继续挂着上一轮那条「当场
    验证通过」,说的是一份**已经不存在**的登录态(审查实测:新 cookie 已落盘,账本还是昨天那条 99 个)。所以
    动 profile 之前先写一条 `writing`,之后无论验证异常、落账失败还是别的退出路径都把它更新成真实结论。
    **登记写不进去就什么都不改**(那是磁盘坏掉时唯一还能让这条不变量成立的做法:什么都没动,原来那条记录照旧
    准确);**登记成了、落账失败**则留在 `writing` 那一档,面板如实说「这一轮没走完、状态不确定」。
    `Storage.setCookies` 抛异常**不等于**一个 cookie 都没写进去,所以那一档不许说「原样没动」。
  - **「写 → 验 → 重开核验 → 落账」整段要串起来,`profile_busy` 不够。** 它答的是「**现在**忙不忙」,是**早一道**
    不是互斥(口径同元规则);profile 的 OS 独占锁在 `install` 返回那一刻就松了,而账还没落 —— 两轮叠起来时晚
    开工的那次可能先落账,面板上那行字从此说的是另一轮的事。用 `_installing`(`flock`,拿不到就当场说「另一次
    正在进行」,**不等**:这是用户点出来的操作)。**反过来钉一边:锁不许留着** —— 一次失败的导入把那颗按钮永久
    变成「另一次正在进行」比没有锁更糟,用户没有任何办法解开它。
  - **「锁被别人占着」和「锁根本建不起来」要分开说。** 只有 `BlockingIOError`(`EWOULDBLOCK`/`EAGAIN`)才是
    并发;数据目录只读、配额满、这个文件系统不支持 flock 都不是 —— 一律翻成「另一次导入正在进行中」的后果是
    用户去关一个**压根不存在**的窗口,然后反复点那颗按钮,而每一次都白弹一个授权窗。锁文件建不起来那一档原来
    直接把 `OSError` 抛给接口,最终只落成一个 500,连原因都看不到。
  - **导入成功之后,就绪那一行要跟着重算**(接口把 `x_channels.readiness` 的新结果一起回去,**口径跟 GET 完全
    一份**)。不然页面上同时挂着「当场验证通过」和「浏览器通道还没有登录过 X」两句互相打脸的话,而后者说的是
    导入**之前**那一刻 —— 用户得自己再点一次「检查连接」才看得到真相。
  - **留痕只记名字和条数,绝不记值。** cookie 值就是登录凭证本身,落进一份明文 JSON 等于把这个功能防的事自己
    做一遍。保证是**结构性**的:`record()` 压根不接收值,所以唯一能注进泄密的地方是调用处(回归钉在那儿)。
  - **留痕只回答「什么时候搬的」,不回答「还能不能用」**(`summary()` 和 `readiness` 是两件事,cookie 过期在文件
    上看不出来)。它读不出来时答「不知道」,**不许降级成「从没导过」**。
  - **两道前置检查的顺序要紧**:先问「读得到吗」(调试端口)再问「写得进吗」(`profile_busy`)—— 反了的话用户

- **三颗动作按钮(登录窗口 / 导入登录态 / 检查连接)任何时候都可点,草稿没存下来时「先保存再执行」**
  (`xChanEnsureSaved`:先走一遍 `saveSourceSettingsNow()`,存成了再做,并用一条 toast 说明"已先保存哪一档"
  ;存不成或存完已经不是那一档就不做)。**不许再改回"灰掉按钮 + title 里写「先点保存设置」"** —— 那是让用户
  替我们走一趟本来就该我们走的流程,而他看到的是一颗按不动的按钮、唯一的解释藏在 hover 才出得来的 title 里。
  后端那道拒绝(`intake_api.x_channel_login` 读**存下来**的那一份)照旧留着:两道各有射程,别只留一道。
- **「这一次动作跑的是不是你眼前这一份」只能在服务端回答**(`intake_api._x_act`:
  三个动作请求都带上调用方眼前那一份,端点取一份快照核对,对不上或者压根没带就 409、
  一个字都不跑)。浏览器那边的「已经保存了」是**本页自己的缓存**,它证不了此刻库里
  存着的还是它 —— 另一个标签页(或任何别的客户端)改一下设置并保存,这一页既不知道、
  也不会重新 PUT,于是按钮打出去的动作跑的是**别人那一份**,结论却贴在这一页的输入框
  旁边(审查实测:第二页把位置改成一个不存在的文件并保存,第一页不刷新直接点「检查
  连接」,检的正是第二页那条)。判据因此跟着**要执行的那次读**待在一起(口径同元规则
  「判据待在写语句自己的 WHERE 里」)。**身份口径只有 `x_channels.config_of` 一份**:
  取法(过 `resolve`,退役名和现用名是同一份)+ 两条可执行文件位置(两边都 trim);
  **只收「动作真正会用到」的那几项** —— 把 `enabled`、同步间隔也算进去的话,用户在
  别处改个无关开关就会让这边的按钮开始拒绝。**反过来钉一边:对得上的照常放行**,
  「这一档不在这里登录」那几句 400 的拒绝也不许被这道闸盖掉。
- **「拿来比的」「拿来跑的」和「同步真正跑的」必须是同一份值**,而归一**只做一次,在
  `reg.get_settings` 那一层**(它本来就在那儿把退役名翻成现用名,各处读设置的地方都从这里
  拿)。一度只放在面板那个 HTTP 入口(`_x_kind`):面板 GET 和三个动作于是一致了,采集
  (`sync.collect` → `x_channels.prefetch`)读的却还是同一份设置的**原值** —— 存着末尾带一个
  空格的路径时,面板比的、面板检查跑的都是 trim 过那一份,**每天那一轮同步跑的却是另一个可
  执行文件**,而面板上一切正常。同一个形状更早的一次:身份把两条路径 trim 了、而执行那一侧
  读原值 —— 这道闸判"对得上"并放行,真跑起来的是**另一个文件**(审查实测:两份同名、只差
  末尾一个空格的可执行文件)。**选 trim 不选逐字比**
  是因为面板发出去之前本来就 trim 过 —— 不规范化的话那种存量设置会永远被拒,而用户对着一份
  看起来一模一样的设置看不出差在哪一步。**两条路径的长度上限两边必须一致**(保存不限长、动作
  限 1024 的后果是一份存得下、却动不了的配置:PUT 回 200、动作回 422,而设置页面一切正常)。
- **GET `/x-channel` 要给完整那一份**(`config`),动作回包也要带着**它这一次跑的那
  一份**。少了前者,前端只能拿上一次权威加载落下的路径去拼一份出来,而那是猜;少了
  后者,结果落地时只能按「还是同一档取法吗」判。
- **「那份共享资料变没变」一律跟「结论归不归眼前这一份配置」分开判**(`xChanTouched`
  的两个参数):请求**发出去过**就算可能动过它,一律推一格;只有「回包带着变完之后的事实、
  而且真落在了这块面板上」那一种算当场覆盖掉,而且**只盖得住它自己推的那一格** —— 这个
  动作之前就欠着的那一次它答不了(一次成功的「检查连接」只更新 `ready/why`,答不了留痕
  那行「上次到底搬成了没有」)。**三颗按钮同一条规矩,「打开登录窗口」也在内**:它一个字
  都不往面板上写,但窗口一开 Chrome 就把 profile 建出来了,`readiness` 那道便宜判断只看
  `Default/Cookies` 在不在 —— 后端的答复当场就变了,而页面上还是开之前那一份。
- **动作结果能不能更新当前状态,判据是「它跑的是哪一份配置」,不是「还是同一档取法」**
  (`xChanOwnsAct`)。同一档里换一条可执行文件位置并保存,旧那次检查的结论就不再是这
  一份的结论了 —— 审查实测:慢检查在途时把位置改成一个不存在的文件并保存,页面已经
  读到「路径不可执行」,随后旧检查成功回来,状态行被写成「已就绪」+ 绿点,而输入框和
  那条可复制命令里都是那条不存在的路径。**两头都要**:后端存着的还是它、页面上此刻
  显示的也还是它。**回执(toast)照旧不进这道判断**,它说的是用户刚点的那颗按钮。
- **「这一份存下来了没有」的判据是整份草稿,不是通道名**(`xChanKey` 把
  `[x_channel, x_feedgrab_bin.trim(), x_chrome_path.trim()]` 压成一个键,`xChanSaved` 记后端此刻存着的那一份)。
  三个动作端点读的都是**存下来**的那一行 settings,`x_chrome_path`/`x_feedgrab_bin` 也在里头 —— 只按通道名判
  相等,改完可执行文件位置直接点「检查连接」就会拿**旧路径**跑一遍,还报得像是在验新填的那个。
  路径输入框因此要 `oninput="xChannelPicked()"`:状态卡得跟着整份草稿动,不然它写着"已保存"而手里这份不是。
- **保存那条路的回包也要带归属判断,跟 GET/POST 两条一样**:`saveSourceSettingsNow` 把发出去那一份的键一起交给
  `fillXChannelFields(settings, sent)` —— **「后端现在存着什么」无条件记下**(拒绝下一次动作要靠它),
  **「把草稿控件改写成这一份」只在草稿没动过时做**(`xChanDraft() === sent`)。慢一点的 PUT 回来时用户多半已经
  又改了几笔,照单回填等于把他手里的东西抹掉。同理 `xChanEnsureSaved` 存完要**两头都认**:后端存的是发出去那
  一份、**而且页面上现在仍是这一份**(`xChanSaved === want && xChannelSaved()`),差一边就不往下做,并说清为什么。
- **存完那次权威重读要等它落地再取动作标记**(`fillSourceSettings` 把 `loadXChannel()` 那个 promise 交回去,
  `saveSourceSettingsNow` 等它)—— 不等的话动作先发出去,随后落地的重读把 `xChanAge()` 的代次推掉,这次动作的
  回包就被自己的面板判成"不是我的"丢掉,用户看到的是点了没反应。
- **「这条结论归不归眼前这一份」和「后端那边变没变」是两个问题,不许绑在同一个条件上**
  (`xChanStale`:结论没能落在面板上时一律重取一次权威状态)。导入写的是那个**共享的**
  profile(`BROWSER_PROFILE` 只有一个,换 Chrome 可执行文件位置并不换它),检查会真起一个
  Chrome 打开它 —— 所以「这条结论不属于眼前这一份」**推不出**「后端那边没变」。审查实测:
  导入在途时改一下 Chrome 位置并保存,保存收尾那次 GET 读到的是「这一轮没走完」,随后导入
  成功的回包因为配置变了被整条丢掉,于是面板一直说「还没有登录过 X」「这一轮没走完」,切走
  再切回来才恢复。**失败和断连也算**(没拿到回包证不了后端没写);**被那道闸拒绝的那一次
  确实没写,但它本身说明我们手里那份「后端存着什么」是错的**,同样要重读。
  **反过来钉一边:保护不许因此放宽** —— 这条结论该不该显示仍然按它跑的那一份配置判。
  **而「失效」是一份要留着的状态,不是"已经发过一条 GET"这个动作**,而且**要记成版本
  不能记成布尔**(`xChanSeq` 共享资料已知变过几版 / `xChanFresh` 面板上这一份覆盖到
  第几版,差着就是还欠一次刷新)。一条读发出去之后,后面任何一个动作、一次改选择都能
  合法把它作废;更要命的是**在动作完成之前就发出去的那条读**:它手里是变完之前的快照,
  却照旧通得过那三道归属检查(结论没落地时 `xChanLands` 压根不推进),于是把布尔清成
  「不欠了」—— 审查实测,导入在途时改位置并保存,保存收尾那条读在导入提交前取到「没走
  完」、被按住一秒才落地,面板从此一直写着「还没有登录过 X」「这一轮没走完」,而权威接口
  早就是完成记录,干等也不会变。所以**每条读在发起那一刻记下它覆盖到哪一版**,落地时对
  不上就整条丢掉、接着补。
  **欠着就补,而且每一条出口都要推一次**:读被丢弃的那一下、读失败且已被作废的那一下、
  三颗按钮各自收尾的那一下、连「动作前保存没过去」那两条提前返回也算。少哪一条都有一种
  顺序补不回来 —— 审查实测的第二处正是「被作废的那条补读回来是 503」:它一个字都没写进
  面板(用户看不见这次失败),而那条出口上原来什么都没有,留痕从此停在「这一轮没走完」,
  显式再点一次检查才补回来。**计数要在落地那一刻就还掉,不能放在 `finally` 里** ——
  `finally` 比 `return` 晚跑,那一格还按着时 `xChanRefresh()` 一律让开,推了等于没推。
  (反过来那一档要分清:**当前这条读失败、而且那句原因已经摆在面板上**的,不自动重试 ——
  再打一轮只会把它刷掉,欠着的那次由下一个动作或下一次进来补。)
  补读之间靠**在飞计数**排队,不是布尔 —— 布尔会让先落地那条把标记清掉、当场又补一条,
  而后发那条还没回来,一路滚下去。
- **被那道闸拒绝(409)跟「跑了但没拿到答复」是两件事,不许记成同一件**
  (`xChanRefused`):拒绝是后端明确说了它什么都没做,出路是重读一次把真相摆出来;
  「结果不知道」那一档是留给真跑过、只是回包没回来的(超时不等于没发生)。
- **「还没读到可操作的配置」跟「用户改过草稿」也是两件事**:读失败那一档 `xChan` 是
  null、草稿是空的,`xChanEnsureSaved` 原来直接往下走 —— 先发一条**空的 PUT**,再被
  保存收尾那次重读恢复出来的真实设置判成「保存完成时这份设置已经又改过了」,而用户
  一个字都没改、动作也压根没发出去(审查 N1)。出路是**先把那次读补上**,补回来之后
  这一次动作照常接着做(堵在那儿等于让他再点一次,而他不知道刚才那下为什么没反应)。
- **读不出可选的取法时,能照抄的那条命令要跟着一起收走**(`loadXChannel` 的失败分支连 `source-x-cmd`、
  `source-x-login`、`source-x-import-state` 一起清掉,清单也收起来)—— 那条终端命令挂在卡片上而不是某个输入块
  里,只藏输入块的话,面板一边说"读不出现在是哪一档",一边还挂着上一档那条命令等人照抄。
- **选完一档就把清单收起来**(`xChannelChanged` 调 `xChanPicker(false)`;可见性只有 `xChanPicker` 一个出口,
  `aria-expanded` 和那枚箭头跟着它走)—— 清单是"换一种"时才要的东西,留着就是三句长说明一直占屏,把刚换这档
  的状态和按钮挤到下面去。
- **每一档的说明都要能单独读懂,不许写「风险同上」。** 面板上那三行是一张按 `CHANNELS` 排的清单,顺序一动,
  "上"指的就是另一档了(把 `browser` 挪到首项那一次,它那句"风险同上"当场指向空气)。
- **那三颗按钮打的是动作端点,一律 `pipePost`** —— `pipeJson(path, {}, 120000)` 实际发的是 **GET**。
- **状态和下一步合成一句、去重按内容判**(`xChannelSay`):feedgrab 那档的「下一步」就是卡片上那条可复制的
  命令本身,而「检查连接」的 detail 已经把原因和下一步拼在一起了 —— 两种来法都会让同一句话在同一屏上写两遍。
  **那条命令留在卡片上、不许收进「可执行文件位置」那个折叠块**:收进去就是不展开一个字都看不见,而状态行
  那边又按去重把它让掉了,两处一起沉默。
- **面板空态那句「要先配置什么」不许写死某一档的前提**(`sources.js` 的 `sourceConfigHint()` 读后端给的
  `configuration_error`)。
- 详细见 `docs/decisions/x-channels.md`。

## 事故形态与实测证据

- **同一批大V账号,三条互斥的取法,选哪条是一个设置**(`social` 的
  `x_channel`,默认 `browser`):
  `feedgrab` 用一份 X cookie 调 X 自己的接口(子进程调用用户装好的 feedgrab
  CLI)、`browser` 复用一个**独立 profile** 里的登录态(我们自己起的无头 Chrome,
  CDP over 管道)、`attach` 直连用户**已经开着**的那个日常浏览器(他自己勾开远程
  调试,CDP over WebSocket)。三条的身份、要准备的东西、边界精度各不相同,口径只有
  `x_channels` 一份。**后两条的差别是「谁的浏览器」**:独立 profile 那条要在无头壳
  里登录一次 X(这条链上唯一必须人在场的一步),日常浏览器那条用他现成的登录态、
  代价是那个调试开关开着时本机任何程序都连得上它 —— 详见下面 attach 那几条。
- **通道只管「没填专用订阅链接的那些 X 账号」。** 填了专用订阅链接(`feed_url`)的
  订阅照旧走 HTTP;非 X 的 social 订阅(Bluesky 的 RSS 之类)同理。判据是
  `registry.uses_channel` —— 它回答的是「这条订阅受 X 通道设置管吗」。
  (原名 `uses_bridge`:桥接那一档删掉之后那个名字就只剩误导了。)
- **后两条不是 HTTP feed,所以不走 adapter 的 `endpoints()/parse()`**,而是在
  `sync.collect` 开头**整批预取**一次(`x_channels.prefetch`),再由
  `fetch_source` 顶上那道分派按订阅各取自己那一份(`take`)。两个理由:
  ①起一个 Chrome 要两三秒,51 个账号各起一次就撞上 90 秒的采集预算,而**同一个
    浏览器 profile 同时只能被一个实例打开**,4 个 fetch worker 并发也不成立;
  ②硬塞进 adapter 的话 `SocialAdapter.endpoints()` 会把账号主页本身当地址返回,
    那是个 HTML 页,解析必然失败 —— 报出来的还是一句跟真实原因无关的
    「没有返回 RSS / Atom」。
- **HTTP 那一侧的采集预算要在预取之后才开始算**(`deadline = time.monotonic() +
  COLLECT_SECONDS` 排在 `_prefetch_x` 后面)。算在前面的话,预取一跑完每条订阅
  都已经超预算,`collect` 的 `deadline - now < SOURCE_SECONDS` 当场把整轮全部
  记成「留待下次同步」—— 而东西明明已经抓在手里了,这一轮的模型/浏览器开销
  全白付。登录态通道另算一份预算(`X_LOCAL_SECONDS`,默认 1200 秒),因为它是
  串行的。
- **「停止」要在起浏览器之前就认**(`x_browser.harvest` / `x_feedgrab.harvest`
  开头各一道)。早就按下的停止不去排队:起完 Chrome 只会把每个账号逐个跳过;
  feedgrab 那边更糟 —— `find_binary` 先跑,它失败时整批报的是「没装 feedgrab」,
  而用户按的是停止,面板上会留下一轮假故障。每个账号之间再问一次(这一批要跑
  十几分钟,不认它的话按下去要等满整轮预算)。
- **边界靠推文时间,水位按订阅存在 `subscriptions.config` 里,而且两条通道
  各一个键**(`x_watermark_browser` / `x_watermark_feedgrab`)。精度不同是实打实
  的:浏览器能读到分钟,feedgrab 只到天(`X_USER_TWEETS_SINCE` 本身只认日期)。
  混用一个键的话,从浏览器切到 feedgrab 会拿一个带时分的值去填那个环境变量,
  那一轮的边界就错了。`save_watermark` 只改自己那个键,别的原样留着。
  天粒度的重叠重抓是安全的:`put_items` 按 `sha256(kind:url)` + `ON CONFLICT
  DO NOTHING` 去重。
- **一条都没抓到时水位不许前进**(两个 `_newest` 都是「没有就沿用旧值」)。改成
  「现在」等于把这段时间宣布为已抓过,而这一轮可能只是没滚到(预算用完、X 限流)
  —— 那几条推文从此再也进不来。水位只前进到确实见过的那条推文。
- **没读到上次的位置,水位一步都不许动**(`_harvest_one` 返回「没读完的原因」,
  `harvest` 里那句 `started if incomplete else _newest(...)`)。三种「没读完」:
  滚动次数(`MAX_SCROLLS`)用完、单个账号的 `ACCOUNT_SECONDS` 用完、页面不再长出
  新内容而又不在时间线底部。抓到的照旧入库,**但水位留在原处** —— 推到「这一轮
  见过的最新」就等于宣布没读那一段已经收过:它们比旧水位新、又比新水位老,从此
  任何一轮增量都选不到(2026-10-08 审查实测:42 条新推、40 次上限,返回 40 条、
  下一轮按新水位筛整个时间线得到 `retry_urls=[]`)。**「把水位退到最老那条」也
  不行**,那条之下的那一段同样全都低于它 —— 留着旧水位是唯一不丢东西的做法,
  代价只是下一轮重叠重抓,而 `put_items` 按 URL 去重。
- **「留着旧水位」在首轮上什么都没留下,所以两条通道存回的是**这一轮真正用过的
  那个下界**(`x_browser` 的 `started`、`x_feedgrab` 的 `since`)。** 新订阅压根
  没有水位,而 `watermark_patch` 对**空值不产生补丁** —— 交一个空的 `water` 回去
  等于什么都没存,下一轮又现算一个「当天往回 `FIRST_DAYS` 天」,**那段没读完的
  日期就随时间往前滑走了**,面板上写的还是「已同步」。实测:9-20 建的订阅首轮
  翻页中断只收进 1 条,10-01 恢复之后下界变成 9-17,9-15 那条推文再也选不到
  (2026-10-09 第 4 轮审查;那条订阅自己的 `history_floor` 还停在 9-15,按原下界
  取回来的那条照样过得了 `sync._within_history`,所以不是历史闸门拦的)。
  **存回下界不会漏掉边界那一天**:上游的日期过滤是 `tweet_date < since_date` 才丢
  (含下界当天),浏览器那侧 `_select` 两轮也是同一个排他下界,窗口逐字相同。
  **读完的那一轮照旧 `_newest(entries, water)`、不许一律存下界**:那样一个长期
  不发推的号会每一轮重读一个越来越大的窗口,而它本来就读完了。
- **「滚不出新东西」要连着 `_BOTTOM_TRIES`(3)次、而且每次都停在页面底部,才算
  真的到底了**(`_SCROLL_JS` 顺带回答 `bottom`)。一次不算:慢网络下的一次懒加载
  空窗和「时间线到底了」在页面上完全同形,把前者当成后者就是给一次没读完的抓取
  盖「完整」的章 —— 而盖完章水位就推进了。不在底部而页面不长高 = 卡住/限流,
  那是「没读完」,不是到底。
- **「翻到底」按**页面出现顺序**数,连续 `_OLD_STREAK`(3)条**自己发的**推都老于
  下界才算**(`_old_enough`)。两件事各有理由:
  ①**不能按时间排序数**:转推显示的是**原推**时间,所以一条很老的转推会排在新推
    中间 —— 按时间排序会把三条互不相邻的旧推拼成一条「连续的老尾巴」,第一屏就
    判翻到底、下面的新推全漏(2026-10-08 审查实测)。`items` 的顺序由 `_COLLECT_JS`
    那个 Map 的插入顺序保证,就是它们在 DOM 里第一次出现的顺序。
  ②**只有原创推的时间能当「读到哪儿了」的证据**(`_own_tweet`):profile 时间线按
    活动时间倒序,而 `<time datetime>` 给的是原推时间。置顶的位置在最上面、时间
    可能是几年前;转推的时间必然 ≤ 它的活动时间 —— 所以「它很老」证明不了我们
    翻过了水位(可能是刚转的一条老推)。反过来「它很新」倒是证明得了,所以
    **任何一条新于下界的时间线条目都把计数重置**。
- **「算不算这条时间线的内容」(入库)和「它的时间算不算证据」(翻到底)是两个
  判据,别合成一个**(`_in_timeline` / `_own_tweet`)。
  入库那份排除两种:①**推广位**(`Promoted`/`推广`)—— 那是广告,不是这个人的
  观点;②**作者不是这个号、又没有转推那一行 socialContext** —— 它不是从这个账号
  的时间线里长出来的(推荐位、「你可能喜欢」),按这个订阅记进去就是把别人的推文
  当成这个大V的观点,和 feedgrab 那一侧按 `/<handle>/status/` 过滤是同一条规矩。
  **转推一定带着一行上下文,所以这么判不会把转推丢掉** —— 而转推正是「他此刻在想
  什么」的一部分,正文里保留那行上下文。入库口径只有这一份,两处各判的话被这边
  丢掉的条目还在"翻到底"那边顶着计数。
- **置顶要入库,只是不参与「翻到底」的证明**(两条通道都是:`_in_timeline` 不排除
  它,`x_feedgrab._entry` 里那句按 `is_pinned` 返回 None 已经删掉)。原来一律丢掉,
  理由是「它每天都在、会被日报当补录反复提」—— **那个理由不成立**:`put_items` 按
  `sha256(kind:url)` + `ON CONFLICT DO NOTHING` 去重,旧置顶重复出现一条都不会重复
  入库,而且它的时间低于水位、`_select` 自己就筛掉了。真实代价在另一头:**刚发出来
  就被钉上去**的推文(宣布新版本、活动预告 —— 正是最该收的那种)被永久丢掉,下一轮
  它已经低于水位,再同步也补不回来(2026-10-08 审查实测)。
- **「有推文卡片却一条都解析不出来」是 X 改版,不是「这个号今天没发推」**
  (`_harvest_one` 里那句 `if seen_articles and not parsed: raise`)。两者必须
  分开:后者安静跳过是对的,前者安静跳过会让这条通道从某天起永远返回空,而
  面板上一切正常。登录失效 / 账号打不开 / 限流同理,各自一句话(`_STATE_JS`
  + `_wait_state`),不许折叠成「时间线上没有推文」。
- **feedgrab 是子进程调用,环境变量白名单 + 显式清场,`OBSIDIAN_VAULT` 必须
  清掉。** 它的输出目录**优先**认 `OBSIDIAN_VAULT`、其次才是 `OUTPUT_DIR`,而
  这台机器上它指的正是知识库那个 vault —— 不清掉,抓来的推文会被 feedgrab 直接
  写进 `vault/X/`,绕过 feed_items、翻译和导出整条链,表现是 vault 里凭空多出
  一批谁也管不着的 md(索引照收,清理找不到)。每个账号一个干净的输出目录:
  共用一个的话这一轮读到的 md 里会混进上一个账号(以及上一轮)的产物,而
  「哪些是这次抓的」没有别的判据。
- **它的产物路径不许写死,只能整棵扫**(`_read_output` 走 `rglob('*.md')`)。
  保存位置是「平台目录 + category」拼出来的(上游 `utils/storage.py` 的
  `save_to_markdown`),而账号推文的 category 是 `status_author/<显示名>`
  (`fetchers/twitter_user_tweets.py`,它那条 api 实现同样),显示名只过了一遍
  文件名清理 —— 中文、空格、emoji 全留着,**猜不出来**。原来按 `X/*.md` 只扫顶层,
  于是**抓到的推文一条也读不到**:`harvest` 把这个空结果当成功存下来、随后把产物
  目录删掉,面板上是「已同步 · 0 条」而知识库里什么都没有。这是最坏的一种形态 ——
  它和「这个号今天没发推」长得一模一样,一行提示都没有(2026-10-08 审查实测:
  产物落在 `X/status_author/Example Person/` 下,`summary.added=0`、
  `item_count=0`,而那份 md 单独交给解析器和 `_entry` 是完全有效的一条推文)。
  **递归不放松归属**:判据是 `_entry` 按推文 URL 里的 handle 过滤(见下面那条),
  跟文件落在哪一层没有关系,而产物目录本来也是本轮为这个账号新建的;顶层那些
  产物(单条推文、长文线程)照旧收得到。
- **它的退出码 0 不代表这一批抓全了,所以没抓全就不许推进水位**
  (`_incomplete` / `_batch_failures`,`harvest` 里那句 `since if note else _newest(...)`
  —— 口径同浏览器通道那条「没读到上次的位置,水位一步都不许动」)。**有两条路都会
  这样**:①翻页时某一页所有轮换账号都失败,它只打一行 `logger.error` 就 `break`
  (`fetchers/twitter_user_tweets.py` 的 `if not response`);②逐条抓的时候单条失败
  只往批量记录里记一笔 `status: failed` 就继续(同一个文件那个 except 分支)。两种都
  在收尾把计数包成一句**普通正文**(`reader.py` 的 `summary`),CLI 的账号主页分支
  `print` 完直接 return —— 只有抛异常才 `sys.exit(1)`(`cli.py`)。于是「进程退出码
  为 0」证明不了这一批没漏。
  **不认出来就是静默丢数据**:水位一推到「这一轮抓到的最新那天」,下一轮的
  `X_USER_TWEETS_SINCE` 就是它,上游按这个下界把更早的推文整段丢掉
  (它那句 `stop_pagination`)—— 漏掉那几条比旧水位新、又比新水位老,**从此任何
  一轮增量都选不到**。抓到的照旧入库、不记 `errors`、不进退避,只是把旧水位留在
  原处 + 一句 `incomplete` 带到面板上(复用现成的 `last_note` →「部分同步」那条链),
  下一轮重叠重抓,`put_items` 按 URL 去重。
  **「没抓全」的两个档来源不同,证据也不在一处。**
  **第一档:翻页半途中断**(`_PAGE_ABORT`)。那一页**压根没拿到**,没拿到的条目
  不会进 `tweet_list`,所以 `failed` 一个都不加:批量记录里只有成功那几行、摘要写
  的是「失败: 0」—— **下面第二档那两道判据各跑一遍都是 0**。实测(2026-10-09 第 3
  轮审查,拿上游 0.26.2 原版 `fetch_user_tweets` + 原版 `cmd_fetch` 复现,只替掉网络
  回包):账号还有 10-07 的推文,首次同步 `added=1`、`errors=[]`、`partial=[]`、水位
  从 10-05 前进到 10-08;把第二页的故障解除再点同步 `added=0`、库里仍然只有 10-08
  那条 —— 这一轮传给上游的下界已经是 `X_USER_TWEETS_SINCE=2026-10-08`,拿最初那个
  下界跑同一个健康上游作对照,两条推文都在。
  **这一档只有日志这一个证据源**,没有结构化的第二道可言:缺口在「没拿到的那一页」
  里,条数、日期我们一个都看不到。「我们拿到的最早那条还没够到下界」倒是看得见,
  但那**证明不了漏**(这个号本来就可能没有更早的推文),所以当不了判据 —— 正因如此
  这一行日志必须自己认准。
  **判据要连「第 N 页」「M 个账号」一起认**:松成裸「均失败」会把 `twitter.py` 里
  那句「所有 GraphQL Cookie 均失败,降级到 FxTwitter」也算进来,那是降级之后照样
  拿到了内容。反过来也不许把「已到达日期过滤边界,停止分页」当成中断 —— 那是
  **读完了**的正面证据,连它也报的话这条通道的水位永远不会前进。日志走
  `logger.error`、上游的 sink 是 `logger.add(sys.stderr, level=INFO)`(`cli.py`),
  而 `_run` 把 stdout 和 stderr 合起来返回,所以这一行一定在我们手里。
  **而这一行要和「回显了用户内容的日志」分开,三道各有射程(`_PAGE_ABORT` +
  `_aborted`)。认的是上游那句话的形状,不是它的几个关键词**:
  ①`>>>` / `<<<` 那两个标记。上游把推文标题和显示名回显进**路径**时
  (`Saved to Markdown: …/<显示名>/<作者>_<日期>:<标题>.md`,`utils/storage.py` 每存
  一篇打一行),路径的每一段都过一遍文件名清理 —— `_ILLEGAL_CHARS_RE` 和
  `_sanitize_folder_name` 都把 `<` `>` 换成空格,所以一条标题里**逐字写着这句报错**
  的推文(排查记录、转发的日志截图)从路径这条通道带不进这两个标记;
  ②**跳过回显了本轮产物目录的行**。真正那句报错里压根没有路径,跳过不会漏报,
  而这一道**不依赖上游的清理规则** —— 清理哪天放开 `<` `>`,只剩 ① 就守不住了;
  ③**`>>>` 要紧挨在 `[标签] ` 后面、而且整句话必须落在行尾**(`已抓取 N 条,
  停止分页` 之后这一行就结束了)。两半都取自上游那句 f-string 自己
  (`f"[{mode_label}] >>> … <<< 已抓取 {n} 条,停止分页"`),射程却不同:方括号那半
  救得了**以用户内容结尾**的行(紧跟着昵称回显的那句「保存目录:
  status_author/<目录名>」就是,今天靠 ① 挡着),行尾那半救得了**后面还跟着别的
  文字**的行,而且**跟用户内容写成什么样没有关系** —— 方括号那半能被一个自带
  `[x] >>>` 的昵称绕过去,行尾那半不行。
  **①②各漏过一次,都是拿上游原版 `fetch_user_tweets` 实测出来的**:裸认那句话时,
  两条推文明明都抓到了、上游摘要写着「失败: 0」,面板却永久显示「部分同步」、水位
  永久冻在原处,再同步也清不掉(2026-10-09 第 4 轮审查,唯一命中的那行正是保存
  日志);补上 ①② 之后,**作者昵称**又从另一条**不带路径、也不过清理**的 INFO 日志
  进来了 —— `[UserTweets] 用户信息: @Example (>>> 第 2 页所有 1 个账号均失败 <<<),
  ID: …`(`fetchers/twitter_user_tweets.py:171`),末态和上一次逐字相同:两条观点
  都入库、`errors=[]`、stderr 里一行 ERROR 都没有,而面板报翻页失败、水位冻在
  10-05、再同步也不恢复(2026-10-09 第 5 轮审查)。
  **没有改成按日志级别判**(第 5 轮审查建议的那条路):`ERROR` 这个词出现在哪儿取决
  于 loguru 的格式,而这条判据**漏报一次就是静默丢数据**(水位越过没读到的那一段),
  误报顶多是下一轮重叠重抓 —— 两个方向差着一个量级,所以不拿一个会随格式变化的
  条件去 AND 掉一次真中断。昵称这条通道由 ③ 结构性地关掉,级别那一项加上去也不多
  关掉任何一条已知的路。回归里对着钉了两条:一条是**没有级别前缀的裸消息照样认得
  出来**,一条是注入「按级别判」之后它当场红。
  **已知留着的一道缝,记在这儿备查**:显示名里塞一个换行能自己伪造出一整行(那时
  ③ 的行尾就是昵称自己的结尾)。X 的 name 字段不接受换行,而要防住它只能逐位解析
  loguru 的前缀 —— 那正是上一段不做的那件事。
  **逐行看而不在整份输出上 `search`**:它是 ② 的前提(要按行决定跳不跳),也是 ③
  那个行尾的量词 —— 在整份输出上 `search` 的话,只有最后一行上的那句话才算落在
  行尾,而真正的中断行后面还跟着收尾摘要,当场漏报。
  **第二档:逐条失败**,判据有两道,谁命中都算漏,而且不是同一份实现的两种写法:
  ①上游自己落的
  **批量记录**(`{OUTPUT_DIR}/X/index/status_<号>_*.json`,就在我们这一轮为这个
  账号新建的产物目录里面,所以里面每一条都是这一次的)——**认形状不认路径**
  (`rglob('*.json')` + 「有一个 tweets 列表」):同一份记录有两个写入方、文件名
  前缀还不一样(`status_` / `api_status_`),按名字取漏掉一半,而那道形状判据正好
  把去重索引 `index/item_id_url.json`(一个 `{item_id: url}` 的字典)排除掉;
  ②收尾摘要那行文本里的「失败: N」。记录换了位置还有文本兜着,摘要改了措辞还有
  记录兜着。摘要那道**必须带上「成功: N」那半截上下文**:写成裸 `失败:` 会被日志里
  的「失败: @某人 - 原因」「补充抓取失败: …」蒙到,而误报把水位**永久**冻住 ——
  那比漏报还难看出来。实测过这一档:更早一天那条临时失败、更新那条成功,面板报
  「已同步 · 新增 1 条」,`errors` 和 `partial` 都是空的,水位从 10-05 跳到 10-08;
  把外部故障解除之后再点同步,`added=0`,那条推文再也回不来(2026-10-08 第 2 轮审查)。
  **②那一道还有一类独占的证据**:上游那条「补充抓取」(UserTweets 没够到下界时
  用搜索往回补)**只把计数并进摘要、不往批量记录里写**(`tweet_list` 只在它自己
  那个循环里追加,`_save_batch_record` 排在补充抓取之后)—— 补充抓取里逐条失败的
  那些只有摘要数得出来。所以这不是「一道主判据 + 一道兜底」,是两道各有射程的判据。
  **两档同时命中就两句话都说**(`_incomplete` 用 `;` 拼):它们是不同的原因,
  用户的下一步也不一样。
  **「补充抓取整段失败/压根没开」那一档仍然没认**:它是第三个形状 —— 缺口在
  `since` 和它实际够到的最早那天之间,而这两个数摘要里都没有,认它只能按那句
  `logger.warning('补充抓取失败: …')` 的措辞判;而它一旦是长期坏的(没浏览器、
  没 API key),水位就**永久**冻在原处、每一轮重抓整个窗口 —— 那个取舍得单独算,
  记在这儿备查(分析写在 `_incomplete` 的注释里)。**和第一档的分界线**:第一档有
  一行**明确说了「这一页失败了、停止分页」**的 `logger.error`,不是一句笼统的警告。
  **只有 `fetched`/`skipped` 算没问题**(`skipped` 是上游自己按去重或互动阈值跳的,
  那是它的决定、不是漏),没见过的状态一律当成漏:漏报是静默丢数据,误报的代价只是
  下一轮重叠重抓 + 面板上一句「部分同步」,两个方向差着一个量级。
  **也没有把水位推到「最老那条失败的前一天」这种精细做法**:那要再信一层
  (失败条目的 `published` 填得全不全、这一批本身有没有被截断、上游那条
  「补充抓取」有没有静默失败),而留着旧水位本来就是这条通道的常态 —— 它的精度
  只到天,每一轮都在重叠重抓。
- **登录提示里的可执行文件必须就是采集时会调的那一个**(`x_feedgrab.login_command`
  过一遍 `find_binary`;`x_channels.login_command` 因此收**整份 settings** 而不只是
  通道名 —— 口径同 `readiness` / `check`,这个模块里凡是要回答「当前这套设置会怎么
  跑」的一律收 settings)。原来写死裸 `feedgrab`:用户把它装在独立虚拟环境里、只在
  面板上填了绝对路径(`harvest`/`doctor` 都认这个设置)时,照页面抄下来那条命令在
  终端里是 `feedgrab: command not found`,首次配置从此走不通 —— 而同一个页面上
  明明显示着那条可用的路径(2026-10-08 审查实测 `exit 127`)。保存设置不会往用户
  终端的 PATH 里加任何东西,所以这条提示得自己把路径带上。两条配套的:①可执行
  文件和数据目录两头都 `shlex.quote`(路径带空格时不 quote 的命令会被 shell 拆成
  两段);②配了路径但当下不可执行时照它**原样显示** —— 用户看得见自己填错在哪儿,

- **不要把 feedgrab 抄进 kb。** 它要的是 X 内部 GraphQL 接口 + 那套
  `x-client-transaction-id` 签名,签名算法要从登录态页面下发的 manifest 里取

- **归属只认 `__biz` 式的身份,不认名字** —— 这里对应的是「别的 handle 的
  status 链接不算这个订阅的内容」(`x_feedgrab._entry` 按 `/<handle>/status/`

  订阅的内容。
- **拿到一个浏览器有两条路,各自是一条通道,不是一个实现细节**:`browser` 自己
  起一个独立 profile 的无头 Chrome(`x_cdp.Chrome`,CDP over **管道**),`attach`
  连上用户**已经开着**的那个日常浏览器(`cdp_attach.Attached`,CDP over
  **WebSocket**)。对照表在 `x_cdp` 的模块注释里,两条的身份、要准备的东西、
  可用性完全不同 —— 所以是四条通道里的两条,而不是一个开关。
  **这里原来写着「不许用 `--remote-debugging-port`」,那条禁令撤掉了**(2026-10-09
  用户点名要这条路)。它的依据是「端口一开,本机任何进程都能连上这个浏览器」——
  **那句话本身仍然成立,而且仍然原样写在 `cdp_attach` 的模块注释和面板上那条通道
  说明里**;撤掉的是"所以不许做",保留的是"所以要说清代价、而且默认不选它"。
  换来的是这条链上**唯一必须人在场的那一步**没了:独立 profile 那条要在无头壳里
  过一次 X 的两步验证和人机校验,而日常浏览器里那份登录态早就在了。
- **管道那条的两个理由里,只有一个还归它自己**:①`\0` 分隔的 JSON 帧一个 recv
  循环就够,所以**不引入 playwright**(它要再下一份自己的 Chromium,几百 MB;

  attach 那条的 WebSocket 同样是手写的(`kb/feeds/ws_client.py`,300 行,

  自己勾出来的。
- **attach 那条的三条硬口径**(`kb/feeds/cdp_attach.py`):
  ①**那个开关只能由用户自己去开**(在浏览器地址栏打开
  `chrome://inspect/#remote-debugging` 勾一次「Allow remote debugging for this
  browser instance」;**这一勾持久、而每条连接都还会弹一次「允许」**,两半分清
  见首节那条)。我们不代劳、也不绕开:不改他的启动参数、不写他的 Local State、不去
  唤起那个页面。面板上「没就绪」那一档给的下一步就是这句话(`ENABLE_HINT`,
  `readiness` 的第三项,`x_channel.js` 只负责把它显示出来)。
  ②**端口是读出来的,不是我们指定的。** Chrome 把那个端口写进 user-data-dir 下的
  `DevToolsActivePort`(第一行端口,第二行 browser 那条 WebSocket 的路径),所以
  发现 = 读这个文件 + TCP 探活(本机实测这个端口是固定 9222,见首节,别再用「因为
  随机」当论证)。固定去敲 9222 只能
  撞上「用户自己带 `--remote-debugging-port` 启动」那一种,那条留作回落
  (`FALLBACK_PORTS`);发现逻辑对某台机器不成立时的出路是 `KB_CDP_ENDPOINT`
  (认 `9222` / `host:9222` / 完整 ws URL 三种写法,**显式指定了就不再去猜别的**
  —— 指错了要当场看出来,而不是悄悄连上另一个浏览器)。
  **`parse_endpoint` 一个异常都不许抛出来**:`urlsplit(...).port` 对非数字和越界
  端口抛的是 `ValueError`,而这个函数坐在**来源面板每次刷新**那条路上
  (`x_channels.readiness` → `registry.configuration_error`)—— 一个写错的环境变量
  能让整条来源面板连带着 500,而真正能用的那几个来源跟它毫无关系(2026-10-09 审查
  实测)。认不出来一律返回 `None`,范围另外用 `_ok_port`(`0 < port < 65536`)自己
  卡住:`urlsplit` 对 `:65536` 抛异常、对别的写法不抛,靠它的异常当校验是碰运气。
  **`urlsplit(value)` 自己也在 `try` 里面,不是只圈那几个取值**:它对
  `ws://[::1`(IPv6 少一个右方括号)当场抛 `ValueError`,两个接口照旧 500 ——
  只圈取值等于把判据定在「哪一步会抛」上,而那取决于标准库的实现(2026-10-09
  第 2 轮审查实测)。整段一律「认不出就返回 None」。
  **写错了也不许回落**(`discover` 里 `if explicit is None: return None`,既不读
  端口文件也不敲 `FALLBACK_PORTS`):「显式指定了就不再去猜别的」那条规则对"认出
  来的地址"和"认不出来的地址"必须是同一句话,不然用户以为自己指到了 A,实际连上
  的是自动发现找到的 B。
  **而且要说出是哪儿错了**(`explicit_problem()` 给原因、`ENDPOINT_HINT` 给三种
  正确写法和"清掉它就回到自动发现",`readiness` 和 `x_browser.probe` 两处都先问
  它)。这一档**不许复用 `ENABLE_HINT`** —— 开关他早就勾好了,再叫他去
  `chrome://inspect` 勾一次是把人往错的方向推,而真正要改的那个环境变量一个字
  都没提到。
  ③**探活必须 TCP connect,不能拿 WebSocket 去试。** 首次 WebSocket 连接会让
  浏览器弹一次授权弹窗,而这条判断是来源面板**每次刷新**都要做的
  (`x_channels.readiness`)—— 拿 WebSocket 探等于每刷一次面板弹用户一次。
  **而且端口文件可能是陈旧的**(浏览器崩溃、强杀都留着它),所以读到端口不等于
  连得上,必须探活:不探的话面板说「已就绪」,真抓的时候才在 connect 上失败。
- **独立 profile 那条的收尾一定做完:关浏览器怎么失败都不许把后面那几步跳过**
  (`x_cdp.Chrome.__exit__` 只剩 `try: self._shutdown()` + `finally:` 关两个 fd、
  状态复位;先好好说一次再 kill 的那两步都在 `_shutdown` 里,**都有界、都不往外
  抛**)。原来是「发 `Browser.close` → `wait`」裹在一个
  `except (OSError, subprocess.TimeoutExpired)` 里 —— 而 `_post` 带上 deadline
  之后写不动报的是 `CdpError`(写出错的 `OSError` 也在那儿翻成了它),于是异常
  从关闭路径冒出去,`kill`/`wait`、关 fd、`proc` 复位**一步都没执行**。
  **留下的不是用户能看见并关掉的登录窗口,是一个还活着的无头浏览器** ——
  这是第 1 轮把写路径改成有界之后带出来的回归(2026-10-09 第 2 轮审查拿真浏览器
  实测:`SIGSTOP` 停住它、灌满命令管道,`__exit__` 抛 `CdpError` 之后进程还活着、
  两个 fd 都还开着,`SIGCONT` 恢复也不自愈)。`__enter__` 起不来时兜底走的也是
  这条路,所以同一个缺口在启动失败那一侧一模一样,而且那时收尾抛出来的异常还会
  **顶掉启动失败那个原因**。`kill` 之后仍然等不到也不抛:fd 一关对端就收到 EOF,
  最坏留下一个正在退出的进程,而抛出去的代价是连 fd 都不关。
  **反过来钉一边:好好退出的那一次不许被 kill** —— `Browser.close` 存在的理由
  就是让它把 profile 存盘,而登录态就在里面。
- **「这个 profile 被占着吗」只认「`SingletonLock` 指着一个活着的 pid」**
  (`x_cdp.profile_busy`,`probe` 的前置检查、`open_login_window` 那道闸、
  `_launch_hint` 三处共用它)。那个链接是 Chrome 的 ProcessSingleton 留下的,
  内容正是 `<主机名>-<pid>`;**它崩了、或者被我们 kill 掉就留在原处**,而 Chrome
  自己也是读这个 pid、发现死了就把锁抢过来(2026-10-09 实测:优雅退出之后链接
  没了;SIGKILL 之后链接还在、指着那个已经死掉的 pid,而下一次启动照样成功并把
  链接改写成自己的 pid)。
  **只看 `lexists` 的后果是把用户堵死,而且和上面那条是同一次事故的后半截**:
  收尾哪一次没能优雅关闭(浏览器卡住,只剩 kill 这一条路),「检查连接」和
  「打开登录窗口」就一起报「登录窗口还开着,关掉它再试」,而**根本没有窗口可关**
  —— 采集那一侧压根不看这个文件,所以只有这两处被堵,它们偏偏是用户唯一能自救
  的两个入口(审查报告里那句「后续检查一直提示被占用」指的就是这里)。
  **不设「看不懂就当占着」的特例**(不是链接、链接内容不是数字,一律不算证据):
  那是在没有证据的时候堵住那两个入口,正是这条判据要改掉的毛病;真有另一个活着
  的实例时这个 pid 本来就是活的,上面那条规则已经答对了。**收尾也不去替 Chrome
  删那把锁** —— 不写别人 profile 目录里的内部文件,判据对了就够。
- **在别人的浏览器里干活的卫生规矩,契约和后果各有一条回归钉着**:标签页一律
  `Target.createTarget {background: true}` 开(不加会抢到前台,把用户正在看的
  东西顶掉)、退出时**只关自己开的那几个**(`Attached._opened`)、**永远不发
  `Browser.close`**(那会关掉用户整个浏览器,连同他所有标签页和没提交的表单
  —— 独立 profile 那条能关是因为那个浏览器是我们自己起的)、顺带路径上**不列
  用户的标签页**(`Target.getTargets` 只在测试里用)。

  浏览器里了**,而我们没认下它 —— 退出清理一个都不关,它就一直留在那儿
  (2026-10-09 审查拿真无头浏览器实测:注入一次 attach 失败,退出之后那张
  `review-leftover` 还在)。多认一张不存在的标签页顶多是 `closeTarget` 报个错被
  吞掉,少认一张就是在别人的浏览器里留垃圾 —— 两个方向差着一个量级。
- **`attach` 和 `browser` 共用水位键 `x_watermark_browser`**(`_WATER_KEY`)。

  `X_USER_TWEETS_SINCE`),所以这里的判据是「精度和语义一不一样」,不是
  「是不是浏览器」。
- **不抄 web-access 那道「拦截页面对调试端口的探测」**(它用 `Fetch.enable` +
  `Fetch.failRequest` 把页面发往 `127.0.0.1:<调试端口>` 的请求拒掉,防站点用

  把事件全丢掉 —— 加一条事件回路是另一件事。不拦的后果是「和用户自己浏览时
  一样」:这条通道的卖点本来就是用他自己的浏览器,比独立 profile 的无头壳更不
  像自动化。真要拦,得先给 `Session` 加事件分发。
- **这条通道不在面板上登录**(`intake_api.x_channel_login` 的第一道分支)。
  拒绝文案**不许建议他换档** —— 他要的登录态就在自己那个浏览器里,我们开一个
  独立 profile 的有头窗口对他毫无用处,那句"先把取法改成「独立 profile 的登录
  态」"等于让他把刚选对的那一档改错。说清「在那个浏览器里打开 x.com 登录一次」

  块里,所以这一档整块隐藏、按钮自然不出现;这条拒绝是走键盘/脚本那条路时的
  兜底。
- **面板上那句静态说明不许写死通道有几条**(`source_types` 里 social 的 `note`:
  「X 的取法在下面的「取法」那一块里选,每一档要准备的东西不同。」)。原来写的是
  「X 可选三种取法」,加完一条通道之后它就成了一句错话,而**它和那张清单并排显示
  在同一屏上** —— 用户看得见的条数和旁边写的对不上。口径跟前端那条「不许写死一张表」是同一个:条数、名字
  这类会跟着通道清单变的东西,一律让 `/api/pipeline/...` 给的那份清单自己说。
  回归直接断言 `note` 里不出现「三种」「四种」这类数量词。
- **它一个输入框都不要,所以它顺带是「新增一条通道不用改前端」那条口径的回归。**
  `x_channel.js` 只按后端给的 id 决定显示哪一块,没有自己那一块的通道就一块都
  不显示;要做的事(去地址栏勾开关)塞不进输入框,就从 `readiness` 的第三项并进
  状态行那一句(`xChannelSay`)。加这一条通道时前端一处都不用改 —— 名字和那句

- **Chrome 把那两个 fd 的编号写死成「读 3 / 写 4」,而 `preexec_fn` 里 dup2 到 3
  实测不成立**(2026-10-08:Chrome 报 `Remote debugging pipe file descriptors
  are not open`,探针 `ls -l /dev/fd` 显示 exec 时 3 号没人占)。口径是:父进程
  先把两端复制到一个空闲高位 fd、`pass_fds` 带过去,再由 shell 的
  `exec 3<&N 4>&M` 落到位(编号在脚本里就是常量)。**高位编号必须 `fcntl.F_DUPFD`
  现取、不许写死两个常量**:kb-web 这个进程里 sqlite、httpx、uvicorn 的 socket
  都在占 fd,dup2 会**静默关掉**目标 fd 原来那个对象,表现是另一条路上的数据库
  连接莫名失败,而这里一个字都看不出来。
- **读写都永远带 deadline,而且 deadline 要在命令发出去之前算好**
  (`x_cdp.Session.call` 里 `deadline = time.monotonic() + timeout` 排在
  `self._send(...)` **之前**,`_post`/`_write` 一路带着它)。读那一半的理由同
  embed_pool 那次事故:攥着锁阻塞的 read 会把一整条链冻住,所以把「挂住」变成
  「报错重试」。**写那一半原来整个没有上限**:先 `sendall` 再算 deadline 的写法
  等于「超时只管读」—— 对端(**用户自己那个浏览器**)不收数据时 `send` 在内核里
  等多久,这条命令就挂多久,而且是在采集线程上挂,`CALL_TIMEOUT` 一秒都管不着
  (2026-10-09 审查实测)。顺序不许反:先发后算的话 deadline 从"写完那一刻"起算,
  写阻塞的那段时间压根不在预算里。
- **socket 和管道一律设成非阻塞,超时由 `select` 按 deadline 管**
  (`ws_client.WebSocket.__init__` 的 `setblocking(False)`、`x_cdp.Chrome._nonblocking_write`
  的 `os.set_blocking(self._w, False)`)。**光「select 等可写 + send」挡不住一条
  阻塞的连接**:BSD/macOS 的 `sosend` 对一条大于可用空间的载荷会**在内核里循环
  等到全部写完**,select 说"可写"只是说"有一点空间";管道同理 —— POSIX 规定阻塞
  `write` 要写满 `nbyte` 才返回。实测拿 4 MB 的 `Runtime.evaluate` 打一个灌满的
  socket,阻塞版当场把测试进程挂死(得 `pkill`),非阻塞版按 `WRITE_TIMEOUT`
  报错退出。所以写是「select 等可写 → `send` 一段 → 接着等」,`BlockingIOError`
  当成"再等一轮"。
- **写超时之后这条连接就废了**(`ws_client` 的 `_broken`:标记 + `_shutdown()`)。
  半条帧已经进了对端的接收缓冲,接着发下一条命令就是帧错位 —— 而错位之后的读是
  **攥着锁阻塞**的那一种(口径同 embed_pool 和 `_MAX_FRAME` 那条)。废掉之后后面
  每条命令立刻报错,由 `x_browser.harvest` 外面那道
  `except (CdpError, EOFError, OSError)` 收尾,这一轮按失败结束而不是冻住。
  **上限是两头取小**(`min(这条命令自己的 deadline, now + WRITE_TIMEOUT)`):短命令
  按它自己的 `timeout` 走(不许因为写路径另有一个 10 秒的天花板就把一条 1 秒超时的
  命令拖到 10 秒),长命令最多在写上卡 `WRITE_TIMEOUT`。收尾那一下另有更紧的
  `CLOSE_TIMEOUT`(2 秒)—— 关连接是清理动作,没有理由为它再等十秒。
  **没有给整条会话加一个跟采集预算挂钩的硬 deadline**:那会把"快到预算、本来落
  `skipped`"的账号改判成 `error`,动的是现成的语义,而写上限已经把"挂死"关掉了。
- ~~**桥接熔断只对桥接通道成立**~~(`sync.collect` 的 `shared_upstream`)。它防的是
  「公共实例挂了,别再拿 50 个账号去撞」;登录态通道的内容已经在预取里抓完,
  这里只是逐条取走,断开只会白扔掉已经付过代价的结果 —— 而那两条通道真出问题
  (登录失效)时每个账号拿到的是同一句话,熔断省不下任何东西。
  **桥接删掉之后这道闸整条拆了**:没有公共实例可撞,留着就只剩"把同一轮里好好的
  源一起扔掉"那一半。现在钉的是反面 ——「同一轮里别人失败不许顺手把后面的跳过」。
- **「这条订阅能不能开工」要问当前通道,三处文案都从同一个判定取**
  (`registry.configuration_error` 按通道分支,`x_channels.readiness` 给
  (就绪, 说明, 下一步))。选了浏览器通道的人看到一片另一档的前提,说的
  是跟他这一轮采集毫无关系的一个设置。收尾那行 `_stage` 的「待配置 N 个(…)」
  和面板那条 `#source-configuration` 横幅都读它,不自己拼一句话。
- **`readiness` 只做便宜的判断(路径在不在、登录过没有),真连一次是
  `check()`** —— 前者被来源面板每次刷新都调,后者是用户点「检查连接」才走的,
  会真起一个 Chrome(`x_browser.probe`)或真跑一次 `feedgrab doctor`。
  **cookie 过期在文件上看不出来**,所以两个都要有。
- **退役通道名的别名表只在服务端**(`_RETIRED` + `resolve()`,`get_settings` 读
  的时候就翻)。这跟公众号那边不一样:**那份选择存在浏览器 localStorage 里、
  在后端的射程之外**,所以要把别名表发给前端;而 X 的通道选择只存在
  `feed_settings` 里,浏览器手里永远拿不到一个退役名 —— 发过去就是摆一套没有
  触发路径的机关,还要配一条假装它要紧的回归。
- ~~**同步间隔是一天一次**~~(`source_types` 里 social 的 `interval_minutes=1440`)。
  **这个键现在没有消费方了**,逐来源的间隔定时整条拆掉了(见 `sync-schedule.md`);
  下面这段留着记当时为什么从 60 改成 1440。
  原来 60 分钟是那条 HTTP 桥接时代的值;登录态通道一轮要起浏览器、滚几十个账号的时间线,
  每小时跑一遍既没有必要,也在给账号攒风险。
- **改 `SourceType.interval_minutes` 只影响没有设置行的新库,存量要迁**
  (`registry._SETTINGS_REV` + `_SETTINGS_FIXUPS`,在 `get_settings` 里归一)。
  已经保存过的那份 JSON 盖在默认值上面,面板保存通道时又把旧间隔原样带回去 ——
  于是「改成每天一次」对所有老用户都没有发生(2026-10-08 审查实测:存量
  `interval_minutes=60` 的设置行,真跑一次当时的 `schedule.tick` 仍然安排一小时后再来)。
  两条口径:
  ①**只迁仍然等于旧默认值的那些**。用户自己挑过的间隔不是我们该动的东西;
    「他挑的恰好等于旧默认值」这一档分不开,按从没碰过办 —— 代价是他再改回去
    一次,而反过来(谁都不迁)的代价是这条需求对存量库永久不生效。
  ②**读的时候归一、写的时候盖章**(`save_settings` 把 `settings_rev` 一起存)。
    反过来写 —— 首次访问这个库时就落一条「已迁移」标记 —— 会在标记落下之后、
    设置行写进来之前留一个窗口,那时这份设置永远不会被迁移;而这正是升级的常态:
    老库里设置行早就有了,标记却是新代码第一次碰库才写的。读侧归一和顺序无关。
- **水位和条目必须在同一个事务里提交**(`x_channels.watermark_patch` 把它交回
  成一份 config 补丁,`sync._save_result` 在 `reg.db()` 那一个事务里跑
  `put_items` + `merge_config` + 成功时间戳;`put_items` / `merge_config` 都收
  `conn=`)。原来是 `take()` 当场存一次 —— 那是 fetch 的工作线程,而条目要等主线程
  的 `_save_result` 才写进库,两个独立事务没有共同的成功/失败边界:存盘失败那一轮
  水位已经推进了,这批推文一条都没入库(2026-10-08 审查实测 `stored_items=0`、
  重试取回 0 条)。**这不是提示不准,是丢数据** —— 浏览器通道可以永久跨多天,
  feedgrab 按天重叠也只保得住最新那一天。
- **存盘之前在那个写事务里认一次「这条订阅还是同一个号吗」**(`sync._repointed`,
  `_save_result` 和 `_save_failure` 各调一次)。采集手里那份订阅快照是**发请求之前**
  读的,而这中间用户完全可能把它改指到另一个账号(`save_subscription` 的 `reset`)。
  之后按 `source['id']` 把手里那份写回去就是:旧账号的推文记成新账号的内容、旧账号
  那条 etag/resolved_url 盖在新 feed 上、**旧账号的水位写进新账号那个键** —— 最后
  一条最狠,新账号比那个时间更早的推文从此任何一轮增量都选不到(2026-10-08 审查
  实测:改成 NewExample 之后库里躺着 `OldExample/status/900`、`next_sync_selection=[]`,
  而 crawl 报 ok、新增 1 条)。失败那一侧同理要认:把旧账号那次失败记在新账号头上
  是按别人的毛病把一条好订阅推进退避(最长 24 小时)。作废的那一轮**一个字都不写**
  (条目、水位、成功时间戳一样不写),记进 `summary['repointed']` 进那行阶段文案 ——
  面板上要说得出这一轮为什么是空的。
  **判据必须和这次写入同生共死,不能在 API 入口先 SELECT 一次。** `intake_api.guard`
  (忙就 409)是**早一道**:它只回答"这一刻在跑吗",答不了"我保存的那一瞬间还没在
  跑吗" —— 已经通过检查、还在途中的那个修改请求照样落在采集中间(审查就是这么
  复现的:修改先过 guard,随后管道才起跑)。口径同 collector 那条「判据就在
  UPSERT 自己的 WHERE 里,不许在 Python 那边先 SELECT 一次」和清理脚本那条
  「真正的互斥是那把锁,问管道忙不忙只是早一道」:先查后写在两个进程之间压根不
  成立(kb-web 不是唯一的写入方),而 SQLite 把写入串行化。所以**那个窗口不靠
  进程内加锁去关**,关掉也只是把"永远"缩成"同时"。
  **「待在写事务里」= 存盘那一步自己先 `BEGIN IMMEDIATE`,而且要排在身份那次
  SELECT 之前**(`sync._claim_write`,两个存盘路径各调一次)。光把 `_repointed`
  搬进 `with reg.db()` 块里**不算**:`reg.db()` 交出来的连接**不在事务里**
  (它那个 `BEGIN IMMEDIATE` 在初始化/迁移之后就提交了),而 python 的 `sqlite3`
  在 legacy `isolation_level` 下 **SELECT 压根不开事务、不持任何锁** —— 于是窗口
  只是从「整轮采集」缩成「检查到第一笔写入之间」,另一个连接的修改照样插得进来,
  后果和这道判据本来要挡的事故**一模一样**(2026-10-08 第 3 轮审查实测:检查那
  一刻 `in_transaction=false`,随后那次真 PATCH 以 200 提交,旧账号的
  `/status/900` 照样记给了新账号、`next_sync_selection=[]`;失败那一侧是旧账号的
  错误连同 1800 秒退避落在一条从没被访问过的新订阅上)。拿到写锁之后这期间的
  订阅修改只剩两种结局,**两种的末态都是对的**:①赶在取锁之前提交 —— 这次
  `_repointed` 看得见,整轮作废;②等我们提交之后才落下 —— `save_subscription`
  的 `reset` 把刚写进去的条目归属、config(两条通道的水位)、成功时间戳一并清掉,
  那本来就等于"用户在一轮采集结束之后改指"。**顺序不许反**(先 SELECT 再升级成
  写事务):WAL 下拿不到快照报的是 `SQLITE_BUSY_SNAPSHOT`,`busy_timeout` 管不着
  它,而且那两句之间同样留着一条缝。锁序照旧是维护锁 → feeds.db 写锁,反向没有
  任何路径。
  **判据是身份(`url` / `feed_url`),不是"这一行被动过没有"**:改个名字、换个分组
  不影响这一轮抓的是谁 —— 连这种也作废的话,一次改名就白扔掉一整轮(登录态通道
  一轮十几分钟)。订阅行已经被删掉时同样作废,别把条目归属重新插回去。
  **换链接那次 `reset` 要把 `last_note` 一起清掉**:它说的是旧账号读到哪儿了,
  留着就是在新账号那一行显示「部分同步」—— 前端的状态链在 `last_success` 之前
  先看它,而 `last_success` 已经清了(同轮审查,列为不拦验收项)。
- **区间补抓要把它那段日期交给采集器当下界,而且不许动日常水位**
  (`prefetch(since=...)`,`sync._prefetch_x` 按 `scope.ranged` 传)。日常水位可能
  已经停在那段日期之后,按水位读的话用户点名的那几天一条也翻不到(审查实测:
  传给采集器的仍是日常水位、`added=0`,而日常水位还被进一步推进了)。水位在
  `prefetch` 里就摘掉 —— 只有一处知道「这一轮是区间」,`_save_result` 重建
  validators 那一句顺带是第二道。
- **用户点的那个日期要在一处换算成带时区、且把起点算在内的下界**
  (`x_channels.since_floor`,`prefetch` 用它而不是把日期原样当水位传下去)。
  两件事都在这一处定,交给下游各自解释必然各漂一头:
  ①**时区按项目统一的 Asia/Shanghai,不按部署机器的。** 裸日期到了采集器那头,
    `fromisoformat` 得到的是个**不带时区**的时间,补齐时用的是宿主时区 —— UTC
    机器上这一天的起点落在上海时间 08:00,凌晨 0 点到 7 点 59 的推文一条也翻不到,
    `errors` 还是空的(2026-10-08 审查实测 `TZ=UTC`:同一天四条只收进 08:01 那条)。
    而入库那一侧的 `published`(`_as_published`)和 `_save_result` 的日期筛选固定按
    上海算,下界必须是同一个口径。第二道在 `x_browser._utc`:**不带时区的写法一律
    按项目时区补齐**,以后谁再把裸日期交进来含义也不跟着机器漂。
  ②**起点算在区间里。** 下游那条选择规则是严格大于(日常水位靠它避免重抓上一轮
    最后那条),而"从 10-05 开始"包含这一天 00:00:00 发的那条 —— 直接把日期当水位
    传下去,零点整那条会被当成"已经收过"丢掉(同轮审查在**上海时区**下照样实测到
    `missing_times=['2026-10-05 00:00']`,所以这是和①互相独立的第二个错)。给的是
    **那一天零点前的最后一瞬**(微秒级):闭区间换成等价的排他下界,下游一条规则
    一个字不用改,而推文时间的源精度到毫秒,真实内容落不进这中间。
  **为什么是在这里换算,而不是给下游加一个「包含起点」的开关**:那只修得了浏览器
  通道。feedgrab 的下界是 `X_USER_TWEETS_SINCE`,只认日期而且按 **UTC 的日**算 ——
  把 `2026-10-05` 原样交给它,上海时间那天 0 点到 7 点 59 同样一条拿不到;换算之后
  它 `[:10]` 得到 `2026-10-04`,那段窗口才回来。多出来的前一天由 `_save_result` 的
  日期筛选收口(它按 `published` 的日期比 since/until,本来就是闭区间),重叠的
  条目也早被 `put_items` 按 URL 去重。
