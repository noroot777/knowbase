# 每日日报(kb/daily.py + kb/daily_run.py)

> 从 CLAUDE.md 外移的决策记录。CLAUDE.md 只留硬约束和一行指针,
> 这里是完整的事故形态、实测证据、回归清单和反向验证红数。原文逐字搬运。

- **窗口是「上一份日报的截止时刻 → 这一次的生成时刻」,不是自然日**
  (`daily.next_window`)。日报早上七点出就该覆盖昨天七点到今天七点;按自然日算的话
  昨晚七点之后的一切掉进两份日报中间的缝里,再也不会被任何一份提到。上一份的截止
  时刻记在**它自己的 frontmatter**(`window_until`)里,链条自描述:状态文件删了能
  接上,补一份旧的也不会让后面的窗口错位。
- **算起点时跳过"今天那一份"**:重新生成今天的日报要的是从昨天那一刻起的完整一天,
  而不是从今早那份的截止时刻起的几小时——后者会把上午已经写进旧版本的内容整段丢掉。
  同理,一天里再生成一次就是**重算同一份**(文件名按窗口截止时刻的日期),不是追加一份
  只有几小时的。跳过的那一份正是这一轮要覆盖掉的同名文件,所以跨文件看仍然是首尾
  相接、不重不漏的。
- **没有"最长回溯几天"这种上限**(`daily.next_window`)。上限会把起点往后挪,被挪
  过去那几天的内容再也进不了任何一份日报:服务停四天、上限三天的话第一天整段永久
  消失,而且一行提示都没有。素材太多是**限量**问题——`collect` 按条数截到
  `MAX_ITEMS`,日报里如实写明"窗口内共 N 条,以上列出最新的 M 条",能补;窗口断链
  不能补。`first_days` 只在一份日报都没有、接不上任何截止时刻时才用得上。
- **窗口的截止时刻在同步跑完之后才定下来**(`daily_run._run` 不给 `until`,由
  `generate` 自己取 now):同步能跑几小时,开跑时就把 until 钉死的话那几小时的内容
  谁也不覆盖。
- **筛的是 `published`(内容的生产时间),不是 `indexed_at`(抓取/入库时间)。**
  两者差几天是常态(实测一批 RSS 发布于 09-26、09-29 才抓进来)。按入库时间出日报,
  读到的是"今天抓到了什么",而人要的是"这段时间世界上发生了什么"。
- **时间字符串必须解析成时间再比,不能比字符串**(`daily.parse_ts`)。库里
  `published` 实测四种写法:`2026-09-28 17:08`(2.1 万篇)、
  `2026-06-14T11:29:37+08:00`(1178 篇)、`2026-09-29`(92 篇)、空(1 篇)。同一天里
  `T`(0x54)排在空格(0x20)后面,于是 `2026-09-28T07:00:00+08:00` 字典序上**大于**
  `2026-09-28 08:00`——按字符串筛窗口会把早上七点发的算进八点才开始的窗口。带时区的
  先换算到本地,只有日期的按当天 00:00(那是这种写法唯一能确定的下界)。SQL 只按
  日期前缀粗筛(两头各放一天给时区留余量),精确判断在 Python 里做。
- **发布在窗口之前、这一轮才入库的内容进「补录」**(`Material.late`,判据是
  `indexed_at` 落在窗口内而 `published` 不在)。严格按生产时间筛的代价就是这批东西
  永远进不了任何一份日报;单列一节、单独计数、prompt 里明确要求不混进要点,既不丢
  也不假装它们是新鲜事。没有发布时间的条目同样走这条路,只会出现一次。
- **日报写进 vault(`<vault>/daily/YYYY-MM-DD.md`),不写 kb.db。** kb.db 是随时
  可以删掉重建的索引,而日报是花了模型钱的产物。`daily/` 不在 `kb/config.py` 的
  `SOURCES` 里,所以它不会被索引——否则日报会变成明天日报的素材,自己引用自己。
- **"同步所有内容" = 依次借用 `kb.pipeline` 跑 `crawl/export/index/extract`,
  一个通道一趟。** 不能并发:管道是单例(一把全局运行锁,index/extract 都要单写者
  写 kb.db),同时开只会有一个被拒。条目化/wiki 不跑——日报不读它们的产物,跑一遍
  几十分钟。进度不另做一套展示,只把管道当前阶段的 detail 转述成
  「<通道>:<阶段详情>」,细节仍旧点进同步中心看。
- **超预算(`KB_DAILY_SYNC_BUDGET`,默认 3 小时)就请求停下、直接生成。**
  "今天的日报没出来"比"日报少了两个来源"严重得多。管道被别人占着时每个通道各等
  `WAIT_BUSY`(900 秒),等不到就跳过这个通道,不是整轮失败。
- **用户按的「停止」和超预算是两件事,别共用一个标记**(`stop_requested` /
  `over_budget`,`_halting()` 只管"还同步不同步下一个通道")。超预算的本意就是
  "别再同步了,拿现有内容出报",停在生成之前反而违背它;而用户按停止之后还接着
  生成,等于把一份同步到一半的日报当成功交出去,还要再花一次模型钱——界面上写的
  是"当前阶段结束后停止"。用户停止落 `phase='stopped'`,前端单独一档,不当失败。
- **进了生成阶段就停不了了,这一档要如实拒掉**(`request_stop()` 返回
  `(受理了没有, 说明)`,`STOP_GENERATING`;前端把按钮置灰并写明原因)。
  `daily.generate()` 是"调模型 + 把文件写完"才返回的一整段,受理下来只会承诺
  一件做不到的事——界面写着"这一轮不生成日报",实际照样多出一份、钱也照花
  (2026-09-30 审查实测)。**这个判断和 `_run` 里"进入生成阶段"那一步共用
  `_lock`**,所以两者严格二选一:要么停止先落下、生成整段跳过,要么生成已经
  开跑、停止被拒;分两步写的话停止请求正好挤在中间时,它既看不到
  `phase='generate'`(于是受理)、又赶不上那道检查(于是照样生成)。
- **只停自己起的那一轮管道,而且认的是 run id、不是布尔**
  (`_state['pipeline_run']`,`start_pipeline` 成功之后才登记)。日报允许在别人的
  管道后面排队等,而 `request_stop()` 原来只看"全局管道在不在跑"就去停它——用户
  想取消的是日报的等待,顺手把别人启动的绿泡泡/RSS 同步也中断了(2026-09-30 审查
  实测)。登记之后还要补一次 `_halting()` 检查:停止请求正好落在"等到空闲"和
  "起跑"之间时,那一刻管道还不归我们,它不会去停。
  **布尔只回答"是不是我起的",答不了"现在跑的还是不是我那一轮"**:我们那一轮在
  两次两秒轮询之间跑完、另一项普通同步紧接着拿到全局管道时,布尔仍是 True,而
  `running` 看起来从没断过——停止就落到了别人头上(2026-09-30 复审实测)。所以
  `pipeline.start_pipeline()` 改成返回这一轮的 **run id**(忙时空串,照旧可以当
  布尔用;`pipeline_retry.start_retry_failed` 那条启动路径也要发一个,不然重试
  运行会继承上一轮的身份),`pipeline_state.request_stop(run_id)` 在自己的锁里比
  一次 id、不一致直接不受理(空串 = 面板那个停止按钮的语义:停当前这一轮,不问
  是谁起的)。返回 id 而不是事后读状态,是为了**原子地**拿到身份——事后再读,
  我们那一轮可能已经跑完、读回来的就是别人的。
  `_sync_channel` 的轮询同样**只认 run id 相同的快照**:换人之后既不去停它,也
  不拿它的阶段结果当成我们这个通道的成绩单(审查者那次复现里,日报把别人那一轮
  的失败写进了自己的 entry)。
- **「拿到结果了」= 亲眼看到自己那一轮 `running` 放下的那份快照,或者按 id 查到
  它的收尾记录;两样都没有就如实记 `unknown`,绝不按成功记账。** 中途快照不算
  终态——那时阶段还是 running/pending,拿它数 error 一个也数不出来,于是"被接替"
  和"跑完了全是绿的"长得一模一样,报成功却没有任何证据(2026-09-30 第 3 轮审查
  实测这里硬编码成了 ok)。所以 `pipeline_state` 按 run id 留最近
  `_FINISHED_KEEP`(8)轮的收尾快照(`_end_run` 里在放下 `running` 之前存,
  `run_result(run_id)` 取),被接替的那条路统一去问它。查不到(被更多轮挤出去)
  才落 unknown:日报照样生成——素材是库里已有的那些,不因为一个通道的结果查不到
  就整轮不出报。
- **勾了"先同步"却一个来源都没选,直接拒掉**(`start()` 抛 `ValueError`,
  API 400,前端按钮边上再拦一道)。放过去的话同步阶段静静地什么都不做、面板
  一路"成功",「同步全部并生成」被悄悄降级成「直接生成」,用户不知道素材根本
  没刷新(2026-09-30 审查实测)。"直接生成"不受这条限制——它本来就不同步。
- **有通道没同步成功时,日报照出,但「同步了」这件事不许糊过去**(`_sync_issues()`
  给名单,三处都读它:完成提示 `_set('done', …)`、面板那条 `daily-sync-note` 横幅、
  写进日报文件的 `sync_failed` frontmatter + 正文那段引用块)。降级拿已有内容出报是
  对的("今天的日报没出来"更严重),可**一份"一个新来源都没同步到"的日报和一份"全都
  同步到了"的日报原来长得一模一样**:三个来源全部连接失败,页面上只有一句绿色的
  「日报已生成」,文件里一个字都没提(2026-09-30 审查实测)。**必须写进文件本身**——
  日报是拿走就读的产物(复制、Obsidian、明天翻回来),面板上的提示留不住;toast 也
  换成 info,绿勾等于把降级说成完整成功。口径是 `status != 'ok'`(error/unknown/
  skipped 都算),前端横幅在 `channels` 空时回落到落盘的 `last_run.channels`(重启
  kb-web 之后进程内那份是空的)。
- **没素材时抛 `LookupError`,绝不写一份空日报**——空日报会把这一天"用掉"
  (列表里有了、按钮变成"重新生成"),而真正的原因(还没同步)反而看不见。
- **定时挂在 `pipeline._scheduler_tick` 那一跳上**,不另起线程:它已经每 30 秒跑
  一次了。日报在跑时 `tick` 直接返回,让公众号定时和订阅定时都别去抢管道——
  日报正握着管道依次跑各通道,这时候插一轮进来只会互相拒绝。
- **「已触发」和「已出报」是两个字段,别拿起跑那一刻去记 `last_fired`。** 起跑就
  记的话,一次模型 502 就让用户整天等不到日报,面板上也看不出还会不会再试。
  `tick` 只 `_mark_attempt`(把下一跳推到 `RETRY_AFTER` 之后),收尾时由
  `_finish_schedule` 决定:临时故障同日补 `MAX_RETRIES` 次,成功/没素材
  (`LookupError`)/用户停止一律"今天到此为止"——后三种重试多少次都是同一个结果。
  **记的是起跑那一天(`sched_day`),不是收尾那一刻所在的那天**:同步能跑几小时,
  23:50 起的那一轮 00:50 才收尾,按收尾时刻记会把第二天那一跳也吃掉。
  `_mark_attempt` 要在 `start()` **之前**调:跑得极快的那一轮(不同步、当场报错)
  已经写完收尾状态了,反过来写会把它盖回去。
- **`_raw_settings()` 不碰采集器注册表**:定时线程每 30 秒读一次只为判断"到点没
  有",通道校验放进来的话每一跳都要把所有采集器模块导入一遍。要校验过的那份用
  `load_settings()`。设置里的 `first_days` 只在**一份日报都没有、接不上任何截止
  时刻**时才起作用;老配置里的 `days`/`max_days` 按它读进来(值留着,意思变了)。
- 存下来的通道一个都不认识了(改名/删掉)时回落到默认范围,不是留一份空列表——
  空列表会让定时日报每天都跑出"一个来源都没同步"。
- **日期字符串即文件名,`Date.fromisoformat` 就是那道路径校验**(`_path_for`)。
  API 层另有 `_check_day` / `_check_time` 给 400。写盘走 mkstemp + `os.replace`。
- **阶段落 `skipped`/`stopped` 的通道不算同步成功**(`daily_run._sync_channel`)。
  2026-09-30 实测:51 个大V账号一个都没配 X 桥接,`feeds.sync.collect` 把它们全
  记成 unconfigured、crawl 整个阶段落 `skipped`(「待配置 51 个」)——而这里原来
  只数 `error`,于是 social 通道报的是绿色的「同步完成」,日报里那一行只剩 extract
  的结果,"一条都没抓到"连同原因一起看不见。超预算/被停止时管道落 `stopped`,同理。
  **只看这一轮请求了的那几个阶段**(`SYNC_STAGES`):没选中的阶段一开跑就是
  `skipped`(见 `pipeline.start_pipeline`),全收进来的话每个通道都要多报两句
  「条目化/wiki 未执行」。
- **正文里的出处编号(`[18][23]`)在落盘时就写成链接**(`daily._link_refs`),
  不留到阅读时。日报是拿走就读的产物(复制出去、在 Obsidian 里翻回来),只在
  kb-web 上可点的话换个读法就退回一串对不上号的数字。链接文字保留方括号
  (`[\[18\]](<url> "标题 — 来源·作者")`),转义是因为 Obsidian 会把裸 `[[18]]`
  当 wikilink;**目标一律套尖括号**(`_md_dest`)——库里的 url 实测有带圆括号的
  (`S2589-0042(26)00811-4`),裸写进 `](…)` 会在第一个 `)` 提前收尾。素材清单里的
  标题同理要转义方括号(`_md_text`,库里十来篇带着 `[视频]`)。编号对不上素材、
  那条没有 url、或者已经是一条链接(`[3](http://…)`)时一律原样留着,不编一个出来。
- **每一处出处编号换不换,由渲染器裁决(`kb/daily_refs.py`),这里不写「哪些片段不许
  动」的规则。** 这是**写进文件**的替换,改错了就是把日报原文改坏——页面、复制全文、
  Obsidian 一起受影响,不是渲染层的事。手写规则的路走过三轮,每一轮都被真实渲染器
  找出新的漏网写法:第 1 轮逐行正则漏掉行内代码 `items[1]`(落盘后成了
  `items[\[1\]](<url> "…")`,照着复制的命令当场是错的)和已有链接的文字
  `[版本 [1]](https://…)`(一条链接裂成两个不同目的地);第 2 轮改成字符级 CommonMark
  扫描,又漏掉跨行代码跨度、单引号/圆括号标题、引用式链接、两层以上嵌套的括号目标;
  第 3 轮继续漏掉**多行定义** `[p]:\n  url`、**引用段里的定义** `> [p]: url`、**原始
  HTML 的 `<a>` 与 `<code>`**、**独立缩进代码块**、**autolink 的地址**。**这份清单不会
  收敛**——把它补全等于把一个 markdown 解析器重写一遍。
  所以判据换成:把某一处换成链接,**渲染一遍看结构变没变**。逐个候选各试各的,接受
  的条件是「这一处之外一个字都没动」——代码元素(行内、围栏、缩进、HTML 写的)连内部
  结构逐字不变、原有链接一条不少且文字与目的地不变(autolink 也是链接,一并管住)、
  图片的 alt 与地址不变、多出来的只能是文字为 `[N]` 的出处链接且数量对得上。判不准
  的一律不换:那一处留成纯文本,面板还能照素材清单补上(`enhanceDailyBody`),而改坏
  了的原文没有任何东西补得回来。这样**正确性不再取决于谁更懂 CommonMark**,上面那
  些写法连同「单边转义 `\[1]`」「`[1]: url 多余文字` 不是定义」这类边角一起自己就对了。
  **比对要连 `<code>` 的内部结构一起比,不能只比文本**:往代码里塞一个 `<a>` 并不改变
  文本,拿文本比的话这道闸对"代码内部别建链接"根本不敏感。**另外单数一道链接嵌套**:
  链接套链接在 HTML 里非法,浏览器会把内层提升成兄弟、原来那条的文字被切掉一截,
  而解析器(bs4 那一类)会如实嵌套、外层 `get_text()` 连内层一起算,看着逐字没变——
  `<a href="…">版本 [1]</a>` 被改坏时就是这个形态。
  **裁决器的方言必须和页面那个渲染器一模一样**(`markdown-it-py` 的 `gfm-like`:
  linkify + 表格 + 删除线,`html=True`)。第 4 轮两条拦验收都出在这里 —— 原来按
  CommonMark 裁决,而页面的 marked 默认开着 GFM:①裸网址 `https://e.org/path/[1]`
  在 CommonMark 眼里只是一段文字(于是放行),在页面上却是一条链接,替换完 href 从
  `%5B1%5D` 变成 `%5B%5C%5B1%5C%5D%5D`,点过去是另一个地址(`www.…` 同理);②GFM
  表格 CommonMark 压根不解析,于是**标题里一个裸 `|` 就把那一格从中间劈开**、右边
  「已可用」被挤出表外也看不出来(库里 215 篇文章标题带着 `|`)。所以 `_md_title`
  把 `|` 转义成 `\|`、`_md_dest` 编码成 `%7C`(尖括号拦不住它:GFM 是**先按行拆
  单元格、再解析 inline** 的),两者在表格内外渲染结果一致。
  **但"换个预设名"不等于对齐:裸网址另有一道不依赖解析器细节的超集判据。** 换上
  `gfm-like` 之后 `www.example.dev/path/[1]` 照样被改坏 —— linkify-it 只认一份有限
  的 TLD 名单(`biz|com|edu|gov|net|org|…`),`dev`/`app`/`cloud`/`news`/`technology`/
  `online`/`blog`/`xyz` 全不在里面,而 marked 对 TLD 不做任何限制:8 个后缀真实页面
  上一测一个准,文字和 href 双双变样、点过去是另一个地址(2026-09-30 第 5 轮审查
  实测)。**补几个后缀就是在维护一份名单**,下一个没见过的照样漏,何况 path 边界、
  backpedal 那几处还有同类缺口 —— 两个 markdown 实现永远不可能逐位对齐。所以:
  ①`_MD.linkify.tlds(r'[a-z0-9\-]{2,}')` 把 TLD 放宽成"任意",让主裁决器的基线别
  明显窄于 marked(不放到一字符是因为那会把 `3.2`、`v1.5` 这类版本号也认成域名 ——
  过度识别只是少加一条链接,不改坏谁);②真正兜底的是 `_autolinked`:marked 的
  autolink 起手式只有 `www.` 和 `scheme://`、尾巴是 `[^\s<]*`(不跨空白、不跨 `<`),
  于是「这个编号落在某条裸网址里」**必然**满足「往左数到最近的空白或 `<` 为止,这
  一段出现过 `www.` 或 `://`」——命中就不换。反过来不成立,所以它是超集,多拒几处
  换"再不会有下一个漏网的后缀"。这两道**不是等价的两份实现**:实测只留 ② 而把 TLD
  退回默认名单,回归全绿;只留 ① 去掉 ②,`www.x.y`(一字符 TLD)当场红。真实日报
  21 KB / 80 处候选,被 ② 挡下 0 处。
  **② 那条起手式正则必须大小写不敏感**(`re.I`)。marked 那条 url 规则本身带 `i`
  标志,`WWW.`/`Www.` 照认。漏掉大小写时两道保护会同时落空 —— 起手式大写、后缀又
  在 ① 认不出的范围里(实测 `WWW.example.中国/path/[1]`、`WWW.x.y/path/[1]`),原
  网址当场被改坏,而小写的同一条因为 ② 命中 `www.` 好好的(2026-10-01 第 6 轮审查
  实测)。**这也说明 ① 会顺手遮住 ② 的缺口**:上一轮的大写样本用的是 `E.ORG`,
  linkify 自己就认得,于是大小写漏判一条测试都没红 —— 所以回归里另有一条直测
  `_autolinked` 的,10 种起手式大小写各一次,绕开这层遮掩。
  **代价是过度保护,已知且接受**:`_autolinked` 只往左看一段没有空白的文本里有没有
  `://`,分不出那是裸网址还是**一条已经收尾的 markdown 链接的目标** —— 于是
  `[产品](https://example.org/keep)[1]` 紧跟着的那个出处不会被写成链接(页面上前端
  兜底照样补得出,拿走 md 文件就是纯文本)。要收窄就得回去解析 markdown 判断"这个
  `://` 在不在链接目标里",而 URL 的 path 里本来就可以有平衡圆括号、`)` 当不了终止
  符 —— 那正是前五轮反复证明会漏的那条路。少一条链接谁也不会被骗,改坏一条原网址
  会把人送到另一个地址:这个方向上宁可多拒。
  **判据是整份渲染结果逐字比,不是挑几类元素比。** 原来只收集代码/图片/链接,
  「表格挤错列、一整格内容丢了」「不可见的引用定义被显示成正文」这类改动全部漏过
  —— 嘴上说"这一处之外一个字都没动",实际只看了那几类。现在的做法:要换的地方先
  换成**哨兵链接**(私用区字符当链接文字,目标和标题跟真链接一模一样),渲染后把
  哨兵链接**整组**还原成原文那一段(合并写法 `[1、2]` 换出来是两条相邻链接,一条条
  还原成 `[1][2]` 就跟原文对不上了),要求和原文的渲染结果**逐字相同**;再确认真
  链接版和哨兵版只差链接文字那一处。用哨兵而不是按 (文字, 地址) 去认,是因为原文
  里本来就有一条一模一样的链接时,猜哪条都说不准。
  **另外单拦一道:哨兵链接不许落在 `<a>`/`<code>`/`<pre>` 里面。** 这两种情况还原
  之后照样逐字相同(容器本身没变),可链接套链接浏览器会拆开(点击目标错位)、代码里
  冒出链接更是把别人照着复制的命令改了。
  **一组里没有素材的那几个编号也要打哨兵**(只是不做成链接)。还原时只把第一个哨兵
  换回整组原文的话,`[1,9]` 里那个没素材的 `9` 生成的 `[9]` 还留在旁边,还原结果成
  了 `[1,9][9]`、跟原文对不上,于是**整组被拒**——有素材的那个编号也白白留成纯文本,
  页面上前端兜底还能补,拿走 md 文件就只剩一串数字(2026-09-30 第 5 轮审查实测)。
  **两边都要过一次解析器再比**(`_norm`):`<img …>` 与 `<img …/>` 这种序列化差异
  不是"内容变了",按原始字符串比会白白漏掉一条出处。
  依赖是 `markdown-it-py[linkify]`(linkify 那个 extra 不能省,少了它裸网址就回到
  CommonMark 的盲区)+ bs4。**它得是显式依赖**:原来只是 rich 的传递依赖,那条链断
  了这里就崩。代价是渲染开销,所以**先整篇一起试一次**(一篇日报的出处多半没有一处
  落在代码或已有链接里,这条路只渲染三遍,实测 21 KB / 80 处 50 ms);过不去才逐个
  各试各的(同一份 2.3 秒),**真遇到才付**。

## 上报账本:日报生成之后再抓到的内容再也不会出现(2026-10-10)

**症状**(仓库主人原话):"日报只要生成后,在重试失败项或加入某些源后就不变了"。

**旧实现的那条缝。** 两个取材桶都是"时间窗 + 取最新 N 条":

- 要点桶 = `since < published <= until`,按 `published` 降序取 `MAX_ITEMS`(120)条;
- 补录桶 = `since < indexed_at <= until` 且 `published <= since`,按 `indexed_at`
  降序取 `LATE_ITEMS`(30)条。

一个条目只有在某个窗口里挤进这两个 top-N 之一才会被报道。**没挤进的在下一个窗口里
两个桶都选不到** —— 它的 `published` 和 `indexed_at` 都已经早于新的起点,于是掉进
两个桶中间的缝里永久消失,而且一行提示都没有。库里也**没有任何一列**记着"这一条报
过没有",所以落选之后不可恢复。

**实测证据**(生产库 2026-10-10,`data/kb.db` 只读副本):

| 日报 | `docs`/`total` | `late`/`late_total` | 补录丢弃 |
|---|---|---|---|
| 10-02 | 1 / 1 | 30 / 40 | 10 |
| 10-04 | 2 / 2 | 30 / 137 | 107 |
| 10-09 | 69 / 69 | 30 / 506 | 476 |
| 10-10 | 82 / 82 | 30 / 679 | **649(96%)** |

有几天的 `docs` 是 1~2 条 —— 也就是说那几天**几乎全部**内容都走补录这一档,而这一档
96% 被丢掉。这不只是"重复内容被滤掉":10-10 那份丢掉的 607 条里,**141 条的发布时间
早于整条日报链的起点(2026-09-29)**,也就是说它们从来没进过任何一份日报的要点桶,
补录那 30 个席位是它们唯一的机会,落选即永久消失。

**症状和这条缝的对应关系。** 2026-10-10 08:07 出了一份日报;10:18 和 10:27 两批重试
抓回 28 篇 RSS 文章,发布时间全部落在 10-09 全天到 10-10 07:54 之间 ——
**一条都不晚于那份日报的 `window_until`**。于是:

- 不手动重新生成:下一份日报的 `since` = `2026-10-10 08:07:14`,这 28 条的 `published`
  全都 ≤ 它 ⇒ 全部只能走补录,和另外几百条抢 30 个席位;
- "新加一个订阅"更糟:`history_floor` 会把该源最近 5 天的存档一次交出来,**整批**都是
  "发布时间早于当前窗口起点"的形态,上百条抢同样的 30 个席位。

**`indexed_at` 还答不出"这一轮才入库"。** 重新导出(补译、补抓正文)会刷新它,所以老
文章每天都重新算一次"刚入库"。按"窗口内发布 + 当时已入库"去反推历史上报过什么,
9 份日报只认得出 **217** 篇 —— 其余全被churn 冲掉了。这也是补录桶长期被旧文占满的
原因(CLAUDE.md 历史深度那节记过同一现象的另一面)。

**修法:判据换成"这一条被哪一份日报带走过"。** 新表 `daily_carried(path, day,
carried_at)`,`_UNCARRIED` 子查询进两个桶的 WHERE。于是:

1. 没带走的条目**留在队列里**,下一份接着带 —— 条数上限从"丢弃线"变成"每份带多少条"
   的限流,日报正文里也写明"没列出的留在队列里,下一份日报接着带";
2. 带走过的再也不是候选 —— 顺带治好了 `indexed_at` churn 把旧文反复推进补录那件事;
3. 补录桶不再需要 `indexed_at`,改成"发布早于窗口起点 + 没带走过 + 发布时间在
   `BACKLOG_DAYS`(30 天)内"。那个 30 天是**编辑口径**(日报不回头报一个月前发布的
   东西),和 `MAX_ITEMS`/`LATE_ITEMS` 那种限流是两回事:超出的条目在成为候选之前
   就被排除,**因此也不计进 `late_total`、不计进面板那个计数** —— 别把它说成
   "照旧排队",那会让人以为所有补抓最终都会被报道。

**四条配套的硬口径:**

- **盖章排在落盘之后。** 方向是不对称的:章没盖上只是这批素材下一份再出现一遍(多报
  一次,看得见);落盘失败而章已经盖上,这批素材再也选不到,**不可恢复**。
  `mark_carried` 失败时只往结果里记一句 `carry_error`,不把已经落盘的这一轮带崩。
- **重新生成同一天要放过它自己盖的那些章**(`_UNCARRIED` 的 `c.day<>?`)。同名文件
  是整份覆盖的,排除掉自己的章等于新版本把早上已经报过的内容整段丢掉。
- **删一份日报要先放回、再删文件**(`daily.delete`)。反过来的话放回失败时文件已经没
  了而章还盖着,那批内容两头落空。按这个顺序最坏情况只是下一份多报一遍。
- **面板那个计数传 `day=''`,一个章都不排除**(`daily.pending`)。它问的是"进过**任何**
  一份日报没有";传当天日期的话今天刚带走的内容会被重新数成新素材,面板上永远有一个
  消不掉的数字。判据和真取材共用 `_select`,所以"面板说有 7 条"和"生成时带走 7 条"
  是同一个结论。

**这个计数长在生成按钮里,不贴在覆盖区间那行字后面**(`daily.js` 的
`renderDailyGenButton`)。它回答的是"点这颗按钮会得到什么",而覆盖区间那行回答的是
"这一份覆盖哪一段" —— 两件事挨在一起会串台(第一版就贴在那儿,仓库主人当场说
"容易让人误解")。配套三条:

- **按钮的名字跟着"目标那天有没有日报"走**:有就是「重新生成日报」(点下去覆盖它,
  所以还会弹一次确认),没有就是「生成日报」。写死成"重新生成"的话第一次用的人会
  以为自己漏了一步。**「这一次写到哪一天」只有一份口径**(`dailyTargetDate()`):
  按钮叫什么、要不要弹覆盖确认问的是同一件事。
- **三种状态三种说法**:有积压 `+N 条新内容`(品牌深绿)、0 条 `没有新内容`(灰)、
  **查不出来整颗藏掉** —— 那一档既不是"有"也不是"没有",写成「没有新内容」是在把
  "不知道"说成"没有"。自定义区间时同样藏掉(后端算的是默认区间那一段)。
- **只靠字色区分,不画底色药丸。** 实测 `--brand-soft`(#DFF0E9)和 ghost 按钮底
  (#EAEEED)差不到 2%,画了等于没画,留着就是一行看不见的声明。
- 删一份日报会把它带走的条目放回队列,所以 `deleteDailyReport` 要连 `loadDailyWindow()`
  一起调 —— 不调的话按钮上还写着"没有新内容",而此刻明明又有了。

旧名字「直接生成」跟着全仓换掉:面板按钮、空同步范围时前后端两处提示、定时那行
「每天 08:00 直接生成」(改成"只用已入库的内容生成")。

**空闲那一跳要把这个数字问回来**(`daily.js` 的 `refreshDailyPending`)。素材是从
**外面**进来的 —— 同步中心跑完一轮、CLI 补抓、定时同步,页面一个事件都收不到。只在
"日报从运行变成完成"那一跳重读的话,数字会一直停在打开页面那一刻(审查实测:后台插进
一篇,页面仍写着「没有新内容」,要点一次「改区间」再「接上一份日报」才更新)。那一跳
**只更新数字、不碰两个时刻输入框** —— 默认区间的截止时刻是"此刻",每跳重填会让展开着
的「改区间」里的值自己往前跳。

**补录席位要给最老的留几个**(`LATE_DRAIN`=10)。只按"新的在前"排的话,持续有新内容
进来时积压里最老的那些永远排不上队 —— 账本保住了它们、席位分配却让它们等到被
`BACKLOG_DAYS` 挡掉,等于换一种方式再丢一次。所以 `LATE_ITEMS`(60)里末尾 10 个席位
固定给发布得最早的那几条(它们离 30 天那条线最近)。

**启用那一刻的一次性盖章**(`daily_carry.ensure_ledger`)。
不盖的话账本一启用,库里两万多篇历史文章全都算"没上报过":实测 `BACKLOG_DAYS=30`
时第一份日报的补录候选是 **1918** 条,要几十份日报才排得空 —— 而那些内容在旧实现下
早就永久落选了,翻出来不是修复、是倒灌。

**判据有两维,缺一不可**:

- **盖不盖,看「它到得比最后一份日报还晚吗」**(`indexed_at > 链头的 window_until`)。
  **这一道承重。** 第一版只看 `published`,自由工作流审查第 1 轮当场打回:账本是
  **懒初始化**的,第一次真正跑到它可能已经是升级之后好几天 —— 用户先点「重试失败
  项」补抓一批、再打开日报面板,那一批的发布时间多半早于链头,于是**正好是这次要救
  的那批内容被永久写死**。实测复现:补抓一篇发布于前天的文章,首次初始化后
  `pending=0`、`generate` 抛「没有未上报过的新内容」、之后每一天也都选不到(`#seed`
  对任何真实日期都满足 `UNCARRIED` 的排除条件,而 `release()` 明确不放这批章)。
  同一条路还覆盖定时那条入口 ——「先同步再生成」是同步**跑完**才进 `generate()`,
  初始化必然晚于补抓。`indexed_at` 只会往前走,所以"到得晚"证得死;反过来老文章重新
  导出也会刷新它,那只是多报一遍,方向是安全的那一边。
- **盖到哪一天,看它的 `published` 落在谁的窗口里** —— 不能一律 `#seed`。同一天重新
  生成时 `UNCARRIED` 放行的是**这一份自己**盖的章;统一记 `#seed` 的话,把区间改回
  某份旧日报再重新生成,它原有的报道会被整份覆盖掉、一条不剩(同一轮审查实测:甲文
  在原文件里,覆盖后只剩新补抓的乙文,`docs=1`)。所以:落在某一份窗口里的记那一份的
  日期,比链起点还早的(以及没有发布时间的)记 `#seed`,**发布在链头之后的不盖**
  (属于下一份的要点桶),**落在链条缺口里的也不盖**(那一份已经不在了,它本就该回到
  队列)。
- **「发布在链头之后不盖」那一档是冗余带**(定点注入红 0 条):链条最后一个窗口就止于
  链头,这种条目在按窗口找归属时本来也落 `None`。留着是构造上的理由 —— 这一档该被
  显式处理过,而不是靠读代码的人去推 `next()` 的默认值。如实记着。
- **比 `published` 必须 `parse_ts` 之后再比**(四种写法,同一天里 `T` 排在空格后面);
  `indexed_at` 库里只有一种写法,可以直接比字符串。
- **一份日报都没有时**没有"链头"可言:分界线取 `first_days` 天前(那正是第一份日报的
  窗口起点),到达分界取"此刻" —— 库里现有的一律算存量。那时确实没有任何证据说明哪
  一条被报道过,而让头一份日报去回顾整个存档只会是一份噪音。
- 盖章 + 写 `daily_state.carry_epoch` 在**同一个 `BEGIN IMMEDIATE` 里**,并且在锁里
  重新查一次那个键(两个进程同时首访时,后一个在锁里就看得见前一个盖的章)。分类在
  锁外做(两万行读一遍、纯内存),锁里只落盘。

**落盘+记账 与 放回+删文件 要整体互斥**(`daily_carry.commit_lock`,`data/` 下自己
一个 lockfile)。两段各自内部的顺序只管**自己失败时往哪边倒**,管不住两段交错:审查
第 1 轮用线程屏障实测到这个顺序 ——

```
生成:_write(今天.md) 完成
删除:release(今天) → unlink(今天.md) → 返回 True
生成:mark_carried(今天, paths) → 成功
```

末态是"记着已上报、却没有任何日报文件"的一批条目,两头落空。阅读区那颗删除按钮在
生成期间本来就能点,所以不是理论上的交错。**不借用 `kb.maintenance` 那把维护锁** ——
那一把在一轮大索引里会被攥住几分钟,等在它上面等于让模型已经出完稿的那一轮卡在收尾;
这把只圈毫秒级的两段,不和任何别的锁嵌套。`delete()` 里的 `is_file()` 也要圈进锁,
否则判断和删除之间又开一道同样的缝。

**不取维护锁。** CLAUDE.md 那节的判据是"写哪张表 + 写不写 vault 里的文章文件":
`daily_carried` / `daily_state` 只有日报自己读写,`daily/*.md` 不在 `SOURCES` 任何一棵
树下(清理脚本和索引都碰不到它),所以日报这条路本来就在那把锁的射程之外 —— 加了账本
也没变。反过来说也不能加:`generate` 中间是一次几分钟的模型请求,把它圈进那把跨进程
独占锁里会把面板同步、定时同步和日报一起冻死,而那节自己写着"模型请求留在锁外"。

**账本那一半在 `kb/daily_carry.py`**,只因为行数(`kb/daily.py` 到了 700 行上限)。
它不认识 vault 里的日报文件、也不认识取材口径,日报链由 `kb.daily._report_chain()`
从各份日报的 frontmatter 读出来传进去,两个模块因此不用互相 import。`STAMP` /
`parse_ts` 跟着搬过去,`kb.daily` 原样绑回自己的模块全局,所以 `daily.parse_ts`
这些既有写法照旧有效。**测试里必须把 `daily_carry.DATA_DIR` 指到 tmp**,不指的话
那把提交锁会去 flock **生产** `data/` 下的 lockfile(同维护锁那条)。

## 迁移盖章的归属:只认那一份自己的素材清单(自由工作流审查第 2 轮)

上一轮把盖章从"一律 `#seed`"改成了"落在某一份窗口里的记那一份",修的是"重新生成旧
日报会抹掉它原有的报道"。**按窗口推断这件事本身是错的**,审查第 2 轮用两条独立反例在
两个相反的方向上各打中一次:

| 形态 | 按窗口推断的结果 | 后果 |
| --- | --- | --- |
| 旧日报里的**补录** | 发布时间早于那一份的窗口 ⇒ 当成链条之前的存量、记 `#seed` | `#seed` 对任何一天的重新生成都满足排除条件,于是覆盖那一份时它一条都选不回来,**已经交付的内容当场消失** |
| 窗口里**当时装不下**的 | 发布时间落在窗口里 ⇒ 记成"那一份带走了" | 从此任何一份日报都选不到 —— **原任务要修的那条缝在迁移这一步原地复发** |

两处都不可恢复。判据因此换成**那一份日报自己的素材清单**(`daily._carried_keys` 从文件
正文里读回来,`daily._doc_key` 是素材身份的唯一口径、盖章和读清单两侧共用)。清单里认
不出的条目一律不盖章:方向按元规则取宽的那一边,放回队列最多多报一遍,盖错了是永久写死。

### 清单是拼装出来的,所以解析要顶住真实写法

实测生产库 10 份日报共 633 条清单条目,解析一版一版收紧:

| 写法 | 踩法 | 口径 |
| --- | --- | --- |
| 裸 `](url)` | `_md_dest`(套尖括号)是后来才加的,**2026-09-30 那一份整份都是裸写法** —— 只认尖括号就读不出它 90 条的归属 | 括号里那一截剥掉尖括号壳之后统一过 `_doc_key` 归一(`_md_dest` 幂等) |
| 账号名里带圆括号(`歸藏(guizang.ai)`) | 贪婪吃到行里最后一个 `)`,url 被截成 `<url>) — 大V观点·歸藏(guizang.ai` | `.+?` 配上「右括号后面紧跟分隔符或行尾」这个锚点 |
| url 自己带圆括号 | 那正是 `_md_dest` 存在的理由 | 非贪婪会先在它那里试一次、锚点不成立再往后退 |
| 标题跨行**而且带空行** | 大V观点的"标题"是推文正文前 500 字符;实测 2026-10-10 那一份 31 条都是这个形态,按行各认各的全判成认不出来 | 除编号开头的行,其余一律并回上一条,**不拿空行当分界** |
| 清单末尾那句引用块 | 跟着并进最后一条 | 链接那条正则**匹配到分隔符就收工**,不要求吃到字符串末尾 |

收紧过程(生产库 633 条里对得上的):裸写法 + 尖括号 431 → 跨行并回 436 → 不依赖结束
标记 468。剩下 165 条**对不上是对的**:按 url 去库里模糊找是 0 篇,它们已经被
`scripts/feed_trim_history.py` 那条存量清理从索引里删掉了,压根不可能再成为候选。

分隔符 `_REF_SEP` 抽成一份,`_page` 拼 refs 和 `_carried_keys` 解析共用 —— 两边各写一个
就是等着漂。

### 已经盖过章的库要跟着重算(`SEED_REV`)

账本是**懒初始化**的:盖过章的库直接走快路径返回。于是"修好的归属"只对从空库开始的人
成立,而最需要修的恰好是按旧算法盖错过的那些库。所以盖章算法带一个版本号
(`daily_carry.SEED_REV`),版本不一致时**整张表重算**。重算安全的理由是构造上的:每一份
日报带走了什么一直记在它自己的文件里,`mark_carried` 记的就是清单里那一批,所以重算得到
的和当初记下的是同一份;读不回来的按不盖章办(多报一遍,不写死)。**改盖章算法必须把这个
版本号加一。**

反过来钉一边:`test_seeding_is_idempotent` 末尾补了一句 —— 盖过章之后真生成的那几份,
不许被"重算"顺手清掉(版本一致时压根不进那条路)。

### 盖章也要和删除互斥

上一轮的提交锁只圈了"落盘 + 记账"和"放回 + 删文件"。**首次盖章是第三段**:读完日报链之后
另一个页面把其中一份删掉(`release` 放回它的章 + 删文件),这边再按过期的清单把那些章补
回去 —— 那一份日报已经不在了,它带走过的内容从此两头落空。审查用线程屏障实测到这个顺序:

```text
初始化:读取日报链,保存日期和窗口
删除:release(日期) -> unlink(日报文件) -> 返回 True
初始化:仍按旧的日报链插入迁移记录,并写入 carry_epoch
→ report_exists=false, ledger={"source/rss/race.md":"2026-10-10"}, material_after_deletion=[]
```

`BEGIN IMMEDIATE` 只保护账本那个事务,保护不了**之前**读进来的 vault 文件。所以
`ensure_ledger` 整段(读日报 → 分类 → 落账本)进 `commit_lock`。两处配套:快路径那次状态
读留在锁外(面板每一跳都走它,常态 0ms);**锁内要再问一次状态** —— 不问的话,前一个进程
盖完、之后又真生成过日报的那些章会被这边的 `DELETE FROM daily_carried` 一起清掉。
模型请求照旧在锁外。


675 这个数字是**这次修复的直接后果,不是缺陷**:它们是 09-29→10-10 这段里发布、而旧实现
按"时间窗 + 取最新 N 条"静默丢掉的内容(10-04/05/06/08 四份日报各只列了 31~32 条,其中

`BACKLOG_DAYS`(30 天)之内。

方向换一点去重。
