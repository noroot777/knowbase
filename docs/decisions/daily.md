# 每日日报(kb/daily.py + kb/daily_run.py)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束(原 CLAUDE.md「每日日报(kb/daily.py + kb/daily_run.py)」)

- **窗口是「上一份日报的截止时刻 → 这一次的生成时刻」,不是自然日**(`daily.next_window`)。上一份的截止时刻记在**它自
  己的 frontmatter**(`window_until`)里,链条自描述。**算起点时跳过「今天那一份」**,所以一天里再生成一次就是**重算同
  一份**。**没有「最长回溯几天」这种上限** —— 上限会把起点往后挪,被挪过去那几天再也进不了任何一份日报;素材太多是**限
  量**问题,窗口断链不能补。**截止时刻在同步跑完之后才定下来。**
- **「这一条上报过没有」按账本判(`daily_carried`),不靠时间窗推断** —— 没带走的留在队列里,下一份接着带;「时间窗 + 取
  最新 N 条」会让落选条目在下一个窗口里两个桶都选不到,静默永久丢失。三条不许动:
  ①生成一份是**放回 → 落盘 → 盖章**三步:**先把这一天上一版的章放回**(否则被挤出清单的旧素材既不在文件里、又记着已上
    报),盖章再排在落盘**之后**(章盖不上只是下一份多报一遍,看得见);
  ②「落盘+记账」与「放回+删文件」整体互斥(`daily_carry.commit_lock`),启用时的一次性盖章也在这把锁里,**删一份日报要
    先盖章再放回**(它带走过什么只写在那个文件里);
  ③盖章两维判:**到达分界线**(`indexed_at` 晚于它的不盖;**分界线一旦钉下就不许再往前挪**)+ **那一份自己的素材清单**
    (`daily._carried_keys`;按窗口推断会把补录记成存量、把当时装不下的记成报过了,两处都不可恢复)。
  **改了盖章算法要把 `SEED_REV` 加一**(否则已经盖错过的库永远走快路径),**而那一趟只重算归属**;**清单解析也算盖章算
  法**,改了它同样要加一。**清单上露过面的内容一律不许判成「链条之前的历史存量」**(那一道兜底把代价从「永久写死」降到
  「多报一遍」);它只用来**否决**终态,不拿来盖归属,**而且那份原文要独立于切分**(`PastReport.text` 是整份正文)。
  **清单起点按抬头自己声明的条数挑**(`## 素材清单(N 条)`,切出来得恰好是 N 条)—— 这几个字在文章标题和推文里都出现
  过,按位置找必然在某个方向上错,而错一次是**一份日报里好几条一起**写死。
- **人工丢弃走 `#drop`,它和 `#seed` 不是一类东西**(`daily_carry.mark_dropped` / `DROP_DAY`)。它回答的是「这几个来源
  的内容别再进日报了」,判据是人当场拍的 —— **库里没有任何东西能把它算回来**。三条不许动:①**盖章算法升版重算时必须把
  `#drop` 留下**(`seed_locked` 的 `DELETE … WHERE day<>?`):`#seed` 的证据是各份日报自己的素材清单、重算得到的是同一
  份,而丢弃跟着被清掉就是把几百条静默倒灌回队列,面板上一切正常;②**只增不改**,不许照 `mark_carried` 的
  DELETE-then-insert 写(那边是「重新生成同一天要整批替换」,而丢弃分几次丢就该累加,照抄会让第二批把第一批静默放回);
  ③`mark_carried` / `release` 一律拒掉 `#seed` 和 `#drop` 这两个保留值。**统计按实际写入行数报**,不按名单长度报。
- **停用一个来源(`config.Source.enabled=False`)= 停止收新内容,库里已有的一个都不动。** 要两处配合:
  `scanner.scan_all` 不再遍历它,**而 `store.remove_missing_documents` 必须豁免它的存量** —— `scan_all` 的产出同时是
  「哪些文件还活着」的唯一依据,只停遍历等于告诉下一轮索引「这些文件全没了」,库里那一批连 chunk、向量、标签一起被删,
  面板上只多一个 removed 计数,而 vault 里的文件明明还在。豁免判据落在那个函数自己身上(它是唯一的删除口,三个调用方
  `pipeline_stages` / `cli` / `scripts/feed_trim_history` 都过它)。**名字、来源组、别名、`PRIMARY_SOURCE_NAMES` 一个
  都不许动** —— 停用只管「收不收新的」,搜索、问答、图鉴和显式按来源查照旧要看得到存量。
- **筛的是 `published`(内容的生产时间),不是 `indexed_at`。** **时间字符串必须解析成时间再比**(`daily.parse_ts`,库里
  实测四种写法)。SQL 只按日期前缀粗筛(两头各放一天),精确判断在 Python 里做。
- **发布在窗口之前、这一轮才入库的内容进「补录」**(`Material.late`),单列一节、单独计数、prompt 里明确要求不混进要点。
  没有发布时间的同样走这条路。
- **日报写进 vault(`<vault>/daily/YYYY-MM-DD.md`),不写 kb.db。** `daily/` 不在 `SOURCES` 里,否则日报会变成明天日报的
  素材。
- **「同步所有内容」= 依次借用 `kb.pipeline` 跑四个阶段,一个通道一趟。不能并发**(管道是单例)。条目化/wiki 不跑。
  **超预算(默认 3 小时)就请求停下、直接生成。**
- **用户按的「停止」和超预算是两件事,别共用一个标记**(`stop_requested` / `over_budget`)—— 超预算的本意就是「拿现有内容
  出报」,而用户停止之后还接着生成等于把半成品当成功交出去。
- **进了生成阶段就停不了了,这一档要如实拒掉**(`request_stop()` 返回 `(受理了没有, 说明)`)。**这个判断和「进入生成阶
  段」那一步共用 `_lock`**,所以两者严格二选一。
- **只停自己起的那一轮管道,而且认的是 run id、不是布尔**(`_state['pipeline_run']`;布尔答不了「现在跑的还是不是我那一
  轮」)。`start_pipeline()` 返回 run id,`request_stop(run_id)` 比一次 id;`_sync_channel` 的轮询同样**只认 run id 相同的
  快照**。
- **「拿到结果了」= 亲眼看到自己那一轮 `running` 放下的那份快照,或者按 id 查到它的收尾记录;两样都没有就如实记
  `unknown`,绝不按成功记账。** 中途快照不算终态。`pipeline_state` 按 run id 留最近 8 轮收尾快照。
- **勾了「先同步」却一个来源都没选,直接拒掉**(API 400)—— 放过去的话「同步全部并生成」被悄悄降级成「直接生成」。
- **有通道没同步成功时,日报照出,但「同步了」这件事不许糊过去**(`_sync_issues()` 给名单,三处都读它)。**必须写进文件本
  身**(`sync_failed` frontmatter + 正文引用块)—— 日报是拿走就读的产物。toast 换成 info,绿勾等于把降级说成完整成功。
- **没素材时抛 `LookupError`,绝不写一份空日报**(空日报会把这一天「用掉」)。
- **定时挂在 `pipeline._scheduler_tick` 那一跳上**,不另起线程;日报在跑时 `tick` 直接返回。
- **「已触发」和「已出报」是两个字段,别拿起跑那一刻去记 `last_fired`。** `tick` 只 `_mark_attempt`,收尾时由
  `_finish_schedule` 决定:临时故障同日补 `MAX_RETRIES` 次,成功/没素材/用户停止一律「今天到此为止」。**记的是起跑那一
  天**(23:50 起的那一轮 00:50 才收尾)。`_mark_attempt` 要在 `start()` **之前**调。
- **`_raw_settings()` 不碰采集器注册表**(定时线程每 30 秒读一次)。存下来的通道一个都不认识了时回落到默认范围,不是留一份
  空列表。
- **阶段落 `skipped`/`stopped` 的通道不算同步成功**,**只看这一轮请求了的那几个阶段**(`SYNC_STAGES`)。
- **正文里的出处编号(`[18][23]`)在落盘时就写成链接**(`daily._link_refs`),不留到阅读时。链接文字保留方括号并转义
  (Obsidian 会把裸 `[[18]]` 当 wikilink),**目标一律套尖括号**(`_md_dest`,库里的 url 实测有带圆括号的)。
- **每一处出处编号换不换,由渲染器裁决(`kb/daily_refs.py`),这里不写「哪些片段不许动」的规则** —— 手写规则的路走过三
  轮,每一轮都被真实渲染器找出新的漏网写法,**这份清单不会收敛**。判据换成:把某一处换成链接,**渲染一遍看结构变没变**,
  接受的条件是「这一处之外一个字都没动」。**比对要连 `<code>` 的内部结构一起比**,并**单数一道链接嵌套**。**判据是整份渲
  染结果逐字比,不是挑几类元素比** —— 要换的地方先换成**哨兵链接**,渲染后把哨兵**整组**还原,要求和原文的渲染结果**逐字
  相同**。**一组里没有素材的那几个编号也要打哨兵。两边都要过一次解析器再比**(`_norm`)。**哨兵链接不许落在
  `<a>`/`<code>`/`<pre>` 里面。**
- **裁决器的方言必须和页面那个渲染器一模一样**(`markdown-it-py` 的 `gfm-like`,`html=True`)。**但「换个预设名」不等于对
  齐**:linkify-it 只认一份有限的 TLD 名单而 marked 对 TLD 不做限制。所以①把 TLD 放宽成任意;②真正兜底的是 **`_autolinked`**
  —— marked 的 autolink 起手式只有 `www.` 和 `scheme://`、尾巴是 `[^\s<]*`,于是「这个编号落在某条裸网址里」**必然**满足
  「往左数到最近的空白或 `<` 为止出现过 `www.` 或 `://`」。**那条起手式正则必须大小写不敏感**(`re.I`),而且**① 会顺手遮
  住 ② 的缺口**,所以回归里另有一条直测 `_autolinked`。**代价是过度保护,已知且接受。**
- **先整篇一起试一次**,过不去才逐个各试各的。依赖是 `markdown-it-py[linkify]`(那个 extra 不能省)+ bs4,**得是显式依赖**。
- **加链接之前生成的那些日报由面板兜底**(`daily.js` 的 `enhanceDailyBody`),**读的是渲染之后那个 `<ol>`,不是 markdown 原
  文**(`dailyRefMap`)。**认的编号写法要和落盘那条路一致。** 粗筛文本节点别用带 `g` 的正则。
- **前端那条横幅有两个来源,清空时必须认一下是谁写的**(`dailyErrorKind`)。不在日报页时也慢速轮询状态(60/120 秒)。
- 详细见 `docs/decisions/daily.md`。

## 事故形态与实测证据

- **窗口是「上一份日报的截止时刻 → 这一次的生成时刻」,不是自然日**
  (`daily.next_window`)。日报早上七点出就该覆盖昨天七点到今天七点;按自然日算的话
  昨晚七点之后的一切掉进两份日报中间的缝里,再也不会被任何一份提到。上一份的截止
  时刻记在**它自己的 frontmatter**(`window_until`)里,链条自描述:状态文件删了能
  接上,补一份旧的也不会让后面的窗口错位。
- **算起点时跳过"今天那一份"**:重新生成今天的日报要的是从昨天那一刻起的完整一天,
  而不是从今早那份的截止时刻起的几小时——后者会把上午已经写进旧版本的内容整段丢掉。
  同理,一天里再生成一次就是**重算同一份**(文件名按窗口截止时刻的日期),不是追加一份
  只有几小时的。跳过的那一份正是这一轮要覆盖掉的同名文件,所以跨文件看仍然是首尾
  相接、不重不漏的。
- **没有"最长回溯几天"这种上限**(`daily.next_window`)。上限会把起点往后挪,被挪
  过去那几天的内容再也进不了任何一份日报:服务停四天、上限三天的话第一天整段永久
  消失,而且一行提示都没有。素材太多是**限量**问题——`collect` 按条数截到
  `MAX_ITEMS`,日报里如实写明"窗口内共 N 条,以上列出最新的 M 条",能补;窗口断链
  不能补。`first_days` 只在一份日报都没有、接不上任何截止时刻时才用得上。
- **窗口的截止时刻在同步跑完之后才定下来**(`daily_run._run` 不给 `until`,由
  `generate` 自己取 now):同步能跑几小时,开跑时就把 until 钉死的话那几小时的内容
  谁也不覆盖。
- **筛的是 `published`(内容的生产时间),不是 `indexed_at`(抓取/入库时间)。**
  两者差几天是常态(实测一批 RSS 发布于 09-26、09-29 才抓进来)。按入库时间出日报,
  读到的是"今天抓到了什么",而人要的是"这段时间世界上发生了什么"。
- **时间字符串必须解析成时间再比,不能比字符串**(`daily.parse_ts`)。库里
  `published` 实测四种写法:`2026-09-28 17:08`(2.1 万篇)、
  `2026-06-14T11:29:37+08:00`(1178 篇)、`2026-09-29`(92 篇)、空(1 篇)。同一天里
  `T`(0x54)排在空格(0x20)后面,于是 `2026-09-28T07:00:00+08:00` 字典序上**大于**
  `2026-09-28 08:00`——按字符串筛窗口会把早上七点发的算进八点才开始的窗口。带时区的
  先换算到本地,只有日期的按当天 00:00(那是这种写法唯一能确定的下界)。SQL 只按
  日期前缀粗筛(两头各放一天给时区留余量),精确判断在 Python 里做。
- **发布在窗口之前、这一轮才入库的内容进「补录」**(`Material.late`,判据是
  `indexed_at` 落在窗口内而 `published` 不在)。严格按生产时间筛的代价就是这批东西
  永远进不了任何一份日报;单列一节、单独计数、prompt 里明确要求不混进要点,既不丢
  也不假装它们是新鲜事。没有发布时间的条目同样走这条路,只会出现一次。
- **日报写进 vault(`<vault>/daily/YYYY-MM-DD.md`),不写 kb.db。** kb.db 是随时
  可以删掉重建的索引,而日报是花了模型钱的产物。`daily/` 不在 `kb/config.py` 的
  `SOURCES` 里,所以它不会被索引——否则日报会变成明天日报的素材,自己引用自己。
- **"同步所有内容" = 依次借用 `kb.pipeline` 跑 `crawl/export/index/extract`,
  一个通道一趟。** 不能并发:管道是单例(一把全局运行锁,index/extract 都要单写者
  写 kb.db),同时开只会有一个被拒。条目化/wiki 不跑——日报不读它们的产物,跑一遍
  几十分钟。进度不另做一套展示,只把管道当前阶段的 detail 转述成
  「<通道>:<阶段详情>」,细节仍旧点进同步中心看。
- **超预算(`KB_DAILY_SYNC_BUDGET`,默认 3 小时)就请求停下、直接生成。**
  "今天的日报没出来"比"日报少了两个来源"严重得多。管道被别人占着时每个通道各等
  `WAIT_BUSY`(900 秒),等不到就跳过这个通道,不是整轮失败。
- **用户按的「停止」和超预算是两件事,别共用一个标记**(`stop_requested` /
  `over_budget`,`_halting()` 只管"还同步不同步下一个通道")。超预算的本意就是
  "别再同步了,拿现有内容出报",停在生成之前反而违背它;而用户按停止之后还接着
  生成,等于把一份同步到一半的日报当成功交出去,还要再花一次模型钱——界面上写的
  是"当前阶段结束后停止"。用户停止落 `phase='stopped'`,前端单独一档,不当失败。
- **进了生成阶段就停不了了,这一档要如实拒掉**(`request_stop()` 返回
  `(受理了没有, 说明)`,`STOP_GENERATING`;前端把按钮置灰并写明原因)。
  `daily.generate()` 是"调模型 + 把文件写完"才返回的一整段,受理下来只会承诺
  一件做不到的事——界面写着"这一轮不生成日报",实际照样多出一份、钱也照花
  (2026-09-30 审查实测)。**这个判断和 `_run` 里"进入生成阶段"那一步共用
  `_lock`**,所以两者严格二选一:要么停止先落下、生成整段跳过,要么生成已经
  开跑、停止被拒;分两步写的话停止请求正好挤在中间时,它既看不到
  `phase='generate'`(于是受理)、又赶不上那道检查(于是照样生成)。
- **只停自己起的那一轮管道,而且认的是 run id、不是布尔**
  (`_state['pipeline_run']`,`start_pipeline` 成功之后才登记)。日报允许在别人的
  管道后面排队等,而 `request_stop()` 原来只看"全局管道在不在跑"就去停它——用户
  想取消的是日报的等待,顺手把别人启动的绿泡泡/RSS 同步也中断了(2026-09-30 审查
  实测)。登记之后还要补一次 `_halting()` 检查:停止请求正好落在"等到空闲"和
  "起跑"之间时,那一刻管道还不归我们,它不会去停。
  **布尔只回答"是不是我起的",答不了"现在跑的还是不是我那一轮"**:我们那一轮在
  两次两秒轮询之间跑完、另一项普通同步紧接着拿到全局管道时,布尔仍是 True,而
  `running` 看起来从没断过——停止就落到了别人头上(2026-09-30 复审实测)。所以
  `pipeline.start_pipeline()` 改成返回这一轮的 **run id**(忙时空串,照旧可以当
  布尔用;`pipeline_retry.start_retry_failed` 那条启动路径也要发一个,不然重试
  运行会继承上一轮的身份),`pipeline_state.request_stop(run_id)` 在自己的锁里比
  一次 id、不一致直接不受理(空串 = 面板那个停止按钮的语义:停当前这一轮,不问
  是谁起的)。返回 id 而不是事后读状态,是为了**原子地**拿到身份——事后再读,
  我们那一轮可能已经跑完、读回来的就是别人的。
  `_sync_channel` 的轮询同样**只认 run id 相同的快照**:换人之后既不去停它,也
  不拿它的阶段结果当成我们这个通道的成绩单(审查者那次复现里,日报把别人那一轮
  的失败写进了自己的 entry)。
- **「拿到结果了」= 亲眼看到自己那一轮 `running` 放下的那份快照,或者按 id 查到
  它的收尾记录;两样都没有就如实记 `unknown`,绝不按成功记账。** 中途快照不算
  终态——那时阶段还是 running/pending,拿它数 error 一个也数不出来,于是"被接替"
  和"跑完了全是绿的"长得一模一样,报成功却没有任何证据(2026-09-30 第 3 轮审查
  实测这里硬编码成了 ok)。所以 `pipeline_state` 按 run id 留最近
  `_FINISHED_KEEP`(8)轮的收尾快照(`_end_run` 里在放下 `running` 之前存,
  `run_result(run_id)` 取),被接替的那条路统一去问它。查不到(被更多轮挤出去)
  才落 unknown:日报照样生成——素材是库里已有的那些,不因为一个通道的结果查不到
  就整轮不出报。
- **勾了"先同步"却一个来源都没选,直接拒掉**(`start()` 抛 `ValueError`,
  API 400,前端按钮边上再拦一道)。放过去的话同步阶段静静地什么都不做、面板
  一路"成功",「同步全部并生成」被悄悄降级成「直接生成」,用户不知道素材根本
  没刷新(2026-09-30 审查实测)。"直接生成"不受这条限制——它本来就不同步。
- **有通道没同步成功时,日报照出,但「同步了」这件事不许糊过去**(`_sync_issues()`
  给名单,三处都读它:完成提示 `_set('done', …)`、面板那条 `daily-sync-note` 横幅、
  写进日报文件的 `sync_failed` frontmatter + 正文那段引用块)。降级拿已有内容出报是
  对的("今天的日报没出来"更严重),可**一份"一个新来源都没同步到"的日报和一份"全都
  同步到了"的日报原来长得一模一样**:三个来源全部连接失败,页面上只有一句绿色的
  「日报已生成」,文件里一个字都没提(2026-09-30 审查实测)。**必须写进文件本身**——
  日报是拿走就读的产物(复制、Obsidian、明天翻回来),面板上的提示留不住;toast 也
  换成 info,绿勾等于把降级说成完整成功。口径是 `status != 'ok'`(error/unknown/
  skipped 都算),前端横幅在 `channels` 空时回落到落盘的 `last_run.channels`(重启
  kb-web 之后进程内那份是空的)。
- **没素材时抛 `LookupError`,绝不写一份空日报**——空日报会把这一天"用掉"
  (列表里有了、按钮变成"重新生成"),而真正的原因(还没同步)反而看不见。
- **定时挂在 `pipeline._scheduler_tick` 那一跳上**,不另起线程:它已经每 30 秒跑
  一次了。日报在跑时 `tick` 直接返回,让公众号定时和订阅定时都别去抢管道——
  日报正握着管道依次跑各通道,这时候插一轮进来只会互相拒绝。
- **「已触发」和「已出报」是两个字段,别拿起跑那一刻去记 `last_fired`。** 起跑就
  记的话,一次模型 502 就让用户整天等不到日报,面板上也看不出还会不会再试。
  `tick` 只 `_mark_attempt`(把下一跳推到 `RETRY_AFTER` 之后),收尾时由
  `_finish_schedule` 决定:临时故障同日补 `MAX_RETRIES` 次,成功/没素材
  (`LookupError`)/用户停止一律"今天到此为止"——后三种重试多少次都是同一个结果。
  **记的是起跑那一天(`sched_day`),不是收尾那一刻所在的那天**:同步能跑几小时,
  23:50 起的那一轮 00:50 才收尾,按收尾时刻记会把第二天那一跳也吃掉。
  `_mark_attempt` 要在 `start()` **之前**调:跑得极快的那一轮(不同步、当场报错)
  已经写完收尾状态了,反过来写会把它盖回去。
- **`_raw_settings()` 不碰采集器注册表**:定时线程每 30 秒读一次只为判断"到点没
  有",通道校验放进来的话每一跳都要把所有采集器模块导入一遍。要校验过的那份用
  `load_settings()`。设置里的 `first_days` 只在**一份日报都没有、接不上任何截止
  时刻**时才起作用;老配置里的 `days`/`max_days` 按它读进来(值留着,意思变了)。
- 存下来的通道一个都不认识了(改名/删掉)时回落到默认范围,不是留一份空列表——
  空列表会让定时日报每天都跑出"一个来源都没同步"。
- **日期字符串即文件名,`Date.fromisoformat` 就是那道路径校验**(`_path_for`)。
  API 层另有 `_check_day` / `_check_time` 给 400。写盘走 mkstemp + `os.replace`。
- **阶段落 `skipped`/`stopped` 的通道不算同步成功**(`daily_run._sync_channel`)。
  2026-09-30 实测:51 个大V账号一个都没配 X 桥接,`feeds.sync.collect` 把它们全
  记成 unconfigured、crawl 整个阶段落 `skipped`(「待配置 51 个」)——而这里原来
  只数 `error`,于是 social 通道报的是绿色的「同步完成」,日报里那一行只剩 extract
  的结果,"一条都没抓到"连同原因一起看不见。超预算/被停止时管道落 `stopped`,同理。
  **只看这一轮请求了的那几个阶段**(`SYNC_STAGES`):没选中的阶段一开跑就是
  `skipped`(见 `pipeline.start_pipeline`),全收进来的话每个通道都要多报两句
  「条目化/wiki 未执行」。
- **正文里的出处编号(`[18][23]`)在落盘时就写成链接**(`daily._link_refs`),
  不留到阅读时。日报是拿走就读的产物(复制出去、在 Obsidian 里翻回来),只在
  kb-web 上可点的话换个读法就退回一串对不上号的数字。链接文字保留方括号
  (`[\[18\]](<url> "标题 — 来源·作者")`),转义是因为 Obsidian 会把裸 `[[18]]`
  当 wikilink;**目标一律套尖括号**(`_md_dest`)——库里的 url 实测有带圆括号的
  (`S2589-0042(26)00811-4`),裸写进 `](…)` 会在第一个 `)` 提前收尾。素材清单里的
  标题同理要转义方括号(`_md_text`,库里十来篇带着 `[视频]`)。编号对不上素材、
  那条没有 url、或者已经是一条链接(`[3](http://…)`)时一律原样留着,不编一个出来。
- **每一处出处编号换不换,由渲染器裁决(`kb/daily_refs.py`),这里不写「哪些片段不许
  动」的规则。** 这是**写进文件**的替换,改错了就是把日报原文改坏——页面、复制全文、
  Obsidian 一起受影响,不是渲染层的事。手写规则的路走过三轮,每一轮都被真实渲染器
  找出新的漏网写法:第 1 轮逐行正则漏掉行内代码 `items[1]`(落盘后成了
  `items[\[1\]](<url> "…")`,照着复制的命令当场是错的)和已有链接的文字
  `[版本 [1]](https://…)`(一条链接裂成两个不同目的地);第 2 轮改成字符级 CommonMark
  扫描,又漏掉跨行代码跨度、单引号/圆括号标题、引用式链接、两层以上嵌套的括号目标;
  第 3 轮继续漏掉**多行定义** `[p]:\n  url`、**引用段里的定义** `> [p]: url`、**原始
  HTML 的 `<a>` 与 `<code>`**、**独立缩进代码块**、**autolink 的地址**。**这份清单不会
  收敛**——把它补全等于把一个 markdown 解析器重写一遍。
  所以判据换成:把某一处换成链接,**渲染一遍看结构变没变**。逐个候选各试各的,接受
  的条件是「这一处之外一个字都没动」——代码元素(行内、围栏、缩进、HTML 写的)连内部
  结构逐字不变、原有链接一条不少且文字与目的地不变(autolink 也是链接,一并管住)、
  图片的 alt 与地址不变、多出来的只能是文字为 `[N]` 的出处链接且数量对得上。判不准
  的一律不换:那一处留成纯文本,面板还能照素材清单补上(`enhanceDailyBody`),而改坏
  了的原文没有任何东西补得回来。这样**正确性不再取决于谁更懂 CommonMark**,上面那
  些写法连同「单边转义 `\[1]`」「`[1]: url 多余文字` 不是定义」这类边角一起自己就对了。
  **比对要连 `<code>` 的内部结构一起比,不能只比文本**:往代码里塞一个 `<a>` 并不改变
  文本,拿文本比的话这道闸对"代码内部别建链接"根本不敏感。**另外单数一道链接嵌套**:
  链接套链接在 HTML 里非法,浏览器会把内层提升成兄弟、原来那条的文字被切掉一截,
  而解析器(bs4 那一类)会如实嵌套、外层 `get_text()` 连内层一起算,看着逐字没变——
  `<a href="…">版本 [1]</a>` 被改坏时就是这个形态。
  **裁决器的方言必须和页面那个渲染器一模一样**(`markdown-it-py` 的 `gfm-like`:
  linkify + 表格 + 删除线,`html=True`)。第 4 轮两条拦验收都出在这里 —— 原来按
  CommonMark 裁决,而页面的 marked 默认开着 GFM:①裸网址 `https://e.org/path/[1]`
  在 CommonMark 眼里只是一段文字(于是放行),在页面上却是一条链接,替换完 href 从
  `%5B1%5D` 变成 `%5B%5C%5B1%5C%5D%5D`,点过去是另一个地址(`www.…` 同理);②GFM
  表格 CommonMark 压根不解析,于是**标题里一个裸 `|` 就把那一格从中间劈开**、右边
  「已可用」被挤出表外也看不出来(库里 215 篇文章标题带着 `|`)。所以 `_md_title`
  把 `|` 转义成 `\|`、`_md_dest` 编码成 `%7C`(尖括号拦不住它:GFM 是**先按行拆
  单元格、再解析 inline** 的),两者在表格内外渲染结果一致。
  **但"换个预设名"不等于对齐:裸网址另有一道不依赖解析器细节的超集判据。** 换上
  `gfm-like` 之后 `www.example.dev/path/[1]` 照样被改坏 —— linkify-it 只认一份有限
  的 TLD 名单(`biz|com|edu|gov|net|org|…`),`dev`/`app`/`cloud`/`news`/`technology`/
  `online`/`blog`/`xyz` 全不在里面,而 marked 对 TLD 不做任何限制:8 个后缀真实页面
  上一测一个准,文字和 href 双双变样、点过去是另一个地址(2026-09-30 第 5 轮审查
  实测)。**补几个后缀就是在维护一份名单**,下一个没见过的照样漏,何况 path 边界、
  backpedal 那几处还有同类缺口 —— 两个 markdown 实现永远不可能逐位对齐。所以:
  ①`_MD.linkify.tlds(r'[a-z0-9\-]{2,}')` 把 TLD 放宽成"任意",让主裁决器的基线别
  明显窄于 marked(不放到一字符是因为那会把 `3.2`、`v1.5` 这类版本号也认成域名 ——
  过度识别只是少加一条链接,不改坏谁);②真正兜底的是 `_autolinked`:marked 的
  autolink 起手式只有 `www.` 和 `scheme://`、尾巴是 `[^\s<]*`(不跨空白、不跨 `<`),
  于是「这个编号落在某条裸网址里」**必然**满足「往左数到最近的空白或 `<` 为止,这
  一段出现过 `www.` 或 `://`」——命中就不换。反过来不成立,所以它是超集,多拒几处
  换"再不会有下一个漏网的后缀"。这两道**不是等价的两份实现**:实测只留 ② 而把 TLD
  退回默认名单,回归全绿;只留 ① 去掉 ②,`www.x.y`(一字符 TLD)当场红。真实日报
  21 KB / 80 处候选,被 ② 挡下 0 处。
  **② 那条起手式正则必须大小写不敏感**(`re.I`)。marked 那条 url 规则本身带 `i`
  标志,`WWW.`/`Www.` 照认。漏掉大小写时两道保护会同时落空 —— 起手式大写、后缀又
  在 ① 认不出的范围里(实测 `WWW.example.中国/path/[1]`、`WWW.x.y/path/[1]`),原
  网址当场被改坏,而小写的同一条因为 ② 命中 `www.` 好好的(2026-10-01 第 6 轮审查
  实测)。**这也说明 ① 会顺手遮住 ② 的缺口**:上一轮的大写样本用的是 `E.ORG`,
  linkify 自己就认得,于是大小写漏判一条测试都没红 —— 所以回归里另有一条直测
  `_autolinked` 的,10 种起手式大小写各一次,绕开这层遮掩。
  **代价是过度保护,已知且接受**:`_autolinked` 只往左看一段没有空白的文本里有没有
  `://`,分不出那是裸网址还是**一条已经收尾的 markdown 链接的目标** —— 于是
  `[产品](https://example.org/keep)[1]` 紧跟着的那个出处不会被写成链接(页面上前端
  兜底照样补得出,拿走 md 文件就是纯文本)。要收窄就得回去解析 markdown 判断"这个
  `://` 在不在链接目标里",而 URL 的 path 里本来就可以有平衡圆括号、`)` 当不了终止
  符 —— 那正是前五轮反复证明会漏的那条路。少一条链接谁也不会被骗,改坏一条原网址
  会把人送到另一个地址:这个方向上宁可多拒。
  **判据是整份渲染结果逐字比,不是挑几类元素比。** 原来只收集代码/图片/链接,
  「表格挤错列、一整格内容丢了」「不可见的引用定义被显示成正文」这类改动全部漏过
  —— 嘴上说"这一处之外一个字都没动",实际只看了那几类。现在的做法:要换的地方先
  换成**哨兵链接**(私用区字符当链接文字,目标和标题跟真链接一模一样),渲染后把
  哨兵链接**整组**还原成原文那一段(合并写法 `[1、2]` 换出来是两条相邻链接,一条条
  还原成 `[1][2]` 就跟原文对不上了),要求和原文的渲染结果**逐字相同**;再确认真
  链接版和哨兵版只差链接文字那一处。用哨兵而不是按 (文字, 地址) 去认,是因为原文
  里本来就有一条一模一样的链接时,猜哪条都说不准。
  **另外单拦一道:哨兵链接不许落在 `<a>`/`<code>`/`<pre>` 里面。** 这两种情况还原
  之后照样逐字相同(容器本身没变),可链接套链接浏览器会拆开(点击目标错位)、代码里
  冒出链接更是把别人照着复制的命令改了。
  **一组里没有素材的那几个编号也要打哨兵**(只是不做成链接)。还原时只把第一个哨兵
  换回整组原文的话,`[1,9]` 里那个没素材的 `9` 生成的 `[9]` 还留在旁边,还原结果成
  了 `[1,9][9]`、跟原文对不上,于是**整组被拒**——有素材的那个编号也白白留成纯文本,
  页面上前端兜底还能补,拿走 md 文件就只剩一串数字(2026-09-30 第 5 轮审查实测)。
  **两边都要过一次解析器再比**(`_norm`):`<img …>` 与 `<img …/>` 这种序列化差异
  不是"内容变了",按原始字符串比会白白漏掉一条出处。
  依赖是 `markdown-it-py[linkify]`(linkify 那个 extra 不能省,少了它裸网址就回到
  CommonMark 的盲区)+ bs4。**它得是显式依赖**:原来只是 rich 的传递依赖,那条链断
  了这里就崩。代价是渲染开销,所以**先整篇一起试一次**(一篇日报的出处多半没有一处
  落在代码或已有链接里,这条路只渲染三遍,实测 21 KB / 80 处 50 ms);过不去才逐个
  各试各的(同一份 2.3 秒),**真遇到才付**。
  **回归必须拿页面那一份 marked 来验**(`tests/daily_refs_marked.mjs`,node 直接
  import `kb/static/vendor/marked.min.js`,由 `tests/test_daily_refs.py` 的
  `TheRealMarkedAgrees` 调起、没有 node 就 skip)。裁决器是 markdown-it、页面是
  marked,第 5 轮正是栽在两者的 linkify 口径不同上 —— 在**后端自己的**渲染器里比
  一遍,只能证明它自己前后一致。样本要按 marked 的真实识别位置写:实测它的
  inlineText 前瞻大小写敏感,`HTTPS://…` 只有在段落开头才被切出来。
- **加链接之前生成的那些日报由面板兜底**(`daily.js` 的 `enhanceDailyBody`):
  它们是花过模型钱的产物,不该为了加链接重新生成一份(重算窗口还会换掉内容),
  序号→原文的对应关系就在同一篇的素材清单里,照它补上就是;新日报上这一步是
  空转(编号已经在 `<a>` 里,遍历文本节点时直接跳过)。同一个函数顺手把正文和
  素材清单的外链都改成新标签打开——在当前标签里跳走等于把 kb-web 连同正在跑的
  管道面板一起顶掉。
- **兜底那份「编号→原文」的对应关系读的是渲染之后的那个 `<ol>`,不是 markdown 原文**
  (`daily.js` 的 `dailyRefMap`)。清单那几行的目标有两种写法(老日报裸写 url、新
  日报套尖括号),而裸写的 url 自己可以带平衡圆括号——自己写正则解析会在 url 里第一
  个 `)` 处断掉,那一整行匹配不上、这一条的编号永远补不出链接(2026-09-30 审查实测,
  生产那份日报的 107 条素材里就有一条 `-(clean).pdf`)。marked 本来就按 CommonMark
  把它解析对了,照抄解析结果比再写一遍解析器可靠。**认的编号写法要和落盘那条路
  一致**(`[1]` / `[1, 2]` / `[1、2]`):两边不一样的话,同一种写法在新旧日报上一个
  能点一个不能。粗筛文本节点别用带 `g` 的那条正则——`test()` 会把 `lastIndex` 留在
  命中处,下一个节点就从半截位置开始找。
- **前端那条横幅有两个来源**(生成失败的原因、列表读不出来的原因),清空时必须认

## 上报账本:日报生成之后再抓到的内容再也不会出现(2026-10-10)

**症状**(仓库主人原话):"日报只要生成后,在重试失败项或加入某些源后就不变了"。

**旧实现的那条缝。** 两个取材桶都是"时间窗 + 取最新 N 条":

- 要点桶 = `since < published <= until`,按 `published` 降序取 `MAX_ITEMS`(120)条;
- 补录桶 = `since < indexed_at <= until` 且 `published <= since`,按 `indexed_at`
  降序取 `LATE_ITEMS`(30)条。

一个条目只有在某个窗口里挤进这两个 top-N 之一才会被报道。**没挤进的在下一个窗口里
两个桶都选不到** —— 它的 `published` 和 `indexed_at` 都已经早于新的起点,于是掉进
两个桶中间的缝里永久消失,而且一行提示都没有。库里也**没有任何一列**记着"这一条报
过没有",所以落选之后不可恢复。

**实测证据**(生产库 2026-10-10,`data/kb.db` 只读副本):

| 日报 | `docs`/`total` | `late`/`late_total` | 补录丢弃 |
|---|---|---|---|
| 10-02 | 1 / 1 | 30 / 40 | 10 |
| 10-04 | 2 / 2 | 30 / 137 | 107 |
| 10-09 | 69 / 69 | 30 / 506 | 476 |
| 10-10 | 82 / 82 | 30 / 679 | **649(96%)** |

有几天的 `docs` 是 1~2 条 —— 也就是说那几天**几乎全部**内容都走补录这一档,而这一档
96% 被丢掉。这不只是"重复内容被滤掉":10-10 那份丢掉的 607 条里,**141 条的发布时间
早于整条日报链的起点(2026-09-29)**,也就是说它们从来没进过任何一份日报的要点桶,
补录那 30 个席位是它们唯一的机会,落选即永久消失。

**症状和这条缝的对应关系。** 2026-10-10 08:07 出了一份日报;10:18 和 10:27 两批重试
抓回 28 篇 RSS 文章,发布时间全部落在 10-09 全天到 10-10 07:54 之间 ——
**一条都不晚于那份日报的 `window_until`**。于是:

- 不手动重新生成:下一份日报的 `since` = `2026-10-10 08:07:14`,这 28 条的 `published`
  全都 ≤ 它 ⇒ 全部只能走补录,和另外几百条抢 30 个席位;
- "新加一个订阅"更糟:`history_floor` 会把该源最近 5 天的存档一次交出来,**整批**都是
  "发布时间早于当前窗口起点"的形态,上百条抢同样的 30 个席位。

**`indexed_at` 还答不出"这一轮才入库"。** 重新导出(补译、补抓正文)会刷新它,所以老
文章每天都重新算一次"刚入库"。按"窗口内发布 + 当时已入库"去反推历史上报过什么,
9 份日报只认得出 **217** 篇 —— 其余全被churn 冲掉了。这也是补录桶长期被旧文占满的
原因(`history-depth.md` 记过同一现象的另一面)。

**修法:判据换成"这一条被哪一份日报带走过"。** 新表 `daily_carried(path, day,
carried_at)`,`_UNCARRIED` 子查询进两个桶的 WHERE。于是:

1. 没带走的条目**留在队列里**,下一份接着带 —— 条数上限从"丢弃线"变成"每份带多少条"
   的限流,日报正文里也写明"没列出的留在队列里,下一份日报接着带";
2. 带走过的再也不是候选 —— 顺带治好了 `indexed_at` churn 把旧文反复推进补录那件事;
3. 补录桶不再需要 `indexed_at`,改成"发布早于窗口起点 + 没带走过 + 发布时间在
   `BACKLOG_DAYS`(30 天)内"。那个 30 天是**编辑口径**(日报不回头报一个月前发布的
   东西),和 `MAX_ITEMS`/`LATE_ITEMS` 那种限流是两回事:超出的条目在成为候选之前
   就被排除,**因此也不计进 `late_total`、不计进面板那个计数** —— 别把它说成
   "照旧排队",那会让人以为所有补抓最终都会被报道。

**四条配套的硬口径:**

- **盖章排在落盘之后。** 方向是不对称的:章没盖上只是这批素材下一份再出现一遍(多报
  一次,看得见);落盘失败而章已经盖上,这批素材再也选不到,**不可恢复**。
  `mark_carried` 失败时只往结果里记一句 `carry_error`,不把已经落盘的这一轮带崩。
- **重新生成同一天要放过它自己盖的那些章**(`_UNCARRIED` 的 `c.day<>?`)。同名文件
  是整份覆盖的,排除掉自己的章等于新版本把早上已经报过的内容整段丢掉。
- **删一份日报要先放回、再删文件**(`daily.delete`)。反过来的话放回失败时文件已经没
  了而章还盖着,那批内容两头落空。按这个顺序最坏情况只是下一份多报一遍。
- **按钮上那个数是「今天第 N 次抓取抓了多少」,不是取材结果、也不是队列总长。** 那是抓取自己的事实,
  记在 `kb/fetch_rounds.py`,硬约束连同事故形态在它的模块 docstring 里(那份账本只回答「今天」)。
  三个数答的是三个问题:**抓回来 9 条**、**这一次选得进 3 条**、**队列里还积着 1097 条**。拿后两个
  冒充第一个的实测后果:第二次同步真抓回来 9 条而按钮写 3 条;抓回来那条发布得早、抢不到补录席位就
  写「没有新内容」;一条没再抓、只重新生成了一次,数字从 9 变成 0。**生成、重新生成、删掉日报都不许
  改变它。**
- **成果的归属只认生产者的回执,不许由任何旁观者的视角猜。** 数的是采集器自己交回来的那份清单
  (`SourceCollector.materialize()` 的返回值,契约在 `kb/collectors/__init__.py`;按来源各记一次,
  记在 `pipeline_stages._run_export` 里各自的 `finally`)。**说不出来就报「不可确认」,不许给一个
  看着确定的数** —— 口径只在 `fetch_rounds.note` 一处,两个采集器、重试入口、将来新增的来源都过它。
  这里错过两版,两版都是拿旁观者冒充生产者:
  - **拿索引的"库里头一回出现这个路径"当成果**:两个方向都错 —— 空抓取碰上 3 篇历史未索引的旧文
    报成「+3 条」,反过来真抓到 2 篇而这一轮不索引则报 0、之后单独索引也补不回来(都是实测)。挂在
    索引上还多一层:那边分 25 篇一批提交,记账排在全部提交之后,中途磁盘满就留下「25 篇已入库、
    按钮写 0 条」且重跑算不回来。
  - **拿物化前后的全 vault 路径差集当成果**:差集分不出"谁写的"。第 3 轮审查实测:本轮确定空抓,
    而物化期间另一个进程手工放进一篇 `source/rss/manual.md`,按钮报「+1 条」。同类还有实时 saver、
    手工导入、并行采集器、常驻服务在这段时间里落下的文件。**挪动快照位置修不全它** —— 旁观者
    拿不到"谁写的"这个事实,只有写的人知道。
  索引、重建索引、CLI 索引、手工导入、条目化都不交回执,一个数都不会变。
- **「收到过回执」不等于「这一轮交完了」:完整性只认那条明确的结束行。** 导出阶段进门先落一张空回执
  (成果从「确定的空集」起步),所以在盘上「刚开始」和「全部交完」长得一模一样;`fetch_rounds.note_end`
  那一行写在**逐来源循环走完之后**,没有它的轮次一律按**下界**报(面板说「至少 +N 条」)。错过的两种
  形态都是第 1 轮审查实测的,而且都落在**确定**那一档上(所以刷新和重试都纠不回来):真实
  `_run_export` 里 `os._exit(23)` 落在交回执前,vault 多了 1 篇而重启后盘上写着
  `{'n':1,'added':0,'partial':False}`;多来源里第一个来源交完回执就让整轮看着完整,第二个还没开口时
  进程没了,已知的下界被当成总数。**轮换(整份重写)要把这一位抄过去** —— 漏了它,一轮完整的抓取过
  一次台面下的维护就变成「至少 N 条」。
- **而「交完了」是按子轮集合算的,不是哪一个子轮说了算。** 一次业务抓取的物化由 N 个子轮各跑一段
  (`daily_run` 那个逐来源循环:每个来源一次管道运行、共用一个批次身份),所以会物化的每一次
  `open_round` 都要登记自己那个子轮身份(`seg` = 这次运行的 `run_id`,口径在
  `pipeline_batch.round_key`),`today()` 只在 `segs == ends` 时才给确定数。第 2 轮审查实测:第一个
  子轮正常收尾,第二个子轮在另一个进程里写出第二篇之后 `os._exit(23)` —— 盘上第一个子轮的结束行让
  整轮报成**确定的 1 条**,而 vault 里躺着两篇。**轮次幂等、子轮登记不幂等**(第二次 `open_round`
  不再开轮,但要补那一行);反过来,结束行**同时**算"这个子轮登记过",否则只勾了导出的那种重试
  (压根没开过轮)会把一轮已经交齐的抓取永久钉在「至少」上。
- **生产者的提交边界在「文件落进 vault」那一刻,不在它后面那次记账确认。** `os.replace` 一成功就进
  回执(`sync._export` 里 `written.add` 排在 `feed_items` 的 UPDATE **前面**),随后那次确认失败只
  意味着"下一轮还会再导一次"。排在后面的那一版实测会永久丢:确认那一下的异常被接成逐项错误、回执
  照旧返回一个看着确定的集合,而重导时这一篇已经不是新文件(`fresh=False`)—— 它**永远**补不回账。
  整段物化半途炸掉、清单只剩一半时返回 `None`,不要返回那半份冒充完整(公众号那条通道正是这么做的:
  子进程判错就 `None`)。
- **证据不许因为「这一刻读不出账」就消失。** 生产者交过的回执、交不出清单时那笔「不可确认」,都得留在
  某处:本进程自己开的那一轮照旧追加(`_mark` 认 `_opened`,它的开轮行要么已落盘、要么还在
  `_unsaved` 里,不会凭空多出对不上轮次的孤行),别人开的那一轮至少记一笔「缺了一行」(`_gaps`),由
  结束行带着 `partial` 落盘。第 2 轮审查实测:只在写出文章后的**下一次**读账上注入一次 `OSError`、
  之后完全恢复,旧实现在 `_mark` 里直接 return,那篇永久不进账而结束行照样写成功 —— 末态
  `n=1, added=0, partial=false`,重读盘上那几行仍自称完整,恢复后重导也不算新文件。**反过来钉一边**:
  读不出账、这一轮又压根没开过(只勾了索引的那种运行在喊成果),那就什么都不记。
- **账本的每一次写都在那把旁挂锁里:取不到锁就一行都不写。** `_locked` 如实交出「这次没锁住」,
  `_flush` 把行攥在 `_unsaved` 里(不追加)、`_rotate` 整步跳过、`today()` 返回 `None`(展示降级成
  「读不出来」);锁一回来,攥着的那几行照旧落盘,数一条不少。上一版的降级是「只许追加、不许轮换」,
  它只挡住了"失锁者自己轮换",挡不住反过来那一半:**另一个持锁的进程**按它读到的旧快照整份重写,把
  失锁者已经追加成功的整轮抹掉(第 1 轮实测失锁者自己轮换、第 2 轮实测持锁者覆盖失锁者 —— 两次的
  末态一样:JSON 行行合法、`today()` 自称确定、结论从 `added=1` 变成 0 条,而那篇文件还在 vault 里)。
  **代价和它的边界**:锁长期取不到(旁挂文件被占成目录、目录只读)时面板一直说「读不出来」,这是
  **有意的**降级 —— 能不能上锁是数据目录的属性而不是进程的属性,所以读的那一侧(面板)和写的那一侧
  同时降级,不会出现"一个进程笃定地报一个少记的数"。抓内容那一侧完全不受影响 —— 账本是展示用的,
  为它把抓取拦下来不划算。
- **「参与过」这件事不许只存在账本里:攥住行的同时留一笔不走那把锁的凭证**(`kb/fetch_pending.py`)。
  上一条那套降级把「写不上就攥着」做对了,但攥着的东西随进程消失 —— **某个子轮的登记行没落盘、进程
  又没了**,盘上一个字都不说明它参与过,而它可能已经往 vault 落了文章。第 3 轮审查实测:真实
  `_run_crawl`/`_run_export` 里第二个子轮开工时旁挂锁坏着(登记行只在 `_unsaved` 里)、随后
  `os._exit(23)` —— 盘上第一个子轮的开轮行/回执/结束行行行合法,`segs == ends` 照旧成立,`today()`
  报**确定的 1 条**,而 vault 里躺着两篇;刷新、重启、重导都纠不回来。所以 `_flush` 每次搬动缓冲都
  顺手把「我还欠哪几轮」写成一笔独立凭证:它**按进程命名、原子整份写、不取任何锁**(锁坏掉正是要留证
  的那一档),只记轮次身份不记条数。`today()` 据此把结论压到**下界**;凭证指向一轮账本里压根没有的
  身份时(登记行一个字都没落下去)干脆答「不可确认」—— 沿用更早那一次的确定数等于把上一次的成果说
  成这一次的。**三处要同一个口径**:凭证的保留窗口 = 账本的保留窗口(`_floor`,凭证活得久了它指的
  轮次已被轮换清掉,面板会从此永久「读不出来」)、行落了盘就撤掉凭证(不撤等于把药丸永久钉在
  「至少」上)、凭证读不出来算「说不清」而不是「没有」。
- **一次写就是一代,代与代各占一个路径,内容从此不改**(`fetch_pending._slot`)。清理只能撤销**自己
  刚读出来、判了过期的那一个路径**,所有者只收**自己写新一代之前就看见的**那几代,新一代没写成就
  一代都不许收。第 4 轮审查实测:上一版一个进程一个固定路径、每次原子替换,清理方「读出五天前的
  内容 → 判过期 → 按同一个路径删」整件事不是原子的,所以它删掉的是所有者刚换上去的**当天那一代**
  —— 盘上从此一笔证据都没有,而 vault 里的文章还在。可达性不靠撞运气:**常驻进程一直用同一个
  `TAG`**,上一次撤销失败之后它跨过保留窗口再工作,旧内容和新内容就是同一个路径。「两边各自原子」
  推不出「整件事原子」。
- **参与证据只认两处,而两处都留不下的时候不许往下抓**(`fetch_rounds.open_round` 那道闸)。
  账本和凭证**能一起失效**(旁挂锁被占成目录 + 凭证目录路径被占成普通文件),而数据目录照旧可写
  —— 第 4 轮审查实测:真实 `start_pipeline`、采集器真写出第二篇、随后硬退出,面板仍报**确定的
  1 条**。旧版这里写的是「数据目录写不进去时开工标记落不下来、那一轮压根不起跑,所以这一档不可
  达」,**那条推理不成立**:早先某一个文件写成功,推不出稍后另外两个文件一定可写(开工标记先写,
  另两条路径稍后才写)。第 4 轮据此把那笔开工标记收成了「第三处证据」,**第 5 轮审查又证伪了这
  一条**:详见下面「证据的寿命」那一节 —— 标记的寿命是**那一轮运行**的(正常收尾清掉、下一次起跑
  覆盖),而参与证据的寿命必须是**那笔欠账**的。所以闸和读侧现在只认两处,它们的寿命正好是欠账
  的寿命:**账本里那条登记行**(追加即不可撤,只随保留窗口轮换)和**那笔独立凭证**(手里还欠行就
  在、行一落盘就撤)。**判据是「读回来确认」而不是「写的时候返回了什么」**(凭证写不上是不出声
  的);**不拦的只有两条**:不物化的运行,以及**账本坏着、而那笔凭证写上了**(坏掉的展示账本不许
  把抓取拦在采集器之前,但它也不能替凭证作证)。**「此刻读不出账本」本身不是证据** —— 第 1 轮
  逻辑审查又证伪了一条出口:原来 `_landed` 在 `ok=False` 时无条件放行,理由是「读不出来时读侧只会
  答不可确认」,而 `ok=False` 还包括一次**瞬时** `OSError`,它一恢复读侧就按剩下那几个完整子轮给出
  **确定的偏小值**(实测两条写路径都坏着、只对起跑那两次账本读注入 `OSError`,真采集器照旧抓、真
  导出又落 1 篇、进程正常退出,全新进程报确定的 2 条而 vault 里三篇)。拦住那一档**单独一个异常
  类型**(`NoEvidence`),编排那一侧据它把原因写进阶段卡片 —— 这道闸的全部代价都押在「误报看得
  见」上,只补一句通用的「流程中断」等于把代价藏起来。
- **「今天第几次抓取」的先后按业务起跑顺序,不按物理行序**(`fetch_fold._order_key` 是唯一出处)。
  账本是多进程追加的,一轮的行会**晚落盘**(写失败时攥在内存里、下一次操作才补上),所以行序不是
  业务序:第 1 轮逻辑审查实测 A 轮 11:00 开、交 2 条,行晚落盘;B 轮 12:00 整轮先落;A 补写之后两轮
  全在盘上、谁都不欠行,而面板写「第 2 次抓取 · +2 条」、时间退回 11:00,重放同一份文件还是这个
  答案。所以开轮行上带一笔**微秒级**起跑时刻(`t`,分钟级的 `at` 照旧写、给展示和存量用),投影按
  `(day, t, key)` 排好序再交出去,**轮换整份重写必须把 `t` 一起抄走**;平局拿 `key` 兜(**不许拿物理
  位置兜**,那等于把顺序又押回行序上)。消费方不许就地再排一次,也不许按末位理解行序。
- **「这一轮算哪一天的」同样不许按行序定:`day`/`at`/`t` 是一份事实,整份取最早那条开轮行**
  (`fetch_fold._start` / `_start_key`)。同一个业务身份会有多条开轮行(读失败那一档会再写一条),
  跨零点时那两条**不同天**。第 2 轮审查实测:只把起跑时刻换成最早那条、`day` 留着物理首行的,折出来
  就是一份自相矛盾的事实(`day` 16 日、`at` 15 日 23:59)—— 今天还没同步过,药丸却说「第 1 次抓取 ·
  +3 条」,今天真的第一次同步之后又跳成「第 2 次」;而 `today()` 正是按 `day` 筛当天那几轮。两处细节
  也钉住:**说不出起跑时刻的那条不许顶掉说得出的那条**(否则 `day` 被抹空,这一轮从此落不进任何一
  天),**两条都说不出时按更早那一天算**(仍是数据的函数,且多报一次抓取在安全那一侧)。轮换因此是
  **归一化者**:整份重写时一轮只剩一条开轮行,它必须带着这份规范化事实,否则矛盾被永久固化、原始
  两条行已经没了。
- **展示用记录的反序列化只有一个口径,而且兜住所有异常**(`pipeline_persist._loads_json`:账本逐行、
  独立凭证、那三份管道落盘都过它)。按异常类型各列一张单子的后果是实测的:**深嵌套 JSON 抛的
  `RecursionError` 是 `RuntimeError` 的子类**,`(OSError, UnicodeDecodeError, ValueError)` 一个都不
  沾,它从读取那一步逃出来、一路冲到抓取阶段的 `open_round`,于是一份手改坏的计数记录能把整次同步
  拦在采集器之前(生产者 `fetch` 调用次数 0)。**坏记录只许降级成「读不出来」,不许当空数据,也不许
  阻断生产者。**
- **那份缓冲是两条线程共用的:确认只许移除自己真写下去的那几行。** 管道在写账本,而面板每 15 秒读
  一次、`today()` 自己又会替攥着的行补写 —— **追加是 I/O,它必须在进程内那把缓冲锁之外跑**(罩进来
  就把面板那一跳堵在磁盘故障后面),于是这期间另一条线程完全可以往缓冲里压进新的回执。上一版追加
  成功之后一句 `_unsaved = []` 把它一起抹掉了:第 3 轮审查实测面板那一跳正卡在追加里、管道线程这时
  记下第二篇的回执,追加一回来缓冲就空了,那一篇再也补不回账(重导时它已经不是新文件),而
  `today()` 自称确定、报 1 条,vault 里躺着两篇。所以确认**按身份(`id`)剔**:按值剔会多剔一条
  (两条 `partial` 标记长得一模一样),按条数剔在两条线程各自确认时会剔到对方新压进来的那几行。
  重复追加不要紧 —— 折叠本来就幂等。**锁序只有一个方向:账本那把文件锁 → 缓冲锁**,缓冲锁里只做
  缓冲自己的事(搬那几行、写那笔凭证),不许在里面追加账本或取任何别的锁。三份内存状态
  (`_unsaved`/`_opened`/`_gaps`)的读和写都过这把锁:`_push`/`_seen`/`_pending`/`_flush`/`_is_open`
  一处不漏,**不挑调用点补**。
- **「这条路径算不算成果」答不出来时,不许当成「确定不算」。** 范围由 `_scope_prefixes()` 算,
  `resolve()` 抛 `OSError`(权限、符号链接层数、目录临时不可用)就整份交 `None`,`note_new` 据此把这
  一段记成「不可确认」;只有 `ValueError`(那棵树确定不在 vault 底下)才跳过它自己。两者压成一种的
  后果:一次临时故障把一份真回执筛成空集,再让结束行把这一轮定成确定的 0 条。
- **「新落下」和「重新写一遍」是两件事。** 导出队列的判据是 `exported_hash<>content_hash`,正文
  补抓、译文回写都会让老文章重新写一遍同一个路径;算进去的话同一篇会连着好几天被报成"刚抓到"。
  判据在写之前问一句 vault 里有没有这个路径(`sync._export` 的 `fresh`;公众号那边导出脚本本来
  只给新建的文件打 `[ok]`)。**范围另有一道在账本上**(`fetch_rounds.in_scope`):衍生树、停用的
  树、`skip_dirs` 不算 —— 和日报取材认的那批树同一份口径,交给每个采集器各判一遍迟早对不上。
- **公众号那条通道的回执来自子进程自己打的行**:导出脚本逐篇打 `  [ok] <天>/<文件名>`、开头打一行
  输出目录,`collector/cli.py` 的 `cmd_export` 把两样收进结构化事件,`wechat_local._receipt` 换算成
  vault 相对路径。**只有子进程判成功、而且清单完整的那一支给确定值**:超时后降级 `--no-images`
  重跑(第一趟已落盘的文章在第二趟算"已存在"被跳过)、子进程判错(写到哪断在哪)、`out` 不在 vault
  里(`KB_COLLECTOR_DIR` 指着旧采集器 / `KB_VAULT_ROOT` 两边对不上)一律返回 `None`。
- **`pending` 只回答「队列里还积着多少没进过日报的」,给 tooltip 用,不上按钮。** 它传 `day=''`
  (一个章都不排除)**而且只读这一次**。不许再补一次「今天那份带走了谁」的查询去扣减:账本**允许**
  出现「日报文件写好了、记账没写上」(那一档故意倒向"多报一遍",见上面放回/盖章那两条),拿它当
  "今天这份里有什么"的完整事实就会凭空报出新增(审查实测:注入一次 `mark_carried` 失败,文件里两篇
  素材俱在,面板却报「+2 条新内容」而真实新增 0);何况候选和扣除项来自两个读取时刻,中间别人提交
  一次,算出来的是两个版本拼起来的数(审查用线程屏障实测 `0 → 1 → 0`,期间一篇新文章都没加)。

**这个计数长在生成按钮里,不贴在覆盖区间那行字后面**(`daily.js` 的
`renderDailyGenButton`)。它回答的是"这次同步抓回来了什么",而覆盖区间那行回答的是
"这一份覆盖哪一段" —— 两件事挨在一起会串台(第一版就贴在那儿,仓库主人当场说
"容易让人误解")。配套四条:

- **按钮的名字跟着"目标那天有没有日报"走**:有就是「重新生成日报」(点下去覆盖它,
  所以还会弹一次确认),没有就是「生成日报」。写死成"重新生成"的话第一次用的人会
  以为自己漏了一步。**「这一次写到哪一天」只有一份口径**(`dailyTargetDate()`):
  按钮叫什么、要不要弹覆盖确认问的是同一件事。
- **六种事实六种说法,一句都不许并进别人**:抓过了 `第 N 次抓取 · +M 条`(品牌深绿;M 为 0 时退成
  灰)、今天一次都没抓 `今天还没有抓取`(灰)、后端答「不可确认」(`fetch: null`)`抓取次数读不出来`、
  还没问过后端(字段缺)整颗藏掉;外加**这一轮的条数全不全**那两档(`fetch.partial`):已知 M>0 时
  `第 N 次抓取 · 至少 +M 条`,一条都说不出来时 `第 N 次抓取 · 条数读不出来`。
  **什么都没抓到的那一次也是一次抓取**:`第 1 次抓取 · 0 条` 和「今天还没有抓取」是两句不同的话。
  **「不可确认」更不许说成「今天还没有抓取」** —— 那是把"不知道"说成"没有",而账本一次写失败之后
  它会一直这么笃定地说下去(旧实现把这一档整颗藏掉,等于干脆不告诉用户)。**下界更不许写成确定值**
  —— 勾了三个来源而第三个炸在半路时,用户会照着一个偏小的数决定不重新生成日报,而真落进库的比它多。
  `null`、`{'n': 0}`、`partial` 三者的分工在 `fetch_rounds.today`。
- **自定义区间照常显示这个数**(抓取事实和"这一份覆盖哪一段"无关),跟着藏掉的只有 tooltip 里那句
  队列积压 —— 后端算的是默认区间那一段。
- **tooltip 里不许写「会由后面几天的日报陆续带走」。** 补录每天有名额,而排到超过 `BACKLOG_DAYS`
  的会直接退出候选 —— 那是一句许不出来的承诺。口径:「留待后续日报择取(超出回溯范围的不再纳入)」。
- **只靠字色区分,不画底色药丸。** 实测 `--brand-soft`(#DFF0E9)和 ghost 按钮底
  (#EAEEED)差不到 2%,画了等于没画,留着就是一行看不见的声明。
- 删一份日报会把它带走的条目放回队列,所以 `deleteDailyReport` 要连 `loadDailyWindow()`
  一起调 —— 不调的话 tooltip 里那句队列积压还停在删之前。**按钮上那颗药丸不该跟着动**
  (删日报改变不了今天抓过几次),探针里正反两边都钉着。

旧名字「直接生成」跟着全仓换掉:面板按钮、空同步范围时前后端两处提示、定时那行
「每天 08:00 直接生成」(改成"只用已入库的内容生成")。

**空闲那一跳要把这个数字问回来**(`daily.js` 的 `refreshDailyPending`)。素材是从
**外面**进来的 —— 同步中心跑完一轮、CLI 补抓、定时同步,页面一个事件都收不到。只在
"日报从运行变成完成"那一跳重读的话,数字会一直停在打开页面那一刻(审查实测:后台插进
一篇,页面仍写着「没有新内容」,要点一次「改区间」再「接上一份日报」才更新)。

**服务器事实只有一个接收口**(`fetchDailyWindow`),抓取事实、队列积压、默认区间每次都接;
`dailyWindowDirty` 只许挡住**改写用户填着的那两个时刻**,挡不到事实本身。两件事绑在一起的
后果实测过两种形态:空闲轮询只把回包里的 `pending` 取走、把新返回的 `fetch` 丢掉,于是同步
在另一个窗口跑完而药丸一直写着「今天还没有抓取」(同一个页面请求的 API 已经返回
`n=1, added=3`);改过覆盖区间时 `refreshDailyPending` 和 `loadDailyWindow` 两处**一起**提前
返回,药丸从此永久停在上一次的次数。反过来也钉着:**空闲那一跳不填两个时刻输入框** ——
默认区间的截止时刻是"此刻",每跳重填会让展开着的「改区间」里的值自己往前跳,所以
`fillInputs` 由调用方给(整块重载才填,轮询一律不填)。

**名额必须盖得住进水量,否则它自己就是积压的来源**(`MAX_ITEMS` 120 → **260**)。
原来的 120 小于窗口内发布的实际进水:实测近 7 天 **184 条/天**(10-08~10-14 依次
188/198/152/128/207/215/203),于是每天约 50~64 条被名额挤出去 —— 而它们在下一个窗口
已经走过自己的发布时间,只能落进补录桶(10-01 以来累计 **656 条**)。补录那边进水
≈**84 条/天**(挤出来的 ~50 + 天生错窗的 ~34)而席位只有 60,**净涨 ~24 条/天**:
队列排干之后会自己重新涨起来,和抓取频率无关。260 覆盖掉 215 那个峰值还有余量,
"被挤出去"这条进水源整个消失,补录只剩天生错窗的那 ~34 条/天、低于 60 个席位,
积压才真正单调下降。上界不是估的:**453 条 / 11.5 万字符的请求实测跑通过**。

天生只能进补录的那 ~34 条/天是**结构性**的,不归名额管:digest/TLDR **100% 且永远**
(一期的 `published` 是期号那天 08:00,实际抓到是次日 09:18)、web/Anthropic **100%**
(列表页只给到日)、social 发布→抓到中位 13.8h、rss 18.3h。**不要顺手把窗口判据改成
抓取时间** —— 那会破坏日报正文里「按发布时间,不是抓取时间」那条承诺,要仓库主人拍板。

**没用「要点桶没用完的席位借给补录」那一招。** 它治的是另一侧(轻量日的浪费:10-14
那轮窗口内只有 112 条、要点桶空着 8 个席位,而补录外面几百条在排队),治不了重量日
**要点桶本身装不下**(207/215 条那两天,共享总额会让要点吃掉全部名额、补录归零);
而且补录一节的出稿长度是有上限的,把总量放成无界反而撑爆出稿。

**出稿长度不许随素材条数线性增长**(`kb/daily_prompt.py` 的 `_LATE_CAP`=30)。
`llm.chat` 的 `max_tokens` 是 8192,而补录那一节原来写死「每条一行」:超过约 150 条时
出稿会从素材清单中间直接截断,**而这一批条目照样全部被盖章** —— 盖章认的是"进过这一份
的输入"而不是"正文里提到了"(那是刻意的,见上面盖章那几条),于是一份坏产物配一批
写死的章,重跑也选不回来。一次为了排干 305 条补录,是手改提示词才跑出来的。
修法是让那一节**随条数退化**:`n <= 30` 照旧一条一行,超过就「按来源和主题归并、
最多 30 行」并把总条数告诉模型。两头都钉着(量少不许顺手也归并)。
**提到 260 之后输入翻了一倍,所以每一节都要有上限** —— 工具那一节原来一条都没有,
补了「最多 20 行」;要点 3~6、观点 1~4、速览最多 12 行本来就有。
换一节无上限就等于换个地方撑爆。

**提示词和取材分成两个文件**(`kb/daily_prompt.py` / `kb/daily.py`):两个上限各有各的
理由 —— `MAX_ITEMS` 的上界是模型吃得下多少素材,`_LATE_CAP` 的上界是出得了多长的稿。
混在一处的后果就是调前者时顺手把后者撑爆(daily.py 也正好到了 700 行上限)。

**还差一道belt:出稿真被截断时不该盖章。** 可靠信号是 provider 的 `stop_reason` /
`finish_reason`,但 `llm.chat` 现在只返回纯字符串,要穿过去得改它在两个供应商上的
共享契约(所有阶段都在用)—— 不在这条任务的边界里,留给仓库主人拍板。
上面那套上限是**由构造保证**出稿长度与条数无关,这一道只是兜底。

**补录席位要给最老的留几个**(`LATE_DRAIN`=10)。只按"新的在前"排的话,持续有新内容
进来时积压里最老的那些永远排不上队 —— 账本保住了它们、席位分配却让它们等到被
`BACKLOG_DAYS` 挡掉,等于换一种方式再丢一次。所以 `LATE_ITEMS`(60)里末尾 10 个席位
固定给发布得最早的那几条(它们离 30 天那条线最近)。

**启用那一刻的一次性盖章**(`daily_carry.ensure_ledger`)。
不盖的话账本一启用,库里两万多篇历史文章全都算"没上报过":实测 `BACKLOG_DAYS=30`
时第一份日报的补录候选是 **1918** 条,要几十份日报才排得空 —— 而那些内容在旧实现下
早就永久落选了,翻出来不是修复、是倒灌。

**判据有两维,缺一不可**:

- **盖不盖,看「它到得比最后一份日报还晚吗」**(`indexed_at > 链头的 window_until`)。
  **这一道承重。** 第一版只看 `published`,自由工作流审查第 1 轮当场打回:账本是
  **懒初始化**的,第一次真正跑到它可能已经是升级之后好几天 —— 用户先点「重试失败
  项」补抓一批、再打开日报面板,那一批的发布时间多半早于链头,于是**正好是这次要救
  的那批内容被永久写死**。实测复现:补抓一篇发布于前天的文章,首次初始化后
  `pending=0`、`generate` 抛「没有未上报过的新内容」、之后每一天也都选不到(`#seed`
  对任何真实日期都满足 `UNCARRIED` 的排除条件,而 `release()` 明确不放这批章)。
  同一条路还覆盖定时那条入口 ——「先同步再生成」是同步**跑完**才进 `generate()`,
  初始化必然晚于补抓。`indexed_at` 只会往前走,所以"到得晚"证得死;反过来老文章重新
  导出也会刷新它,那只是多报一遍,方向是安全的那一边。
- **盖到哪一天,看它的 `published` 落在谁的窗口里** —— 不能一律 `#seed`。同一天重新
  生成时 `UNCARRIED` 放行的是**这一份自己**盖的章;统一记 `#seed` 的话,把区间改回
  某份旧日报再重新生成,它原有的报道会被整份覆盖掉、一条不剩(同一轮审查实测:甲文
  在原文件里,覆盖后只剩新补抓的乙文,`docs=1`)。所以:落在某一份窗口里的记那一份的
  日期,比链起点还早的(以及没有发布时间的)记 `#seed`,**发布在链头之后的不盖**
  (属于下一份的要点桶),**落在链条缺口里的也不盖**(那一份已经不在了,它本就该回到
  队列)。
- **「发布在链头之后不盖」那一档是冗余带**(定点注入红 0 条):链条最后一个窗口就止于
  链头,这种条目在按窗口找归属时本来也落 `None`。留着是构造上的理由 —— 这一档该被
  显式处理过,而不是靠读代码的人去推 `next()` 的默认值。如实记着。
- **比 `published` 必须 `parse_ts` 之后再比**(四种写法,同一天里 `T` 排在空格后面);
  `indexed_at` 库里只有一种写法,可以直接比字符串。
- **一份日报都没有时**没有"链头"可言:分界线取 `first_days` 天前(那正是第一份日报的
  窗口起点),到达分界取"此刻" —— 库里现有的一律算存量。那时确实没有任何证据说明哪
  一条被报道过,而让头一份日报去回顾整个存档只会是一份噪音。
- 盖章 + 写 `daily_state.carry_epoch` 在**同一个 `BEGIN IMMEDIATE` 里**,并且在锁里
  重新查一次那个键(两个进程同时首访时,后一个在锁里就看得见前一个盖的章)。分类在
  锁外做(两万行读一遍、纯内存),锁里只落盘。

**落盘+记账 与 放回+删文件 要整体互斥**(`daily_carry.commit_lock`,`data/` 下自己
一个 lockfile)。两段各自内部的顺序只管**自己失败时往哪边倒**,管不住两段交错:审查
第 1 轮用线程屏障实测到这个顺序 ——

```
生成:_write(今天.md) 完成
删除:release(今天) → unlink(今天.md) → 返回 True
生成:mark_carried(今天, paths) → 成功
```

末态是"记着已上报、却没有任何日报文件"的一批条目,两头落空。阅读区那颗删除按钮在
生成期间本来就能点,所以不是理论上的交错。**不借用 `kb.maintenance` 那把维护锁** ——
那一把在一轮大索引里会被攥住几分钟,等在它上面等于让模型已经出完稿的那一轮卡在收尾;
这把只圈毫秒级的两段,不和任何别的锁嵌套。`delete()` 里的 `is_file()` 也要圈进锁,
否则判断和删除之间又开一道同样的缝。

**不取维护锁。** `maintenance-lock.md` 那条的判据是"写哪张表 + 写不写 vault 里的文章文件":
`daily_carried` / `daily_state` 只有日报自己读写,`daily/*.md` 不在 `SOURCES` 任何一棵
树下(清理脚本和索引都碰不到它),所以日报这条路本来就在那把锁的射程之外 —— 加了账本
也没变。反过来说也不能加:`generate` 中间是一次几分钟的模型请求,把它圈进那把跨进程
独占锁里会把面板同步、定时同步和日报一起冻死,而那节自己写着"模型请求留在锁外"。

**账本那一半在 `kb/daily_carry.py`**,只因为行数(`kb/daily.py` 到了 700 行上限)。
它不认识 vault 里的日报文件、也不认识取材口径,日报链由 `kb.daily._report_chain()`
从各份日报的 frontmatter 读出来传进去,两个模块因此不用互相 import。`STAMP` /
`parse_ts` 跟着搬过去,`kb.daily` 原样绑回自己的模块全局,所以 `daily.parse_ts`
这些既有写法照旧有效。**测试里必须把 `daily_carry.DATA_DIR` 指到 tmp**,不指的话
那把提交锁会去 flock **生产** `data/` 下的 lockfile(同维护锁那条)。

## 迁移盖章的归属:只认那一份自己的素材清单(自由工作流审查第 2 轮)

上一轮把盖章从"一律 `#seed`"改成了"落在某一份窗口里的记那一份",修的是"重新生成旧
日报会抹掉它原有的报道"。**按窗口推断这件事本身是错的**,审查第 2 轮用两条独立反例在
两个相反的方向上各打中一次:

| 形态 | 按窗口推断的结果 | 后果 |
| --- | --- | --- |
| 旧日报里的**补录** | 发布时间早于那一份的窗口 ⇒ 当成链条之前的存量、记 `#seed` | `#seed` 对任何一天的重新生成都满足排除条件,于是覆盖那一份时它一条都选不回来,**已经交付的内容当场消失** |
| 窗口里**当时装不下**的 | 发布时间落在窗口里 ⇒ 记成"那一份带走了" | 从此任何一份日报都选不到 —— **原任务要修的那条缝在迁移这一步原地复发** |

两处都不可恢复。判据因此换成**那一份日报自己的素材清单**(`daily._carried_keys` 从文件
正文里读回来,`daily._doc_key` 是素材身份的唯一口径、盖章和读清单两侧共用)。清单里认
不出的条目一律不盖章:方向按元规则取宽的那一边,放回队列最多多报一遍,盖错了是永久写死。

### 清单是拼装出来的,所以解析要顶住真实写法

实测生产库 10 份日报共 633 条清单条目,解析一版一版收紧:

| 写法 | 踩法 | 口径 |
| --- | --- | --- |
| 裸 `](url)` | `_md_dest`(套尖括号)是后来才加的,**2026-09-30 那一份整份都是裸写法** —— 只认尖括号就读不出它 90 条的归属 | 括号里那一截剥掉尖括号壳之后统一过 `_doc_key` 归一(`_md_dest` 幂等) |
| 账号名里带圆括号(`歸藏(guizang.ai)`) | 贪婪吃到行里最后一个 `)`,url 被截成 `<url>) — 大V观点·歸藏(guizang.ai` | `.+?` 配上「右括号后面紧跟分隔符或行尾」这个锚点 |
| url 自己带圆括号 | 那正是 `_md_dest` 存在的理由 | 非贪婪会先在它那里试一次、锚点不成立再往后退 |
| 标题跨行**而且带空行** | 大V观点的"标题"是推文正文前 500 字符;实测 2026-10-10 那一份 31 条都是这个形态,按行各认各的全判成认不出来 | 除编号开头的行,其余一律并回上一条,**不拿空行当分界** |
| 清单末尾那句引用块 | 跟着并进最后一条 | 链接那条正则**匹配到分隔符就收工**,不要求吃到字符串末尾 |

收紧过程(生产库 633 条里对得上的):裸写法 + 尖括号 431 → 跨行并回 436 → 不依赖结束
标记 468。剩下 165 条**对不上是对的**:按 url 去库里模糊找是 0 篇,它们已经被
`scripts/feed_trim_history.py` 那条存量清理从索引里删掉了,压根不可能再成为候选。

分隔符 `_REF_SEP` 抽成一份,`_page` 拼 refs 和 `_carried_keys` 解析共用 —— 两边各写一个
就是等着漂。

### 已经盖过章的库要跟着重算(`SEED_REV`)

账本是**懒初始化**的:盖过章的库直接走快路径返回。于是"修好的归属"只对从空库开始的人
成立,而最需要修的恰好是按旧算法盖错过的那些库。所以盖章算法带一个版本号
(`daily_carry.SEED_REV`),版本不一致时**整张表重算**。重算安全的理由是构造上的:每一份
日报带走了什么一直记在它自己的文件里,`mark_carried` 记的就是清单里那一批,所以重算得到
的和当初记下的是同一份;读不回来的按不盖章办(多报一遍,不写死)。**改盖章算法必须把这个
版本号加一。**

反过来钉一边:`test_seeding_is_idempotent` 末尾补了一句 —— 盖过章之后真生成的那几份,
不许被"重算"顺手清掉(版本一致时压根不进那条路)。

### 盖章也要和删除互斥

上一轮的提交锁只圈了"落盘 + 记账"和"放回 + 删文件"。**首次盖章是第三段**:读完日报链之后
另一个页面把其中一份删掉(`release` 放回它的章 + 删文件),这边再按过期的清单把那些章补
回去 —— 那一份日报已经不在了,它带走过的内容从此两头落空。审查用线程屏障实测到这个顺序:

```text
初始化:读取日报链,保存日期和窗口
删除:release(日期) -> unlink(日报文件) -> 返回 True
初始化:仍按旧的日报链插入迁移记录,并写入 carry_epoch
→ report_exists=false, ledger={"source/rss/race.md":"2026-10-10"}, material_after_deletion=[]
```

`BEGIN IMMEDIATE` 只保护账本那个事务,保护不了**之前**读进来的 vault 文件。所以
`ensure_ledger` 整段(读日报 → 分类 → 落账本)进 `commit_lock`。两处配套:快路径那次状态
读留在锁外(面板每一跳都走它,常态 0ms);**锁内要再问一次状态** —— 不问的话,前一个进程
盖完、之后又真生成过日报的那些章会被这边的 `DELETE FROM daily_carried` 一起清掉。
模型请求照旧在锁外。

675 这个数字是**这次修复的直接后果,不是缺陷**:它们是 09-29→10-10 这段里发布、而旧实现
按"时间窗 + 取最新 N 条"静默丢掉的内容(10-04/05/06/08 四份日报各只列了 31~32 条,其中
30 条还已经被存量清理删掉了)。抽样 40 条核对:标题在任何一份已有日报里出现过的只有 2 条,
而那 2 条都是**同一份稿子的副本**(量子位同题发了 7 次、另一篇在 InfoQ 和机器之心各一份)
—— 被带走的那一份盖着章,其余是另外的文档,不是匹配失败。按 60 条/份的限流约 11 天排空,
`BACKLOG_DAYS`(30 天)之内。

**不给标题加兜底匹配**:同稿副本会让"另一篇文章恰好同名"被当成报过了,那是在拿不可恢复的
方向换一点去重。

## 启用账本那一刻的三条缝(自由工作流审查第 3 轮)

上一轮把盖章的归属换成了"只认那一份自己的素材清单",判据本身是对的。第 3 轮打中的是
它周围三处:**升版重算时另一维跟着动了**、**清单读回来的边界在一种真实写法上错位**、
**账本启用之前日报就可能先没了**。三条的末态一模一样 —— 本该还在队列里的内容被盖成
`#seed`,而 `#seed` 对任何一天的重新生成都满足排除条件,**永久写死**。

### ① 重算只该修归属,分界线一个毫秒都不许往前挪

`SEED_REV` 升版会把整张表按当前算法重算。原来那句 `stamp = head.strftime(STAMP)` 在
重算那一趟取的是**当下**的链头,于是分界线跟着往前跳了一截:

```text
旧分界 09-28 08:00 → 61 篇补抓回来的文章 indexed_at=09-29 09:00,全都"到得晚",一个章不盖
一份日报带走 60 篇(LATE_ITEMS),剩 1 篇留在队列里等下一份
升版重算,分界线挪到 09-30 08:00 → 那 1 篇突然"到得不晚"了
  → 发布时间 09-26 早于链起点 → 记 #seed → 从此任何一份日报都选不到
```

`indexed_at > 分界线` 那一道的全部意义是"它到得比账本启用还晚,所以不可能被哪一份带走
过"。这句话一旦成立就永远成立,分界线往前挪等于把已经给出的豁免收回去。口径改成
`state.get(EPOCH_KEY, '') or head.strftime(STAMP)` —— **已经钉下的那个值原样用**,
只有从来没盖过章的库才现算。两维各管各的:归属按清单重算,到达分界线一次钉死。

### ② 推文正文自带有序列表,一条素材被拆成好几行

大V观点那一档的"标题"是推文正文的前 500 字符,里面常常自带编号列表:

```markdown
1. 今天分享两个实用技巧

1. 先阅读说明
2. 再运行示例 — 大V观点·某某(<https://x.com/…/status/12345>)
```

上一轮的解析是"行首 `N. ` 就是新的一条",于是这一条被拆成三条:真正那条只剩标题首行、
读不出 url,后两条是凭空多出来的身份。两个方向各错一次 —— 清单里认不出它 ⇒ 窗口里已经
报道过的观点次日又被取材一遍;而它发布时间若早于链起点,就被第三条规则判成 `#seed`,
**重新生成那一天时一条都选不回来**。

判据因此换成**结构**:编号开头的行只有在"上一条已经读完"时才开新的一条(`_closed`)。
读完的定义分两支 —— 链接那一支要等 `](…)` 那半边出现,没有链接的那一支要等
`REF_SEP`。不拿空行当分界(推文正文里本来就有空行),也不拿"行首是不是编号"当分界。

配套把链接正则的左半边收成 `^\[[\s\S]*?(?<!\\)\]` —— 标题里的方括号写出去时是转义过的
(`md_text`),不排除 `\]` 的话一条标题带 `[视频]` 的素材会在那里提前收尾,`](` 对不上、
整条读不出归属。

### ③ 删除要先把账本启用了再放回

账本是懒初始化的,**第一次真正跑到它可能是升级之后好几天**。这期间用户完全可能先删掉
一份日报:

```text
库里只有 09-28 那一份日报,账本还没启用
用户删掉它 → 文件没了(它带走过哪些素材只写在这个文件里)
次日打开面板 → 首访盖章,读日报链读到 0 份
  → 那篇文章发布于 09-27,早于"没有链头时取 fallback_days 天前"的起点 → #seed
  → 用户删日报的本意是"重新生成一份",而那篇文章再也选不回来
```

`delete()` 因此在放回之前先盖一次章(`carry.seed_locked`,它已经持着 `commit_lock`,
走不取锁的那个入口),把这一份的归属先读进账本,紧接着 `release` 把它们当场放回队列。
顺序是构造上的:证据(素材清单)只在文件里,文件一删就再也读不回来了。

## 清单解析这件事不会收敛,所以给结论加一道(自由工作流审查第 4 轮)

第 2 轮修「跨行标题」、第 3 轮修「标题自带有序列表」、第 4 轮又找出两种:**裸方括号
开头的无链接标题**和**标题末尾的成对反斜杠**。四种写法都是生成器自己写得出、解析器
读不回来的,末态每次都一样 —— 那一条交不出归属,落到"发布早于链起点 ⇒ 历史存量"
那一档记成 `#seed`,**重新生成那一天时一条都选不回来**。

这和日报出处编号那一节学到的是同一课(「手写规则的路走过三轮,每一轮都被真实渲染器
找出新的漏网写法,**这份清单不会收敛**」)。所以这一轮做两件事:把已知的两种写法
修对,**并且给"历史存量"这个结论本身加一道**,让下一种漏网写法的代价回到"多报一遍"。

### ① 没有 url 的那一支,标题是**裸**写进去的

`_page` 对无链接那一支一个字符都不转义(`f'{i}. {d["title"]}{_REF_SEP}…'`),所以
一条「[视频] …」开头的补录在清单里长得和链接那一支一模一样:

```text
1. [视频] 此前已经报道的补录文章 — RSS·某号 · 补录
2. [紧跟在后的另一篇](<https://example.org/companion>) — RSS·某号
```

上一轮的 `_closed` 按「以 `[` 开头 ⇒ 等 `](…)`」分支,于是第 1 条永远等不到它的链接,
第 2 条被并进来 —— 两条的归属一起丢掉,双双 `#seed`。

### ② 标题末尾的反斜杠是**成对**写出去的,那不是转义

`md_text` 把 `\` 写成 `\\`。标题「Windows 本地缓存目录 C:\models\」于是落成
`[… C:\\models\\](<url>)`,而 `(?<!\\)\]` 只问「紧挨着的那一个是不是反斜杠」,把这条
合法链接拒了。判据改成按**连续反斜杠的奇偶**:`(?<!\\)(?:\\\\)*\]`。

### ③ 收尾认的是整个「— 来源·账号」,而且只在最后一行上问

①的修法不能简单改成「有分隔符就算读完」—— 大V观点那一档的标题是推文正文,里面自带
一个 ` — ` 很平常,那一条会在半截处被切开。所以第二支认的是 `_ENTRY_TAIL`
(分隔符后面紧跟 `来源·账号`),而且只看**最后一行**:`_page` 把收尾拼在一条的末尾,
跨行标题中间那些行不该作数。

配套第三道:**编号得接得上**。清单是 `enumerate(shown, 1)` 写的,编号必然连着走;
推文正文里那截列表多半从 1 重新数起。三道各有各的独有射程,注入任何一道都有行为用例
变红(见下表),**缺一不可**。

### ④ `SEED_REV` 要跟着解析器走 —— 解析器也是盖章算法的一部分

改了清单解析却没动版本号,上一版真实盖错过的库命中 `_seeded` 快路径,修好的解析器
一次都跑不到:用户装了修复版,原补录照样回不来。版本号升到 3。

这条「忘了升版本」的失效模式没法由普通行为回归抓住(新版本号下的库怎么跑都对),
所以另有一条**按名单钉住**的回归:把解析那几个符号的 AST 摘出来算一个指纹,逻辑一变
就红,提示把版本号也带上。指纹走 AST,改注释和 docstring 不会红。

### ⑤ 清单上露过面的内容,不许判成「链条之前的历史存量」

前四条都是"再堵一种写法"。第五条治的是**后果**:读不出归属本来按"不盖章"办,可它
随后还要落到第三档上被盖 `#seed` —— 于是"解析漏了一种写法"的代价不是多报一遍,
而是**永久写死**。既然这份写法清单不会收敛,就给结论加一道:

```text
owner 里有            → 盖那一份的归属
indexed_at > 分界线   → 不盖(到得比账本启用还晚)
发布早于链起点:
    在某份清单上露过面 → **不盖**(证据不全,不许下终态)   ← 这一轮加的
    否则              → #seed
```

**判据的两道收紧都是拿生产数据调出来的**:

| 口径 | 迁移中被豁免 | 实际是什么 |
| --- | --- | --- |
| url 或标题,裸子串 | 324 篇 | 323 篇是同稿副本(每天重发的「量子位编辑作者招聘」一类) |
| 标题那一支只认**库里独一份**的 | 7 篇 | 6 篇是短标题(「git」「测试」「-」)撞在某条的中间 |
| 标题还要落在**一条的开头** | 2 篇 | 标题总写在条目开头,链接那一支多一个 `[` |

同稿副本那一档是关键:其中一份被带走过,**剩下几份是另外的文档、确实从没报道过**,
`#seed` 对它们是正确结论。拿标题兜底会把几百条同名稿子倒灌进后面几份日报。

**这不是"给标题加兜底匹配"**(那条禁止的是拿标题去**盖归属** —— 同稿副本会让另一篇
同名文章被当成报过了,方向是不可恢复的那一边)。这里只用来**否决**一个终态,同名撞上
的后果仍然是多报一遍。

兜底的独立射程实测过:把 `_closed` 换回上一轮那个读不出裸方括号标题的实现,审查自带
的三条边界反例**仍然全绿** —— 那条内容不再被写死,只是留在队列里等下一份。

### 假抬头有两个相反的方向,所以位置选不出真抬头

| 形态 | 假抬头在哪 | 「取最后」 | 「取最前」 |
| --- | --- | --- | --- |
| 模型在要点里把模板抄了一行 | 真抬头**前面** | 对 | 错(要点自己是有序列表时,那几行当场被切成素材) |
| 一篇文章的标题里写着这几个字(`日报模板中的 ## 素材清单 应该怎样组织`) | 真抬头**后面** | 错 | 对 |
| 一条推文原样贴了 markdown 提示词模板(`## 素材清单` 独自占一行) | 真抬头**后面**、而且**在行首** | 错 | 对 |

原实现取最后,所以后两种各踩一次。第三种说明「行首」这一道也拦不住 —— 推文标题是
原样写进清单的,它里面的换行在文件里就是真换行。

**判据换成抬头自己声明的条数**:`## 素材清单(N 条)` 是 `_page` 写的格式,候选倒序
各试一次,**切出来恰好 N 条**的那个才是真起点。这是结构性的,两个方向一起覆盖。

**一条都对不上就交空的。** 半截清单比读不出来更坏:前面那几条交不出归属,随后被
发布时间判成历史存量、永久写死;读不出来只是多报一遍。

## 覆盖那一轮的三步顺序,和「页面没见过 running」(自由工作流审查第 1 轮 · owWV)

### ① 覆盖成功、记账失败 ⇒ 被挤出清单的旧素材两头落空

重新生成同一天的日报时,`generate` 原来是两步:`_write` 整份替换文件 → `mark_carried`
把这一天的章整批换成新清单。顺序的理由写在注释里 ——「章盖不上只是这批素材下一份再
出现一遍(多报一次,看得见)」。

**那句话只对首次生成成立。** 覆盖那条路上,新文件已经把上一版带走、这一版没选上的
素材(名额挤出去的、补录轮不到的)从盘上抹掉了,而 `mark_carried` 的 DELETE/INSERT
是一个事务:它失败后 rollback,恢复的是**旧**那一份的归属。于是那几条素材
**既不在任何日报文件里,又被 `UNCARRIED` 判成已上报** —— 日报里看不到、下一份也再
选不到,不可恢复。审查用 1 + 120 篇样本(真实 `MAX_ITEMS`)在 `daily_carried` 上挂
一个故障注入触发器实测到这个末态,`generate` 还沿正常完成路径返回。

修法不是交换两步(那样落盘失败会把新素材提前写成已上报),而是**在落盘之前先把这一天
上一版的章放回**。三步因此变成「放回 → 落盘 → 盖章」,每一步失败都只倒向「多报一遍」:

- 放回失败:文件一个字节都还没动,整轮抛错,旧日报和旧账本都完好。
- 落盘失败:章已经放回,这一天的素材下一份重新带走;文件还是旧那一份。
- 盖章失败:文件是新的、这一天无章,下一份把这一天的素材再报一遍。

整段仍在 `commit_lock()` 里,所以和「放回 + 删文件」那一段不会交错。首次生成时那次
放回删 0 行。

`release()` 就是「把这一天的章放回」的唯一实现,删除那条路本来就在用它 —— 口径一份。

### 记账失败要在收尾文案里说出来

`carry_error` 原来只装进返回值、`progress` 打一行进 log。面板上那句收尾文案仍是一句
干净的「日报已生成:N 条素材」,用户看不出这一轮是降级完成的(这一天的素材会在下一份
里重复出现一遍)。现在 `daily_run._run` 把它拼进 `note`,和「N 个来源未同步成功」那半
同一个位置。

### ② 页面没见过 running 的那一轮,列表和正文永远不刷新

`refreshDailyStatus` 判「要不要重读列表和正文」用的是 `dailyState?.running && !s.running`
这个跳变。不同步直接生成那条路(素材不多时)在两次轮询之间就跑完了,页面一次都没见过
`running = true`:

- 按钮上那个数字归零了 —— 空闲每一跳都问 `/api/daily/window`(那是上一轮修的)。
- 列表和阅读区还停在上一版。审查实测:接口已经是 `docs=2, late=2`、正文含
  「素材清单(4 条)」,页面仍显示 `late=1`、3 条素材和旧的生成时刻,等多少轮轮询都
  不变,只有整页刷新才看得到新内容。

**提示归零了而正文没变**,正是这次任务「补抓之后重新生成要能看到新内容」的反面。

判据改成「有没有出现一轮新的**已结束**运行」,和 `pipe.js` 那条(`pipeDoneRun`)同一个
形状:`doneRun = s.running ? '' : (s.run_id || s.finished_at || '')`,和上一次记下的不同
就刷新。**身份认 `run_id`** —— `finished_at` 只精确到秒,而这一档治的正是跑得极快的
那种运行。所以 `daily_run` 给每一轮发一个 `daily-{N}`(`_run_seq`,只在 `_lock` 里自增),
`get_state()` 带出来。

三条配套:

- **第一跳不算新结果**(`dailyDoneRun !== null`):那时页面刚打开,正文本来就是现读的。
- **一轮只说一次**(比的是身份,不是「非空」):每跳都重拉列表会把用户自己点开的那一份
  顶掉 —— 他翻着上周的日报,十几秒后被 `dailyCurrent = s.result?.date` 拽回今天这一份。
- **不弹 toast**:这条路也会在别处(定时、CLI、另一个标签页)跑完一轮时走到,弹窗就
  成了噪音。`finished` 那一支照旧弹(用户在这个页面上按的按钮)。

`loadDailyReports()` 自己会重开当前选中那一份,所以刷新列表就顺带刷新了阅读区。

## 身份跨重启也得唯一(自由工作流审查第 2 轮 · owWV)

上一轮给每一轮日报发的身份是 `daily-{N}`,`N` 是模块级计数器。**它在重启那一刻归零**,
而旧页面还开着、手里攥的是重启前那个 id:重启后第一轮又叫 `daily-1`,和页面记着的
逐字相同,于是 `fresh` 不成立 —— 列表和正文永远停在旧版,正是上一轮要治的那个后果。

上一轮我判断过这个场景,结论是「重启后页面必然有一次成功查询读到空的 run_id,撞车
窗口极窄」。**那个判断漏了一环**:空闲轮询是 15 秒一跳,而「重启 + 生成」完全可以整个
落在一跳里(`./kb.sh restart` 之后手点一次同步正是 CLAUDE.md 写明的日常路径,桩模型
或素材不多时生成只要一两秒)。审查用真实服务重启 + 真实 API 生成实测到:页面读到了新的
`finished_at`(14:11:12),按钮归零,而正文还是 14:09 那 3 条。

两道,各管一段:

- **承重:身份前面加一段进程启动时现取的命名空间**(`daily_run._RUN_NS`,
  `uuid4().hex[:8]`,`_new_namespace()` 是它的唯一口径)。重启换一个,所以重启后那一轮
  不可能和重启前的任何一轮同号。
- **兜底:前端的身份是 `run_id` 和 `finished_at` 两段拼起来的**,哪一段变了都算新一轮。
  万一哪天 id 又撞上(另一种归零写法、另一个进程),完成时刻变了照样刷。代价是极端情况下
  多刷一次列表,按元规则换掉「静默停在旧正文上」。
  **不是**把判据换成时间戳 —— 它只精确到秒,同一秒里跑完的两轮拿它分不开。

### 反向验证(定点注入,各改一处表达式)

```text
① `_new_namespace()` 写死成常量      → 只有「跨重启不同号」红
② run_id 不带命名空间(回到 daily-N) → 只有「跨重启不同号」红
   (①② 都不碰「同一进程两轮不同号」那条 —— 两条各管一段,缺一不可)
③ 前端身份只取 run_id                → 浏览器:撞号那两条红(独占)
④ 前端身份只取 finished_at           → 浏览器只有**摆盘自检**红(页面记的身份里
   不再有 `daily-` 那一段),没有行为用例红
```

**同形状但没动的是管道那边**:`pipeline_state.new_run_id()` 给的是 `run-{seq}`,同一个
进程内计数器、同样在重启那一刻归零,而 `pipe.js` 的 `pipeDoneRun` 判据和这边一样。那是
另一条路上的事(管道的待处理数刷新),这一轮不越界去动它 —— 记在这里,免得下一个人以为
两边已经一致。

④ 如实记着:`run_id` 那一半在**浏览器层**没有独占的行为用例 —— 它治的是「同一秒里跑完
两轮」,而桩模型下一轮也要一秒以上,这个时序在页面上构造不出来。它的承重回归在后端那条
「跨重启不同号」上,外加那条摆盘自检钉住「身份里必须带 run_id 这一段」。

## 同一天的两次正文读取,先发后到的那份会盖掉新的(自由工作流审查第 3 轮 · owWV)

`openDailyReport(date)` 允许并发读取,返回时只问一句 `dailyCurrent !== date`。**同一天的
两次读取,这句话一个都挡不住**:用户点开今天这一份(这次读取慢),紧接着点「重新生成」,
生成完那一跳自动重读**同一天** —— 两次的 `date` 逐字相同,于是旧那份先发后到,把已经显示
出来的新正文、元信息和复制内容一起盖回旧版本。而完成身份已经记下,后面多少轮轮询都不会
再补刷,所以这不是闪一下:审查实测左边列表写着 5 条、正文只剩 4 条、按钮写「没有新内容」,
只有手动再点一次那一行才回来。

这一条**不是上一轮的改动引入的** —— `openDailyReport` 在整个任务 diff 里一个字都没动过,
触发它的「生成完自动重读」那一跳(`finished` 分支里的 `loadDailyReports()`)也在本任务
之前就在。上一轮新加的 `fresh` 分支只是多了一条同样会触发它的路径。

判据改成**两道,各管一段,缺一不可**(`stale()`,成功和失败两侧共用):

- `dailyCurrent !== date` —— 选中的已经不是这一天了。**删除那条路把 `dailyCurrent` 清成
  空串却不经过 `openDailyReport`**(所以序号一动不动),在途的那次读取只有这一道挡得住,
  否则刚删掉的正文会被画回阅读区。
- `seq !== dailyReadSeq` —— **同一天又读了一次**,这一次已经被替代。单调序号,进函数时取号
  (口径同 `pipe.js` 的 `pipeStatusVersion`)。

**失败侧走同一道判据**:被替代的那次读取报出来的错也是陈旧的,让它落到 UI 等于拿一句
「读取失败」盖掉一份已经读到的日报。

### 反向验证(定点注入,各改一处表达式)

```text
① stale() 只留 `dailyCurrent !== date`(去掉序号那道)
   → 浏览器 3 条红:「旧正文晚到也盖不回去」、「后面两跳轮询也没被它带回旧版」、
     「被替代的那次读取报错也盖不掉已经读到的正文」
     (红出来的 extra 正是报告描述的后果:阅读区从「3 条素材」退回「2 条素材 · 补录 1 条」)
② stale() 只留序号那道(去掉「不是这一天了」)
   → 只有「在途那次读取不许把删掉的正文画回来」红(独占;阅读区被画回了「今日要点」)
③ 失败侧退回只判日期
   → 只有「被替代的那次读取报错也盖不掉已经读到的正文」红(独占)
```

### 真实页面复现(独立无头 Chrome,CDP 直连)

沙箱日报页 98 项全绿(本轮新增 14 项)。

构造只控制**真实响应的到达顺序**,不碰响应体:`HOLD_REPORT` 包一层 `window.fetch`,把下一次
读今天这份正文的真回包扣住,放行时原样交还。**两份内容的差别靠真生成两次、各用一个区间
造出来** —— 窄区间(今天 00:00 起)把那条发布得更早的素材算成补录,宽区间(09-01 起)把它
算进要点,于是元信息那行字能分得出此刻屏幕上是哪一份(「2 条素材 · 补录 1 条」对
「3 条素材」)。摆盘各有自检,免得两份恰好同形时判据不敏感。

**失败那一侧伪造的只有「它失败了」这件事**(抛 `TypeError('Failed to fetch')`,浏览器 fetch
真正的网络失败形态),不是响应内容 —— 等 `pipeJson` 那 15 秒超时也能到同一档,但白等。

删除那一档要先把别的日报都删掉:`loadDailyReports(false)` 在还有别的日报时会去开那一份、
顺手把序号推进,第二道就把在途那次也挡了,第一道的独占射程会被遮掉。

## 没有 url 的标题碰撞,和先发后到的旧**列表**(自由工作流审查第 1 轮 · -8gPF)

### ① 无 url 的那条归属匹配不是硬证据

`daily_page.doc_key(url, title)` 在 url 为空时退化成 `'题:' + 标题`。盖章那一步
(`seed_locked` 的分类循环)原来是:清单里匹配上就写那一份的日期、`continue`,而
docstring 还写着「清单上有它就不问迟到那一道 —— 实际带走过是正面证据,比任何推断
都硬」。**那句话的前提是身份可靠,而无 url 时它不可靠**:两篇同名文档共享一个键,
于是真的新抓到的那一篇被旧日报抢走归属,`UNCARRIED` 从此永远排除它 —— 永久漏报,
而面板上写着「没有新内容」。审查用现有测试的隔离库实测 `pending.items=0`、
`collect().all()=[]`,生成直接答「没有未上报过的新内容」;另外在真实索引链路上
(两篇同名无 url 的 md、真跑 `kb index`、清掉启用标记模拟首次迁移)复核了同一结果。

**迟到那一道救不了它** —— 它排在匹配**之后**,匹配一命中就 `continue`,这一档压根
到不了。

判据改成:**无 url 的那一支只在「标题在库里独一份」时认**(口径同 `_on_a_list` 的
`once`)。证据不够就**一个章都不盖**:既不记这一份的归属,也**不往下走到 `#seed`**
—— 它在某份清单上露过面,判「链条之前的历史存量」同样是永久写死。留在队列里最多
多报一遍,看得见、补得回(元规则:漏报是静默丢数据,误报顶多重抓一次)。

`SEED_REV` 跟着升到 **5**:盖过章的库走快路径,不升版的话修好的判据对**已经按旧
算法盖错过的那些库**一次都跑不到 —— 而那正是最需要修的。顺带记一句:那条按名单
钉住的指纹回归只覆盖 `daily_page` 的解析器那一半,改 `seed_locked` 自己的分类判据
要自己记得升版。

上一轮给**正文**读取加了序号,但那只约束 `openDailyReport` 自己发的请求,**挡不住

## 旧那篇被清理之后,「库里独一份」当场失效(自由工作流审查第 2 轮 · -8gPF)

### ① `once` 数的是**当前**库,它证不了历史身份

上一轮把无 url 的那条归属匹配收成「标题在库里独一份才认」。审查指出这道判据选错了
维度:`once` 来自 `SELECT title FROM documents`,而 `store.remove_missing_documents`
把旧那篇收掉之后(来源下线、清理脚本删过、vault 里那篇 md 不在了),撞了名字的新
文章在库里就成了**唯一**叫这个名字的 —— 检查当场放行,归属照旧被旧日报抢走。后果
和上一轮逐字相同:`UNCARRIED` 永远排除它,永久漏报,面板上写着「没有新内容」。

审查的 `ledger-retention.py` 三个场景(首次启用 / 从版本 4 升级 / 对照组),前两个
实测:新文章被盖上 `2026-09-28`、`pending.items` 归零、`collect()` 空、生成直接抛
「没有未上报过的新内容」。本轮修复后三个场景的 `actual_new_document_carried` 全部
为 `false`、`pending_items` 全部为 1。

判据因此抽成 `_match_holds(title, when, late, until, once)`,**三道各排除一种「它
不可能是那一篇」,缺一不可**:

1. **库里只有这一篇叫这个名字**(上一轮那道)。同名两篇都还在库里、又都发布在那一
   份的窗口里时,只有这一道分得开「该盖的只有一篇」。
2. **到达不比分界线晚**。晚于分界线的那批是账本启用之后才入库的,哪一份日报都不
   可能带走过。这一道原来排在归属匹配**之后**(匹配一命中就 `continue`),对这一支
   是瞎的。
3. **发布不晚于那一份自己的截止时刻**。日报筛的是 `published`,比窗口截止还晚才
   发布的内容不可能出现在它的清单里。为此 `owner` 从 `{key: day}` 改成
   `{key: (day, until)}` —— 那一份自己的截止时刻是这一道的唯一依据。

三道都站在「宁可不盖」那一边。反过来钉一边:真的是那一篇旧素材重新导出时三道全过、
照旧盖章 —— 不是把所有无链接素材一概判新(那等于把补录的归属整类丢掉,重新生成
那一份时它一条都选不回来)。

`SEED_REV` 升到 **6**,把已经按版本 5 盖错过的归属一起改回候选。

## 到达早晚要问「那一份自己的时刻」,不是整条链的分界(自由工作流审查第 3 轮 · -8gPF)

### ① 全局分界答不了「那一份生成时它在不在库里」

上一轮给无 url 的归属匹配加了「到达不晚于分界线」。审查指出这道判据的参照物选错了:
`stamp` 是**整条链的**分界(首次启用时的链头,或已冻结下来的那个值),它只回答「这一批
是账本启用之后才到的」,答不了「**那一份**日报生成的时候这篇文章在不在库里」。于是一篇
到达落在**两份日报之间**的补抓文章三道全过:

1. 旧那篇已清理,当前库里标题唯一 ⇒ 第一道放行;
2. 发布早于所匹配那一份的窗口截止 ⇒ 第三道放行;
3. 到达晚于**所匹配的那一份**、却早于后面那几份和链头 ⇒ 第二道放行。

审查实测(`migration-boundaries.py`,首次启用与从版本 5 升级两条路径各一次):发布
09-27 20:00、入库 09-28 13:00 的新来源同名文章被盖上 `2026-09-28`,待报道归零,生成
直接答「没有未上报过的新内容」;另在真实 vault + 真实 `kb index` + 真实服务上复核,
`/api/daily/window` 返回 `items=0, late=0`,页面写着「重新生成日报 没有新内容」,点下去
真生成一份也不带它。

判据因此改成**逐项问所匹配的那一份自己的时刻**:`owner` 从 `{key: (day, until)}` 改成
直接记那一份 `PastReport`,第二道换成 `arrived > past.latest_pickup()`。

**`latest_pickup()` 优先用那一份自己记的 `generated`,读不出才回落到 `until`。** 这两样
不能等同:自定义历史区间的 `until` 可能比真正生成的那一刻早好几个月(覆盖
2026-01-01→01-02 的那一份是今天生成的),而它确实带走了今天入库的补录 —— 一律拿 `until`
当生成时刻会把那条合法归属判成「到得太晚」、放回队列,重新生成那一份时它一条都选不回来。
回落到 `until` 是**更严**的那一边(常规日报两者本来相等),方向上只会多报一遍。

**全局分界那一道原样留在「没命中任何清单」那条路上** —— 它在那里回答的正是它能回答的
那个问题(账本启用之后才到的,哪一份都带不走)。审查那句「修复不能通过挪动全局冻结分界
来实现」说的也是这件事:分界一旦钉下就不许再动。

`SEED_REV` 升到 **7**,把已经按版本 6 盖错的归属一起改回候选。

**顺带修掉了上一轮列为「不拦」的那条**:账本启用之后入库、随后真的被某一份日报带走过的
无链接文章,上一版会因为「到得比分界晚」在升版时被整条摘掉归属、重新进下一份日报(同一
条内容报两遍)。按那一份自己的生成时刻问,它的归属是真的,留着。回归
`test_a_document_the_chain_picked_up_after_the_epoch_keeps_it` 反过来钉住这一边。

#### 来源身份那一半:已评估,这一轮没做

审查建议里还有「及来源身份」。实测口径是对得上的:那 11 条无链接清单条目的尾巴
(`— 来源·账号`)和文档现拼出来的 `_label(source)·account` **逐字相同 11/11**,所以真要
做,当下的代价是零。独占射程也真实存在 —— 两篇同名、不同来源、**都在那一份生成之前**
入库,日报带走了旧那篇,旧那篇后来被清理,这四个条件同时成立时只有来源身份分得开。

这一轮没做,理由是它会**新增一类清单解析依赖**:归属的成立从此要求「`_label(source)·

但那是个**持续**的噪音源,换来的是一个四条件同时成立、审查也未复现的场景。真要加,
形状已经想清楚:`PastReport` 多一份 `(key, credit)` 对,`daily_page` 多一个解析函数,
`_match_holds` 第四道判「两边都解析得出且明确不同 ⇒ 拒」,注入侧把 `_label` 一起传下来。

## 出稿完成 ≠ 取材快照,外加清单里那半截来源(自由工作流审查第 4 轮 · -8gPF)

### ① `generated` 记的是出稿完成,它证不了「这篇文章进过那一份的输入」

上一轮把上界换成了那一份自己的 `generated`。审查指出它仍然不是取材时刻 —— 真实顺序是
**读素材 → 关连接 → 调模型(几十秒到几分钟)→ 落盘写 `generated`**,所以模型跑那段时间
里入库的文章满足「到达不晚于 generated」,却一个都没进过模型输入和这一份的清单。

审查实测(`generation-arrival.py`,真实 `daily.generate` / `collect` /
`remove_missing_documents` / 迁移 / `pending`,只有模型响应是本地桩,**桩在拿到已组好的
prompt 之后才写入新文档、并等到现实中的下一分钟才返回**,没有手改 `generated`、没有伪造
时钟):14:07:16 模型已拿到输入(里面没有 B),B 随后入库,14:08 真实写下
`generated: 2026-10-13 14:08`;清单里只有 A,待报道仍是 1 —— **生成那一次是对的**。清理 A、
退回版本 6 再升级重算之后,B 被盖成 `2026-10-12` 已报道,待报道 1 → 0,当天 `generate`
抛「没有未上报过的新内容」。另在真实 `kb.server:app` 上点过「生成日报」:按钮写「没有新
内容」,`/api/daily/window` 的 `pending.total=0`,点下去只得到失败横幅。

所以 `_page` 另记一行 **`collected`(取材快照,秒精度)**,由 `generate` 在 `collect()`
返回那一刻取。`latest_pickup()` 变成三档:`collected` → `generated` → `until`。
`generated` 保留在第二档,老日报只有它 —— 那一段窗口的风险由第四道兜住大半。

### ② 第四道:清单里本来就记着来源和账号,丢掉它等于自愿只拿间接证据

审查连着两轮点名:无链接匹配仍不核对来源和账号。前三道**全都只能排除**「它不可能是那
一篇」,而清单那一行的收尾(`— 来源·账号`)是唯一的**正面**身份证据。第三轮我评估后把它
留作后续,理由是「新增一类清单解析依赖、是个持续噪音源」;这一轮的实测说明只靠时间维度
会**一个边界一个边界地冒**(第 2 轮 `once`、第 3 轮全局分界、第 4 轮 `generated`),所以
补上:

- `daily_page.carried_credits()` 读出无链接条目各自记的「来源·账号」,`daily._doc_credit()`
  按**和 `_page` 收尾逐字相同**的口径拼出这篇文档该写的那一份(两处共用一个函数)。
- 判据是**两边都读得出、而且明确不同时才拒**。那一份没记下(老格式、收尾读不出)就不问
  这一道 —— 宁可少拒一次,也不拿一个没读准的来源去否决真实归属。
- 代价知情并保留:公众号改名、来源标签改写之后它会判成冲突、把归属放回,那是多报一遍。
- `· 补录` 那个后缀是 `_page` 另加的标记、不属于来源,读的时候摘掉 —— 不摘就会把**补录**
  那一档的真实归属全部判成冲突,而那正是最该保住归属的一档。

`SEED_REV` 升到 **8**。

### 顺带修掉了上一轮列为「不拦」的那条

`latest_pickup` 的 docstring 把三档各自的精度和方向都写明了。

## 推断给不出正面证据,所以让日报自己记下带走了哪几篇(自由工作流审查第 5 轮 · -8gPF)

前四轮一直在给「无 url 的那条归属匹配」加判据:第 2 轮加「库里独一份」,第 3 轮加「到达
不晚于那一份自己的时刻」,第 4 轮把上界换成取材快照、再加「清单记的来源·账号不冲突」。
每一轮都真的堵住了上一轮那个样本,而第 5 轮的复现说明这条路**有个上界**:

> 窗口内 121 条素材,`MAX_ITEMS` 是 120。A 进了清单,B 落选。两篇的**标题、来源、账号
> 逐字相同**,B 发布在窗口里、入库早于取材快照;A 随后被清理,于是 B 在库里成了独一份。
> 四道判据**一道都分不开它们** —— B 被盖成那一份的已报道素材,待报道 1 → 0,当天生成
> 直接答「没有未上报过的新内容」。

四道判据的形式都是「排除**它不可能是**那一篇」。全过只说明「没有证据否定」,不等于「有
证据肯定」。而「名额装不下」在生产库里天天发生(实测 2026-10-12 那一份:150 条素材),
所以这不是一个边角形态。**再加第五道判据也救不了**:两篇文档在**库里能读到的每一个字段上
都相同**,区别只在「当初模型看见的是哪一篇」—— 那件事只有当初那一次生成知道。

### 修在上游:把结论本身存下来

`mark_carried` 记的一直是**真实的文档路径**,问题出在升版重算:它 `DELETE FROM
daily_carried` 之后只能从日报文件反推,而清单那一行不带身份。所以让 `_page` 把它写进
frontmatter:

```yaml
carried_plain:
- source/rss/picked.md
```

**只记没有原文链接那几条。** 有链接的 url 本身就是身份、清单那一行已经存着它,而 `path`
会随标题或账号改名而变(slug 和目录都按它们拼),记下来反倒是个会过期的身份 —— 真实
生产库里 11 份日报的清单共 650 条,其中无链接的只有 11 条,名单因此很小。

盖章那边两条路分工(`seed_locked`):

1. **名单排在所有推断之前**。它记的就是当初盖的那一批,一一对应。顺带兜住「清单那一行
   解析不出身份」那一档 —— 名单在 frontmatter 里,不经过清单解析器。
2. `key` 撞上某一份、而那一份**交了名单**时:名单就是全部真相,一个章都不盖(它和那一份
   带走的只是**同名**)。那一份**没交名单**(现有的每一份日报都是这个形态)才回落到四道
   推断 —— 否则账本一升版就把上千条历史归属整批放回、倒灌进下一份日报。

`_match_holds` 的射程因此收窄成「没交名单的老日报」,docstring 写明了这件事和它的上界。

**另一处顺手改掉**:`doc.arrived > past.latest_pickup()` 改成 `>=`。取材快照和 `indexed_at`
都只到秒,同一秒里谁先谁后分不出来 —— 按元规则判不准就扣留(拒了最多多报一遍)。这一条
只对没名单的老日报那条路有意义;审查报告也明说了它**单独不足以**修复上面那个上限场景。

### 实测

两个复现脚本(`round-5/overflow-attribution.py`、`generation-boundaries.py`)修复后都翻过来:

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 121 条撞上 120 条上限,落选那篇 | 盖成 `2026-10-12`、待报道 1 → 0、当天生成失败 | 归属为空、待报道 1、当天日报真的把它作为**补录 1 条**带走 |
| 同秒到达(`collected == indexed_at`) | 同上 | 归属放回、待报道 1、当天补录 1 条 |

`round-5/minute-compatibility.py` 那条「不拦」项的两档也都成立 —— 但它的 legacy 档要**连
名单一起摘掉**才算真的老格式(那个脚本写的时候还没有这一行,只删 `collected` 不够):
有名单的那一份现在归属保留、**不再多报一遍**,真正的老格式仍然多报一遍(知情保留)。

**生产库只读试跑**(`immutable=1` + `.backup()` 到 tmp,日报目录复制一份过去):修复前后
账本**逐行完全一致** —— 21538 行、22668 篇文档、11 份日报,11 份全是老格式(名单是这一版
才开始写的),所以推断那条路行为逐字不变,`>=` 一条都没命中。升版重算跑一遍、结果相同,
用户看不到任何变化。

### 定点注入(九处,全部 FAIL、零 ERROR)

```text

② 名单查询排在推断之后(顺序反了)          → 4 条红
③ 有名单也照旧走推断(名单不否决同名)      → 2 条红(含复现 A 那条)
④ 同秒算"不晚"(>= 退回 >)                → 1 条红(独占)
⑤ `_page` 压根不写名单                    → 1 条红(独占)
⑥ `_page` 把有链接的也记进名单            → 2 条红
⑦ 名单成员 `str()` 强转(不认类型)         → 1 条红(独占)
⑧ 名单只防 `None`、不认别的类型           → 1 条红(独占)
```

**⑧ 第一版注入时是 0 FAIL / 48 ERROR,按上一轮那条教训先怀疑用例** —— 把 `isinstance`

摆 `carried_plain: 一行字符串` 的(yaml 解析成 `str`,**逐字符**迭代之后名单变成一堆单字符
path、盖不上任何东西,而「那一份交了名单」这件事成立,于是推断被否决、一个章都不盖)。

**⑥ 红的那两条里有一条是既有用例**(`test_a_url_on_the_list_is_enough_on_its_own`),它恰好

**①② 红的四条里有两条是既有用例**,它们跑真实 `generate`、素材没有链接,所以修复后走的是

## 推断整个退役:旧日报是升级时唯一存在的形态(自由工作流审查第 6 轮 · -8gPF)

第 5 轮把结论存了下来(`carried_plain`),但给**没有名单的那几份**留了一条回落 ——
照旧用四道判据推断。那一轮的事故记录还写着「生产库 11 份日报全是老格式,所以推断那条
路行为逐字不变」,并把它当成「向后兼容」。

**那恰恰是唯一会发生的那条路。** 名单是版本 9 才开始写的,升级时用户手里的每一份日报
都没有它。第 6 轮用 `git archive ea4182f` 解出版本 8 的代码、由**它自己的** `daily.generate()`
生成日报(没有手改 frontmatter、没有调小条数上限、没有伪造迁移版本),再把那份日报和
版本 8 的库交给当前版本:

| | 升级前 | 升级后 |
| --- | --- | --- |
| 账本版本 | 8 | 9 |
| 落选那篇在旧日报的模型输入里 | 没有 | 升级不会改变这件事 |
| 它的已报道归属 | 无 | `2026-10-12`(错) |
| 待报道 | 1 | 0(错) |
| 下一份生成 | 该补录它 | `LookupError`,没有未上报过的新内容 |

所以**推断这条路整个退役**:有 url 就按 url 认(url 本身是身份),没有 url 就只认名单,
名单上没有就按证据不足办。判据加到第四道也只是把「排除」做得更细,证不了「是同一篇」。

### 不盖章的代价是什么 —— 和前几轮 docstring 里写的不一样

第 2~5 轮每一条「期望盖章」的用例都论证过:「不盖章等于把补录归属整类丢掉,重新生成
那一份时它一条都选不回来」。**那个论证只对「盖错成 `#seed`」成立**,对「一个章都不盖」
不成立 —— `UNCARRIED` 是 `NOT EXISTS(… c.day<>?)`,没有任何章的文档必然放行。真跑一遍
钉死三件事(回归 `test_an_old_reports_unlinked_material_is_reported_once_more` 一条里
全测了):

```text
升级后它的归属            → 无
重新生成那一份选得到吗    → 是      ← 没有被写死
下一份会多报一遍吗        → 是      ← 这才是真实代价
盖成 #seed 之后再问一次   → 否      ← 前几轮真正担心的东西,和"不盖章"是两件事
```

所以「清单上露过面就一律 `continue`、不往下走 `#seed`」那一道仍然承重,而且**`_on_a_list`
兜底接不住它**:兜底的标题支要求"库里独一份"(同稿副本不许靠标题豁免),而同名两篇正是
这条路最常见的形态。定点注入去掉那个 `continue`,红的就是这一条。

`immutable=1` + `.backup()` 到 tmp,日报目录复制一份过去。修复前后逐行比:

少了这两条,一个「什么章都不盖」的实现会全绿,而那会让每一份日报的全部素材在升级后整批
倒灌进下一份。

**上一轮那条升级用例是假的,这一轮换掉了**:它摆的是「带名单的日报 + 版本 8 的账本」,
而版本 8 的代码压根不写名单 —— 那个组合在现实里不存在,所以它只证明了"新格式重算"。
现在摆的是无名单日报 + 上一版真实留下的错章(`test_a_genuine_legacy_report_does_not_consume_the_namesake`)。

## 归属只能由生产者给,账本要能被重放(自由工作流审查第 3 轮 · lk8E5)

两条都是前一轮那两条的**同一类**没修好,不是新问题。

### ① 旁观者的差集分不出「谁写的」

上一轮把记账从索引挪到了物化,但仍然是**在物化两端各取一次全 vault 路径快照、拿差集当成果**。
快照是旁观者的视角:它只看得见"文件多了",看不见"谁写的"。实测(审查 `reproduce.py`,真
`sync.export` + 另一个**进程**手工写入):本轮确定空抓、真导出器写了 0 篇,而物化期间另一个进程
放进一篇 `source/rss/manual.md` —— 药丸报「+1 条」。同类的还有实时 saver、手工导入、并行采集器、
常驻服务在这段时间里落下的文件;**挪动快照位置一条都修不掉**,因为"谁写的"这个事实只有写的人有。

改法是让生产者交回执:`materialize()` 返回它这一轮新写的那几篇(契约在
`kb/collectors/__init__.py`),管道只收回执、按来源各记一次。两个采集器都接上了 ——
feeds 那边 `sync._export` 本来就逐篇算出了 `rel`(它只是没交出来);公众号那边导出脚本本来就逐篇
打了 `  [ok] <天>/<文件名>`,现在连同一行输出目录由 `collector/cli.py` 收进结构化事件、
`wechat_local._receipt` 换算成 vault 相对路径。**交不出清单就报「不可确认」**,不给一个看着确定的数。

### ② 一次写故障之后,重放不许少记、也不许多记

上一轮把账本改成了追加 + 内存重试,修掉了表象,但没有恰好一次的保证。两条实测形态**都不用重启**:

- **少记**:数据目录短暂不可用让开轮那一行没写下去,随后物化真落了 2 篇。`note_new` 只查盘上有没有
  这一轮,查不到就把整份清单丢掉 —— 而开轮行这时正好补写成功,于是面板**笃定地**写「第 N 次抓取 ·
  0 条」,刷新也纠不回来。
- **多记**:`write` 成功而 `fsync` 报错(那几行其实已经进了文件),重试把同一行再追加一遍 ——
  存条数就翻倍,2 篇报成 4 篇。

四处一起改,口径都在 `kb/fetch_rounds.py` 的模块 docstring 里:

- **回执行存路径集合,折叠取并集** —— 同一行追加两遍、同一轮被两条通道各报一次、同一个进程重放,
  结论都一样。这是「重放不多记」的全部依据。
- **`_is_open` 盘上和手里都算** —— 开轮行还攥在 `_unsaved` 里时,它那一轮的回执照样记得下去。
- **攥不住的行换成「不可确认」标记,不静默切尾**(`_flush`);开轮行一律留住,它一丢后面的回执就成了
  对不上轮次的孤行、整份账本当场变成「读不出来」。
- **读、追加、轮换全在同一把文件锁里**(`_locked`,旁挂一个空文件 —— 轮换走原子替换,锁在被换掉的
  inode 上等于没锁)。**这把锁是叶子**:持有期间不许再取别的锁,否则面板每 15 秒那次读会撞上一整轮
  导出持有的维护锁。

### 「投影不完整不许解除不可确认」落在开轮行上

写失败之后进程就没了,那几行既没落盘也不在内存里 —— 这一刀仍然救不回来。但账本从此**不会撒谎**:
开轮时就记下这次运行后面跑不跑物化(`ex`),会物化却一条回执都没等到的轮次一律算「不可确认」。
两种运行在账本上长得一模一样(一条开轮行、没有回执),而一个的 0 条是确定的、另一个不是。
这同时答掉了「另一个进程看不见本进程手里那几行」:它读到的是 partial,不是一个确定的 0。

### 刻意保留的口径:补导积压算进这次同步

审查第二个用例(3 条 `fetched_at=2026-10-14` 的旧待导记录,本轮远端抓到 0 条,补导之后报
`added=3`)**是按用途刻意选的,不是漏判**。这颗按钮回答的是"要不要再花一次模型钱重新生成日报",
而那 3 篇此刻才进 vault、正是这一份日报能多拿到的东西;算回昨天那次抓取、今天显示 0,对这个用途
就是错的。要改成「这次从远端新发现多少」得在 `feed_items` 和本机绿泡泡库两处各加一列抓取身份,
那是另一件事,也得仓库主人先定口径 —— 同理「只勾了导出的那种运行算不算一次抓取」。

### 回归

  上那个数)。
- `tests/test_fetch_receipt.py`:回执说了算 / 说不出来报 partial / 范围筛选 / 真 `sync.export` 的
  「新落下」判据 / 公众号那条通道的换算与三种说不出来 / 坏编码账本不许拦住抓取。

### 反向验证(定点注入,各改一处表达式)

账本与回执十三处 + 采集器子树两处,全部 FAIL、零 ERROR;前端摘掉 partial 那一支,探针 2 条红
(`第 2 次抓取 · +2 条` / `· 0 条`)。两条值得记下来:

- **「几条线程各跑几轮」那种并发写法注入之后全绿** —— 轮换只在有过期轮次时触发,第一次重写之后就
  没有了,后面几十次开轮压根不走那条路。改成摆出来的交错(拖慢整份重写、期间另一条运行追加)才红。
- **坏编码那条一开始红成 ERROR**(异常穿出 `_run_crawl`)。判据是后果,所以用例自己接住异常判红:
  「异常穿出去 = 这一轮一个号都没抓」。

## 「交完了」要有一行明确的凭证(自由工作流审查第 1 轮 · lk8E5 / OVsIMej)

上一轮把成果归属从「旁观者的差集」改成「生产者的回执」,但**完整性**还是从「收到过任意回执」
推出来的。这一轮的三条实测都落在同一句上:**盘上那几行可以全部合法、也收到过某个回执,却仍然
不是完整的业务事实** —— 而旧实现在这三种情况下都给出**确定**的结论,所以刷新和重试都纠不回来。

### ① 开始不许冒充完整

`_run_export` 进门先 `note_new(key, ())`,折叠时任何 `paths` 行都把 `got` 置真,`today()` 又按
`ex and not got` 判缺口 —— 于是「刚开始」在盘上和「全部交完」一模一样。实测:真实 `_run_export`
里生产者执行真的 `sync.export('rss')`,随后 `os._exit(23)` 落在交回执前,vault 多了 1 篇,父进程
重读账本得到 `{'n':1,'added':0,'partial':False}`。多来源那一侧同形(第一个来源交完回执就足以让
整轮看着完整)。

改法:加一条 `end` 行,`note_end` 写在**逐来源循环之后**;`today()` 的缺口判据换成
`ex and not end`。于是「还没交完」和「确定 0 条」在盘上终于不一样了。存量账本行没有这一位,折出来
就是未完成 —— 那几轮只能说「至少 N 条」,因为新代码确实证明不了它们完整,这比继续笃定地报一个数
安全。轮换要把这一位抄过去,否则一轮完整的抓取过一次维护就退化成下界。

### ② 已经落进 vault 的文件不许因为后面那次确认失败而消失

`sync._export` 原来是「两道都要卡」:`os.replace` 成功 **且** `feed_items` 的 `exported_hash`
更新成功才进 `written`。实测用一个 `BEFORE UPDATE OF exported_hash` 触发器只拒绝确认(文件照常
落盘):vault 新增 1 篇、导出阶段报错,账本给 `{'n':1,'added':0,'partial':false}`;**删掉触发器
重跑也救不回来** —— 这一篇已经不是新文件(`fresh=False`),它永远进不了任何回执。

改法:`written.add` 挪到 `os.replace` 之后、UPDATE 之前。确认失败只意味着下一轮还会再导一次;
而"文件进了 vault"是既成事实,它会被索引、会进当天日报取材。公众号那条通道本来就是这个边界
(导出脚本写完文件立刻打 `[ok]`,子进程判错则整份 `None`),这一轮只对齐了订阅那一侧。

### ③ 没锁住就不许做覆盖式轮换

`_locked` 取不到锁时直接放行,而 `open_round` 里的 `_rotate` 是整份原子替换。实测把旁挂锁文件换成
目录(账本自身仍可正常读写)、用屏障拖住第一次 `_write_atomic`,让另一条运行完成开轮和成果确认,
再放行旧快照轮换:已经确认过的 `acknowledged-writer` **整轮消失**,只剩 `rotator`,`_read()` 仍然
`ok=True`,结论从 `added=1` 变成确定的 0 条。

改法:`_locked` 把「锁住没有」`yield` 出来;`_rotate` 没锁住就整步跳过,`today()` 没锁住就返回
`None`。**抓内容不受影响**(追加照做:`O_APPEND` 的单次写不互相截断,并集折叠让重放幂等),降级
只落在展示上。

### 顺带修掉的两条不拦项

- **N4**:攥在手里没落盘的那几行,原来只能等下一次抓取才补写,面板在这期间一直说「读不出来」。现在
  `today()` 发现 `_unsaved` 非空就先取独占锁 `_flush([])` 一次 —— 故障一好,下一次读自己就补上。
- **N2**:`/api/daily/window` 的接收层加了**代次**(同 `schedules.js` 那道门):发请求前占号,回包
  落地时被更晚的读取顶掉就整趟作废;填输入框前**再认一次** `dailyWindowDirty`,不按发请求时算出的
  旧判据覆盖用户刚填的两个时刻。

### 没有在这一轮动的(报告自己也判的不拦项)

- **N1**(停用来源的树身份 vs 文档 `source` 身份):它落在 `kb/scanner.py` / `kb/store.py` 的删除口
  上,改的是**唯一那个删除函数**的语义,而报告连续两轮都判不拦、并写明「不以它要求本任务额外扩边」。
  要动得先定「树归属和保护身份以哪一个为准」,那是仓库主人的口径。
- **N3**(模型正文截断没有强制识别):等共享 provider 返回契约拍板,本轮没有调用付费真实模型。
- **N5**:夹具末尾那行空白已经删掉(`git diff --check` 干净)。

### 回归

- `tests/test_fetch_rounds.py` 的 `CompletenessIsAnExplicitEndTests`:回执不等于交完、两个来源中途
  没了报下界、轮换保住「交完了」那一位、失锁不许把已确认的轮次轮换掉(并钉住失锁期间只说
  「读不出来」)。

### 反向验证(定点注入,各改一处表达式)

账本/回执两批共 18 处,**17 处定点红、零 ERROR**;前端两处各红到对应那一条
(`在途的旧回包…` 给出 `第 1 次抓取 · +1 条`;`等回包期间刚填的…` 给出
`since: 2026-09-01T00:00`),还原逐字节一致。三条值得记下来:

- **`_mark` 里「读不全就什么都不记」那一道注入之后是绿的,而它是真冗余。** 同一处
  紧跟着还有 `_is_open`,读不全时它认的那两个来源(盘上折出来的轮次、内存里那条
  开轮行)正好覆盖同一批情况,所以摘掉前一道判据的可观察末态不变 —— `today()`
  两种写法都给「读不出来」(`ok=False` 一直在)。保留它是因为便宜,**但不要为它
  编一条用例**。
- **「挤掉的行换成不可确认标记」那一条一度变绿**:这一轮加了 `end` 之后,那条用例
  里的轮次本来就「没交完」,缺口把标记盖住了。用例补上 `note_end` 才重新敏感 ——
  同一个数字有两个来源时,要把另一个按住才测得出这一个。
- **浏览器那两条的桩要「攥得住人」**:第一版按「下一趟」攥,结果攥到的是页面自己
  的空闲轮询那一趟,我们等的 promise 永不 resolve,探针挂住十几分钟、一行输出都
  没有。改成①先把空闲轮询停掉、②按回包序号攥、③等它真的停住再往下走,并且给
  等待加 3 秒上限(攥不到人就红,不许挂死)。

## 完整性要绑在子轮集合上,证据不许静默丢掉(自由工作流审查第 2 轮 · lk8E5 / OVsIMej)

上一轮加了那条明确的结束行,但三个分支没闭合:**结束行只罩住一次调用**、**读账失败会把已经交到
手里的回执就地丢掉**、**绕锁的追加没人保护**。三条都落在同一句上:恢复之后给出一个**确定**的数,
而那个数比 vault 里真有的少。判据一律是「这个数确定不确定」,不是「这个数等于几」—— 第二条实测里
`added` 恰好等于真实值,只看数字看不出问题。

### ① 结束凭证要绑整批:子轮登记 + 完成集合

`daily_run` 按来源依次发起 N 次 `FETCH_STAGES`,它们共用一个批次身份,而 `_run_export` 每次都写
一条结束行;折叠时 `end` 一旦置真就永远是真。实测:第一个子轮写一篇并正常收尾,第二个**真实子进程**
同 key 再跑抓取/导出,写出第二篇后 `os._exit(23)` 不经任何 finally —— 两篇 md 都在,读出来仍是
`n=1, added=1, partial=false`。

改法:账本多两种行 —— `{'key','seg'}`(这个子轮开工了、它会物化)和 `{'key','seg','end'}`
(这个子轮交完了);`open_round` **每次调用**都登记自己(轮次本身仍幂等),`today()` 的判据换成
`segs == ends and (segs or not ex)`。**集合而不是计数**:一次 fsync 重放会把计数推成完整,集合取
并集则重放幂等(这和回执存路径集合是同一条理由)。结束行同时把自己记进 `segs`,所以只勾导出的那种
重试不会把一轮交齐的抓取反而钉在「至少」上。轮换要把 `segs - ends` 和 `ends` 都抄过去。

子轮身份就是这次运行的 `run_id`,和业务 key 在同一处算出来(`pipeline_batch.round_key`)——
`pipeline_stages` 原来那个 `_round_key()` 搬了过去:身份是批次那一层的事,而且那个文件正顶着 700 行
上限(搬完 693)。

### ② 读账短暂失败,不许把已经拿到的回执丢掉

`_mark` 读到 `ok=False` 就直接 return(回执、unknown、结束行三者都走它)。实测只在写出文章后的
**下一次**账本 `read_text` 注入一次 `OSError`、之后完全恢复:末态 `n=1, added=0, partial=false`,
`_unsaved` 空,盘上有空回执和 end、没有那篇文章的回执;重读同一文件折叠仍自称完整。隔离网页里用真实
`sync.export` + 真实 `kb index` 跑同一故障,API 和按钮都写「第 2 次抓取 · 0 条」,tooltip 说「新加了
0 篇」,刷新不变,**而恢复后再导出也不会把它当新文件**。

改法:两份进程内事实。`_opened` = 本进程亲手开过的轮次 —— 读不出账时它顶替 `_is_open`(自己开的那一
轮一定存在),那一行照旧追加;`_gaps` = 真的没留住行的轮次 —— 结束行据此一并写上 `partial`,于是
「恢复后未补齐证据不得仅凭一个 end 解除未知」落在**盘上**,换个进程重读也仍然说「至少」。两份都按
`_KEEP_KEYS` 挤最老的,挤出去那一档落在安全侧。

### ③ 所有写者同一套互斥协议:没锁住就一行都不写

上一轮只禁了「失锁者自己轮换」,反过来那一半没堵:进程 A 持锁、读到旧快照、停在原子替换之前;
进程 B 仅 `flock` 失败(其余文件系统调用正常),真实写出 `source/rss/ack.md`,开轮、回执、end 全部
追加成功、`_unsaved` 为空;A 随后按旧快照完成轮换 —— B 已落盘的整轮消失,`today()` 自称确定、报
`n=1, added=0, partial=false`,那篇文件还在。

改法:`_flush` 只在持锁时真写,否则把行留在 `_unsaved`。于是**账本的每一次写都在锁里**,没有"没人
保护的追加"可被覆盖;失锁期间展示降级成「读不出来」,锁一回来攥着的那几行照旧落盘。

**这一刀的边界要写下来**:锁长期取不到(旁挂文件被占成目录、目录只读)时面板一直说「读不出来」。
这是**有意的**,理由是"能不能上锁"是**数据目录**的属性而不是进程的属性 —— 管道就跑在 kb-web 进程内
(见 CLAUDE.md「服务与运行时」),读的那一侧和写的那一侧要么都能锁、要么都不能,所以不会出现"一个
进程笃定地报一个少记的数"。真要出现混合情形(两个进程以不同身份跑、只有一个能上锁),那个失锁进程的
整轮不会进账 —— 代价和"它进账之后被持锁者抹掉"一样,但这一版至少在它自己那一侧如实说「读不出来」,
而且不需要第二个账本来记"这里缺了一行"。

### ④ 同类静态位置:范围没读全 ≠ 确定不在范围内

范围),而 `note_new` 又按这份范围过滤真实回执。报告标的是推断,没实测 —— 这一轮按它改了口径并补了

只跳过它自己(**反过来钉一边**:否则存量配置里有一棵外挂树,每轮都永久写「条数读不出来」)。

## 「没有留下参与证据」不等于「没有参与」(自由工作流审查第 3 轮 · lk8E5 / OVsIMej)

第 2 轮把「交完了」绑到了子轮集合上,但那一层只看**成功登记在盘上的**子轮。审查据此指出同一条
拦项的两个未闭合分支 —— 判据仍是那一句:**不能仅因剩下的行合法、已知的子轮都交齐,就断言整次抓取
和全部回执完整**;「没有留下参与证据」不等于「没有参与」,「缓冲变空」不等于「全部已确认」。两条的
根不变量都加在**比触发路径更上一层**的地方,不是在复现到的那一条调用点上打补丁。

### ① 登记行没落盘的子轮也要留下参与证据(`kb/fetch_pending.py`)

实测形态:真实 `_run_crawl`/`_run_export` 里第二个子轮开工时旁挂锁被占成目录(登记行只进了
`_unsaved`),它写出第二篇之后 `os._exit(23)` —— 盘上第一个子轮那一套行行行合法,`segs == ends`
成立,API 和按钮报**确定的「第 1 次抓取 · +3 条」**,而当批真写了 4 个文件。

修在**「参与过」这件事的持久化**上,不在 `today()` 的判定式里加特例:`_flush` 每次搬动缓冲都把
「我还欠哪几轮」原子写成一笔按进程命名的凭证,**不取账本那把锁**(锁坏掉正是要留证的那一档)。
硬约束、三处口径(保留窗口同源 / 落了盘就撤 / 读不出来算说不清)和剩下那一档真救不回来的形态,
写在上面硬约束一节「『参与过』这件事不许只存在账本里」那条。

**为什么不是「整批未完成凭证」或者「拿开工标记交叉确认」**(报告给的另两条路):
- 整批凭证(开轮行记 `pend`、只有 `daily_run` 收尾才写 `bend`)在**日报那条批次**上成立,但它把
  「批次还开着」和「某个子轮丢了证据」混成一句:一次同步跑半小时,这期间面板一直只能说「至少」,而
  报告自己那条 `test_03`(读账失败恢复后要回到**确定**值)在它下面会变红。它也盖不住**没有批次的
  单轮**(单来源同步、重试失败项)——那一档的开轮行和登记行是同一次 `_flush` 写的,一起丢掉之后
  账本里连那一轮都不存在,拿更早那一次的数当今天的答案照旧少报。凭证那条两档一起闭合。
- 开工标记(`kb/pipeline_open.py`)是**可信的**业务运行凭证,但它证明的是"有一轮起跑过" —— 直接拿
  「标记还在」当未完成的判据会把"只有一份终态写失败"和"只勾了索引的运行"一起误报成未完成,而且它
  只认**最后**那一轮(单文件覆盖),多子轮的中间那个丢了证据它一个字都不说。**本轮因此没有用它。**
  这一节当时还把它写成了另一头的闸(「数据目录写不进去时它落不下来、那一轮压根不起跑,所以账本和
  凭证一起写不进去那一档不会产生外部影响」)—— **第 4 轮审查证伪了这条推理**,于是它以「按抓取/
  批次口径关联身份」的形式当了一轮第三处证据;**第 5 轮审查又把这一步整个否掉了**(标记的寿命是
  那一轮运行的,不是那笔欠账的 —— 正常收尾就清掉),见后面「证据的寿命」那一节。本轮这句
  「**没有用它**」的结论最后是对的,理由也正是这一条:它只认最后那一轮、而且随运行收尾消失。

### ② 确认只许移除自己真写下去的那几行(`_flush` 的缓冲协议)

实测形态:`_flush` 取了 `_unsaved + objs` 的快照,`_append` 在锁外做 I/O,成功之后一句
`_unsaved = []` —— 这期间另一条线程压进来的回执被一起抹掉。面板每 15 秒读一次、而 `today()` 自己
就是那个补写的人,所以这不是理论上的交错:审查用屏障摆出来,末态是那一篇永久不进账(重导时已经
不是新文件)而 `today()` 自称确定。

修在**缓冲的排队/确认**这一层:三份内存状态的读写一律过一把进程内的 `RLock`,确认**按身份剔**,
锁序钉成「文件锁 → 缓冲锁」且缓冲锁里不许做 I/O 之外的任何取锁动作。覆盖面是按函数闭合的,不挑
调用点:`_push`/`_seen`/`_pending`/`_flush`/`_is_open` 全在锁里,于是持锁、失锁、读账失败、轮换、
`today()` 补写五条路自然都过同一套协议。细节见硬约束一节「那份缓冲是两条线程共用的」。

**缓冲锁本身没有独立的红,这是如实的**:交错是用屏障摆定的,观察得到的丢数据全被「确认按身份剔」
堵住了;锁是**冗余带** —— 它挡的是将来某个写者绕过这几个函数直接碰那三份状态。所以这一轮的红落在
确认协议上(注入①),锁的职责写进注释而不是靠一条测不敏感的用例冒充覆盖。

### ① 账本和凭证会一起写不进去,而开工标记写成功推不出它们可写

实测形态(审查 `reproduce.py:test_01`,全程真代码):真实 `pipeline.start_pipeline` 起跑、真实
`mark_open` 落盘成功(证据里留着那一笔的身份),**之后**才把旁挂锁占成目录、把凭证目录的路径占成
普通文件;采集器真往 vault 写出第二篇,两条路径恢复后紧接着 `os._exit(23)`(`finally` 一句都跑不
到)。末态:两篇文件都在,盘上只有第一个子轮那一套合法的行、一笔凭证都没有,本进程和**全新进程**
都报 `{'n':1,'added':1,'partial':false}` —— 不是故障期间暂时读不出来,是笃定地少报。

旧版文档把这一档判成不可达,依据是「数据目录写不进去的话开工标记也落不下来、那一轮压根不起跑」。
**这条依据不成立**:开工标记在 `kb/pipeline.py` 起跑闸那里**先**写,另外两条路径稍后才写,早先某
一个文件写成功推不出稍后另外两个文件一定可写(更推不出所有文件永远共享同一种故障)。

修在**证据协议**上,不在 `today()` 里加特例:

- **第三处证据 = 那笔开工标记本身**(新模块 `kb/fetch_claim.py`)。它和账本、凭证不一样 —— 不是
  尽力而为的旁文件,而是**起跑的前提**(落不下来就不许起跑),所以凡真抓过的运行盘上一定有过它。
- **按抓取/批次口径关联身份,不看「标记还在」。** 标记里多记两样(`pipeline_open.mark`):`batch`
  (没有批次的独立运行留空,键的还原走 `pipeline_batch.round_key_of`,**和 `round_key()` 同一条
  算法**)和 `fetches`(crawl 在不在计划里 = 当日账本上开不开一轮)。读侧:标记指的键不在账本里 →
  整句「不可确认」;键在、而它那个子轮没有登记行 → 这一轮按**下界**报。缺了这两个字段(老格式)
  或者读不出来 → 「说不清」,不是「没抓过」。
- **位置按账本自己那个数据目录解析,名字只有一处算**(`fetch_claim._marker`:`DATA_DIR /
  pipeline_state._open_file().name`)。直接用 `_open_file()` 的绝对路径会在只打桩了账本一侧的环境里
  读到**另一个库**那份标记 —— 测试共用 `KB_DATA_DIR`,那是「一条用例的残留带红别人」和「审查脚本
  读不到本该读到的标记、静默放过一次少报」两头都踩的写法。
- **三处一处都留不下就不许往下抓**(`open_round` 那道闸,只管会物化的调用)。继续抓就是产生一批
  永远不会进账的文章(重导时它们已经不是新文件)。**不拦两种**:不物化的运行,以及账本整份读不
  出来 —— 那时读侧只会答「不可确认」,而坏掉的展示账本不许把抓取拦在采集器之前。闸的判据读回来
  问(`_landed`),不看写的时候返回了什么:凭证写不上是不出声的,它的返回值证明不了什么。

### ② 过期清理会按旧内容删掉所有者刚写上去的新一代

实测形态(审查 `reproduce.py:test_02`):清理方 `_load` 读出五天前那份、判了过期;所有者这期间真实
`_certify` 把**同一个路径**原子替换成当天的身份、真写出第二篇;清理方随后按先前读到的结论
`unlink` 那个路径 —— `current_certificate_removed=true`,两篇文件都在,而重启后仍确定报 1 条。
可达性不靠「新进程撞上同一个随机名」:**常驻进程本来就一直用同一个 `TAG`**,上一次撤销失败
(`put` 吞掉了 unlink 的 `OSError`)之后它空闲跨过保留窗口再工作,旧文件和新文件就是同一个路径。

修法是报告给的两条之一 —— **不可变分代身份**(另一条是「同一互斥协议」,没选:凭证那一笔是在进程
内缓冲锁里写的,给它再加一把跨进程锁就把锁序从「文件锁 → 缓冲锁」拧成了三层,而真正要防的只是
「删掉的不是我判过期的那个版本」):

- 一次写就是一代,路径是 `<TAG>-<第几代>.json`,**代号只增不复用,路径上的内容从此不改**。
- 清理删的是「我刚读出来、判了过期的那个路径」—— 那个路径不会再变新,所以「判过期」和「删掉」
  之间不存在那一类。
- 所有者只收**自己写新一代之前就看见的**那几代:两条线程各写一代时,后写的那一代一定不在先写者
  的名单里,所以**最新那一代永远留在盘上**。
- **新一代没落下来就一代都不许收**(`put` 的 `older = []` 那一支):旧的那几份是「我还欠着行」唯一
  的说法,删了就回到「盘上一个字都不说明它参与过」。
- 同一进程留下好几代时 `held` 取并集:多报「至少」是安全的一侧,漏掉任何一代都是静默少记。

### ③ 坏记录不许阻断生产者(报告 N5,不拦验收那一条也一并修了)

`_load` / `_fold` 原来各列了一张异常单子(`OSError, UnicodeDecodeError, ValueError`),而**深嵌套
JSON 抛的 `RecursionError` 是 `RuntimeError` 的子类**,一个都不沾。审查实测:一份 1100 层嵌套的
凭证(或账本行)就能让 `open_round` 抛出去 —— 而 `put` 每次都要经 `_prune` 读**别人**那几份文件,
所以一份手改坏的旁文件能把整次同步拦在采集器之前,生产者 `fetch` 调用次数 **0**。

口径收到一处:`pipeline_persist._loads_json`(`except Exception`,**不碰 `BaseException`** —— 吞掉
`KeyboardInterrupt` 等于让 Ctrl-C 失灵),`_load_json` 在它上面,账本逐行、独立凭证、开工标记三处
都过它。读侧保留「说不清」,不把坏记录当空数据。

### 为什么这一轮没有把闸做成「写不上就拒绝起跑」

那是 `pipeline_open.mark` 的形状(边界落不下来就不起跑),放在这里会和本块另一条硬约束对撞:
**账本是展示用的,坏掉的展示账本不许把抓取拦住**(`_read` 那条、以及本轮 N5)。所以闸的判据不是
「有没有写成功」,而是**「读侧会不会笃定地少报」**:三处证据任一还在、或者账本整份读不出来(读侧
一律答「不可确认」),都放行;只有「账本读得出来、里面没有我这一笔、凭证也没有、标记也不认」
才拦 —— 那正是后来会笃定少报的唯一状态。

### 这一轮没动的东西

per-item 的 `(抓取身份, 内容身份)`、远端新发现与补导旧内容之分、export-only 算不算一轮,仍在独立

## 证据的寿命:哪一笔**算**证据,不是哪一笔还在(自由工作流审查第 5 轮 · lk8E5 / OVsIMej)

第 4 轮把「参与过」的第三处证据收在了那笔**开工标记**上,理由是它不是尽力而为的旁文件、而是起跑的
前提。审查这一轮指出:那条理由对的是**它写下来的时刻**,管不了**它什么时候被拿走** ——
**不能从「最新那份标记现在不存在/指向别人」推导「没有尚未入账的子轮」。**

### 实测形态:不用硬退出,正常收尾就够了

审查 `reproduce.py`(全程真代码,一条安全断言 1 FAIL / 0 ERROR):第一个子轮真实
`start_pipeline(['crawl','export'])` + 真实 `sync.export` 写两篇、正常收尾,账本确定 `added=2`;同一
批次的第二个子轮仍走真实 `start_pipeline`,**开工标记成功落盘之后**才把账本锁路径占成目录、凭证
目录占成普通文件;它真写出第三篇并交回路径,**不杀线程、不注入终态保存失败**,让真实 `_end_run`
完整跑完 —— `running=false`、`finished_at` 非空、`persist_error` 空,两份终态都在,**而那笔开工标记
被正常收尾清掉了**,四条未入账的行只剩在那个进程的内存里。进程 0 退出。恢复两条占位路径后,两次
**全新进程**都报 `{"n":1,"added":2,"partial":false}`,而三篇文件都真在 vault 里。

标记一共有三个会被拿走的时机,全都和那笔欠账无关:**正常收尾删除**(`pipeline_state._end_run`,
两份终态一写上就 `clear`)、**下一次起跑覆盖**(两个起跑入口都写自己那一笔)、以及它只认**最后**
那一轮(单文件)。所以「它不在」能说明的只有「上一轮运行收尾了」,说明不了「没有欠账」。

### 修法:闸和读侧只认**寿命和欠账绑死**的证据,标记整条退出抓取账本

报告给的方向是「把参与证据保留到它的回执或不可确认状态已可靠落盘,统一约束收尾删除、下次覆盖和
过期清理」。本轮按这条判据重新挑证据,而不是去给标记续命:

- **登记行**(账本里那条 `{key, seg}`):追加即不可撤,只随保留窗口轮换(和凭证同一个 `_floor`)。
- **那笔独立凭证**(`kb/fetch_pending.py`):手里还欠行就在,行一落盘就撤,分代之后连清理也只能
  撤销自己判过期的那一代(第 4 轮那条)。

两处都正好活到「这一笔欠账交清」为止,所以**它们不在就是真的没欠**。闸(`open_round`)和读侧
(`today()`)现在都只认这两处,**`kb/fetch_claim.py` 整个删掉**,开工标记里那两个只为抓取账本加的
字段(`batch` / `fetches`)也一并摘掉 —— 留着等于邀请下一个人再据它推一次。`round_key_of` 的唯一
外部消费方是它,算法折回 `pipeline_batch.round_key` 一处。

闸因此在这一档落下来:**两处都记不下就不许往下抓**,盘上那笔标记认不认这个子轮都一样。那一档
**单独一个异常类型**(`fetch_rounds.NoEvidence`),编排那一侧(`pipeline._run_pipeline` 的 crawl
分支)据它把原因写进阶段卡片和日志 —— 收尾只会补一句通用的「流程中断,未完成」,而这道闸的全部
代价都押在「误报看得见」上。类型要窄:拿 `RuntimeError` 当判据会把采集器自己抛的运行时错误也说成
「抓取没有起跑」,那句话会把人引到磁盘和权限上去。

### 为什么不是「给标记续命」

报告的建议读起来更像后者,本轮没选,理由是**它要同时钉四处,而每一处都新添一条锐边**:收尾删除要
先问抓取层欠不欠(可以);下一次起跑的覆盖要把没交清的身份**继承**进新标记(于是这份名单只增不
减,得再加一条「什么时候可以忘掉它」);而「忘掉」的判据只有两个候选 —— 「账本里已经有它」(那
一轮被轮换清掉之后永远不成立,面板从此永久「不可确认」)或者「按日子过期」(宿主机时钟和项目时区
差半天,判错的方向正是静默回到那个少记的确定数)。**一条不健全的推理换三条新锐边,不划算。**

反过来,去掉那条推理之后的代价是**一次看得见的拒绝**:账本和凭证都写不下去(而数据目录照旧可写,
典型是上一次事故留下的 `fetch_rounds.lock` 目录或 `fetch_rounds.pending` 文件)时,每次同步的抓取
阶段红一条、上面写着该看哪里。按本块一直用的那条口径 ——「漏报是静默丢数据,误报顶多重抓一次」
—— 这一头是对的:那几篇文章一旦落进 vault 又不进账,重导时它们已经不是新文件,补不回来。

### 边界(本轮没动)

  闸管不着。它和「export-only 算不算一轮」是同一个决定的两面,整条仍在独立任务 `vB1WvxsM3GVs`。
- per-item 的 `(抓取身份, 内容身份)`、远端新发现与补导旧内容之分,同上;共享绿泡泡库的 schema
  一个字没动。报告的 N1 / N2 / N3 是旧项且明确不拦,本轮没碰。

## 读不出账不是证据,行序不是业务序(自由工作流审查第 1 轮 · lk8E5 / C2vVyQ)

上一轮(第 5 轮 · OVsIMej)把参与证据收成了两处:登记行、那笔独立凭证。这一轮审查在**同一个准入
不变量**下找到了另一条成功出口,又在它旁边找到一个独立的排序问题。两条都是**真实落盘 + 真实导出**
复现的,脚本在 `free-review/C2vVyQ4GgHrz/round-1/`(`safety_checks.py` + `review_fixture.py`)。

### F1:`_landed` 把「这一刻读不出账本」当成了证据

**形态。** 两条写路径一起坏着(旁挂锁被占成目录、凭证目录被占成普通文件)时,`open_round` 会退到
`_landed` 问一句「盘上还留得住吗」。那一版的第一句是 `if not ok: return True` —— 账本读不出来就放行。
审查在这上面加了一手:**只对起跑那两次账本读注入 `OSError`,随后恢复**。于是闸放行、真采集器
`fetch` 跑了、真 `sync.export` 又保存 1 篇、管道**正常收尾**、进程 0 退出;恢复两条路径之后,全新
进程读出来是 `{"n":1,"added":2,"partial":false}`,而 vault 里有 3 篇。再抓一轮同一批次,回执是空的
—— 漏掉那篇已经不是新文件,**补不回来**。

**为什么那条理由不成立。** 旧理由是「读不出来不等于我那一行没落下去,而且那时读侧本来就只答不可
确认」。后半句只在账本**永久**坏在盘上时成立。`_read` 的 `ok=False` 还包括一次瞬时 `OSError`:
**「这个请求读不到」推不出「将来的读者都会知道这一轮不全」** —— 读失败一过去,盘上剩下的就是此前
那几个完整子轮,集合相等、没有缺口凭证,于是重新给出一个确定的偏小值。

**修法:读失败只让我们看不见登记行,不代表证据在。** `_landed` 现在是

```
rounds, ok = _read()
if ok and any(...那一行在...):  return True     # 读得出来才谈得上「登记行在盘上」
return key in fetch_pending.mine(_pending_folder())
```

于是准入不变量闭合:**获准物化的每个子轮,盘上都有一份寿命覆盖它那笔欠账的证据**(登记行追加即
不可撤;凭证手里还欠行就在)。误报的方向也按既有口径钉住:**账本坏着、而凭证写上了的那条路径照旧
放行**(坏掉的展示账本不许把抓取拦在采集器之前),不物化的运行照旧不拦。

### F2:`mine[-1]` 把物理追加顺序当成了业务起跑顺序

**形态。** 账本是多进程追加的,而一轮的行可能晚落盘。审查用两个真进程摆出来:A 轮 11:00 开、交 2 条
回执和结束行,`_append` 返回 False(行攥在内存、凭证写上);B 进程 12:00 正常开第二轮、交 1 条,整轮
落盘;A 的写故障恢复,`today()` 顺手补写。此刻**两轮全在盘上、谁都不欠行**,物理顺序却是
`later-round` 在前、`earlier-round` 在后 —— 面板写「第 2 次抓取 · +2 条」,时间退回 11:00。重放同一
份文件还是这个答案,所以不是竞争窗口,是**投影契约**写错了。

**修法:让顺序成为数据的函数。** 开轮行上多一笔 `t`(`%Y-%m-%d %H:%M:%S.%f`,定宽零填充,按字符串
比就是按时间比;分钟级的 `at` 照旧写,展示和存量账本都只有它)。`fetch_fold._order_key` 给出
`(day, 起跑时刻, key)`,`_fold` **排好序再交出去**,`_rotate` 整份重写时把 `t` 一起抄走。几处细节各有
理由:

- **`day` 放最前**:存量行的 `at` 万一不是完整日期,也只会乱在它自己那一天里,不会跨天错位。
- **平局拿 `key` 兜,不拿物理位置兜**:同一微秒开的两轮没有真实先后可恢复,而补写、重放、轮换重写
  必须给出同一个答案 —— 拿行号兜平局就又把顺序押回文件布局上了。
- **存量行没有 `t`**:退回 `at + ':00.000000'`,同一分钟内排在带 `t` 的新行前面(那几行确实是更早的
  版本写的)。只增不减,老账本一个字都不用改。
- **同一轮重复开的那几条开轮行取最早那个起跑时刻**:读失败那一档会给同一个 key 再写一条开轮行,
  按「先见到的那条」算的话「这一轮几点开的」又变成行序的函数。

用例 —— 那正是「分钟级精度不够」这句话唯一能被证伪的地方。

## 一轮算哪一天的,也不是行序说了算(自由工作流审查第 2 轮 · lk8E5 / C2vVyQ)

第 1 轮按「业务起跑顺序」修的是**同一天里两轮的先后**;第 2 轮指出同一个不变量没修完整 ——
「业务结果与重放/追加顺序无关」不只管时分,**日归属也在里面**。报告判成「旧 F2 这一类尚未修完整」,
不是另一条新问题。复现脚本在 `free-review/C2vVyQ4GgHrz/round-2/crossday_check.py`。

**形态。** 同一个业务身份可以有多条开轮行(读失败那一档,`open_round` 走的是「没见过这一轮」那条
分支),跨零点时那两条**不同天**。第 1 轮的合并只换 `at`/`t`,`day` 还留着物理上先遇到的那一条:

```
盘上(物理序):{"day": "10-16", "at": "10-16 00:01", ...}   ← 第二个子轮,先落盘
             {"day": "10-15", "at": "10-15 23:59", ...}   ← 23:59 起跑那条,晚补写
折出来     :{"day": "10-16", "at": "2026-10-15 23:59"}    ← 自相矛盾的一份事实
```

`today()` 按 `day` 筛当天那几轮,所以错的不止 tooltip:**今天还没同步过,药丸就说「第 1 次抓取 ·
+3 条」**(那 3 条是昨天的),今天真的第一次同步之后它又跳成「第 2 次」。把同一组合法行按子轮整组
交换再折一次,答案变成 10-15 —— 数据相同、布局不同就换答案,所以是投影契约,不是竞争窗口。

**修法:起跑事实整份取同一条行。** `fetch_fold._start(one)` 交出 `{day, at, t}` 三样,`_start_key(one)`
决定几条开轮行里挑谁:

- **`(0/1)` 那一位是「知不知道起跑时刻」,不知道的不许顶掉知道的。** 存量行、手改坏的行可能连 `at`
  都没有;让空的赢就等于把这一轮的 `day` 也抹空,它从此落不进任何一天,面板永久说「今天还没有
  抓取」而那一轮真抓了。
- **两条都知道时取最早那一条**(「先见到」又是行序)。
- **两条都不知道时拿 `day` 兜平局,不拿物理位置兜。** 这一档没有真实先后可恢复,但答案仍要是数据的
  函数;往早的那天算也是安全那一侧 —— 记在今天会让药丸多报一次抓取。

消费侧一个都没改口径:`_order_key` 仍是 `(day, 起跑时刻, key)`(现在两样来自同一份事实)、`today()`
仍按 `day` 筛、`_rotate` 仍从折好的轮次整份重写 —— 于是**轮换顺带成了归一化者**:两条开轮行压成一
条,带着规范化后的那份事实。漏了这一步的后果是矛盾被永久固化,而原始两条行已经没了。

### 红在哪儿(这一轮新增的五处注入)

| 注入 | 红在哪儿 |

| `_fold` 重复开轮那一支整支删掉 | 新增四条 + `..._reopened_after_a_read_failure_keeps_its_first_start`、`..._rotation_writes_the_round_back_onto_its_own_day` |
| 起跑事实只换时刻、不换 `day`(第 2 轮那个形态) | `..._started_yesterday_is_not_todays_first`、`..._same_events_in_either_layout_answer_the_same`、`..._rotation_writes...`、另两条 |
| `_start_key` 不分「知不知道起跑时刻」 | `..._an_open_line_without_a_start_time_cannot_erase_the_day` |
| `_start_key` 两条都没时刻时不拿 `day` 兜 | `..._two_open_lines_with_no_start_time_still_pick_the_earlier_day` |
| 重复开轮取**最晚**那一条 | 上面全部 + `..._a_ledger_we_cannot_read_right_now_is_not_evidence_either` |
