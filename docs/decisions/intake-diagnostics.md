# 「问题与待办」(kb/intake_diag/ + kb/web/intake_diag_api.py + kb/static/js/diag*.js)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是事故形态、实测
> 证据和回归清单。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

这块面板存在的理由:一轮同步跑完之后,面板答不出「**还有多少条在等、卡在哪一环、为什么**」。
排查那天库里真实的积压是 RSS 待补 212 条、RSS 补抓重试耗尽 226 条、网页专栏耗尽 1 条 —— 那三个数
当时**只能手写 SQL 问出来**,而耗尽那一档在屏幕上连一个痕迹都没有(它按设计离开队列、按 feed 原本
那份壳走完导出,一切看起来正常)。

## 硬约束

- **详情那一屏不加次级标题,也不复述下面排着的按钮。** 原先每块都顶着一行小标题
  (「收录进度」「最后一次失败的原话」「接下来会发生什么」「这一条的身份」),而下面那块
  东西自己就长着那个样子:四段进度条、灰底等宽的证词、一段话、一组事实;身份那块还把
  四句话摆成四个灰框,每句前面挂一个说明它是什么的词(「内容编号」「收进来的时间」)。
  建议里也不再写「用『从浏览器采集』最省事,否则试『换链接』」—— 那几颗按钮就排在这段话
  底下,顺序还是后端按主次给的(`lanes.Lane.exits`)。
  **留下来的只有屏幕上看不出来的那些**:再试一轮会不会还是同一个结果、它的壳入没入库、
  这一下要不要花模型的钱、「立即执行」的射程是整类来源。还有一句**解释屏幕上没有的东西**
  的话也留着:来源问题那一侧明说这里为什么没有「不再收录」(`tests/intake_diag_probe.mjs`
  钉着 `不该被用来停用一整条订阅`)—— 人找不到那颗按钮时,下一步多半是去别处乱点。

- **它和同步中心那个「需处理」答的不是同一个问题,屏幕上不许共用那个词。** 这一份数的是「**全库**
  还有多少**条内容**没走完收录」(量词是**条**);同步中心数的是「**这一轮 / 今天**那几**步**欠不欠
  账」(`kb.pipeline_retry.today_failed` / `owed_now`,量词是**步骤**)。两个数字天生不一样,同一屏上
  两个数配同一句话是最糟的那一种 —— 人会以为其中一个坏了。所以这块面板那一组叫**「待决定」**,页头
  那行事实数字写明「条」,并且由**服务端**给出一句话明说另一份在哪(`overview` 的 `note`)。
  **不许反过来去改 `pipe_view.js` 的「需处理」** —— 那个词在那边和重试那颗按钮是同一个数字,它的
  口径有自己那一份决策文档(`retry-scope.md`)。
- **每一档的判据都从它真正的主人那里取,这一层只做分组和排序**(`lanes.where`):补抓三档转手
  `fulltext.queued_sql` / `held_sql` / `exhausted_sql`,翻译两档转手 `translate_scope.queued_sql` /
  `RETRY_SQL`。**一条新的 WHERE 都不许发明** —— 发明一条的后果是面板上的数字和管道真正会取的那一批
  分叉,而人照着面板做决定。
- **计数、列表、分桶三处必须用同一份判据**(`lanes.exclusive_where`),而且**各档要互相减掉前面
  那几档**(`lanes.probes` 的顺序就是「一条内容算哪一档」的唯一答案)。原始判据彼此**本来就重叠**,
  这不是 bug:一条正文试满额度的英文内容按设计会带着那份壳走完翻译和导出
  (`fulltext.unsettled_sql` 刻意放它过去),所以它同时满足「正文重试耗尽」和「待翻译」。屏幕上它
  只能算一条,而且只能算在**根因**那一档 —— 人要做的是把正文弄对,不是再买一次翻译。
- **「等着写入知识库」那一档不许要求 `fulltext_at` 非空,挡住重复计数的是**档位顺序**。**
  那 212 条还没补抓的壳确实也满足 `exported_hash<>content_hash`(导出闸门正扣着),但补抓三档排在
  它前面,`exclusive_where` 已经把它们整个减掉了。把那一道写进这一档自己的判据里,顺带把**压根不需要
  补抓**的内容一起挡在面板外面 —— 自带中文全文、来源没开补抓的条目 `fulltext_at` 永远是空的,于是它
  **一个档位都不属于**:顶上那个「还有多少在等」漏掉它,点进去也找不到,而它就是真实积压里最常见的
  一类(自带全文的博客、手动收录、网页专栏)。
- **「已完成」那两档要自己带一句「知识库里就是这一份」**(`exported_hash=content_hash`),不许靠
  「排在后面」推。补抓成功 ≠ 已交付:正文刚补齐、还没轮到导出的那一条,此刻库里躺的还是那个几十字的
  跳转壳(或者什么都没有),算进「已完成」等于告诉人「这件事办完了」而检索里压根搜不到 —— 而它恰好
  是这条链上最常见的中间态(补抓和导出是同一轮里先后两步)。**档位顺序只保证它不会被数两遍,答不出
  「它算不算完成」。** 详情里那三句话同理:「还没写进知识库」/「知识库里就是这一份」/「知识库里躺着
  的是它早先那一版」按这一条自己的导出回执分开说。
- **「已完成」的判据只许落在成功时间戳加交付回执上,绝不许挂在失败计数上。**
  (`fulltext_at<>''` / `translated_at<>''` + 时间窗 + `exported_hash=content_hash`。)要求
  `fulltext_tries>0` / `translate_tries>0` 的写法等于「只认失败过又成功的那几条」,而这条链上**三条
  到达成功的路都会把那个计数清零或压根不碰它**:`release`/`reopen`/`relink` 放回队列时清零、翻译成功
  写入时**必定**清零、人工粘贴一次失败都不制造。于是「重试 → 成功 → 入库」这条最常走的路跑完之后,
  那一条**一个档位都不属于**:文件在、回执对上、成功时间非空,而列表和聚合共用的那份判据把它排除了,
  人在「已完成」里找不到自己刚处理好的东西(审查实测 `lanes.split` 返回的桶名是空串)。**夹具里手工
  种一个 `fulltext_tries=1` 的完成样例只证明「这种种子显示得出来」**,证不了真实成功那一条进得了档 ——
  所以回归要从真实 `requeue` → 补抓/翻译 → 导出一路跑到分档。
- **「已完成」要盖住三条到达成功的路,纯入库那条也算。** 一条自带中文全文、不需要补抓也不需要翻译的
  内容,`fulltext_at` / `translated_at` **永远**是空串 —— 只有那两档的话,人在面板上对它点过「立即
  执行」、它也真写进了知识库,而他在「已完成」里找不到结果(报告原话:这几档「不是一个覆盖成功后
  状态的闭环」)。所以 `feed_items` 加一列 `exported_at`,**由交付确认那一句和回执同一笔写下**
  (`sync._export` 里那条带判据的 UPDATE),`ingest_recent` 档按它取。**那一档排在另两档之后**
  (`probes()` 的顺序),所以补抓 / 翻译成功的那几条照旧归各自那一档、不会数两遍;它照旧自己核一遍
  `exported_hash=content_hash` —— 那个时刻记的是**最近一次**交付,内容在那之后又更新过时这一条要回到
  待办里(反过来钉一边)。老库那几千行补空串 = 不在任何回看窗口里,行为逐字不变。
- **「还没取到全文」「需人工确认」「确定失败、预算耗尽」三档必须分开,不许统称「抓取中」。** 三者的
  下一步完全不同:等一轮调度 / 人看一眼 / 人决定要不要再给一轮额度。统称之后那 226 条又变回看不见。
- **「立即执行」的射程必须说实话,而且那句话由服务端给**(`actions.scope_of`,前端只负责显示)。
  留在前端的后果是改了阶段清单没人想起去改那句话,而那句话正是人据以决定要不要花这笔钱的全部信息。
  三条真相:`pipeline.start_pipeline(stages, crawl_filter=...)` **只有 `export` 这一段认
  `crawl_filter`**;`index` 是整个 vault 的增量比对、要拿维护锁、和来源无关;`extract` 走
  `kb.extract.pending_docs(conn)`,**压根没有来源参数**,按全库取数、花模型的钱。所以**「只执行这
  一条」做不到,按钮上不许这么写** —— 顶上那颗叫「立即执行本类」,逐条那颗的确认框里如实写着
  「范围是整类来源,不只是你点的 N 条」。`export` 里的 `materialize()` 还会联网补抓并调用翻译模型,
  那也算射程,也要写进去。
- **`actions.RUN_STAGES` 必须和 `kb.web.browser_capture_api.CONTINUE_STAGES` 逐字相等。** 两处各自
  演进的话,同一句「条目化提取不在这一步」会在一个页面上成真、在另一个页面上变谎。这是结构红,行为
  用例证明不了它。
- **确认框弹出时签一张计划凭证,提交时按现态再签一张比一比**(`actions._ticket`,`/run` 的
  `plan`)。不绑凭证时 `/scope` 和 `/run` 各按「此刻这几条在哪一档」重新选路:确认框里写着「条目化
  提取不在这一步」,而等待期间那一条补抓完成、变成待翻译,提交时就改走了另一条路、另一份射程 ——
  **用户同意的是一份计划,跑掉的是另一份,而那一份要花模型的钱**。只给「正文→翻译」这一种转换加一个
  if 治不了它:反向转换、混选变化、来源在确认期间改指都是同一类。凭证绑的是**整份计划** —— 路由名、
  kind、阶段清单、来源 id、付费射程指纹,以及选集里**这几世的这几条**(`key` + 档位 + `life` +
  `content_rev`,见 `lanes.identities`)。**不绑展示数字**:「此刻队列里 N 条」每一轮同步都在变,绑进
  去等于让人每次都重看一遍一句没变过的话。路由名签在最前面,所以两条路的票**不可能互换**。
  `/run` 不带凭证一律 400,对不上一律 409 且**什么都不许开始**。
- **来源那一档的票签的是「这条订阅此刻长什么样」,不是它的编号。**(口径只有
  `kb/intake_diag/warrant.py` 的 `source_sig` 一份 = `source_id` + `rev` + **实际通道** +
  **当前通道的下界** + `actionable`,`subscriptions.rev` 在 `save_subscription` 的 UPDATE 里 `rev+1`。)
  `problem_id` 就是「编号 + 问题类型」拼出来的,所以序列:确认框写着「重试来源 A」→ 人在停留期间把
  这条订阅改指到 B → B 也连接失败 → 回到那个还开着的确认框点「开始」—— 编号没变、问题类型没变、
  证据原话都可能一字不差,于是票对得上,实际重试的是 B,还带着「人按的、跳过退避」(审查实测
  `same_plan=true`)。**不签 `url` 本身**:地址 A→B→A 之后那个字符串逐字复原,而代次只会往前走
  (同上面那条「可复原的输入值不是身份」——**计划身份不能由稳定编号和路由名代替完整执行输入**,
  这是和 R2 同一类)。`since` 另外单独签:确认框里那句「保留的同步下界是 X」承诺的就是它,而它由采集
  进度改(`merge_config`)、**不经 `save_subscription`、因此不动 `rev`**。`actionable` 同理(它还取决于
  整条来源的设置)。**刻意不签 `evidence`**:同一条订阅每一轮失败都会重写它,签进去等于让人每轮重看
  一句没变过的话(口径同上面那条「不绑展示数字」)。
- **下界要按这一轮真正会用的那条通道取,不许按固定顺序试几条取第一个非空值。**
  (`warrant.source_floor` → `x_channels.watermark(source, channel_of(settings))`,和真跑那一轮
  `x_channels.prefetch` 同一个取法。)三条通道里 `timeline` 压根没有水位键、`attach` 和 `browser`
  共用一个:两条通道都留过水位时,按顺序试出来的是**另一条**通道的下界,于是确认框里承诺的「保留的
  同步下界是 X」和这一轮真正用的那个不是同一个值。**通道本身也要签进票**:两条都配好时「都能跑」
  不等于「是同一份计划」—— 切一下通道,`actionable` 不变、`rev` 不变,而有效范围和执行路径整个换了。
- **验过的那一份描述要带着去开工,一路交到执行和写入处;只在入口核一次关不掉那个窗口。**
  `/run` 把 `plan['expect']`(`{source_id: sig}`)交给 `intake_api.start_sync(expect=...)`,那边
  **在它本来就只读一次的那份 `reg.subscriptions(kind)` 上**比对、对不上一律 409,**然后把它随
  `crawl_filter['expect']` 交下去**(按 `reg.id_target` 索引,和 `accounts` 同一个身份口径);
  `pipeline_stages._run_crawl` 从 `_scope_entries` 那一份读它、放进 `FetchScope.expect`,
  `sync_select.pick_sources` 用**同一份口径自己重算一次**再比 —— 对不上就**作废这一条**,不进选源
  名单。只核到入口的后果是:占住管道之后、crawl 真读到这一条之前它随时可能被改指,而执行器手上只有
  编号时会按编号重读一份**新**配置当成旧授权来跑。**作废不是失败也不是「检查过」**:退避一格没动、
  水位一个字没改(说「检查过」等于替改完之后那一条宣布它同步过了),这一轮如实报一个 `stale` 计数。
  采集那一头的改指照旧由 `sync._repointed` / `_claim_write` 管(结果整批丢掉),三处方向一致。
- **执行范围那一份照旧只有 `channel` / `accounts` 两个键。** 描述走 `_scope_entries` 那一份
  (和展示用的 `retry` 标记同一条路),不扩 `crawl_channels` —— 理由在 `pipeline_stages._scope_entries`:
  多一个键就会跟着跑进执行和付费边界。
- **人点那一刻「这几世的这几条」要跟着每一次写入走,不能只靠服务端现取一次。** 现取防的是**并发
  写入方**(补抓 worker 刚把这一行换掉),它防不了**旧表单**:页面开着、或者那份点名意图占着管道等了
  十几分钟,期间这条内容被清理删掉又从同一个链接收回来 —— key 一个字都没变,而人的决定说的是另一条。
  所以 `/body`、`/link`、`/shelf`、`/requeue` 各带页面那一刻的 `life`(列表和详情接口本来就带着
  `life` 这一列出去),「立即执行」那份意图带 `fulltext_retry['lives']`;服务端一律过
  `warrant.life_sql()` 把它 **AND 进写语句自己的 WHERE**(元规则),`rowcount==0` 就是拒绝。
  **缺了照旧放行**:CLI、脚本直调、存量页面点的就是「现在这一条」,一律拒会让那几条路跑不起来 ——
  而带了就必须比(反过来钉一边)。
- **翻译那条路的射程指纹只认服务端重签那一份**(`plan['scope_sig']`)。`RunRequest` 里**刻意没有**
  `scope_sig` 这一格 —— 收下客户端带来的指纹等于让页面自己声明「这一轮的付费射程是多大」,而那正是
  这道闸要挡的事。取不到指纹时一律 409:那个端点把空串解释成「没有确认框、脚本直调」而放行,可这里
  恰恰是从确认框来的。
- **本面板任何一条路的阶段清单里都不许出现 `extract`**(`actions.FORBIDDEN_STAGES`,`_signed` 里
  真写进去了就 `AssertionError` 当场炸)。两条交回既有端点的路**原本的清单里就带着它** —— 照原样交
  出去,确认框里那句「条目化提取不在这一轮」当场变成谎话,而人是照着那句话决定点下去的。所以那两个
  端点拆成**薄路由 + 可传阶段清单的函数体**(`intake_api.sync` / `translate_retry` 只是把各自原本
  那份清单填进去,公开行为逐字不变;本面板调 `start_sync` / `start_translate_retry` 并传自己那一份)。
  这是结构红,行为用例证明不了「**所有**路都没有」。
- **「立即执行」要真的碰到人选的那几条。** 「待人工确认」和「重试已停止」两档**本来就不在**
  `fulltext.queued_sql` 里(前者等的是人,后者额度已用完),所以只往 `crawl_filter` 里放一个
  `channel` 的后果是:人勾了那几条、页面说已开始、同步中心真跑了一轮,而他勾的那几条**一次也没被重
  试**。点名意图放在 `crawl_filter['fulltext_retry']`、由 `export` 阶段的 `materialize()` 消费
  (口径逐字照既有的 `translate_retry`):先 `fulltext.reopen` 按现态解除挂起 / 还回额度,再让它们排在
  补抓队列**最前面**(`fetch_pending(keys=)` 在 `ORDER BY` 最前面插一段 `CASE WHEN key IN (...)`)。
  **插队不是锦上添花**:放回队列把额度清成 0,而取数是「失败过的优先」—— 不插队的话它们排在几百条
  「从没试过」的后面,一轮上限 40 条,那一轮照旧一条都轮不到。**也不许改成「多跑一轮点名的」**:
  一条失败但仍留在队列里的内容会在同一轮里被取两次(两次网络请求、两次扣额度)。
  **意图只放在 `start_pipeline` 原子写进去的那份状态里**:占不到管道 = 这份状态压根没写 = 库里一个
  字节都没动。先改库再占管道的写法在 409 那一支会把挂起和额度提前改掉,而人看到的是一句「没有开始」。
- **有现成的起跑路径就不许自己再写一条。** 翻译走既有的 `/api/intake/{kind}/translate-retry`
  (它自己带额度清零、点名、`scope_sig` 那道「确认期间范围变没变」),来源走既有的
  `/api/intake/{kind}/sync`,而且是**在服务端直接调那两个函数** —— 这样这块面板的处理记录里才有那
  两笔,而「我上次对这一条做过什么」正是它存在的理由。只有正文/入库那一档没有现成路径,用
  `actions.run`。
- **混着选时拒绝,不许挑一条路跑。** 一次按两份不同的射程跑,确认框里写不出一句不说谎的话;让人
  分两次点,代价只是多一次点击。
- **跑不起来的要先拒,不要先给一段承诺**(`_refuse_unactionable`)。`/{kind}/sync` 对停用的订阅和
  没配好的通道各有一句 400;先承诺再被退回,人看到的是两句互相矛盾的话 —— 尤其 X 限流那一档,那句
  退回正是「还没有登录过 X」,恰好把人引到这块面板**最不该**引他去的地方。
- **X 那两类问题绝不许说成「掉登录」。**
  · 启动限流(`x_page_state.XSessionThrottled`):启动请求被限流、页面应用没能启动,本轮没读到这个
    账号的时间线 —— **不是**登录过期、**不是**安全验证。出路是等后端那份会话冷却(`x_cooldown`:
    45 秒起,反复撞上翻倍到最多 180 秒),而 `x_browser` **已经会**等冷却并在预算允许时把受影响账号
    排到队尾重试一次 —— 文案不许写成「完全没有自动重试」,也不许承诺「冷却结束就会成功」。
    **冷却一律由后端统一等待**,不许为了绕开频率限制每点一次就新开一个会话。
  · 覆盖未完成(`subscriptions.last_note`):浏览器时间线最多滚 40 次、每账号 50 秒预算,连续 3 次
    没长出新内容又没到底也算没读完;原同步下界**不前移**,已取得的内容照旧入库,下一轮按原下界重叠
    重抓、按 URL 去重。现有实现**重新导航账号页、不是从上次像素位置续滚**,所以那颗按钮叫
    **「重试此范围」**,**不许承诺断点续传**,也要如实说「同样的预算或加载障碍下这一次仍然可能读
    不完」。
  · **判不准一律落进通用档,而通用档一个字都不提登录。** 只有否定式允许出现(「不需要重新登录」正是
    要说的那句话),祈使式一句都不许有。
- **`last_error` 和 `last_note` 答的是两件事,按列分流,不许拿关键词去搜 `last_note`。** 后者那句话
  里**会原样嵌着限流那段文案**(实测形态见下),搜关键词会把一个「成功但没读完」判成「启动限流」,
  于是屏幕上说「本轮没读到这个账号」,而它其实读到了一堆内容。
- **来源连接问题不是一篇文章。** 它走自己的四步(`sources.SOURCE_STEPS`:访问来源 → 读取时间线 →
  检查覆盖 → 结束检查),**不套文章那四步**;**不提供「不再收录」**(那颗按钮的射程是一条内容,拿它
  停用整条订阅是把单篇排除悄悄放大),批量勾选里也要禁掉。**来源复查恢复不等于发现了新文章**,更不
  计为新文章入库。
- **「不再收录」是可撤销的搁置,不是 `kb/feeds/exclusion.py` 那一份永久移除。** 那一份会把 key 写进
  `feed_item_exclusions`、删掉 `feed_items` 那一行、删掉导出的 md、从 kb.db 里收掉文档,还装了一个
  BEFORE INSERT 触发器让这条链接**再也收不回来** —— 一颗写着「可在已搁置里恢复」的按钮背后是一次
  不可逆删除,是最糟的一种谎。所以另开一张旁表(`feed_item_shelf`),**一个字节的正文、一行条目、
  一个文件都不碰**,恢复 = 删掉那一行。
- **搁置那一道要 AND 进四族判据:补抓、翻译、待办、**以及交付**(`shelf.free_sql`)。前三族是
  `fulltext.queued_sql` / `held_sql` / `exhausted_sql` / `release`、`translate_scope.queued_sql` /
  `RETRY_SQL` / `manual_sql`,不带的话人点完「暂缓」下一轮照旧去抓、照旧买一次翻译,而屏幕上那一行
  确实变成了「已搁置」。
- **交付那一道是承重处,而且它的方向和前三族是反的 —— 这一条单独写,因为上一版就漏在这里。**
  `sync._export` 问的是「这一条可以写进 vault 了吗」,而它的判据是**队列的反集**
  (`AND NOT (fulltext.queued_sql())` / `AND NOT (translate.queued_sql())`)—— 于是往队列里加一道
  **正向**筛选,在交付那头**取反成放行**:人点完「不再收录」,这一条当场「不在补抓队列里」「不在翻译
  队列里」,导出照旧把它写成 md。**离开某个队列不等于获准进入下一个环节**,所以交付层必须自己明说
  一句 `AND {shelf.free_sql()}`。**那一句要排在所有统计语句之后** —— `queue`/`cond` 那几条统计各自
  只带 `kind` 一个占位符,在它们之前往 `args` 里追加会让绑定数当场对不上,整个导出阶段抛
  `ProgrammingError`。
- **交付的放行由那条确认 UPDATE 自己说,文件跟着那个结论走。** 上一版是「取数时筛一遍 → 写文件 →
  无条件 `UPDATE ... SET exported_hash,path`」,于是**取数之后、确认之前**那一下点的「不再收录」拦不住
  任何东西:文件已经落进 vault、回执照旧写上,而面板上那一行确实变成了「已搁置」(审查实测,
  和「搁置的内容被导出了」是同一类,只是窗口挪到了这一轮之内)。现在那条 UPDATE 带着
  `AND content_hash=? AND {shelf.free_sql()}`,`rowcount==0` 就是**拒绝**。
  **拒绝要归因,因为两种拒绝的善后方式相反**:正文在这期间被换过(`content_hash` 那一道)→ **文件
  照旧留在 vault 里**,那是既成事实、第一份回执是它唯一的机会(`link-grab.md` 和 `daily.md` 两处都
  钉着,`tests/test_grab_store.py` 有定点注入的红);被搁置 → 刚写出来的那个文件 `unlink` 掉、回执从
  `written` 里撤掉、计一笔 `refused`,`note` 里如实说「N 条在这一轮里被暂缓或不再收录(没有写进知识
  库)」。归因那一句是拒绝**发生之后**才问的、**不是准入检查**(准入已经由那条 UPDATE 自己的 WHERE
  一锤定音),所以它判错的两个方向都安全:归到搁置就多重导一轮,归到正文就留着一个下一轮会被覆盖掉
  的文件。
  **刻意不改成「先占回执再 `os.replace`」**:那样顺序干净,但进程在「回执已提交、文件还没落盘」之间
  被砍掉的话,库里说已交付、vault 里什么都没有,而这一条**此后再也不会被选到** —— 不可恢复的那个
  方向(元规则:漏报是静默丢数据,误报顶多重抓一次)。现在这个顺序的每一种失败都停在「文件在、回执
  没占上」,下一轮重算同一份内容、原子替换同一个路径。
  **它盖不住的那一种,写在代码里也钉在回归里**:已经交付过的那一条正在刷新它那篇 md 时被搁置,新文件
  已经原子替换掉旧文件、`unlink` 会连旧那一份一起删掉 —— 所以那种情况下文件留着,计一笔 `done`,
  承诺的「不再写新的」仍然成立,而「把已经入库的那一份也撤回」从来不是那颗按钮的承诺。
- **在途的正文写回也认它**(`fulltext._save` / `_fail` 三种写回同一个 WHERE)。人点下按钮的那一刻
  可能正有一轮补抓在路上:判据只有内容身份和抓取目标的话,它回来照旧写得进去 —— 而那颗按钮承诺的是
  「正文、文件和已经入库的内容一个字都不动」。作废它的代价只是白抓一轮(恢复之后它回到队列、额度和
  待办都没动过)。**译文写回(`translate._save`)刻意不带这一道**:那一笔模型调用**已经付过钱**,
  拒收等于扔掉它、恢复之后再付一次;而它写的那几列不参与交付,上面那道闸门已经把整条挡住了。
  两边取舍不同是因为代价不同 —— 这边作废的是一次还没花钱的抓取。
- **每一次外呼之前现问一遍「现在还获准吗」**(`shelf.admitted`,补抓与翻译两条 worker 各在发请求前
  一步问)。上一版只在**取样那一刻**筛过一遍判据,于是那一批一旦取出来就等于拿到了整轮的执行权:
  人点完「不再收录」,队列里还没派发的那几条照旧一条接一条地发请求、照旧买翻译(审查实测
  形态)。这是一类问题 —— **「取样时可执行」不等于「后续一直有执行权」**,所以判据要在**真正花钱
  那一步之前**再过一遍,而不是在取数处筛得更严。拒掉的记 `summary['shelved']` 并在收尾那句话里如实
  说「N 条在这期间被暂缓或不再收录、没有去取 / 没有翻译」(元规则:统计按实际写入结果报)。
  **残留的那一瞬如实写在 `admitted` 的 docstring 里,不许在文案上吹成「一点下去就不会再发请求」**:
  查到获准和真正发出请求之间仍有一个指令的窗口,要彻底关掉它得给每条在途请求一个落库的在途标记、
  并把那颗按钮的承诺改成「会等在途那一笔结束」—— 那是另一件事。这一道保证的是**确定的那一半**:
  搁置成功之后**不会再开始**新的请求。
- **`fulltext.unsettled_sql` 是例外,刻意不带**:它答的是「这一条的正文还没定下来」,带上之后一条被
  暂缓、手里还是跳转壳的英文内容当场变成「正文已定」、排进翻译队列。
- **搁置要分开回答两个问题,各有自己那一列:「哪一世的内容」和「这一世的哪一次决定」。**
  · **「哪一世」= `feed_items.life`**(`kb/feeds/schema.py`:16 字节随机 → 32 位定长 hex,由一个
    `AFTER INSERT ... WHEN new.life=''` 触发器发,五条插入路径共用一份)。`item_key` 按网址算:存量
    清理删掉一条、下一轮又从同一个链接收回来,key 一个字都没变,而库里那是另一行、另一份正文。
    **上一版拿「`fetched_at` 只在 INSERT 时写」加「`content_rev` 一生只增」两道组合认这件事,而那两
    列都是可以重复的本地状态** —— `fetched_at` 只记到秒(同一秒删掉重收是常事),新插进来的
    `content_rev` 从 0 起(上一世本来就是 0 时 `>=` 照样成立)。**本地可重复的状态不是身份**,所以
    判据换成那一列的相等。那一列是 ALTER 补出来的,**回填必须在同一笔事务里**,否则存量那几千篇的
    `life` 全是空串 —— `item_life<>''` 一条都认不出,面板上每一颗按钮对老内容**静默无效**,而新收进
    来的内容一切正常(只看新库测不出来)。触发器**建在 `migrate()` 里而不是 `SCHEMA` 里**:SQLite 在
    `CREATE TRIGGER` 时就解析触发器体里的列名,老库上那一列还不存在。
  · **「哪一次决定」= `feed_item_shelf.decision_id`**(每次 `shelve` 新发一个,原地改写也新发)。
    恢复要绑它:同一条内容先暂缓、恢复、再「不再收录」,处理记录里第一条那颗「恢复」若只按 key 删,
    会把**后来**那次决定一起取消。`created_at` 顶不了这个用 —— 它只记到秒,三步落在同一秒里是常事。
    **缺编号时一律拒绝,不许退化成按 key 删**;`shelf.release` 要求 `decisions` 与 `keys` 一一对应,
    `rowcount==0` 就是「这颗按钮已经失效」。处理记录里那颗撤销按钮的可用性由 `shelf.live_decisions`
    现查(**明确失效**,而不是点下去才拿到一句拒绝)。
    **这两头问的必须是同一个问题,`life` 那一道两边都要带**(审查实测):上一世那一行还躺在旁
    表上,只按编号查的话,一条删掉重收、**从来没有被搁置过**的内容,旧记录里那颗「恢复」显示为可点,
    点下去 `release` 还真按 key + 编号删掉了那一行、报一句「已恢复 1 条」。两处现在都 AND 上
    「这一行记的就是库里此刻这一世」。
  · **认不出来就当「没有搁置」/「没有记录」**:继承上一世的「不再收录」等于拿一个针对别的内容做过的
    决定静默挡住它,而面板上看不见;处理记录同理(`ledger.for_item(key, life)`,`life` 为空直接返回
    空集)。反过来,**同一世里换过一版正文的照旧算搁置着**(不然按钮会在正文更新后静默失效)。
  · **上一世留下的那几行不必回收**:三处读都认不出它们(`shelf._match`),下一次对同一个 key 搁置时
    由 `ON CONFLICT(item_key)` 原地改写成这一世。
- **判据待在写语句自己的 WHERE 里,`rowcount==0` 就是拒绝信号**(元规则)。路由上那个 kind 过了合法
  性校验**不等于**请求体里每个 key 都属于它;身份那几个值要在**同一条语句里现取**,不在 Python 那边
  先 SELECT 一次。分桶一律按**库里此刻的事实**(`lanes.split`),不按前端传来的说法 —— 页面上那一份
  可能已经过时几秒了,而处理出口是按档分的。
- **统计按实际写入结果报,跳过的如实列出**(元规则)。给 5 个 key 只放回 3 条就说 3;处理记录里的
  `affected` 也是真写进去的行数。
- **不做快照回滚。** 把 `fulltext_tries` 按快照写回 `MAX_TRIES` 是在**伪造一次没发生过的失败**,而
  下一轮补抓会照着这个假数字拒绝重试它。只有搁置这一个出口真的可撤销(删一行就回到原状),其余几个
  记录在案、不给撤销按钮,处理记录里把这件事明说。
- **「仅重新排队」不许打 `translate_manual`。** 那一列是「立即执行」那一轮的**付费边界**(只译带标记
  的),而它在每一轮重试开始时会被整类清掉 —— 在这里打上既到不了那一轮,又会让下一次常规同步把这
  一批顶到队首。这颗按钮承诺的只是「下一轮同步会正常轮到它」。
- **「挂起」的恢复必须走既有通道 `fulltext.release`**,不许另开一条判据:那条路的 WHERE 里已经钉着
  「还没补到全文」「还挂着」「这条订阅现在还开着补抓」三道(`fulltext.md`)。人工挂起这一族只有
  `GET /{kind}/held` + `POST /{kind}/held/release` 一个通道,`scripts/feed_held_cli.py` 是它的 CLI。
- **一次工作的身份不能由「可复原的输入值」拼出来**(`fulltext.work_version`,**五道**:
  `content_hash` + `content_rev` + `fulltext_url` + `life` + `fulltext_gen`)。前三道**每一道都能被
  复原**:地址 A→B→A 之后 `fulltext_url` 逐字复原;存量清理删掉一条、下一轮从同一个链接收回来,
  `content_hash` 一模一样而 `content_rev` 从 0 起(上一世本来就是 0 时两边相等)——于是旧请求回来
  照旧写得进去,而那是另一行、另一次收录(审查实测:改回 A 之后那个旧结果被收下)。
  所以再加两道**只能前进**的:`life`(哪一世,随机 16 字节,见下面那条)和 `fulltext_gen`(**抓取
  代次**,改指 `relink`、人工放回 `release`、点名重试 `reopen` 的耗尽那一支各加一)。
  **代次独立于内容修订号**:换链接不是换内容,`content_rev` 不许动 —— 别人手上那份**内容**工作资格
  不该因此作废。**取样和所有写回同源**:`fetch_pending` 把这五列一起选出来,三种写回(成功、异常、
  证据不足)用同一个判据,不是只在成功那一支加一次预检。
- **「换链接」改的那一列是补抓的工作输入。** 换链接**不碰内容**,内容那两道认不出它,于是:
  worker 读到旧地址和旧内容身份 → 人换成新地址 → 旧请求回来 → `_save` 照旧通过,把**旧地址**那一页的正文写进去、`fulltext_at` 一置,自动
  补抓此后再也不碰这一条 —— 新地址一次都没去过,而面板上这一条显示「正文已补齐」。失败那一侧同样:
  旧地址的超时被记在新地址头上,还扣掉一次重试额度。**工作输入变了,旧输入产生的结果一律作废**,
  那一道(以及放回队列那两个出口)现在由 `fulltext_gen` 统一表达,理由见上一条。
- **「换链接」不许动身份那一列。** `item_key` 按原网址算:换掉 `feed_items.url` 会让
  `exclusion.failure()` 里那道 `item_key(channel,url)==key` 不再成立,失败明细里「不再抓取」那颗按钮
  会**静默消失**;而把 key 一起重算就不是这条内容了(订阅归属、收藏、已导出的那篇 md 全挂在旧 key
  上)。新地址写进 `feed_items.fulltext_url`,只决定「这一次去哪儿抓」。**这一下也不抓** —— 立刻跑
  一轮要占住管道,而 409 会把保存一起拒掉。**换上来的地址只认网页**:PDF 的字节解出来是一段
  `%PDF-1.4 …` 加几百个替换字符,长度轻松越过正文门槛,于是「补抓成功」、条目离开队列,还拿这堆乱码
  去买一次翻译。
- **「正文已补入」不算「已入库」**(状态契约):`POST /body` 只换正文、打上 `extract_stale`,写进知识
  库是下一轮导出的事,那条内容落在「等着写入知识库」那一档。准入判据和浏览器采集那条路**逐字同一
  份**(`browser_capture._admit_body`),不另立第二套。
- **正文那三档的主入口是「从浏览器采集」,「手动补正文」是兜底,两颗在一道闸上。** 会落到这三档的
  多半是「页面上没有识别出正文,可能需要登录或由脚本渲染」「这一页要求先完成验证或登录」
  「HTTP 403」—— 那些页人**已经在浏览器里开着、登录态也在**,从那个标签抓比让他手工全选复制粘贴
  顺得多,也不容易粘坏。所以 `capture` 在 `lanes.Lane.exits` 里**紧排在 `body` 前面**(那个元组的
  顺序就是屏幕上按钮的顺序,前端只负责画),视觉上是那两者里的主项。**两颗只许成对出现**:它们写的
  是同一列、过的是同一份准入,一颗开一颗关的后果是开着的那颗点下去只在服务端被拒,而屏幕上看不出
  为什么。禁掉时那句理由同样**只有服务端那一份**(`item` 的 `paste_block` ←
  `source_types.link_body_refusal`,空串 ⇔ 许可),而且**既进 `title` 也就地显示一行** —— `title` 在

  `browser_capture._same_life` 一处回答,不在交接处再判一遍(完整口径和互指在
  `browser-capture.md`)。**批量栏里不给这一颗**(一个浏览器标签就是一篇文章)。
- **已搁置里「暂缓」和「不再收录」分别显示,都不计为解决**(状态契约)。
- **来源连接问题单独报一个数,不混进那几组的「条」数**(`overview` 的 `source_problems`)。

  `last_note`,贡献**两条**来源问题。混进去之后页头会说「还有 N 条内容在等」而其中两条点进去找不到

  `offset` 推到**已经拿到的条数**并**追加**(按 key 去重:两次请求之间队列可能动过)。
- **单文件 700 行是硬上限**(CLAUDE.md),这一块撞了五次,五次的拆法都照仓库里的既有先例 ——
  **原地再导出**,让原来那个名字继续成立(调用点、注释指向、`patch.object` 打桩点一个都不用改):

  络请求都没有、一个字节都不写。**不许靠删注释压空行凑数**(CLAUDE.md 明说)。
  **搬完要逐符号对过原文**(元规则:广域回归可能全绿,因为新函数压根没进过
  执行路径)。
- **界面**:色值一律走 token(演示页那几个十六进制对应 `--danger` / `--warn` / `--line`),重点色仍是
  深松绿;箭头一律走 `icons.js` 的 `arrow(kind)`;反馈走 `ui.js` 的 `toast` / `confirmBox` /

## 事故形态与实测证据

- **226 条看不见的失败。** 补抓重试试满 `fulltext.MAX_TRIES` 之后,条目**按设计**离开队列、按 feed
  原本那份壳走完翻译和导出 —— 面板上一切正常。排查那天手写 SQL 问出来的是 RSS 待补 212、RSS 耗尽
  226、网页专栏耗尽 1。这就是「三档不许统称」那条约束的来处。
- **同一条内容被数两遍。** 各档用原始判据直接相加时,一条正文耗尽的英文内容同时落进「正文耗尽」和
  「待翻译」,屏幕上顶部总数和各档之和差几条,而人看不出多出来的是什么。按 `probes()` 的顺序逐档减
  掉前面那几档之后两个数相等。
- **那 212 条壳在「等着写入知识库」里再数一遍。** 它们的 `exported_hash<>content_hash` 同样为真(导出
  闸门正扣着)。第一版靠「要求 `fulltext_at` 非空」挡住,**那个修法连带挡掉了压根不需要补抓的内容**;
  现在靠档位顺序挡(见硬约束那一条)。
- **搁置的内容被导出了。** 审查把三条还没导出的内容全标成「不再收录」,真跑一次
  `sync._export`:vault 里出现 3 篇 md,三条的 `exported_hash` 全从空变成非空。原因是交付层读的是
  队列的反集,而搁置是加在队列正向判据里的 —— 取反之后它变成放行。三份既有回归当时全绿(它们验的是
  「离开了补抓队列」「离开了翻译队列」,而那两件事确实发生了)。
- **同一秒、代次都是 0 的那一下,上一版的身份判据漏判。** 删掉重收撞在同一秒里(`fetched_at` 只记到
  秒),而上一世没补过正文、`content_rev` 本来就是 0,新行也从 0 起 —— 两道同时成立,这条全新的内容
  继承了上一世那次「不再收录」:它一次都不会被补抓、不会出现在待办里,而面板上什么也看不见。
- **旧那颗「恢复」取消了后来那次决定。** 暂缓 → 恢复 → 不再收录之后,处理记录里第一条上那颗「恢复」
  若只按 key 删,会把「不再收录」一起取消:人翻了一眼旧记录、点了一下和这条内容当前状态毫无关系的
  按钮,内容静默回到待办里。
- **确认框里那段话和跑掉的那一轮是两份计划。** 等待期间那一条补抓完成、从正文档跳到翻译档,提交时
  `/run` 重新选路走了翻译 —— 按**整个范围**放回队列并调模型,而确认框里写的是「导出 + 索引」。
- **人勾的那几条一次也没被重试。** 「待人工确认」和「重试已停止」本来就不在补抓队列里,只传
  `channel` 的那一轮按队列取数,他勾的那几条一条都没进去 —— 而页面说已开始、同步中心那一轮确实跑了。
- **「展开更多」永远看不到第 41 条。** 前端把 `limit` 当成「累计展开数」,而服务端把它夹在
  `lanes.PAGE` 封顶:按钮一直在、每次点都"成功",列表一行都没多。
- **列表标题坐在深松绿按钮底色上。** `.care-row-main` 是个 `button`,而 base.css 给 `button` 一层
  深松绿填充 —— 不做完整重置的话标题和那行红色失败原话都躺在 `rgb(23,96,79)` 上。
- **日界上判反。** `fulltext_at` / `translated_at` / `intake_care_log.at` 存的都是 `reg.now()` 的
  UTC ISO 带偏移(`2026-10-09T07:56:11+00:00`),而 `datetime('now','-7 day')` 给的是
  `2026-10-19 10:52:45` —— 没有 `T`、没有偏移,字符串比较在日界上判反(`'T' > ' '`),而这几列上没有
  可用的日期函数索引可言。窗口下界一律自己按项目时区算出来再折回 UTC(`lanes.resolved_cutoff`、
  `ledger._cutoff`)。
- **确认框承诺了一轮必然被退回的执行。** X 启动限流那一条的出口是 `/{kind}/sync`,而通道没配好时那个
  端点以 400 拒掉「待配置:浏览器通道还没有登录过 X」—— 先承诺再被退回,等于把限流一路引到「再登一
  次」。现在 `sources.problems` 把 `reg.configuration_error` 的结论当 `blocked` 带出来,`scope` 和
  `run` 两个入口都先拒。
- **`last_note` 里嵌着限流原话。** 实测某账号的 note 是「滚动次数用完,没有读到上次的位置;有 67 条
  折叠推文暂缓补全(X 限制了访问频率,页面应用没能启动…),留到下次同步再试」。拿限流关键词去搜它
  会把这个「成功但没读完」判成「本轮没读到这个账号」。按列分流就没有这个问题。
- **表单一提交就关,服务端那句拒绝无处可去。** 换链接填了个 PDF 地址时服务端给的是字段级拒绝,而
  对话框已经关了:屏幕上什么都没发生,刚填的地址也丢了。
- **搁置拦不住下一轮。** 判据只加在面板自己的取数上、没加进 `fulltext.queued_sql` 时,人点完「暂缓」
  那一条照旧被下一轮抓走 —— 按钮只是在屏幕上改了个字。
- **取数之后、确认之前那一下搁置拦不住导出。** 上一版的顺序是「取数时筛一遍 →
  写文件 → 无条件写回执」,所以窗口不在轮与轮之间,就在这一轮之内:定点注入(在 `sync._kept_meta`
  之后搁置那一条)之后,`exported_hash` 和 `path` 都落了下来、md 也在 vault 里,而面板上那一行确实
  是「已搁置」。改成「文件跟着那条带判据的确认 UPDATE 走、`rowcount==0` 就把刚写的文件收回」之后,
  同一个注入序列下文件不在、回执没占上、`refused` 计了一笔,而同一轮里另一条没搁置的照旧交付。
  **这里差点修出第二个事故**:一律按「确认被拒就把文件收回」写的话,**正文换过**那一档的文件也会被
  删掉 —— 而那一档早就被钉成不变量(`test_grab_store.py` 那条定点注入的红、`daily.md` 的「已经落进
  vault 的文件不许因为后面那次确认失败而消失」)。所以拒绝之后要归因,两档各自善后。
- **搁置成功之后,队列里还没派发的那几条照旧在花钱。** 报告的原话是「不是要求丢掉已经付过钱的在途
  译文,而是**连尚未派发的请求**都会在『不再收录』成功之后开始」。定点验证:把 `WORKERS` 压到 1、
  打桩 `fetch_one` / `translate_item`,在第一条处理中时搁置第二条 —— 加了派发前那道闸之后外呼只发生
  **1 次**、`summary['shelved']` 记 1、那一行一列都没动,收尾那句话里有「没有去取」。
- **地址改回去之后,旧请求的结果被收下。** A→B 时旧工作资格确实被拒(这是正对照),
  但改回 A 之后 `fulltext_url` 逐字复原,那张旧票又成立了;删掉重收那一路更齐 —— 摘要、修订号、
  空地址三样**同时**复原(实测 `same_three: true`),于是上一世派出去的那一笔写进了新收回来的这一行。
  加上 `life` + `fulltext_gen` 之后两条路都拒,而**新取的那一份照旧写得回去**。
- **旧确认启动了改指后的另一个来源。** `problem_id` = 编号 + 问题类型,两样都没变,
  报告实测 `same_plan=true`。签上 `rev` 之后同一序列签出两张票(`same_plan=false`),而且起跑那一下
  把验过的那一版交给 `start_sync` 再核一次:改过的拒 409、**什么都没有开始**(`started: []`),
  没改过的照旧跑。
- **验票之后那一瞬改指,整轮照旧跑了改完之后那一条。** 上一条只修到入口,而入口那道关不掉「校验全
  过了、`start_pipeline` 还没被调」那一瞬:审查按真实 `/scope` → `/run` 复现,把 `update_source`
  插在调度边界上,确认文字仍点名 `source-a`、响应说「同步已开始」,传下去的范围只剩
  `accounts=['id:117']`,真实采集器于是选中并访问了 `https://source-b.example.org/feed.xml`,
  `checked=1`、`repointed=0` —— 一条拒绝都没有。根因是**核过的描述被丢掉、只交编号给执行器**,而
  `sync._repointed` 比的是「这次重新读到的」和「存盘时的」,不是人确认过的那一份,所以补不上这个缺口。
  现在描述随 `crawl_filter['expect']` 一路交到 `sync_select.pick_sources`,它用同一份口径重算一次再比:
  同一序列下**一个地址都没访问**、`stale=1`、`checked=0`、`succeeded_ids` 空,而什么都没改的那一轮
  照旧读它。
- **确认框承诺的下界不是这一轮会用的那个。** 上一版按 `browser` → `timeline` → `feedgrab` 的固定顺序
  取第一个非空值,而 `timeline` 压根没有水位键、真跑那一轮按 `channel_of(settings)` 取:两条通道都留
  过水位时屏幕上那句「保留的同步下界是 X」说的是另一条通道的进度。**通道本身也没进票**:两条都配好
  时切一下通道,`actionable` 和 `rev` 一个都不变,那张旧票照旧对得上,而执行通道和有效范围整个换了。
- **旧表单的决定落在新一世上。** `/body`、`/link`、`/shelf`、`/requeue` 的请求只有 key 和 kind,而写入
  那一侧「现读一次身份」防的是并发写入方,不是旧表单:框开着的时候这条内容被清理删掉又从同一个链接
  收回来,现读到的 url / 指纹 / 修订号全是新一世的,于是那段正文、那个新地址、那次「不再收录」**写得
  进去** —— 而人断言的是另一条内容。「立即执行」那份点名意图更久:它占着管道等到导出阶段才被消费。
  现在页面那一刻的 `life` 随请求走、AND 进每条写语句,同一序列下四个端点一律 `rowcount==0`、点名意图
  一条都放不回,而**带着新那一世的同一个请求照旧写得进去**。
- **处理成功之后在「已完成」里找不到。** 两档要求 `*_tries>0`,而放回队列会把它清零、翻译成功写入
  **必定**清零、人工粘贴压根不制造失败次数。审查实测:真 `requeue` → 真补抓/翻译成功 → 真导出之后
  `fetch_done=1`、`translate_done=1`、两篇的文件都在、`exported` 为真、成功时间非空,而
  `lanes.split` 返回的桶名是空串 —— 不是前端没刷新,是列表和聚合共用的那份判据排除了它们。夹具里那个
  手工 `fulltext_tries=1` 的完成样例把这件事盖住了:它只证明「这种种子显示得出来」。
  **同一次扫描还露出第三条路**:纯入库那一类(自带全文、既不补抓也不翻译)导出之后哪一档都不在 ——
  那两列永远是空串,而人对它点过「立即执行」。现在交付确认那一句同时写下 `exported_at`,
  `ingest_recent` 按它取。
- **循环 import。** `registry.SCHEMA` 把 `shelf.SCHEMA` 和 `ledger.SCHEMA` 拼进建表脚本,所以这两个
  模块在模块层 import `registry` 会成环,一律在函数里延迟 import。

## 还没做的(知情留下,不是忘了)

- **`kb.browser_capture._same_life` 还在用旧那两列认「这一世」**(`item_fetched_at` + `content_rev`),
  没有改到 `feed_items.life` 上。它是另一块功能的回执契约,有自己那几条回归(里面直接摆
  `item_fetched_at`),而它判错的方向本来就是安全那一侧(**认不出来就当没有回执**,顶多让人再贴一次)。
  搁置这边判错的方向是反的(认错了就静默挡住一条全新的内容),所以先只改了这一边。要并到一份口径上,
  那是 `browser-capture.md` 那一块自己的一轮。
- **条目那一世只钉住了「本面板发起的写入」这一侧。** `/body` 走的是
  `browser_capture.save_pasted`,现在它收一个可选的 `life` 并把那一道 AND 进自己的 UPDATE;而**扩展
  那条路**(浏览器采集)照旧用它自己的 `_same_life`(`item_fetched_at` + `content_rev`),没并到
  `feed_items.life` 上 —— 理由同下面那条,那是 `browser-capture.md` 那一块自己的一轮。
  「从浏览器采集」那颗按钮因此**刻意只交 key 过去**:在交接处再判一遍只会多出第三份口径,而两边
  判错的方向本来就都在安全那一侧(认不出来一律当「没有回执」)。
- **「这一问返回之后、系统调用发出之前」那一瞬关不掉。** 派发前那道闸(`shelf.admitted`)和逐段那道
  (`translate._permit`)都是「发请求之前再问一次库」,问完到真正发出去之间仍有几微秒 —— 它的代价是
  **最多多花一次**已经在手上的那一笔,而不是「整批照旧花完」。要彻底关掉得让付费那一侧参与同一个
  事务,而那一侧是外部 HTTP。
- **总览和分节共用一个请求序号**(`CARE.seq`),所以总览单独刷新也会把正在飞的分节请求作废一次 ——
  代价只是多一次取数。**面板空闲时注意不到别处起了一轮同步**:它靠自己那个轮询发现,别的页面点的
  那一下不会推过来。
- **动作和记账是两笔事务**(先写库、再 `ledger.record`)。中间崩掉的话库改了而账上没有那一笔 ——
  方向是「少记一笔」,不是「记一笔没发生的」,而账只是旁证、不参与任何判据。
- **「手动补正文」成功之后没有「再贴一次」的入口。** 原来这里写的是「等它走到下一档再点一次」,
  **那句话是错的**:贴成功之后它落在 `ingest_queued`,而那一档的出口只有
  `run` / `snooze` / `exclude`,**既没有 `body` 也没有 `capture`**。所以贴错了的话这块面板给不出第二
  次机会 —— 要重采得走补抓页那条路(`browser-capture.md`,那一页上有「重新采集正文」),或者等它
  被重新收录。要不要在那一档也开这一对出口是个产品决定(它意味着「已定的正文」可以被再改一次),
  留给主人拍板。
- **`/browser-capture` 还是没有一个正经的导航入口。** 本轮把「问题与待办」这一处补上了(那一档本来
  就最需要它),但整页仍然只能从逐条入口进、或者记住地址。给侧栏加页签牵扯导航结构,**留给主人
  拍板**,不在这一轮里自己加。
- **往后翻那一下不是一个稳定游标。** `offset` + 定长 `limit` 的老问题:两次请求之间这一档会动 ——
  缩短了的话第二页会跳过挤进窗口的那几条(刷新才看得到),变长了的话第二页的前几条是已经见过的 key、
  去重之后那一下**可能一行都没多**,而按钮还在那儿。代价是多点一次或刷新一次,**判据和每一条的处理
  出口都不依赖这个顺序**;要彻底治得换成按排序键的游标(keyset),那是另一件事。
- **逐档取数不是同一个快照**:每一档各发一条 SELECT,一轮同步正好跑在中间时两档的数会差一两条。
  总数和各档之和因此可能短暂不等 —— 它不是计数口径错了(那一条由 `exclusive_where` 保证),
  刷新一次就一致。
- **演示页上三处决定是在实现时按真实管道改的,没来得及问主人**:顶上那颗「执行待办」在真实管道里
  做不到「只执行这一条」,改成了「立即执行本类」;「撤销」只对搁置开放(别的出口是快照回滚,见硬
  约束);来源连接问题不给批量勾选(那颗按钮的射程是一条内容)。三处的理由都写在上面,但那张 demo
  是主人逐块点过的,**要不要这么改应该由他拍板**。
