# 分类图谱(scripts/wiki/build_catgraph.py)

> 从 CLAUDE.md 外移的决策记录。CLAUDE.md 只留硬约束和一行指针,
> 这里是完整的事故形态、实测证据、回归清单和反向验证红数。原文逐字搬运。

- **一共三张图谱,回答的不是同一个问题。** `graph.html`(build_graph_html.py)是
  「最近两周公众号在聊什么」——实体共现、滚动 14 天窗口;`graph-projects.html`
  和 `graph-skills.html`(build_catgraph.py)是「我长期盯的这两类东西现在都有
  哪些、各归在什么用途下」——全量、按固定分类表分区、不设时间窗(时间做成
  筛选器)。路由 `/graph`、`/graph/projects`、`/graph/skills`,顶栏三个链接。
  `/graph/{name}` 的文件名走**白名单**,不拿 URL 片段去拼——vault 根下还放着
  别的东西,`/graph/{name}.html` 那种写法等于把整个 vault 顶层变成可读的。
- **分组口径直接复用 `kb.projects`(图鉴那一套),不自己再扫一遍条目树。**
  写法变体合并、hard 软广剔除、soft 打标记全在那里;第二份实现必然漂。
  为此给 projects.py 加了 `all_groups()`:list_tools 只给 meta,get_tool 会把
  正文 md 读进来(5000 多组逐个调等于把整棵条目树读一遍)。
- **类目是写死的固定表(`scripts/wiki/taxo_tables.py`),模型只负责选 code。**
  让模型自由起标签的话,同一个项目今天叫「命令行工具」明天叫「CLI」,分区每轮
  换一副样子,"经常看"的上层视角就没了。开源项目两层(9 个大类 / 45 个子类,
  另加「其他」),skill 单层(13 个大类 +「其他」)——368 个 skill 再分子类
  每格只剩个位数。表和 `Cat`/`Taxonomy` 单独一个文件,是因为 `taxonomy.py` 写到
  越过 700 行上限,而分类表是里面最独立的一块(纯数据、没有模块级可变状态)。
  **`CACHE_DIR` 那种被测试改写的模块变量不能这么搬**:搬走之后 `T.CACHE_DIR = tmp`
  只改到一份副本,另一边照旧读生产目录。`taxonomy.py` 原样再导出这几个名字。
- **判定结果按 norm 长期缓存在 `data/taxonomy_{key}.json`,一个条目判一次。**
  日常重生成是零 LLM 的,只有新条目才判(`--max-new` 默认 400,防某天涌入几百条
  把管道拖长)。缓存文件里带 `Taxonomy.sig()`:**改分类表就自动全量重判**——
  不作废的话老 code 对不上新表,那批条目会挂在一个不存在的类目下、页面上直接
  消失。**指纹必须覆盖所有会进 prompt 的字段**,不只是 code/group/sub:
  `hint` 是类目说明、`extra_rules` 是 skill 那条成员资格规则,改了判定就该变,
  只哈希 code 的话规则修正完页面上还是老那批成员(2026-09-22 第 1 轮审查发现);
  `fallback`/`item_zh` 同理。写盘是「唯一临时文件 + rename」:截断重写会让并发
  读者读到半截 JSON,而坏 JSON 被当成空缓存,下一次 build 就把几千条重判一遍。
- **「只看有仓库」按解析出的主机名判,不能退化成「有任意 http 网址」。**
  `project_url` 里官网/文档站/应用商店一大把(opencode.ai、prettier.io、
  code.visualstudio.com),按有没有 URL 筛的话这个开关名不副实——实测 3183 个
  项目里这么筛还剩 2833 个,其中 154 个根本不是仓库(2026-09-22 第 1 轮审查
  发现)。口径是 `kb.repo_url.repo_host()` 的 `REPO_HOSTS` 白名单,精确比对或
  后缀匹配,**不用字符串包含**(`github.com.evil.cn` 会蒙混过关)。同一个函数
  也决定 `select_projects` 的并集口径、pill 上那个小圆点和面板链接的文案。
  **图鉴聚合 `project_url` 时挑哪一条也得用它**(`projects._pick_url`):同一个
  工具 A 文给官网、B 文给仓库,原来只认字面量 `github.com`,Hugging Face /
  Gitee 上的仓库会输给官网——而「只看有仓库」是按聚合后这**一个** url 判的,
  这个条目就被当成没有仓库筛掉,open-weight 模型那几个连开源项目图谱都进不去
  (2026-09-22 复审第 1 轮发现,实测 7 个条目受影响)。所以口径单独放在
  `kb/repo_url.py`,图鉴和图谱都 import 它,仓库里只有这一份。
- **判不出来的一律落 fallback(「其他 · 待归类」),不许瞎猜一个类目。**
  `--max-new` 截断和模型漏判都会留尾巴,显示成待归类是诚实的,硬塞进某个分区
  就成了假信息。模型给出表外 code 时 `classify` 直接丢弃,同理。
- **归类整体失败时既不写缓存、也不覆盖旧图。** 一批都没判成(没配 key、中转站
  挂了、缓存文件坏了)时:`classify` 不落盘——写一份空 items 上去等于把老文件
  里几千条结论抹掉,不可逆;`build_one` 看到「有条目但一个都没归类、而且旧图
  已存在」直接 SystemExit——否则就是拿满屏「待归类」悄悄盖掉一张好页面,日志
  里还看不出来。首次生成(没有旧图)不受影响,那时满屏待归类是如实反映。
- **「指纹变了的全量重判」和「同指纹下的增量新判」是两条路,别混成一条。**
  混着走的形态是这样的:改一句 `extra_rules` → 指纹变 → 旧缓存整份失效 →
  可 `--max-new 400` 照样截断 → 3183 条完整旧判定被 400 条新判定**就地盖掉**,
  剩下 2783 个节点当场变「待归类」,页面也跟着被覆盖。**模型全成功也会发生**,
  不需要任何故障,而且不可逆(2026-09-22 第 2 轮审查发现)。所以重判那一趟:
  ①**不受 `--max-new` 限制**(它是给增量兜底的,重判是维护者主动改表换来的,
  3183 条实测约 4 分钟);②有批次失败就保住旧缓存、把进度留在暂存里下轮接着判,
  `classify` 返回 `Verdicts(complete=False)`,`build_one` 据此**拒绝用半份结果
  覆盖旧图**。判出来 0 条时同样按未完成处理,不然「全成功但一条没解析出来」会
  提交一份空缓存上去,和上面那个事故等价。
- **判定一律先落暂存 `data/taxonomy_{key}.staging.json`,不直接写正式缓存**
  (`staging_path`;中途落盘落的也是它)。**增量那一侧同样如此**——原来只有
  重判走暂存、增量直接写正式缓存,于是页面验收不过时 `discard()` 无从撤起:
  缓存丢了而 vault 里旧页面还在(两边不在一处,是真实故障形态),或者候选
  大换血、新的一批全判成 `X`,第一次跑就把坏判定固化进正式缓存,第二次「全部
  命中缓存」、不再问模型,模型恢复也救不回来(2026-09-22 第 6 轮审查发现)。
  暂存在下一轮会被续上(同指纹),所以中途被打断也不白跑。
- **「判完了」= 每一条都拿到了有效 code,不是「没有批次抛异常」。** 模型返回
  语法合法的 JSON 却只含一截(输出被截断、id 重复、给的 code 在表外被过滤),
  `run()` 不抛异常、批次记成功——3 个批次各回 1 条也会 promote 上去,101 条旧
  判定被 3 条覆盖、页面 98 个节点变待归类,和第 2 轮那次截断的后果一模一样
  (2026-09-22 第 3 轮审查发现)。所以 promote 的判据是 `left == 0`。漏项会
  **只拿缺的那些再问几轮**(`_RESIGN_RETRIES`,批次更小更容易回全),那是为了
  别因为模型偶尔漏一条就整轮白等,**不是放宽判据**——补不齐照样保住旧缓存旧图。
- **正式缓存在「新图验收通过 + 页面落盘」之后才提交**(`Verdicts.commit()`,
  由 `build_one` 在 `out.write_text` 之后调)。缓存提交和图的质量校验不在一个
  事务里的话,上面那些拦截就只保住页面、保不住缓存:fallback 本身是表内合法
  code,模型给每条都回 fallback 时 `left == 0`、当场 promote,`build_one` 到
  「一个都没归类」才拦下——页面是保住了,可那份还能用的旧缓存已经被换成一份全
  是「待归类」的新缓存,之后每轮全命中、不再问模型,页面永远更新不了
  (2026-09-22 第 4 轮审查发现)。顺序也不能反过来写:页面写失败时同样是没提交,
  下次重来。
- **重判结果「等于没判」按不作数处理**,而且连暂存一起扔掉。判据是「落在
  `void_codes | {fallback}` 里的占到 `VOID_SHARE`(90%)」——全「待归类」是一种,
  skill 全判成 `X`(不是 skill)是另一种,后者判完就被 drop 掉、节点数直接归零。
  **不是只有 100% 才算坏**:1 条正常 + 100 条待归类同样会被发成一张满屏待归类的
  页面,还把那 100 条固化进正式缓存,之后全命中、再不重试(2026-09-22 复审第 2
  轮发现)。少于 `VOID_MIN_N`(20)条时只认 100%:新进来两三条确实判不出来是
  正常的,按比例算会把正常增量拦下(真实缓存的 void 占比:projects 1.6%、
  skills 24%,离 90% 很远)。那不是判定结果,是这一趟坏了(提示词/模型/中转站);
  暂存留着的话下一轮全命中、不再问模型,同一个坏结果会一直卡在那儿——扔掉才能
  在模型恢复后自己走出来。维护者确实故意收紧了规则时用 `--allow-shrink`
  (`classify(allow_degenerate=)`)放行,和页面那道比例下限同一个开关。
- **这条判据的分母是「这一趟新拿到的判定」,不是整份缓存**(`finish()` 里的
  `fresh = codes - base`,`base` 是进来时正式缓存里已有的那些;续上的暂存算
  这一趟的)。拿整份缓存当分母的话缓存越大越掩盖问题:3188 条的正式缓存下,
  即使新增 400 条全废,占比也只有 12.6%,`VOID_MIN_N` 更是早就被缓存总数满足
  ——「已有正常大缓存 + 某天整批新增全部退化」这条最常见的路径完全不设防,
  坏判定当场入库,下一轮全命中缓存、再不问模型(2026-09-22 复审第 3 轮发现)。
  页面那几道也挡不住:旧节点和已归类数都不减,只是新增的全落「待归类」。
  全量重判时 `base` 本来就是空的,分母自然是整份新判定,两种模式一套代码。
- **`res.complete=False` 无条件拦死,跟有没有旧页面无关。** 这道闸原来写成
  `not res.complete and out.exists()`:首次生成、页面被人删了或产物丢了的时候,
  一份已经判定「不作数」的结果照样被写成 0 节点的新页面,还以退出码 0 收场,
  `wiki_daily` 那头看到的是成功(2026-09-22 复审第 1 轮发现)。没有旧页面可保
  ≠ 坏结果可以发。按「这张图长什么样」验收的那几条(`quality_problem`)仍然
  只在有旧图时比,首次生成如实反映。
- **页面落盘走 `_atomic_write`(同目录唯一临时文件 + rename),别直接 write_text
  到正式产物上。** 磁盘满/进程被杀/写到一半抛异常都会先把好页面截成半截再报错
  ——缓存那头的两阶段提交完好,kb-web 却已经在拿一份坏 HTML 对外服务
  (同轮发现)。同目录才能保证 rename 是原子替换;失败时删掉临时文件,旧页面
  逐字节不变,缓存也因为没走到 `commit()` 而原样保留。
- **「验收基线 → 落页面 → 提交缓存」整段要拿跨进程锁圈起来**
  (`taxonomy.publish_lock`,flock 在 `data/taxonomy_{key}.publish.lock` 上)。
  页面和缓存是两个文件、两次 rename,各自原子只保证「不出半截文件」,管不住
  两个 writer 交错:A 写完页面 → B 写页面并提交 B 的缓存 → A 再提交 A 的缓存,
  **两个进程都以退出码 0 收场**,最终页面来自 B、缓存来自 A,下一轮又拿 A 的
  缓存把页面刷回去,一路没有任何告警(2026-09-22 复审第 3 轮发现)。CLI、
  wiki_daily 子进程、手动重跑、kb-web 管道都是独立进程,`_state["running"]`
  那种进程内状态约束不了它们。锁的是**单独的 lockfile**、只创建不删除,理由
  和 `secrets.json` 那把锁一样。`_io_lock` 因此得是 `RLock`:`save_cache` 也要
  取它,而它是在发布锁里被调的。验收读旧图基线必须在锁内——在锁外读的话,
  刚比过的旧图转头就被另一个 writer 换掉了。
- **缓存提交失败要把页面回滚回去**(`build_catgraph._publish`)。发布锁只挡
  writer 交错,给不了跨文件的失败原子性:页面换好了、`res.commit()` 却因为
  磁盘满/权限/IO 错误炸了时,任务确实报错退出,可 Vault 里的正式页面已经从
  100 节点变成 120、缓存还停在 100——「失败的发布不改变正式产物」当场不成立,
  没人重试的话这个不一致一直挂着(2026-09-22 复审第 4 轮发现)。所以进锁后先
  把旧页面的字节收在手里,提交失败就原子换回去(首发失败则删掉那张页面);
  这一轮判出来的暂存留着,重试一次就能好。回滚本身再失败时打一行 stderr 说清
  「页面是新的、缓存是旧的」,然后把原异常抛出去。
- **暂存里的东西都是「没验过的半成品」,续用前要按原批次各验各的**
  (`taxonomy.load_runs`,暂存文件里的 `runs` 记着哪几条是同一趟判出来的)。
  质量判定跑在 `finish()` 里,而判定结果在那之前就已经落盘了:进程在这段窗口
  里被杀(或者另一个 writer 抢先读走),这批本该判「不作数」的结果就留在盘上
  ——下一轮把它和更多正常结果合在一起算占比,20 条全 `X` 的被 180 条正常的
  稀释成 10%,当场随整份缓存提交,再下一轮全命中缓存、不再问模型,坏结果永久
  固化(2026-09-22 复审第 4 轮发现)。所以:①续上的每一批各自过一遍
  `_void_bad`,坏的那批当场从盘上抹掉、这一轮重判;②`finish()` 的分母是
  **这一趟自己判的那些**(`codes - base - resumed`),不含续上的批次——混在
  一起算的话,反方向同样能稀释(180 条正常的续批 + 20 条全废的新批)。
  老格式暂存(没有 `runs`)整份当一批验:读不到分组不等于验过了。验过的批次
  不会被这一趟的失败连坐,留在暂存里继续当进度。
- **暂存里凡是正式缓存已经有的 key,一律以正式缓存为准**(`classify` 里那段
  `clash`)。暂存不记自己基于哪一版正式缓存:旧 writer 在别人提交之后才把自己
  那份写进共享暂存、随即崩掉,下一轮 `codes.update(part)` 就拿旧结论盖掉了新
  提交的那条——条数还没变,「有没有新东西可提交」又按条数判成没有,于是恢复轮
  **以退出码 0 收场**,页面按暂存发、缓存留在正式值上,每一轮都这样,暂存还
  永远留在盘上(2026-09-22 复审第 5 轮发现)。所以同名 key 直接丢掉、暂存顺手
  清掉,「有没有新东西可提交」也改成比内容(`codes == official`)。
  **这一步也是老格式暂存的正解**:`1f1446e` 之前写暂存落的是整份 codes(含正式
  基线),「整份当一批验」正好把第 3 轮那个错分母请回来——20 条全废的新增混进
  100 条正式基线算成 16.7%,照样提交(同轮发现)。摘掉基线之后剩下的才是上一趟
  真正新判的那批。
- **`save_cache` 成功就等于缓存提交完成,后面清暂存失败只是收尾告警**
  (`taxonomy._promote`)。两步共用一个异常边界的话,`build_catgraph._publish`
  会把 `commit()` 的任何异常都理解成「缓存没提交」,于是把页面回滚成旧的——
  缓存已经是新的 120 条、页面却被换回旧的 100 节点,反方向的半提交是自己制造
  出来的(2026-09-22 复审第 5 轮发现)。清不掉的暂存下一轮会因为「正式缓存
  已经有了」被丢掉,自己就收尾了。**清暂存的每一处都得是这个边界**(统一走
  `taxonomy._cleanup` / `_rewrite_stage`):恢复路径原来还在裸调 `unlink`,
  权限问题不消失的话,「下一轮自己收尾」就成了「以后每一轮都在恢复阶段异常
  退出」(2026-09-23 复审第 6 轮发现)。该丢的判定在内存里已经丢了,盘上那份
  下一轮照样会被重新识别、重新丢掉,没理由让一次 unlink 失败把整轮带崩。
- **发布前要比一次「基线有没有被别人换过」**(`build_catgraph.publish_sig`,
  读候选之前记一份,进锁后再取一次比)。读基线 → 判定 →
  建图 → 渲染那一大段跑在**锁外**(判定要问模型,几分钟起,攥着锁不放会把另一
  条路堵死),所以发布锁只保证两次发布动作不交错,认不出**后拿到锁的那个是基于
  陈旧基线跑出来的**:旧任务能以退出码 0 把刚发布的 40 节点页面刷回 30 节点、
  连新增的 10 条缓存一起抹掉;`--no-llm` 那条路的 commit 是空操作,只把旧页面
  重发一遍,留下页面 30 节点、缓存 40 条的长期分裂(2026-09-23 复审第 6 轮
  发现)。基线不一致 = 别人在我们跑的这段时间里发布过、那一版更新,**这一轮就
  不发了**(打一行说明、退出码 0):我们判出来的东西并回暂存,下一轮接着提交,
  一条都不丢。重试再发没有意义——我们的候选扫描也是那时候做的,一样旧。
- **基线是发布序号 + 两个文件的内容:正式缓存 + 正式页面字节**
  (`build_catgraph.publish_sig`)。两个问题都要问:序号(`taxonomy.bump_gen`)
  回答「发布序列有没有往前走」,内容签名回答「东西一不一样」。**只比内容会被 ABA 骗过去**:产物在我们跑的这段
  时间里经历 A→B→A(回退再恢复,或者同样输入重发一次),结束时缓存和页面字节
  与开工时逐字相同,旧任务就认定没人发布过,把陈旧快照发出去,期间明明有两次
  发布成功完成(2026-09-23 复审第 8 轮发现);**只比序号又挡不住绕过发布流程的
  改动**(页面被手工删掉/覆盖、缓存被别的脚本写过)。内容那两半也缺一不可:
  一轮构建的产物有两个文件,只比 `norm → code` 的话页面这一层完全没保护,而
  页面还取决于锁外读到的那份候选快照(数量、名字、简介、链接、提及次数、共现
  边),这些变了缓存可以一个字节都不动——`--no-llm` 撞上新候选只把它显示成
  「待归类」,默认构建全部命中缓存时简介/热度变了也不写缓存,长期缓存里本来就
  躺着当前快照没有的 norm(第 7 轮发现)。缓存那半按内容算(别人只更新了昵称
  之类的话判定没变,不该让整轮白跑),页面那半按字节算——同样的输入渲染出同样
  的字节,页面没有「只是重排、内容等价」这回事。**要在 `load_groups()` 之前取**:
  候选快照一读完,我们手里的输入就定死了,这之后别人发布的任何一版都比我们新
  (`--kind all` 时 skills 是在 projects 判完几分钟后才开始建的,拿那时候的
  产物当基线正好漏掉这段窗口)。
- **发布序号在动任何正式产物之前推进,推进不了就整轮放弃**(`build_catgraph._publish`
  第一步)。序号、页面、缓存是三次独立的 rename,凑不成一个事务,只能选先推进
  还是后推进,而两个方向的代价差着一个量级:**后推进**会留下「产物已经换了、
  序号没动」的窗口——写序号那一步失败是一种,进程刚好死在页面换好之后是另一种
  (普通的 kill、宿主机重启都能触发,不需要任何 I/O 故障),A→B→A 走完一圈后
  签名逐字回到开工时那版,陈旧任务认不出期间发生过两次发布、静默覆盖最终页面,
  正是加序号要挡的那件事(2026-09-23 复审第 9 轮发现);**先推进**最坏只是后面
  失败时序号多走一步,别的任务多拒一轮(打一行说明、退出码 0,下一轮自己就好),
  正式产物一个字节没动。危险的假阴性换安全的假阳性。所以序号写失败一律
  fail-closed、连页面都不换——它代表的是「有人在这段时间里动过发布流程」,不是
  「发布一定成功了」,CAS 要的正是前者。
- **序号写盘要 fsync(文件 + 父目录),不能只 rename。** 它存在的全部意义就是在
  别的进程、别的时间点被读到;只落进页缓存的话宿主机一重启就没了,ABA 那道防线
  跟着一起没(同轮发现)。值 = 自增计数 + 随机后缀,后者保证文件丢了、计数从头
  开始时也不会撞回旧值。
- **基线「读不出来」一律 fail-closed,不许退化成「还没有」。** `read_gen` 只把
  `FileNotFoundError` 当成空串(真的没发布过),别的 `OSError` 和坏内容(空文件、
  半截 token、别的东西写过)一律抛 `taxonomy.GenUnreadable`;`publish_sig` 里
  读正式页面那一半同理,只有文件不存在才算「还没有页面」。把读失败折叠成「没有」
  等于读侧自己把一半基线扔掉:一个两次取基线都读不到 sidecar 的陈旧任务(权限、
  瞬时 I/O 故障),序号那一半两次都是空,CAS 当场退化回纯内容比较,产物走完
  A→B→A 之后它照样把陈旧快照盖上去、退出码 0——写侧提前推进和 fsync 全白做
  (2026-09-23 复审第 10 轮发现)。`bump_gen` 走同一条路:读不出已有序号时既不
  知道该接着谁往下数,更不能拿 `1-xxxx` 去盖它——盖掉等于把「有人发布过」这个
  事实连同故障一起抹平(实测陈旧任务真的会把计数重置成 1)。取基线是在动任何
  东西之前,那时候退出最干净:报错退出码,产物一个字节没动。
- **共享暂存只有一个写入口 `taxonomy._edit_stage`:读-改-写,整段在
  `stage_lock` 里,而且各人只动自己那一批。** 暂存是所有 writer 共用的一个文件;
  只把「被拒时并回去」那一下做成读-改-写是不够的——普通分类阶段的落盘仍是整份
  覆盖、提交完又是整份删除,而且都不持锁,于是一个在别人发布之后才开工、正式
  基线完全合法的第三方 writer 能把刚并回去的唯一判定盖掉、发布成功后再把整个
  暂存删掉,被拒的那一轮明明打印了「判定已并回暂存」(2026-09-23 复审第 8 轮
  发现)。所以:①每一批带**身份**(`runs` 是 `{批次id: [norm]}`,老格式的列表
  自动编号),`stash` / `_restash` 只替换自己那个 id,别人的原样留着;②
  「提交完清暂存」= 把**自己刚提交的那些 key** 摘掉(`_edit_stage` 每次都按正式
  缓存过滤),**不是 unlink**;③「这一趟不作数」= 把**自己那一批**摘掉,同样
  不是 unlink;④摘完真的一条不剩了才删文件。**取锁顺序永远是 publish → stage**,
  反过来没有任何路径,所以两把锁不会抱死。
- **CAS 拒绝发布时,要在锁里把自己判的并回暂存**(`taxonomy._restash`,
  `Verdicts.keep()`)。我们在分类阶段写过一次不代表它还在盘上——赢的那个随后写
  一次就把我们那份盖掉了。于是「判出来的判定留在暂存里,一条都不丢」是假的:
  那条唯一判定既不在正式缓存也不在暂存,模型钱白花,日志还说留下了
  (2026-09-23 复审第 7 轮发现)。正式缓存已经有的 key 一律不并(以正式缓存
  为准),写盘失败只告警——并不回去顶多是下一轮重判一遍,不该让「不发布」这条
  本来就安全的路径变成异常退出。
- **提示词/调模型/解析回包在 `scripts/wiki/taxo_llm.py`**(`taxonomy.py` 又一次
  越过 700 行时拆的,理由同 `taxo_tables.py`:那一块最独立)。`taxonomy` 把
  `_PROMPT`/`_llm`/`_parse`/`default_model` 原样绑回自己的模块全局,所以测试里
  `T._llm = fake` 这种打桩照旧有效——`classify` 是按 taxonomy 的全局去找它们的。
  **`CACHE_DIR` 那种被测试改写的模块变量仍然不能这么搬**(搬走之后
  `T.CACHE_DIR = tmp` 只改到一份副本)。归类结果对象 `Verdicts` 后来也因为同一个
  上限搬进了 `taxo_verdicts.py`(纯值对象 + 三个收尾动作,不碰文件),`taxonomy`
  照旧再导出这个名字。测试的子进程模板同理:`tests/test_catgraph_concurrent.py`
  越线时拆出 `tests/catgraph_children.py`。
- **页面验收看的是「这张图实际长什么样」,不是某个 code 的名字**
  (`build_catgraph.quality_problem`)。只对 fallback 做特判挡不住 skill 那条
  `X` 路径:X 是合法 code,`drop_codes` 把它们全踢掉之后 `meta.total == 0`,
  而「有条目却一个都没归类」那道检查要求 total 为真——0 节点的空图连同坏缓存
  一起提交,之后全命中、不再问模型,空图永久固化(2026-09-22 第 5 轮审查发现)。
  所以有旧图在时,三种情况一律拒绝写页面并 `res.discard()`:0 节点、一个都没
  归类、**新图不到旧图的 `MIN_KEEP`(50%)**。最后一条挡的是「只剩零星几个」
  这种不为零的塌方,基线来自旧产物头部那行机读标记(`catgraph_page.page_stats`,
  只读两行,老产物没有这行就跳过比例检查),而且**节点数和已归类数两个维度都要
  比**:fallback 节点不会被 drop 掉,100 条判定退化成「待归类」时 total 和旧图
  逐字相同、只看节点数那道阈值压根不动,好页面照样被换成满屏待归类
  (2026-09-22 第 7 轮审查发现)。确实该缩的那次(比如故意收紧分类规则)加
  `--allow-shrink` 放行。
- **「这一轮一个候选都没扫到」是故障信号,不是「没什么可验收的」。** 那句
  `if not picked: return ""` 原来直接跳过了后面所有比例检查:vault 没挂上、上游
  扫描出错、某个过滤器回归,都会让几千节点的好页面被一张 0 节点的新页**原子
  替换**,还以退出码 0 收场——原子写只保证不出半截文件,挡不住这种「完整但错」
  的覆盖(2026-09-22 复审第 2 轮发现)。旧图本来就是空的(或首次生成)才放行,
  确实要清空加 `--allow-shrink`。
- **skill 图谱的成员资格也由归类这一步决定。** 候选是「任一条目打过
  topic/skill工具」,里面混着 Claude Code、豆包这种"本体是软件、只是带 skill
  能力"的(标签打在条目上,聚合时任一条目命中就算)。分类表里有个 `X` 档专收
  它们,判成 X 的不进图谱——严格标准抄的是 `scripts/skill_tag_backfill.py`
  那套「按分发形态判」的措辞,两处说的是同一件事。实测 358 个候选里 83 个是 X。
- **共现边 = 同一篇原文里被一起拆出来的两个条目**,权重是一起出现过几篇。
  一篇拆出 40 个以上条目的月度盘点跳过:那里面两两相连既不是"相关",
  边表还会炸。每个节点最多留 10 条最强的边。
- **文章不内嵌进节点,只存文章表下标。** 一篇盘点文章能拆出几十个条目,
  标题+URL 内嵌等于复制几十遍——开源项目那张图的 10460 条记录其实只出自
  3203 篇文章。
- **点哪一份副本,就以哪一份为准。** 同一个节点在「近 30 天热议」和它的分类区
  里各有一份 pill,连线源点和 `scrollIntoView` 原来一律取**首个可见副本**——点
  分类区那份会被拽回顶部的热议区,连线也从热议那份出发,用户刚点的位置直接被
  滚出视口(2026-09-22 复审第 1 轮发现)。`select(i, from)` 把来源元素记进
  `anchor`,`livePill()` 优先用它;面板上的关联按钮、搜索回车这类没有来源元素的
  入口照旧退回首个可见副本。**滚动还得等面板挤压布局落定再做**(延后 360ms,
  和连线重画同一个窗口):面板一开主栏变窄、pill 整体重排,同一个 pill 的文档
  坐标能挪上千像素,立刻滚等于按旧坐标滚,照样把它甩出视口。
- **筛选改变可见集时,选中态得跟着走。** 当前选中项被筛掉了要整个 `reset()`:
  留着的话面板展示的还是一个已经不在结果里的节点,而 `body.hasSel` 会把所有
  可见 pill 压到 opacity .2 却没有一个是亮的,整片结果区看起来像被禁用。
  切排序同理——pill 全换了位置,`resort()` 末尾必须重画连线,否则路径还从
  排序前的坐标出发(两条都是 2026-09-22 第 1 轮审查发现)。
- **反过来,选中一个被筛掉的节点之前要先把挡它的筛选放开**(`catgraph.js` 的
  `relax()`,收在 `select()` 里)。面板那排「常一起出现」是按共现关系列的,跟
  搜索词/时间窗/热度/仓库开关没有半点关系,点进去的目标十有八九不在当前结果里
  ——`apply()` 里那道保护是「筛选变了就检查选中项」,关联跳转从旁边绕过去了,于是
  进入和上一条一模一样的坏状态:面板展示着一个不在结果里的条目、可见 pill 全灰、
  一个选中的都没有、连线也画不出来(2026-09-23 复审第 1 轮发现,线上
  graph-projects.html 实测 `visibleSelected=0 visibleDimmed=152 edgePaths=0`)。
  **只放开挡路的那几项,而且控件跟着回位**(搜索框清空、seg 跳回「全部」、仓库
  按钮弹起):用户得看得见筛选被放开了。**「挡没挡住」要逐项各判各的**——搜索那
  一项尤其容易写成「`F.q` 非空就清掉」,可组合筛选下目标常常仍然命中搜索词、只被
  别的项挡着(搜「Claude」+「30 天」点到 Bun,Bun 简介里就有 Claude),顺手清掉
  它会让结果从 18 个当场炸回 3187 个(2026-09-23 复审第 2 轮发现)。命中判定
  (`hitsQ`)因此只有一份,`match()` 和 `relax()` 共用。放宽只会让更多 pill 露出来,
  所以 `relax()` 里那次 `apply()` 不会把别的选中项弄没;`match(i)` 为真时直接返回,
  常态下一次重排都不多做。回归在 `tests/test_catgraph_browser.py`:真页面 + 无头
  Chrome(CDP 直连 playwright 缓存里的 chrome-headless-shell,不装 playwright、
  不连网),四种筛选各单独跳一次,外加三种「搜索仍命中 + 另一项挡住」的组合,
  共用一次浏览器启动。
- **搜索框回车要先把这次输入同步落定再找**(`F.q !== v` 就 `clearTimeout(qt)` +
  赋值 + `apply()`)。`F.q` 是防抖 120ms 之后才更新的,而回车分支里的 `match()`
  读的就是它:已经搜着一个词、换成另一个再立刻回车,目标会被**上一个**搜索条件
  排除,回车什么也没打开;120ms 后防抖把列表换成新词,还顺手把旧选中项 reset 掉,
  最后停在「列表是新词、面板关着、一个选中的都没有」(2026-09-23 复审第 3 轮
  发现,实测搜 Claude 回车再换 Blender 立刻回车:`shown=4 panelShown=false
  panel="Claude Code" visibleSelected=0`)。
- **搜索框的回车还要排掉输入法组合态**(`e.isComposing || e.keyCode === 229`)。
  中日韩输入法在组合阶段就用 Enter 确认候选,浏览器给页面的事件带
  `isComposing=true`——不排掉的话,中文搜索选第一个词按的那个回车就把详情面板
  打开了,词还没敲完(2026-09-23 复审第 4 轮发现,实测组合态输入「教学管理平台」
  确认候选即打开「教学管理平台(基于Spring Boot)」)。`compositionend` 之后的
  普通回车才算数。回归用真实 `CompositionEvent` / `InputEvent` / 带 `isComposing`
  的 `KeyboardEvent` 走一遍(无头浏览器里没有系统候选窗,但页面拿到的是同一批事件)。
- **「近 30/90 天」的截止日全程按 UTC 算**(`catgraph.js` 的 `cutoff`)。
  `meta.built` 是后端 `date.today()` 落下来的裸日历日,页脚那句「近 30 天有
  提及 N」也是后端按 `date.today()-30` 数的;前端要是按本地时区解析它的午夜再
  `toISOString()`,UTC+8 下截止日退回前一天,窗口凭空多含一天——实测项目图谱
  筛出 430 而页脚写着 409,同一张页面自己跟自己对不上(2026-09-22 第 10 轮
  审查发现)。所有 UTC 正偏移时区都会踩。`tests/test_catgraph_window.py` 把
  这段真代码抠出来丢给 node,在四个时区下和 Python 的日历减法逐个对。
- **页面样式和脚本放 `scripts/wiki/assets/catgraph.{css,js}` 的真文件里**,
  构建时读进来内联,产物仍是单文件(要能脱离 kb-web 直接用浏览器打开)。
  两张图共用这一份外壳,差别只有标题/主色/「只看有仓库」那个开关。
- 面板里的「在图鉴里看全部记录」跳回 `/?tool=<norm>`,由 gallery.js 的

  关掉抽屉再刷新它又自己弹出来。
- **三张图谱的子进程挂了必须让 `wiki_daily.py` 非零退出**(`run_step`)。管道那头

  ①`graph:`/`catgraph:` 这个标签单独拼在前面、**只截错误正文**:整句一起
  `[-200:]` 的话,稍长一点的报错就把开头的标签截没了,面板上连哪张图挂的都
  看不出来;②摘要取 **stderr 里最后一条真正的错误行**——多行 traceback 在
  stdout 那边只留一句「Traceback (most recent call last):」,根因在 stderr 末行,
  `wiki_daily:` 开头那句是它自己的汇总(只说哪张图挂了),得跳过去继续往上找;

  可展开)——子进程是 `capture_output=True` 抓的,不主动写出来的话它哪儿都不会
  出现,用户只能手工重跑一次才能看到根因(2026-09-22 第 9 轮审查发现)。
