# 同步的历史运行(kb/pipeline_state.py + pipeline_history.py + pipe_history.js)

## 硬约束

- **最近几轮同步的终态要落一份盘,单独一个文件。** 面板那份当前状态只留最后一轮,
  而一轮的红很容易在被人看见之前就被下一轮覆盖掉:上午那轮翻译报了 503、导出阶段
  判了红,晚上一次「重试失败项」跑完全绿,面板上就只剩那一轮的结论 —— **那个红没有
  任何地方查得到**,只剩来源面板上一句温和的「还在等翻译」。
- **`pipeline_state.json` 的既有字段只增不减**(同元规则那条):加字段可以(`run_seq`
  就是后来加的),**改语义和删字段不行**。那一份喂的是「重试失败项」的
  范围派生(`pipeline_retry` 从它恢复 `crawl_filter` / `export_filter` / 失败名单),
  读错一个字段的后果是**静默不抓** —— 用户点重试、面板报「已跳过」,该补的那几条一个
  都没抓(见 `retry-scope.md`)。拿一条不可恢复的路径去换一个只读展示不值。代价是最新
  那一轮在两处各存一份(约 6 KB),**有意的冗余**。
- **历史那几个函数搬去了 `pipeline_history`,但名字要从 `pipeline_state` 原样再导一遍**
  (`_history_file` / `_save_history` / `load_history` / `_run_record` /
  `_history_rounds_strict`)。它们原先就住在 `pipeline_state` 里,仓库里一大片测试和调用
  方按 `pipeline_state.X` 这个名字 patch 或调用 —— 搬完不再导的话,**广域回归可能全绿**
  (改用新名字的那几处自己是对的),而没跟着改的那几处悄悄打在一个没人读的位置上。
  **依赖只许一个方向**:`pipeline_history` 在函数体里晚导入 `pipeline_state`(模块级会成
  环),反过来那一侧是模块顶上的再导出。拆它的理由只是行数上限。
- **历史文件的位置从 `_STATE_FILE` 派生,不另立一个模块变量**(`_history_file()`)。
  测试隔离落盘状态时 patch 的是 `_STATE_FILE`,另立一个的话每个走到 `_end_run()` 的
  既有测试都得记着再 patch 一次 —— 漏掉的那个会去写**生产**那份历史,而漏没漏在测试
  输出上一个字都看不见(同 `maintenance-lock.md` 里 `DATA_DIR` 那条)。派生之后隔离点
  只有一个,不可能漏。
- **轮次身份必须跨进程唯一,不只是进程内**(`new_run_id` 里那一截 `_RUN_EPOCH`)。
  它原来是进程内自增的 `run-{序号}`,只用来认「内存里那一轮是谁」;历史落盘**按身份
  去重**之后它变成了一个跨重启的持久化键 —— 重启后序号从 1 重新开始,新的 `run-1`
  和上个进程那个 `run-1` 并不是同一次运行,却会把它从历史里**替换掉**(连失败原因和
  日志一起),后面每一轮接着覆盖对应的那一轮:**远在保留上限之前就开始丢**,而丢没丢
  在面板上一个字都看不见。取「启动秒 + 随机两字节」而不是 pid:pid 会被系统复用,同一
  秒里重启两次也不算罕见(口径同 `catgraph.md` 里发布序号那条)。老库里 `run-N` 那种
  旧身份和新格式撞不上,到点自然被保留上限挤出去。
- **按 run id 幂等,但空身份一律追加。** 空串不是身份 —— 拿它当键去重会把两轮各自跑过
  的运行合成一条(没经过 `start_pipeline` 的那条路身份就是空的)。历史里少一轮是静默丢
  数据,多留一条只是多一行。
- **「能不能替换『最近一次运行』」和「能不能补全自己已有的那条历史」是两种权限。**
  发布被拒那一档(期间另有一轮更新的独立运行收尾了)只失去前一种:那一批自己那条历史
  还是自己的,这次的结论得补得进去 —— 不然翻那一轮的同步历史永远查不到日报到底成没成、
  为什么没成(「最近一次运行」那一格已经被别人接替,而日报自己那份留档下一轮又被下一份
  日报换掉)。所以历史层另有一个**按身份原位更新**的出口(`update_history_round`):
  **不插队、不改排序、没有那一条就什么都不做**(那张清单是倒序的,`_save_history` 会把
  记录插到最前面 —— 被拒那一档走它就等于让一批更早的运行看着像是最后跑的那一轮)。
  没有那一条时**绝不新增一行**,而且要把这件事说出来(原因并进批次账本,由
  `close_batch` 的调用方报给用户);那一下炸了同理:**不许抛**(它在日报那条
  `finally` 里跑),也不许不出声。**换上去的那一份自己合,不读内存里那格权威汇总** ——
  被拒这一档我们压根没动它,动了就等于声称自己是最新的那一轮。
- **原子换文件**(同目录唯一临时文件 + rename)。这份文件比状态文件大得多(带着每轮
  80 行日志),而面板那条读历史的请求随时在跑,截断重写的窗口里读到的是半截 JSON
  (同 `llm-stages.md` 那条)。写失败不出声:它是只读展示,写不写得上不该影响这一轮
  同步的结论。
- **同一个身份的两份记录是同一次事件的不同字段投影** —— 恢复层按这个前提挑轮次
  (`_newest_round` / `same_event`)。批次层改了「一轮结果」的含义(状态文件里是整批
  汇总,而汇总继承最后那个子轮的身份),所以它**必须把两份落盘接到同一个业务结果
  上**:口径和事故形态在 `sync-schedule.md` 的硬约束一节。
- **三份留档读的那份终态,要在它们开跑之前就齐全。** 历史那一份走的是
  `_run_record()` → `run_record(ps._state)`(它**不走** `run_payload()`:那一份没有
  `log`),所以凡是收尾时才往 `_state` 里补的字段,都必须补在三份留档**之前**。
  结果账(`results`,逐来源的结论,见 `retry-scope.md`)原来补在 `_end_run` 那个
  `finally` 里 —— 于是状态文件里写着 `results.crawl.wechat_local=ok`、同一个
  `run_id` 的历史里却是 `results={}`(第 1 轮自由审查 N2 实测)。**状态文件写不上那
  一档正是靠历史恢复的**,而恢复回来那一轮少了这份账就退回「整步那张合并卡片」,
  一轮里只有 RSS 失败时公众号跟着被算成欠着,点一次重试又把它抓一遍。
- **给人翻的那份记录里,整轮来源存的是「答案」不是「输入」**(`run_record` 的
  `scopes`:`run_scopes(state)` 的结果,空通道那一格不存 —— 它的含义是「不挂在任何
  具名来源上」,存着它那一行会显示成一个空名字)。这一份**故意不含 `export_filter` /
  `crawl_retry`**,而「只补导出」那一轮的来源恰恰只写在导出范围里(它的抓取范围是
  `{"force": true}`):于是光凭这份记录答不出「这一轮作用在哪」—— 历史那行写「未记录
  来源」、点开它主视图写「选择来源后开始一次同步」,而那一轮真真切切地在往那个来源里
  写文章(第 1 轮自由审查 R1 实页实测,口径在 `retry-scope.md` 第一节)。
  **不许改成把 `export_filter` 存进来**:「挑中的这一份没有重试派生字段」正是 `scope`
  那档欠账的判据,存进来等于让重试从一份只够展示的记录里派生范围 —— 那条路错一个字
  就是**静默不抓**。存结论没有这个风险:重试那条路一个字都不读它。
- **这份摘要不许因为「恢复成了当前结果」就消失。** 那句「恢复不把它搬进 `_state`」
  当初给的理由是「那边有两份 filter、自己派生得出来」—— 而**取历史那一份时这句话
  不成立**:历史故意不存 `export_filter`,而只补导出那一轮的来源只写在导出范围里,
  所以恢复回来的内存**派生不出来**。它的抓取范围是 `{"force": true}`,派生出来的是
  一个空通道:面板那行「本次范围」说不出来源,开着的来源页按来源列表判要不要重读
  条目、于是认不出这次完成通知跟自己有关,那几条就不刷新(只补导出不改条目总数,
  其余刷新判据也补不上这一次)。
  口径:**同一个 run_id 在历史里已有的、安全可展示的事实,恢复之后不该变少。**
  - **仍然不进常驻 `_state`**(那条理由的另一半照旧成立:多一格就要在每条起跑路径
    上各清一次)。实现是一个只在恢复时写一笔的旁路(`_restored_scopes`),由展示
    那一道唯一口径 `_latest_locked()` 附在**它要递出去的那份副本**上。
  - **按 run_id 认人**:换了一轮就不许再念上一轮的来源 —— 那一行和订阅的写保护都读
    它(`run_scopes`),漏进去的后果是订阅被错标成「正在同步」。
  - **只补、不覆盖、不反填**:内存里自己有那一格时不动它;更不许把它反填成
    `export_filter`(那正是上一条禁的事),也不许给某个页面加一道新的时序猜测。
  回归 `tests/test_pipeline_restore.py` 的 `RestoredScopeTests`:**后果**那一条判的是
  「恢复之后面板那行念得出 RSS」,反面两条是「换了一轮不许再念」和「`_state` 一格都
  没多」,另一条**反过来钉一边**验状态文件完整那一档压根不走旁路、照旧念得出。定点
  注入过这三处:展示边界不附回、恢复时不记那一笔、不按 run_id 认人。
  **夹具那边有个坑**:`HistoryCase.restart()` 原先只清 `_state`,而状态文件写失败那
  一档 `pipeline_batch._save_own` 会把这一轮快照放进内存权威位(有意的:面板要显示
  降级完成),`last_result()` 优先念它 —— 于是「重启之后拿不到的东西」在用例里照旧
  拿得到,恢复那条路整段没被执行到而用例全绿(本轮实测:定点拆掉修复也不红)。
  所以 `restart()` 要把进程内那几格权威一起清掉,那才叫重启。
- **这一格要逐字段验,和来源范围过同两道**(`_valid_round` 里用 `_names_ok` /
  `_channel_ok`):历史那行和主视图逐条读 `channel`,混进一个 `null` 就在那一下抛;
  只验到「是个字典」还不够 —— `accounts` 落成一个数字时照旧过门,而消费方把它当
  可迭代的摊开,那一下抛 TypeError,前端那份同口径的显示成 undefined 条。回归
  `tests/test_run_scopes.py` 的 `HistoryProjectionTests`、页面那一侧
  `tests/pipe_scope_probe.mjs`。
  **两个起跑入口要清掉同一样东西**(`pipeline.start_pipeline` 与
  `pipeline_retry.start_retry_failed` 各写一份 `_state.update`):上一轮的结果账留在
  内存里跨过来,这一轮就会声称自己覆盖了一个它压根没碰的来源。
  回归 `tests/test_channel_attribution.py` 的 `HistoryProjectionTests`。
- **留档失败不许把一轮已经做完的同步变成「永远进行中」。** `_end_run()` 里那两份落盘
  (`_save_last_run` / `_save_history`)是**旁路** —— 状态文件喂「重试失败项」的范围派生
  (重启之后才用得上),历史文件只给人翻;而发布终态(`_finished`)和放下 `running` 是
  **这一轮能不能收尾**。所以那两行待在 `finally` 里,**判据钉在 finally 上,不钉在
  「捕获里列了哪几个异常类型」上**:按坏法一种一种往捕获里补,下一种坏法照旧重现。
  失败如实记一笔 `persist_error()`,由 `/api/pipeline/runs` 带给面板。
- **「最新那一轮」只有一份口径**(`last_result()`),展示和重试都从它取。优先内存
  (`_state` 收尾后存的就是终态),**磁盘那份是给重启做恢复的 —— 它写失败了不该改变活
  进程里「最新是哪一轮」这个事实**。原来展示和重试各自直读 `load_last_run()`,于是最近
  状态写失败(权限、满盘)那一轮静默落后整整一轮。**`running` 时回退磁盘**:那时内存里
  躺的是正在跑的这一轮(阶段还是 pending),拿它派生重试计划会错 —— 这一档要的恰恰是
  「上一轮」,而那只有磁盘有。判据放在 API 一处(`status` 的 `last_run` 字段),前端照旧
  用 `pipeResult` 那份口径。
- **整次重试只取一份快照,而且起跑前要核对身份没变**(`start_retry_failed`)。计划、抓取
  范围、导出范围全从同一份派生 —— 原来计划和范围各读一次「最近一次」,两次之间别的窗口
  或调度器恰好跑完一轮的话,计划来自新那一轮的失败、而导出范围还是旧那一轮的来源。
  `retry_failed_plan` 因此收一个 `run` 参数(缺省自己取,给单独问「有没有失败项」的调用
  方用)。**锁内那道核对无条件做**,拿不准不许放行 —— 下面「起跑那道并发核对」那条写了
  为什么:要误拒的那两档(重启后内存还没跑过任何一轮、升级前落的老记录)恰好也是并发
  窗口,兼容它们是**降级比对**的事(身份没有就比收尾时间,`result_version` 保证任何一份
  快照都有值),不是放掉不变量的理由。
- **两份留档分别尝试、分别诊断,不许串在一个 `try` 里。** 串着的话状态文件写失败就把
  本来写得成的历史一起跳过 —— 那一轮在历史里直接不存在,而「历史里没有这一轮」和「这一
  轮还没跑过」在面板上长得一模一样。失败时**同时往那一轮自己的日志里写一行**:
  `persist_error()` 是内存变量,重启之后就没了,而日志跟着那一轮留在历史记录里。
- **落盘原语和候选判据待在 `pipeline_persist`,不跟运行状态混在一处。** 那边管的是
  阶段、日志、锁、收尾(错一下是「这一轮的进度不对」),这边管的是序列化、原子换文件、
  历史形状、完成版本、谁更新(错一下是「恢复之后拿错了一轮,面板显示上一轮的结论、
  重试去抓上一轮的来源」)。**这边的函数一律不碰 `_state`**,要比哪一份传哪一份进来;
  `pipeline_state` 那边只包一层默认 `_state` 的 `result_version` 给「现在这一屏是哪个
  版本」用。
- **两份落盘的读、写、序列化口径只有一份**(`_load_json` / `_dump_bytes` /
  `_write_atomic`),三件事各钉一个点:
  **读兜住所有异常**,不只 `OSError` / `JSONDecodeError` —— 这两份文件是外部状态,
  `read_text(encoding='utf-8')` 碰上非 UTF-8 字节抛 `UnicodeDecodeError`、深嵌套 JSON
  抛 `RecursionError`,两个都不属于那两类。而且**先按字节读、再 `errors='replace'`
  解码**:能读出来的尽量读出来,坏字节变成 U+FFFD 而不是整份丢掉(「漏报是静默丢数据」
  —— 历史里少一轮,在面板上和「还没跑过」长得一样)。
  **写按 `errors='replace'` 编码**:`ensure_ascii=False` 是为了文件能给人读,代价是
  编码那一步会炸 —— 某条旧记录里混进一个孤立代理字符(JSON 里合法、UTF-8 里不合法),
  `UnicodeEncodeError` 从写盘抛出来。按 replace 落盘,坏掉的只是那一个字符。
  **替换没成功一律把临时文件收掉**(`finally` 里 unlink):同进程里重名覆盖,但每次
  重启换一个 pid,留下来的慢慢堆着没人收。
  这两道是**冗余保护**:第一道在留档层隔离,第二道在收尾层兜底。**各有自己的回归** ——
  端到端那种「坏文件 + 走 `_end_run`」的用例两道都在时绿、单道去掉也绿,钉不住任何一道。
- **附属结果的新鲜度判据是「成功应用了哪一轮」,不是「见过哪一轮」**
  (`pipe_fresh.js` 的 desired / applied)。状态轮询回答「现在是哪一轮」,而历史列表和
  待处理数各是**另一次**请求取回来的 —— 只记「见过」的话,那一次附属请求失败之后后续
  轮询只知道「这一轮见过了」、不知道「屏幕上还没对上」:列表长期停在旧那份清单,等多久
  都不补,页面上还一个字都不说。**只有渲染成功才确认**;失败就留着缺口、按退避补读、
  并在面板上如实说一句这块是旧的。
  **退避挂在状态轮询上,不另起计时器**:轮询本身 6 秒一次(跑的时候 1.5 秒),再叠一层
  就有两套时钟,离线时还会变成无间隔重试。到上限只停自动重试,提示和那颗「重新读取」
  留着。
  **历史和待处理数走同一套**,不在两处各判一遍(那条 `catch` 原来是同一个形状:清掉
  欠账、保留旧值、什么都不说)。
- **翻历史时那句状态提示要换成只读语义**(`pipeStateHint` 开头那一档)。最新视图下它
  写的是「可重新配置一次同步,或按上次抓取范围重试失败项」,而翻历史时那颗按钮已经藏掉
  也禁用了 —— 提示指着一个按不到的操作,说的又是**另一轮**的失败。
- **落盘那份按天留,不按条数,而且窗口之内一条都不删**(`pipeline_retention`)。按条数封顶
  的旧口径在「一天里点了二十次重试」那天会把前几天连同它们的红一起挤掉 —— 而那正是最想
  回查的时候。
  · **窗口(`_HISTORY_DAYS`)是唯一会让一轮记录消失的判据。** 不许在它后面再塞一个条数
    上限:第 1 轮审查实测 `kept[:400]` 那一版,400 轮全落在 66 小时 40 分之内、再跑一轮,
    最老那一轮当场被删,而它距离三天到期还有五个多小时,面板上一个字不说。**不是「400 太
    小」** —— 任意硬条数上限都优先于时间窗,换个更大的数字照样是「保留最近 N 轮」,而用户
    要的是「保留三天」。
  · **判不出时间的一律留着。** 丢一条历史**不可恢复**(那一轮的红没有第二个地方查得
    到),多留一条只是多一行 —— 同元规则。升级前的旧记录、被手改坏那一行、`finished_at`
    落成数字(`strptime` 抛的是 `TypeError` 不是 `ValueError`)都走这一档。
  · **`_HISTORY_FLOOR` 是下限,不是上限。** 窗口判据建在墙上时钟上,而时钟会往前跳
    (手动改、NTP 校正、换时区):跳过去那一刻**整份历史看着全都过期了**,下一次收尾就
    把存量一次清光,面板上一个字都不说。它顺带盖住「一周只同步一次」那一档。
    **它只限制损失,不等于兜住了时钟** —— 跳过去之后新写的那一轮自己也带着跳过的时刻,
    拿「最新那条记录的时刻」当锚点照样救不回来。**所以这个数要给小**:给大了会反过来
    把窗口架空(三天里本来就常只跑五到二十轮,下限 10 的话实际生效的又成了按条数留)。
  · **体量那道守卫按字节算,而且只削重物、不删记录**(`shed_bulk`、`_HISTORY_BYTES`)。
    它要防的本来就是「这份文件每收尾一轮就整份重写一次」的成本,而成本按字节算:实测一轮
    1~28 KB(明细占大头、日志其次),一千轮瘦记录比四十轮带满明细的还小,按条数封顶会在
    前者上白削、在后者上又不够。超了从最老那头削两级 —— **日志正文**(面板本来就为「那
    一轮没留日志」备了一句诚实的话),再**把明细清单削到前 3 条**(`failures_total` 留着,
    于是面板念的是既有那句「明细 · 50 项(仅列前 3 条)」,和后端 `_cap_failures` 截断过
    的那一档走同一条显示路径)。**削明细时总数要先补上**:`_cap_failures` 只在它自己截断
    过的那一档写 `failures_total`,不补的话 50 条削成 3 条之后面板按数组长度念「明细 ·
    3 项」—— 削过和没削过长得一模一样。
  · **削的成本必须是线性的:改一条只重编那一条,不许为了对一次总数把整份再编码一遍。**
    这一步跑在收尾那把锁里(`_end_run`),而状态端点要同一把锁 —— 慢在这儿就是**页面读
    不到状态**。实测每削一条都重编整份的那一版:420 轮带满明细(约 10 MB)累计编码
    5.2 GB、收尾 29.6 秒,面板那条请求等了 29.5 秒,而前端 15 秒就超时报「连接失败」;
    改成增量维护之后收尾 0.14 秒、状态请求 0.1 秒。所以总量按「各条自己的字节之和」增量
    维护,**和最终那份文件差一点缩进和逗号 —— 预算本来就是数量级口径**(防的是「每轮重写
    一次」的成本),不是精确到字节的不变量。
  · **坏行只许坏自己。** 落盘那一层只保证根是字典、每条记录是字典(`_history_runs`),
    **没保证 `stages` 也是字典**:历史里一条 `stages` 落成非空数组/字符串的记录,削明细时
    `.values()` 当场抛 `AttributeError`,由收尾那层接住记成「留档失败」—— 于是**整份历史
    一个字节都没写进去**,那条坏行还在,下一轮超预算时又抛一次,**新跑的几轮从此全都查不
    到**(而面板只说一句留档失败)。按既有契约跳过这一行就好(同 `pipeline_failures.strip`
    和 `_valid_round` 的显式类型检查),**那条坏行自己也留着** —— 删它才是静默丢数据。
  **保留天数由后端报给面板**(`/api/pipeline/runs` 的 `keep_days` → `history_keep_days()`),
  前端不写死一个数字:两处各写一份的话,改了这边而面板照旧念旧数字,而那句话正是用户判断
  「我还查不查得到前天那一轮」的唯一依据。**后端没给就只报轮数,不编**(老后端、探针桩)。
- **账本的回收窗口跟着这一份走,不另猜一个条数**(`pipeline_failures`,见
  `failure-drop.md`):历史一扩大,那本账就会先于它淘汰身份,于是用户点过「不再抓取」的那
  几篇又出现在还翻得到的那几轮里。
- **留的天数和 `_finished` 那个数不是一回事,也不该统一。** 内存里那份只为「等的那一轮
  刚被接替」这个窄窗口,几轮就够;落盘这份是给人翻的,按天留。
- **日志自动展开记的是「哪一轮已经展开过」,不是一个布尔。** 布尔那一版的重置条件是
  「此刻这一屏不在跑」,而**翻历史也满足它**:跑着的时候手动收起、去翻一轮、再回到最新,
  日志又被顶开(第 1 轮审查实测 `open` 从 null 变回 "")。翻历史不是新起了一轮。
  **反过来钉一边**:真又起了一轮(身份变了)照旧自动展开一次。回归在
  `tests/pipe_layout_probe.mjs` 那一节(它自带的桩能摆出「有一轮在跑」)。
- **「哪一行是此刻屏幕上那一轮」要有证明,位置不算证明。** 清单和当前状态来自两条独立的
  请求、两份独立可失败的落盘,**允许不同步**:留档失败那一轮根本没写进历史文件,于是清单
  首条是上午那个红,而状态端点报的是下午那一轮的成功。按「排第一而且没在跑」认最新的那
  一版,点上午那个红会退出只读、屏幕换成下午的「同步已完成」,那一轮的失败明细**再也打不
  开**(第 1 轮审查用扩展实点,`archive-first-click.png`)。
  · 证明由**后端**给:`/api/pipeline/runs` 每行带 `is_current`,判据是
    `same_event(行, last_result())` —— **只认可信身份**,不看内容,也不许退到展示版本
    (它在旧记录上会撞,见下面那条)。证明不了就不标,那一行照旧打开它自己那一轮。
  · 前端再拿**手上这份快照的版本**对一次:后端那次证明只对它生成回包那一刻成立,而这份
    清单可能是个迟到的旧回包。两道都过得去才算「最新」。
  · **标签、选中态、点击动作三处共用这一个判据** —— 各判一次的话标签说是最新、点下去打开
    的是另一轮。
  · **渲染那一刻的证明只对那一刻成立,而这一行会在 DOM 里待很久。** 后台又跑完一轮、状态
    端点报的已经是它,而这一列那次历史查询恰好失败(503):整列一个字没重渲染,上午那个红
    **还挂着上一次渲染留下的「最新」和「回到最新」那个动作** —— 实点下去屏幕停在新那一轮、
    `readonly: false`,上午那一轮的 503 读不到。两道,**都要在**:
    列表按 `` `在跑没跑|屏幕上那一轮的版本` ``(`pipeHistorySig()`)重渲染 —— 只记「跑没跑」
    的那一版漏掉「空闲 → 空闲、但又跑完了一轮」;以及**点的那一刻再核验一次**
    (`pickPipeRun`),它是冗余带,接的是「这一列就是没能重渲染」那一档。
- **翻历史时「重试失败项」必须按不下去。** 它重试的永远是**最后一轮**的范围
  (`retry_crawl_scopes` 读的是 `load_last_run()`),而屏幕上显示的是上午那一轮 ——
  **「看到的那一轮」和「按下去会动的那一轮」必须是同一轮**(同 `translate.md` 里确认框
  那件事)。两道:`renderPipeState` 里按 `pipeViewing` 藏掉,`renderPipeButtons` 里另有
  一道 disabled(轮询的 finally 会单独调它,两道射程不同)。
- **「这一屏在显示哪一轮」只有一份口径**(`pipeResult`)。翻历史时在 `renderPipeState`
  开头换一份快照进去,整套渲染(阶段卡片、失败明细、进度条、日志)一个字都不用改。
  **`running` / `stop_requested` 要按「那一轮已经结束」给** —— 它们说的是此刻,而被翻到
  的那一轮早就收尾了,混着用会把上午那一轮的阶段配上此刻的「执行中」。
- **此刻的待处理数不许贴在被翻到的那一轮旁边**(`pipePending` 那几行、`pipe-issues` 里
  的积压那一档)。它说的是现在,贴在上午那一轮旁边就是一句谎话。
- **「列表上这一轮怎么一句话说」要复用阶段卡片那两个判据**(`pipePlannedStages` /
  `pipeHasFailure`)。自己再数一遍的话,列表上写「已完成」而点进去是两个红。
- **轮次列和被它改写的内容并排,不许待在页尾。** 点一行走的是
  `viewPipeRun` → `renderPipeState`,**整屏**(概况卡、失败明细、进度、阶段、日志)按那一
  轮重渲染 —— 它是个视图切换器,不是一张归档清单。原来它在页尾:1440×900 实测那一行在
  y≥1047、被改写的那块在 y=84,**点下去屏幕上什么都看不见**,而退出入口(`#pipe-viewing`)
  又在页顶,一次「这轮不对,看上一轮」是两趟整页滚动。判据落在**「被点的那一行和被改写的
  那块同屏可见」**上,不落在「DOM 挂在哪个父节点下」。
  · **`#pipe-viewing` 搬进概况卡里**:它回答的是「这张卡现在讲的是哪一轮」,那句话就该长
    在卡上。元素 id 和那颗 `.ghost` 不许改名 —— 浏览器探针按它们点「回到最新」。
  · **那一列要钉住**(`position: sticky`):展开一条问题明细就能把左边那列步骤拉长几百
    像素,选择器不能跟着滚出去。
  · **窄屏(`<=1180px`,和 `pipeline.css` 里那条塌列的断点同一个数)单列时它排到步骤上面、钉住关掉** —— 选择器要在被它改写的内容
    之前;那一档照旧靠 `viewPipeRun` 末尾那次 `focus()` 把视线带过去
    (**已经在视口里就 `preventScroll`**,并排那一档再滚一次是无谓的跳动)。
  · **`#pipe-history-list` 里只许有留档那几行。** 正在跑的那一轮不在留档里,它那一行待在
    列表**外面**(`#pipe-history-live`)—— 插进去会把 `nth-child` 的位置挤掉,而浏览器
    探针正是按它点「第几轮」。
  · **首行那一枚就是「最新」,点它一律回到最新。** 它显示的内容和最新视图逐字相同,点出
    一个只读态是个没有意义的末态。挑一轮和回到最新落在同一处。
- **失败明细只在步骤行里有一份。** 概况卡那一块原来逐条抄 `stages[k].detail`,而同一个
  字符串在下面那几行步骤的 `.pipe-stage-detail` 里已经有一份(存量实测有 200 字的)——
  同一屏上出现两遍,同元规则「口径只有一份」。那一块的职责收敛成「哪几步 + 去哪看」,外加
  一颗「看第一个」(只滚动和展开,不动任何东西,所以翻历史时照旧给)。
  · **消费这一条的探针有两份,口径要一起改**:`tests/pipe_layout_probe.mjs`(总览不含
    原因、阶段行含原因)和手工那份 `tests/subs_probe.mjs`(它原来要求**总览里含
    `503`**,两套判据不可能同时满足)。改成「总览点名那一步 + 原因在那一步行里读得到」,
    **不是把重复文案恢复回去**。
- **日志默认收起,跑起来时自动展开一次。** 它是出事才看的东西,常驻一块深色块会把整页的
  视觉重心占住。**只在翻上来那一下展开,之后不再管**:每次轮询都强制展开的话,用户跑着的
  时候自己收起来会被下一跳顶开。**也不自动收** —— 收在他正读着最后几行的时候同样是抢。
- **正在看的那一轮被挤出记录时退回最新。** 留着一份谁都查不到的快照,屏幕上那条
  「正在查看」就指着一轮列表上没有的运行。
- **历史刷新要保留在途期间的补刷需求,而且那一笔欠账要清在发请求之前**
  (`pipeHistoryWanted`)。「又跑完一轮」这件事**一轮只说一次**(`refreshPipe` 的
  `wasRunning` / `newResult` 两个分支),在途时直接复用旧 promise 的话那一次机会就没
  了:旧回包把列表设成它取到的那两轮,而 `pipeDoneRun` 已经更新成新那一轮,后续轮询
  再也不进那个分支 —— 列表自己追不平,得切走再回来才补齐。
  **清在「接受回包之后」同样不行**:在途期间别人记的那一笔会被它一起清掉,而那一笔
  恰恰是说「你这次取的已经不是最新的了」。
  另有一道「这份回包过时没有」的身份校验(发请求前记下 `pipeRunKey`,回包回来比一次)。
  **它今天是冗余带,如实记着**:每一条走到那一档的路上,`pipeFreshCheck` 都已经调过一次
  `loadPipeHistory()`,于是欠账那一道自己就够,定点去掉这一道**红 0 项**。留着是构造上
  的理由 —— 它回答的是「这份回包过时没有」,欠账回答的是「还有没有人想要一次刷新」,
  两个不同的问题。
- **两个附属结果的刷新只有一处判据:落后就补**(`pipeFreshCheck`)。原来是三个事件分支
  各自直接调一次(running→idle、没见过 running 的那一轮、首次读到结束状态),外加一道
  按退避补漏 —— **两套判据在同一个 tick 上重叠**,一次读失败会被紧跟着那次成功立刻盖
  过去,「失败了要说一句」永远轮不到。收敛成一处之后那三档自然都被覆盖:身份一变
  applied 就落后,首次 applied 是空的也落后。
  覆盖到的那三档各有来由,都别当成可以省:**首次**那一档是「刷新页面后立刻打开同步
  中心、恰好有一轮在状态和历史两个回包之间结束」——历史取到的是不含它的那一份,而那一
  次读取按定义不是「新结果」(基线就是它);**两种回包顺序都得兜住**,所以不许改成
  「只去掉历史那边的空身份短路」(那只治得了状态先到的一半 —— 历史先到时旧回包落地那
  一刻快照还是 null,拿什么都比不出来)。
- **applied 的凭据必须来自回包自己,不能拿此刻的页面快照盖章。** pending 回包带
  `run_id`,历史回包按它**最新那一轮**的身份。拿快照盖章的后果:一份属于上一轮的待处理
  数被标成「已追平最新那一轮」—— 缺口不存在、提示不出现、补读也不会发生,面板永久写着
  「还有 1 项内容待提取」而后端早就是 0。
  **pending 那边另有一道「对不上就不应用」**(回包身份必须等于当前快照身份),所以那边
  盖章用哪个表达式都一样(定点只换盖章**红 0 项**,真冗余);**history 没有这道条件**
  (留档失败那一档本来就等不了),盖章是它唯一的凭据 —— 那一处的注入有红。
  **留档失败是例外**:后端如实报了 `error` 时,那一轮根本没写进文件、补读多少次也追不
  平,这时按 desired 盖章,面板另有一句说那一轮没留下。
  **还没有快照时(首次,状态回包还没到)一律不应用、也不在那里循环重查** —— 快照一直是
  null、一直对不上,欠账留着等 `pipeFreshCheck` 来接。
- **「落后」不等于「请求失败」,两种都要补读。** 请求成功、只是拿到的数据属于上一轮,
  这一档原来根本不算缺口 —— 而它恰恰是上面那条的事故路径。提示的时机两档不同:请求失败
  **立刻**说(`reason` 非空);拿到旧数据**连试两次仍没追平**才说,一次就说的话正常的
  时序追赶会在面板上闪一下。
- **「这一屏对应哪一轮终态」只有一个版本口径,而且任何一份快照都有值**
  (`result_version`:身份 → 收尾时间 → `"none"`)。`run_id` 是后来才加的字段,所以凡是
  拿「有没有身份」当判据的地方都得另开一条兜底分支,而那些分支各自带一个事故:前端把
  空身份当「已追平」(面板永久停在旧数字)、后端「拿不准一律放行」(旧快照绕过并发核对)。
  **「从没跑过任何一轮」也是一个确定的版本,不是「未知」** —— 这一句是上面两档的根因:
  空串在原来的代码里同时表达「还不知道」和「已经追平」,两种处理各错一档。
- **两个端点报的版本必须同一份口径**(`/api/pipeline/status` 的 `result_version`、
  `/api/pipeline/runs` 的 `version`),前端不许自己从清单首条或顶层字段拼。各算一遍就会
  在某一档上岔开,而岔开的后果是静默的:对不上就一直补读(忙循环),或者被当成已追平。
- **启动后第一次读状态,要把磁盘终态恢复进 `_state`**(`_restore_once`,懒做、只做一次、
  `running` 或已有收尾时间时不动)。「最新那一轮的终态在内存里」这个契约 `last_result()`
  和起跑核对都建在它上面,而新进程里身份、起止时间全是空的 —— 不恢复的话重启那一档是个
  洞,前后端各要一条特例去绕,而那两条特例就是上一条说的两个事故。恢复之后
  `last_result()` 的内存判据也降成**只看收尾时间**(旧格式记录没有身份,它一样是终态)。
- **恢复要核对两份落盘,不能只信状态文件**(`_newest_round`)。那两份是分别写、分别
  诊断的,所以状态文件写失败而历史写成功时,磁盘上最新那一轮**只在历史里** ——
  只读状态文件会把**上一轮**当成「最新」固化下来,展示、完成版本和重试计划一起退回去。
  **判据按凭据强弱排三级**:①两边都有完成序号就按它;②历史是倒序的,「状态文件那一轮
  出现在首条后面」就足以证明首条更新;③两样都没有才退回比收尾时间 —— 而时间**分不出
  来时不许默许老那份**,见下面两条。
- **先后要有一个落在盘上的凭据,墙上时钟不够**(`run_seq`:`_end_run` 落盘**之前**发、
  两份各带一份)。那两份是分别写、分别可失败的,所以磁盘上它们记着的可能是不同轮次,
  而恢复时必须分得出谁更新。`_now()` 只到秒,两轮落在同一秒**不是构造出来的**:一次
  「重试失败项」紧跟一次同步,两个 `finished_at` 实测都是 `16:08:29`。序号由
  `_next_seq()` 取两份现有记录里的最大值 +1,所以它**跨进程单调**,不随内存那个自增
  计数器重启归零(模块里那个叫 `_id_seq`,只管拼身份,跟这个不是一回事)。
- **发号读失证时发 0,不许从 1 重新开始。** 0 在 `_seq_of` 那边表示「这一轮没有顺序
  凭据」,恢复时序号那一档直接走不通、退到位置和时间去证明。发一个**看着合法的小
  整数**是最坏的那一档:它和磁盘上那些号不相等,于是恢复层拿它当成「谁更晚」的证明
  用 —— 实测形态是磁盘上已经三轮、序号 1/2/3(第三轮 A 的导出 503),第四轮 B 成功
  但发号那次读失证、B 的状态文件又没写上,于是磁盘上状态记着 A/3、历史首条是 B/1;
  恢复当场判出「A 更新」,页头显示 A 的 503,点「重试失败项」导出阶段收到的是 A 那
  个来源,而 B 明明已经成功。**失证必须是「没有凭据」,不是「一个小凭据」。**
- **墙上时间不是顺序凭据,凭据只认两样:同一份历史里的位置、同一代发出来的完成
  序号。** 两样都不成立就报 `order`,**不许拿收尾时间凑一个先后出来** —— 时钟会往回
  跳(手动改、NTP 校正、夏令时),那时后跑完的那一轮时间更早,判据于是反过来指向旧
  那一轮,**而且报「完整」**:页头显示它的失败、重试可点,点下去抓的是它那个来源。
  实测形态:A 轮失败(状态写上了、历史没写上)、B 轮成功(发号读失证所以没有号、
  历史写上了、状态没写上),这期间时钟回拨过 —— 两轮的收尾时间成了 18:30:05 和
  18:30:00,重启后页头是 A 的 503,而历史里唯一那行写着 B 已完成。
- **序号那一档不拿收尾时间去反驳。** 时钟回拨的时候**号才是对的那一个** —— 它单调,
  而时间会往回跳。所以两边都有同代号且不等时,大的就是更晚,不再看时间。
- **顺序凭据要自己带出处**(`seq_gen`,发号世代)。单调性是**发号那一步**的性质,不是
  数值本身的性质 —— 而老代码在发号读失证时从 1 重新开始,那些**回退号已经落在盘上
  了**,修了发号也追不回来。单看一个正整数分不出它是哪一代发的:状态文件 7 号、历史
  首条 2 号,按数值信它就判出「7 号那一轮更新」,而它其实是旧的。所以 `_seq_of` 只认
  当前世代的号,**没出处的一律当没有**(退到位置证据,没有就报 `order`)。换一套发号
  逻辑就把世代加一,跨世代一律不比。
- **「同一轮」要能证明,不许拿展示版本相等充当它。** `result_version` 保证非空
  (身份没有就降级到秒级收尾时间),**不保证一轮唯一** —— 两条都没有身份而收尾时间又
  相同的旧记录版本就会撞。那个捷径排在顺序判据**最前面**,所以位置和序号那两道连被
  问到的机会都没有:实测两轮都是 19:30:00,状态文件记着 A 的翻译失败、历史唯一那行
  是后来 B 的成功 —— 页头显示 A 的 503、重试可点,点下去导出阶段收到的是 A 那个来源。
  证明走 `same_round`,**两级,而且两级互斥 —— 不是「先试一个再试另一个」**:
  1. **可证明唯一的事件身份**(`event_id`:当前世代 writer 写的记录,它的
     `run_id` 一定出自 `new_run_id()`、带着跨进程唯一的那一截)。旧格式那些
     `run-1` / `run-2` 只有进程内自增、**重启之后会重复**,一个都不信。
     **任一边拿得出它,就只看它相等不相等 —— 第 2 级一步都不许走。**
  2. **两份副本的内容逐字相同**(`_ROUND_FIELDS`:起跑/收尾时刻、类别、停没停、
     计划、阶段、抓取范围、日志)。只在**两边都拿不出身份**时(旧格式)才谈。同一轮
     的两份是从同一份 `_state` 写出去的,所以一字不差。
  **让第 2 级盖过第 1 级是漏报。** 身份不等是最强的「不是同一轮」证明,而内容那一级
  比的字段里**没有** `export_filter` / `crawl_retry` —— 恰恰是重试范围和失败名单:
  实测两次快速重试落在同一秒(21:04:00),阶段、抓取范围、日志逐字相同,身份是
  `run-6acf76695d2e-1` / `-2`,导出范围分别是 A订阅 / B订阅 —— 内容兜底把它们判成同
  一轮,`/api/pipeline/retry-failed` 返回 200(该是 409),重试线程实收 A订阅。
  **一边有出处一边没有也是「不是同一轮」**:同一轮的两份副本出自同一次 `_end_run`,
  身份和世代必然一致,一新一旧说明中间至少隔了一次升级(典型是升级后跑完一轮、状态
  文件那次写失败)。少了第 2 级本身是**误报**:升级前那最后一轮(两份都写成功、确实
  是同一轮)会被判成「先后证明不了」,重试被拦一次 —— 代价只是重抓一次。
- **同一个「同一轮」口径还要喂两处:位置锚点和起跑核对。** 位置锚点拿展示版本去历史
  后续行里找状态那一轮的话**找到的可能是另一轮**,「首条更新」这个结论就建在假锚点
  上;起跑核对(`start_retry_failed` 锁内那道)比展示版本的话,期间又跑完一轮而两轮
  版本撞上时整条放行 —— 手上那份其实已经不是最新了。
- **内存那份终态也要带世代标识。** 不带的话活进程里那份快照的 `event_id` 是空的,
  起跑核对就只剩「内容逐字相同」那一级兜底 —— 那是给旧格式留的退路,不该当主路使。
- **出处要跟着那一轮走,恢复不许沿用内存里的默认值。** `_state` 初始带的是当前世代,
  而恢复回来的可能是旧格式记录(压根没有这个字段):漏掉它的话,升级前那一轮的
  `run-1` 和可能回退过的 `run_seq` 在内存里就**冒充**成了「当前这一代发的号」——
  `seq_gen` 的全部意义就是让凭据自己带出处,改掉它等于让 `event_id` / `_seq_of`
  自己的门槛失效。**反过来,出处和号要在同一处定**:开新一轮那两段(普通同步、重试
  起跑)都不碰 `seq_gen`,所以由 `_end_run` 发号时一起署名 —— 不然恢复过一次之后内存
  那份终态**永久失证**,起跑核对一直吃内容兜底那一级。
- **「这一轮发生过没有」和「这一份渲染得了没有」是两个契约,不许合成一个判据。**
  前者叫 `_event_round`(是字典 + 有收尾时间),后者叫 `valid_round`。一轮跑完过这件事
  由它的身份、完成序号和在历史里的位置记着;正文坏掉只说明**这一份读不出来**。
  **挑最新那一轮只许按前者过滤候选** —— 按后者过滤的话顺序凭据连同正文一起被丢掉:
  实测 B 轮(成功、范围是 B订阅)只有 `log` 落成字符串,身份、当前世代、递增的
  `run_seq` 全在,恢复却返回 A 轮(翻译失败、范围是 A订阅)并报**空欠账**,页头显示
  A 的 503、按钮可点,点下去导出阶段收到的是 A订阅。**可显示性只能决定怎么呈现一条
  记录,不能决定这次运行有没有发生。**
  挑中的那一轮渲染不了时,正确的末态是三件事一起:**展示退回读得出来的那一份、欠账
  记 `broken`、拦住按旧范围重试**。连带两条:
  · **「一份都挑不出来」不等于「确定从没跑过」** —— 两份都坏时欠账要如实记下来再说
    「恢复这件事做完了」,否则面板报「尚无运行记录」而那颗按钮照旧可点。
  · **欠账那道闸要排在「有没有失败项」前面**:两份都坏时 `last_result()` 给的是空
    字典,计划于是也空的,拒绝理由就成了「上次运行没有失败项」—— 而真相是「最新那
    一轮的留档坏了,屏幕上这一轮不是最新的」。两句话会让人做出完全不同的下一步。
- **内容逐字相同够用来认一份副本,不够用来授权重试**(`same_event` vs `same_round`)。
  `_ROUND_FIELDS` 里没有 `export_filter` / `crawl_retry`,因为给人翻的那份历史副本本来
  就不写这两个字段 —— 不是它们无关紧要,恰恰是重试范围和失败名单。所以旧格式(两边都
  没有可信身份)下内容相等证明不了事件唯一:实测两次不同的重试落在同一秒、步骤和日志
  相同、各自的导出范围是 A订阅 / B订阅,内容相等把它们判成同一轮,于是「状态文件那份
  完整」这个结论成立、欠账报空,重试端点返回 200、线程收到 A订阅。
  **凡是「要据此放行重试」的地方过 `same_event`**(只认可信身份):恢复那条捷径。
  **位置锚点也只认身份**:内容相等不是唯一的 —— 旧格式 saved 其实可能晚于首条,而历史
  里留着更早的另一轮、它的显示字段恰好和 saved 相同,拿内容去找就「找到」了它,于是断言
  首条更新、把更早那一轮摆上屏幕。重试那边是安全的(欠账非空、按钮按不下去),**可顶部
  那一屏在说假话** —— 而「展示对不对」是这颗判据的另一半职责。没有身份就降到序号档、
  再不成就 `order`。
  **只剩一处仍过 `same_round`**:锁内起跑核对(它问的是「这期间
  状态变没变」,两边同源时必须为真;真又跑完一轮的话那一轮带着当前世代的身份,身份级
  当场判出不等)。**代价换过来了,而且换得对**:升级前那最后一轮(两份都写成功、确实
  是同一轮)从此落到 `order` —— 展示仍是它,只是重试要先跑一次完整同步。那是误报,
  顶多多跑一轮;反过来是漏报,静默按旧范围抓错来源。
- **消费契约要验到被消费的那一层为止**(`valid_round`)。意思是「拿这一份渲染一屏不会当场
  炸,而且那一屏说的是实话」,所以**被直接消费的字段逐个验,外层形状对不代表里面那层
  也对**:
  · 时间得是字符串、不是「真值」就行 —— 一路走到页面上按字符切(`pipe_view.js` 的
    `replace` / `slice`),落成数字时那一下当场抛;`started_at` 同一条路。
  · `log` 得是列表 —— 落成字符串时日志那一屏 `lines.join()` 当场抛。
  · `stages` 得是**非空**字典、每个元素也得是字典 —— 混进 `null` 时 `pipeRunLabel`
    的 `st.status` 当场抛(那一处没有可选链);而一个阶段都没有的记录不抛却更坏:
    数不出红也数不出跳过,`pipeRunSummary` 把它汇总成**「已完成」** —— 一轮根本没跑
    过的「成功」。
  · `planned_stages` 得是 None 或列表。
  · **验到叶子**:失败名单的每个元素得是字典(前端逐条读 `f.pending` / `f.title` /
    `f.reason`,混进一个 `null` 就在 `failures.every` 那一下抛);那本账里的 `targets`
    得是列表、`at` 得是字符串。
  · **抓取范围和导出范围过同一份口径**(`_filter_ok`):`export_filter` 原来压根没验,
    而重试正是从它派生导出范围的。`accounts` 落成字符串那一档最阴 —— 后端那一迭代把它
    **拆成一个个字符**当订阅名,不抛,而是静默按一串不存在的名字去抓,等于一条都不抓。
  · **嵌套一层**:每个阶段里那个失败名单(`failures`)得是列表 —— 落成字符串时
    `pipe_view.js` 的 `failures.every` / `.map` 当场抛,实测打开同步中心就一直停在
    「正在读取同步状态」,下面一句「状态暂时无法更新:failures.every is not a
    function」,整屏不可用。来源清单(`crawl_filter.channels`,前端 `.map`、后端还要
    按 scope 取 `accounts` 迭代)和失败名单那本账(`crawl_retry`,按字典访问)同一条路。
  上面那几个异常**都冒到状态渲染那层,整屏变成「状态暂时无法更新」**,不是只跳过一行
  —— 历史行那道 try/catch 只保护它自己那一行,**保护不了它被打开之后的整屏**。所以
  判据待在读取边界这一处,恢复挑最新、端点标 `invalid` 都过它。
- **「最新那一轮」回落到磁盘那份时也要过这道形状判据。** 那一档走的是「恢复还没成功
  / 恢复拒了磁盘那份」,而拒的理由多半正是形状不对:`load_last_run()` 是宽口径的
  「磁盘那份原样」(还有只取失败名单的消费者在用它),`_latest_locked` 的回落不补这一道
  的话,被恢复挡在门外的那份记录从这里原路进来,照旧交给面板整屏渲染和重试派生。
  **宁可报「尚无运行记录」** —— 那是实话,而且跑完一轮就补回来了。
- **判据按「不依赖别处做对」排序,不按强弱直觉**:位置证据 → 完成序号。
  序号看着最硬,可它的单调性要靠发号那一步做对;位置证据只用同一份文件内部的先后
  次序,这份文件读出来了就成立。**而发号错过的号已经落在盘上了,修了发号也追不回来**
  —— 老代码失证时从 1 重新开始,那些小号就在存量里:历史首条是真正最新的那一轮却只
  有 1 号,状态文件记着的上一轮有 3 号、而它**还留在历史里**。序号排在位置前面的话,
  它判出「3 号那一轮更新」,而历史自己的次序就在反驳它。
- **序号和收尾时间指向不同的一轮时报 `order`,不许挑一个。** 那是发号一度回退过的
  签名(存量记录里就有)。两样凭据互相矛盾时谁都不可信,报「证明不了」、拦住重试,
  跑完一轮自己就好了。
- **「可解析但形状不对」和「读不出来」是同一档,都不许当成「这份副本没有」。** 恢复
  那一步会就此静默认可另一份 —— 而它可能正是旧的那一轮;追加那一步会拿一个空集合
  整份替换掉存量(下一条)。`_history_shape_ok` 的口径:要么文件不存在,要么是
  `{"runs": [...]}`;`runs` 里个别元素不是字典**不算**形状坏(那一条过滤掉就是了,
  它只坏自己那一行)。展示那条路照旧走宽口径(`load_history`,少显示几行、不出声)。
- **「文件里是 `null`」不是「文件不存在」。** 两者都返回 `None` 的话,上面那些
  「`None` = 确定没有」的判据就把一份坏文件当成了空库:恢复静默认可另一份(可能正是
  旧的那一轮),追加拿空集合整份替换。`_load_json_strict` 因此在解出 `None` 时抛。
- **两份落盘的根形状各有一个判据,而发号和恢复共用它们**(`_state_shape_ok` /
  `_history_shape_ok`)。各写一遍的话两处会在某一档上岔开:发号层把坏根当成「没有
  记录」照旧发号、恢复层却拒绝 —— 而「这一份算不算有」在两处必须是同一个答案。
- **「不算一轮运行」的记录要标出来,不许显示成一轮成功,也不许当清单版本凭据**
  (端点的 `invalid` 过的是恢复那边同一个 `valid_round`)。历史首部多个 `{}`(坏文件、
  半截写入)就够:它**不抛**、字段「齐」,照常渲染就是一行「时间未知 · 同步 · 未记录
  来源 · 已完成」—— 一轮根本没跑过的「成功」,而恢复那边早就拒绝这种记录。版本那头
  同样要跳过它:拿无效首行算出来是 `none`,状态端点报的却是真实那一轮,两边永远对
  不上 —— 面板于是一直提示「历史还没追平」、补读一直在跑,点「重新读取」也不消失。
  前端把它和「渲染时抛」走**同一个出口**(坏行就地说明):那是同一件事的两种形态。
- **历史追加的存量只许来自「确实读出来了」或者「文件确实不存在」,别的一律抛,而且
  原文件一个字节都不许动**(`_history_rounds_strict`)。追加之后是整份原子替换,而
  **原子性只保证新文件完整、不保证旧记录还在** —— 拿一个因为读失败而空着的集合去
  替换,就是把存量删掉。实测形态:库里已经三轮(其中一轮带着失败原因和日志),第四轮
  成功、只在这一次读上注入一个 `PermissionError`,历史当场从 3 条变 1 条,而两份都
  写成功、诊断是空串,**面板上一个字都不说**。抛出去正好:`_end_run` 那两份是分别
  尝试、分别诊断的,这一份写不上只少一条历史记录、面板会如实说一句。
  **这条翻掉了「坏文件不许从留档层逃出来」那个更早的要求**,分界是**这一份存量读不
  读得出来**:非 UTF-8 字节按 `errors='replace'` 读之后仍是合法 JSON、形状也对(坏的
  只有那一个字符),孤立代理字符读得出来、抛在**写**那一步 —— 这两种照旧隔离在留档层
  里、照旧追加成功。真读不出来的(深嵌套 JSON、形状不对)才抛。**代价是有意的**:
  文件真坏了的话历史从此写不进去,每轮在面板上说一句,直到有人把它删掉 —— 比静默删
  掉存量强,那一笔不可恢复。
- **按身份删行只认「这一份记录实际合并了哪几轮」,不许据「内存权威位上有没有结果」
  反推**(`_save_history` 的 `superseded` 取 `pipeline_batch._aggregate_covers()`,由
  发布那一刻一并记下)。一轮日报的几次运行合并出一份汇总之后,那份汇总要顶掉它合并
  进去的子轮各自留下的行(一条业务结果只占一行,批次那一侧的口径在
  `sync-schedule.md`);但**权威位上也可能躺着一轮普通运行自己的快照** —— 落盘失败那
  一档会把它记上去,好让面板看得出这一轮是降级完成的(`pipeline_batch._save_own`)。
  它一轮都没合并,按「有缓存就是整批」去删,期间那几轮各自唯一那条历史就没了。实测
  形态:先一轮 RSS 抓取失败留下它那行,用户自己点的那轮同步赶在这一批中间收尾、只给
  它的状态写入注入一个 `OSError` —— 那行抓取失败当场消失,而两边都没出声(状态文件里
  那份是上一次写成功的,面板看着一切正常)。发布被拒之后写下的那份局部结果同样占着
  权威位、同样一轮都没合并,是同一类的第二条触发路径。**少删那一边是安全方向**(只是
  历史里多留一条旧记录),所以 `covers` 缺省是空集:新的赋值点忘了传它只会少删、不会
  丢数据。反过来钉一边:**真的汇总即使状态写失败,历史存的也还是完整汇总、顶掉的也
  还是那几轮** —— 退回局部结果等于把这一批的失败连同重试名单一起抹掉。回归
  `tests/test_history_rows.py`(两个方向各定点注入一次,各红两条)。
- **候选要先验,不能只过滤非字典**(`_valid_round`:得是字典**且有收尾时间**)。历史
  首条是个空对象时(坏文件、半截写入),不验的话它就被当成「最新」比一轮,把后面那些
  仍能证明更新的记录**整段遮住** —— 恢复于是退回状态文件那一份,而它可能正是旧的。
- **先后证明不了就如实报出来,不许默许老那份**(第三档 `order`)。序号、倒序位置、
  收尾时间三样都分不出时,「选状态文件那一份」看着保守,其实是在**赌**:它要是旧的,
  重试就按上一轮的范围去抓。这一档和另外两档一样拦住重试、面板上如实说一句,**跑完
  一轮就自己好了**。
- **恢复得不完整时要说出来并拦住重试,不许静默退回上一轮的范围**(`restore_gap`)。
  历史记录**没有重试派生字段**(`export_filter` / `crawl_retry`,有意的),所以取它那
  一份时导出范围和失败名单是空的 —— 拿上一轮的去抓会把失败那个来源摘掉:面板报
  「导出完成 · 已保存 0 条」,而它那几篇一个都没落盘(见 `retry-scope.md`)。后端那道
  闸在 `start_retry_failed`,面板上那颗按钮同时按不下去并如实说一句。**跑完一轮就
  补回来了**(`_end_run` 收尾时清),所以「重新读取」不该清它。
- **「读不出来」和「确定没有」必须分得开**(`_load_json_strict`:文件不存在才返回
  `None`,其余一律抛;旗标只在**读成功之后**才置位)。两者都当成「没有」的话,一次
  瞬时读失败会被永久固化成「这个库从没跑过」:内存里那份终态一直是空的,而展示那条
  路照旧从磁盘读得到真实那一轮 —— 起跑核对拿空版本去跟它比,**每一次重试都报「这期
  间又跑完了一轮」,而其实什么都没跑过**。展示那条路照旧用宽口径(读不出来少显示几
  行、不出声)。
- **「有可追溯的边界」是起跑的前提,不是事后的提示**(`pipeline_open`,两头都要钉住):
  · **写不上就不许起跑。** 原来是「写不上只记一笔诊断、照旧跑」—— 那个取舍把代价算小
    了:它的代价不是「这一轮的结果将来可能说不清」,而是**系统会重新授权上一轮的范围、
    而用户看不见**。这一档**事后推不出来**(两份终态都是上一轮、逐字一致,而标记这一笔
    也没落上 —— 磁盘上没有一个字指向这一轮),「跑完之后、收尾之前再落一笔」也救不了它 —— 那时写盘同样是坏的。
    误报的代价很小而且看得见(这一轮不跑、面板上说清为什么;数据目录写不进去本来就是
    用户该知道的事,何况那一轮的终态也一样写不上)。
  · **读不出来算「说不清」,不算「没有」**(`gap` 三档:`''` / `'lost'` / `'unknown'`)。
    权限、I/O、半截写入、非 UTF-8 字节,以及读出来的**根**不是字典(`null`、`[]`、
    一个字符串)都归 `unknown`;而且**这一档不许固化** —— 和另两份落盘同一个处理:
    下一次读状态时再核对一遍。
  · **三份落盘过同一个严格读取**(`_load_json_strict`)。「不知道不能算没有」在三处必须
    是同一句话;第三份走宽口径的话,前两份守住的不变量就从第三份漏出去。
  · **判「文件不存在」只认 `FileNotFoundError`,不许用 `Path.exists()`** —— 后者吞掉
    `OSError`(父目录权限不足、路径里有一节不是目录、底层 I/O 错误)返回 False,于是
    「看不见」长成「没有」,而这两件事在这里导出的结论完全相反。
  · **闸在锁里、`_state` 还没认下这一轮之前**,占不住就什么都没改。放在
    `_state.update` 之后的话,拒绝起跑得把那一堆字段挨个撤回去 —— 撤漏一个就是下一轮
    带着上一轮的范围。
  · **标记带的是这一轮自己的出处,不许拿常驻那份运行状态顶替。** 恢复过一次之后它的
    `seq_gen` 是被恢复那一轮的出处(旧格式压根没有这个字段,于是是 None),借来的出处
    让新一轮的标记认不出身份 —— 而「认不出身份」正是失证的判据之一,于是误报。
  · **收尾两份都写上了才清标记**,任一份失败就留着;判据是「标记那一轮**在两份落盘里
    一份都找不到**」,不是「标记还在」、也不是「标记不是挑中的那一轮」(后两种各会多报
    一整类)。
- **「没起跑」有两种,要说给用户听的那一句不许合并。**「管道已在运行中」和「这一轮的
  边界落不下来」在用户眼里是完全不同的下一步:前者等一下再点,后者要去看磁盘和权限。
  照着前者报等于把一个要动手的故障说成「等一下再点」,用户会一直点下去。原因**收在调用
  方自己传进来的列表里**(`start_pipeline` 的 `refused`),不放模块变量 —— 两个窗口同时
  点同步时,「刚才那次为什么没起」只有自己这一次的调用答得准。
  **每个用户可见的调用方都要念它**:面板(`pipeline_api`)、两条订阅入口
  (`intake_api`)、以及**日报**(`daily_sync._sync_round`)。日报漏接的形态是它把空
  返回值一律改写成「同步管道已被其它任务占用,本轮跳过」,而一轮日报有 N+1 段 ——
  各来源那几轮加入库那一轮会**各劝一次「等一下」**,而那一档等不好,真实原因只留在
  管道日志里。调度那条路(`_scheduler_tick`)不编界面文案,照旧只记日志。
- **消费契约验到叶子,不止验容器。** 容器对而元素坏的那几档后果一样静默、甚至更糟:
  来源名落成字典时重试派生拿它当**字典键**去查失败名单,`TypeError: unhashable type`
  从保护块外抛出去,整次重试变成一个说不出原因的 500;订阅名(`accounts` 的元素)和重试
  目标(`targets` 的元素)落成字典时都不抛,被当成一串 `{'id': 3}` 去筛选、去传给采集器
  —— **静默一条都不抓**。抓取范围和导出范围过同一份口径(`_filter_ok`),范围根上和每个
  scope 里各有一份订阅名单,两个落点共用同一个元素判据。
- **起跑核对的另一边走 `_latest_locked()`,不许直读 `_state`。** 它和 `last_result()`
  是同一份口径(那个要拿锁,核对必须在锁内比,所以抽成两层)。各写一遍的话「恢复还
  没成功」那一档上两边会岔开,后果就是上面那条的永久误拒。
- **历史行递给范围判据的是整份运行快照,不是裸 `crawl_filter`。** 判据是这一轮
  **计划里有没有** crawl / export(`pipeRunScopes` / `pipeLibraryOnly`,口径在
  `pipe_channels.js`,主视图和订阅页走的是同一份);裸 filter 会落进留给存量记录的
  兼容分支,而 `start_pipeline` **一律**往 filter 里盖一个默认采集器名 —— 于是日报
  那个只跑 index/extract 的子轮在列表上被说成那个来源,点进去主视图写的却是
  「全库(不按来源)」。**全库那一档自己有话说(「全库」),不许回落成「未记录
  来源」** —— 它不是没记,是不按来源。回归在 `tests/pipe_history_probe.mjs` 末尾那
  一组(真 DOM 读数),反向那一边钉的是按来源那一轮照旧写出来源名。
- **每条历史记录都要带一个能选中它的键,而且逐行唯一**(端点里的 `row_key`:有完成
  序号就 `seq-N`,没有退回 `result_version`,撞了加 `#2`),渲染、点击、再次定位、
  高亮共用它。原来按 `run_id`,而那是后来才加的字段:没有它的那几条在属性里就是空
  字符串,点下去查找要求 `undefined === ''` —— 那一行**看得到却打不开**。
- **选择键和新鲜度版本是两个契约,不许共用一个字段**(`key` 对行、`version` 对轮)。
  新鲜度那边要的是「这一屏是哪一轮」,**两条记录属于同一轮时本该相等**;选择键要的是
  「点的是哪一行」,相等就是故障。合用一个的话,一边的降级口径会变成另一边的 bug:
  升级前落的记录没有身份,`result_version` 降级到收尾时间,于是**同一秒跑完的两轮键
  会撞** —— 点较早那行打开的是较新那一轮(`find` 只找得到第一条)。
- **两个附属结果对「请求成功了、取回来的是另一轮」要一个口径地回报。** 历史那边拿
  回包自己的版本盖章(追不平就扣一次预算),待处理数那边对不齐时不应用 ——
  所以它要在退出循环时显式回报一次,否则这一块的预算一次都不扣:每轮状态轮询都再补
  几次查询,既到不了上限、也到不了「连试两次才说」那个提示阈值,面板一个字不说而后台
  一直在扫库。
- **起跑那道并发核对无条件做,「拿不准一律放行」不是兼容策略。**「两边都有身份才比」是
  为了别误拒重启和升级前的老记录,可那两档恰好也是并发窗口。兼容旧记录是**降级比对**
  (身份没有就比收尾时间)的事,不是放掉不变量的理由。
- **补读预算属于目标版本,不属于页面的一生。** 目标一换就重新给;**明摆着读不了的那一档
  不读也不扣**(跑着的时候没有终态可追平,待处理数那个加载器本来就直接返回);**次数由加
  载器回报结果时扣**(`pipeFreshOk` / `pipeFreshMiss`),不在调度那一步扣 —— 它可能因为在
  途而一次请求都没发,那种空转扣掉的是一次没用过的额度。
- **对不齐就退出循环,交给那道有界补读**(`refreshPipePending` 的 `spins` 上限 + 「没有
  快照 / 又跑起来了」那一档直接返回)。在循环里等身份变好等不到:快照不会因为我们重查
  而出现。
- **一条坏记录只许坏它自己那一行**(`pipeHistoryRow` 各自兜一次)。这些字段全来自落盘
  文件,形状没有任何保证。
- **历史条目的身份走 `data-run` 读,不拼进 `onclick`** —— `esc` 把引号转成实体,而属性值
  里的实体会在解析时还原,拼进去的话一个带引号的身份就把那句 JS 拆了。

## 事故形态

翻译服务返回 503 那一轮,`sync._new_failures` 判了红,导出阶段如实报了「N 条翻译失败」。
**那个判红是对的,也只认本轮**(此前失败单独一档、不判红 —— 见 `translate.md`,那是有意的:
一条永久失败的内容不该把每一轮都标红)。问题全在后面:当天晚上一次「重试失败项」跑完,
`_save_last_run()` 整份重写了 `pipeline_state.json`,上午那一轮的阶段结果连同它的失败明细
和日志一起消失。用户第二天来看,面板上是一轮全绿的「重试已完成」,而那十条内容仍然躺在
库里没有译文 —— 唯一的线索是来源面板上一句「还在等翻译」。

两件事的分界线要划清:**判红只认本轮是对的,留档只留最后一轮是错的。** 修的是后者。

落档本身还有两个形态,都是「留了但你看不到」:

**重启把前一轮顶掉。** 身份是进程内自增的,重启后第一轮也叫 `run-1`,按身份去重时它把
上个进程那个 `run-1` 整条替换掉。真实复现:两个独立进程共享一个数据目录各跑一轮,第一轮
报 503、第二轮成功,读历史只剩成功那一轮 —— 失败原因、失败明细、日志全没了,而历史里
「只有一轮」看上去和「才刚用起来」一模一样。

**一轮新结果恰好落在历史请求在途的那几百毫秒里。** 顶上和日志都换成新那一轮了,底部
列表却一直少它,等多久都不补 —— 必须切走再回来。原因是「又跑完一轮」一轮只说一次,而
那一次说的时候历史请求在途、被直接合并掉了。

**同一件事在首次加载那一刻还有一个形态,而且更难看见。** 刷新页面后立刻打开同步中心,
一轮恰在两个回包之间结束:顶上的阶段卡片和日志都是新那一轮,底部列表却是上一轮那份清单,
**长期**少最新一轮。这一档和上面那个不一样 —— 上面那个至少有人调过第二次(新结果那一
分支),这一档连那次调用都没有:首次读取只建立基线,`newResult` 按定义为假。真实复现是
「后端 4 轮、页面 3 行,等过一次空闲轮询仍是 3 行,切走再回来才 4 行」。

**坏历史文件把整条同步卡死。** 历史文件里一个非 UTF-8 字节,解码异常就从
`_save_history()` 逃出来:阶段卡片和日志已经写着「管道结束」,而标题是「同步正在启动」、
按钮禁用,新同步和失败重试一概被拒,点停止也救不回来(线程早退了)。普通同步和失败重试
共用这段收尾,两条入口一起死;等这一轮结果的人(`daily_run` 那条)也一直等不到。重启能
解开内存里那个状态,但坏文件还在,下一轮又来一遍 —— **重启不是根治**。

**一次读失败换来长期过期。** 那一轮唯一的一次历史补刷恰好失败(503),顶上已经是新那
一轮,底部列表却长期少它,等自动轮询也不补,页面上一个字都不说,切走再回来才补齐。
待处理数那条 `catch` 是同一个形状,后果是面板上那个数字一直停在处理前。

**最新那一轮的失败显示成上一轮的成功。** 最近状态写失败(权限、满盘)那一轮,磁盘副本
落后整整一轮,而展示和重试都直读它:界面同时出现「上一轮的结果没能留档」和「同步已
完成」,阶段卡片写着上一轮的「已保存 3 条」,日志却写着这一轮的「HTTP 503 翻译失败」。
方向反过来就是显示着上一轮的失败、而「重试失败项」**去抓上一轮那条订阅** —— 实测里
重试的导出收到 `accounts=['订阅 A']`,而导致这个计划的失败发生在订阅 B。

**重试的范围和计划来自两轮。** 计划和范围各读一次「最近一次」,两次之间另一个窗口或
调度器恰好跑完一轮:锁内只看 `running`,于是允许起跑 —— 计划 `export → index → extract`
来自 B 的失败,实际导出范围却是 A 的来源。

**旧的待处理数被盖成最新。** 全新页面、快照还是 null 时发出的 pending 查询,回包带的是
上一轮的身份和数字(`extract=1`);它迟到落地时新一轮已经把它清成 0。原来空身份一律放行、
再拿当前快照盖章,于是那个 1 被应用上去**还被标成「已追平最新那一轮」**:缺口不存在、
提示不出现、补读也不会发生,面板永久写着「还有 1 项内容待提取」,切走再回来才归零。

**一秒两千次扫库。** 上面那一条的修法是「应用的凭据必须是回包自己的身份」,而新进程和
从没跑过的新库里那个身份是空的:回包既不应用、也不清欠账,循环立刻发下一次查询。实测
全新服务 1.3 秒里发出 2044 次待处理数查询(重启的那个 2033 次),每一次都去扫一遍库,而
页面上那个数**始终是空的**;新鲜度那边同时报 `applied === desired === ''`,所以一句提示
都没有 —— 两处都把空串当成了「已经追平」。

**一轮跑得久,补读预算就没了。** 跑着的时候没有终态可追平(目标是空串),而两块附属结果
都算落后、每次状态轮询各扣一次额度。实测一轮跑 29 秒,两块的 `tries` 都到了上限 5,其中
待处理数那块**一次请求都没发出去**(运行中那个加载器直接返回);跑完之后目标前移,额度
却已经满了:再空闲轮询 13 秒,`pending.extract` 仍是 1、历史里仍缺这一轮,面板写着
「已停止自动重试」,点一次「重新读取」才回来。

**没有身份的旧快照绕过了并发核对。** 升级前落的那份记录没有 `run_id`,「两边都有身份才
比」这道核对于是整条跳过:实测拿一份去掉身份的快照、期间另一轮 B 成功结束,
`start_retry_failed()` 照旧返回 `(True, 'export → index → extract')`,导出收到的范围是
`accounts=['A']` —— 抓的是跟当前失败无关的那个来源。

**重启之后退回上一轮。** 状态文件和历史是分别写的,所以写失败那一轮之后磁盘上两份
各记着不同的轮次。恢复只读状态文件,于是**旧那一份被当成「最新」固化下来**:实测上
一轮成功、这一轮翻译 503(状态文件写失败、历史写成功),重启之后页头写着「同步已完
成」,而历史第一条就是那个失败;反过来摆(上一轮失败、这一轮成功)点「重试失败项」,
导出阶段实际收到的是**上一轮那个来源**(`accounts=['A']`)。

**一次读失败,重试就永久被拒。** 恢复的旗标在真正读之前就置位,而「读不出来」和
「确定没有」都返回 `None` —— 一次瞬时读失败(权限、磁盘抖动)于是被固化成「这个库从
没跑过」。展示那条路照旧从磁盘读得到真实那一轮,起跑核对却拿空内存去跟它比:实测
重启后打开同步中心,页面正常显示 503 和重试按钮,连点两次都是 409「这期间又跑完了
一轮，请重新点一次」,而其实什么都没跑过。

**同一秒跑完的两轮,磁盘上分不出先后。** 一次「重试失败项」紧跟一次同步,两份落盘各写
失败一次,于是它们记着不同轮次 —— 而两个 `finished_at` 实测都是 `2026-10-14 16:08:29`。
「比收尾时间」这一档在这里什么也证明不了,而它原来的败法是**默许状态文件那一份**:恢复
之后面板显示的是上一轮的结论,「重试失败项」照旧可点,按下去抓的是上一轮那个来源。

**历史首条是个空对象,后面那些记录就整段看不见了。** 候选只过滤非字典的话,`{}` 会被当
成「最新」拿去比一轮 —— 它既没有序号也没有收尾时间,三档判据一条都走不通,于是恢复退回
状态文件那一份。坏的只有一行,被遮掉的是整段仍然可信的凭据。

**同一秒跑完的两轮在面板上点不开第二行。** 选择键和新鲜度版本共用一个字段时,升级前落的
那两条记录(没有身份)都降级到收尾时间,而它们同一秒 —— 两行的 `data-run` 完全相同,点
较早那一行,`find` 只找得到第一条,**打开的是较新那一轮**。实测两行的键都是
`2026-10-14 21:04:00`,点第二行打开的是 `started_at: 21:00:00`(第一行那一轮)。

**发号失证之后,「谁更晚」的证明反过来指向旧那一轮。** 这是上面同秒那条的下一层:
给了序号,可序号自己也是读磁盘算出来的。磁盘上已经三轮、号发到 3,第四轮发号那次读
失证 —— 老代码从 1 重新开始,于是这一轮带着 1 号落进历史首条,而状态文件(没写上的
那一份)还记着 3 号那一轮。恢复按序号比:3 > 1,旧那一轮被当成最新固化下来,欠账
报的是空(「两份对得上、凭据证明了谁更新」)。页头显示它的 503、按钮可点,点下去导出
阶段收到的是它那个来源。

**一次读失败,整段历史被替换掉。** 追加前读存量走的是展示那份宽口径(读不出来就空
列表),读完立刻整份原子替换 —— 于是「这一次没读到」变成「存量里本来就没有」。库里
三轮(其中一轮带着失败原因和日志),第四轮成功、只在那一次读上注入一个
`PermissionError`:历史当场从 3 条变 1 条。两份**都写成功了**,所以诊断是空串,接口
回包里 `error` 为空、版本还是最新的 —— 面板和新鲜度检查都察觉不到存量已经没了。

**形状不对被当成「这份副本没有」。** `{"runs": 3}` 这种可解析但形状不对的内容,在
恢复那一步会让历史整份消失(于是静默认可状态文件那一份,而它可能是旧的),在追加那
一步和读失败走同一条路(空集合 → 整份替换)。

**时钟往回跳过一次,旧那一轮就成了「最新」。** 这是「两份各记一轮」那一族的最后一
档:位置证据不存在(旧那一轮的历史没写上)、序号也没有(发号那次读失证),原来退到比
收尾时间 —— 而时钟回拨之后后跑完的那一轮时间更早。判据于是反过来指向旧那一轮,
**欠账还报的是空**(「凭据证明了谁更新」)。页头显示它的 503、重试可点,点下去导出阶段
收到的是它那个来源;而历史里唯一那一行写着另一轮已完成。手动改时间、NTP 校正、夏令时
都会让这件事发生,不需要谁故意构造。

**存量里那些回退号,按数值信就会信错。** 老代码在发号读失证时从 1 重新开始,那些号
已经落在盘上了 —— 状态文件 7 号、历史首条 2 号,而历史里没有状态那一轮(位置证据不
成立)。单看数值判出「7 号更新」,它其实是旧的。两轮又恰好同一秒时,拿时间去反驳也
反驳不了。

**历史首部一个 `{}`,面板上就多出一轮「成功」。** 它**不抛** —— 字段取不到就是空,
于是渲染成「时间未知 · 同步 · 未记录来源 · 已完成」。而恢复那边早就拒绝这种记录
(`valid_round`),同一个问题在两处给出两个答案。版本那头跟着错:清单版本取首行算出
`none`、状态端点报真实那一轮,两边永远对不上 —— 面板一直提示「历史还没追平」、补读
一直在跑,点「重新读取」也不消失。

**两条旧记录的展示版本撞上,旧那一轮就成了「同一轮」。** 这是「两份各记一轮」那一
族里**最靠前**的一道:版本相等就直接返回状态文件那一份、报空欠账,位置和序号连被问到
的机会都没有。而那个版本保证非空、不保证唯一 —— 身份没有时它降级到**秒级**收尾时间。
实测两轮都是 19:30:00、都没有身份(升级前的格式,不是坏文件):状态文件记着 A 的翻译
失败和 A 的重试范围,历史唯一那行是后来 B 的成功 —— 重启后页头显示 A 的 503、重试可
点,而且**连「历史还是上一轮」那句提示都没有**,点下去导出阶段收到的是 `accounts:
['A-failed']`。旧格式那些 `run-1` / `run-2` 同理:它们只有进程内自增,重启之后会重复,
按身份信就判出「同一轮」。

**同一个捷径还让位置锚点和起跑核对失真。** 位置锚点拿版本在历史后续行里找状态那一
轮,找到的可能是版本撞上的**另一轮** —— 「首条更新」这个结论建在假锚点上;起跑核对
比版本的话,期间又跑完一轮而两轮版本相同时整条放行,派生出来的计划和范围全是上一轮的。

**身份分出来了,内容那一级又把它判回同一轮。** 把展示版本和事件身份分开之后,证明
剩两级 —— 可两级要是「先试身份、再试内容」,身份**明确不同**那一局就落到内容兜底手里:
而内容比的字段里没有 `export_filter` / `crawl_retry`,于是「看起来一模一样」的两轮,
该抓的来源完全不同。实测两次快速重试都收尾在 21:04:00,阶段、抓取范围、日志逐字相同,
身份是 `run-6acf76695d2e-1` / `-2`、序号 1 / 2、世代都在:`same_round` 返回真,
`/api/pipeline/retry-failed` 返回 200(该是 409),重试线程实收 `accounts: ['A订阅']`
—— 而最新那一轮要抓的是 B订阅。恢复那边同样:`_newest_round([B], A)` 返回 A、欠账为空,
页头显示上一轮、按钮可点、连一句提示都没有。

**「这一份读不出来」被当成了「这一轮没发生」。** 上一条把坏形状挡在门外之后,挡的
方式是把整条记录从候选里过滤掉 —— 而候选那一步要回答的是「哪一轮最新」,它只需要身份、
序号和位置,全都不在坏掉的正文里。于是最新那一轮连带它的全部顺序凭据一起消失,剩下的
旧那一份成了「最新而且完整」:实测 B 轮(成功、范围是 B订阅)只有 `log` 落成字符串,
身份、当前世代、递增的 `run_seq` 全在,恢复返回 A 轮(翻译失败、范围是 A订阅)、欠账
报空 —— 页头显示 A 的 503、「重试失败项」可点,历史那边只说「有一轮记录读不出来,
已跳过」,**没有一句话提示顶部那一屏不是最新的**;点下去导出阶段收到
`accounts: ['A订阅']`。方向比上一条更坏:原来是显性炸屏(一眼看得见),现在是静默抓错
来源。**两份都坏那一档更远一步**:一份都挑不出来被固化成「确定从没跑过」,面板报
「尚无运行记录」而按钮照旧可点。

**那一轮跑完了,而磁盘上一个字都没留下。** 两份终态都在收尾时写,都失败那一档新身份、
完成序号、终态和那笔留档诊断全在内存里,重启把内存清空 —— 于是剩下的两份旧副本彼此一致,
`same_event` 正确地证明「它们是同一次事件」,而**那句话被当成了「没有更新的一轮」**:实测
B 轮(成功、范围是 B订阅)两份写入都报满盘,重启后页头又显示 A 的 503、空欠账、**没有任何
过期提示**,点「重试失败项」导出阶段收到 `accounts: ['A订阅']`。进程在跑完之后、收尾之前
被杀掉是同一档。这一档**推断不出来**:两份都是 A、完全一致,没有任何痕迹能指向 B。只能
在开工之前就落一笔。

**一处渲染问题否决了一份完整的事件证据。** 上一条把「发生过没有」和「渲染得了没有」分开
之后,前者的判据里还留着时间字段的类型检查 —— 而时间是显示字段:实测 B 轮的 `started_at`
被改成数字,身份、当前世代、完成序号 2 和成功阶段全在,整条却被当成「没发生过」过滤掉,
恢复返回 A 轮、报空欠账,页面上重试又抓了 A订阅。**换个显示字段还是同一出戏**,所以判据
从根上改成「拿得出事件元数据就算发生过」。

**边界那一笔自己也会失败,而失败被解释成「没有需要核对的新运行」。** 上一条让开工之前
先落一笔,可那一笔是 best-effort:写不上照旧起跑、读不出来当成不存在,两头都通向同一个
结局。实测两局:①A 轮翻译 503 正常留档,B 轮成功、开工标记和两份终态都注入满盘 ——
B 照旧起线程、真跑完了导出,重启后页头是 A 的 503、空欠账、没有过期提示,点「重试失败项」
导出阶段收到 `accounts: ['A订阅']`;②标记正常写上了、只有两份终态写失败(标记指着 B),
重启时只对**第一次**读标记注入 `PermissionError`(文件一个字节没动、另两份全可读)——
宽口径把异常吞成空值、失证判据返回假,恢复 A、报空欠账、真点一次重试又抓了 A订阅,而且
解除注入之后**不再核对**(恢复已经固化)。反向证据在同一局里:另起一个进程读同一份文件、
不注入错误,正确地报出 `lost` —— 检测能力一直在,被一次读失败吞掉了。

**内容相等被当成了事件唯一的证明。** 旧格式下两边都没有可信身份,于是「两份副本内容
逐字相同」成了唯一的那一级 —— 可它比的字段里没有导出范围和失败名单(给人翻的那份副本
本来就不写),所以两次**不同的**重试落在同一秒、步骤和日志相同时也判成同一轮:实测
A 的范围是 A订阅、B 的范围是 B订阅,状态文件留着 A、历史只留 B 的显示副本 ——
`same_round(A,B)` 为真、`_newest_round([B],A)` 选 A 报空欠账,重试端点返回 200、线程
收到 A订阅。拿「升级前最后一轮会被误拦一次」去换这个,换错了方向。

**坏形状不是只坏那一行,是坏整屏。** 时间验住之后,`log` 落成字符串、`stages` 里混进
`null` 这两种形状照旧算「有效终态」:恢复把它读进内存,日志那一屏 `lines.join()` 当场
抛、`pipeRunLabel` 的 `st.status` 当场抛 —— 异常冒到状态渲染那层,**整屏**变成「状态
暂时无法更新」。空 `stages` 不抛却更坏:数不出红也数不出跳过,汇总成「已完成」。历史行
那道 try/catch 只保护它自己那一行,**保护不了它被打开之后的整屏**。还有一条绕路:恢复
拒掉之后,`_latest_locked` 回落读的是宽口径的 `load_last_run()` —— 不补判据的话那份
记录从这里原样进来,照旧交给整屏渲染和重试派生。

## 实测证据

- 真实的 `data/pipeline_state.json` 是 6.2 KB(含 80 行日志),一轮不含日志约 1.5 KB。
- 内存里的 `_finished` 本来就留了最近几轮,但**只存 `stages` 四个字段、不落盘、且只能按
  run id 精确查** —— 它服务的是「日报等自己那一轮的结果」那个窄窗口,给不了「翻一翻上午
  那一轮」。
- 探针实测:点重试那一下弹出的 toast(`#toast-host` 是 fixed、浮在页面底部)**正好压住
  历史列表**。`getBoundingClientRect()` 照旧给一个有宽高、在视口里的矩形,于是「点了但
  什么也没发生」会静默绿着 —— 所以 `clickAt` 里加了 `elementFromPoint` 命中测试,并且
  清 toast 要**等它真的弹出来**(`retryFailed()` 是异步的,点完立刻清是清在回包之前)。
- 同一个探针还实测出:历史列表在整页底部(日志框自己就 440px 高),不先
  `scrollIntoView` 的话算出来的 y 落在视口下方,`dispatchMouseEvent` 点出去谁也没点到。
- 实测过的坏法有三种,抛的异常各不相同:非 UTF-8 字节 → `UnicodeDecodeError`、
  2000 层嵌套 JSON → `RecursionError`、旧记录里转义的孤立代理字符 → 写那一步的
  `UnicodeEncodeError`。**反例也记着**:普通坏 JSON、权限错误、磁盘满(`OSError` 那
  一类)原本就被隔离住了,核心同步照旧收尾 —— 问题不在「坏文件」,在**收尾依赖
  「异常恰好属于已捕获类型」这个不可靠判据**。
- 「非 UTF-8 字节」那一档按 `errors='replace'` 读之后**还能读出那一条记录**(坏的只是
  那一个字符),比整份当读不出来扔掉强。
- **生产里那次首次状态读取发生在页面加载时,不是点开同步中心时**:`initWorkspace` 收尾
  处本来就有一次 `refreshPipe()`(「别的 tab 或调度器起的活,在图鉴页也要发现」),而
  `refreshPipe` 在途时**复用同一个 promise** —— 点「同步中心」只会发历史那一条,不会再
  发一次状态查询。摆首次加载那一局时这一点是决定性的:按住状态回包必须设在**导航之前**,
  设在点击之前的话按住的是下一次轮询,而那时快照早就有了(实测 `pipeDoneRun` 已经是上
  一轮的身份),整局就不再是「全新页面」。
- **自然时钟下同秒是常态,不用构造**:上面那两个 `16:08:29` 是真跑出来的,`_now()` 只到
  秒而一轮同步的收尾动作远快于一秒。
- **`_newest_round` 最后那个 `return` 一度漏了第二个元素**(写成 `return saved,` —— 单
  元素元组),而它**从没被任何用例走到过**:那一档正是「两份各记一轮、序号又分不出」,
  当时没有用例摆得出这一局。补上之后定点注入(去掉那个 `''`)只红一条,是它独占的。
- **非 UTF-8 字节在严格读取下也读得出来**:`_load_json_strict` 和宽口径那份一样先按
  字节读、再 `errors='replace'` 解码,所以 `{"runs": [{"run_id": "\xff\xfe"}]}` 解出
  来是合法 JSON、形状也对。四种坏法实测分成两边:非 UTF-8 和孤立代理读得出来(照旧
  追加),深嵌套 JSON 抛 `RecursionError`、`{"runs": 3}` 形状不对(都抛,原文件不动)。
- **完成序号的进程内高水位和「恢复时复制 `run_seq`」都是冗余带**,定点去掉**红 0 条**
  —— 想清楚了是真冗余不是用例不敏感:发号读的是磁盘不是内存,而读成功时磁盘上最新那
  一轮的号就是本进程上一轮发的(它写成功了),所以 +1 天然单调。留着是因为它兜的那一
  档(磁盘上的最大值比本进程发过的还小)将来可能真出现:截断只留最近几轮、或者有谁
  写个清理脚本把老记录删掉。
- **时间档删掉之后要反过来钉一边**:同一代的号在手上时,时钟回拨不许动摇它(号更大
  的那一轮就是更晚,哪怕它的收尾时间更早)。只钉「没凭据时不许拿时间凑」的话,把
  序号那一档也改成「和时间矛盾就报 order」同样全绿 —— 而那是错的:号才是对的那个。
- **给存量摆的那些记录要补 `seq_gen` 才保持射程。** 手工摆的记录没有世代标识时
  `_seq_of` 一律返回 0,序号那一档压根走不通 —— 于是「位置排在序号前面」那一条变成
  红 0 条(位置证据自己就足够了)。要钉它就得让两边的号**都带出处**。
- **「内容逐字相同」那一级不只给旧格式兜底,也接住「摆局刻意同源」那一类用例**:
  定点去掉它会带红十几条既有重试用例 —— 它们 patch 两边返回同一个手工快照(注释里
  写明了摆局该同源),而那份快照没有世代标识,事件身份是空的。
- **起跑核对那一处要单独摆一局才钉得住**:现有「期间又跑完一轮」那条用的是当前格式
  (身份变了,比展示版本也判得出来),所以把它改回比版本**红 0 条**。要钉它得摆两轮
  都没身份、收尾时间又相同 —— 版本撞上,而内容不同。
- **「两级互斥」要往两个方向各钉一次。** 把身份那一级短路掉,红的是三个消费者(恢复
  捷径、位置锚点、起跑核对)外加「身份相等就算同一轮」那条反向钉边;反过来给身份那一级
  加上「内容也得相同」,红的只有那条反向钉边 —— 两个方向分别对应漏报和误报。
  **放松成「两边都有身份时才看身份」只红一新一旧那一局**,所以严到「任一边拿得出身份
  就只看身份」这一步有它自己的射程,不是顺手写严的。
- **出处那两笔各钉一段**:恢复不覆盖世代标识 → 红在「旧记录拿不出事件身份」那一段
  (实收 `run-1`);收尾不署名 → 红在「再跑一轮之后出处回到当前世代」那一段。两笔是
  一对:只做前者,恢复过一次之后内存那份终态永久失证。
- **失证那一档的判据要往两个方向各试一次。** 写成「标记还在就报失证」带红六条既有
  用例(只有一份写失败、以及先后分不出来的那几局都被多报一档);写成「标记不是挑中的那
  一轮」只红一条,但那一条恰好说明同一件事。正确的判据是「标记那一轮**在两份落盘里一份
  都找不到**」,而它的反向钉边(标记没清但那一轮确实在历史里 → 仍报 `scope`)要单独摆。
- **两个起跑入口各有自己的红。** 失证那条用例走的是摆盘里的「跑一轮」,而摆盘绕过了
  起跑那一段 —— 所以它对「普通同步那条路不落标记」压根不敏感(定点注入红 0 条)。要钉住
  就得各摆一条真走起跑入口的用例(拦住线程、只看标记落没落),两条分别只红自己那一处。
  **摆盘也要跟着落标记**:不落的话每个走到收尾的用例都在一个「从来没有标记」的世界里,
  而生产里永远有。
- **边界那两头各自独占一条红。** 写闸关掉只红「写不上不许起跑」那两条(普通同步那条
  连带把 409 那句话的用例一起带红 —— 同一条起跑路);读那头把异常档改成空值,红的是
  「读不出来不算没有」「坏根不算没有」「不许固化」三条,其中坏根那条是因为内容是 `null`
  的那一份走的正是异常路(`_load_json_strict` 解出 `None` 时抛)。把 `unknown` 改成固化
  只红「不许固化」那一条。
- **`Path.exists()` 那一笔要单独摆才有红。** 换回 `exists()` 之后,注入读失败那几条照旧
  绿着 —— 它们注入的是 `read_bytes`,而那一步在两种写法里都抛。要钉住就得摆「文件在、
  而 `exists()` 一律说不在」这一局(它正是权限/路径故障下 `exists()` 的真实行为),判据
  落在「那一份标记照旧读得到、报得出 `lost`」上。
- **叶子那一层的两个落点各有一笔注入。** 范围那一级(来源名、订阅名的元素)和失败名单
  那本账里的 `targets` 元素是两处独立的判据,放松任一处都红在同一条用例上 —— 那条用例
  一次摆九种坏法 + 一行正常记录,断言是**逐行的有效/无效清单**,所以红起来看得出翻的是
  哪一行。
- **「发生过没有」和「渲染得了没有」各有自己的红。** 把候选过滤换回按可渲染性,红的
  是「坏的最新轮照旧算最新」和「两份都坏不等于没跑过」两条;只把「一份都挑不出来」
  那一档的欠账吞掉,只红后面那一条。欠账闸不提前同样只红后面那一条 —— 红在它第三个
  断言上(拒绝理由说的是「上次运行没有失败项」而不是「留档损坏」)。
- **新档位要在面板上单独钉一次**:后端那几档欠账共用一句模板,`PIPE_RESTORE_GAP` 漏
  掉键时回落到笼统的「恢复得不完整」—— 后端全绿、页面上那句话却没说明白。页面探针
  里摆这一档时**先确认那颗按钮本来可点**(不在翻历史、没有别的欠账),否则「按不下去」
  这条断言不独占。
- **恢复捷径换成只认身份之后,原来那条「内容相同就算同一轮」的用例连同结论一起翻过
  来**:它现在钉的是「照旧展示它、但不许据此放行重试」。判据翻转要在用例自己的
  docstring 里写明理由,不然下一轮读到会以为是退化。
- **回落那一处有独立的红**:只收紧 `valid_round` 不补回落判据时,「渲染不了的记录不算
  最新那一轮」单独红一条 —— 恢复拒了它,它还能从 `load_last_run()` 原路回来。

## 回归

**身份那一条非得真起两个进程不可**:`_run_seq` 归零**模拟不了重启**(真重启会连
`_RUN_EPOCH` 一起重新生成),而手工给两轮不同的身份恰恰把要验的那件事假设掉了。两个子
进程共享一个 `KB_DATA_DIR`,各走生产那条启动路径(`start_pipeline` 发身份、起线程、
`_end_run` 落盘),判据落在**「第一轮那个红还在不在历史里」**上 —— 身份撞不撞是机制,
断言排在后面。


`tests/test_pipeline_history.py` 的后端那一族钉的是:**下一轮跑完之后,上一轮那个红还
查不查得到**(含它的失败明细和它自己那一轮的日志),以及被停的那一轮如实写着 stopped、
幂等、空身份不合并、坏文件降级成空列表。**反过来钉一边**:承重的那份
`load_last_run()` 一个字段都没少、重试名单照旧派生得出来。隔离那一条顺带由整族共用的
摆盘钉着(只 patch `_STATE_FILE`)。

`tests/test_pipeline_select.py` 问的是**两份独立可失败的状态之间能不能互相冒充**:正常
那一档最新那一轮标得出来(**反过来钉一边** —— 判据写成「一律不标」能让别的几条全绿,而
那样面板上「最新」那一枚就永远不出现)、留档失败那一档一行都不标、旧格式没有可信身份也
不标。页面那一侧由 `tests/pipe_latest_probe.mjs` 实点:它摆四局(正常、留档失败、**后端
标错了**、**这一行已经在 DOM 里而状态往前走了**),三道守卫各有自己的红 —— 定点注入「按
位置认最新」红 5 条(其中一条正是实点出来那个形态:点上午那个红,`detail` 是「第三轮又是
503」、`readonly: false`),只去掉前端那道版本对照红 1 条,签名里只记「跑没跑」红 1 条
(列表不重渲染,旧那一行还挂着「最新」),`pickPipeRun` 不再核验红 3 条。
**判据一律落在后果上,不落在 `onclick` 那串文本上** —— 原来按 `/exitPipeHistory/` 去匹配
属性文本,动作换个函数名就会红,而「点上午那个红到底打开了哪一轮」才是要钉的事;现在是
点下去再读 `#pipe-viewing` / `#pipe-stage-export`。那一局还把**点击那一刻那道冗余带**单独
钉了一条:不经过重渲染直接调 `pickPipeRun`(页面上到不了这一步 —— 状态一更新就会重渲染),
缺了它「列表没能重渲染」那一档就只剩一道守卫。

`tests/test_pipeline_retention.py` 接着问**留多久**(分出来只为行数,两边共用同一个
`HistoryCase`;摆局手法不同 —— 这一族要往文件里放几天前那几轮,而 `run_round` 一律按此刻
落时间,所以它自带 `_seed`/`_ago`)。**三道口径各留一份红,不许合在一条用例里验** ——
窗口写错了会被下限兜绿,反过来也一样:验窗口的两条把 `persist._HISTORY_FLOOR` 让开,验
下限的那条用一个**只拨快 `now()`** 的钟(不整份换掉 `datetime`,`strptime` 还要照常解析
记录里那些时刻)把窗口逼到全都过期。面板那一条的判据落在**回包**上,不是落在「两个名字
相等」上 —— 后者是重导出的同义反复,端点里写死一个 7 它照样全绿(实测:改成相等断言时
那次注入不红)。

**窗口之内那条按真实数量摆**(401 轮全落在 66 小时内,再跑一轮):这正是第 1 轮审查判红
的那个形态,按条数封顶的任何一版都在这里红。体量那两条分别钉「记录还在」和「削掉的是重
物不是结论」—— 少哪一条另一条的红都会没人接:把 `shed_bulk` 改回「删记录」红的是前者,
把补 `failures_total` 那一句删掉红的是后者。

**成本那一条的判据是累计编码的字节数,不是墙上时间。** 用例规模(60 轮带满明细)下两种
实现都在一秒内跑完,时间分不开;字节差两个数量级 —— 实测注入「每削一条重编整份」那一版
累计 110 MB,而输入才 2.2 MB(线性那版约 3 倍输入,所以判据写成「小于 4 倍输入」,同样是
数量级口径)。**坏行那一条的判据落在后果上**:诊断是空的、新那一轮查得到、谁也没被删、
那条坏行自己还留着;定点去掉 `stages` 那道类型守卫,它红在 `persist_error()` 上
(`AttributeError`),而别的九条全绿 —— 那正是事故的形状:整份历史没写进去,面板只说一句
留档失败。

在途补刷有三档,各有自己的一组,**少哪一组都会让另一组的红没人接**:

1. **身份变了**(已有快照,旧回包迟到、期间又跑完一轮)——靠身份校验或欠账补上。
2. **在途期间又来一次调用**(手工清掉快照、手工补调一次)——这一组**摆的是机制,不代表
   生产的首次加载**,它验的只是「那一笔欠账保不保得住」。摆局**必须先把列表清空并渲染
   一次**:上一组收尾时它正好是三行,不清的话「追平成三轮」在摆局那一刻就已经为真,这
   一项会静默绿着。
3. **真实的首次加载**(整局只有一个真实动作:点「同步中心」)——**不给页面变量赋值、
   不手工补调 `loadPipeHistory()`**。手工补一次调用就把要验的那件事验没了:生产那条路
   上第二次调用从哪来,正是这一档的全部内容。两种回包顺序各一组(状态先到 / 历史先到),
   初始值如实记一笔(`snapshot: null`、`doneRun: null`、`wanted: false`),并钉住「历史
   那一条是点开那一下发出来的」—— 地址栏残留的 `#pipe` 会让页面自己打开同步中心,那样
   起点就不干净了。
   **反过来钉一边**:状态没变时后续轮询不许每次都重复查一次历史。

`tests/test_pipeline_boundary.py` 单独一族,钉的是**起跑的前提成立不成立**(`restore`
那边钉的是「恢复本身做对了没有」)。写那一头和读那一头各一组:写那头验「不起线程、运行
状态一个字没改、那一句 409 说的是真话」,并**反过来钉一边** —— 目录写得进去时两条起跑路
照旧起跑、标记带着自己的身份和出处(这两条按入口分开写,合成一条的话红起来指不出是哪条
起跑路漏了标记)。读那头的四档各一条(读不出来 / 坏根 / `exists()` 说谎 / 确证不在),加
一条「瞬时读失败之后还能核对出来」——它同时是前一条的反向证据(同一份文件、解除注入之后
报得出 `lost`,说明不是摆局漏写了文件)。
**这一族里不许 patch `threading.Thread`**:`pipeline.threading` 就是标准库那个模块对象,
patch 它等于把整个进程的 `Thread` 换掉,而 `TestClient` 自己要起线程 —— 走 HTTP 那一条
会整条挂住不返回。闸在起线程之前就拦下了,本来也没有线程可拦,判据改成直接看运行状态。

留档失败那一族(`PersistFailureTests`)按两道分开钉,**不要只写端到端那一条**:
走 `_end_run` 的坏文件用例在两道都在时绿、单道去掉也绿,钉不住任何一道。所以第一道
(留档层隔离)**直接调 `load_history()` / `_save_history()`**、不经过 `_end_run`;第二道
(收尾不变量)**注入一个谁都没列进捕获的异常类型**,判据落在「running 放下来了没有、
等结果的人拿不拿得到终态、下一轮起不起得来」上。另外两条各自独占:坏字节不许让整份
丢掉、替换失败不许留下临时文件。**反过来钉一边**:留档又成功时那条诊断要撤掉。

新鲜度那三组(页面侧)摆的是「那一轮唯一的一次补刷失败」:缺口留住没有、补没补回来、
靠的是不是退避补读、面板上说没说。**待处理数那一组必须真有一轮新结果** —— 「缺口」的
定义是 desired 已经前移而 applied 还落在旧那一轮上,在「已经追平」的状态下让它失败不是
缺口(屏幕上的数就是这一轮的),那样摆会在摆局那一步就不成立。**反过来钉一边**:后端
留档失败那条诊断出现时,阶段卡片照旧显示后端那一轮的真实结论。

定点注入分得开这三档:只去掉历史那边的空身份短路,只有「历史先到」那一组红;把欠账
改成清在接受回包之后,第 2 档和「状态先到」红。

可信终态那一族(`LatestResultTests`,在 `test_pipeline_restore.py`)五道注入各有
**独占**的红:`last_result()` 退回只读
磁盘、两份留档串回一个 `try`、`retry_failed_plan` 忽略传进来的快照、去掉锁内身份校验、
身份校验少了那两道「拿不准就放行」的守卫(最后这一道红在**反向**那条:重启之后照旧要
能重试)。

applied 凭据那两组:pending 侧摆的是「全新页面、快照还是 null 时发出的查询,回包迟到」
—— 退回被审版(无条件应用 + 当前快照盖章)后红在「旧那份待处理数不许被应用上去」,诊断
输出就是 `{pending:{extract:1}, applied===desired}` 那个误判形态。history 侧摆的是
「清单落后于当前这一轮、而后端没报错」—— 那边没有「对不上就不应用」的条件,盖章是唯一
凭据,所以这一组对它敏感;**pending 侧只换盖章红 0 项**(条件已经保证两个表达式同值,
真冗余),如实记着。

**改了既有用例的摆盘要重新验它还敏感。** `test_the_crawl_card_explains_an_empty_retry_round`
原来靠「直接改磁盘文件」摆局,而磁盘不再是权威之后那一局在摆局那一步就不成立,改成摆
内存那一份 —— 改完定点注入过一次,红的仍是「卡片没说明原因」。
**换符号也要连 patch 目标一起换**:`pipeline_retry` 从 `load_last_run` 改用 `last_result`
之后,五个既有测试文件里 patch 旧名字的那六处会**静默失效**(patch 的东西不再被调用,
测试照旧绿、但不再隔离)。

版本口径那一族(`RestoreTests` + 端点那条)九道注入各有**独占**的红:恢复失效(红在
「重启之后读得回来」和反向那条「重启之后照旧要能重试」)、版本只认身份(红在「没有身份
的快照也有版本」和「两个端点报同一个版本」)、起跑核对退回「两边都有身份才比」(红在
「旧格式快照不许绕过核对」)。前端那五道:版本改回前端自己拼(两个探针各有红,history
那边的诊断输出就是 `applied=收尾时间 vs desired=起跑时间` 那个永久缺口)、运行中也扣
预算、目标换了不重置、次数回到调度那一步扣、历史凭据回到「清单首条的 run_id」、去掉
逐行隔离。

**预算那两道在端到端那一局里互相掩护**:跑着期间目标一直是空串,「目标换了重新给」压根
不触发,所以那一局只对「运行中不扣」敏感;反过来「目标换了重新给」只在**目标非空时就
把额度耗光**那个局里才看得出来,而那要等上百秒的退避才攒得出来 —— 所以它和另外两道细
节(调度步不扣、回报时扣)一起放在手工摆槽位的机制单测里,**射程只到那一层的判据**,它
们在真页面上确实生效由端到端那两组管。

**忙循环那一项的基线必须取在导航之前**:页面加载时 `initWorkspace` 收尾那次状态读取就
会引发一次待处理数查询,基线取在它之后的话忙循环已经发生完了,这一项什么也拦不住(第一
版就是这样,实测 0 次重查)。**`spins` 上限和「对不齐就返回」是冗余带** —— 版本恒非空之
后那个忙循环本来就不成立,单独去掉其中一道都抓不住,如实记着。

**坏记录那一组不走摆局断言**:整表被一条坏记录带走正是本组要抓的后果,落成「摆局没成」
会把后面两条检查一起带走(第一版就是这样,只红了一条「摆局没成」),改成两条独立判据
之后两条都红。

**patch 出来的手工快照要带着身份,或者把 `_state` 的身份一起清掉。** 起跑核对无条件做
之后,`test_pipeline_stop` / `test_refill_script` 里那几处 `patch.object(..., 'last_result',
return_value={...})` 的子用例在第二轮起会被认成「这期间又跑完了一轮」—— 那道核对是对的,
是摆局该干净(每个子用例是独立的一轮)。

恢复那一族(`test_pipeline_restore.py`,和可信终态同一份文件 —— 两者都在回答「拿哪
一份当最新」)六道注入各有**独占**的红:恢复只读状态文件、新旧判据退回「只比收尾时
间」(红在两轮同秒那两条)、去掉那道 gap 闸、旗标在读之前置位、严口径退回宽口径、起
跑核对直读 `_state`。**反过来钉一边**:状态文件就是最新那一轮时恢复要完整、重试照旧
能起;历史那份写失败(方向相反)时要认状态文件那一份,**而且那一局两轮落在同一秒** ——
不摆同秒的话「按历史位置判」和「按时间判」都是绿的,那一道就没人接。

**瞬时读失败那一条的注入要打在真实的那次 IO 上**(`Path.read_bytes`),不是打在
`_load_json_strict` 上 —— 打在它身上的话「读不出来一律抛」那一道被 patch 盖掉,用例
对它不再敏感(真这么写过,红 0 条)。打在 IO 上顺带也钉住了宽口径那一份照旧吞异常。

**`_newest_round` 最后那条「历史首条不比状态文件新」的路径原来没有任何用例走到**,
于是它里面一个 `return saved,`(少了第二个返回值,解包时才炸)一直绿着。补那一局
(历史写失败 + 同秒两轮)之后它独占地红。

**选择键那一道要拆成两处各自验**:后端派生那一行由端点用例钉(探针的 mock 自己算
`version`,注入后端代码对它无效,红 0 项),前端拿它当键那三处由探针钉。

**`spins` 上限现在有独占的红了**(上一轮记的是「冗余带」):摆「回包版本稳定落后」那
一局 —— 去掉上限之后 8 秒里发出 38379 次查询、循环收不了尾。**那一局不走摆局断言**:
收不了尾正是本组要抓的后果,落成「摆局没成」会把后一条检查一起带走。

`tests/pipe_history_probe.mjs` 钉的是**页面上那几行字**:翻到上午那一轮时阶段卡片显示
它那个红和「503」、失败明细在、日志是那一轮自己的;翻历史时重试按钮藏起来且禁用、真点
一下发不出一个请求、此刻的待处理数不贴上来;轮询几轮之后还停在那一轮;回到最新、同一行
再点一次、以及那一轮被挤出记录时退回最新。**反过来钉一边**:最新视图下重试按钮照旧
能点。

`tests/pipe_layout_probe.mjs` 钉的是**几何**,不是文字:那一列和它改写的那块屏幕并排、
scrollY=0 时两边都在视口里、滚动之后它还贴着、失败明细不重复一遍、「看第一个」跳得到、
那句保留口径两种写法各一次、日志默认收着而那一轮的日志照旧在 DOM 里。**它自带一个无状态
的桩后端**(不碰真库,`keep_days` 由桩给),所以这一份能单独跑。**窄屏那一条必须量两个
宽度**:一次注入在 1100 不红、在 820 红 —— 原因是另有一条 `@media (max-width: 1180px)`
排在后面覆盖了它,1000–1180 这一段里栅格塌成单列而那一列还 sticky 着、还没换到前面,
**正是「选择器排在它要改写的内容后面」这件事自己**。

恢复那一族(`tests/test_pipeline_restore.py`)和可信终态共用 `HistoryCase` 的摆盘,但判据
完全不同:那边问「下一轮跑完之后上一轮还查不查得到」,这边问「新进程启动时拿回来的是哪
一轮、拿不准时说没说」。**三档欠账各要一组**,少哪一档那一档就没人接:

1. **`scope`**——挑中历史那一份(没有重试派生字段)。摆法是只让状态文件那次写失败。
2. **`unknown`**——有一份读不出来。**注入必须打在真实的那次 IO 上**(`Path.read_bytes`),
   打在 `_load_json_strict` 上的话「读不出来一律抛」那一道就被 patch 盖掉了,红 0 条。
   **反过来钉一边**:只是**瞬时**读失败(下一次读得通)时重试照旧放行、欠账清空 ——
   「读不通那一刻要拦」和「好了之后要放」是两条,分界是**这一刻读不读得通**。
3. **`order`**——先后证明不了。摆法是**手工写两份都没有 `run_seq`、收尾时间又相同的
   文件**,判据落在「面板显示哪一轮」「重试拒不拒、那句话说没说」上。

序号那一条反过来也要钉:**两轮真落在同一秒时它必须分得出来**(patch `_now` 返回同一个
时间串,A 的历史写失败、B 的状态写失败),判据是恢复到 B、欠账是 `scope`。去掉落盘里那个
`run_seq` 的定点注入会把这一条和「历史写失败时保住状态文件那一份」一起带红 —— 后者现在
正是靠序号证明的。

选择键那两条**分前后端各钉一次**,少哪一边都证明不了全程:端点那一条直接改文件去掉
`run_id` 和 `run_seq`、让两条同一秒,断言键逐行唯一(**反过来钉一边**:正常跑出来的那几
轮各有序号,键就是 `seq-N`);页面那一条摆同一局,断言两行 `data-run` 不同、**点第二行
打开的是第二行**。只钉端点的话前端把键换回版本也全绿(mock 自己算键,压根不走后端那
行)——那正是一次红 0 条的由来。

**页面探针里相邻两组行数相同就会互相遮蔽。** 「摆局先把列表清到已知状态」这条在在途补刷
那一族里写过一次,后来又在另外两组上复发:它们的等待判据都是「列表变成两行」,而上一组
收尾时正好也是两行,于是 `until` 在摆局那一刻就为真,判据跑在**旧 DOM** 上。它的表现很
像偶发——诊断是判据之后第二次求值,那时新清单往往已经应用上了,所以两次跑打出来的诊断
值还不一样。**等待判据只许用「只有新局才满足」的条件**:先清空并确认 0 行,或者把状态
查询那一侧的事实(desired 已前移)一起写进摆局前提。

**叶子那一层单独一条用例**,和外层、嵌套各自分开:外层摆四种(日志、`null` 阶段、空阶段、
计划),嵌套摆四种(失败名单、来源清单两种、那本账),叶子摆六种(名单里的 `null`、两处
`accounts` 落成字符串、导出范围落成字符串、`targets` / `at` 类型不对)。三条都**反过来钉
一边**,而叶子那条的好行要带**真实的失败明细**(`failures=[{...}]`)—— 用空名单的话「元素
得是字典」这一句压根没被问到。

**坏正文那一族要分三处摆,每一处问的不是同一件事**:挑最新那一步问「顺序凭据还在不
在」(坏的那一轮照旧算最新、欠账 `broken`、重试被拦);「一份都挑不出来」那一档问
「会不会被固化成从没跑过」;端点那一步问「这一行标没标 `invalid`」。嵌套坏形状和外层
坏形状**摆在各自的用例里**,因为它们证的是判据的不同层 —— 外层那条摆四种(日志、
`null` 阶段、空阶段、计划),嵌套那条摆四种(失败名单、来源清单两种、失败名单那本账),
两条都**反过来钉一边**:同一局里放一行好的,断言它照旧有效。

**「同一轮」那一族要按凭据档位摆,而不是按触发点摆** —— 每一档再分别喂三个消费者
(恢复捷径、位置锚点、起跑核对)。这一轮补的三档:两份都带身份且**身份不同、内容逐字
相同**(必须判成两轮);两份**身份相同、内容不同**(必须判成同一轮 —— 同一轮的两份本来
就不全同,状态那份带重试派生字段);**一边有出处一边没有**而内容恰好相同(必须判成两轮)。
位置锚点那一局得把**位置证据和序号档的结论摆成相反的**(首条的号比状态文件那份小)才钉
得住 —— 两档结论一致时锚点认错了也看不出来。

**坏形状那四种摆在同一局里,外加一行好的**:日志落成字符串、阶段混进 `null`、阶段为空、
计划落成字符串,断言 `invalid` 逐行是 `[真,真,真,真,假]`,并断言清单版本仍取第一个有效行
(两个端点对得上)。回落那一处**单独摆一局**:状态文件坏形状、历史空,断言「最新那一轮」
是空字典、重试被拒 —— 恢复拒了它,它还能从 `load_last_run()` 原路回来。页面探针那边
mock 的有效性判据跟着收紧(**口径只有一份**:mock 像真后端那样标 `invalid`,`rowsValid`
那个开关仍只用来摆「后端漏标」那一局)。

**探针贴到 700 行上限时,先拆再加**:起无头壳、接 CDP、求值、轮询、真鼠标点击这一段是
**页面无关**的,搬到 `pipe_history_cdp.mjs`(搬完逐符号对过原文,只去掉一处重复的 `sleep`
定义);页面特有的那几个选择器仍留在探针自己手里。`pipe_pending_probe.mjs` 里那份副本
没有跟着搬 —— 它是另一块功能的探针,两份要是同时改动才值得再往上抽一层。

顺序凭据那一族的回归**分发号层和恢复层两处,各自独占**:发号那一条直接在读上注入、
断言它发 0(而不是一个小整数);恢复那一条摆完整形态(三轮之后,发号读失证 + 状态文件
写失败),断言展示的是真正最新那一轮、欠账是 `scope`、重试被拒。**注入只许罩住发号
那一步** —— 罩住整轮的话 `_save_history` 的读也失败,那一份就按「存量没读出来」抛了,
历史里压根没有这一轮,这一局摆不出来。

**位置证据排在序号前面这一条,要用「存量里已落盘的回退号」才钉得住。** 拿「发号读
失证那一局」去钉它红 0 条:那一轮的序号是 0,序号那一档本来就走不通,判据顺序换了也
不影响结论。真正的射程是两个号**都是正整数、都非 0**而大的那个实际更旧 —— 手工摆
历史首条 1 号(真正最新)、状态文件 3 号(上一轮,还留在历史里)。

**非破坏性那一条的判据落在「文件内容一个字节都没变」上,不是「抛了没有」。** 抛出去
只是手段;存量丢没丢才是用户遇到的后果。三种摆法同一个根因(读失败 / 深嵌套 / 形状
不对),一组里一起摆。

**完成序号的进程内高水位是模块级的,测试摆盘要清掉它** —— 生产里它该跨轮累积,测试里
不清的话「磁盘上发到第几号」这个前提当场不成立(实测前提断言拿到的是 20 而不是 3)。

顺序凭据那一族单独一个文件(`tests/test_pipeline_order.py`),和恢复那一族分开:那边问
「恢复这件事做对了没有」(内存读回来了没、活进程被盖没被盖、读失败之后还能不能重试),
这边问「凭据够不够」。摆盘、模拟重启和那三种定点注入(两份落盘分别写失败、读失败)都
在 `HistoryCase` 上,三家共用。

**坏行那一条要两端各钉一次**:端点那条断言「坏行标出来了、好行没被连带标坏、清单版本
取第一个有效行、两个端点照旧对得上」;页面那条断言「没显示成已完成、就地说明、两行好
的照旧渲染得出来、没有永久落后的提示」。只钉一端都证明不了全程 —— 端点标了而前端照常
渲染,面板上还是那行假成功。**页面探针的 mock 要跟上这个契约**:它的状态端点原来从清单
首条取版本,历史里混进一行坏记录就让它也报 `none`(真后端那一条走的是内存里那份终态,
不可能是个 `{}`)。

**「渲染时抛」和「内容不算一轮运行」是同一件事的两种形态,各摆一组**:前者摆
`finished_at` 落成数字(`slice` 当场抛),后者摆 `{}`(不抛、字段「齐」)。两组都断言
「只坏它自己那一行」,而出口是同一个。

「同一轮」那一族的回归**按凭据分档摆**,一档一条:展示版本撞上(两轮旧格式、同秒)、
旧身份重复(两条 `run-1`、时间不同)、假位置锚点(后续行那条版本和状态那条撞上、内容
不同)。**反过来钉两边**:升级前那最后一轮(两份都写成功、内容逐字相同)照旧认得出是
同一轮、重试照旧放行;旧格式下位置证据成立那一局(历史里还留着状态那一轮)照旧判出
首条更新。少了这两条反向的,判据就可以砍得太狠而全绿。

**页面探针这边要摆「后端漏标」那一局**:`valid_round` 现在会把坏时间戳标出来,所以
前端自己那道 try/catch 成了冗余带 —— 而冗余带的回归只能靠「上游漏标」来摆(mock 里
一个开关强制 `invalid: false`)。同一个文件里紧跟着的那一组摆正常档(后端标了),两档
都断言「只坏它自己那一行」。
