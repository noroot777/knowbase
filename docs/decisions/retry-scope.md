# 「重试失败项」的范围(kb/pipeline_retry.py + pipeline_daybook.py + pipeline_results.py +
# feeds/sync.py + feeds/retry_targets.py + pipeline_state.py + collectors/)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束

- **这颗按钮要补的是「今天还欠的那些」,不是「最近一次运行」里那些**(`kb/pipeline_daybook.py`)。「最近一次运行」只有
  一个位子,而一天里会跑好几轮:09:12 一轮 RSS 抓取失败、10:20 一轮公众号成功收尾,后者当场把前者顶掉 —— 于是点重试
  要么收到一句「上次运行没有失败项」,要么按最近那一轮的范围从头跑一遍(2026-10-19 10:34 那一次),而 09:12 该补的那条
  一直没补上。账本**按 (步骤, 来源, 目标) 记一格,只认今天**:「同一天继承之前的状态」和「不跨天」是同一份判据的两面。
- **结清的判据是「这一次真跑过的范围覆盖了这一格」,不是「同一条通道刚有一轮结束」。** 记到通道那一层就够的话,同一天
  「只同步订阅 A 失败」之后「只同步订阅 B 成功」会把 RSS 那一格整个换成 B 的成功 —— A 的失败从此不在计划里,而它的
  `last_error` 还在。三条:①这一轮点名了几个目标 ⇒ **只写那几格**,不碰整通道那一格、也不碰别的目标;②这一轮跑的是整
  通道 ⇒ 它确实把这个通道跑了一遍,所以**先清掉这个通道这一步的全部旧账**再写结论;③整通道**失败**而采集器留下了失败
  名单 ⇒ 只写名单里那几个目标(B/C 在那一轮里明明成功了;名单是 `collect` 扫完之后一次写的,崩在半路压根不写 ——
  「没有名单」另有含义:整批失败,按原范围重跑)。
- **抓取和导出各读自己那份有效范围**(`_owners`:crawl 读 `crawl_filter`、export 读 `export_filter`,回落只为升级前的
  旧记录)。拿抓取范围给导出记账的后果是「只补导出」那一轮的成功记到了**空通道**上,原来那个来源的导出 error 留在原处
  —— 下一次重试照旧派生出 export/index/extract,补好的那一步被反复重跑。**这里不用 `run_scopes`**:它答的是另一个
  问题(「这一轮整体作用在哪几个来源上」,见下一条)。
- **「这一轮整体作用在哪几个来源上」= 按来源执行的那几步各自范围的并集**(`pipeline_stages.run_scopes`,前端那一份
  同口径是 `pipe_channels.js` 的 `pipeRunScopes`,**两份实现各有自己的红、输出形状也对齐**)。**不许拿某一步的范围当
  整轮事实**:只读抓取那一份的话「只补导出」那一轮一个来源名都报不出来(它的抓取范围是 `{"force": true}`),后果是
  ①开着的订阅页在重试成功之后**一直显示翻译失败和等待翻译**(它靠「这一轮带不带本来源」决定要不要重读条目,而仅
  翻译/导出既不改订阅行也不改收录总数 —— 另外两个判据对它都是瞎的,下一次轮询照旧什么都不重读,只刷新整页才看得到
  译好的正文);②同步中心写「选择来源后开始一次同步」、历史那行写「未记录来源」;③**订阅的增/改/删写保护整条失效**
  —— 导出正写它那几篇文章,而订阅可以删。**也不许写成 `crawl_filter || export_filter`**:只导出那一轮 `{"force": true}`
  已经为真,而抓取 A / 导出 A+B 那一轮又会漏掉 B。**判据是这一轮计划里有没有那一步**,不是 filter 里写着谁
  (`start_pipeline` 一律往 filter 里盖一个默认采集器名),**纯全库那几步一个来源都不凭空附加**。同一个来源两步都在时
  那一格的 `accounts` / `retry` 取**抓取**那一份(它是收窄过的那一份,而「本次范围」那行念的正是它);要问「某一步在
  这个来源上的范围」的一律自己读那一步的 filter。
- **失败名单只在它收窄得住全部欠账时才用**(`_owed`):`retry_crawl_scopes` 拿名单**替换**整个范围,所以整通道那一格还
  欠着时只认它自己那一份名单(别的目标各欠各的,拿它去收窄会把它们摘掉),逐目标那几格要**每一格都有名单**才合起来用。
  不用名单不等于乱抓 —— 范围本身已经是那几个失败的目标了。
- **账本在收尾层折,一轮一次,折的是那一轮自己的终态**(`pipeline_state._save_daybook`,挂在 `_end_run` 那三份留档
  里)。**不许事后拿整批合并出来那一份折** —— 一批里 RSS 失败 + 公众号成功合成一个 error,再按合并后的来源清单摊开,
  公众号那一格也成了 error,继承当场反向。**只折这一轮计划过的那几步**:没计划过的那一档是 `skipped/未选择`,折进去
  就是拿「这一轮没跑它」盖掉「今天早些时候它失败了」。
- **后记的那一格盖掉先记的那一格,不取最重的那一档** —— 那正是「继承」。取最重的话今天之内它再也变不回绿色,这颗按钮
  每次都去重抓一遍已经好了的来源。
- **逐来源的结论由执行器自己交回来,不许从那张合并卡片反推**(`kb/pipeline_results.py`,`_per_channel` 里一个来源一格)。
  合并卡片只够展示:`pipeline_segments._merge_segments` 把各段扁平并起来、项里不带来源归属,一轮里只要有一个来源失败,
  整张卡片就是 error。照它摊开的后果是**一轮同时抓公众号和 RSS、只有 RSS 一条订阅失败时,公众号那一格也成了 error**
  (说明里同时写着「公众号已抓完」和「RSS…失败1个」),点重试把已经抓完的公众号又抓一遍 —— 而用户要的正是「9:12 抓过
  的不要再抓」。**账上有这个来源自己那一条就必须用它**;拿不到才退回整步那张卡片(存量记录、全库那几步、这一轮没轮到它
  就被停了),那是保守档 = 旧行为 = **宁可多记一格失败**(漏记是静默丢数据,多记顶多重抓一次)。
- **记账的键是「实际覆盖的目标、归一到稳定 id」**,不是请求里写的那几个字。两道各管一头:
  · **身份归一**(`collectors.TargetIdentity`,订阅那边按 `reg.in_scope` 归到 id)。同一条订阅在「请求里叫 A」和「失败
    名单里叫 63」两种写法下会记成两格,后来成功清掉其中一格、另一格的红永远留着 —— 页面同时显示「4/4 完成」和「今天还有
    1 个步骤没补上」,点下去后端回一句「今天已经抓成功、没有要补的来源」:一个点不动也消不掉的死局。**匹配不上的那几个
    原样留着**(刚被删掉或改了名),从账上摘掉就是漏记。
    **归一只做在「这一轮计划的范围」和「从账本读进来的旧键」这两侧;成功回执那一侧一个字都不许过它**
    (`pipeline_results.cover` **不收采集器**,靠签名钉住 —— 归一第一件事就是去取采集器的 `TargetIdentity`,
    拿不到它就无从再匹配一次)。采集器交回来的 `Coverage.targets` 本身已经是稳定身份(订阅源报订阅 id、
    公众号报账号名),再过一遍范围匹配等于把**选源方向**那份宽度搬到**记账方向**,而两个方向的安全侧是
    **反的**:选源宽一点 = 多抓一条(重抓一次就好),**记账宽一点 = 拿一次没发生的成功清掉另一条订阅的真
    失败**,它从此不进重试计划。实测形态:A 编号 63 名字「A」、B 编号 64 名字「63」—— 先只同步 B 并让取文
    失败(账上 `{"64":"error"}`),再只同步 A 并成功,裸着的回执 `63` 经那份宽匹配扩成 `["63","64"]`,账本
    变成 `{"64":"ok","63":"ok"}`,B 的 `last_error` 还在原处而重试计划已经是 `[]`。**反过来不归一的代价只
    落在安全那一侧**:键对不上就是「这一笔谁也清不掉」= 多抓一次。所以「宁可宽一点」**只在选源方向上成立**,
    `reg.in_scope` 的 docstring 按那一侧写的,别当成全局规则搬走。
    **归一要同时管「这一轮新写的键」和「从账本读进来的旧键」**(`pipeline_results.stable_keys`,折账入口在
    `_fold_into` → `_restable`)。只管新写那一侧的话,升级前按显示名记下的那一格留在原处,同一条订阅照旧是两格 ——
    上面那个死局换个来历又回来了。**撞到同一个 id 时晚的那一笔留下**(账本一直是后记的盖先记的,那正是继承);
    **归一不出来、或者一个名字匹配上好几条(有歧义)时原样留着**,不许从账上摘掉。
  · **覆盖范围由执行契约定**(`pipeline_results.WHOLE_SOURCE_STAGES`)。导出走 `materialize()`,它压根不收目标、扫的是
    整条来源,所以导出的覆盖**就是整条通道**;按请求那几条订阅给它记账的话,「A 的范围跑了一次导出」清不掉「B 的导出
    失败」,下一次重试照旧派生出 export/index/extract。往那张表里加步骤之前先确认它真的扫整条来源 —— **报宽了就是把没跑
    过的旧失败一起清掉(静默丢数据),报窄了顶多多重跑一次**。
  · **点名跑了几个目标、而且留下了失败名单时,名单之外那几个记成功**:它们这一轮确实抓成了,记成失败等于下一次又去抓
    它们(名单恰恰是采集器说「只有这几个还要重抓」)。
- **「红记在哪几格」和「绿清掉哪几格」用的不是同一个范围 —— 这两边必须反着来**:红按**这一轮计划过的范围**记,
  绿只按**这一轮真跑成了的那几个**清(`collectors.Coverage`:`targets` 是真跑成的那几个身份,`whole` 是「整条来源
  跑了一遍、一个都没剩」;`pipeline_results` 那一格同时存 `planned` 和 `covered`,`pipeline_daybook._fold_into`
  按它折)。两边同一个范围的后果是反着的两种静默丢数据:按执行事实记红 ⇒ **零覆盖**那一轮(采集器压根没装好、通道
  起不来、取文一次都没发)覆盖范围是空的,它那一笔红一格都没记上,而页面照旧「检查 0/1 个来源」绿色收尾 —— 这一轮
  的失败从此谁都不知道;按计划范围清绿 ⇒ 这一轮明明一条都没取到,早些时候那几笔真失败被**当成已经补上了**。
  **零覆盖又没有红要记时,那一格一个字都不许动**(留在原处 = 下一次照旧补得到)。
- **覆盖范围由采集器自己交回来,它报不出来(返回 `None`)才退回请求范围** —— 存量采集器不必改就还是老行为,而退回
  那一档是保守的:宁可多记一格失败。**每一条返回路径都要交一份**:`fetch` 中途 return 的那几个分支(没装好、起不来、
  底层库读不出来)忘了交,那一轮就被当成「整条来源跑了一遍」,整通道的旧账当场清空。
- **推断出来的那份覆盖范围,只在这一步真执行过时才算成功证据**(`pipeline_retry.stage_ran` 判一次,
  `pipeline_daybook._coverage` 是唯一消费方)。采集器报不出来那一档按计划范围推断,而**导出压根不用采集器报**
  (它扫整条来源)、**全库那几步连来源都没有** —— 所以它们一律是推断值,一律带着「整条覆盖」收尾。**跳过、被停、
  没轮到的那几轮照它结清就是拿一步压根没跑盖掉一笔真失败**(实测两条,都不需要用户主动制造故障:采集器没装好时
  导出报 `skipped`、条目化脚本被手动实例占着时整理报 `skipped`,外加等维护锁时按停止那一档的 `stopped`)。
  **跳过不许清旧失败,也不许凭空新建失败**:零覆盖 + 没有红要记 ⇒ 那一格一个字都不动。
  **判据是白名单**(只有 `ok` / `error` 算执行过):认不出来的状态算成「执行过」是静默丢数据,算成「没执行」顶多
  把补好的那一步再跑一次。**采集器自己报过的那一档不过这一道** —— `Coverage` 是执行事实、卡片只够展示,一轮里
  有一条订阅缺配置时整张卡片就是 `skipped`,而那一轮真抓成的那几条照旧结清(不许为了挡住跳过那一档把整个来源
  重新标红)。
- **「这个来源这一步有没有结论」这件事,建账要在跑之前、停止那一道要在建账之前**(`_per_channel`)。建了账就等于说它有
  结论,而收尾那一下会把没报过结论的那一格记成 error —— 于是按了停止反倒给今天留下一笔欠账,下一次重试去抓一个用户
  明确叫停的来源(整步那一格是 `stopped`,按现有口径不算欠,两处就对不上了)。
- **一个来源的准备、执行和汇报待在同一道隔离里面,一步都不许露在外面**(`_per_channel`:取采集器、建它那一格账、跑,
  外加汇报那一段,全在同一个 try 里)。建账要先算这一步在这个来源上实际覆盖哪几个目标,点名了目标就要**读一次订阅库**
  —— 而这一步在 fetch **之前**。只把执行那一句圈进去的话,这次读失败时异常是从 `with` 那一行抛的:连这个来源自己的
  try 都还没进去,整个来源循环当场跳出,**勾着的其余来源一个都不跑**(实测:订阅源的身份查询抛 `OSError`,同一轮里
  健康的公众号 `fetch` 调用次数为 0;同一个故障落在 fetch 里时它是 1)。**采集器整条路上只许取一次**:打桩按调用次数
  发实例,多取一次会让后面那个来源拿到串位的采集器。准备阶段炸了也**要补一段**挂它自己的名字 —— 不补的话那一笔落成
  「整步 error」,把这一轮里别的来源也一起染红,而那恰恰是结果账要避免的事。
- **已有的来源结论不因它存在哪一份落盘里、从哪个入口恢复而丢失**(序列化/反序列化与重试规划这三道边界同一份契约:
  `run_payload` / `pipeline_persist.run_record` / `_restore_once`,外加 `_end_run` 往内存那份终态也存一份)。
  落盘写上了、恢复却不读它,等于自己把事实扔掉:状态文件里明明写着「公众号这一步 ok、RSS 失败」,重启之后那颗按钮又
  把公众号抓一遍(实测 `restored.results` 整个字段缺失、`retry_wechat=['wechat_local']`)。**降级那一档也必须消费它**
  (`unfinished` 的 `alone`:退回「最近一次运行」之前先按结果账折一遍,走的是和账本同一份口径),原样把那份合并卡片
  交给旧规划器就是把整步失败重新摊给所有来源。**只有「说不出来」才允许退回保守档**,不是「这条路上没接线」。
- **结果账清在三份留档都取完之后**(`_end_run` 那个 `finally`,`run_payload()` 负责把它带出去)。早清一步,当日账本折到
  的就是空账、退回整步那张合并卡片;不清则是拿上一轮的结论去清这一轮的欠账。
- **内存欠账那几桶按 (账本文件, 日键) 分,旧日那些要扫掉**(`_sweep`,挂在唯一的访问入口 `_bucket` 上)。只有「今天」
  那一桶会被折进账本、也只有它会被 `unfinished` 读到,所以旧日那些留着没有任何用处:磁盘一直写不进去的那种坏法下,它们
  会一天一桶地攒在进程里(各最多 `_PENDING_MAX` 轮完整留档),而 `_lost` 那个计数也没有清理路径、旧日的数字念出来就是
  一句错话。**判据是「和今天差几天」,不是「现存的日键里最近那几个」** —— 后者在中间隔了几天不开机时留下的恰恰是最老
  那一桶(5 天前那一笔和今天那一笔正好凑成「最近两个」)。**扫掉不等于把旧账搬进今天**:「继承只在当日内」是用户定的
  边界,搬过来就是拿昨天的失败去派生今天的重试。
- **没指定来源的那一轮也要记一格,键就是空串**(整库同步 —— 面板上一个来源都没点,`crawl_filter` 是空的,摊出来的范围
  `channel` 也是空的)。把它当成「没有来源可挂」丢掉的话,`stages` 这一层照旧多出 crawl/export 两个空字典:账本看着
  「今天跑过」、每一步却都合成成「未选择」—— **这颗按钮对最常见的那一轮回一句「上次运行没有失败项」**,那一轮的红一个
  入口都没有了。空串那一格的含义是「不挂在任何具名来源上」,合成快照时**不进来源范围**(`{}` = 没有范围 = 照默认采集器
  全抓),和那一轮自己的 `crawl_filter` 一模一样。
- **账本不许盖得住「最近一次运行」自己报出来的失败**(`_overlay`)。折账本是旁路,写不上只记一笔 `persist_error` 就过去
  了 —— 可它写不上的那一轮要是正好带着红,账本里就只剩之前那几轮的样子、而它们多半是绿的:这颗按钮回一句「没有失败项」,
  那一轮的红一个入口都没有。退回去只读账本是**漏报**。所以合成之前把「最近一次运行」再盖一次,三道判据各管一个方向:
  · **账本里已经有它那一轮就不盖**(按 run id 认)。不是为了省事:批次那一档「最近一次运行」是**整批合并出来那一份**,
    来源清单是全批的、阶段是合起来的,盖上去就是 RSS 失败 + 公众号成功合成一个 error 再摊到两个来源上,公众号那一格当场
    变红 —— 继承反向,下一次重试去重抓一个今天已经抓成了的来源。汇总继承最后那个子轮的身份,所以按身份认得出来。
  · **账本比它新就不盖**(比的是同一个时钟:`at` 和 `finished_at` 都出自 `pipeline_state._now()`)。跑着的时候
    `last_result()` 回落的是磁盘上**上一轮**那份,按它盖回去的话今天之内那个来源再也变不回绿色。**跨天那一档走的也是
    这条** —— 昨晚那一轮比今天任何一格都旧。
  · **两边的时刻都读不出来时照旧盖**:宁可多抓一次,不许漏。
- **账本空了(今天一轮都没有)或者读不出来,退回「最近一次运行」那一份** —— 那是这颗按钮一直以来读的东西,不是新的
  坏法;比「拦住不许重试」合用。账本写不上同另两份留档一档:**旁路,不许挡住收尾**,代价只是退回存量行为。
- **降级要在派生层判一次、而且一路说到面板。** 「读不出来」「合不成范围」「今天有几轮压根没记上」三句话各自一条,都从
  `daybook.unfinished` 出来,跟着起跑消息走到 toast、同时落一行运行日志(toast 是一次性的,而这件事是事后回头查才想得
  起来的)。**形状不对和读不出来同一档**(`read` 里判一次就抛):放着不判的话内层不是字典时会在 `.values()` 那一步抛
  —— 而那一抛在 `today_failed` 里被兜住、在 `start_retry_failed` 里没有,同一份文件让状态接口照常、点一下重试却 500。
- **折账本失败的那一轮要留得住缺口**:它留在内存里(`_pending`,键带着账本文件和日键),下一次 `fold` 连它一起折、
  合成快照时也先盖上去。什么都不留的话,后面任何一轮成功收尾都在一份不完整的账本上接着写,而「当前有一格」被当成了
  「今天的历史齐全」。**满了挤掉最早那一笔要记一笔 `_lost` 并说出来** —— 那一档是真的补不回来(进程退出之后那几轮的
  终态哪儿都没有);而「盖最近那一轮」那一道管的正是进程已经退出的那一档,**两道各管一段、各有自己的红**。
- **这颗按钮露不露脸也按「今天还欠不欠」判,不按「最近一轮红不红」**(回包字段 `today_failed`,口径
  `pipeline_retry.today_failed`;面板那一处在 `pipe_view.js` 的 `pipe-retry` 那一行)。后端补得再对也要先有人点得到它:
  09:12 抓取失败、10:20 一轮全绿收尾之后最近那一轮一个红都没有,按旧判据按钮当场藏掉 —— 今天早些时候那几笔**连点的机会
  都没有**。账本空着时 `today_failed` 退回最近一次运行,所以它只会**多**显示、不会少显示(多显示那一档点下去照旧按真实
  计划跑;少显示那一档是用户再也碰不到的红)。**按钮冒出来就要有一句话说清它为什么在**,而那句话**排在「这一轮自己有几
  步失败」之后** —— 这一轮自己报了红时屏幕上的卡片正指着它们,把注意力引到别处是另一种谎。
- **整个「需处理」区(标题、说明、重试按钮)共用那一份当日待补判据。** 那颗按钮在 `#pipe-issues` **里面** —— 只给它自己
  解除隐藏是不够的:祖先藏着时它的 `hidden` 是 false、高度却是 0,页面上明说「今天早些时候还有 1 个步骤没补上」而一个
  可点的东西都没有。**可操作性取决于整条祖先链**,所以探针量的是祖先链 + 外接矩形 + 命中测试,不是那一格属性
  (`tests/pipe_owed_probe.mjs`)。这一档的说明里**不许写「明细在下面那一步里」**:下面那几张卡片讲的是这一轮(全绿),
  欠的那几步在屏幕上压根没有自己的卡片。
- **「本轮是怎么结束的」和「今天还欠什么」也是两件事,各说一句**(`pipe_view.js` 的 `pipeRoundSoFar`)。「今天早些时候
  还有 N 个步骤没补上」那一句原来排在停止、跳过、「完成数等于总数」几档**之前**就返回,于是**「本轮一个红都没有」被当成
  了「本轮全部执行成功」**:今天先有一次导出失败、后来只跑了一轮被跳过的导出时,标题和进度正确写着「部分步骤已跳过」
  「0 / 1 完成」,同一屏那句话却说「本轮的步骤都完成了」。被停止、以及计划里还有步骤没跑完那两档形态一样。
- **「这一轮红没红」和「现在还补得到什么」是两件事,界面上不许用 OR 把它们混起来**(`pipe_view.js`:收尾标题、那句
  说明、问题区的藏不藏与标题、重试按钮,四处都只认 `today_failed`)。**空集是答案,不是「没答」** —— 拿这一轮的红去
  兜底的后果正是后端已经修掉的那个死局原封不动留在页面上:今天先抓成、后来又失败的那条订阅(或者失败之后被停用、
  删掉的)后端已经从待补里摘掉了,而 OR 让它重新放行 —— 页面说「1 个步骤需处理」、点下去回一句「这颗按钮没有要补
  的」、刷新还是那样。**「需处理」是一句催人动手的话**,所以它和那颗按钮一起对齐到「现在真补得到」;**这一轮的红
  照旧说出来**(收尾标题写「N 个步骤失败(已不用补)」、那句说明指一句去哪看、阶段卡片照旧是红的),两件事**分开
  表达**,不改写历史、也不为了让按钮有事可做去重抓已经继承成功或被停用、删除的订阅。
- **翻历史时那个区念屏幕上那一轮自己的红**(`shownStages` 那一道):那时它是一块只读的导航(按钮另有自己的 `viewing`
  守卫)。一并按「现在补得到什么」判的话,翻到一轮红的记录连「看第一个」都没了 —— **反过来钉一边**,两个坏法靠探针
  里两组的颜色分辨。
- **「需处理」这个词只许一处念,而且那一处要和那颗按钮同一个数字**(`pipe-issues-title`,按
  `shown` 算)。**收尾那句标题(`pipe-state-title`)只讲这一轮**:「N 个步骤失败」。两处都写
  「需处理」的后果是同一屏上两个数字配同一句话 —— 这一轮红了 1 步、今天另外还欠着抓取时,
  标题写「1 个步骤需处理」而那个区写「2 个步骤需处理」。**「已不用补」只在真答得出来的时候
  说**:翻历史时 `owed` 是被主动置空的(它说的是此刻这一天,而屏幕上是另一轮),拿它去念
  「已不用补」就是在一份没有今天信息的视图里替今天下结论,而那一轮今天很可能还欠着。
- **旧服务那一档要显式降级,不许靠 OR 顺带兜住**:回包里压根没有 `today_failed` 这个字段时才退回这一轮自己的红
  (判据是「这个字段在不在」,不是「它是不是空的」)。这不是假想:`kb/static` 每次请求从磁盘读、而 Python 模块要重启
  才换(CLAUDE.md「服务与运行时」),所以「新页面 + 旧进程」是真会出现的状态。
- **「这颗按钮会跑哪几步」只许有一个答案**:`retry_failed_plan()` 缺省那一档也过 `owed_now`(账本 + 现在补不补得到),
  不是只读账本。只读账本的话,单独问一句的人看到整条链,而同一刻真点下去是「没有要补的」—— 下一个调用方就这样继承
  了旧口径。**起跑端自己算过就按它传进来的那个走**,不在缺省那一档再覆盖一遍;**问不出来退回只按账本答**(多排一步
  顶多白跑一次,少排一步是用户再也补不上的那几笔)。
- **「页面说今天还欠的」和「这颗按钮现在真补得到的」是同一份派生,只许算一次**(`owed_now`:状态端的
  `today_failed` 和起跑端的 `start_retry_failed` 都过它)。各算一遍的后果是一个**点不动、也消不掉的死局**:账本记着
  抓取欠着,而执行端按当日继承 / 停用 / 删除把目标过滤空了 —— 页面一直说「今天还有 1 个步骤没补上」,点下去回一句
  「没有要补的来源」,刷新还是那样。三种形态都走同一条路:今天成功过之后又失败、失败之后被停用、失败之后被删掉。
  **只摘得掉抓取那一步**:别的几步各有自己的可补性,不能因为抓取过滤空了就把整张问题卡抹掉(index / extract 真失败
  时照旧要补)。**不改账本,只改这一次派生出来的那一份** —— 账本记的是「今天真失败过」,那是事实;改写它等于把历史
  改了。**问范围要开那个来源自己的订阅库,所以只在抓取真欠着的时候问**(只有 index 失败、而订阅库恰好打不开的那一轮,
  不该被一个跟它毫无关系的故障拖住);**读不出来一律照抛,由调用方降级** —— 状态端兜住它、宁可多显示一次,起跑端
  照旧让它说出原因。
- **这颗按钮的范围 = 继承上一轮的「来源」+ 各来源自己留下的失败名单**(`retry_crawl_scopes`)。继承的是「哪几个
  channel、上次点名了哪几个目标」,**不是「抓多少东西」** —— 后者按**来源逐个**收窄,外加一个 `retry` 字段说明这一项
  是怎么来的(`targets` / `all`)。
- **不收窄的两个缺口是反着的**:①继承来的 `accounts` 是空的,而空在 `sync.collect` 里正好是**全部**;
  ②`FetchScope.force` 这条路上压根没人传过,而失败恰恰会记一个 `retry_at`。
- **名单要在失败那一刻记下来,不能事后从别处反推**(`note_retry_targets` 写、`retry_notes` 读):按 `last_error` 筛会
  漏掉「已改正、还没验证过」的;从阶段状态那份 failures 反推拿到的 `title` 对公众号来源是文章标题;一个全局布尔会让一
  个来源的失败类型决定另一个来源抓多少。
- **必须按来源各记一份,因为「整批失败」和「只坏了一条」是两件相反的事** —— 两者在 `subscriptions` 那边长得一模一样,
  **分得开它们的只有「这个来源留下名单了吗」**。
- **「仍然需要重抓」的判据是「那一轮失败之后有没有成功同步过」**(`feeds/retry_targets.still_failing` —— 当日继承和
  失败名单收窄那两道待在这里,`sync` 越过 700 行上限时拆出去的,口径一个字没动、原处照旧 re-export)。**名单的时刻要用采集器自己那
  套时间格式**(UTC ISO,不是本地空格格式)—— ISO 的 `T` 排在空格后面,整份名单会被摘空。`at` 因此是**必填**的。
- **外加一档「当日继承」:今天已经成功抓过的那一条,哪怕后来又失败了,这颗按钮也不再抓它**
  (`feeds/retry_targets._succeeded_today`)。**继承只在当日内** —— 跨天由日期判据自动清零,这是仓库主人点名的边界,**不许改成滚动
  窗口或「最近 N 小时」**。这颗按钮的射程是「把上一轮没成的补上」,不是「再取一次新内容」。
- **当日那条判据必须换算时区再取日期,不许截 `last_success` 的前 10 个字符**:它是 UTC ISO,日界比 Asia/Shanghai 早
  8 小时。**读不懂的时刻算「没成过」,不按项目时区补齐。**
- **当日继承只收窄这颗按钮,不许漏进单独同步**(「我的订阅」那条路不走 `still_failing`)。两条都收窄的话,今天抓成过、
  晚些时候又坏了的那条订阅**当天就彻底没有入口了**。
- **拦路的东西还拦着就拒绝起跑,不许让它原地红一遍**(`crawl_blocked`):拒绝 = 上一轮的结论、失败名单、导出范围
  **一字未动**,下一次重试照旧从它派生。「抓得动」的判据是采集器自己那份 `status()`(`online and ready`),**这里不另
  写一份**。**问不出来一律放行,有一个抓得动就不拦**(并且当场返回,不再往下探测)—— 拦住整轮会把同一轮里本该重试的
  index / extract 一起带走。拒绝那句话要带**来源名、原因和下一步**,而且**每一个抓不动的都要出现**。
- **那道闸问的是「这一次要抓的那几个」,不是整条通道。** 范围收窄到几条订阅时把名单交给
  `status(targets=...)`(契约写在 `kb.collectors.SourceCollector.status` 上;范围匹配只有一份口径
  `registry.in_scope`,`sync.collect` 挑订阅用的是同一个)。不交的后果是**用 B 能抓证明 A 能抓**:
  同一条来源里 A 要走 X 通道而那个浏览器被占着、B 填了专用订阅链接好得很,整条通道于是「还有抓得动
  的」,只重试 A 也照样放行,A 必定再失败一次 —— 正是这道闸要挡的那个代价。**两档反过来钉住**:
  `retry: "all"` 照旧问整条通道(那时要抓的确实是它的全部订阅);**「范围里一条启用着的订阅都没对上」
  要放行**(它答的是"这一轮没有来源",答不了"这几个抓不动",而拦住会把同一轮本该重试的 index /
  extract 一起带走)。**逐个目标没有就绪这个概念的来源原样忽略范围** —— 本机库那条路问的是"采集器
  装没装好、那个库读不读得出来",跟抓哪几个号确实无关。
- **抓不动也只摘抓取那一段,不是整条计划一起扣下**:同一轮里红掉的 index / extract / Wiki 跟那个浏览器毫无关系,
  一起扣下的后果是用户点一次只收到一句「先把这件事处理掉」,而本来能补的几步一步都没补。**只有这一次确实只剩抓取可做
  时才整个拒绝**(那才是白跑)。摘掉的那一步**是 `skipped`、而且卡片上写清为什么**:标成成功会把这条红就此丢掉,
  记成失败又会被面板和下一次的计划判据当成这一轮刚失败的东西。该补的那几个来源**留在当日账本里**(这一轮没把它们列进
  计划,`daybook.fold` 就不碰那几格),拦路的东西撤掉之后点重试照旧派生得出来 —— 这一条才是「不许标成功」的判据。
- **一条都没失败也要记一份空名单**(那份空名单本身就是「这个来源扫完了」,而「压根没留下名单」另有含义)。名单**带着它
  自己那一轮的 run id**。
- **报不出名单的来源按原范围重跑**(`collectors.RetryNarrowing`)。**这不是缺陷,是另一种真实情况**(公众号的失败是文章
  级的,而它的 targets 是账号级的)。生成计划这一步**不许抛**。
- **「这个来源一个都不用抓」= 整个来源不进这一轮,不是给它一个空 `accounts`**:全空时走
  `retry_failed_plan(nothing_to_crawl=True)`,crawl 整个摘出计划。
- **export 走上一轮**原来**那几个来源,不跟着 crawl 收窄**,而**「原来那几个来源」必须自己落一份盘**(`pipeline_state`
  的 `export_filter`,三处写入口)。**常规同步那条路要把它重写成自己那一份**,不靠「没设过就回落」兜底。
- **造范围这一步的故障不许扩散到别的阶段上,三道各有射程**:①**先定计划,只有 `"crawl" in plan` 才去问名单**;②**认名
  字和问名单一起护在那道 `except` 里**;③**名单是空的就别开库**。
- **收窄要和 `targets` 取交集**,不是扫一遍库里所有失败的订阅。**「预算跳过」和「退避中」那两档不进名单**(压根没被尝
  试过,下一轮轮转本来就会补齐)。
- **没有要重抓的时要说清为什么、并指到正确入口**(`RETRY_NOTHING`,crawl 落 `skipped`)。
- **收窄过的那一轮要把范围说出来,而且按来源各说各的**(`pipeRunScopes` 透传 `retry`)。
- 详细见 `docs/decisions/retry-scope.md`。

## 事故形态与实测证据

- **这颗按钮的范围 = 继承上一轮的「来源」+ 各来源自己留下的失败名单**
  (`retry_crawl_scopes`)。继承的是「哪几个 channel、上次点名了哪几个目标」,
  **不是「抓多少东西」** —— 后者按**来源逐个**收窄,结果写成那个来源自己的
  `accounts`,外加一个 `retry` 字段说明这一项是怎么来的(`targets` = 收窄到了失败
  的那几个 / `all` = 这个来源收窄不了,按原范围重跑)。
- **不收窄的后果实测过,而且两个缺口是反着的**(2026-10-09 用户报告:大V观点同步
  时一个账号地址填错导致那一条失败,改好之后点「重试失败项」,51 个账号的时间线
  全被重新读了一遍):
  ①上一轮是「同步大V观点(全部)」,继承来的 `accounts` 是**空的**,而
    `sync.collect` 里空的含义正好是**全部** —— 一个账号填错地址,换来整条通道
    十几分钟的重读 + 白攒的账号风险,而真正该重试的那一条和别人没有任何区别;
  ②`FetchScope.force` 的注释从一开始就写着「手动重试可跳过来源退避」,可**这条
    路上压根没人传过它** —— 而失败恰恰会给那条订阅记一个 `retry_at`(最短 1800
    秒,见 `sync._save_failure`),于是失败后的半小时内点这颗按钮,唯一该抓的那条
    被记成 `deferred` 跳过。合起来就是「该抓的不抓、不该抓的全抓」。
  用户这一次没撞上②,是因为改链接时 `save_subscription` 的 `reset` 把 `retry_at`
  一起清成 0 了。
- **名单要在失败那一刻记下来,不能事后从别处反推**(`pipeline_state.note_retry_targets`
  写、`retry_notes` 读,`sync.collect` 收尾时调一次,跟着 `last_run` 一起落盘)。
  三条反推的路各自不成立:
  ①**按 `last_error` 筛**:改链接时 `save_subscription` 的 `reset` 把它连同退避
    一起清空,于是「已改正、还没验证过」的那条被当成「已经恢复」漏掉 —— 用户修完
    地址点这颗按钮,那个账号一条也不抓,而那正是原始需求那一局(第 1 轮审查实测);
  ②**从阶段状态里那份 failures 反推**:项里的 `title` 对订阅来源是订阅名,对公众号
    来源却是文章标题和「推送归属待核实」这类句子(见 `wechat_local._report`),拿它
    当目标名传下去那一侧一个都匹配不上;多来源时那份明细还是**扁平合并**的、项里
    不带来源归属(`_merge_segments`),想按来源各取各的还得先给每项打上归属;
  ③**一个全局布尔**:那是第 1 轮被审那一版 —— 它让一个来源的失败类型决定另一个
    来源抓多少东西(见下一条)。
- **必须按来源各记一份,因为「整批失败」和「只坏了一条」是两件相反的事。**
  一条订阅自己抓不动 → 名单里有它,下一轮只抓它;整个来源这一轮压根没开工(登录态
  读取器崩了、采集器抛异常)→ `collect` 整个抛出去,那时**一条订阅都还没被碰到**,
  也就没有名单可言,这时该重抓**整个来源**。两者在 `subscriptions` 那边长得一模一样
  (都是一个 `last_error` 都没有),**分得开它们的只有「这个来源留下名单了吗」**。
  全局布尔的实测后果:大V整批失败 + RSS 一条逐项失败那一轮,两个来源都按失败项
  收窄,而大V一份名单都没留下 → 收窄成空集,恢复连接之后点重试它一条也不抓,
  面板上还不再显示需要处理的失败(第 1 轮审查第 2 条)。
- **「仍然需要重抓」的判据是「那一轮失败之后有没有成功同步过」**(`sync.still_failing`:
  `last_success` 比名单那一刻新就摘掉,订阅被删、停用、id 压根不存在的一并摘掉)。
  改过链接的那条 `last_success` 被 `reset` 清成了空串,所以它留在名单里 —— 这正是
  ①那条路换掉的东西。同一秒分不出先后时按「还要重试」算(保守多抓一次)。
- **名单的时刻要用采集器自己那套时间格式**(订阅那边是 `reg.now()` 的 **UTC ISO**,
  不是 `pipeline_state._now()` 的本地空格格式),所以 `note_retry_targets` 的 `at`
  是**必填**的 —— 少传一个参数当场报错,比悄悄用错格式好。ISO 的 `T`(0x54)排在
  空格(0x20)后面,同一天里 ISO 那个恒大于空格那个,于是「它后来成功过吗」会一律
  答成「是」,整份名单当场被摘空、这颗按钮变成「什么都不抓」。
- **一条都没失败也要记一份空名单。** 那份空名单本身就是「这个来源这一轮扫完了、
  没有要重抓的」这句话,而「压根没留下名单」另有含义(整批失败,按原范围重跑)——
  不记的话两者再也分不开,一个全程顺利的来源会被当成整批失败重抓一遍。
- **名单带着它自己那一轮的 run id**(`retry_notes` 身份对不上一律当成「这一轮没有
  名单」)。整批失败那一轮一份名单都没留下,而 `_state` 里还躺着**更早**那一轮的
  名单、会连同这一轮的状态一起落盘 —— 照它收窄就是按上一轮的失败去抓。带着 run id
  所以不必在每条启动路径上各清一次。
- **报不出名单的来源按原范围重跑**(`collectors.RetryNarrowing` + `retry_narrower`,
  不支持这个能力的采集器没有这个方法)。**这不是缺陷,是另一种真实情况**:公众号的
  失败是文章级的,而它的 `targets` 是账号级的,压根对不上(正文重试本来由它自己的
  `article_fetch_state` 退避管)。来源名现在认不出来了(改名/退役)同样走这一档,
  而且**生成计划这一步不许抛**到 HTTP 层 —— 那会把同一轮里本该重试的 index/extract
  一起带走(同 `refill_script` 那条"永不抛"的理由)。
- **「这个来源一个都不用抓」= 整个来源不进这一轮,不是给它一个空 `accounts`。**
  `accounts` 空的含义是「全部」,两者正好相反,而这条路上搞混的代价就是上面那场
  事故。所有来源都空了的时候走的是 `retry_failed_plan(nothing_to_crawl=True)`:
  crawl 整个摘出计划 —— 范围是空的,真让它跑,`crawl_channels` 会按「没指定来源」
  回落到默认采集器,抓的是另一个来源。
- **export 走上一轮**原来**那几个来源,不跟着 crawl 收窄**(`_run_retry_failed` 收
  `crawl_filter` 和 `export_filter` 两份)。两者的失败是各自的:一个来源完全可能
  crawl 成功、export 失败(翻译扣着不导出、vault 写不进去…),跟着 crawl 一起被
  摘掉的话它那一步就再也没人重试了。
- **而「原来那几个来源」必须自己落一份盘**(`pipeline_state` 的 `export_filter`,
  三处写入口:`_state` 的默认值、`_save_last_run`、两条启动路径各写一次)。只传给
  当次那个线程、只把**收窄后的** `crawl_filter` 落盘的话,这条口径只在**第一次**
  重试上成立:第二次重试又从那份收窄范围派生一次导出范围,于是第一次重试里**仍然
  导出失败**的那个来源就此被摘掉 —— 面板报「导出完成 · 已保存 0 条」,而它那几篇
  文章一个都没落进 vault,再点重试也不会回来(2026-10-09 第 2 轮审查实测:两个
  来源同一轮,social 的导出位置被占住,第二次重试只导出了 rss,social 那 3 条
  一篇 md 都没有)。
  **常规同步那条路要把它重写成自己那一份**(`start_pipeline` 里显式
  `"export_filter": deepcopy(crawl_filter)`,不靠"没设过就回落到 crawl_filter"
  兜底 —— `_state` 是模块级常驻的,上一轮如果是重试,里面躺着的是那一轮的导出
  范围,不覆盖的话这一轮的落盘会把它原样带走)。回落只给升级前那些没有这个
  字段的旧记录用。
- **造范围这一步的故障不许扩散到别的阶段上,三道各有射程。** 这颗按钮的射程远不止
  抓取,而问各来源的失败名单要读那个来源自己的订阅库:
  ①**先定计划,只有 `"crawl" in plan` 才去问名单**(`start_retry_failed` 里
    `scopes = retry_crawl_scopes(prev) if "crawl" in plan else []`)。无条件先问
    一遍的话,上一轮只有 index 失败、这会儿订阅库又恰好打不开(锁着、权限、路径
    没挂上)时,那个异常一路冒到 HTTP 层 —— 用户收到一句「Internal Server Error」,
    索引和后面的提取一步都没起跑(2026-10-09 第 2 轮审查实测)。**这一道和采集器
    无关**,所以它必须自己有一条用例。
  ②**认名字和问名单一起护在那道 `except` 里,故障只圈在这一个来源里**
    (`retry_crawl_scopes` 的 try 要罩住 `narrower.retry_targets(note)`,不只罩住
    `active_collector`)。问不出名单 = 这个来源收窄不了,按原范围重跑。
  ③**名单是空的就别开库**(`sync.still_failing` 的 `if not ids: return []`)——
    答案只能是空集。这一道是 feeds 这个采集器自己的早返回,换一个无条件读自己库的
    采集器就不成立了,所以它和 ① 不是一件事的两种写法。
- **收窄要和 `targets` 取交集,不是「扫一遍库里所有失败的订阅」。** 上一轮可能只
  同步了用户在订阅页勾的那三条,重试不该把上周留下的另外五条失败订阅一起拖进来。
  交集就在名单自己身上 —— 它记的是**这一轮**真失败过的那几条。
- **「预算跳过」和「退避中」那两档不进名单**,这是有意的:它们压根没被尝试过,
  本来就会在下一轮同步里按 `last_attempt` 轮转补齐(见 `collect` 里那句
  pending.sort),水位一个字没动,不该借这颗按钮把整个来源再抓一遍。
- **没有要重抓的时要说清为什么、并指到正确入口**(`pipeline_retry.RETRY_NOTHING`,
  crawl 那张卡片落 `skipped` 并写上它)。原来它把整个来源重抓一遍、面板上还是一张
  绿卡片,和「这个按钮坏了」长得一模一样。真想重抓某一条的入口是「我的订阅」里的
  单条同步(`POST /api/intake/{kind}/sync` 带 `source_ids`,它本来就带 `force`)。
- **收窄过的那一轮要把范围说出来,而且按来源各说各的**(`pipe_channels.js` 的
  `pipeRunScopes` 把 `retry` 透传给前端,`pipe_view.js` 那行「本次范围」照它说话:
  `targets` 写「仅重试失败的 N 个订阅」,`all` 照原范围写)。给所有来源一律写
  「仅重试失败项」是一句谎话 —— 它承诺了报不出名单那个来源并没有发生的收窄;
  照 `accounts` 一律写「全部订阅」也是,那正是刚被修掉的那个行为。
- **这颗按钮和「上一轮还没结束」无关。** 前端在 `running` 时就把它 `disabled`
  (`pipe.js`),后端 `start_retry_failed` 还在 `_lock` 里撞 `_state["running"]` 返回
  409「管道已在运行中」—— 它能真的起跑,说明上一轮已经收尾了。
- 回归分两个文件 + 一份共用摆盘(`tests/retry_scope_fixture.py`),**判据一律是
  「哪些目标真的被碰了」** —— 数 `fetch_source` 收到的订阅 id、以及预取收到的账号
  名单;只验「有没有打上标志」的话,一个把标志传下去却没人认它的实现也能全绿。
  `tests/test_retry_scope.py`(23 条,单来源):一条地址错了只抓它而另两条一次请求
  都没发、**改正地址之后那一条照样被重抓**(第 1 轮拦验收 1 的复现,还断言条目
  真的是按新地址抓回来的)、以前好着这一轮才坏的照样抓(**钉住时间格式混用那个
  坑**)、退避里的失败订阅抓得到、不扩大到上一轮没点名的历史失败订阅、普通同步
  **带 force 也不许收窄**、都修好了就拒绝起跑且文案点名「我的订阅」、范围空了不许
  回落到默认采集器、crawl 那张卡片说得出这一轮为什么是空的;外加
  **来源级整轮故障照旧全量重抓**(反过来还钉一边:留下了名单的那一轮照旧收窄 ——
  两条合起来才说明判据是「名单在不在」)、直测 `still_failing` 四种情况、名单那条链
  的契约(空名单也要记 / 陈旧名单不作数 / 换届重开一份 / 报不出名单的来源连名单硬
  塞给它也按原范围重跑)。
  **启动路径那一组**(`StartupIsolationTests`,把订阅库换成一个**目录**让
  `sqlite3.connect` 真抛 —— 指到一个不存在的目录骗不过 `reg.db()`,它自己会
  `mkdir(parents=True)`):只重试 index 时坏库不拦路、索引和提取真的起跑了
  (**后果那一条**,复现审查那份 500;它要 ①③ 同时失效才红,所以 ①③ 各自另有
  一条)、`"crawl" not in plan` 时**一次名单查询都没发生**(判据是**问了几次**,
  不是"抛没抛异常" —— 那道 `except Exception` 把 AssertionError 也一并吞掉,拿
  一个会被吞掉的异常当判据,这条用例对顺序压根不敏感)、空名单直测不开库、
  **名单问不出来时那个来源退回原范围**而不是收成空集、也不把整次重试带走。
  `tests/test_retry_multi_source.py`(9 条,多来源 + 面板):**一个来源整批失败、
  另一个只坏了一条时各按各的范围重试**(第 1 轮拦验收 2 的复现)、反过来钉一边
  (两个来源都是逐项失败时两边都收窄)、已经没有要重抓的那个来源整个不进这一轮、
  **export 收到的是原来那两个来源**、**登录态通道只重读失败那一个账号的时间线**
  (判据是**预取**收到的 handle 名单 —— 用户真正付的代价在那一步,而这条通道在
  HTTP 那一侧压根不发请求,数 `fetch_source` 答不了它;那一局要打桩
  `x_channels.readiness`,没真登录过的话这几条订阅会被判「待配置」、压根进不了
  pending)、反过来钉一边(常规同步照旧整批预取)、面板那行范围六种形态
  (**抠 `pipeRunScopes` 和 `scopeText`/`scope` 的真代码丢给 node 求值**)。
  **连续两次重试那一组**(`RepeatedExportScopeTests`):第一次重试里导出**仍然
  失败**、排除障碍后第二次重试,判据是 **vault 里真的落了那 3 篇 md**(不是
  "范围里有没有它")。导出故障是真的 —— 用一个普通文件占住 `source/social` 该在
  的位置,真实 `sync.export` 开头那句 `root.mkdir(exist_ok=True)` 当场抛
  `FileExistsError`;`_run_export` / `materialize` 一行不打桩,**打桩成功正好绕开
  唯一要验的那件事**(阶段分段、失败落盘和 `retry_failed_plan` 看到的东西都得是
  真的)。只把"配了 key 吗"按死成没配 —— 那是真实的 `skipped` 那一档,也顺手保证
  这一组一次模型请求都不发。另有反过来钉的一边:**常规同步把导出范围重写成自己
  那一份**,而且这一条**真走 `pipeline.start_pipeline`**、不用摆盘那个 `_begin`
  —— 要验的正是生产启动路径有没有重写它,拿摆盘替它写一遍就把它挡在射程外了
  (第一版就是这么写的,注入"生产那一行去掉"全绿)。
  摆盘的 `_begin` 因此也要跟着 `start_pipeline` 写一份 `export_filter`:漏掉它的话
  这几组用例会落在生产那条"没设过就回落"的兜底上,而那条只为旧记录存在。
  摆盘里**收尾那一步 `_end_run()` 不能省**:`start_retry_failed` 读的是**落盘的**
  last_run(失败名单也在里面),少了它这一局的前提压根建立不起来(下一步点重试
  只会收到「上次运行没有失败项」)。
  反向验证定点注入十版,各红 1~13 条:按 `last_error` 筛(第 1 轮被审那版的核心)
  红 9 条、整个不收窄红 13 条、**没留下名单的来源也按失败项收窄红 2 条**(所以这套
  用例分得出「两档没分开」和「整个没收窄」)、不打 `force` 红 9 条、名单不带 run id
  守卫红 1 条、名单时刻用本地格式红 2 条、一条都没失败就不记空名单红 2 条、
  `pipeRunScopes` 丢掉 `retry` 红 1 条、export 跟着收窄后的范围跑红 1 条、范围空了
  crawl 仍进计划红 4 条。
  **第 2 轮审查那两条修完之后另注入七版**,各红/错 1~4 条:导出范围从收窄后的抓取
  范围派生(就是第 2 轮被审的那一版)红 1 条 —— 红的正是审查那份证据
  (`3 != 0 : social 那几条文章一篇都没落盘`);导出范围不落盘红 2 条;常规同步不
  重写它红 1 条(`['rss'] != ['social', 'rss']`:上一轮重试那份范围漏进来了);
  启动路径退回被审那一版(顺序 eager + 没有早返回 + try 只护住认名字)红 2 错 2 ——
  其中那条 ERROR 正是审查那份证据(`OperationalError: unable to open database
  file`,也就是 HTTP 500 的根因);只退"先定计划"红 1 条、只退"空名单不开库"红 1 条
  (**两道各有射程,少哪一道红哪一条**);问名单那一下留在 `except` 之外(第 1 轮
  那一版)错 1 条。**注入脚本自己那个坑照旧**:同一个文件注入两三处时用
  `setdefault` 存原文,`saved[rel] = text` 会被后一处读成"已经注入过一处"的版本。

## 跳过的那一步,把今天没补好的事当成已经解决

第 1 轮自由审查 R1 实测两条,都走真实收尾、真实折账:

1. **导出根本没执行。** 同一天先摆一轮公众号导出失败(重试规划 `export → index → extract`),再开一轮只导出、
   让「采集器装好没有」那一问答不可用 —— `WeChatLocalCollector.materialize` 走它自己那条 `skipped` 分支,导出
   子进程一次都没起。折完账:旧失败被 skipped 顶掉,`today_failed=[]`、规划变成 `[]`,再点重试收到一句「上次运行
   没有失败项」。真页面上也是这样:初始页有「1 个步骤需处理」和可点的「重试失败项」,仅勾导出跑完一轮之后重试
   入口消失,**整页刷新也回不来**(原错误还在历史行里看得见,但补不上了)。
2. **整理工具被另一个实例占着。** 同一天先摆一轮整理失败,再真走 `_run_projects`,只把条目化脚本的返回码换成 3
   —— 它报 `skipped / gzh gate: 有手动实例在跑,本轮跳过`,一条条目都没条目化、也没入库。旧 error 同样被顶掉,
   重试被拒。**「另一个任务存在」不是「那个任务一定会成功」的证明。**

来历是一处:覆盖范围报不出来时按计划范围推断,而导出和全库那几步的推断值永远是「整条覆盖」。所以判据立在
**日账结算层**(`_coverage` 那道 `stage_ran`),不是在导出那一处打补丁 —— 同一个形状在每个新的 `skipped` /
`stopped` 出口上都会重新长出来一遍。

## 「只补导出」那一轮,一个来源名都报不出来

第 1 轮自由审查 R1 实页实测:隔离库里摆一条 RSS 原文(翻译错误「模型返回 503」)、留一笔当天的导出失败,开着
「我的订阅 → RSS」(页面写「1 条外文内容还在等翻译」「1 条外文内容翻译失败」),再在另一个标签点「重试失败项」。
那一轮 `export → index → extract` 全绿、接口里 `stuck.failed` 和 `stuck.queued` 都归零、中文标题和正文都回来了,
而**那一页保持打开 37 秒、覆盖至少两次来源轮询,仍然显示旧的失败提示和等待翻译的内容** —— 只刷新整页才看得到
译文。同一刻同步中心写「选择来源后开始一次同步」,本轮历史写「未记录来源」。

真实终态的关键字段:`planned_stages=["export","index","extract"]`、`crawl_filter={"force":true}`、
`export_filter={"channel":"rss","accounts":[]}`。来历是一处:**「整轮来源」这个问题只读了抓取那一份范围**,而抓取和
导出早就是两份了。于是所有消费方同时判错:同步中心那行、历史那一列、订阅页的忙碌归属与结束重读、三个订阅修改端点
共用的那道写保护、合并运行的来源标签。所以判据立在**运行快照 / 来源投影的契约层**(`run_scopes` / `pipeRunScopes`
各一份),不是在「只补导出」这一条触发路径上打补丁。

**历史那一份另有一道**:给人翻的那份记录**故意不存 `export_filter`**(那一份不许喂给重试派生),所以它改为存
**结论**(`run_record` 的 `scopes`)。不许改成把 `export_filter` 存进去 —— 「这一份没有重试派生字段」正是 `scope`
那档欠账的判据(详见 `pipeline-history.md` 第一节)。

交的是点名的那几个或者「整条来源」。**坏法要定点注入**:把「覆盖范围」退回请求范围、或者让某一条
返回路径不交覆盖 —— 整份换回旧版是证明不了的(接口变了满屏 ImportError)。

**「页面说欠的 = 按钮补得到的」那一道要把三种形态各摆一局**(今天成功过之后又失败、失败之后被停用、
失败之后被删掉),**每一局都同时问页面那一份和点一次的回答** —— 只验其中一侧的话,两处各判一遍那个
死局照旧漏得过去。**反过来钉一边**:同一轮里红掉的 index 跟那条订阅毫无关系,它照旧欠着、照旧起得了
跑。两个坏法靠这两组的颜色分辨:「收窄过头」只红反向那一局,「压根没收窄」把三种形态和起跑端那几条
一起带红。这一组的「点一次」**每一步都要打桩,连抓取也打**(理由同下面「拒绝起跑」那一类):判据是
「它起没起跑」,而写错的那一版会真起一轮线程把范围放开成整库 —— 本机的公众号采集器被拉起来跑真子
进程,用例挂在那儿不动,要的那个红压根报不出来。

**「公开问一句」那一档也要有自己的红**:三种形态下 `retry_failed_plan()` 不带参数问出来的也得是空 ——
只验状态端和起跑端的话,缺省那一档留着旧口径没有任何一条用例会红。**那几局摆的是「同一刻问三处,答案
必须一样」**,所以每一局都同时问页面那一份、点一次的回答,外加单独问一句的那个答案。

**拿计划当判据要小心它现在多问了一层**:批次合并那几局钉的是「合并没把那条红抹掉」,而
`retry_failed_plan()` 不带参数现在还要问一句「那几条订阅现在还抓不抓得到」—— 摆盘里那份失败名单点的是
一条压根不存在的订阅,于是那几局的颜色会跟着**共用那个库里恰好有没有这条订阅**变,而要验的那件事压根
没被验到。那几局因此改成两问:账本上那一笔还在不在(纯的,不碰订阅库),加上链按合并后那一轮派生得出来。

**内存欠账那两桶各有自己一局**:旧日那一桶扫得掉(而且不许把它的红搬进今天)、今天那一桶扫不掉
(只验前者的话,一个「一律清空」的实现也全绿 —— 而那正是漏报)。

**记账单位那一组要把「同一条通道里的两条订阅」分开摆**:只验「RSS 失败、公众号成功」那一组时,
按通道记和按目标记两种实现都全绿 —— 分得开它们的只有**同一条通道内**那几局(只跑 B、整通道跑一遍、
整通道失败留下名单)。**缺口那两道(内存里那笔、盖最近那一轮)各自注入一次都要有红**:两道都在时
任何一道单独失守都被另一道兜住。
判据落在**后果**上:名单被摘空没有 / 抓取请求发了几个 / **拒绝之后 `load_last_run()` 那份留档
是不是一字未动**。反向验证定点注入十一版,各红 1~3 条:当日继承整条不做、有过成功就继承(跨天也
摘)、日界按 UTC 算、读不懂的时刻算成过、不带时区的时刻算今天、整道拦路闸不做、问不出来就拦、
有一个抓不动就拦、只报第一个抓不动的、拦住之前先改状态、这一轮不抓东西也要问一遍。

**逐来源隔离那一道的红在 `tests/test_sync_channels.py`**(准备阶段炸了,勾着的其余来源照样跑完、
面板上看得出是谁挂的)。**反向验证要把建账那一下放回隔离外面才复现得了** —— 只把外层那个 try 去掉
是红不出来的:那时建账还在内层 try 里,隔离照旧有效。

**范围就绪那一组要摆出「同一条来源里一个坏一个好」**:A 不填专用订阅链接(内容走 X 通道)、B 填上
(跟通道无关),只把「X 通道现在配好没有」换成定值 —— 整条 `configuration_error` / `in_scope` /
`status` / 闸一行不打桩。打桩那道闸本身的几组用例也得**像真采集器那样把范围内那几条报回
`targets`**:报空的那一下会被闸按「一条都没对上」放行,验的就不是"拦路的还拦着"了;签名不认
`targets=` 那个参数同理 —— 抛出来的 TypeError 被「问不出来一律放行」吞掉,**打桩静默穿不过去**。

**日界那条必须定点摆时刻才测得出来**:别的用例全在白天跑,UTC 日期和项目时区日期恰好相同,拿
UTC 日期比也一样绿 —— 所以 `_succeeded_today` 收一个 `now` 参数,用例把「北京 06:00」和「昨天
上午那次成功」摆在那条缝里。

**「拒绝起跑」那一类用例要把后面几个阶段打桩掉**(`refuse()` 里那几道)。不打桩的话,反向验证时
一条「闸不做」的注入会让那一轮真去索引整个 vault,看起来像卡死而不是像红。

**「没有失败项就拒绝起跑」这一类还要自己摆出「没有提取积压」那个前提**(`no_backlog()`)。计划空
下来之后 `retry_failed_plan` 会问一句 vault 里有没有没提取的文档,而那一问读的是**共用的**
`KB_DATA_DIR/kb.db` —— 本仓库任何一次真索引都会往里添文档,于是这一类用例的红绿取决于别人留下的
库存(2026-10-19 实测:一次误跑的真索引让两条存量用例当场变红,而红的地方跟改动毫无关系)。
