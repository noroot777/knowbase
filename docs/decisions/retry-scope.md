> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束(原 CLAUDE.md「「重试失败项」的范围(kb/pipeline_retry.py + feeds/sync.py + pipeline_state.py)」)

- **这颗按钮的范围 = 继承上一轮的「来源」+ 各来源自己留下的失败名单**(`retry_crawl_scopes`)。继承的是「哪几个
  channel、上次点名了哪几个目标」,**不是「抓多少东西」** —— 后者按**来源逐个**收窄,外加一个 `retry` 字段说明这一项
  是怎么来的(`targets` / `all`)。
- **不收窄的两个缺口是反着的**:①继承来的 `accounts` 是空的,而空在 `sync.collect` 里正好是**全部**;
  ②`FetchScope.force` 这条路上压根没人传过,而失败恰恰会记一个 `retry_at`。
- **名单要在失败那一刻记下来,不能事后从别处反推**(`note_retry_targets` 写、`retry_notes` 读):按 `last_error` 筛会
  漏掉「已改正、还没验证过」的;从阶段状态那份 failures 反推拿到的 `title` 对公众号来源是文章标题;一个全局布尔会让一
  个来源的失败类型决定另一个来源抓多少。
- **必须按来源各记一份,因为「整批失败」和「只坏了一条」是两件相反的事** —— 两者在 `subscriptions` 那边长得一模一样,
  **分得开它们的只有「这个来源留下名单了吗」**。
- **「仍然需要重抓」的判据是「那一轮失败之后有没有成功同步过」**(`sync.still_failing`)。**名单的时刻要用采集器自己那
  套时间格式**(UTC ISO,不是本地空格格式)—— ISO 的 `T` 排在空格后面,整份名单会被摘空。`at` 因此是**必填**的。
- **一条都没失败也要记一份空名单**(那份空名单本身就是「这个来源扫完了」,而「压根没留下名单」另有含义)。名单**带着它
  自己那一轮的 run id**。
- **报不出名单的来源按原范围重跑**(`collectors.RetryNarrowing`)。**这不是缺陷,是另一种真实情况**(公众号的失败是文章
  级的,而它的 targets 是账号级的)。生成计划这一步**不许抛**。
- **「这个来源一个都不用抓」= 整个来源不进这一轮,不是给它一个空 `accounts`**:全空时走
  `retry_failed_plan(nothing_to_crawl=True)`,crawl 整个摘出计划。
- **export 走上一轮**原来**那几个来源,不跟着 crawl 收窄**,而**「原来那几个来源」必须自己落一份盘**(`pipeline_state`
  的 `export_filter`,三处写入口)。**常规同步那条路要把它重写成自己那一份**,不靠「没设过就回落」兜底。
- **造范围这一步的故障不许扩散到别的阶段上,三道各有射程**:①**先定计划,只有 `"crawl" in plan` 才去问名单**;②**认名
  字和问名单一起护在那道 `except` 里**;③**名单是空的就别开库**。
- **收窄要和 `targets` 取交集**,不是扫一遍库里所有失败的订阅。**「预算跳过」和「退避中」那两档不进名单**(压根没被尝
  试过,下一轮轮转本来就会补齐)。
- **没有要重抓的时要说清为什么、并指到正确入口**(`RETRY_NOTHING`,crawl 落 `skipped`)。
- **收窄过的那一轮要把范围说出来,而且按来源各说各的**(`pipeRunScopes` 透传 `retry`)。
- 详细见 `docs/decisions/retry-scope.md`。

## 事故形态与实测证据

- **这颗按钮的范围 = 继承上一轮的「来源」+ 各来源自己留下的失败名单**
  (`retry_crawl_scopes`)。继承的是「哪几个 channel、上次点名了哪几个目标」,
  **不是「抓多少东西」** —— 后者按**来源逐个**收窄,结果写成那个来源自己的
  `accounts`,外加一个 `retry` 字段说明这一项是怎么来的(`targets` = 收窄到了失败
  的那几个 / `all` = 这个来源收窄不了,按原范围重跑)。
- **不收窄的后果实测过,而且两个缺口是反着的**(2026-10-09 用户报告:大V观点同步
  时一个账号地址填错导致那一条失败,改好之后点「重试失败项」,51 个账号的时间线
  全被重新读了一遍):
  ①上一轮是「同步大V观点(全部)」,继承来的 `accounts` 是**空的**,而
    `sync.collect` 里空的含义正好是**全部** —— 一个账号填错地址,换来整条通道
    十几分钟的重读 + 白攒的账号风险,而真正该重试的那一条和别人没有任何区别;
  ②`FetchScope.force` 的注释从一开始就写着「手动重试可跳过来源退避」,可**这条
    路上压根没人传过它** —— 而失败恰恰会给那条订阅记一个 `retry_at`(最短 1800
    秒,见 `sync._save_failure`),于是失败后的半小时内点这颗按钮,唯一该抓的那条
    被记成 `deferred` 跳过。合起来就是「该抓的不抓、不该抓的全抓」。
  用户这一次没撞上②,是因为改链接时 `save_subscription` 的 `reset` 把 `retry_at`
  一起清成 0 了。
- **名单要在失败那一刻记下来,不能事后从别处反推**(`pipeline_state.note_retry_targets`
  写、`retry_notes` 读,`sync.collect` 收尾时调一次,跟着 `last_run` 一起落盘)。
  三条反推的路各自不成立:
  ①**按 `last_error` 筛**:改链接时 `save_subscription` 的 `reset` 把它连同退避
    一起清空,于是「已改正、还没验证过」的那条被当成「已经恢复」漏掉 —— 用户修完
    地址点这颗按钮,那个账号一条也不抓,而那正是原始需求那一局(第 1 轮审查实测);
  ②**从阶段状态里那份 failures 反推**:项里的 `title` 对订阅来源是订阅名,对公众号
    来源却是文章标题和「推送归属待核实」这类句子(见 `wechat_local._report`),拿它
    当目标名传下去那一侧一个都匹配不上;多来源时那份明细还是**扁平合并**的、项里
    不带来源归属(`_merge_segments`),想按来源各取各的还得先给每项打上归属;
  ③**一个全局布尔**:那是第 1 轮被审那一版 —— 它让一个来源的失败类型决定另一个
    来源抓多少东西(见下一条)。
- **必须按来源各记一份,因为「整批失败」和「只坏了一条」是两件相反的事。**
  一条订阅自己抓不动 → 名单里有它,下一轮只抓它;整个来源这一轮压根没开工(登录态
  读取器崩了、采集器抛异常)→ `collect` 整个抛出去,那时**一条订阅都还没被碰到**,
  也就没有名单可言,这时该重抓**整个来源**。两者在 `subscriptions` 那边长得一模一样
  (都是一个 `last_error` 都没有),**分得开它们的只有「这个来源留下名单了吗」**。
  全局布尔的实测后果:大V整批失败 + RSS 一条逐项失败那一轮,两个来源都按失败项
  收窄,而大V一份名单都没留下 → 收窄成空集,恢复连接之后点重试它一条也不抓,
  面板上还不再显示需要处理的失败(第 1 轮审查第 2 条)。
- **「仍然需要重抓」的判据是「那一轮失败之后有没有成功同步过」**(`sync.still_failing`:
  `last_success` 比名单那一刻新就摘掉,订阅被删、停用、id 压根不存在的一并摘掉)。
  改过链接的那条 `last_success` 被 `reset` 清成了空串,所以它留在名单里 —— 这正是
  ①那条路换掉的东西。同一秒分不出先后时按「还要重试」算(保守多抓一次)。
- **名单的时刻要用采集器自己那套时间格式**(订阅那边是 `reg.now()` 的 **UTC ISO**,
  不是 `pipeline_state._now()` 的本地空格格式),所以 `note_retry_targets` 的 `at`
  是**必填**的 —— 少传一个参数当场报错,比悄悄用错格式好。ISO 的 `T`(0x54)排在
  空格(0x20)后面,同一天里 ISO 那个恒大于空格那个,于是「它后来成功过吗」会一律
  答成「是」,整份名单当场被摘空、这颗按钮变成「什么都不抓」。
- **一条都没失败也要记一份空名单。** 那份空名单本身就是「这个来源这一轮扫完了、
  没有要重抓的」这句话,而「压根没留下名单」另有含义(整批失败,按原范围重跑)——
  不记的话两者再也分不开,一个全程顺利的来源会被当成整批失败重抓一遍。
- **名单带着它自己那一轮的 run id**(`retry_notes` 身份对不上一律当成「这一轮没有
  名单」)。整批失败那一轮一份名单都没留下,而 `_state` 里还躺着**更早**那一轮的
  名单、会连同这一轮的状态一起落盘 —— 照它收窄就是按上一轮的失败去抓。带着 run id
  所以不必在每条启动路径上各清一次。
- **报不出名单的来源按原范围重跑**(`collectors.RetryNarrowing` + `retry_narrower`,
  不支持这个能力的采集器没有这个方法)。**这不是缺陷,是另一种真实情况**:公众号的
  失败是文章级的,而它的 `targets` 是账号级的,压根对不上(正文重试本来由它自己的
  `article_fetch_state` 退避管)。来源名现在认不出来了(改名/退役)同样走这一档,
  而且**生成计划这一步不许抛**到 HTTP 层 —— 那会把同一轮里本该重试的 index/extract
  一起带走(同 `refill_script` 那条"永不抛"的理由)。
- **「这个来源一个都不用抓」= 整个来源不进这一轮,不是给它一个空 `accounts`。**
  `accounts` 空的含义是「全部」,两者正好相反,而这条路上搞混的代价就是上面那场
  事故。所有来源都空了的时候走的是 `retry_failed_plan(nothing_to_crawl=True)`:
  crawl 整个摘出计划 —— 范围是空的,真让它跑,`crawl_channels` 会按「没指定来源」
  回落到默认采集器,抓的是另一个来源。
- **export 走上一轮**原来**那几个来源,不跟着 crawl 收窄**(`_run_retry_failed` 收
  `crawl_filter` 和 `export_filter` 两份)。两者的失败是各自的:一个来源完全可能
  crawl 成功、export 失败(翻译扣着不导出、vault 写不进去…),跟着 crawl 一起被
  摘掉的话它那一步就再也没人重试了。
- **而「原来那几个来源」必须自己落一份盘**(`pipeline_state` 的 `export_filter`,
  三处写入口:`_state` 的默认值、`_save_last_run`、两条启动路径各写一次)。只传给
  当次那个线程、只把**收窄后的** `crawl_filter` 落盘的话,这条口径只在**第一次**
  重试上成立:第二次重试又从那份收窄范围派生一次导出范围,于是第一次重试里**仍然
  导出失败**的那个来源就此被摘掉 —— 面板报「导出完成 · 已保存 0 条」,而它那几篇
  文章一个都没落进 vault,再点重试也不会回来(2026-10-09 第 2 轮审查实测:两个
  来源同一轮,social 的导出位置被占住,第二次重试只导出了 rss,social 那 3 条
  一篇 md 都没有)。
  **常规同步那条路要把它重写成自己那一份**(`start_pipeline` 里显式
  `"export_filter": deepcopy(crawl_filter)`,不靠"没设过就回落到 crawl_filter"
  兜底 —— `_state` 是模块级常驻的,上一轮如果是重试,里面躺着的是那一轮的导出
  范围,不覆盖的话这一轮的落盘会把它原样带走)。回落只给升级前那些没有这个
  字段的旧记录用。
- **造范围这一步的故障不许扩散到别的阶段上,三道各有射程。** 这颗按钮的射程远不止
  抓取,而问各来源的失败名单要读那个来源自己的订阅库:
  ①**先定计划,只有 `"crawl" in plan` 才去问名单**(`start_retry_failed` 里
    `scopes = retry_crawl_scopes(prev) if "crawl" in plan else []`)。无条件先问
    一遍的话,上一轮只有 index 失败、这会儿订阅库又恰好打不开(锁着、权限、路径
    没挂上)时,那个异常一路冒到 HTTP 层 —— 用户收到一句「Internal Server Error」,
    索引和后面的提取一步都没起跑(2026-10-09 第 2 轮审查实测)。**这一道和采集器
    无关**,所以它必须自己有一条用例。
  ②**认名字和问名单一起护在那道 `except` 里,故障只圈在这一个来源里**
    (`retry_crawl_scopes` 的 try 要罩住 `narrower.retry_targets(note)`,不只罩住
    `active_collector`)。问不出名单 = 这个来源收窄不了,按原范围重跑。
  ③**名单是空的就别开库**(`sync.still_failing` 的 `if not ids: return []`)——
    答案只能是空集。这一道是 feeds 这个采集器自己的早返回,换一个无条件读自己库的
    采集器就不成立了,所以它和 ① 不是一件事的两种写法。
- **收窄要和 `targets` 取交集,不是「扫一遍库里所有失败的订阅」。** 上一轮可能只
  同步了用户在订阅页勾的那三条,重试不该把上周留下的另外五条失败订阅一起拖进来。
  交集就在名单自己身上 —— 它记的是**这一轮**真失败过的那几条。
- **「预算跳过」和「退避中」那两档不进名单**,这是有意的:它们压根没被尝试过,
  本来就会在下一轮同步里按 `last_attempt` 轮转补齐(见 `collect` 里那句
  pending.sort),水位一个字没动,不该借这颗按钮把整个来源再抓一遍。
- **没有要重抓的时要说清为什么、并指到正确入口**(`pipeline_retry.RETRY_NOTHING`,
  crawl 那张卡片落 `skipped` 并写上它)。原来它把整个来源重抓一遍、面板上还是一张
  绿卡片,和「这个按钮坏了」长得一模一样。真想重抓某一条的入口是「我的订阅」里的
  单条同步(`POST /api/intake/{kind}/sync` 带 `source_ids`,它本来就带 `force`)。
- **收窄过的那一轮要把范围说出来,而且按来源各说各的**(`pipe_channels.js` 的
  `pipeRunScopes` 把 `retry` 透传给前端,`pipe_view.js` 那行「本次范围」照它说话:
  `targets` 写「仅重试失败的 N 个订阅」,`all` 照原范围写)。给所有来源一律写
  「仅重试失败项」是一句谎话 —— 它承诺了报不出名单那个来源并没有发生的收窄;
  照 `accounts` 一律写「全部订阅」也是,那正是刚被修掉的那个行为。
- **这颗按钮和「上一轮还没结束」无关。** 前端在 `running` 时就把它 `disabled`
  (`pipe.js`),后端 `start_retry_failed` 还在 `_lock` 里撞 `_state["running"]` 返回
  409「管道已在运行中」—— 它能真的起跑,说明上一轮已经收尾了。
- 回归分两个文件 + 一份共用摆盘(`tests/retry_scope_fixture.py`),**判据一律是
  「哪些目标真的被碰了」** —— 数 `fetch_source` 收到的订阅 id、以及预取收到的账号
  名单;只验「有没有打上标志」的话,一个把标志传下去却没人认它的实现也能全绿。
  `tests/test_retry_scope.py`(23 条,单来源):一条地址错了只抓它而另两条一次请求
  都没发、**改正地址之后那一条照样被重抓**(第 1 轮拦验收 1 的复现,还断言条目
  真的是按新地址抓回来的)、以前好着这一轮才坏的照样抓(**钉住时间格式混用那个
  坑**)、退避里的失败订阅抓得到、不扩大到上一轮没点名的历史失败订阅、普通同步
  **带 force 也不许收窄**、都修好了就拒绝起跑且文案点名「我的订阅」、范围空了不许
  回落到默认采集器、crawl 那张卡片说得出这一轮为什么是空的;外加
  **来源级整轮故障照旧全量重抓**(反过来还钉一边:留下了名单的那一轮照旧收窄 ——
  两条合起来才说明判据是「名单在不在」)、直测 `still_failing` 四种情况、名单那条链
  的契约(空名单也要记 / 陈旧名单不作数 / 换届重开一份 / 报不出名单的来源连名单硬
  塞给它也按原范围重跑)。
  **启动路径那一组**(`StartupIsolationTests`,把订阅库换成一个**目录**让
  `sqlite3.connect` 真抛 —— 指到一个不存在的目录骗不过 `reg.db()`,它自己会
  `mkdir(parents=True)`):只重试 index 时坏库不拦路、索引和提取真的起跑了
  (**后果那一条**,复现审查那份 500;它要 ①③ 同时失效才红,所以 ①③ 各自另有
  一条)、`"crawl" not in plan` 时**一次名单查询都没发生**(判据是**问了几次**,
  不是"抛没抛异常" —— 那道 `except Exception` 把 AssertionError 也一并吞掉,拿
  一个会被吞掉的异常当判据,这条用例对顺序压根不敏感)、空名单直测不开库、
  **名单问不出来时那个来源退回原范围**而不是收成空集、也不把整次重试带走。
  `tests/test_retry_multi_source.py`(9 条,多来源 + 面板):**一个来源整批失败、
  另一个只坏了一条时各按各的范围重试**(第 1 轮拦验收 2 的复现)、反过来钉一边
  (两个来源都是逐项失败时两边都收窄)、已经没有要重抓的那个来源整个不进这一轮、
  **export 收到的是原来那两个来源**、**登录态通道只重读失败那一个账号的时间线**
  (判据是**预取**收到的 handle 名单 —— 用户真正付的代价在那一步,而这条通道在
