# 软广筛选(kb/extract.py 的 promo)

> 从 CLAUDE.md 外移的决策记录。CLAUDE.md 只留硬约束和一行指针,
> 这里是完整的事故形态、实测证据、回归清单和反向验证红数。原文逐字搬运。

- **判定搭在提取阶段,不单开一个 LLM 阶段。** 提取是「每篇原文各跑一次、覆盖
  所有非 pre_tagged 来源」的唯一一步,正文已经在 prompt 里了,多要一个 promo
  字段只多几十个输出 token;单开一步等于把同一篇正文再买一遍。喂进去的正文
  总量没变(还是 6000 字符),但改成**头 4800 + 尾 1200**——软广的转化钩子
  (注册地址、「阅读原文领取」、推广落款)基本都在文末,只截开头一个都看不到。
- **三档 none/soft/hard,只有 hard 被当成广告处理。** 公众号里大量内容是
  「厂商自家通稿」「带返利链接的推荐」,它们有推广性质但技术信息仍然有用,
  落 soft 保留;hard 才是「整篇买下来卖一个产品」的投放稿。判定认不出时一律
  落 none:错杀会让一篇正常文章连同它的实体从条目化和检索里一起消失,漏判
  只是留着一篇广告。
- **hard 的两条边界是拿真实样本调出来的,别删**(2026-09-16 随机采样 50 篇时
  各抓到误杀):①**只看正文主体,不看文末的固定推广位**——GitHub猿 这类号每篇
  文末都挂代充值广告,不写清楚模型会因为那条尾巴把正经资讯文判成 hard;
  ②**推广对象是开源项目时一律不判 hard**,最多 soft——号主把一个 4.3K Star 的
  开源项目吹上天、顺带拉群,那是这类号的文风,不是买量投放。修完这两条,
  13 例定向回归(含 5 个已知真软广)全部符合预期。
- **口径只有一份**(`_PROMO_RULES`),提取阶段的完整 prompt 和存量补判的轻量
  prompt 共用它;两处各写一份的话标准会各漂各的。
- **消费方一律读 `documents.promo_level`,不要各自再判一遍**:条目化 gate 读到
  hard 直接否掉(省的是 gate + transcribe 两次调用,后者是最贵的一步);
  检索(`search.Filters.exclude_promo`)和枚举(`aggregate`)默认挡掉 hard。
  **软广子句不进 `_filter_sql`**:后者的返回值还被 `_vec_leg` 用来判断「召回有没有
  被缩到小子集」(有就把 KNN 候选放大到 4000),混进去会让每一次普通检索都误判。
- transcribe 那一侧**按当前判定再拦一道**:存量补判之前 gate 已经放行过一批,
  那些 state 记录还是 `project_article=true`,只看 state 会拿全文去拆投放稿。
- **hard 原文的衍生条目(`dr-gzh-projects`)按 `url` 一起挡掉**,口径只有
  `store.promo_exclude_sql()` 一份,检索和枚举都调它。只挡原文的话,拆出来的
  条目仍然带着广告产品的实体留在库里(2026-09-16 第 1 轮审查发现)。里面那句
  `pm.url <> ''` 不能省:库里几十篇没有 url 的文档会互相匹配上、集体消失。
- **`flag/软广` 是双写的:DB 的 `doc_tags` + md frontmatter,两边都得跟着判定走。**
  `doc_tags` 每次 `upsert_document` 都按 frontmatter 重建,只写库的标记下次
  重索引就没了(第 1 轮审查发现);反过来,hard 改判成 none/soft 时 md 里那行
  也必须摘掉(`remove_writeback_tag`),否则重索引又把误判带回库里
  (第 2 轮审查发现)。`save_promo` 返回「上次是 hard、这次不是」的信号,
  提取流水线和 backfill 都据此调 `sync_promo_tag`;回写改了文件就同步
  `refresh_content_hash`,免得下一轮 index 白白重建这批文档。
- **提取有三条路,tag 回写只能有一份实现**(`extract.writeback_extraction`):
  管道 `_extract_pass`、`kb extract --writeback`、`scripts/extract_parallel.py`
  (后者自称与前者等价)。原来三处各拼各的 tag 列表,软广同步只接进了管道,
  另外两条一条写不进 md、一条改判摘不掉,第 1、2 轮防住的漂移原样留在旁路上
  (第 3 轮审查发现)。`PROMO_TAG` 在 slug **之后**追加——它已经是最终形态,
  跟着 topic(`_topic_slug`)/entity(`_tag_slug`)过一遍会被改写成别的 tag。
- 存量补判走 `scripts/promo_backfill.py`(scan/run/report),只判软广、不重跑
  整套 extract,并按「标题 + 正文长度桶」**同稿归组**:8857 篇存量里有 2357 篇
  是同一份稿子的副本(克隆号互转、代充值广告同一个号发了 177 次),每组只判
  一篇、结论广播给同组。归组键带长度桶是因为光看标题会把「量子位编辑作者招聘」
  这类撞名的不同文章判成同一篇。补完一次 `promo_level=''` 就不再有新增。
- **soft 是「留着 + 降权 + 打标」,不是第二个 hard。** 检索里乘一个系数
  `search.SOFT_PROMO_WEIGHT`(0.85)。RRF 的分数全挤在窄带里,乘系数约等于
  **平移名次**:大致往后挪 `(1/w - 1) * (RRF_K + 1)` ≈ 11 名——同分的中立文章
  能排到它前面,一篇明显更相关的 soft 不会被赶出去。要调松紧改这一个数,
  别动 `RRF_K`(那是两路融合的量纲)。
- **降权必须在截断 top_k 之前做。** 排完再降只是在这 k 篇里换位置,被压下去的
  soft 仍然占着名额,排在 k+1 的中立文章永远补不上来。所以 `search()` 里先
  `effective_promo_levels` 拿到全部候选的档位、算完加权分再截断;`Hit.score`
  报的是降权后的分,报原分会让列表里出现「下面一条分数更高」。
- **「有效档位」只有一份口径**(`store.promo_level_sql` / `effective_promo_levels`):
  自己判过用自己的,没判过(条目化衍生条目永远是空的)按 `url` 从原文继承,
  同 url 多篇取最重的一档。这和 `promo_exclude_sql` 挡 hard 时的回溯是同一条
  关系——只标原文的话,一篇 soft 拆出来的工具条目在搜索和引用里仍然干干净净。
- **打标要覆盖四个展示面**:搜索结果(`Hit.promo_level` → `/api/search`)、
  问答引用(`askflow`/`askagent` 的 refs)、图鉴卡片与时间线。前端统一走
  `core.js` 的 `promoBadge()`,别在各处各判一次 level。
- **图鉴是唯一不走 search/aggregate 的面**:它按 vault 文件聚合(那个「每工具
  多来源记录」的粒度只有文件层有),所以统一排除口径覆盖不到,hard 投放稿拆出
  的条目原来照样在图鉴里占一行。`projects._apply_promo` 补这一道:**过滤放在
  分组之前**(提及次数/号数/首末时间都按条目算),查库失败就降级成「全部保留、
  不打标」,不让图鉴因为库的问题整个打不开。
- **图鉴的缓存签名必须带上软广状态**(`projects._promo_sig`)。原来只看条目文件
  的数量和最大 mtime,可补判改的是**原文**那一行 `promo_level`,衍生条目文件
  一个字节都没动——签名不变、缓存不失效,于是「跑完 backfill 刷新图鉴,刚判
  成 hard 的工具还在原地」,除非重启 kb-web(第 1 轮审查发现)。签名取的是
  **逐篇 (path, promo_level, url) 的摘要,不能是聚合量**:分档计数 + MAX(promo_at)
  在「两篇同一秒对调 hard/soft」时逐字相同,可该显示的卡片已经换了一张
  (第 2 轮审查发现);`promo_at` 只到秒,一轮 backfill 六个并发同秒改判很常见。
  摘要里带 url 是因为继承关系按 url 回溯;不带 promo_at——它变而结论没变时
  本来就不需要重建。开销量过:1888 篇已判文档 8.0 ms,同一次请求里
  `_scan_sig` 扫 10213 个条目文件要 70.8 ms,只占一成。取签名和重建共用一条
  连接,否则每个图鉴请求要多付一次 connect(里面有 sqlite_vec 扩展加载)。
