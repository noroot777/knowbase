# 软广筛选(kb/extract.py 的 promo,落库与交付在 kb/extract_promo.py,回写在 kb/extract_writeback.py)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证红数。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。

## 硬约束(原 CLAUDE.md「提取阶段的两道判定(kb/extract.py 的 promo 与 body_gap)」)

- **软广判定搭在提取阶段,不单开一个 LLM 阶段**(正文已经在 prompt 里了)。喂进去的是**头 4800 + 尾 1200**(转化钩子基本都
  在文末)。
- **三档 none/soft/hard,只有 hard 被当成广告处理。** 判定认不出时一律落 none —— 错杀会让一篇正常文章连同它的实体从条目化和
  检索里一起消失。**hard 的两条边界是拿真实样本调出来的,别删**:①只看正文主体,不看文末的固定推广位 —— **但「借壳」是它的
  例外**;②**推广对象是开源项目时一律不判 hard**,最多 soft。**口径只有一份**(`_PROMO_RULES`),完整 prompt 和存量补判的轻量
  prompt 共用。
- **「借壳」判 hard:正文整篇搬别人的稿当壳、文末接一段代充值/代开会员/卖号/中转站额度的交易。** 边界①放过的是「这个号自己
  写的东西 + 它每篇都挂的加群课程尾巴」,不是这个。**判据落在那段推广自己在卖什么,不落在正文多正经、也不落在出现过「充值」
  两个字**:要有具体对接方式(微信号、二维码、落地页)加上「办理/代充/代开/续费」的动作。**反面要连同口径一起写进 prompt,
  少一条就误杀**——正文在报道中转站泄露事件、介绍镜像源监控项目、拿「中转站」作比喻(「学术走向产业的中转站」「人肉中转站」)、
  文末那串是本号历史文章导航而某条标题带「怎么买、怎么充值」、正文在讲官方订阅档位怎么选、文末只是加本号社群或加作者好友
  (哪怕写了「加微信」),全都不算。
- **补判的同稿归组键是「喂给模型的那三样逐字相同」:账号 + 标题 + 正文,直接用 `extract.input_fingerprint`。** 组内任一篇的
  prompt 和代表篇一个字节都不差,
  所以广播结论不是推断 —— 问的是同一个问题。**长度桶这种近似判据不许当成共享结论的依据**:一个号把「每日资讯」当标题反复用
  是合法输入,广告段有没有也可能只差几十个字,于是两篇不同的文章落进同一个桶,带交易段那篇判出的 hard 被广播给另一篇正常
  教程 —— 那篇连实体带条目一起从检索和图鉴里消失,而脚本报的是「软广 ×2」。反过来的组合一样坏:代表篇是正常稿时,另一篇的
  已有 hard 会被盖成 none。**正文不做空白规范化、长度也不入键**:折叠空白能多并掉几组,但 `clip_body` 的截断点会跟着空白数
  漂,喂进去的内容未必还相同 —— 漏并一组的代价是一次调用(约 $0.004),并错一组的代价是一篇正常文章被永久隐藏。账号和标题
  留在键里不是为了「证明同稿」,它们本来就是 prompt 的一部分(判定要看「这个号在卖什么」)。**「两篇喂给模型的是不是同一组
  输入」这个判据只有一份**:归组和落库校验(`_input_moved`)比的是同一个函数 —— 各算一遍的话,这边认为"同一组、可以共用答案",
  那边认为"不是同一组、这个结论作废",广播出去的判定全被拦在门外,而脚本报的是「软广 ×N」。
- **`--recheck`(重判已判过的)必须配 `--account`。** 守卫在 `_scope_args`,不在 SQL 里 —— 越早拦住越不会「跑了一半才发现范围
  错了」。`accounts` 传空列表当「没给」:解释成「哪个号都不要」的话,一次参数失误会静默变成「一篇都没判」而脚本照旧报成功。
  **不给 `--recheck` 时取数范围一个字不许变**,否则每轮管道的存量补判会把全库判定重跑一遍。
- **重判这条路上两道闸,缺哪一道都是「把判出来的 hard 静默擦成 none」。** 方向和首次补判相反:首次写错了下一轮还救得回来,
  重判是**去覆盖一个已有结论**,擦掉之后 `extracted_at` 还在、`pending_docs` 是空的,再同步多少轮也不会自己纠正。
  ①**没拿到合法 level 不许当成「不是广告」**:`normalize_promo` 的「认不出落 none」兜底只对首次判定成立,重判要开
  `judge_promo(require_verdict=True)` —— 拿不到就抛、整组记失败、旧结论一个字不动。**反过来钉一边:模型明确说 none 时照旧改判、
  照旧摘 flag**,不然这道闸就成了「hard 再也改不回来」。②**旧正文的判定不许盖掉新正文的结论**:判据钉在 `save_promo` 那条
  UPDATE 自己的 WHERE 里(`content_hash`),而喂给模型的那三样(标题、账号、正文)和它们所属的那一版从
  `store.doc_input_snapshot` **一条语句**里取 —— 分两次读的话,两次之间的索引可以把这一篇换版,候选里就成了旧标题配新正文,
  而条件写拿到的是新版本号、照旧放行。0 行 = 这期间换版了 = 这一轮跳过。
- **判定、`doc_tags`、md 那行必须在同一个协调区间里对齐**(`extract_promo.commit_promo`)。形状和提取那三条路的
  `commit_extraction` 一样:模型请求留在锁外、交付在维护锁内、进锁之前先 flush(锁序是维护锁 → SQLite 写锁,反过来会把持锁的
  清理卡死)、锁内先问一次这一篇还在不在(`doc_tags` 对 `documents(path)` 是外键,等锁期间被清理掉就得安静跳过)。粒度按篇 ——
  整趟几千篇要跑几十分钟,圈起来等于攥着锁等几十次模型往返。**落库在锁外、只有摘 md 那一下在锁内的话,中间插进一次完全合法的
  索引就会把改判毁掉**:`upsert_document` 不碰已经是 none 的 `promo_level`,却按**还没摘**的 frontmatter 把 `flag/软广` 重新
  插回 `doc_tags`;随后的回写只摘 md、不再回头清库里那行,还顺手把 `content_hash` 刷成当前文件的,于是下一轮索引报「未变」
  直接跳过 —— 错的那行**永久**留在库里,普通检索正常、`promo_level` 是 none,唯独按 `flag/软广` 过滤仍然捞得到这篇已经纠正
  为正常内容的文章。
- **判定针对的那组输入(标题 + 账号 + 正文),必须同时是「索引里那组」和「磁盘上那组」—— 三者同一才允许固化,而且这道判据
  要落在落库之前。**
  `version_seen`(= `documents.content_hash`)只证明**索引记录**没换版,证明不了磁盘上那份 md 还是模型读过的内容:导出和索引
  各自取锁、按两个阶段依次调用(`feeds.sync` → `pipeline_stages`),一次补判完全可以插在两者之间 —— 那时磁盘上已经是新正文、
  chunks 和 `content_hash` 还是旧的,条件写照旧放行。所以 `commit_promo` 在锁内、落库之前两道一起问:
  ①`disk_input_indexed`(磁盘上那组输入进索引了吗)②`_input_moved` 关掉第一道(索引里那组换版了吗)。
  **拦下来就是一个字都没写** —— 库里和 md 里仍是原来那份判定、彼此一致,下一轮等索引跟上再判。
- **「磁盘上那组输入进索引了吗」的判据是模型输入那三样 —— 既不是整个文件的 hash,也不止正文。** 拿整文件 hash 会把「只改了
  别的 frontmatter 字段」(翻译回写 summary、tag 回写、wiki 追加图谱尾区,都是常态)算成"没进索引",于是一次输入压根没动的合法
  改判被拦掉;**反过来只比正文也不够** —— 模型请求在途时磁盘上的标题被换掉(正文一个字没动)是常态,放行就把旧标题下判出的
  hard 固化到新标题上:文章在界面上已经是另一篇,却带着别人的广告判定被永久隐藏。所以 `disk_input_indexed` 三样各走索引自己
  那条路:标题和账号按 `scanner.frontmatter_input` 读(**和索引 upsert 进库的同一份口径**),正文按 `normalize_body` →
  `split_chunks` 过一遍(**和 `cli.cmd_index` 同一对函数**)再和库里比。**和提取那三条路的差别别照抄**:它们拿整文件 hash
  当判据、作废整份结果是安全的(下一轮 `pending_docs` 会把这一篇再提一遍),而补判一旦 `promo_level` 非空就再也不进默认候选,
  作废 = 永久漏摘。
- **`refresh_content_hash` 不许替别人那份还没索引的改动签一张「已索引」的收据。** 它写的是「这个文件索引过了」—— 而
  `content_hash` 就是索引判「要不要重建」的唯一依据。回写之前文件就已经和库里记的不一样(别人刚改完、索引还没跟上)时,无条件
  刷新会让 `doc_needs_reindex` 从此说「未变」,那份改动永远进不了 chunks。所以带 `expect`(= 我动手之前读到的那份文件 hash)的
  条件写,**判据待在 UPDATE 自己的 WHERE 里;0 行不是失败**,正是想要的末态 —— 这一篇继续带着「待索引」。
  **`expect` 没有默认值,也不许再加一个无条件分支。** 原来那个分支留给两个「自己刚写完这个文件、紧接着刷」的单线程脚本
  (`backfill_youtube_summaries`、`wiki/wiki_daily`),理由是它们手里没有动手之前那个值 —— 可那个值它们一直有(写之前读的那份
  原文),而「单线程」只排除了自己,排除不掉另一个进程里正在跑的导出。一个无条件分支就够把上面那个末态造出来。
  **但 `expect` 这一道自己也不够,它只证明得了「库没换版」。** 「登记 `content_hash` = 声明已索引」这个不变量的完整判据
  (再加上「登记的是本次**写出去**的那一份」和「这一份现在重新索引一次库里不会变」)见 `maintenance-lock.md`。
  **注意那两道判据不是一道**:`disk_input_indexed` 用的 `kb.doc_rewrite.index_input_matches` 比的是**模型输入那三样**
  (标题/账号/拼接正文),够它判「能不能固化一个判定」——而**登记那张收据不用这一道**,它要整份索引等价
  (`index_projection_matches`:还有 `doc_tags`/`url`/`published`/`source`/`chunk.heading`,以及逐块而不是拼接的正文)。
  这两道各有射程,`tests/test_doc_rewrite_roster.py` 钉着「登记那边没有退回来用模型输入那一道」。
- **`save_promo` 只返回「写进去了没有」,统计按它报。** 换版跳过的那几篇什么都没写,算进 hard/soft 计数就是报一个没发生的
  结果,而那是人决定「要不要接着跑几千篇」时唯一看得到的东西。**它原来还返回一个「要不要摘 flag」的一次性信号,那个信号连
  同参数一起删掉了** —— 判据见下面「幂等对齐」那条。**整组都没拿到判定时退出码非 0**:自动化按 0 判成功,而「一篇都没判成」
  和「判完了」是两件事(模型挂了、配额用尽、prompt 里的 JSON 约定被改坏都长这样)。
- **没拿到结论的「兜底 none」不许覆盖已有判定 —— 闸在落库那一层,所有路都从那一句过。** `normalize_promo` 认不出 level 时
  填一个 none 并标 `fallback`:这一篇还没判过时那是对的保守值,可是**提取那条路同样会覆盖已有判定** —— 正文补抓回来后
  `fulltext.retire_stale` 只清 `extracted_at`、**明确保留**原来的 promo,于是一篇已经判 hard 的广告带着结论重新排进提取,
  一个缺 promo 字段的回包就把它擦成 none:广告重新进检索、两处 flag 一起摘掉,而界面显示提取成功、`extracted_at` 非空,
  这一篇从此掉出所有待办。`judge_promo(require_verdict)` 那道 strict 只管得到重判那条路(全量提取不能开 strict:绝大多数
  文章是第一次判,一个坏回包不该把 entity/topic/summary 整份丢掉)。**反过来钉一边:明确的 none 照旧放行。**
- **消费方一律读 `documents.promo_level`,不要各自再判一遍**:条目化 gate 读到 hard 直接否掉,检索和枚举默认挡掉 hard。
  **软广子句不进 `_filter_sql`**(后者的返回值还被 `_vec_leg` 用来判断「召回有没有被缩到小子集」)。transcribe 那侧**按当前
  判定再拦一道**。
- **hard 原文的衍生条目按 `url` 一起挡掉**,口径只有 `store.promo_exclude_sql()` 一份。里面那句 `pm.url <> ''` 不能省(库里
  几十篇没有 url 的文档会互相匹配上、集体消失)。
- **`flag/软广` 是双写的:DB 的 `doc_tags` + md frontmatter,两边都得跟着判定走。** 只写库的标记下次重索引就没了;反过来
  hard 改判成 none/soft 时 md 里那行也必须摘掉。**四条路(管道、`kb extract --writeback`、并行脚本、补判)的 tag 回写只能
  有一份实现**(`extract.writeback_extraction`)。`PROMO_TAG` 在 slug **之后**追加。
- **md 那行按「库里那份判定」幂等对齐,不按「上一次是不是 hard」**(`extract_promo.align_promo_tag`)。那个一次性信号只在
  「这一次恰好改判了」时为真,于是**一次失败之后就再也没有第二次机会**:第二次重判时库里已经是 none,信号为假,压根不会去碰
  文件,而 md 那行还在 —— 两次都报成功。幂等对齐则是谁来调、调几次,末态都一样。代价是补判那条路每篇多读一次 md(提取那三条
  路本来就要读),值这个钱。`promo_level = ''`(还没判过)两样都不做:那时 md 那行是提取阶段写进去的唯一记录。
- **对齐完要回读确认,而且按索引的读法**(`promo_tag_in_md` 走 `scanner.parse_frontmatter` + `frontmatter_tags`,也就是
  `yaml.safe_load`)。这道确认的后果就是「索引下一轮会不会把它读回库里」,所以不能另写一套读法:按行删的那条正则覆盖不到
  flow-style(`tags: [flag/软广]`),而 `remove_writeback_tag` 返回的 False 跟「本来就没有」长得一模一样。**对不上就抛
  `PromoTagNotAligned`,不许返回「摘干净了」**;同理 `read_text` 的 `OSError` 不许静默换成 False。引号项(`- "flag/软广"`)
  那条正则自己认。
- **交付跨两个存储,所以待办是「判定提交前的协议」,不是失败之后的记账**(`documents.promo_tag_pending`,写它的口径只有
  `mark_promo_tag_pending` 一份)。kb.db 的事务管不着 vault 文件:权限、磁盘满、进程被杀都能让判定落了库而 md 那行还在,而
  这一篇按 `promo_level <> ''` 从此掉出所有默认候选 —— 没有待办,谁也不会再回来看它一眼。所以**落待办和判定在同一个事务里**
  (`save_promo` 的最后一句):要么两样一起进库,要么一起回滚。**清它要等 md 那行写回并回读确认之后**(`align_promo_tag`),
  顺序反过来等于把兜底让给了随后那一步的运气。
  **只挂在 `except` 上的那一版挡不住头号时序** —— 那条路只在「我们还活着、还能执行一条 SQL」时才落得下来。实测:判定提交之后、
  写 md 之前对进程下 `SIGKILL`(退出码 -9),末态是库里 none + md 里挂着 flag + `promo_tag_pending` 一行都没有,`sync-tags`
  报「待对齐 0 篇」。出口是 `promo_backfill sync-tags`:目标状态就是库里那份判定,所以**不花钱**。脚本把这一档和成功
  **分开报**(`unsynced`),报成功就是说末态是一致的。**反过来钉一边:没被打断的那一次不许留着待办**,不然 `sync-tags` 每次
  把整库重走一遍,真被打断的那几篇淹在里面。
- **索引重建 `doc_tags` 时,`flag/软广` 那一行以库里的判定为准,不以 frontmatter 为准**(`store._align_promo_tag`,判据待在
  两条写语句自己的 WHERE 里)。`upsert_document` 把 doc_tags 整表删掉再按 md 的 tags 重建,而它不碰 `promo_level` —— 于是 md
  里一行过时的 flag 就成了这张表的唯一真相来源,一次完全合法的索引就能把它插回库里,按这个标签过滤的查询从此照旧捞得到这篇
  已经纠正为正常内容的文章。md 那行过时的路子不止一条(回写失败、有人手工改了 frontmatter),所以判据不能是「上一次回写成功
  了没有」。**反过来钉一边:库里判 hard 而 md 那行缺着时要补上**,不然一篇真广告在重建索引之后就不带这个标签了。
  `promo_level = ''` 两样都不做 —— 那时 md 那行是唯一的记录,按「矛盾」摘掉等于凭空丢数据。
- 存量补判走 `scripts/promo_backfill.py`,按「账号 + 标题 + 正文指纹」**同稿归组**(8857 篇里 2357 篇是同一份稿子的副本),
  每组只判一篇、结论广播给同组。**广播时每篇各按自己那一版的号判**,不许整组共用代表篇那一版:副本的 frontmatter 各带自己的
  url 和落库时间,`content_hash` 天生不同,共用就是一篇都写不进去。
- **soft 是「留着 + 降权 + 打标」,不是第二个 hard。** 检索里乘 `search.SOFT_PROMO_WEIGHT`(0.85);要调松紧改这一个数,别动
  `RRF_K`。**降权必须在截断 top_k 之前做**(排完再降只是在这 k 篇里换位置,被压下去的仍占着名额)。`Hit.score` 报降权后的分。
- **「有效档位」只有一份口径**(`store.promo_level_sql` / `effective_promo_levels`):自己判过用自己的,没判过(条目化衍生条目
  永远是空的)按 `url` 从原文继承,同 url 取最重的一档。
- **打标要覆盖四个展示面**(搜索结果、问答引用、图鉴卡片与时间线),统一走 `core.js` 的 `promoBadge()`。**图鉴是唯一不走
  search/aggregate 的面**(按 vault 文件聚合),所以 `projects._apply_promo` 补这一道,**过滤放在分组之前**;查库失败就降级成
  「全部保留、不打标」。
- **图鉴的缓存签名必须带上软广状态**(`projects._promo_sig`)—— 补判改的是**原文**那一行,衍生条目文件一个字节没动。签名取的是
  **逐篇 (path, promo_level, url) 的摘要,不能是聚合量**(分档计数 + MAX(promo_at) 在「两篇同一秒对调」时逐字相同)。取签名和
  重建共用一条连接。
- **`store.doc_body()` 返回空串有两种原因,下一步完全相反**(`body_gap`):`empty` = md 正文自己就是空的,重抓有机会补上,进
  「需回填」清单;`no_text` = 正文**有内容,只是一个字都没有**(整篇一张长海报图、纯表格),**回填救不了它**。不分档的话它会被
  当成「正文为空,需回填」**永动地**每轮重报、把 extract 标红,而「重试失败项」每次都去重抓那张图。
- **判据是「md 正文照 chunker 自己那套规则剥完还剩不剩字」**(走 `parse_frontmatter` + `normalize_body` + chunker 的
  `strip_markup`),不是「md 正文是不是空的」,更不是「有没有图片」。**「空没空」要在剥掉阅读装饰之后问**
  (`wikilib.linkify_doc` 对空壳照样追加图谱尾区)。**第三种形态:剥完还剩字、却一个 chunk 都没有 —— 这一档不许落终态**,一律
  按最保守的 `empty` 办。**读不到文件**同理落 `empty`。
- **终态存的是当时那份 `content_hash`,不是一个布尔**(`documents.no_body_hash`)—— 布尔是永久封死,按 hash 走则是 index 一写
  新 hash 就自动回队列。`no_body_hash <> ''` 那半不能省。写回按元规则带条件,**正文和它的版本号要在同一个快照里读出来**
  (`store.doc_body_version`,一条语句)。
- **`pending_docs` 是唯一口径**,所以一处改动同时治提取队列和面板那个「当前待处理 N 项」。**新那档的文案里不许出现「正文空」
  三个字** —— `retry_failed_plan` 就是按这三个字决定要不要跑回填脚本的。**它不判红、不进 failures 明细**,落终态时要把这一篇的
  旧失败计数一起清掉。
- **新增那一列在老库上是 ALTER 补的,所以「读列集合」和 ALTER 要在同一把写锁里**(`_add_columns`:缺列才 `BEGIN IMMEDIATE`,
  **并在锁里重新读一次**列集合)。**常态不取锁。**
- **面板上的「当前待处理 N 项」不能只在 running→idle 那个跳变上刷新**(`pipe.js` 另按「出现了一轮新的已结束运行」判)—— 这一
  档一次模型都不调、整轮几百毫秒,页面**一次都没见过 `running=true`**。这条路**不弹「已结束」那句 toast**。**而那次刷新不许被
  在途的积压查询吞掉**(`pipePendingWanted`:在途时记一笔欠账,等它收尾了补发,**真的应用上去才算刷新完**)。**回包「是哪一轮
  的」认 `run_id`,不拿 `started_at` 当身份。**
- **三条提取路径共用同一份判定。** `extract_parallel.py` 的预筛循环按「试过几次」提交、不按「写进去几条」(条件 UPDATE 返回 0
  行时也开着事务,而它后面的回写要先取维护锁)。
- **想真正读到这类文章的内容只能 OCR / 多模态读图**,那是按篇计费的另一笔开销,没做。
- 详细见 `docs/decisions/promo.md`、`body-gap.md`。

## 事故形态与实测证据

- **判定搭在提取阶段,不单开一个 LLM 阶段。** 提取是「每篇原文各跑一次、覆盖
  所有非 pre_tagged 来源」的唯一一步,正文已经在 prompt 里了,多要一个 promo
  字段只多几十个输出 token;单开一步等于把同一篇正文再买一遍。喂进去的正文
  总量没变(还是 6000 字符),但改成**头 4800 + 尾 1200**——软广的转化钩子
  (注册地址、「阅读原文领取」、推广落款)基本都在文末,只截开头一个都看不到。
- **三档 none/soft/hard,只有 hard 被当成广告处理。** 公众号里大量内容是
  「厂商自家通稿」「带返利链接的推荐」,它们有推广性质但技术信息仍然有用,
  落 soft 保留;hard 才是「整篇买下来卖一个产品」的投放稿。判定认不出时一律
  落 none:错杀会让一篇正常文章连同它的实体从条目化和检索里一起消失,漏判
  只是留着一篇广告。
- **hard 的两条边界是拿真实样本调出来的,别删**(随机采样 50 篇时各抓到误杀):
  ①**只看正文主体,不看文末的固定推广位**——号主每篇文末都挂一段加群/课程广告,
  不写清楚模型会因为那条尾巴把这个号自己写的资讯文判成 hard;②**推广对象是
  开源项目时一律不判 hard**,最多 soft——号主把一个 4.3K Star 的开源项目吹上天、
  顺带拉群,那是这类号的文风,不是买量投放。修完这两条,13 例定向回归(含 5 个
  已知真软广)全部符合预期。
- **边界①当初放得过宽,「借壳」那一类被它一并放过了。** 事故形态:一个号把
  新智元/量子位的资讯稿整篇搬过来——连「新智元报道」的抬头和「编辑:桃子」的
  原号署名都照抄——文末接一段「如需获取 ChatGPT Plus/Gemini/Claude 稳定续费
  升级服务,加微信 ysle0310 备注 189」。整篇唯一属于这个号自己的东西就是那段
  联系方式,而正文那部分在库里本来就有原创版。
  **根因是规则自相矛盾**:「代充值」原先既列在 hard 的清单里(「代充值、代开
  会员、共享账号、API 中转站一类导流文也算」)、又列在「可以忽略的文末尾巴」里,
  同一个词在相邻两段里两种办法,模型只能在矛盾处抛硬币。实测:同一份搬运稿的
  53 个副本判出 52 个 none、1 个 hard,none 那批给的理由逐字是「文末的充值广告
  是公众号固定版位而非本篇文章内容」——**模型没有失误,它是照着规则办的**。
  后果是 52 篇搬运广告稿活在检索、日报和图鉴里,而被搬的那篇原创只有 1 篇,
  一个主题下搜出来的几乎全是搬运件。
- **修法是把代充值这一类从「可忽略的尾巴」里拿出来单列,同时把反面钉进同一段
  prompt。** 反面那一串不是凑数的:词面扫一遍全库,「中转站/代充值/充值」在判定
  窗口里命中、却判 none/soft 的有 188 篇,除掉搬运号自己的 164 篇,剩下 24 篇
  **全是**另外三种用法——本号系列文章导航里有一条标题叫「Codex 怎么买、怎么
  充值」、正文在报道中转站泄露 6TB 数据、把「中转站」当比喻。头一版规则只写了
  正面,那 24 篇里的原创技术文当场被判成 hard(它文末是「加 考拉 好友回复 AI」
  的社群引导,被模型当成了代充对接),所以「加群 ≠ 代充」「历史文章导航里的标题
  不算」这两条必须明写。
- **定点验证:14 篇真实样本,6 篇借壳稿(含原判 none 和原判 soft 的)全部 →
  hard,8 篇反向样本全部保持原档**——被搬的新智元原创、中转站泄露报道、
  「人肉中转站」比喻、原创项目推荐、原创观点文、原创技术教程、原判 soft 的
  Codex 技巧文、开源项目介绍。
- **重判那条路加上之后,`normalize_promo` 的兜底从「保守」变成了「撤销」。** 实测:让模型侧回一个合法 JSON `{}`(字段缺失,
  不是坏 JSON,所以不走原地重试),`judge_promo` 正常解析、兜底成 `{"level":"none"}`,`--recheck` 把它当有效结论覆盖掉原来的
  `hard` —— 末态是 `level=none`、DB 和 md 两处 `flag/软广` 一起消失、这篇广告重新出现在默认全文检索里,而脚本打印
  「判定 1 篇,hard 0,soft 0,失败组 0」、退出码 0。**没有任何一处会再提醒**:它不在 `pending_docs` 里,下一轮同步也不碰它。
  修法是给 `normalize_promo` 加 strict、`judge_promo` 加 `require_verdict`,把「回包里没有合法 level」也算进那一次重试,
  两次都拿不到就抛,整组落到失败计数里下次重跑。
- **重判读走正文到写回之间,正文可能整篇换掉,而新那版往往已经判过一次。** 时序:worker 读走旧正文 → 另一条连接走完补抓、
  导出、索引,把这一篇换成新正文,正常提取把新版判成 `hard`(走的是带维护锁和版本校验的 `commit_extraction`)→ 旧请求回来,
  `save_promo` 无条件 UPDATE,把刚判出来的 `hard` 覆盖成旧正文的 `none`、两处 flag 一起摘掉。实测末态:库里正文是新那版的
  代充值广告、`promo_level=none`、`promo_reason` 写着「旧正文是正常行业资讯」、默认检索又能搜到它、`pending_docs` 为空。
  **这不是抢锁抢出来的随机结果**,是「双连接、新正文先完成、旧请求后返回」这个合法时序的必然。默认不重判时初始已判文档
  不在候选里,所以这个场景是随 `--recheck` 一起进来的。
- **归组键不带账号时,这次的修正会反噬。** 库里有 300 组是跨账号同稿,最大的
  两组正是「谷歌Gemini 4开跑了」(新智元 1 篇 + 搬运号 53 篇)和「OpenAI大神教你
  如何榨干Codex」(量子位 1 篇 + 搬运号 57 篇)。搬运版判 hard、结论按旧归组键
  广播过去,原创那篇就连实体带条目一起从检索和图鉴里消失。带上账号的代价是
  7230 组变 7570 组,多 340 次调用——换的是「不会把原创号的文章判成广告」。
- **口径改了而存量不重判,等于新文章一套标准、存量另一套。** 所以补判脚本加了
  `--recheck`;它覆盖已有判定,所以要求必须配 `--account` 圈定范围:无目标跑一次
  是 9000 多篇、把所有历史结论(含人工核对过的)一起盖掉。改 `_PROMO_RULES` 之后
  顺手核一次 `PROMPT_OVERHEAD` —— 它只用于 scan 的费用预估,偏小不会让判定出错,
  但会让人按一个虚低的报价决定要不要跑几千篇。
- **口径只有一份**(`_PROMO_RULES`),提取阶段的完整 prompt 和存量补判的轻量
  prompt 共用它;两处各写一份的话标准会各漂各的。
- **消费方一律读 `documents.promo_level`,不要各自再判一遍**:条目化 gate 读到
  hard 直接否掉(省的是 gate + transcribe 两次调用,后者是最贵的一步);
  检索(`search.Filters.exclude_promo`)和枚举(`aggregate`)默认挡掉 hard。
  **软广子句不进 `_filter_sql`**:后者的返回值还被 `_vec_leg` 用来判断「召回有没有
  被缩到小子集」(有就把 KNN 候选放大到 4000),混进去会让每一次普通检索都误判。
- transcribe 那一侧**按当前判定再拦一道**:存量补判之前 gate 已经放行过一批,
  那些 state 记录还是 `project_article=true`,只看 state 会拿全文去拆投放稿。
- **hard 原文的衍生条目(`dr-gzh-projects`)按 `url` 一起挡掉**,口径只有
  `store.promo_exclude_sql()` 一份,检索和枚举都调它。只挡原文的话,拆出来的
  条目仍然带着广告产品的实体留在库里(2026-09-16 第 1 轮审查发现)。里面那句
  `pm.url <> ''` 不能省:库里几十篇没有 url 的文档会互相匹配上、集体消失。
- **`flag/软广` 是双写的:DB 的 `doc_tags` + md frontmatter,两边都得跟着判定走。**
  `doc_tags` 每次 `upsert_document` 都按 frontmatter 重建,只写库的标记下次
  重索引就没了(第 1 轮审查发现);反过来,hard 改判成 none/soft 时 md 里那行
  也必须摘掉(`remove_writeback_tag`),否则重索引又把误判带回库里
  (第 2 轮审查发现)。**现在的判据是库里那份判定,不是那个一次性信号**
  (`align_promo_tag`,见硬约束里「幂等对齐」那条);回写改了文件就同步
  `refresh_content_hash`,免得下一轮 index 白白重建这批文档 —— 但那一句带
  `expect` 条件,不会替别人那份还没索引的改动一起签收据。
- **提取有三条路,tag 回写只能有一份实现**(`extract.writeback_extraction`):
  管道 `_extract_pass`、`kb extract --writeback`、`scripts/extract_parallel.py`
  (后者自称与前者等价)。原来三处各拼各的 tag 列表,软广同步只接进了管道,
  另外两条一条写不进 md、一条改判摘不掉,第 1、2 轮防住的漂移原样留在旁路上
  (第 3 轮审查发现)。`PROMO_TAG` 在 slug **之后**追加——它已经是最终形态,
  跟着 topic(`_topic_slug`)/entity(`_tag_slug`)过一遍会被改写成别的 tag。
- 存量补判走 `scripts/promo_backfill.py`(scan/run/report),只判软广、不重跑
  整套 extract,并按「账号 + 标题 + 正文指纹」**同稿归组**:8857 篇存量里有
  2357 篇是同一份稿子的副本(克隆号互转、代充值广告同一个号发了 177 次),每组
  只判一篇、结论广播给同组。**键里是正文指纹而不是长度桶** —— 后者是个猜,
  形态见下面「同稿归组猜错了」那节。补完一次 `promo_level=''` 就不再有新增。
- **soft 是「留着 + 降权 + 打标」,不是第二个 hard。** 检索里乘一个系数
  `search.SOFT_PROMO_WEIGHT`(0.85)。RRF 的分数全挤在窄带里,乘系数约等于
  **平移名次**:大致往后挪 `(1/w - 1) * (RRF_K + 1)` ≈ 11 名——同分的中立文章
  能排到它前面,一篇明显更相关的 soft 不会被赶出去。要调松紧改这一个数,
  别动 `RRF_K`(那是两路融合的量纲)。
- **降权必须在截断 top_k 之前做。** 排完再降只是在这 k 篇里换位置,被压下去的
  soft 仍然占着名额,排在 k+1 的中立文章永远补不上来。所以 `search()` 里先
  `effective_promo_levels` 拿到全部候选的档位、算完加权分再截断;`Hit.score`
  报的是降权后的分,报原分会让列表里出现「下面一条分数更高」。
- **「有效档位」只有一份口径**(`store.promo_level_sql` / `effective_promo_levels`):
  自己判过用自己的,没判过(条目化衍生条目永远是空的)按 `url` 从原文继承,
  同 url 多篇取最重的一档。这和 `promo_exclude_sql` 挡 hard 时的回溯是同一条
  关系——只标原文的话,一篇 soft 拆出来的工具条目在搜索和引用里仍然干干净净。
- **打标要覆盖四个展示面**:搜索结果(`Hit.promo_level` → `/api/search`)、
  问答引用(`askflow`/`askagent` 的 refs)、图鉴卡片与时间线。前端统一走
  `core.js` 的 `promoBadge()`,别在各处各判一次 level。
- **图鉴是唯一不走 search/aggregate 的面**:它按 vault 文件聚合(那个「每工具
  多来源记录」的粒度只有文件层有),所以统一排除口径覆盖不到,hard 投放稿拆出
  的条目原来照样在图鉴里占一行。`projects._apply_promo` 补这一道:**过滤放在
  分组之前**(提及次数/号数/首末时间都按条目算),查库失败就降级成「全部保留、
  不打标」,不让图鉴因为库的问题整个打不开。
- **图鉴的缓存签名必须带上软广状态**(`projects._promo_sig`)。原来只看条目文件
  的数量和最大 mtime,可补判改的是**原文**那一行 `promo_level`,衍生条目文件
  一个字节都没动——签名不变、缓存不失效,于是「跑完 backfill 刷新图鉴,刚判
  成 hard 的工具还在原地」,除非重启 kb-web(第 1 轮审查发现)。签名取的是
  **逐篇 (path, promo_level, url) 的摘要,不能是聚合量**:分档计数 + MAX(promo_at)
  在「两篇同一秒对调 hard/soft」时逐字相同,可该显示的卡片已经换了一张
  (第 2 轮审查发现);`promo_at` 只到秒,一轮 backfill 六个并发同秒改判很常见。
  摘要里带 url 是因为继承关系按 url 回溯;不带 promo_at——它变而结论没变时
  本来就不需要重建。开销量过:1888 篇已判文档 8.0 ms,同一次请求里
  `_scan_sig` 扫 10213 个条目文件要 70.8 ms,只占一成。取签名和重建共用一条
  连接,否则每个图鉴请求要多付一次 connect(里面有 sqlite_vec 扩展加载)。

### 重判的交付不原子:改判只成了一半,而且不可恢复

重判原先的时序是「锁外 `save_promo` 删掉 `doc_tags` 那行 flag 并提交 → 锁内
摘 md 那行」。中间那个窗口里跑一趟**完全合法**的索引(任何一次正常的文档更新
之后都会跑),改判就只成了一半:

1. `upsert_document` 不碰已经改成 none 的 `promo_level`,但 `doc_tags` 每次
   upsert 都按 frontmatter 整表重建 —— 它读到的是**还没摘**的那份 frontmatter,
   于是 `flag/软广` 被重新插回库里。
2. 随后的回写只负责摘 md 那行,不会再回头清库里那行(它压根不知道有人插回去
   过),还顺手把 `content_hash` 刷成当前文件的 hash。
3. 下一轮普通索引因此报「未变」直接跳过 `upsert_document` —— **错的那行标签
   永久留在库里**。

末态很隐蔽:`promo_level` 是 none,普通全文检索正常返回这篇文章、卡片上没有
广告徽标,`pending_docs` 是空的、脚本报的是成功;唯独**按 `flag/软广` 过滤**
仍然捞得到这篇已经纠正为正常内容的文章,而且再同步、再索引多少轮都不会自己
纠正(2026-10-14 确定性复现:交错那趟索引之后 DB flag 仍为 true、md flag 为
false,事后另跑一趟普通索引报「新增/更新 0,未变 1」)。

修法是让补判也有一个协调入口(`extract_promo.commit_promo`),把条件写、
`doc_tags` 对齐、提交、摘 md 那行圈进同一把维护锁 —— 和提取那三条路的
`commit_extraction` 同一个形状。**这把锁对同一个线程是可重入的**
(`maintenance_lock` 的 `_held.on` 是线程局部标记),所以用「同线程里同步跑一趟
索引」来验这件事是验不出来的:那个形态下索引会直接穿过区间,而且对
`commit_extraction` 一样穿得过去(对照实测:在它的区间里同线程插一趟索引,
新提取的 `topic/new-topic` 没能进库、库里留着被重建的 `topic/old-topic`,而 md
里两个都有)。真实形态里索引从不在补判那个线程里跑(管道在 kb-web 进程内、
`kb index` 是另一个进程),所以回归用的是**另一个线程**,判据落在「那趟索引
有没有在区间里拿到锁」加上三处标记的末态。

**反过来的那一半同样要钉**:补判的回写不许传输入指纹。`_input_moved` 的第一道
比的是整个**文件**的 hash,而只改 frontmatter 的流程是常态(翻译回写、tag
回写、wiki 追加图谱尾区);传下去的话一次正文压根没动的合法改判会被判成作废,
末态是库里 none、frontmatter 还挂着 flag,下一次索引又把它重建回来。提取那
三条路传指纹是对的,因为对它们「作废整份结果」是安全的 —— 下一轮
`pending_docs` 会把这一篇再提一遍;而补判一旦 `promo_level` 非空就再也不进
默认候选,作废等于永久漏摘。

### 判定针对的正文和磁盘上那份不是同一份:新正文永久搜不到

重判的交付原来只核对 `documents.content_hash`(索引**记录**那一版)。它答不了
「磁盘上那份 md 还是模型读过的内容吗」—— 导出和索引是两个各自取锁的阶段
(`feeds.sync` 导出 → `pipeline_stages` 索引,`pipeline` 依次调它们),一次补判
完全可以插在两者之间:那一刻磁盘上已经是新正文,chunks 和 `content_hash` 还是
旧的,条件写照旧放行。

末态(确定性复现三次):磁盘上是一篇代充值广告的新正文,库里存着对**旧**资讯
正文判出的 `none`;回写摘标签时 `refresh_content_hash` 把**新文件**的 hash 写进
库,于是 `doc_needs_reindex` 说「未变」—— 再跑一轮普通索引报「新增/更新 0,
未变 1」。界面上的样子是:搜新正文里的词一条结果都没有,点开这篇文章却显示
新的代充值正文;`promo_level` 非空,所以它也不再进任何默认候选,再同步也不恢复。

两头都修了,而且**判据放在落库之前** —— 拦下来就是一个字都没写,库里和 md 里
仍是原来那份判定、彼此一致:

- `commit_promo` 锁内先过 `disk_input_indexed`(磁盘上那组输入按索引自己的读法
  各读一遍、和库里比)和 `_input_moved` 关掉第一道(索引里那组换版了吗);
- `refresh_content_hash` 带 `expect` 条件写,**0 行就是对的末态**:这一篇继续
  带着「待索引」,下一轮重建一次就对了。

**为什么不能简单地「文件 hash 对不上就拒绝」**:只改别的 frontmatter 字段是常态
(翻译回写 summary、tag 回写、wiki 追加图谱尾区),那样会把一次输入压根没动的
合法改判拦掉,而 md 里那行 flag 就此摘不掉。

**反过来,判据也不能只细到正文一层。** 磁盘上的标题被换掉、正文一个字没动
同样是常态(补抓回来的正文和标题各走各的回写),只比正文就放行 —— 末态是旧标题
下判出的 hard 固化在新标题上:文章在界面上已经是另一篇,带着别人的广告判定被
永久隐藏,而 `promo_level` 非空让它掉出所有默认候选。所以判据正好是**模型输入
那三样**:标题、账号、正文(`extract.input_fingerprint`),别的 frontmatter 字段
一概不看。

### 同稿归组猜错了:一篇正常教程被另一篇广告连带隐藏

归组键原来是「账号 + 标题 + 正文长度桶(500 字一档)」。长度桶是个**近似**,而
它的结论会**覆盖另一篇文章的判定**:一个号把「每日资讯」当标题反复用是合法
输入,广告段有没有也可能只差几十个字。确定性复现:同号两篇同题,910 字的开源
教程 + 960 字的搬运代充值广告,广告那篇稍长当了代表,末态是教程也被判 `hard`、
理由写着「同稿判定:…/group-ad.md」、两处 flag 都为 true、正常全文检索返回不了
它(放开广告排除的底层检索仍能返回,所以不是没索引),而脚本报的是「软广 ×2」。
反过来的组合一样坏:代表篇是较长的正常稿时,另一篇的已有 `hard` 会被盖成 `none`。

现在的键是「账号 + 标题 + 正文指纹」——**喂给模型的那三样逐字相同**。这样广播
不是推断:组内每篇的 prompt 和代表篇一个字节都不差,问的是同一个问题。代价是
组数变多(同稿副本之间常有「本文转载自…」一类差异,那本来就该各判一次),
漏并一组花一次调用(约 $0.004),而并错一组是一篇正常文章被永久隐藏。

### 回写失败之后没人回来看它:两处标记永久不一致

判定进的是 kb.db 的事务,md 那行进的是 vault 文件,**没有一个事务能同时管住
两者**:维护锁只挡竞争,挡不住权限错误、写失败、进程被杀。原来的末态是:
DB `promo_level=none`、DB flag 已摘、md flag 还在,脚本只打印一句同步失败提示、
汇总仍报「判定 1、失败组 0」;撤去故障再重判一次也修不回来 —— 那时的判据是
`save_promo` 返回的「上一次是不是 hard」,而库里已经是 none,信号为假,压根不会
去碰文件。随后一次**完全合法**的索引(改一项无关 frontmatter 元数据即可触发)
按 md 把 `flag/软广` 读回 `doc_tags`,于是 `/api/search?...&tag=flag/软广` 返回
这篇已经纠正为正常内容的资讯。

三道一起修,各管一头:

- **判据换成库里那份判定,幂等对齐**(`align_promo_tag`):谁来调、调几次,末态
  都一样,所以第二次重判也修得回来;
- **对齐完回读确认**(`promo_tag_in_md`,走索引那套 `yaml.safe_load` 的读法),
  对不上就抛 `PromoTagNotAligned` —— 按行删的正则覆盖不到 flow-style
  (`tags: [flag/软广]`),而 `remove_writeback_tag` 的 False 和「本来就没有」
  长得一模一样;`read_text` 的 `OSError` 也不再静默换成 False;
- **待办在判定提交前就落下**(`promo_tag_pending`,`save_promo` 的最后一句,和判定
  同一个事务),出口是 `promo_backfill sync-tags`(目标状态就是库里那份判定,
  不花钱);脚本把这一档和成功分开报(`unsynced`)。

**待办只挂在 `except` 上挡不住头号时序。** 那条路只在「我们还活着、还能执行一条
SQL」时才落得下来 —— 而要防的第一种情况恰恰是进程在中间没了。注入一次真实
`SIGKILL`(子进程在判定已提交、md 还没写的那一瞬间给自己 `-9`,父进程检查末态):
库里 `none`、md 里挂着 flag、`promo_tag_pending` 一行都没有,`sync-tags` 报
「待对齐 0 篇」—— 两处永久不一致,而没有任何待办指向它。所以落待办和判定进同一个
事务(要么两样一起进库、要么一起回滚),清它要等 md 那行写回**并回读确认**之后。
反过来也钉一边:没被打断的那一次不许留着待办,不然 `sync-tags` 每次把整库重走
一遍,真被打断的那几篇淹在里面。

**另外钉住索引那一侧**:`upsert_document` 重建 `doc_tags` 时,`flag/软广` 以库里
的判定为准(`store._align_promo_tag`)。md 那行过时的路子不止一条(回写失败、
有人手工改 frontmatter),判据不能是「上一次回写成功了没有」。反过来也钉一边:
库里判 hard 而 md 那行缺着时要补上。

### 兜底的 none 擦掉已有的 hard:strict 只拦住了重判那条路

`normalize_promo` 认不出 level 时填一个 none —— 那条兜底只对「这一篇还没判过」
成立。重判那条路已经用 `judge_promo(require_verdict=True)` 拦住了,但**全量提取
同样会覆盖已有判定**,而它不能开 strict:绝大多数文章是第一次判,一个坏回包不该
把 entity/topic/summary 整份丢掉。

触发链是现成的:一篇 `hard` 文章补回正文后,`fulltext.retire_stale` 清掉
`extracted_at` 却**明确保留** promo(绿泡泡正文回填 `pipeline_retry` 同理),于是
它带着 hard 重新排进提取(`pending_docs` 不排除已有 hard);模型回一个能解析、
但缺 `promo` 字段的 JSON,`_extract_once` 把它归一成明确的 `{"level":"none"}`,
`commit_extraction → save_extraction → save_promo` 一路放行 —— 广告重新进检索、
两处 flag 一起摘掉、`extracted_at` 设上,界面显示提取成功,这一篇从此掉出所有
待办。

修法是**把「有效判定」和「兜底值」分开**:`normalize_promo` 兜底时标一个
`fallback`,`save_promo`(所有覆盖已有判定的路都从这一句过)看到它就不覆盖已有
结论、返回「没写进去」。明确的 none 照旧放行 —— 不然 hard 就再也改不回来了。
