# 夹具服务自己什么时候退(tests/fixture_life.py + tests/serve_*.py)

> **这一份的第一节就是这一块的硬约束(不许怎样)—— 动这块代码之前先读它**,后面是完整的事故形态、
> 实测证据、回归清单和反向验证。CLAUDE.md 只留跨块的元规则和一张索引。
> 硬约束和下面的展开**说的是同一条口径,要改规则两边一起改**。
>
> 跟 `probe-shell.md` 是同一个所有权问题的另一半:那份管**探针起的 chrome**,这份管
> **夹具这个 Python 服务进程自己**。两边的判据和凭据**都不一样**,理由见「为什么不能照搬探针那边」。

## 硬约束

- **判据是「没人用了」,不是「父进程没了」。** `tests/serve_*.py` 手起时的**合法**用法就是跨多个
  shell 共用一个:起服务那个 shell 当场就退,随后另一个 shell 才跑探针。所以这边**不许**照搬
  `probe_shell.mjs` 的「没拿到凭据就现读 ppid」—— 那样夹具一起跑就自杀,这条合法的路直接断掉。
- **主防线是空闲超时**(`KB_FIXTURE_IDLE` 秒,默认 15 分钟,`0` 关掉给手动调试页面的人)。它不问谁是
  父进程,**因此手起这条路也盖得住** —— 那正是实测泄漏的全部来源。
- **装防线时要把继承来的 `SIGINT=SIG_IGN` 复位**(`_rearm_sigint`,在 `install()` 和拿到凭据之后的
  `_arm_owner()` 各一次,口径同一份)。自退的第一道发的是 SIGINT —— 为的是让 `main()` 那个
  `ExitStack` 退得了栈、临时根删得掉。可后台起的进程(shell 的作业控制、`nohup`、CI 和任务哨兵那条
  非交互的链)把 SIGINT 设成 SIG_IGN,而 `exec` 之后「被忽略」这个处置是**继承**的(被捕获的那种才
  复位成默认)。于是第一道一点动静都没有,兜底 SIGTERM 直接结束进程、清理一行都不跑,盘上留下一份
  完整的沙箱库 —— `fixture_root.py` 记着的那个事故形态,换一种起法又犯了一遍。**只在它正被忽略时
  动手**(调用方自己装过 handler 的要尊重),而且必须在装防线那一刻做:`signal.signal` 只能在主线程
  调用,`_bail` 跑在看门狗线程里。
- **ASGI 那几个盖不住这个坑,别拿它们验。** uvicorn 自己装 SIGINT handler,把继承来的 SIG_IGN 覆盖掉
  了;只有裸 server 那一档(`serve_workspace.py`,靠 `except KeyboardInterrupt` 接住)会失守。
- **空闲是「手上一个请求都没有,而且距上一个回完够久了」,不是「距进门够久了」。** 只在进门
  `touch()` 一次的话,读上游、发响应、等流式数据那几秒全算成空闲:实测 1 秒上限下一个 4 秒的慢请求
  被拦腰砍断,客户端拿到 502。所以每个请求从进门到回完整段计在途(`active()`),`should_exit` 里
  `busy == 0` 是和空闲时长并列的条件。
- **在途从「请求头整份读完、而且解析成功」开始算,不从 `handle_one_request` 进门算。** keep-alive 连接
  等下一个请求时阻塞在读请求行上,把那一段算成在途的话,挂着一条连接就能让夹具永不退出 —— 防线换个方向
  失守而已。**代价也写明**:请求头发到一半的连接同样还不算在途,所以极慢地送请求头时夹具可能在这份请求
  提交完之前按空闲退掉(实测 idle=1、发完请求行和半截 Host 再等 2.5 秒,进程已经 rc=0,补发剩下的合法头
  只收到 EOF)。两边只能选一边;真要兼顾就得在 HTTP 解析层把「空连接」和「已经开始的请求」分开、再给半截
  请求一个自己的时限,那是另一件事。
- **在途数、上一个请求回完的时刻、「已经决定收场了」这个闸门是一份状态、一把锁。** 分开更新就会出现
  「没有在途,而完成时刻还是上一个请求的」那一瞬,看门狗正好在这里醒来便把刚回完的请求判成空闲很久:
  实测(确定性线程注入)一个 4 秒的慢请求正常返回之后 19 毫秒夹具就退了,远没到承诺的空闲时间。所以
  `_leave` 的两样更新在**同一个临界区**里;`should_exit` 是**纯函数**,`busy` 和 `idle` 由 `_decide`
  在那一个临界区里一起取 —— **不许在 `_check` 里自己拼 `should_exit(..., inflight(), idle_seconds())`**,
  那是两次独立取锁,竞争又回来了。
- **「决定收场」和「还接不接请求」也在那同一把锁里。** 否则判据读到 `busy == 0` 之后、动手之前又进来
  一个请求,那个 0 就过期了,刚接下的请求会被砍掉。`_enter()` 返回「接纳了吗」,闸门落下之后一律不接纳;
  收场只走一次。**反过来钉一边**:这道闸门一旦误落,夹具会对所有请求装死而面板上看不出来。
- **副防线是原调用方看门狗,凭据是一根继承下来的管道,不是一个 pid**(`KB_FIXTURE_OWNER` 写
  `"<fd>:<token>"`,`fixture_server()` 用 `os.pipe()` + `pass_fds` 交下去,token 预先写进管道)。
  夹具读到 EOF 就知道调用方没了。它盖的是「跑测试那个进程被 SIGKILL、`finally` 里的 `reap()` 一行
  不跑」那一档。
- **不许改回「环境变量里那个 pid 启动时还是不是我的父进程」那套判据。** 七个 ASGI 夹具在开服务之前
  要建库、导出、建索引,调用方死在那几十秒里时夹具读到的 ppid 已经是 1 —— 那套判据会把**正确的**
  凭据当成继承来的陈旧值丢掉,副防线整个不装。管道没有这个窗口:凭据可不可信由「写端是不是还开着」
  回答,与谁是父进程无关。
- **读凭据那次等待必须带超时,而且不许改那个 fd 的状态。** 环境变量里的 token 比管道里的内容长时
  (被人篡改、或者凭据写了一半),阻塞读会**永远卡在模块加载里**,而且这一刻日志还没准备好,现场只有
  一个不动的进程。所以等可读走等待器(下一条),读完**什么都不还** —— 它本来是什么状态就还是什么状态。
- **分类只许认 errno,不许认异常类型。** `OSError` 不等于「这个 fd 坏了」:建等待器自己要申请内核资源,
  `EMFILE` / `ENFILE` / `ENOMEM` 都能让它失败,而那些说的是「**我们这边**没资源了」,跟远端那个调用方在
  不在毫无关系。实测在建等待器那一刻把子进程软上限压到 96 占满 fd,内核真给出 `OSError(24)`,凭据照旧被
  吞成「没有 owner」—— 资源恢复之后页面能开、调用方取消之后还是同一个进程。所以口径只有一份
  (`_is_stale`):**只有 `EBADF` 算陈旧凭据**,其余一律 `OwnerUnusable`。认领、建等待器、读 token、后续
  监测四处共用它,别在某一处给某个 errno 开特例。另外两类在这里不算错:`EINTR`(信号打断)和 `EAGAIN`
  (非阻塞下的假醒)都是「接着等」,上面那道超时兜着。
- **盯不住了不等于「还盯着」。** 看门狗那一侧再也回答不了「调用方还在吗」时,两种错法的代价不对称:当成
  「还在」是**静悄悄**永久留着一个没人要的进程;当成「没了」顶多把一轮还活着的验证打断 —— 那是**响的**。
  所以照旧按「没了」收场,但**要说一句为什么**,不许冒充正常的 EOF。
- **等待机制不许用 `select.select`,而且「盯不住」不等于「没有 owner」。** `select.select` 在
  fd ≥ `FD_SETSIZE`(1024)时抛 `ValueError`,而 `os.pipe()` 不保证给低号、`pass_fds` 又原号传下来 ——
  调用方只要先开着一千来个文件,凭据就落在高位上。把那个 `ValueError` 当成「从来没有 owner」的后果实测
  过:调用方取消之后页面照旧 200、进程还是同一个,而默认 900 秒的空闲那一道救不了它(页面还在轮询就
  一直续命)。所以①两处等待(认领和看门狗)统一走 `selectors.DefaultSelector`(kqueue / epoll,没有那道
  上限);②**凭据有效却装不上一律抛**(`OwnerUnusable`)—— 模块加载失败、夹具起不来、`fixture_server`
  当场报启动失败。**「少一道防线」必须是响的,不能是静的。** 注意这跟「凭据验不过」是两件事:token
  对不上、不是 FIFO、号已经坏了,那些说的是继承来的陈旧值,照旧安静地退回无主(手起那条合法的路靠它)。
- **所有权那道防线在模块加载时就装,空闲那道在摆盘之后才装。** 前者要盖的正是摆盘那几十秒;后者装
  早了的话建库、导出那段本身就是「没有请求」,夹具会在起身途中被自己的空闲超时收掉。
- **启动提示一律走 `announce()`,入口里不许再出现裸 `print`。** 「先装防线、再说话」这个顺序必须由
  **一个出口**保证:六个入口各写一遍 `print(...)` 然后 `guard(app)` 的话,顺序对不对就要逐个去看 ——
  上一版六个全错。`install()` 在 `guard` 里面,而 stdout 没人消费时那次 `print` 就阻塞在那儿,
  `install()` 永远执行不到;手起这条路本来就没有 owner,于是**一道防线都没装**,进程永久留着,而
  `print` 阻塞不抛异常,外面什么都看不到。实测:给手起的夹具一根预先填满的 stdout,过了空闲上限进程
  还在、端口不响应;一开始消费那根管道它立刻起来服务,随后正常退掉。**提示丢得起,防线丢不起** ——
  那一行自己也走那个有界队列,没人消费就丢掉。`install()` 因此必须幂等(`announce` 和 `guard` 都会叫它)。
- **收场发的是 SIGINT,不是 SIGTERM。** Python 对 SIGINT 的默认行为是抛 `KeyboardInterrupt`,
  `main()` 里那个 `with contextlib.ExitStack()` 退得了栈;SIGTERM 没有 handler 时是**直接结束**,
  清理一行都不跑 —— 手动跑那一档的临时根归夹具自己删(口径在 `tests/fixture_root.py`),发错信号就是
  把那个事故形态又犯一遍。后面还有 SIGTERM 和硬退两道兜底:**一道自己卡住的防线比没有更糟**。
- **日志不许挡住任何一道防线。** 没人消费 stderr 时那根管道会满,而满管道上的 write **是阻塞不是
  异常**,`try/except` 拦不住:它能让退出路径卡在发信号之前(连硬退都到不了),也能让请求线程永远停在
  「在途」上,把空闲超时一并堵死。出路是**把 stderr 挪出所有防线的路径**:谁要说话都只往一个有界队列
  里丢(`_say`,满了就丢,从不等),真正的 write 由一个专门的守护线程做 —— 它卡在满管道上无所谓,
  没有任何人等它。访问日志也要覆盖 `log_message` 走同一条路,**交还给 `http.server` 原来的实现不行**。
  **日志丢得起,正在服务的请求和防线丢不起。**
- **不许改调用方共享的 fd 状态,一个比特都不许。** `O_NONBLOCK` 不挂在「我这个进程的 2 号」上,它挂在
  open-file-description 上,而手起夹具继承的 stderr 跟调用方是**同一份** —— 把 fd 2 设成非阻塞来躲开
  上一条,调用方和一切共享者一起看得见:实测调用方自己什么都没做,它的 write 开始抛 `BlockingIOError`、
  输出缺行。`dup` 也隔不开,复制出来的 fd 指的还是那一份。同一条口径管**借来的凭据 fd**:读 token 用
  `select` 问「可读了吗」,不设非阻塞;更不许在拒绝凭据时「设回阻塞」—— 那不是恢复原状,是按我们的猜测
  改了别人的东西(实测:原本非阻塞的 pipe、token 故意写错,凭据被拒,而它被留成了阻塞的)。
  **反过来也得受得住**:既然不碰它的模式,`_watch_owner` 等 EOF 也得走 `select` —— 直接 `os.read` 在
  一个非阻塞的凭据上当场拿到 `BlockingIOError`,它是 `OSError` 的子类,会被吞成「写端关了」,夹具刚起来
  就自己退掉。
- **口径只有一份**:该不该退全在 `should_exit()`,续命全经过 `touch()`。两条适配路只负责把请求接上
  去 —— uvicorn 那 7 个走 `guard(app)`,`serve_workspace` 那个裸 `ThreadingHTTPServer` 走
  `TouchingHandlerMixin`。**两条路各有自己的红**,一条的回归盖不住另一条。
- **`guard` 要把 `lifespan` 排除在在途之外。** 它从起到停贯穿整个进程,**不是**一次请求;算进去的话
  在途永远 ≥1,空闲超时永远不到点,这道防线等于没装。
- **回收只认「那个 pid + 它的启动时刻」,端口和脚本名都不是所有权凭据。** 「是这一种服务、正在用这个
  端口」在另一轮的同型夹具接手之后一样成立 —— 实测:本轮的 A 退出、另一轮的 B 接手同一个端口,按
  「名字对上、端口对上」清理把活着的 B 杀掉了。pid 也会被回收,所以要连启动时刻一起比(`_identity`):
  同一个 pid 上的两个进程,启动时刻必然不同。`fixture_server()` 为此在 `SandboxBase.pid` 上把这一轮
  那个进程交回来。**发信号的每一条分支都只许作用在核验过的那个身份上,一条都不例外** —— SIGCONT 也是
  信号,不许为了「先放它走才收得动」把它发在核验之前。
- **身份只许由进程**不可变**的那部分构成:pid + 启动时刻,两样都要。** 命令行**会变** —— `execv` 一跑就换
  一副样子,把它算进身份,记在 exec 之前的那一份就永远对不上,上面那条保守分支一个字都不碰。实测的后果:
  整套一起跑稳定留下一个**手起的**夹具 —— 偏偏是那条用例,因为它的立意正是「没有 owner、空闲防线也关了,
  所以它不该自己退」,**没有任何别的东西会来收它**;而单条跑机器闲、exec 抢在 pid 那一行前面,一次都看
  不见。反过来,**pid 也不能从那个串里省掉**:启动时刻只精确到秒,同一秒里起来的两个进程读出来一模一样,
  而回收那两个出口只比这个串 —— 实测杀掉本轮的 A、紧接着起另一轮的 B,拿 A 的身份去收 B,串对上了,活着
  的 B 被一刀砍掉。**「等够了时间命令行应该稳定了」不是不变量**,加大预算只是把窗口推远。
- **「量不出身份」和「它已经没了」是两件事,所以身份只有三种答案,而且各有一个形状。** `ps` 起不来、被
  权限或资源挡住时回空串,等于告诉回收方「没什么要收的」—— 那正是静默漏一个进程的形态。所以口径是三态:
  量出来了给那个串、平台**明确说**没有这个进程给空串、判不出来抛 `IdentityUnknown`(它是 `AssertionError`
  的子类,所以「测试里抛出去是**响的**」照旧成立:用例当场红,不会把一个活着的夹具留在后台)。
  **「判不出来」要有专门的类型,不能让消费方去认一个宽类型。** 认「凡 `AssertionError`」会把别处真正的
  断言失败一起吞掉,反向验证跟着假绿;认「凡 `OSError`」更不行 —— 那是**按异常类型分类**,口径同
  `_is_stale`(「这个号坏了」和「我们没资源了」不是一件事)。所以转换只在一处做:起 `ps` 失败时把
  `OSError` 换成 `IdentityUnknown`,消费方只认这一个形状。
- **「它已经没了」要按平台真说出来的那句判,不许按「反正不是成功」判。** `ps` 找不到那个号时给的是
  `rc == 1` 且两条流都是空的,判据就写这个。写成「非 0 加 stderr 空」的话,**被信号杀掉的 `ps`**(rc 是
  负数、同样没有 stderr)也会落进来:一个活着的夹具就这样静默变成「没什么要收的」,而回收那两个出口只
  看这一个返回值。
- **进程一建出来就要有人认领它,取样排在登记之后。** `addCleanup(self._reap_pid, pid, _identity(pid))`
  是**先求实参、再登记**:上一条说了 `_identity` 量不出来一律抛,而它抛在那一行的时候登记压根没发生 ——
  用例当场红,刚起来的那个夹具谁都不认领。**让用例报红不等于把它创建的进程收回了**:实测在取样那一处定
  点注入它自己声明的 `AssertionError`,已有清理(收中间进程、关 stdout)全部执行成功,留下的还是那个真夹
  具,ppid 已经是 1、页面照样 200,而那条用例起的正是「没有 owner、空闲也关掉」那一档,没有任何别的东西
  会来收它。所以口径是 `_claim_pid`:**先登记,再把身份填进那个盒子**。
- **回收时要有一条不靠取样的所有权证明。** 两个回收出口原来都是「再取样一次,对不上就返回」—— 取样本身
  抛出来时 `addCleanup` 只记下一条错误,那个进程照旧留在后台。创建者手里本来还有一条:`holder`(起它的那
  个中间进程)是它的父进程、又永远不 `wait()`,所以 holder 活着的时候这个号即使已经退了也还只是僵尸,不
  可能落到别人手上。于是判据只有一份(`_mine`):身份能量出来就按身份,量不出来或者还没量就按 holder,
  **两条都用不上一律抛** —— 凭一个号就动手会杀掉别人的进程,安静地放过它则是静默漏一个还在服务的夹具。
  `holder` 自己的清理要登记在 `_claim_pid` **之前**(清理后进先出,于是收孙进程排在收它之前);反了的话
  `_mine` 当场抛,是个响的红而不是静默漏。
- **准备阶段申请的东西也要一成功一登记,而且环境前提要显式处理。** 高位凭据那条用例要先占满低号;上一版
  用一句列表推导一次申请 1100 个,全成功了才 `addCleanup` —— 中途某一次 `os.open` 抛出来时那个列表压根还
  没赋给变量,前面已经开成功的几百个号就没人收了(整数被丢掉不会关掉内核里的 fd)。实测把软上限压到 128
  跑它,清理全跑完之后进程里还剩 125 个开着的号,紧接着一次普通 `open(os.devnull)` 就 `EMFILE`,**后面每
  一条用例都跟着坏**。**准备失败只该让这一条跳过,不该污染整轮**:所以逐个申请逐个登记,软上限不够就显
  式抬高、硬上限也不够就明说跳过(`_hold_high_fds`,中间进程那一侧同口径)。
- **摆盘那一段的输出要在边界上统一圈住,`stdout` 和 `stderr` 两条都要,不许只管入口那行提示。**
  `announce()` 只保证入口自己「先装防线、再说话」;摆盘途中还有别人替我们说话,而且两条通道上都有 ——
  阅读页和片段那两个夹具要先调 `kb.cli._index_pass()` 建索引,它完成时那行 `print` 走普通 stdout;七个
  ASGI 入口导入 `kb.server` 那一路会发弃用警告,`kb/store.py` 导入的 jieba 还会按
  `logging.StreamHandler(sys.stderr)` 把初始化日志**同步**写 stderr。默认缓冲下那点东西留在 Python 的缓冲
  区里,所以满管道的烟测照旧能开页面,**那是偶然**;`-u` / `PYTHONUNBUFFERED=1` 下它立刻落到底层 fd,手起
  又没人消费那根管道时,进程就堵在建库里,`install()` 根本没跑到,唯一那道空闲防线一行都没装上 —— 这一刻
  两个自退条件都没在跑,`KB_FIXTURE_IDLE` 设多小都没用。所以边界立在 `fixture_voice.py`:**模块一加载就把
  fd 1 和 fd 2 都换成谁都堵不住的管子,`install()` 那一刻换回真身**(每条一个守护线程一直读着,读出来的进
  那个有界队列,真没人消费就按老规矩丢掉)。八个入口都在这个窗口里面,将来谁在摆盘阶段多打一行、哪个依赖
  多写一句日志,都不用再想一次。三点要记住:①这个边界只在**夹具进程**里立(按 `sys.argv[0]` 判),被测试
  import 进来时换掉那两个号会把别人的输出一起吞掉;②`dup2` 改的是**我们自己这张 fd 表**,不是那个共享的
  open-file-description,所以它跟「不许给借来的 fd 设非阻塞」不冲突;③`_say` 要在入队那一刻就把 1 / 2 换成
  `os.dup` 出来的真身,否则自己的话会被送回搬运线程绕一圈。
- **这道边界立不起来就当场退,不许「算了接着跑」。** `dup` / `pipe` / `dup2` / 搬运线程任意一步失败,上一
  版都是直接 `return`:接下来**可能**一切正常,也可能在摆盘途中某一次别人的同步输出上永久阻塞 —— 正是上面
  那个「一道防线都没装、进程永久留着」的形态。退掉只是一次看得见的启动失败(`_wait_listening` 当场报 `rc`、
  `fixture_server` 报启动失败),留下来才是静默漏一个永久夹具。**用 `os._exit` 不抛异常**:抛出去 Python 要
  把 traceback 写到 stderr 上,而「stderr 现在写不写得动」正是判不准的那件事,一写就可能永久卡住 —— 那是把
  「漏一个在服务的夹具」换成「挂一个什么都不干的进程」,没换好。理由走那个有界队列、给它半秒,说不出来也
  照样退。另外**先起搬运线程再换号**:反过来的话线程起不来那一瞬间 fd 1/2 已经指着一根没人读的管子。
- **「少一道防线就等于没有防线」对每一道必需的后台线程都成立,所以那个出口只有一个、分两档。** 摆盘边界
  之外还有两道也是线程:说话那一侧的搬运线程、空闲那道的看门狗。任意一道起不来时裸着往下走,留下的都是
  同一个形态 —— 一个什么都不干、谁都不收的永久进程。所以三处共用一个 `no_defense`,而它必须**看自己在谁
  的进程里**:在夹具入口进程里 `os._exit`(抛出去要把 traceback 写回「现在写不写得动正判不准」的那个
  stderr);被 import 进**测试主机**时只许 `raise` —— 在那里 `os._exit` 会把整轮测试连同所有人的清理一起
  带走,别人起的夹具也跟着漏,那比原本要防的那一个严重得多。
- **装配顺序本身是不变量:最后一道防线先起来,才撤摆盘那道边界。** 反过来的话,线程起不来那一瞬间边界已经
  撤了,它的 traceback 要写回一根可能堵着的真 stderr,进程就挂在那儿 —— 既没开出端口,也没退。另外那个幂等
  标志只许在线程**真的起来之后**置位:提前置上,后面每一次 `install()` 都会被它挡掉,而第一次其实没装上。
- **裸 fd 一申请成功就登记回收,别指望后面那个 `finally`。** `os.pipe()` 之后写 token、拼 env、`Popen`
  都可能抛(解释器不在、工作目录没了、权限不足、fd 用光),抛在那里就到不了 `finally`,而裸 fd 没有
  Python 对象替它收。最难受的是「快到打开文件上限了」这种失败:失败本身还在继续吃掉本该释放的资源,
  重试越多越快撞墙。关的时候走一个待关集合,**不要 `suppress(OSError)` 双关** —— 号被关掉之后可能立刻
  被别处复用,对着一个已经不是我们的号再 close 一次,关掉的是别人的东西。
- **嵌套起来的那个测试壳,它那本清理账也是一种资源 —— 壳一存在就得把账交给外层。** 这一块有好几条用例
  要在用例里再 `起与收()` 一个壳、让它去起真夹具,然后断言「壳的清理跑完之后那个夹具没了」。外层 runner
  **不会**去翻另一个 `TestCase` 的账本,所以中间任何一步抛出来(壳里起夹具失败、断言在清理之前就红了),
  内层登记好的那些清理就一条都不跑,它起的真夹具留在后台。口径是 `self.addCleanup(shell.doCleanups)`
  **紧跟在壳建出来那一行**之后 —— `doCleanups` 幂等,正常路径上再显式翻一次账也不会重复收。这跟上面「进程
  一建出来就要有人认领」是同一条规则,只是这次漏的那层资源是**账本**本身。表示级的守卫在
  `tests/test_probe_contract.py`:谁实例化了那个壳,同一个函数里就得有那一行。
- **跨进程交回来的消息要无损编帧,不许用分隔符拼。** 中间进程要把端口、pid、那份临时根的路径一起交回来,
  上一版按空格拼一行、收的那头 `split(" ")` —— **临时目录的名字里合法地可以有空格**(`TMPDIR` 自己就可能
  带),那一刻路径被截成两截,核前缀那一步当场对不上,收根的 `addCleanup` 登记的是个错路径。换 JSON:它自己
  负责转义,新加字段也不用再数位置。「换成别的分隔符」不算修 —— 空白不只有空格一种。

- **内层再跑一轮 unittest 的那种子进程,整棵树的最终回收责任在外层。**
  `subprocess.run(..., timeout=...)` **只 SIGKILL 直接那个子进程**:被强杀的测试运行器一条
  `addCleanup` 都跑不了,它起的中间进程和夹具就都没人收。这一刻三道防线同时失效 —— 夹具的
  owner 写端攥在**活着的**中间进程手里,EOF 那道不会响;那几条用例起的又正是 `idle='0'` 那
  一档,空闲那道本来就关着;收场那道要进程自己走到才算。实测把一个内层运行器在起好夹具之后
  按住到外层 deadline:运行器没了,中间进程和夹具都还活着、页面 200、那份根也还在。所以口径
  只有一份(`_run_nested`):给内层一个**独立会话**(它的 pid 就是那个新组的 pgid,按组收,
  不按端口或脚本名去猜别人的进程),再给它一份**隔离的 `TMPDIR`**(里面留下的根由我们删,
  同样不按名字猜别人的目录)。
- **「等到它退出」和「可以不管它的后代了」是两件事,所以组首不能是内层自己。** 把内层直接起成
  组首的话,拿退出码这件事本身就把尸收了 —— 而 pgid 的归属证明跟着消失,后代却可能还活着:
  内层被外部杀掉时它压根没跑自己的清理。实测两条出口各留下一个在服务的夹具(中间进程也在、
  页面 200),而外层一切正常、清理全跑完。所以中间加一个**锚点**:它是那个新会话的组首,起
  内层、等内层退、把退出码**原子地**(先写再改名)落到文件上,然后自己退掉;**它的尸只由
  回收那一处收**。于是从起跑到我们自己放手,那个 pgid 一直被它占着(组里只要还有成员、
  **僵尸也算**,内核就不会把这个号分给别人),按组动手的证明始终成立。`returncode` 一旦有值
  就什么都不做 —— 那是回收那一处自己收过尸了(口径同 `_mine` 的 holder 那条:证明用不上就
  不动手)。
- **所有终态走同一条收场路,而且不能只挂在 `addCleanup` 上。** `unittest` 遇到
  `KeyboardInterrupt` 会在 `_Outcome.testPartExecutor` 里把它一路往上抛,`run()` 里
  `self.doCleanups()` 那一行**压根不执行** —— 外层被取消时「进程一建出来就登记回收」一个字
  都不算。实测:外层 rc=-2、日志是 KeyboardInterrupt,内层运行器、中间进程、夹具三个全活着、
  页面 200。所以正常退、超时、内层被外部杀掉、外层自己被取消这四条,都从那个函数自己的
  `finally` 过一遍:**先按组收、再收尸、读完那几份输出、最后把两份目录都删掉**。顺序一条都
  不许反 —— 根删在前面的话服务还活着就没了工作目录,读排在删后面什么都读不到;**两份目录都
  得在这儿删**,只挂在清理上的那一份在取消那条路上每次留一个。
  调用方「那个目录底下什么都不剩」的断言也排在清理**前面**,这是同一个理由的另一面。
- **取消是一个验证出口,它一样要走完清理 —— 而这条得补在基类那一层,不是逐个创建点补。**
  上一条说的是**助手自己的** `finally`;可一条普通用例直接起的夹具压根不经过那个助手,它靠的
  还是 `addCleanup`,而取消这条路上那行清理压根不执行。实测两个创建点各一次:直接起一个手起档
  的夹具、隔着中间进程起一个,给运行器发 SIGINT 之后 rc=-2,而夹具(以及那个中间进程)都还
  活着、页面 200 —— 那一档是 `idle='0'` 又没有 owner,三道自退防线全关着,它会一直在后台服务
  下去。所以在 `起与收.run()` 里接住 `KeyboardInterrupt` 再跑一次 `doCleanups()`:**所有创建点
  (直接起的、隔着中间进程的、认领来的孙进程、起独立会话的)共用同一个清理栈,补一处就都管了**。
  `doCleanups` 自己抛什么都不许盖掉取消那个异常;而 `KeyboardInterrupt` 不是 `Exception` 的子类,
  所以第二次 Ctrl-C 照旧打得断这段收场。
- **「调用过 `killpg`」不等于「整棵树已经退出」。** 信号是异步投递的,而按组收完下一件事就是读
  输出、删那两份目录 —— 删早了等于把一个还在服务的夹具的 cwd 抽掉。所以在那儿等到那一组里除了
  组首之外都走掉再往下,**探测必须排在收尸之前**(组首的尸还占着这个 pgid,内核就不会把它分给
  别人,这一轮探测问的才是我们那一组)。判据自己写一遍 `ps -eo pid=,pgid=` 过滤,不用 `ps -g`
  (各家对它的解释不一样,有的按会话首算);**量不出来一律当「还剩着」** —— 判不出来当成「都走
  了」正是「等了 0 毫秒就去删目录」的形态,等满上限顶多慢 5 秒。
- **拥有它的那个进程自己没走到收场时,跨会话那棵树按账兜底。** 助手的锚点必须 `setsid` 成自己
  那一组(否则按组收会打到调用方自己那一组),于是**外层那一组的 `killpg` 到不了它**;而外层被
  强杀的时候那条 `finally` 一行都不跑,跨会话又没有「按会话杀」这种系统调用。实测:让用例在它
  的断言之前先抛个普通 `AssertionError`,登记的清理**全部正常执行**,而锚点、内层运行器、中间
  进程、夹具四个全活着、页面 200。所以内层**立一本账**:把那几个号连各自的身份在同一刻一起写
  下来(身份串里有空格,这份账走 JSON;先落 `.part` 再改名,读到的一定是整份),外层按这本账
  逐个收,判据仍是 `_mine` 那一份。`_identity` 量不出来照旧抛 —— 那会儿账还没立,读账那边看到
  的是「压根没有这份账」,用例当场红,不会变成静默漏一棵树。
- **身份这一问不许需要「届时还申请得到新资源」。** 原先只有 `ps` 一条路,而那是起一个子
  进程 —— fd 紧张时建管道/fork 当场失败,于是**已经创建好的那棵树在最需要收的时候反而判
  不出归属**。实测真把软上限压到 64 占满:账在、也读得出来,外层也收掉了,内层四个进程
  和页面照旧 200,缺的只是「再 fork 一次」。所以主路改成内核那条纯系统调用
  (`sysctl` 读 `kinfo_proc` 的 `__p_starttime`,不用 fd 也不建进程),`ps` 留作后路。
  三件事连带钉住:**①偏移要自己核**(偏移 40 处的 `p_pid` 必须等于问的那个号,对不上是
  「判不出来」,不许当成身份 —— 靠一组猜出来的偏移回收进程会杀掉别人);**②一条路走到
  底、不混用**(内核给到微秒、`ps` 只到秒,记的时候用一条收的时候用另一条就一定对不
  上,所以这个选择在模块加载时定下来,跨进程的内层/外层也是同一条);**③两条路各有
  自己的回归**,后路那几条注入要显式切回后路再打桩,否则桩压根打不中。
- **一项判不出来不许放弃其余项。** 按账回收是个循环,上一版第一个号抛出去之后剩下几个
  连试都没试过 —— 实测 fd 紧张那一次漏的就是后面那三个加一个在服务的页面。全部试完,把
  失败的攒起来一起抛(抛仍然是响的,只是不再顺带放过别人)。
- **「账上没有」不能证明「那边没起东西」。** 账原先是整棵树起齐之后一次性发布的,于是从
  第一个进程跑起来到发布完成之间,**整棵树和页面都已经可用而正式账还不存在**;实测在那个
  窗口里取消:取消收场确实跑了,回收因为文件不在直接返回,四个进程全在、页面 200。所以
  两处一起改:**创建任何东西之前先立开工标记**,**一个号一拿到手就记一笔**(一行一条
  JSON、`O_APPEND` 追加,半截只会出现在最后一行,读的时候丢掉没有换行结尾的那行就行)。
  判据随之变成:没开工 → 安静;**开了工而账上一条都没有 → 抛**(判不出来不许返回「确定
  没有」)。逐笔追加还有一层好处:它不需要「先写 `.part` 再改名」那种整份发布,而整份发布
  正是那个窗口的来源。
- **「回调开始执行」不等于「回收已经完成」。** `unittest` 执行一项 cleanup **之前**就把它
  从栈里弹掉了,于是第一次取消正好落在那一项里面时,它既没跑完、也不在栈上,再跑一次
  `doCleanups()` 也找不回来 —— 实测取消落在身份那一问上:外层已经退出,内层四个进程和
  页面照旧活着,而账本反而被剩下的清理删掉了。所以关键回收都经 `_担上` 登记:**进这一项
  之前记上,跑完才划掉**,`run()` 收尾时把没划掉的再跑一遍;被打断的那一项**原地再试一
  次**,**第二次取消照旧放手**。那本账要**懒取**,不许靠 `run()` 先跑过 —— 有一类用例直接
  实例化裸壳、自己跑它的 `doCleanups()`,那条路上 `run()` 压根不经过(实测:漏了这一点会
  让那两条用例当场红在「内层那本账没人翻」上)。
- **回收和它依赖的那份证据是同一个责任单元 —— 一起成,或者一起留着。** 上一版把「删这份
  目录」单独登记在清理栈上,而取消那条路上是「先跑剩下的清理、再补跑被打断的那一项」。
  于是剩下的清理先把目录连账本一起删了,补跑那一下读到的是「没开工、没有账」—— 待办被
  划掉而整棵树留在后台(实测:补跑时账本和开工标记都已经消失,四个号全在、页面 200)。
  **账本是重试唯一的依据,不许排在重试前面被别人释放掉。** 两处一起改:删目录挪进回收
  那一项里、排在它**之后**;取消路上**先补跑、再跑剩下的清理**。两道各能救同一个形态,
  所以反向验证要**两处一起注回去**才看得到红。同理,「进程收干净了」才动它交出来的目录,
  「整组还有成员没确认退出」时那两份目录一个字都不动 —— 「已经尝试过按组收」不是安全
  释放依赖的依据。
- **「账上有几笔」不等于「这几笔覆盖了全部已创建的后代」。** 上一版在那个助手**返回之后**
  才记它内部起的中间进程和夹具,可它内部就已经把两个都起起来、还等了页面就绪 —— 那段时间
  里树是活的,账上却只有先记下的两笔。实测:让拥有它的那个进程挂在那个助手**里面**(于是
  它一行收场都跑不了)、而整棵树又在它自己的会话里(外层那一组的 `killpg` 到不了),按账
  兜底只收得到先记下的两个,中间进程和夹具留在后台 —— **那道「开了工而账空就抛」的检查
  被「账上有两笔」整个绕过去了**。所以交接挪进创建点自己里面(`_记`):一个号拿到手就交
  接,排在「等页面就绪」之前;两份由子进程建的目录同理(`_记目录`)。
- **「已经试过一次」不等于可以放手。** 补跑里普通失败原地再试一次(第一次失败多半是依赖
  还没就位),两次都不成才划掉**并且说出来** —— 静静划掉就是把一个可能还在服务的后代丢
  在后台。
- **身份那一问要逐平台覆盖,不许拿一个平台的通过写成所有平台的保证。** macOS 走 `sysctl`
  那条不用 fork、不用 fd 的路;Linux 走 `/proc/<pid>/stat`(一次 open/read,比起子进程便宜
  一个量级,但**仍然要一个 fd**,真的一个都不剩时照旧判不出来 —— 那一刻落到 `ps` 后路,
  两条都不成就抛,仍然是响的)。解析那一行有两个坑:进程名在第二个字段里**带括号、里面
  什么字符都可能有**,所以要从**最后一个** `)` 之后开始数字段;第一个字段要核,它必须等于
  问的那个号(口径同 macOS 那条的回声自校验)。**Linux 这条路没有在实机上验过**,这里只
  钉住它的解析和三种结果的形状。
- **账本路径和那条兜底的登记,必须从同一个出口出来。** `_开账` 既给路径、又把「按账收」和「删
  那份目录」一起登记上,登记顺序在那儿定死:**按账收先跑、删目录后跑**。分开写的话「拿了路径、
  忘了登记兜底」这种漏法不会在任何一条用例上报红,只会在后台留下一棵还在服务的树 —— 所以验它
  的那条用例也**跑自己的清理栈**,而不是直接调那个兜底函数。
- **立那道输出边界的过程本身,也不许依赖旧输出写得动。** 上一版是「先把 Python 层缓冲倒给真
  fd、再换号」。真管道满了又没人消费、而缓冲里确实有东西(包装程序在 import 入口之前打过一段
  **不带换行**的字)时,那次同步 `flush()` 就永久停在那儿 —— `suppress(Exception)` 接得住
  异常,**接不住阻塞**。而这一刻 owner 和空闲两道看门狗都还没装(`fixture_life` 是在自己模块
  体里 import 这个模块的),没有任何更晚的硬退出能打断它。所以顺序倒过来:**先换号,再倒
  缓冲**。换完号之后倒进的是那根一直有搬运线程读着的管子,那点旧内容照旧出得去(经队列写回
  真身,同一条通道上先后不乱),堵也只堵搬运线程,主线程照旧把余下的防线装完。「改调用方
  fd 的阻塞状态」照旧不许用来绕开它。

- **`tests/test_fixture_life*.py` 是 `test_no_test_launches_a_sandbox_server_itself` 唯一的例外,而且
  必须是**:它那条验的正是**夹具自己**退出时删不删得掉那份根,所以不能给 `KB_FIXTURE_ROOT` —— 走
  `fixture_server` 的话根归父进程,它的 `finally` 会把结论盖掉,收场信号改错了也照样全绿。

## 事故形态与实测证据

- **后台起法下第一道被架空:裸 server + 继承的 `SIGINT=SIG_IGN`,退出码 -15、临时根留在盘上。**
  实测四格(裸 server / uvicorn × 继承 SIG_IGN / 不继承):**只有「裸 server + 继承」这一格**退出码
  是 -15,另外三格都是 0 —— uvicorn 自己装 handler 盖住了,前台起法压根不触发。**它不报错**,唯一
  的外在迹象就是那个退出码,所以「退了就算」这种放宽会把它整个放过去。

**在本机实测到 9 个孤儿夹具**:存活 20 小时到 10 天 22 小时,全部 `ppid=1`,占着 9 个高位端口
(50997、51005、51901、52312、53579、53948、58817、59358、64257),进程名在端口面板上显示为
`knowbase`。**8 个里 7 个所属的 worktree 早就删了**,进程还钉着那份已删目录里的 `.venv`,磁盘也跟着
不释放。它们是 `serve_workspace.py` / `serve_sources.py` / `serve_snippets.py` 三种。

**漏在哪一条路上**:`tests/headless.py` 的 `fixture_server()` 起的夹具是有主的 —— 它挑端口、建临时
根、在 `finally` 里 `reap()`。漏的是另一条:会话为了跑一轮界面探针,在 Bash 里直接
`python tests/serve_workspace.py --port 51005 &`。那个 shell 一退,夹具被过继给 init,而这些脚本本身
是裸的 `serve_forever()` / `uvicorn.run()`,**没有任何一方负责收它**。这不是三层防线漏了一层,是这条
路压根在 `run_probe` 的射程之外。

**顺带的存量**:同一天 TMPDIR 里有 300 多份 `kb-source-qa-*`,那是另一个口径
(`tests/fixture_root.py`)在它生效之前攒下的,跟这一块无关。

**这道防线自己踩过的三个坑**(都实测过,都在回归里):

- 收场发 SIGTERM:夹具 rc=-15,临时根一个没删,正是 `fixture_root.py` 记的那个事故重演。改 SIGINT 后
  rc=0、根删掉。
- 凭据按 pid 判陈旧:真调用方被 SIGKILL 之后夹具照样从摆盘途中继续开服务、端口还能访问 —— 副防线
  在最需要它的那个窗口里恰好不装。
- 读凭据用阻塞 `os.read`:环境变量 token 和管道内容对不上时**整个模块加载挂死**,日志里一个字都没有。
  症状是连一个进程都不起的用例也跟着卡住。
- 把 fd 2 设成非阻塞来躲开满管道:**调用方的 stderr 跟着一起变**,它自己什么都没做,write 开始抛
  `BlockingIOError`、输出缺行。
- `_leave` 锁里减到 0、放了锁才刷新完成时刻:中间那一瞬被看门狗判成空闲很久,慢请求回完 19 毫秒后
  夹具就退了。
- 按「脚本名 + 端口」清理:另一轮复用同一个端口的同型夹具被 SIGKILL 杀掉。
- 摆盘边界只圈 stdout:给真阅读/片段入口各一根填满的 **stderr**、`-u` 关掉缓冲,过了三倍空闲上限进程
  还在、HTTP 不响应、沙箱根还在;一开始读那根管子,它八秒内就起来服务、随后按空闲正常退掉 rc=0。
  「一开始消费就恢复」和「之后按 idle 正常退」一起排除了「只是建库慢」和「idle 没生效」两种解释。
- 身份取样排在清理登记之前:取样一抛,已有清理全部成功执行,留下的还是那个真夹具 —— ppid=1、页面 200。
- 回收判据认「凡 `AssertionError`」:真实的取样失败来自起 `ps` 那个子进程**本身** —— fd 不够时建管道或
  fork 就失败,内核给的是 `OSError`,它从判据里漏出去,`holder` 那条还能用的证明压根没机会用。实测把软上限
  压到 64 再占满号,清理当场中断,那条「没有 owner、空闲也关掉」的夹具留在后台,页面照样 200。
- absent 判据写成「非 0 就算没有」:`ps` 自己被信号杀掉时 rc 是负数、也没有 stderr,一个活着的夹具就这样
  静默变成「没什么要收的」。
- 必需的线程起不来却裸着往下走:实测两道各注入一次,进程挂在那儿到六十秒超时,一个端口都没开出来、也没退
  —— 挂住的那一步正是把 traceback 写回已经撤了边界、而且堵着的 stderr。
- 那个出口在**测试主机**里也 `os._exit`:实测整轮退出码 126、`Ran N tests` 一行都没打出来,别人起的夹具跟着
  一起漏。
- 嵌套的那个壳没把清理账交给外层:实测内层起的真夹具留在后台,而外层那条用例自己是红的 —— 红归红,进程照旧
  没人收。
- 交回来的那行消息按空格拼:把临时目录名换成带空格的,实测核前缀那一步当场对不上,那份根没人收。
- 内层那一轮用裸的 `subprocess.run(..., timeout=...)` 跑:实测把它在起好夹具之后按住到外层
  deadline,运行器被杀掉并 wait,中间进程和夹具都还活着、页面 200、那份根还在 —— 不是「清理还在
  慢慢跑」,是它压根没有机会跑。
- 倒缓冲排在换号之前:给一根预填满的真管道、在 import 入口之前往 Python 缓冲里写一段不带换行的
  字,两条通道各自都是进程活着、首页不监听,线程栈停在那次 `flush` 上;一开始消费那根管子它才
  继续往下跑、按空闲正常退掉。
- 把内层直接起成组首、只在超时那条路上收:两条出口各实测一次 —— 外层被 SIGINT 取消(`doCleanups`
  不跑)、内层被外部 SIGKILL(拿到退出码时尸已收、证明没了),后代都留在后台、页面 200,而外层
  那一侧看起来一切正常。
- 隔离目录只挂在 `addCleanup` 上:取消那条路上每跑一次留一份(里面是内层的输出和退出码文件)。
- 只把收场补在助手的 `finally` 里、没补在基类的 `run()` 上:两个创建点各实测一次 —— 一条普通
  用例直接起的夹具、以及隔着中间进程起的那一对,运行器 SIGINT 之后 rc=-2,它们都还活着、页面
  200。那两条压根不经过助手,靠的还是取消路上不执行的那行 `addCleanup`。
- 只按组收外层那一组:让用例在断言之前先抛个普通 `AssertionError`(清理**全部正常执行**),锚点、
  内层运行器、中间进程、夹具四个全活着、页面 200 —— 它们在另一个会话里,外层那一组的 `killpg`
  到不了,而外层被杀掉就跑不了自己的 `finally`。
- 账本路径和兜底登记分两处写:把那行登记去掉,整轮回归照旧全绿(验兜底的那条用例是直接调函数
  的),而后台留着一棵在服务的树 —— 所以那条用例改成跑自己的清理栈。
- 身份只有 `ps` 一条路:真把软上限压到 64 占满 fd(归还一个保证账还读得出来),账在、外层也
  收掉了,而内层四个进程和页面照旧 200 —— 判不出归属就一个都不敢动,缺的只是「再 fork 一次」。
- 整棵树起齐才一次性发布账:发布前那个窗口里取消,取消收场确实跑了、回收因为文件不在直接返回,
  四个进程全在、页面 200。
- 关键回收只挂在 `addCleanup` 上:取消落在身份那一问上(第一次,不是连按两次),那一项既没跑
  完也已出栈,外层退出而内层四个进程和页面照旧活着,账本反而被剩下的清理删掉了。
- 删目录单独登记、取消路上又先跑剩下的清理:补跑那一下账本和开工标记都已经消失,于是按
  「没开工就安静」划掉待办,四个号全在、页面 200。
- 交接排在助手返回之后:拥有者挂在那个助手里面(中间进程和夹具都已起来、还在等页面)、树
  在它自己的会话里,按账兜底只收得到先记下的两个,夹具留在后台。
- 原样跑一条用例、不注入任何故障:拥有者没走到自己的 `finally` 时留下两份空的验证目录
  (里面是内层的输出和退出码文件)—— 所以那两份目录也要交给外层那本账。

## 为什么不能照搬探针那边

`probe_shell.mjs` 盯 `process.ppid`,而且「没拿到环境变量就现读 ppid」—— 那边成立是因为探针由
`run_probe()` 起、一轮之内跑完,调用方全程活着,ppid 变了就**一定**意味着没人在等结果了。

夹具不是。它的生命周期**本来就**跨会话里的多个 Bash 调用,起它的 shell 当场就退是正常的。把
「ppid 变了」当判据的话,夹具一启动就判自己是孤儿、当场退出。

所以两边的凭据不是同一个东西:探针读 `KB_PROBE_PARENT`(一个 pid,没拿到就现读 ppid),夹具读
`KB_FIXTURE_OWNER`(一根管道的 fd 加 token,没拿到就**不装**这道防线、只靠空闲超时)。
**夹具这边不读 `KB_PROBE_PARENT`**,`headless.py` 里两个变量都设,各给各的那一半。

## 回归与反向验证

- 实现分两份:`tests/fixture_life.py` 管「什么时候该退」,`tests/fixture_voice.py` 管「话怎么说出去」
  (有界队列 + 两条通道的摆盘输出边界 + 立不起来就退)。**依赖单向**:说话那一侧不认识前者。
- 回归分三份,共用两个助手 —— `tests/fixture_life_probe.py` 是纯函数(等端口、造凭据、取身份、占高位号、
  复位状态),`tests/fixture_life_cases.py` 是要用 `addCleanup` / `skipTest` 的起/收基类。
  `tests/test_fixture_life.py` 打进程内那几层(判据、一致的那道边界、所有权凭据、身份判据、空闲上限的读
  法、两条适配路);`tests/test_fixture_life_outcome.py` 打后果(真起一个进程,断言「那个进程还在不在」
  「那份根还在不在」「客户端拿到的是什么」「调用方那一端的 fd 模式变没变」);
  `tests/test_fixture_life_identity.py` 专打「按身份收掉它」那一组。
- **那个起/收基类把 bare `Popen` 收在了一处,所以结构守卫要按「谁继承了它」判。** `test_probe_contract.py`
  原先只按「文件里有没有 bare `Popen`」扫 `test_*.py` —— 基类一抽出来,别的测试文件继承过去就能一行
  `Popen` 都不写地自己起沙箱服务,那条守卫一个字都看不见。所以既把那个助手文件带进扫描范围,又加一条按
  继承判的。
- **每一条该退的都配一条不该退的**:空闲到点要退 / 一直有请求不许退、在途没回完不许退、空闲的
  keep-alive 连接不算在途;原调用方没了要退 / 没有原调用方(手起、跨 shell 共用)不许退、非阻塞的凭据
  不许当成 EOF;闸门落下不接纳 / 没在收场照旧接纳;身份对不上不许碰 / 对上就得真收掉;
  空闲上限设 `0` 之后放着一天也不许退。后面那半边是这套设计的核心 —— 它一旦失守,会话就没法再手起
  夹具跑探针了。
- **那两处竞争不能靠两个线程去抢窗口,要在锁边界上看。** 放锁的那个线程还攥着 GIL,它在别人被调度起来
  之前就把下一把锁又拿回去了 —— 实测分两步落的版本在 2000 轮抢锁里**一次都没被抓到**,而毫秒级的空闲
  上限又会让循环本身的合法间隙随机变红(项目里记过这类时间预算型 flake)。所以换掉 `_COUNT`:在每次
  放锁时记一笔 `(在途, 完成时刻有多旧)`,断言**没有任何一笔是「在途 0 + 完成时刻很旧」**;再数一次
  `_check` 走一遍取了几次锁,必须是**一次**。两条都是确定的,不含时间预算。
- keep-alive 那道防线**不能用真夹具来钉**:夹具是 `HTTP/1.0`,一个请求就关连接,那个场景在它身上构造
  不出来,用例会永远绿在「服务端把连接关了」上。要钉就在测试进程内自己搭一个 `HTTP/1.1` 的服务器,
  读进程内的 `inflight()`。
- **「前台单跑全绿、后台跑同样那几条红」先怀疑信号处置,不要先怀疑负载。** 那几条「发一次 SIGINT
  模拟取消」的用例在后台起的链里压根测不到东西:整条进程链继承 `SIGINT=SIG_IGN`,那一下毫无动静 ——
  被发信号的那个要么照旧睡着(我们等到上限超时),要么自己正常跑完(退出码 0、stderr 一个字都没有)。
  两种症状看着都像「取消路径坏了」或者「机器太忙」,实际是**这条用例在那种起法下一个字都没验**。
  判法是确定的、不用猜:把 SIGINT 设成 SIG_IGN 再单跑一遍 —— 实测同一组用例前台 14 条全绿 44 秒,
  SIG_IGN 下同样那 4 条红、跑了 943 秒,和后台那一跑一模一样。出路是被发信号的那几个脚本开头把处置
  复位(说明写在 `_取消它` 上,口径只有一份),夹具自己那一侧见上面那条硬约束。
- **「机器一忙就随机红」是个很顺手的归因,所以它特别容易把人带偏。** 这几条红按时间预算处理过一轮
  (放宽等退出的上限、把钉死的退出码放宽成「反正它退了」),红照旧,而且顺带把那个真缺陷唯一的外在
  迹象(-15)也一起放宽掉了。**上限可以宽,判据不许宽** —— 分不清是哪一类的时候,先去复现它,别先
  动判据。
- **「端口关了」这个判据,得先立住「它曾经开过」。** 夹具的号由中间进程交回,而它吐 pid **不等孙进程
  listen**。所以注入点一旦落在「等页面就绪」**里面**,那一刻端口对好坏两版都是关着的,判据恒绿 —— 只
  在机器被别的活拖慢十倍时才偶然红一次,看着像反向验证成立,其实量的是时序(项目里记过这类时间预算型
  flake)。凡是经由「等页面就绪」或账本里那笔端口拿到的号,才自带这个前提(那笔记在助手返回之后);绕
  过它的时候就改判**那几个号还在不在** —— 中间进程睡着、夹具那一档不自退,这个判据跟机器快慢无关。
- 身份对不上那条断的是**退出码**不是「`ps` 里还在不在」:那是测试进程自己的子进程,收掉之后在被
  `wait()` 之前是僵尸,照样列在 `ps` 里。
- 结构守卫在 `tests/test_probe_contract.py`(沙箱根的所有权、谁可以自己起沙箱服务;例外覆盖上面那两份)。
- **反向验证按定点注入做,每处只改那一句**:`claim_owner` 回到阻塞读 / 不比对 token / 改借来 fd 的模式、
  `_watch_owner` 回到阻塞读、把 fd 2 设成非阻塞、访问日志走原生 `sys.stderr`、`_leave` 分两步落、
  `_enter` 去掉收场闸门、`_check` 分两次取锁拼判据、`should_exit` 去掉 `busy == 0` / 让 `gone` 等在途
  回完、`guard` 不排除 `lifespan`、`idle_limit` 不挡非有限值、收场信号改回 SIGTERM、所有权防线等到
  `install()` 才装、在途从 `handle_one_request` 进门算、两条适配路各自去掉在途计数、`serve_workspace`
  不装 `install()`、`fixture_server` 不把读端传下去 / 让管道裸着撑到 `Popen` 之后、`_reap_pid` 只比
  脚本名、`_reap_stopped` 先 SIGCONT 再核验、按异常类型分类(凡 `OSError` 一律当成凭据无效)、身份掺回
  命令行 / 省掉 pid、量不出身份时静默回空串、高位用例全开完才登记回收、摆盘阶段不立输出边界 / 只圈
  stdout 不圈 stderr、边界立不起来就「算了接着跑」、身份取样排回清理登记之前、`_mine` 去掉 holder 那条
  不靠取样的证明、别的测试文件继承那个起/收基类、`_mine` 回到认「凡 `AssertionError`」、`_identity` 不把
  起 `ps` 的 `OSError` 转成 `IdentityUnknown`、absent 判据回到「非 0 就算没有」、搬运线程与空闲看门狗各自
  起不来时裸着往下走、`install()` 回到「先撤边界再起最后一道」、那个出口去掉两档、嵌套的壳不把清理账交给
  外层、交回来那行消息回到空格拼、内层运行器回到裸的 `subprocess.run(..., timeout=...)`、倒缓冲
  排回换号之前、某一处调用点绕开那个助手(扫源码的那条)、内层直接当组首并只在超时那条路上收
  (上一版的完整形态)、按脚本名杀而不是按组杀 —— 每一处都有对应的红。
- **输出边界那一条两条通道各一份红,而且都断在后果上。** stdout 那条用满管道 + `-u` 跑真阅读入口,
  stderr 那条同形;断的都是「照旧起得来服务、空闲到点照旧自己退」,不是「那行字打出来了没有」。
  「立不起边界就退」那条在真入口上定点注入 `os.pipe` 的 `EMFILE`,断的是退出码加「一个端口都没开出来」
  —— 注入回「算了接着跑」的版本会真把服务开起来、rc=0,红得很干净。**八个入口都实测过**:常规一轮、
  stdout+stderr 两条都灌满再一轮,十六次全部起得来(首页 200)、rc=0、端口不再监听、沙箱根删掉
  (`jieba.cache` 是 jieba 自己的缓存,不算夹具沙箱)。边界本身只有一处实现(模块加载时的那一下),
  所以逐入口再钉一遍等于把同一行钉八次,入口那一侧只留烟测。
- **「创建到可靠回收之间不许留窗口」要两个窗口各一份红,再加一条反过来的。** 登记前失败那条:在取样处
  定点注入它自己声明的 `AssertionError`,**先确认那个夹具真在服务**,再把壳的清理照常跑完,断言进程没了、
  端口也不响应了。回收时失败那条:正常起好之后只在那一次回收取样上注入,断言它照样收得掉。反过来那条:
  身份还没量出来、又没有 holder 时**必须抛**,而那个无关的进程一个字都不许碰。
- **那条「真 `fixture_server` 给得出凭据」的用例要自己收掉那份临时根。** 它故意 SIGKILL 中间进程,于是
  中间那边 `fixture_server` 的 `finally` 一行都不跑,实测每跑一次在 TMPDIR 里留一个空的 `kb-fixture-*`。
  所以让中间进程把根的路径一起交回来,由用例 `addCleanup` 收 —— **路径是从子进程输出里读来的,送进
  `rmtree` 之前要核一遍前缀和它在不在临时目录底下**。整组跑完之后 TMPDIR 里一个新目录都不该多。
- **身份那一条要两头各一份红,而且构造出来、不靠机器忙。** 「掺进会变的东西」那一头:fork 之后先睡两秒再
  `execv`,把 exec 前那个窗口**撑开**,断言在它换命令行之前记下的身份换完之后照旧收得掉。「把 pid 省掉」
  那一头:**把同一秒里起来的那一对构造出来**再断言身份不同 —— 原先只有「同型夹具一个字都不碰」那条会撞上
  它,而两次起进程落不落在同一秒要看机器,那是项目里记过的时间预算型 flake。另外补一条表示级的:判据只有
  一份,别处不许自己去 `ps` 里捞启动时刻(扫源码时需要把 needle 拼出来,否则那一行自己就被扫中)。
- **「准备阶段污染整轮」那一条的红要落在后果上,不是落在「它红了没有」。** 断言顺序是:漏没漏下开着的号、
  后面还能不能开文件,**然后**才是「该跳过而不是红在半路」。注入时量到清理跑完还剩 125 个开着的号。
- **注入要忠实到那一版的完整形态。** 把那句列表推导换回去、却留着抬上限/跳过那一段的话,子进程里直接走
  跳过分支、压根到不了那句推导 —— 红 0 条。这跟「反向验证要定点注入」不矛盾:定点指的是**只改那一处逻
  辑**,不是只改其中一行。同理,引用一个**不存在**的测试名也会让 `unittest` 返回非 0,那是**假红**。
- **验「收得掉」之前要先收掉它的父亲。** 中间进程还活着又永远不会 `wait()`,孙进程被 SIGKILL 之后会以
  僵尸的身份一直列在 `ps` 里,`_wait_dead` 永远等不到它消失 —— 口径同上面那条僵尸。
- **注入之后红 0 条先怀疑用例。** 这一块量到过三次:访问日志那条原先只验「退得掉」没验「别的请求回得
  出」;keep-alive 那条用真夹具构造不出来;那两处竞争靠抢窗口抓不到。三次都是用例不敏感,不是冗余 ——
  改完用例之后各自都有红了。**还有一例是注入点选错**:`IdentityUnknown` 是 `AssertionError` 的子类,所以
  单把消费方的捕获放宽回「凡 `AssertionError`」是**行为中性**的,真正的修复点在「起 `ps` 失败那一次转换」
  上。补一条「不是量不出身份的那种错不许被吞掉」把窄化本身钉住之后,两处才各自敏感。
- **注入的异常要用那个接口真的会抛的类型。** 在取样处注入一个比它声明的更宽的异常,钉的就不再是「判不出来
  时怎么办」,而是「什么都接得住」—— 接口一收窄,那条用例自己先红,而被钉的行为其实没坏。
- **「整棵树都收掉了」要按终态分别钉,四条路一条都不能靠另一条代表。** 正常退和超时那两条由
  既有用例钉着;另外两条各要一个外层子进程:**外层被取消**那条给它发 SIGINT,**内层先退**那条
  从外面把内层运行器 SIGKILL 掉。两条都要先确认前提(账本真写出来了 = 内层确实起到了夹具;
  外层的日志里真有 `KeyboardInterrupt` = 走的真是取消那条),再断言后果 —— 那两个号都没了、
  端口不响应、那份根不在盘上。**判据不是「外层红没红」**:内层先退那条里外层是正常走完的。
- **按组回收要钉反面:该收的收掉,不该碰的一个字都不许碰。** 让一个无关的夹具跟它并存(那个
  夹具不在锚点那一组),真触发一次按组回收,断言它照旧活着、页面照旧开着。这一条对「按脚本名
  杀」那种写法敏感 —— 注入 `pkill -f` 之后它当场红。
- **扫源码的那条守卫要钉不变量,不要钉某一个函数名。** 它要的是「有按组回收的归属证明」,
  而那个助手只是实现它的一种方式;自己把两个必要件写齐的(独立会话 + 按组收且只在还没收尸时
  动手)也得放行,否则守卫会把正确的新写法判成违规。另外**`addCleanup(self._sweep_session, …)`
  里那个名字不是一个调用**,按「提到了没有」判,按「调了没有」判会漏。

- **取消这条出口要**逐个创建点**各钉一条,别只钉那个最复杂的。** 最容易漏的恰恰是最朴素的那个
  (一条用例直接起一个夹具),它压根不经过那个助手。断言排在清理**前面**,所以防线没生效时就
  是红的;随后那条按账的兜底照旧会把它收掉 —— **用例报红不等于把它创建的进程留在了后台**,这
  两件事得分开。还有一条:**SIGINT 只许发给运行器那一个号,不许按组发**(它起的夹具跟它同组,
  按组发等于我们自己把夹具杀了,用例会假绿)。
- **判据落在退出码上,不要对自己的子进程用「`ps` 表里还有没有这个号」。** 自己起的夹具被
  收掉之后是一具没人收的僵尸,照旧列在 `ps` 里,按那个判会永远红。别人的子进程(中间进程
  起的那些)由 init 收尸,消失得干净,那边才能用。
- **注入要落在真正在跑的那条路上。** 身份主路换成内核那条之后,原先打 `subprocess` 桩的几条
  用例**全都打不中了**(四条红,其中两条还是因为别的改动顺带暴露的真 bug)。后路的回归不能
  丢:那几条显式切回后路再注入;主路另给一条,把它的三种结果各钉一遍。
- **有两条保证造不出稳定的红,如实记在这儿,不要为它们造空壳用例。** ①「按组收完等整组走掉」:
  `SIGKILL` 不可阻塞,要让它可观察地延迟,目标得卡在不可中断睡眠里 —— 这是一条**顺序保证**
  (回来之后才删目录),不是某个能观察到的时间窗;注入「不等」之后整轮照旧全绿。②「组成员
  量不出来就当还剩着」:`ps` 在测试机上一直起得来,那条分支压根不进执行路径,而 fd 耗尽那一类
  形态已经由身份判据那条红覆盖了。**能钉的是那个判据本身**:给一个有后代的组,它必须把后代报
  出来、把被跳过的那个号排除掉 —— 这一条有红(把过滤条件写反当场红)。
- **「等满上限」不等于「确认退出」,那个事实要说出来。** 整组等待是尽力而为的(那一问自己
  也可能慢,所以它带 timeout),等满还有成员时打一行「未确认退出」并记下是哪几个 —— **只报
  不抛**:抛在收场里会盖掉调用方真正的结论,而那份目录留着也比删掉一个还在服务的夹具的 cwd
  安全。
- **烟测和审查脚本判「端口还开着没有」要直连,不许经过 HTTP 代理。** 这台机器的 `no_proxy` 里
  没有 `127.0.0.1`,`urllib` 对本机的请求会走代理:没人监听时代理回的是 502 或者干脆超时,而
  那跟「服务起来了但出错了」在判据上分不开 —— 量到过一次 502,差点读成端口泄漏。端口那一问
  用 `connect_ex`;真要走 HTTP 的那一问(首页回多少)自己带一个空的 `ProxyHandler`。
- **「内层被掐掉」那条红要落在后果上,而且要先确认它真起到了。** 断言顺序是:外层确实超时了、
  内层**真把那本账写出来了**(没写出来说明它还没起好夹具就被掐了,那条用例什么都没验到),
  然后才是那两个号都没了、端口不响应、那份根不在盘上。另外**注入那一版会真留下一个孤儿**,
  跑完要按它报出来的那个号收掉 —— 核对过命令行再动手。

- **`test_grab_probe` 本来就约一半概率红在「面板没装完」上,别记到这一块账上。** 它等的是面板里
  「同步全部」换成「写入知识库」,等不到就 60 秒超时。归因做过两道:①跑探针的同时每 0.5 秒采样夹具
  进程,一百多个样本里它**全程都活着**,所以不是哪道防线把它收了;②把空闲那道整道关掉
  (`KB_FIXTURE_IDLE=0`,owner 那道因为调用方全程活着本就不触发)再连跑,红绿分布照旧。
  **只拿一次绿就下结论会归因错**:这条用例单跑、连跑都可能绿,第一次量到的「关掉防线就绿」是巧合。
- **走 CDP 的那一批界面探针整体都会随机红,红的是哪几条每次都不一样。** 量到过:同一组五个套件
  连跑两次,红的用例三次互不相同;同一条单跑两次全绿;`tests/test_fav_snippets.py` 的
  `setUpClass` 则稳定红在探针那根 WebSocket 没连上(`snip_probe_lib.mjs` 里等 `open` 的那一行)。
  **判归因要在基线 worktree 上跑同一组**,而且不止一次 —— 量到过基线一次全绿、另一次红五条跨
  四个套件,比工作树还糟。再加一道:用 AST 顺着 import 把那条用例的依赖链列出来,看本轮改动的
  文件在不在里面。
