# YouTube 频道订阅与低成本内容处理

## 当前边界

这一轮先整理用户在 `/dr-dig-ytb` 来源池中维护的频道，为后续「订阅管理」准备底表，
并核对 `/dr-auto-ytb2b` 的内容处理链路；不运行这两个 skill 的刷新或搬运任务。

本轮产物是 `kb/youtube/defaults.json`。它还没有接入运行时，没有导入订阅数据库，
不会在界面新增频道、自动轮询、下载视频或调用模型。不要把「底表已准备」报成
「订阅管理已上线」。这是上游来源池快照，不是从用户登录的 YouTube 账户读取的订阅。

## 已确认的方向

- 保留排名，而且排名必须在下载和语音转录之前，作为是否值得花算力的准入机制。
- 不是每个关注频道的新视频都做深处理。未入选的视频只保留轻量候选信息和分数。
- 复用下载、语音转录和基于原始内容生成中文总结的能力，不移植整套搬运流水线。
- 第一版不启用画面理解、抽帧、OCR 或原生多模态视频分析，也不宣称信息无损。
- 不采用把 `/dr-dig-ytb` 已生成的榜单文章再次导入、摘要、汇总的旧视频报告链路。
- 不删除历史视频笔记，不停用其他来源的日报，也不在本轮修改现有日报运行行为。

目标处理顺序：

```text
频道订阅 → 轻量发现与元数据 → 排名、去重、预算准入
    → 仅处理入选视频 → 字幕或语音转录 → 中文内容笔记 → 新内容的日报素材
```

上面的最后一步消费的是本次入选视频的实际内容，不是对上游榜单文章再次摘要。
最终在哪个现有日报入口消费这些素材，留到接入实现时确定，不预设复用旧报告导入器。

## 频道底表及导入契约

来源为 `daily-report/data/ai_youtube_sources.csv`，2026-10-24 的本地快照共 52 条：

| 来源池 | 数量 | 后续订阅管理中的默认行为 |
|---|---:|---|
| `creator_core` | 38 | 出现在频道列表，允许进入轻量候选排名 |
| `interview_pool` | 10 | 出现在访谈池，先筛 AI 相关单集，再进入候选排名 |
| `creator_watchlist` | 4 | 出现在观察名单，不自动进入候选排名 |

完整原始名称、URL、类别、状态和备注均保留。`pool` 对应上游 CSV 的 `type`。
`channel_id` 从原始 `/channel/UC…` 地址提取，是后续频道去重身份，不以显示名称去重。
`provenance.sha256` 是原始 CSV 字节的 SHA-256，便于追溯快照；它不是远端频道有效性证明。

`ranking_enabled` 只表示是否参与候选排名，不代表已经导入、启用定时或批准下载。
它按来源池推导，不直接用 `status == core`：上游访谈池中有 8 条 `watchlist`，
但原 skill 的日常候选规则仍包含整个 `interview_pool`，不能迁移时静默漏掉。

保留 skill 的四个频道加权，用稳定频道 ID 定位：

| 频道 | `score_multiplier` |
|---|---:|
| AI Search | 1.25 |
| Two Minute Papers | 1.25 |
| AI News & Strategy Daily · Nate B Jones | 0.75 |
| Matthew Berman | 0.75 |

其他频道为 1.0。不要把 Nate B Jones 的降权误用到 Nate Herk。
后续评分对热度和价值分分别应用此系数，不据此直接决定下载。

未来接入订阅管理时，应把分组、状态和权重作为可编辑字段，按 `seed_revision`
做一次性、可重入导入；同时覆盖已有安装与新安装。用户修改、停用或删除后，不能在
每次启动时被默认名单覆盖或恢复。不要直接把底表塞进现有 RSS 默认源：当前尚无
对应的 YouTube 订阅和处理通道，那样只会产生看似已接入的错误状态。

## 排名和算力准入

保留 `/dr-dig-ytb` 的热度、播放增速、可取得时的频道相对表现、主题价值、标题噪声
及频道权重。保留热度榜和价值榜两个维度，避免只有播放量大的视频才有机会入选。

第一阶段只使用标题、简介、发布时间、播放信号等轻量信息，不为评分先下载全片，
也不为所有候选先生成转录；轻量评分是否需要模型调用，在实现时单独设置预算。
同一视频可跨榜展示，但深处理队列按 `video_id` 去重，只付一次下载、转录和总结成本。

第二阶段才从排名结果中按单轮数量、累计时长和资源预算准入；具体阈值暂未实现或确定。
入队与完成应分别留账。未入选、未轮到、转录失败不是一类状态，不能混为「已处理」。
候选可以在后续增速变化时重评，不把「曾出现在榜单」等同于「已生成内容笔记」。

默认延续 skill 对 Shorts、直播、预告和整段软广的谨慎过滤；访谈逐集判断相关性。
不要直接继承搬运流水线的「访谈一律停止」作为本系统规则，否则访谈池会变成摆设。
45 分钟门槛属于上游搬运策略；本系统的长视频预算应显式配置，不启动耗时任务等人确认。

## 对上游下载与理解链路的核对

`/dr-auto-ytb2b` 本身是编排器：刷新排名，取热度 Top 10，创建 `/dr-ytb2b` 任务，
并编排配音、渲染、复核链接与 Obsidian 同步；不是一个独立的视频理解引擎。

底层 `daily-report/youtube_pipeline.py` 的 `download_youtube` 使用 `yt-dlp`
下载媒体并保存元数据、缩略图；当前搬运配置下载高清视频，不能原样套进低成本收录。

同一文件的 `transcribe_video` 支持不同转录引擎；实际
`config/youtube_pipeline.bilibili_test.json` 配置为 `whisper-cpp`、`whisper-cli`、
`ggml-base.en.bin` 和 8 个线程。该分支先用 FFmpeg 提取 16 kHz 单声道音频，再做
本地语音识别，产出带时间信息的转录。它不是把全部视频画面送给视觉模型理解。

`/dr-ytb2b` 的「Video Content Summary」要求将视频元数据与转录或字幕提供给模型，
生成 `metadata/video_content_summary.md`，并记录模型、失败与回退日志。
因此可以复用其「真实内容 → 中文结构化总结」的产物契约，但不能据此宣称覆盖画面。
当前配置中的英文模型不应无条件用于其他语言，未来要单独处理语言选择和模型适配。

本项目的建议精简链路是：先复用可用且质量合格的字幕或已有转录；缺失时只下载音频，
做本地转录，再对转录进行分段事实提取和中文总结。字幕读取、音频单独下载是接入时
新增的节省策略，不是声称上游现有流水线已经按这个顺序运行。

保留原始转录、时间戳、处理状态和内容笔记，重试不重跑已成功的阶段。
本地 ASR 不消耗语言模型输入输出 token，但仍消耗本机资源；文本总结仍有 token 成本。
任务并发、线程数、每轮时长和缓存清理要设预算，不能直接照搬上游并发配置。
默认不做逐句全文翻译、字幕重排、配音脚本、TTS、MP4 渲染、上传或发布。

## 本轮验证范围

只核对本地 skill、上游代码和来源池；不启动榜单刷新、浏览器、下载、模型或搬运任务。
静态校验覆盖 52 条记录的字段完整性、频道 ID 格式与唯一性、上游字段逐项一致、
来源池计数、排名准入及四个权重。界面导入和端到端处理尚未实现，不在验证结论中。
