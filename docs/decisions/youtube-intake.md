# YouTube 频道订阅与低成本内容处理

普通同步使用带登录态 flat 列表发现，再按预算增量补齐元数据；精确快照在 6 小时后
进入刷新队列，未轮到的候选保留预排资格与未知/缓存说明，处理前仍须校准事实。
已完成或已排除的视频不因快照过期重复探测。显式日期补抓保留详细发现及原有总预算。
尚未轮到补元数据不等于频道失败；只有登录态/限流等出口级错误，或该频道整批候选
均探测失败，才把元数据错误升级到频道。单条失败与原有延后原因保留在视频上。
不升级为频道连接失败不等于同步完成：未解决的视频错误、正在处理、已尝试但未完成、
本轮取消都扣留成功覆盖，不清除订阅原有错误、失败次数和退避。只有未尝试的干净候选
可因元数据预算未轮到而豁免；这一判据不随六小时缓存过期改变。
实际请求后元数据不完整或中断，由存储层记录持久 `metadata_pending`，冷却期内仍是未完成；
成功补齐精确元数据或做成合格内容后才清除。纯待补元数据只附说明，不改变健康候选的
`candidate` 状态；真实处理延后才是 `deferred`。成功覆盖异常必须归入来源失败与本轮历史。
快照时间统一由存储层的精确 entry 写入口记录；同步告警与阶段耗时分开保存和展示。
本节后文历史「详细解析优先」和依据旧 DR 辅助脚本制定的发现预算已被此决策替代，
串行间隔、登录态、请求级熔断及发布资格要求不变。当前细节见 `../youtube-incremental-discovery.md`。

## 硬约束

- 本系统直接发现频道更新，不读取 `/dr-dig-ytb` 的成品榜单作为视频正文，也不启动搬运任务。
- 先轻量排名，后按预算处理；未入选视频不下载、不转录、不调用内容模型。
- **全程使用浏览器登录态**：元数据、字幕、音频和列频道都带 `--cookies-from-browser`，浏览器由
  `youtube.cookies_browser` 指定（接受 `chrome` 与 `chrome:Profile 1` 两种写法，校验口径只有
  `login.validate` 一份）。**我们自己不碰加密 cookie**：只把浏览器名交给 yt-dlp，由它去读、去解密；
  不读 cookie 文件、不解析、不落盘、不记日志，错误原文里只取分类用的特征串。**不打开、不接管、
  不激活浏览器窗口**，也不做任何写操作。访问受限仍必须留下可重试错误。
- **交给 yt-dlp 的那份 cookie 库要钉死在 profile 一级，不许被扩展分区顶掉**
  （`login.cookie_store` / `cookie_view`）。yt-dlp 自己的做法是在整个浏览器目录里
  `max(所有叫 Cookies 的文件, key=mtime)`（`yt_dlp/cookies.py` 的 `_find_files` + `_newest`），
  本意是「多个 profile 就用最近用过的那个」。但 Chrome 130+ 把**每个扩展的 cookie 分区**也命名为
  `Cookies`，摆在 `<profile>/Storage/ext/<扩展 id>/<序号>/` 下 —— 哪个扩展刚活动过，它就被当成
  「最近用过的 profile」。**实测本机**：主库 `Default/Cookies` 983 KB、19:33:24，内置扩展那份
  32 KB、19:32:09，**只差 75 秒**；同一分钟里跑两次同一条命令，一次读到 1843 条并打出
  `Found YouTube account cookies`，一次只读到 30 条、当场撞 `Sign in to confirm you're not a bot`。
  **这就是「明明登录着却时好时坏」的根因**：那一轮根本是以未登录身份出去的，而面板上只看得见下游
  那道墙，于是人被一次次送去重新登录。做法是在数据目录下搭一份**只有两个链接**的视图
  （`<profile>/Cookies` 和视图根的 `Local State` 各指向浏览器里那一份真文件），把视图的 profile
  路径交给 `--cookies-from-browser` —— yt-dlp 在视图里走一遍 `os.walk` 只看得见那一个 `Cookies`。
  **我们仍然不碰 cookie 本身**：一个字节都不复制、不读内容，改的只是「用哪一份库」。
  `Local State` 必须一起链上：Windows 的解密密钥从**视图根**取（`get_cookie_decryptor`）。
  几条反过来的边：**yt-dlp 的本意要留着**（多 profile 时照旧挑最近用过的那个，写死 `Default` 会把
  一个早就不用、而且没登录的 profile 交出去）；**点名了 profile 就只认它那一份**；
  **Firefox / Safari 不钉**（单文件存储，没有同名分区这回事）；**搭不起来就如实降级**（Windows 上
  建符号链接要特权，退一步试硬链接，两样都不行就照旧只交浏览器名，并在面板上说清这一轮没钉住 ——
  悄悄退回去等于让人继续猜）；**挑选这一步的任何 `OSError` 都不许外溢**（它挂在每一次 yt-dlp 调用
  的前面；`Path.is_dir()` 只替常见的那几个 errno 兜底，别的照旧往外抛）。
  回归 `tests/test_youtube_challenge.py`——**判据是「yt-dlp 按它自己的算法会读到哪一份库」**，
  用例里复刻了它那两行；只断言我们那个函数的返回值，等于把被测逻辑抄一遍。
- **准备视图的临时名要逐调用唯一，光有 pid 不够**（`login._link` 走 `diagnosis.serial()`）。
  真实并发是**同一个进程里的两个线程**：面板那颗「检查登录态」在 FastAPI 的线程里，同步在后台线程里，
  它们的 pid 一样。只带 pid 时的交错：线程 A 刚建好 `Cookies.<pid>.tmp`，线程 B 进来 `unlink` 掉它，
  A 的 `os.replace` 撞 `FileNotFoundError` → `cookie_view` 把准备失败降级成「只交浏览器名」→
  **yt-dlp 又回去在整个浏览器目录里挑最近被写过的那一份，正是上面那条要修的原问题**。
  序号用 `diagnosis.serial()` 而不是另造一个：进程内那个计数器只有一份（`media.unique` 给输出文件
  编号也走它），pid 管跨进程、它管进程内，合起来才唯一。
- **「这一次用的是哪一份 cookie 库」要跟那一次调用一起走，不许事后重算**
  （`login.arguments` 在 `diagnosis.COOKIES` 那条道上记一笔，`login._noticed` 和 `collector.caution`
  从账上读）。原先是面板在检查收尾时**再调一次** `cookie_view` 看「现在钉不钉得住」—— 那是另一次
  准备：刚才那一次因为线程撞车或权限不足降级了、这一次又建成功，面板就一个字都不说，人看到的是一次
  干净的结论，而它恰恰是以未登录身份出去的。同步那条路更彻底：它压根不调那个事后出口，一个字都没
  说过 —— 而它才是「抓回来的内容到底带没带登录态」的那一轮。几条跟着的边：
  **单独一条 `COOKIES` 道，不蹭 `YOUTUBE` 也不蹭 `LOCAL`** ——
  前者会让 `cross-device link`、`operation not permitted` 这种本机理由撞上 `login._COOKIE` 的宽特征、
  被报成「读不出 cookie，去钥匙串放行」；后者那一档是**失败**（`on_disk` 抛 `ToolFailure`），而这一条是
  「成了，但用的不是最想用的那一份」，东西照旧抓得回来。**并列，不互相顶掉**（它和 yt-dlp 说的那一档
  下一步完全不同，只报一件另一件就白搭）。**点名了 profile 路径的那一种不算降级**（`login._explicit`
  一份口径，`cookie_store` 和 `arguments` 都过它）—— 他正是为了绕开这件事才点名的，照「没钉住」报等于
  每一轮都劝他换浏览器。**说法只有一份**（`CAUTIONS[login.UNPINNED]`），检查和同步读的是同一句话。
- **JS 挑战的解题脚本随 yt-dlp 一起装，而且不走 `--remote-components`**
  （`toolchain.SOLVER` / `challenge()`）。YouTube 现在会对一部分请求发一道 JS 挑战，yt-dlp 要用本地
  解题脚本（`yt-dlp-ejs`）配一个 JS 运行时（deno / node / bun / quickjs）去算；官方可执行文件自带
  那份脚本，**pip 装的那份不带**，所以我们自备的环境要显式带上它。实测形态（cookie 完全正常、
  `Found YouTube account cookies` 1843 条）：`n challenge solving failed` →
  `Only images are available for download` → 默认格式选择器一个都没匹配上 →
  `Requested format is not available` **当场抛错**，连「检查登录态」都报错。装上脚本之后同一条命令
  打出 `Using challenge solver lib script v0.8.0 (source: python package)`、退 0、45 个格式里 8 个
  是纯音频。**不开 `--remote-components`**：那个开关让 yt-dlp 在抓取时从 GitHub/npm 现拉脚本，等于
  把一段每轮都要联网取、而且没版本锚的代码放进采集路径；本地 pip 包同一条渠道、跟 yt-dlp 一起更新，
  也能离线跑。几条跟着的边：**解题脚本装不上不许连 yt-dlp 一起不装**（它只影响下音频那一步，元数据、
  列频道、字幕照旧能跑；一起失败的话用户连版本都更新不了，而他点那颗按钮多半正是因为抓不到东西）；
  **缺脚本和缺运行时分开报**（前者点一次更新，后者得自己装个 deno，让用户做的事完全不同），读的是
  `yt-dlp -v` 的调试抬头（`Optional libraries:` / `JS runtimes:`，它不带 URL 时退 2、抬头照印，所以
  不看退出码）—— **问 yt-dlp 自己认不认，不去猜它的 site-packages**：自备那份和 PATH 那份住在不同
  环境里。
- **要让人装的运行时只有 deno 一个，不许说成「四个里随便一个」**（`login.RUNTIME`，面板和两处文案
  都指着它）。一手源码：`yt_dlp/options.py` 的 `--js-runtimes` 写着 `default=['deno']`，帮助里也写着
  Only "deno" is enabled by default —— **没显式启用的 node / bun / quickjs 它压根不会用**。
  本机实测：node 和 deno 都装着，`yt-dlp -v` 的抬头只印 `JS runtimes: deno-2.9.0`；显式加一次
  `--js-runtimes node` 才变成 `deno-2.9.0, node-26.4.0`。所以照「装个 node 就行」说等于让人白装一趟，
  而面板上照旧提示缺运行时。**所以 `JS runtimes:` 那一行印的是「启用且找得到」的，不是「机器上装了」的**
  —— 只装了 node 的机器上那一行就是 `none`，那不是读错了。**也不替他把那三个启用上**：未知开关会让
  yt-dlp 当场 `no such option` 退出（实测），而自备那份的版本由用户自己点更新决定；为此再探一次
  「这版认不认这个开关」要在每一次调用前面加一道缓存，**缓存错了就是每一条路全断**。代价不对等，
  所以只说实话。
- **能力探测的每一项都是三态，判据是「那一行抬头印出来了没有」，不是退出码**
  （`toolchain.challenge()` 返回 `UNASKED` / `''` / 版本号，外加 `challenge_error`）。
  **不许按退出码判成败**：不带 URL 的正常探测本身就退 2（实测）。原先两项初始化成空串、
  只在读到抬头时覆盖，等于把「没问到」说成「确实没装」—— 审查实测：`yt-dlp -v` 临时报
  `ERROR: temporary capability inspection failure`、退 1、一行抬头都没印的那一轮，面板照旧
  让人去装 `yt-dlp-ejs` 和 deno（机器上两样都在），真正的检查错误一个字都没显示；让同一个
  替身恢复抬头、**不装不卸任何东西**，那两句误报就消失了。落未知的有四种：没有 yt-dlp、
  探测报错、超时、输出里没有抬头（**只印了其中一行时另一项照旧未知，印出来的那一项照旧要认**）。
  面板那边**缺失一律判严格相等 `=== ''`** —— `!info.script` 把 null 也算成缺，等于把三态压回两态。
- **「这一项还没问过」和「问过了，确实没有」必须分得开**（`toolchain.UNASKED` / `local()`，面板
  `youtubeShowYtdlp` 据 `null` 判未知）。事故形态（审查在真实页面上实测）：便宜那条状态快照压根不返回
  `script` / `runtime` 两个键，面板拿 `!info.script` 判缺失 —— **缺席和空串都是假**，于是一打开订阅管理
  就红字说两样都缺，而那台机器上 `yt_dlp_ejs-0.8.0` 和 `deno-2.9.0` 都在；离开再回来一样，因为那条快照
  每次都这么答。`local()` 不起子进程（它是面板每次刷新都读的那一份），所以它答不了 —— 但**必须答出
  「我答不了」**。回归钉的是**集合**：`challenge()` 答的每一个键 `local()` 都要答（不然以后再加一项能力
  而忘了跟上，那一项在面板上又会变成「确实没有」—— 同一个类问题换个字段再来一遍）。
- **不下载的那几条路不许因为「没有可下载的格式」整条失败**（`media.ytdlp` 的
  `--ignore-no-formats-error`）。元数据、列频道、字幕**压根不需要任何格式**，却跟着格式选择一起
  失败。带上这个开关之后，同一次调用退 0、元数据照旧完整，那两句话降级成 warning 留在输出里
  （`yt_dlp/YoutubeDL.py` 里 `formats_to_download` 为空时就是这两条分支）——分档照旧看得见，面板上
  并列说出来。**下音频那一步不带它**：那里「没有可用格式」是真失败，带上之后 yt-dlp 会退 0、却一个
  音频文件都没下下来，我们只好报一句「未取得音频」，真正的原因就此丢掉，人照着去查磁盘和 ffmpeg。
- **失败分六档，分不清就都不说**（口径只有 `login.classify` 一份，顺序即优先级）：
  `cookie_unreadable`（读不出 cookie —— 去授权钥匙串 / 退出浏览器 / 换 profile）、
  `bot_wall`（出口撞机器人验证 —— **出口 IP 级，带登录态通常能过，换 yt-dlp 版本无效**）、
  `no_access`（这一条内容本身不可访问 —— 私有、会员专属、已下架）、
  `not_logged_in`（真的没登录或登录态失效 —— 去那个浏览器里登录一次）、
  `rate_limited`（出口被限流 —— 等一段时间、把一轮的量调小或换出口）。
  每一档让用户做的事完全不同，混成一句「登录失败」会让人反复去登录而问题在另一头；判不准一律落
  `unknown` 并原样交出 yt-dlp 那句话 —— 猜一个具体原因比承认不知道更坏。
  **cookie 那一档优先于一切墙**（它是因，墙是果），而 yt-dlp 把「解不开 cookie」只报成一条
  **warning**（`cannot decrypt v10 cookies: no key found`），所以 `--no-warnings` 不许加回去，
  这条特征串也必须认得出来。**`bot_wall` 和 `no_access` 都不蕴含未登录**：前者已经登录的人照样
  会撞上，后者只要第一个启用频道的最新一条恰好受限就会把整个账号判成未登录。
  **429 要排在 `bot_wall` 前面**：429 是「网页根本没下下来」，后面那些墙都是它的下游。真机形态
  （用户报的那一次）：YouTube 先回 429，yt-dlp 换别的 player 客户端重试，最后报出
  `Sign in to confirm you're not a bot` —— 两句话一起回来时照 bot 那一档说「带上登录态通常能过」
  是错的，他本来就带着 cookie，照着做只会再登一次。**特征只认 `http error 429` 和
  `too many requests` 两串**，别把「rate」「limit」这类词放进来：误判成限流会让人白等一个小时。
  还有一档是 `js_challenge`（那道 JS 挑战没解开 —— 见上面那条，**排在所有墙的后面**：上面那几档都是
  人要去做一件具体的事，而且都比挑战更靠前，429 和机器人验证甚至会让挑战这一步根本跑不到）。
  **它只认挑战自己那几句话**：光有「格式不可用」不算 —— 那也可能是这条视频真的没有音轨，那时让人去
  装 JS 运行时是帮倒忙，所以照旧落 `unknown` 原样交出原文。
  **判出来的那一档必须穿得过公共归并层**（`login.merge`）：那一层原先拿按证据强度排的
  `_STRENGTH` **兼着当白名单**，加 `js_challenge` 时没人记得同步第二份 —— 于是同步一条没有
  字幕的视频、去下音频撞上那道挑战时，分档一过归并就变成 `undecided`、完整原文跟着清空，
  视频失败详情里只剩开头那截普通工具输出，`collector.wall` 也收不到这一档、进不了失败归并
  （审查用真实子进程复现）。口径钉成两件事分开：**「有哪几档」只有一份名单**（`VERDICTS`，
  从 `_MARKS` 那张表派生，`classify` 也从同一张表走），**`_STRENGTH` 只排顺序**（`strength()`，
  没列进去的已识别档排在最后、照旧穿得过去）。两份名单的顺序本来就不一样（`classify` 把
  cookie 排第一，归并把 429 排第一：前者问「这段文本说的是什么」，后者问「这几条里哪一条最能
  解释这次失败」），所以不能合成一份；但**漏在排序那份里顶多是优先级垫底，不许变成「判不出来」**。
  回归 `tests/test_youtube_verdicts.py` 钉的是**集合**：`VERDICTS` 里每一档都要穿过去。
  反过来钉三边：排序照旧说话（429 + 挑战一起回来时说 429）、判不出来的照旧落 `UNDECIDED`、
  **白名单放开不许把别的上游一起放进来**（本机的 `permission denied` 进不了 `walls`）。
  **`AUTH_CODES` 则刻意不派生**：新加一档该不该整组归并要人判一次，逼人判的是那条集合级回归
  （加档时当场红）。两处要求相反是因为代价不对等 —— 漏在归并层是静默丢掉分档和原文，
  漏在 `AUTH_CODES` 只是这一档的失败不成组、每一条照旧看得见。
  **并列警告只许说得住的那半截**：`CAUTIONS['js_challenge']` 一度写着「这一轮只拿到元数据和
  字幕」，而同一句话也挂在失败路的摘要上 —— 审查实测的那一轮恰恰一条字幕都没有。表头那条
  「都不许断言内容已经到手」整张表一起钉（回归按 `CAUTIONS` 全表扫，不是只盯新加那一档）。
  **判准了还不算到位，它得落进库里、再被读回页面还是它。** 归并层修好之后这条链还断在末端：
  `storage.failed` 自己 `str(error)[:1000]` 落 `reason`/`last_error`，而**异常消息只是摘要**
  （`ToolFailure` 的消息是 `summary；excerpt(diagnostic)`，`media` 合并多条原因时又把每条裁到
  300 字 —— 那是摘要的本分，不是缺陷）。于是分档对、完整诊断对、`collector.wall` 也收对了，
  **候选排名那一行仍然只有开头那截普通工具输出**：既看不到那道 JS 挑战，也看不到「格式不可用」
  （审查用真实子进程 + 真实库 + 真实页面复现，视频行只剩「处理失败，待重试：python 执行失败；
  WARNING: ordinary download context …」）。**末端把上限从 300 调到 1000、1200 都补不回来** ——
  缺的不是字数，是「该读哪一份」。口径：**失败落库或上屏的文本只有一个出口
  `diagnosis.shown`，裁字只发生在那儿，每个数据库出口都不许自己再裁一刀**；
  `login.evidence` 只是它在订阅失败明细那一处的名字，实现不许再有第二份。
  **它交的是「摘要在前、权威诊断在后」，而且两份各有自己的预算、各自两头都留 —— 整句不许
  合起来裁一次**。合着裁的那一版后果是：多次失败把摘要堆到 600 字以上时，1000 字的视频行
  前半全被摘要占掉，**诊断开头那一行落进省略的中段**，而分档恰恰常是开头那一行定的。
  审查实测：人工字幕失败 → 自动字幕 en 失败 → en-orig 报 `HTTP Error 429`（在诊断开头）、
  后面跟着长重试上下文和末尾的机器人验证，`code` 和 `walls` 都是 `rate_limited`，而页面上
  那一行只有普通上下文和 `Sign in to confirm you are not a bot` —— **把「请求过多」显示成了
  「机器人验证」**，照它的提示去重新登录没有用。所以**决定性那一行在头还是在尾不是我们能
  预先知道的**（429 在头、格式不可用在尾，两种都实测过），诊断自己也要两头都留；
  **预算先给诊断**（它是「为什么是这一档」的原文，摘要只是上下文，而摘要那一份还很容易因为
  carrier 里嵌过诊断片段而重复占用）。两份都要、谁也替不了谁：摘要说的是「这一轮试了哪几步、最后停在哪」，多条原因合并时只有它还记得前面
  那几次；诊断是工具自己说的那句话，决定性的一行常在尾部。**只给诊断会把先前那条原因顶掉**
  （本轮实测：改成只给诊断之后，`tests/test_youtube_diagnosis.py` 那两条「先前那条原因不许被
  顶掉」当场红 —— 那也是上一次审查留下的约束，两头必须同时成立）。拼的是
  `ToolFailure.summary` **自己留的那份原始摘要**，不是从异常消息上切：消息是「摘要 + 裁过的
  诊断」拼出来的、拆不回去，拿它再拼一次会让决定性那一行印两遍、还白占掉一半字数预算。
  判据落在**重新读库、经真实 ranking 接口拿回来的那一份**里，不落在异常对象上
  （异常对象上一切正常恰恰是这次事故的伪装）。
  回归 `tests/test_youtube_verdicts.py` 钉两层：**集合级**（`VERDICTS` 每一档的决定性原文
  **头尾两处**和阶段摘要都要到得了视频行；头部那个判据刻意不写 429 —— `coded` 认限流那一道
  在分档之前，写 429 会让每一档都变成 `rate_limited`、整个循环空转，429 那一幕单独原样复现）
  ＋**结构级**（AST 扫 `kb/youtube/*.py`：凡往 `reason`/`last_error` 写字的调用都不许带切片，
  凡交给 `_save_failure` 的都必须先过 `_Told` —— 后者管的是**包外**那个共用出口，前一条扫
  不到它。以后新开一个末端当场红，不必等下一轮审查拿真实页面复现）。
  **用例自己也要先证明它没在空转**：carrier 里的阶段摘要得真实地长到 `media` 那一刀（300 字）
  裁不进诊断，否则「诊断开头也要在」会被摘要那一路顺带满足、变成恒绿。
  反过来钉一边：短消息原话一字不动、空消息退回类名、同一句话不许印两遍。
  **频道那一侧交给主干那个共用出口之前，必须先在 YouTube 这条适配边界上过一次**
  （`collector._Told`）。`_save_failure` 自己 `str(error)[:FAILURE_CAP]`，那一刀**从头裁**；
  而 `discovery.merge` 的消息是两份各约 800 字的工具摘要拼起来的、轻松超过那道上限。
  审查实测：详细路径报超时、后路 flat 末尾报 `challenge solver` 和
  `Requested format is not available`，分档和完整诊断都对（`js_challenge`），写进库的频道
  `last_error` 恰好 1200 字、决定性那两行一个字都没留下，面板上展开「查看失败原因」只看到
  先前那次超时和后路开头的普通上下文；`summary.errors.reason` 同样丢。
  **先前「那一刀只是冗余带」的判断是错的** —— 依据是 `ToolFailure.__str__` 已经把诊断过了
  一遍 `excerpt`，但 `discovery` 的 carrier 根本不是单个 `ToolFailure`。过了 `_Told` 之后它
  才真的只剩冗余带：那道上限抽成 `sync.FAILURE_CAP` 由两侧共读，**两处各写一个 1200 的话，
  主干哪天调小、来源侧就静默退回「从头裁」**（回归直接钉「交过去的文本不长于那道上限」，
  不靠「内容碰巧还在」—— 后者在 `discovery` 这个形状上有第二条满足路径）。
  `_Told` 还要**原样转走 `unavailable` / `notice`**：换一个异常对象去交付最容易顺手丢的就是
  它们，丢了之后「这几条取不到」那条提示从面板上整条消失。
  **主干那一侧的本体不动**：它服务所有来源，而 `diagnostic` 这个约定今天只有 YouTube 有
  （主干不认识任何具体来源），所以那边只多了一个常量名、行为一个字没改。
  归并同因失败按 `login.AUTH_CODES`（除 `no_access` 外那几档）整组判，**不是只看 `not_logged_in`** —— 实测最常撞
  的恰恰是机器人验证和出口限流那两档；不同档不许并成一句。`rate_limited` 严格说不是登录态问题，
  但它和那几档同一个形态（一个出口、一次全中），而用户第一反应正是「是不是没登录」—— 归并那一句
  话恰恰是用来说清它不是的。
- **诊断证据的运输口径只有一份:分类在完整文本上做,裁字数只许发生在展示那一端**
  （`kb/youtube/diagnosis.py`）。同一条链上丢过两次决定性的那一行，两次都不是分类函数的错：
  `diagnosis.diagnostics` 原先只留**尾部** 800 字，而 429 在前面、机器人验证在后面——一裁就把限流
  裁成了 bot 墙，面板让人去重新登录，他本来就带着 cookie；面板上那行「yt-dlp 原文」又只取**开头**
  400 字，最终那句错误从另一头丢掉。所以：`diagnostics()` 一个字都不裁（文件已被 `pump_output` 按 8 MiB
  封顶，整份读进来不是新增风险）；失败在抛出的那一刻就把分档算完，随 `ToolFailure.code` 往上走；
  消费方一律走 `login.coded(error)`，**不许各自 `classify(str(error))`**——异常消息为了给人看已经
  裁过两头，决定性那一行可能正在被省略的中段（`collector` 原先就是拿存过库、裁过三道的 `reason`
  重新分类，于是整批失败被归并成「机器人验证」）。给人看的那一份走 `diagnosis.excerpt`，**两头都留**。
- **元数据那一行先剪再量，剪的判据和选轨的判据是同一份**（`diagnosis.redact` / `trim` / `translated`）。
  事故形态（真实请求实测）：yt-dlp 退 0、45 个格式 21 个带音频，`--dump-single-json` 那一行 11.55 MiB，
  其中 11.42 MiB 是 `automatic_captions`（177 个语言键、2.3 万条，九成九带 `tlang`，即现场翻译的自动字幕）。
  `redact` 原先**先量 4 MiB 单行上限再解析**，整行换成替身，`media._single` 报「YouTube 元数据无效」；
  替身又以 `[` 开头、被 `diagnostics()` 当 JSON 行滤掉，面板上的原文只剩同一份输出里那几句 JS 挑战警告，
  分类器照它们让人去更新 yt-dlp——而用户早就是最新版、挑战也早已解开。**大小因视频而异**（同一轮另一条
  只有 0.67 MiB），所以同步时成时不成、「检查登录态」那条却必挂。`--extractor-args youtube:skip=translated_subs`
  **不管用**（它只管人工字幕的翻译）。所以：JSON 行先 `scrub` 再 `trim` 掉带 `tlang` 的条目、**按条目剪不按键剪**
  （同一个键里原文和译文会混着），剪完再量；`media.tracks` 排除现场翻译用的是同一个 `translated()`，两边不许
  各写一份。真超限时写的是 `OVERSIZE`（`kb:` 开头，**不许长得像 JSON**），非 JSON 行的上限照旧。
  **「是本机丢的」这一档（`diagnosis.CAPPED`，上游 `LOCAL`）每个出口都要成立，只修一个口不算修完**：
  认替身只许过 `diagnosis.lost` / `dropped`，**三个解析口**（`_single` 与列频道的 `_listed` / `_detailed`）都过它；
  `lost` **只认行首**，行首那一份只有 `redact` 写得出来（工具自己印的同样开头的行会被垫一个空格）——
  在全文里数子串的话，简介里原样抄了这句话就被当成丢了一行；
  列到了别的几条时照旧收下、丢掉的那条记进 `notes`，事后核对读不了盘也不许把已解析的条目整批丢掉；
  输出**总量**上限走 `diagnosis.flooded`，而且要等完成边界读完原文再抛（裸 `RuntimeError`
  会被检查说成「连不上 YouTube」，先抛的那版原文是空的）；`_collect_listing` 重包时没有半截输出就用解析那一抛自己的上游；
  `login.coded` 只为它破例放过非 YouTube 上游；`merge` 排不出 YouTube 档时它优先于「判不出来」；
  检查结论有它自己的一句话（`MESSAGES[CAPPED]`），列频道那步撞上它不许说成「连不上」；
  **并列提醒按档压、不按结论整条关**（`login.MUTED` / `beside`，检查与同步两条路同一份口径）：
  结论是它时只压 JS 挑战那一档（那一句正是当初冒名顶替的东西），读不出 cookie、限流这些前一步
  说过的话照旧并列在 —— 按结论整条关掉的那一版把它们一起吞了，而那条通道是它们唯一的出口；
  反过来**取到了**的那一轮，JS 挑战那句并列提醒照旧在。审查实测：只修 `_single` 时，列频道那两条路照旧被
  判成 `js_challenge`、归并成几十个频道一句「去更新 yt-dlp」；检查一边说「没能归类」一边并列让人装 deno。
  解析之前另有一道 64 MiB 硬天花板（`_PARSE_CAP`，`json.loads` 占原文约 4 倍内存）；嵌套过深按非 JSON 行处理
  （`scrub` 也是递归的，和 `json.loads` 一起在保护里），泵线程连 `MemoryError` / `RecursionError` 也兜住记进
  `failure`。**只剪自动字幕、不剪 `subtitles`**：后者里的翻译轨
  `tracks(automatic=False)` 会选，剪了就是丢数据；它不会同样撑爆，靠的是 yt-dlp 侧的前提 ——
  `get_translated_subs` 要 `--write-auto-subs` 或 `--list-subs` 才为真，而 `probe` / `detailed_videos`
  都不带。**哪天给 `--dump-json` / `--dump-single-json` 那几条命令加上它们，先回来重看这一条。**
  回归 `tests/test_youtube_oversize.py`（集合级：每一种语言当原语言，剪前剪后选出的轨一样；全部结论 × 全部
  并列档，检查与同步各一遍；端到端走真子进程，每个出口一条），落库再读回页面那一段在
  `tests/test_youtube_verdicts.py` 的 `JUDGED`（本机上限那一档不在 `VERDICTS` 里，要单独并进去）。
- **跑成功了也要把工具的警告交出去，而且不许把警告升级成失败**（`diagnosis.heard` / `record` /
  `witnessed`，`login.CAUTIONS`）。cookie 解密失败在 yt-dlp 那边只是一条 warning：进程退 0、公开视频
  照旧列得出来，于是那条铁证跟着临时输出一起被删，面板上只剩「能带着登录态取到元数据」，而这一轮
  其实没带上登录态，到同步时字幕和音频才全军覆没。反过来那一边同样钉着：`ready` 仍是 `True`、`code`
  仍是 `metadata_ok`、`confirmed` 仍是 `False`，只多一条 `warning` **并列**显示——升级成「登录态无效」
  会让人去重新登录，而他刚刚明明取到了元数据。`CAUTIONS` 和 `MESSAGES` 刻意分开写、不许复用：同一个
  分档在这两处的结论完全不同（那边是「这一轮没成」，这边是「成了，但这份成功可能不算数」）。命中缓存
  那一次没起过进程，不许报警告。回归 `tests/test_youtube_diagnosis.py`（从真子进程跑起——只测
  `classify()` 的返回值对这两处恒绿）。
- **诊断的运输口径只有一条：在工具调用的共同完成边界记账，谁开的账谁读。**
  记账在 `media.run` 那个 `finally` 里（`diagnosis.record`，一次调用一条、带上游标记），**成功、半截、
  失败一视同仁**；开账的两处是 `collector.heeded`（发现一步一本、处理一步一本）和 `login.check`
  （整次检查一本），读账的是 `collector.caution` 与 `login._noticed`，**两条消费路径吃的是同一份集合**。
  **不许回到出参**：出参挂在每个生产者自己的成功交接点上（`captions`/`asr` 是「拿到产物再 `heed` 交出去」、
  `probe` 是「写完缓存再 append」、列表路是「parse 出条目再 append」），那几个交接点随便哪一个不走到，
  这一次工具到底说了什么就整段没人知道。审查实测两条：① 字幕子进程明说 `cannot decrypt v10 cookies`
  并退 1，`heed` 压根没执行，外层拿到的是空袋子，面板上只剩「没有可用字幕，且本地语音转录已关闭」，
  `cautions`/`walls`/`last_error` 全空；② 检查那一侧列表成功、随后 `probe` 超时，早返回只按那条超时
  生成 `code`/`detail`，前面收到的 cookie 警告一个字都没有，页面显示「yt-dlp 报了一个没能归类的错误」。
  同形的还有两处（按代码推断、同一个判据）：`probe` 在写完元数据缓存之后才交警告，缓存写失败就连警告
  一起没了；列表路先 parse 再 append，条目解析不过时警告也进不去。几条跟着的边：
  **后面那一步失败只许往后追加原因，不许抹掉前面那几条**（`obtain` 那两道 `login.merge(..., broken)`
  —— 普通异常和 `NotAttempted` 同一个口径：本机转录关着、缺工具、模型语言不对、ffmpeg/whisper 失败、
  取不到音频都走它，不是只有「关着」那一种，否则下一个组合换个入口又走回来）；
  **一步一本账、出了这一步就交账**（`heeded` 的 `finally`；一本账跨两步会让同一条警告被后面那一步再
  记一遍，归并按频道去重、但档数不去重）；**交账不许押在产物成没成上**（**「这条诊断有没有发生」不能
  由「后面那个产物成不成」推断** —— 字幕解析不过、完整性校验不过、本机转录失败、成品落库失败，随便
  哪一条都能让已经收到的那句警告整段蒸发）；**读账只认 YouTube 那个上游**（`witnessed` 的 `origin`
  过滤 —— 本机 ffmpeg/whisper 和模型服务也往同一本账上记，不过滤就会拿它们那句 `permission denied` /
  `429` 当成「读不出 cookie」「出口被限流」）；**同一个频道同一档不许在面板上说两遍**（`wall` 已经说过
  的那一档从 caution 那句话里减掉，`collector` 里的 `unsaid` —— 这个局部变量**不许叫 `pending`**，
  外面那个「还没轮到的频道」正叫这个名字，一赋值就把收尾那句「撞上 429 后提前收手，还有 N 个频道
  未轮到」整段吃掉）；**不许升级成失败**（取到的照旧收下、照旧出成品，一条 cookie 警告不该让这个频道
  颗粒无收）；**认不出的档一个字都不说**（`unknown` 什么都证明不了，而 yt-dlp 平时的退路警告每轮好
  几条，一律照搬会把要紧的那条埋掉）；**归并要在落库之前**（订阅那条提醒 `last_notice` 取的就是那一刻
  的 `message`，放到后面拼等于面板上永远少这一句，而它是唯一的展示落点）。跟着一条措辞约束：
  **那句话不许自称「取到了内容」**（`CAUTIONS` 与摘要前缀都只说「请求发出去了」）——同一句话在失败路
  上照样要说，而那时内容恰恰没拿到，写成「取到了内容」会和紧挨着的「没有可用字幕」自相矛盾。展示落点
  是**同步摘要**：`kb/static/js/sources.js` 的订阅行只在 `last_error` 为空时才显示 `last_notice`，所以
  失败频道的那条提醒只能靠摘要那句话露出来。
- **本机文件操作一律标 `LOCAL`，临时文件的清理只走 `media.heed` 一个出口**（`diagnosis.on_disk`）。
  裸 `OSError` 没有上游，按 `login.coded` 的兜底算 YouTube，而 `permission denied`、`no such file or
  directory` 两个串都在 `login._COOKIE` 里 —— 一次建目录、写缓存、删日志失败就成了「读不出浏览器的
  cookie」，面板让人去钥匙串放行，而该做的是改权限或腾磁盘。`missing_ok=True` 只挡「文件不在」，挡不住
  权限不足和只读目录，所以那七八处散着的 `path.unlink(missing_ok=True)` 收成了一个 `heed`。
  **但已经有异常在飞时 `heed` 只闭嘴**（`sys.exc_info()`）：清理挂在 `run` 的 `except` 和两处 `finally`
  上，那时正在抛的那条才是人要看的原因，拿「删不掉某个日志」顶掉它等于把线索换成一条噪声——口径同上面
  那条「只许追加、不许抹掉」。临时名带 pid 和序号（`unique`），留在盘上也不会和谁撞。
- **「检查登录态」通过只证明工具链和出口通，不证明那份登录态有效**（`metadata_ok`，带
  `confirmed=False`）：取元数据这一步公开视频也过得去，真正用到登录态的是字幕和音频，那要等同步
  才知道。面板因此有三档文案，绿色只留给真拿到证据那一天。`readiness` 更弱（只看目录和 yt-dlp
  在不在），同样不许自称确认 —— **cookie 过期在文件上看不出来**。
- **登录态不就绪时整轮不开跑**，且**不写 `last_error`、不推退避**：缺的是本机配置，不是这些订阅的
  毛病，配好之后该立刻能跑。失败里同一类原因要在同步说明里归并成一句带频道数的话，逐条明细照旧
  留在 `errors` 里 —— 48 条一模一样的失败要逐条读完才明白只有一个原因。
- **发现全程带登录态，公开订阅只留给「没有登录态」那一档**（`discovery.fetch`）。仓库主人两次点名：
  先是「那就全程登录态吧」，再是「改成 daily-report 那种，它都运行的好好的」；性能代价（单频道从几秒
  到半分钟一档、48 个频道串行约 35 分钟，一轮封在 `DISCOVERY_CEILING`、剩下的下一轮接着查）已经如实
  报过，他没有收回这两句。所以：
  1. `detailed()`：频道视频页**带登录态逐条解析**（`media.detailed_videos`，不带 `--flat-playlist`）。
     拿回**真实** `upload_date`/`view_count`，所以条目**不打 `approximate`**，**显式日期范围那一轮
     照旧走它**。按 `DETAIL_LIMIT` 封顶（实测约 4.3 秒一条、`--playlist-end 4` 用 16 秒拿回 4 条真
     日期，20 条 78 秒）。
  2. `approximate()`：同一个地址、同一把 cookie，加 `--flat-playlist`。**只给 id、标题和时长**，发布
     时间按列表顺序**估算**、打 `approximate` 标记，真实日期等 `media.probe` 才算数。
  **只有第 2 条在显式日期范围那一轮被禁** —— 拿估算值去满足用户指定的范围等于编造那条结论。
  在这之前整条退路一起禁，于是主路取不到的那一轮这个频道颗粒无收（连库里既有候选都不处理，审查
  实测入选 0、处理 0）。
  **`settings=None` 是唯一不带登录态的那一档**：那时没有 `cookies_browser`，公开那份 Atom 是唯一的
  办法（`rss()`，带 `RSS_ATTEMPTS`/`RSS_BACKOFF` 重试，照 daily-report 的
  `--retry 3 --retry-delay 1 --retry-all-errors`；**退避放不下就别退避**）。生产里走不到它 ——
  `collect` 开跑前先过 `login.readiness`，而 `settings.of` 给 `cookies_browser` 的默认值是 `chrome`、
  拿不到空值。**这条分支必须是显式的**：原来是「先试公开、失败再带登录态」，那等于每一轮都先付一次
  那批 47/48 的 404 风险和一次重试的时间，而用户要的是另一件事。`RSS_SHARE=0` 不算修好 ——
  它照样会发那一次请求。
- **发现阶段一个频道一个频道地查，两个之间歇 `DISCOVERY_SPACING`（1 秒）—— 不许并发**
  （`collector.collect`）。参数是借 daily-report 的：它那份 `fetch_yt_channels.py` 起先也是 8 路并发
  （拿 `feeds/videos.xml`），后来整个换成 `fetch_yt_channels_v2.py` 的串行 + `time.sleep(1)  # Rate
  limit`，自此每天 48 个频道、每个逐条解析 20 条都跑得通；我们原先 4 路并发、频道之间不歇，**量比它
  小却撞上了 429**——YouTube 限的是**出口的瞬时请求速率**，不是一天的总量，所以快不起来的地方只能用
  等来换。**不要为了快改回并发**：429 的原话落在登录态检查上（`rate_limited`），面板上显示成「看不出
  登录态」，从那头根本追不到并发这一端。daily-report 全程没用 `--sleep-requests` 之类的参数，这边也
  不自己加。三条反向边同样钉着（`tests/test_youtube_pacing.py`）：只有一个频道的那一轮不许白等一拍；
  **歇着的那一秒里**点的停止也要当场生效（循环开头那道 `not stopped()` 只管得着「查完那一刻」点的，
  所以歇完之后那道检查不是冗余，但它的回归必须打在歇着那个窗口上）；额度要把歇的那几拍算进去
  （`discovery_budget`），否则每一轮固定有最后几个频道被预算闸拦掉、静默进 `skipped`。**处理阶段本来就是串行逐条**，和 daily-report
  的第二遍（`build_yt_dlp_metadata_probe_command`，同样一条视频一次 `--dump-single-json`）同形状，
  那一头不用再加间隔。
- **撞上「请求过多」就当场收手这一轮，而且判据是请求级的、本轮共享的**（`kb/youtube/throttle.py`：
  `media.ytdlp` 和 `llm_request.request` 各一道 `guard`，**记这一笔罚的地方只有一处 ——
  `media.run` 的那个 `finally`**，所有 yt-dlp 子进程共用的完成边界，成功、半截、失败都过
  （`throttle.witness`）；生命周期由 `collector.collect` 的 `throttle.opened()` 圈定）。限的是**出口**，不是撞上的那个频道：接着查下去的话，
  剩下的频道每一个都再去撞一次同样的墙——惩罚被这一轮自己加深、拖长，面板上多出几十条不是它们自己
  毛病的失败，它们还一起进了退避，**下一轮想试都试不了**；处理阶段同形，还会再探满 `max_videos * 3` 次。
  **这件事不许只挂在外层那两个 `except` 上。** 「这一次接住了一条 429」不等于「这一轮之前没撞过」，
  退出某个循环也不等于不再发请求——审查实测三种漏法一条都不经过那个 `except`：①逐条解析撞 429 后
  **后路 flat 照旧起一个进程**，它要是成功了限流只留在被丢弃的原因列表里（`walls` 是空的，这一轮接着
  查下一个频道）；②同一个进程**先印出一条正常视频再 429**，转成「部分成功」，限流只剩一句说明文字；
  ③发现阶段退出之后**处理阶段无条件开跑**，去探前一个发现成功的频道的视频，把那条本来正常的视频也
  带成 `failed` 和退避（首次 429 之后还多起了两个进程）。字幕那条链还会接着试别的语言、自动字幕，
  最后起音频下载，而真走到 `asr` 时第一句话是「ASR 已关闭/缺工具」——**原始的限流到那儿就传不出去了**。
  所以 `asr` 在读工具状态**之前**先过一道 `guard`（本地已有的 `whisper.json` 照旧能用，它不发请求）。
  **挂在各个调用点上记这笔罚必然漏，所以口径只有一份、落在共用的完成边界上**：字幕和音频拿到产物之后
  **当场把日志删了**，而 429 很多时候只是一条警告（进程退 0、字幕也完整），于是那一次挨的罚谁都不知道
  （审查实测：第一次字幕 429 之后又发起了两次新的读取）。各个调用点照旧调 `witness` 取分档，`trip`
  第一笔说了算、不会算成两笔。**「这一次有没有撞上限流」是个独立事实（`login.limited`），不许从展示
  分档的返回值反推**：`classify` 只能给出一种结论，而 cookie 那一档排在限流前面——同一份输出既报
  cookie 解密失败又报 429 时，照分档判就一笔都记不下来（审查实测：两个频道的详细列举都带这两条，
  这一轮照旧查完 `checked=2`）。
  **保留已经取得的条目和诊断是对的，但不该连「本轮须停止发请求」一起吞掉。**
  **没轮到的那些一个字都不写**（不记 `last_error`、不推退避，口径同登录态不就绪那一道）：它们没失败，
  只是没轮到，照旧进 `skipped`。撞上的那一个照常记失败和退避——它这一次确实没拿到东西，原文也得留得住。
  处理阶段剩下的候选一律 `deferred`（「这一轮没轮到」，下一轮回得来），**不许写 `filtered`**：那会让它们
  带着一条不是自己的理由留在库里。「还有 N 个频道未轮到」那句话前面要不要加「撞上 429 后提前收手」，
  **按熔断账判、不按 `walls` 判**——后路补上来和部分成功这两种形态都没有异常落进 `walls`。
  反过来那几边钉着：**只认限流那一档**，普通失败照旧往下查、后路照旧走——认宽了的话一个频道地址写错
  就能把整轮同步掐掉，或者一次网络抖动就让这个频道颗粒无收，而面板上只写着「同步完成」。
  **本地中断不是限流**：人点停止、预算用尽走的是 `media.Interrupted`，一个字都进不了这本账。
  **「没发出去」和「发出去失败了」是两种结果，不是同一种**（`throttle.NotAttempted`）：拒绝起跑只说明
  这一轮先前撞过，被拒的那条视频、那个频道**什么毛病都没有**——不记失败次数、不推退避、不进「重试
  失败项」、不记进 `walls`，当前及剩余候选一律 `deferred`，被拒的频道退回 `pending` 算「没轮到」。
  混成一种的那一版把元数据已经取到的候选记成「处理失败，待重试」、把发现成功的频道记成「连接失败」，
  两边各推一次半小时退避，而 `last_error` 自己写着「没有再发起新的请求」（审查实测，页面截图在案）。
  **消费方按类型认，不比对提示文字**（文案会改）。**但它只在这条目标上「一次都没发出去」时才是结论**：
  同一个频道、同一条视频上已经发生过真实失败（第一条路撞了 429、人工字幕撞了 429），**那条真实失败
  说了算**——它确实没拿到东西，该记的失败和退避照记、原文也得留得住（`discovery.fetch` 的后路分支、
  `media.captions`/`obtain` 的 `if not broken: raise`）。两边都要有自己的红。
  **加这两道专用分支的时候，逐语言的普通失败收集一条都不许少**（`media.captions` 那个
  `except (ValueError, OSError, RuntimeError, TypeError, AttributeError)`）：删掉它的那一版让第一种语言
  的 json3 一坏就掀翻整个语言循环，`broken` 永远是空的、上面那句 `if not broken` 也不可达——而另一种
  语言的完整字幕就在那儿（审查实测：视频同时挂着 en 和 zh，只起了 en 那一次子进程，视频记成「没有
  可用字幕，且本地语音转录已关闭」、连频道一起推了半小时退避，独立对照读取证明 zh 能解析出整段内容）。
  **人工和自动两类共用这个循环**，所以漏的不是某一类。
  **跨轮不留冷却**（立刻再同步一次照旧可能撞上）；**轮外没有熔断状态**，面板上点一次「检查登录态」
  行为一个字不变。回归 `tests/test_youtube_throttle.py`（熔断与拒绝）和 `tests/test_youtube_diagnosis.py`
  （诊断怎么运到人眼前）——两份都**从真子进程跑起**，断言的是「哪几次调用真的发生了」和库里那几条的
  末态，不是「认没认出 429」；假 yt-dlp 和跑一整轮那套夹具是**共用的一份**（`tests/youtube_tool_stub.py`），
  抄两份之后其中一份会跟着代码走偏，而红只在另一份上出现。
- **限流的判据必须带着上游走，`429` 这个状态码不证明请求来自 YouTube**（`diagnosis` 的 `YOUTUBE` /
  `MODEL` / `LOCAL`，`login.coded` 只认 `YOUTUBE` 那一档）。`collector.process` 那个 `try` 同时罩着
  YouTube 元数据、字幕、音频、内容模型、认证和持久化——审查实测：**所有 YouTube 请求都成功、只有
  内容模型返回 429** 的那一轮，面板说的是「出口被 YouTube 限流、网页根本没下下来、换出口也有用」，
  还把一个无辜的频道记进了登录态提醒；照那句话去换出口对模型配额一点用都没有。本机工具同形：
  ffmpeg 的 `permission denied` 落在 `login._COOKIE` 里，一判就成了「读不出 chrome 的 cookie」，
  让人去钥匙串放行而问题在磁盘上。所以**上游在请求边界就标上**（`media.run(origin=…)`、
  `llm_request.failed`），**没标的按 `YOUTUBE` 算**——漏标一条真限流会让这一轮接着朝同一个出口撞下去
  （静默加深惩罚），多标一条顶多让这一轮早收手。模型那一档走自己的熔断和自己的措辞
  （`throttle.NOTICES[MODEL]`、`throttle.model_limited`，**和 `login._LIMIT` 分开写不许复用**）：
  撞上配额之后这一轮不再调模型，剩下的候选 `deferred`，而且不说「换出口有用」。
  合并多条原因的地方（发现的两条路、字幕的几种语言）要用 `login.merge` 把分档带上，
  **不能只留文字**——文字为了给人看已经两头裁过，中段那一行 429 正好在被省略的那一段里。
  **归并层还有一条来源不变量：输入里一条 YouTube 的都没有，输出绝不许默认成 YouTube**（`login.merge`
  的 `elif`）——不标来源的话 `coded` 按 YouTube 算，本机那一侧的 `permission denied` 又被判回「读不出
  cookie」，面板让人去钥匙串放行而问题在磁盘上（审查实测：工具输出目录不可写，直接调用判得对，过一次
  归并就错了）。**混着 YouTube 的那种照旧按默认走**：里面确实有一条，标成本机会把 cookie 那一档的线索
  一起丢掉。
  **一条都排不上名次时，「判不出来」就是结论，不是「没判」**（`login.UNDECIDED`，只许 `merge` 写）：
  留空的话 `coded` 会拿 `carrier` 那段**拼起来的**消息重新分类，本机的 `permission denied`、模型服务的
  `429` 混在里面，猜一次就又成了「读不出 cookie」「出口被限流」（触发例：详细读取本机写盘失败、后路
  随后普通超时）。**这一档和 `classify` 算出来的 `unknown` 分开写**——算出来的那种只说明「这一份
  文本没中任何特征」，`coded` 照旧该去看完整诊断；这一档是「别再判了」。今天每个生产方的 `code` 都在
  和 `diagnostic` 同一份文本上算，两种读法恰好一致，**所以这道分开是冗余带**（代价一个常量）：
  `_collect_listing` 的 `code` 取自解析错误、`diagnostic` 取自工具输出，只差一步就不一致，合着写会把
  「回去看完整诊断」那一道一起关掉。
  **上游要一路带到边界**：起不了子进程的 `OSError`（工具在、没有执行权限）标 `LOCAL`，口径同
  `llm_request`；半截输出要把底下那条真实失败整个带着（`media.PartialOutput.cause`），消费方
  （`media._collect_listing`）一条合法条目都没有时按它的上游和分档抛，不按「没有可解析的条目」算——
  只装一句 `str(error)` 的那一版把本机写盘失败的上游就地丢了，再过一次归并就成了「读不出 cookie」。
  **反过来钉一边：没有半截输出的那一半照旧按解析错误和 `YOUTUBE` 算**——顺手把它也改掉（上游默认值
  写成本机之类）的话，每一次普通的列举失败都不再是 YouTube 的墙，面板上「同步完成」而 `walls` 是空的。
  **挑哪一条按证据强度、不按到达先后**（`login._STRENGTH`，`unknown` 不是结论、不参与排序）：
  逐条解析先报机器人验证、后路随后报 429 时，按先后挑就对外说成「带上登录态通常能过这一道」，
  而用户本来就带着登录态、这一轮正是因为 429 停的（审查实测）。同理，**同一份输出里 cookie 和 429
  都在时对外说的是限流那一档**（`login.coded` 优先认限流）：`walls` 说「读不出 cookie」、面板让人去
  钥匙串放行，放行完再跑还是撞同一道墙——**停止原因、`walls` 分档、给用户的下一步必须是同一件事**。
  cookie 那条证据照旧留在给人看的原文里（`login.evidence`），它才是钥匙串那一步的依据。
  **「这一轮为什么停的」也不许被后写的一句话盖掉**：模型还没配那一轮原先只剩「入选视频待配置翻译和
  内容笔记模型」、`walls` 还是空的（审查实测），看着像只差个模型配置——两件事同时成立就并列着说。
  本机那一侧同形：建工具输出目录、日志泵写盘、起模型子进程失败都标 `LOCAL`（`permission denied` 不标
  就落进 cookie 那一档），而**原文不分上游都要读上来**——ffmpeg 为什么失败，人得在面板上看得见。
- **归属也不许为了补一个 ID 去发公开请求。** 带登录态那两条路的 `channel_id` 以 **yt-dlp 自己报的那
  一份**为准（`media._detailed`/`_listed` 带回来），补不上时退到 `discovery.local_identity`（地址里的
  `/channel/UC…` 或库里缓存的那一份，**一次请求都不发**）。会发请求的 `discovery.channel_id()` 只给
  公开那条路用 —— handle 订阅第一轮原先要先解析一次公开主页，于是**带登录态的工具还没起跑就可能
  被公开请求拦住**。
- **第 2 条路不许走 `feeds/videos.xml`。** daily-report 的 `fetch_yt_channels.py` 是把那个订阅地址交给
  yt-dlp 的（仓库主人点名照它做），但 **yt-dlp 不认领这个地址**：离线核过匹配到的是 `generic`，
  而 generic 把那份 Atom 当成**单个视频页**处理 —— 实测只抠出最新那 1 条，`--max-downloads 10`
  根本没机会生效。拿它当退路等于一个频道只补回一条视频。两条 yt-dlp 发现路共用
  `media._channel_url`，差别只在 flat 与否。
- **普通列表、指定日期详细发现与增量元数据各有独立预算**：普通列表单频道 30 秒、整轮最多
  900 秒；指定日期详细发现单频道 90 秒、整轮最多 1800 秒；元数据更新整轮 120 秒。
  普通列表失败不再启动详细展开退路，未轮到的视频保留预排，不把预算不足当成频道失败。
  **一批也不许被自己的闸拦住**：额度正好是 `rounds × per_source` 时「剩下的时间够不够再跑一整批」
  这道判断在第一批就差那几微秒，待查频道 ≤ 并发数的那一轮于是一个都没查（实测 `checked=0`，
  面板上只说「部分频道未轮到」），所以第一批无条件放行。
- **估算日期不许留到成品里。** 第一次拿到真实元数据的那一刻就是闭环的时刻：`admission.calibrate`
  把估算的发布时间和播放量换成事实值、抹掉 `approximate` 标记，随后调用方拿**同一个**
  `ranking.qualify` 重判资格（窗口、指定日期范围、订阅历史下界、未来时间全在 `ranking.rejection`
  那一份里）—— **`admission` 里不另写一份窗口判断**，口径只有一份。
  **重判必须逐个归属来一遍，不是只重判代表那一个。** 同一条视频可以同时挂在编号链接和 handle
  链接下、也可以挂在两条历史下界不同的订阅下；代表取权重最高的那个归属（`qualify` 里那一份口径，
  `score()` 和这次重判都过它）。只重判代表的事故形态：新订阅历史下界一天前、老订阅六天前，真实
  发布时间三天前 —— 代表（新订阅）按日期该拒，于是这条视频被**全局**判死，下一轮只同步老订阅时
  入选 0、处理 0。重判一个归属都不剩时落 `filtered`（配 `gate_code='window'`、`score_rank=0`），
  **不落 `excluded`** ：日期这类判据是「这一轮不要」，而 `excluded` 连放宽窗口都救不回来。
  读不出事实时间就 `deferred` 留在原处重探
  （`UNDATED`），**不拿「现在」冒充发布时间**，也不永久排除 —— 留在原处的代价只是下一轮按 URL
  去重地再探一次。事故形态：估 2026-10-27、实际 2026-10-25，指定 10-27 补抓时那条前天的视频被收
  进来，而且成品、检索和日报上带的日期还是 10-27。`storage.recalibrate` 的判据
  （`json_extract(entry,'$.approximate') IS 1`）待在 UPDATE 自己的 WHERE 里。
- **未知不等于不合格：拿估算值判出来的「不合格」不许当场固化。** `ranking.rejection` 返回
  `(理由, 判得准)`，`qualify` 据此分出**三种**结局 —— 合格、拒绝、**还判不了**；判不了的那一档
  照旧给代表、照旧进榜，`score()` 把它的 `reason` 写成 `ranking.UNKNOWN`，**不写 `filtered`**。
  为什么这是硬约束：核实只发生在进了 ranked 的条目上（`process` 里探一次元数据 → `calibrate`
  → 同一个 `rejection` 定论），而 `filtered` 会把它排除在 ranked 之外 —— 两件事一起成立就是
  **这一轮再也救不回来**。两种实测事故形态：①只补抓 10-26，真在那天发布的视频报「不在本次指定
  日期范围」、一条不收（估算日期约等于「现在」，落在范围外）；②标题没提 AI、简介还空着的视频
  直接被过滤，没有机会再确认（后路的简介是空的，那是「不知道」不是「与 AI 无关」）。
  **`calibrate` 要连简介一起补回来**：只补日期和播放量的话，核实完还是拿空简介去判，结论和没核实
  一模一样 —— 这条闸只做了一半。**反过来钉两边**：判得准的拒绝不许跟着放水（用户移除、观察/隔离
  名单、已确认不可处理、连估算日期都解析不出来），核实完确实与 AI 无关的照旧拦住、照旧不下载；
  **「没有简介」和「不知道简介」是两件事** —— 逐条解析带回来的空简介就是真的空，按空字符串放水会
  让这些条目每轮白探一次元数据而结论不变。**有界在哪**：核实用的就是 `process` 自己那道探测预算
  （`probes >= max_videos * 3`、`rank_limit`），没轮到的留在候选里、下一轮接着来；估算条目的分
  是拿 `views=0` 算的，天然排在事实候选后面，所以这道放宽不会抢走正经候选的预算。
  回归 `tests/test_youtube_unverified.py`。
- **只有一个分、一张榜**（`score` / `score_rank`，仓库主人拍板：不再区分热度和价值）。两组信号仍然
  都在同一个式子里（播放量与增速、`VALUE` 关键词加分、`NOISE` 标题党扣分，最后乘频道权重），
  **但别再拆回两个分**：两张榜意味着准入要写成「名次 A 以内**或**名次 B 以内」，实际准入面是两个
  上限之和，面板上那两个数字谁都说不清一轮会处理几条。`heat`/`value`/`heat_rank`/`value_rank`
  四列**停止读写但不 DROP**（主干迁移只增不减），补列那一刻把老的热度名次搬进 `score`/`score_rank`
  ——不搬的话存量库在下一轮排名跑完前整张榜都是「—」。设置上 `heat_limit`/`value_limit` 两个旧键
  **仍然要认**（`settings.LEGACY_LIMITS`，折成取宽的那一个）：`validate` 对不认识的键是整个抛，
  而它同时管**读**存量设置，只认新键的话库里存着旧键的人一打开这一块，连预算和登录态配置一起读不出来。
- **估算数据不许覆盖已有的精确数据**，判据待在 `storage.discover` 那条 INSERT 自己的 CASE 里（不许先
  SELECT 再决定）。反过来钉一边：精确数据照旧覆盖估算数据。写错的后果是一条已排好名的候选被降级成
  「没有播放量」，下一轮候选榜上就找不到它。**榜单那一行要把 `approximate` 带到前端**
  （`storage.listing`）：后路是从频道列表页发现的，那上面没有播放量、`views` 一律写 0，面板不知道
  这回事就会把「读不到」显示成「0 次观看」—— 那是在替 YouTube 说一句它没说过的话。
- **列频道只有 `approximate` 那条走 `--flat-playlist`**；单视频那三条路必须带 `--no-playlist`。
  **列不出东西一律抛** —— 真空频道和列举失败在这条路上分不开，抛的代价只是重列一次，漏报则是这个
  频道从此「今天没有新内容」。抛的时候要带上 `media.diagnostics(output)`（只取非 JSON 行）：那份
  警告才说得出是 cookie 解不开还是别的，否则只剩一句「没列出任何视频」。
- **列表路按条目收，不按进程的退出码收**（`media._collect_listing` + `PartialOutput`，两条列频道的路
  共用这一份）。列频道是「一条视频一行 JSON」的流式输出：中间夹一条私有视频、或者预算在第 7 条上
  到点时，前面**已经整行印出来**的那几条一点问题都没有。按退出码一刀切的事故形态（审查用两个真实
  子进程复现）：第一条正常视频的 JSON 整行印了出来，`run()` 按非零退出抛异常并把整份输出删掉，
  解析函数连看一眼的机会都没有 —— 普通轮次丢掉事实元数据改走估算，显式日期那一轮**整个频道报失败**。
  **「没列完」要如实说出来但不算失败**：原话记进 `notes` 出参，由 `collector` 转成 `summary['partial']`
  和面板上那句「N 个频道没列完」（口径同 `feeds.sync` 的 `partial`）—— 记成 `error` 会显示「连接
  失败」并让这条订阅进退避，而它这一轮明明带回了东西。
  **单视频那三条路不许沾这个契约**（`run()` 默认仍是全有全无）：半份元数据比没有更坏，时长、语言、
  字幕清单缺一样，后面每一步都在猜。按停止键那一下也不许拿半截结果固化末态。
- **子进程的输出文件名一处唯一化**（`media.unique`，在 `media.run` 里，调用方一律用返回值）：
  同一个视频被两个订阅同时处理、或上一轮的进程还没退，两边写同一个固定文件名就会互相截断，
  表现成「JSON 解析失败」或读到半份元数据。**原子替换保护的是读者，不是同名的另一个写者。**
- **元数据不许把凭证写进库和日志**（`media.scrub`）：yt-dlp 的 `_calc_headers` 会把整条 cookie 串塞进
  `info_dict['cookies']` 和 `http_headers`，而 `sanitize_info` 不摘这几个键 —— 落盘就等于把登录态
  抄进了 feeds.db 和失败明细里。
- **子进程输出进磁盘只有一条边界，就是 `diagnosis.pump_output`。** 不许把 stdout/stderr 直接重定向到文件
  （`subprocess.run(stdout=open(...))` 那一类）：yt-dlp 自己的 debug 行和报错原文里也带 cookie 串，
  那条路上 `scrub` 一个字都没经过。口径是：子进程一律 `PIPE`（`stderr=STDOUT`），由 `_pump` 边读边
  过 `redact()` 再写，**日志文件以 `0o600` 建**。脱敏这一族（`redact` / `pump_output` / `scrub` /
  `unique`）和「挑哪几行给分类看」（`diagnostics`）住在同一个文件里：它们是同一份输出上的同一件事，
  遮多了分类就没线索、遮少了凭据就落了盘，两头的口径必须摆在一起读（`media` 照旧按名字用它们）。脱敏按**值的形状**判、从它开始遮到行尾（`k=v; k=v;`
  这种整条 cookie 头要连后面几段一起遮）：
  **按「这一行里有没有 cookie 这个词」整行丢是错的** —— 那会把
  `WARNING: cannot decrypt v10 cookies: no key found` 一起吃掉，而那句警告正是
  `login.classify` 区分「读不出 cookie」和「没登录」的唯一依据（实测：整行丢之后 `diagnostics()`
  回空，四档分类退化成一档）。另外两道闸在同一处：单行超过 4 MiB 换成 `[...]`、整份输出超过 8 MiB
  就停止写并标记，免得一条疯掉的进度行把磁盘灌满。
- **`toolchain.upgrade` 的返回键集合必须跟 `status()` 一样**：面板只读 `installed`，键名换一个字，
  **装成功**也会在界面上红着说「没有找到 yt-dlp」。文件系统那一类失败要包成 `RuntimeError` 带上原因，
  `OSError` 漏出去就是 Starlette 的纯文本 500，前端只能榨出一句无信息的「失败」。
- **面板上三个慢动作（打开面板读状态、检查登录态最长 120 秒、更新 yt-dlp 最长 600 秒）回包落地之前
  先对身份**（通用约束在 `docs/decisions/frontend-feedback.md`）：身份在**发请求那一刻**取。
  事故形态：检查在途时改选并保存另一个浏览器，那条迟到的成功结论就贴在新选择旁边说「有效」，
  它说的却是上一轮。身份还要**跟回包时的现状比**：保存的那一份都换掉了就整条作废，只是下拉上有
  未保存的新选择就照显示、但写明它说的是哪一个。
- **身份的粒度是「这一个资源的这一次请求」，不是「这一块面板」。** 三个动作共用一个代次的事故形态
  （审查在真页面上实测两种）：①更新 yt-dlp 期间点一次检查，更新装完回来的新版本号写不进页面，
  版本行停在旧版、按钮已恢复 —— 页面同时挂着「已更新」和一个旧版本号；②刚切过来、状态还在途时点
  检查，浏览器下拉永远只剩一项、工具行一直停在「正在检查工具和模型配置…」，重开页面才恢复。
  **被作废的那两份结果并不过期**，这和「把 Firefox 的旧结论贴到 Chrome 旁边」不是一类。口径分三层：
  **面板身份** `youtubePanel`（换来源、重填整块面板才推 —— 那一刻页面上那几格全换成服务端那一份了，
  在途的回包一律无主；**两道提前返回那里不许推**，那是「什么都没发生」）、**各资源自己的代次**
  `youtubeSeq`（只作废同一个资源上一次的请求）、**共享显示区的归属**（登录结论那一行、版本那一行）。
  第三层要两道判据，少一道就错一头：**①在途的里面有档位更高的**（更新 > 检查 > 状态：更新真的会换
  版本、检查真的连一次网、状态只是便宜的那一道快照），那块区是它的，档位低的回包不许抢在它前面写，
  **但照旧要把自己那块收尾** —— 清掉 loading、补齐浏览器清单，不许只 `return`；**②自己发起之后这块
  区已经被人写过**（`youtubeWrote` 修订号），那份比自己新，这份是旧的，丢掉。
  **档位只拿来比在途的那几个，不许留在显示区上。** 留下来就只升不降：更新一结束没人再写那块区，
  它的占用却把之后**新发起**的每一次检查都挡在外面 —— 登录结论照旧刷新、版本行永远停在更新时那句
  话，像只坏了半边，重开页面才好（审查第二轮实测）。所以「结束」要包含成功、失败、超时和半路判废，
  一律在 `finally` 里松开（`youtubeRelease`）。**反过来钉一边**：真正重叠的那次旧检查在更新装完之后
  才回来，①已经不拦了，判据②接住它 —— 不然刚装上的 2099.01.01 会被它带的旧版本号倒回去。
  **代次拦不住另一类写入：状态回包改的是人正在填的那两格。** 选浏览器和填资料名都不发请求、
  也就不推代次，而 `/youtube/status` 要等后端查完工具和登录态（审查实测压到 12 秒）。所以另立一个
  「人碰过了」的身份位（`youtubeBrowserDraft`）：碰过之后状态回包只许补下拉清单，显示值一律用页面上
  那一份（`youtubeBrowserSpec()`，写回去是空操作，于是「显示值从哪来」仍然只有一处判断）；保存或换
  来源重填面板时这一位清零。另一半是**已存的那份规格要同步填一次、不等 status**：等它填的话，这期间
  点了检查或更新（那两个回包都不带浏览器清单）这两格就一直空着，而这时保存预算会把空白资料名当成
  「他不要资料名了」存回去。事故形态：预存 `firefox:Profile 1`，切过来趁「正在检查登录态配置…」填
  `Profile 2`，回包落地把它改回 `Profile 1`，一句提示都没有。
- **yt-dlp 只往数据目录装，不碰用户的 brew/pip**（`toolchain`，解析顺序是自备优先、PATH 兜底）。
  **版本旧不是「抓不到」的充分原因**，面板上只报版本、不写成待修故障。
- **更新不动正在用的那一份：新环境建在 `tools/ytdlp/envs/<时间戳-pid>`、跑一次 `--version` 自检、
  过了才原子改指针文件 `current.txt`**（`_publish`，`os.replace` 对文件在两个平台上都是原子的；
  不用符号链接是因为 Windows 建它要特权）。任何一步没过就丢掉这份新的，原来那份一个字节没动过。
  原地 `pip install --upgrade` 的事故形态有三种：卸载和安装之间那段窗口里采集照样会起 yt-dlp
  （`_INSTALL` 那把锁只有更新自己拿，`command()` 谁都不拿）、pip 被超时杀掉留下半装的环境、
  而 `command()` 只看入口文件在不在所以看不出里头缺东西。**自检要问刚装好那一份**
  （`_version_of([新入口])`），不能用 `installed_version()` —— 发布之前它还指着旧环境，等于拿旧版
  给新版背书。**新环境必须建在它的最终位置**：venv 脚本里的 shebang 是绝对路径，建完再改名就跑不起来。
  指针读不出、指到一份不存在的环境、或者内容里带路径分隔符，一律退回旧布局（venv 直接装在
  `home()`，存量库就是那样），**不许返回一条不存在的路径** —— 那会让面板报「没有找到 yt-dlp」，
  而机器上明明还有一份能用的。发布之后留最近两份环境：一份给「发布那一刻正好有一轮采集已经解析过
  旧路径」兜底，清不掉也不算失败（Windows 上删正在跑的那份会失败）。
- 不下载视频画面、不做视觉理解，不做配音、渲染、上传。笔记必须明确未分析画面，不能声称信息无损。
- 英文字幕全文分块译成中文，完整译文与中文笔记一起入库；翻译失败不能用英文成品冒充成功。
- 字幕、转录、翻译和笔记分阶段缓存。失败、预算留待下轮和成功入库必须分开留账。
- 候选先记入 feeds.db 的独立表；只有完成中文内容笔记后才写 feed_items，沿现有导出和索引链路进入知识库。
- 入库在维护锁与写事务内再次核验订阅身份；被删除、停用或改指的订阅不得被旧回包写入。
- 内容处理结果与本轮调度状态分开保存；预算延后、缺配置或中断不得清除旧错误或上报成功覆盖。

## 订阅管理

`kb/youtube/defaults.json` 保存上游频道快照，共 52 个：38 个核心创作者、10 个访谈频道、4 个观察频道。
核心与访谈共 48 个默认启用，观察名单默认停用且不排名；访谈逐集判 AI 相关性，不沿用搬运流程的访谈禁令。

启动时按独立 `youtube-defaults-rev` 幂等补种新库和存量库，不覆盖用户更改，不恢复已删除频道。
频道可在「我的订阅 → YouTube → 订阅管理」增删、停用、改分组和排名权重。
接受 `/channel/UC…`、`/@handle` 和官方频道 feed 链接，拒绝单视频链接和其他站点地址。
频道改指会重置旧频道的规则和历史状态，避免继承错误身份。

视频内容在 `youtube_videos` 按 video_id 全局去重，`youtube_video_sources` 单独保存每个订阅的归属和提交状态。
同一频道的编号链接与 handle 链接可以复用一次处理结果；删除或停用首个订阅不影响其他有效订阅收取成品。
改址时淘汰该订阅的旧链接归属，提交时仍核对当前地址。旧 `youtube_candidates` 只做增量迁移、不删除表，
已有候选、成品、错误与归属迁入新表；迁移完成标记避免重复导入旧状态。
订阅改址在同一事务通过触发器清除全部视频归属，改走再改回相同 URL 也视为新生命周期。
条目关联删除时同步撤销归属的 committed；复用与提交还核对实际关联，不能仅凭旧标记跳过补交。
永久排除记录不属于可修复的缺关联，继续禁止重新收录。
该用户决定按内容身份作用于发现、排名、媒体/模型准入和发布，不能由 force、资格修复或处理状态重置撤销。
永久移除的视频不计入频道播放量基线，也不再以其旧失败阻塞来源成功；媒体和模型阶段开始前重新核验排除记录。
已经启动的单次媒体操作不能追回成本，但若期间发生永久移除，后续内容模型与发布不再继续。

最终成品另存当前完整性策略版本、原文输入快照/指纹与成品指纹；发布时重新核验，不以 ready 状态代替校验。
同步遇到无当前凭据的旧成品时转入重新处理，保留原 note 作为恢复证据，旧归属重新等待提交。
资格迁移与隔离在 feeds 数据库初始化事务中统一执行，不依赖 crawl、来源范围或启用状态。
停用、删除、改址和无归属的旧正文也必须在读取、导出前变为待校验说明；有效凭据的存档仍可阅读。
该隔离只改本地资格和待导出正文，不触发媒体或模型，不自动重新启用或补抓已移除的订阅。
已收录的旧正文先替换为明确的待校验说明，不继续标成完整转录；重建成功后更新同一条 feed_items，
保持 URL、路径和首次发现身份，变更正文指纹并使旧译文、提取结果失效，沿现有导出与索引链路更新知识库。
旧成品修复不受新视频的默认窗口限制；显式日期范围仍生效，已关联订阅的旧正文可跨新历史下界修复。

频道权重保留原值：AI Search、Two Minute Papers 为 1.25；Nate B Jones、Matthew Berman 为 0.75；
其他频道为 1.0，Nate Herk 不降权。原始 CSV 的出处和 SHA-256 保存在快照 provenance 中，不代表远端可用性认证。

## 排名与预算

> **这一段的前两句是全程登录态之前的写法，留着只为记住当时的权衡，别当现行规则读。**
> 现在普通同步是**带登录态 flat 列表 + 增量元数据**（`discovery.fetch` / `candidate_metadata`），
> 生产路径不使用匿名 RSS；频道之间仍**串行**、隔 `DISCOVERY_SPACING` 一拍。
> 指定日期才使用详细发现。预算与未核实候选的现行口径在本文件第一节。

频道更新优先读取公开 RSS；handle 先解析成稳定频道 ID。每轮最多四个并发轻量请求，发现阶段预算约 90 秒。
RSS 只提供近期条目，因此日期补抓不能保证完整历史，不宣称已扫描频道全部视频。
RSS 取不到时改用 yt-dlp 列频道（`discovery.approximate`），它只给 id、标题和时长，排名因此降级为
只按标题关键词与频道权重（播放量那几项在 `views=0` 时为零）；这一轮不宣称有播放量数据。

无需 LLM 的轻量评分使用播放量、播放增速、当前候选中的频道相对表现、主题价值关键词、标题噪声和频道权重，
**算出来只有一个分**（`score`）。
这是确定性启发式筛选，不是逐条读完内容后的质量判定；仅标题和简介不明确的 AI 内容可能被保守过滤。
同一视频先逐个有效归属判断分组、日期与历史下界，有至少一个合格归属才合并成一次处理计划。
共享视频采用合格归属中的最高排名权重；同权以较小订阅 ID 确定代表，其余归属不因代表选定而失去提交资格。
**只有一张候选榜**（`score_rank`），同一视频按 video_id 只处理一次；页面可查看分数、名次、处理状态和原因。
已排除的视频不占准入排名；已完成的视频仍保留榜单名次。

默认准入：最近 7 天，候选榜前 10（`rank_limit`），每轮最多 3 条、累计 60 分钟、单条不超过 45 分钟。
处理阶段默认上限 900 秒，本地 ASR 默认 2 线程、逐视频串行；上述预算均可在来源设置里改。
API 部分更新单个 YouTube 设置时保留其他已设预算，不将其重置为默认值。
该合并保证顺序调用；通用设置读改写目前仍可能在并发局部保存时丢更新，不承诺并发合并。
数量预算计入已经开始的尝试（包括失败），累计时长同理，避免坏视频反复耗资源。
元数据探测也有次数上限。超过时长预算留待下轮，不记成处理失败。
已识别的 Shorts、直播、预告、直播回放和不可靠时长不自动处理。
准入结论带类型和重新检查条件：缺时长或首映待发布延后 120 秒，正在直播延后 900 秒，期满重新探测时跳过旧元数据。
Shorts 和已完成直播回放保留排除状态，但显式重试仍会重新核验；旧版无类型的 excluded 首次升级时重新开放探测。
Shorts 类型按 yt-dlp 的 `media_type=short` 归一判断，同时兼容旧缓存中的 `shorts`；不依赖 watch/Shorts 地址形状。
首次发现的不可处理视频仍可能占用本轮已选名额，下一轮才让后面的普通视频进入；不宣称同轮补满。
不保证仅凭标题识别所有 Shorts 或整段软广；后续知识库原有内容提取仍可执行其软广判定。
失败原因独立记为 `last_error`，只在该视频真正完成中文成品后清除；日期过滤、退避、排名变化、预算不足、
缺模型和停止不会清账。来源还有旧错误或 deferred/processing 视频时扣留成功覆盖，不能冒充本轮完整同步。

## 字幕复用与语音后备

只有准入视频才探测元数据，顺序为：

1. 本系统校验过的转录缓存。
2. daily-report 中 video_id 严格匹配的既有原文 SRT（不复用视频文件）。
3. 按语言优先顺序逐条尝试作者上传字幕，首条损坏不会跳过其他作者字幕。
4. 逐条尝试原语言自动字幕；排除带 `tlang` 的自动翻译轨道。
5. 无合格字幕时，仅下载音频，用 FFmpeg 转成 16 kHz 单声道，再调用 whisper-cli。

字幕先解析 JSON3/VTT/SRT，清理标签和滚动字幕重复；缓存、既有 SRT、远端字幕和 ASR 共用同一校验层。
校验可读性与有效时间戳；开头缺失超过 max(5 秒, min(30 秒, 时长的 5%))、中间间隙超过
max(15 秒, min(60 秒, 时长的 10%))、时间区间并集覆盖不足 65% 均拒收；超过 3 分钟的视频还要求末尾达到 75%。
这些保守门槛可能拒绝长时间静默的视频，检查通过也不等于语义无损，不能补齐画面信息。
元数据有字幕时缓存 900 秒、无字幕时 120 秒；上游元数据也按此过期，强制重试跳过两处元数据缓存。
字幕缺失或获取失败时移除本系统元数据，下次可重新发现补上的字幕；已验证转录缓存仍独立复用。
音频最多 100 MB；不存在音频流时不回退到视频流。ASR 结果先保留 whisper.json 与音频，只有转录缓存成功
落盘后才清理音频和中间 WAV；缓存保存失败时下次优先复用已完成的 ASR 结果。
Whisper 英文专用模型不能用于其他语言或不明语言；缺工具、模型或字幕访问受限时明确报错。

## 中文输出与成本

「英文内容翻译」模型负责完整字幕的分块翻译；新增「视频 · 中文内容笔记」模型阶段可独立选择，也可跟随问答模型。
每块最大约 3000 字符，校验译文为中文且时间标记未丢失、增添或换序；每个时间标记段必须有正文，
译文有效字符数至少为原段的 15%，用来拒绝明显空段和摘要冒充全文，并非语义完整性证明。
分段要点可逐级归并，最终生成中文标题、概述和结构化正文；完整中文转录另附其后，时间标记可跳回原视频。
译文保留产品名、代码、URL 和 token 等技术术语，不添加外部事实；作者声称不得伪装成独立核验结论。
缓存身份包含阶段、模型、提供方、输入内容和版本；换模型或输入会重新生成对应阶段。
所有阶段的缓存命中与新结果写入都先验证后置条件：译文逐段合格、要点为非空且不超过 1000 字的中文、
归并结果必须实际缩短、最终 JSON 字段完整且为中文。旧的坏结果只失效对应输出，再请求该阶段；合格原文与译文保留。
完整性策略版本为 `youtube-notes-v2`，旧版翻译与笔记缓存不直接复用。
所有翻译、摘要、归并和最终笔记调用共用绝对截止时间。模型 SDK 关闭自动重试，独立请求子进程由父进程
每至多 100 ms 检查停止和总预算；取消时回收进程组、关闭连接和管道，返回后再拒绝迟到回复。
上述取消依赖父进程正常存活；服务被强制结束时尚无子进程自有看门狗或父存活检测，不承诺异常退出后的任务回收。

模型未配置时仍可发现和排名，但不开始下载转录。失败不会发布半成品，已完成阶段供下一轮重试复用。
省下的是全量下载、重复 ASR 和画面模型成本；入选视频的全文翻译仍有文本 token 成本。
此来源接入已有同步、导出、索引和日报选材，不额外生成另一套 YouTube 日报。
历史 `dr-youtube-dig` 文档未在这里删除或重写，但本通道不依赖它们。
已有日报保存了来源范围的用户，需要在日报同步范围中手动勾选 YouTube 才会自动追踪，不覆盖其原有范围。
目前没有候选、字幕、失败音频的全局保留期限或磁盘总配额；长期运行需关注数据目录容量。

## 为什么从「仅公开访问」改成全程登录态

原来的第一节写着「仅用公开访问，不自动读取浏览器 cookie，不绕过登录墙」。这条由仓库主人改掉了，
依据是这个来源接入后**一条成品都没产出过**，以及下面这组实测 —— 两道墙串在前后两步上，
挡住任何一步都等于这个来源不工作：

- **发现那一步**：48 个启用订阅里 47 个的 `feeds/videos.xml` 返回 Google 通用 404
  （`The requested URL ... was not found on this server`）。已排除 UA（四种）、`playlist_id=UU…/UULF…`
  变体、以及出口 —— 从另一个国家的独立出口请求同样 404。它是**间歇**的：同一轮同一分钟内，
  TheAIGRID 那一个成功拿满 15 条。所以不是端点下线，是端点侧分片不一致，且**跟登录态无关**
  （这个端点本来不需要登录）。
- **视频那一步**：唯一一个 RSS 通了的频道，它的视频全部撞 `Sign in to confirm you're not a bot`。
  裸跑 yt-dlp 2026.06.09 和 2026.10.26 撞的是同一道墙 —— **出口 IP 级，不是版本旧**。
- **带登录态之后**：同一出口、同一个 2026.06.09，两条撞墙视频一次通过；列频道对三个 404 频道
  各约 1.4 秒全部通过（48 个频道四路并发落在 90 秒发现预算内）。
- **但登录态不是无限通行证**：不带 `--flat-playlist` 去逐条解析 20 条，带着有效 cookie 也会从中途
  开始撞墙、25 秒 0 条成功。（**「所以只能走 flat」是当时的结论，后来被改掉了**：逐条解析改成串行、
  每个频道有自己的预算之后它是主路，flat 退成后路 —— 现行口径看第一节和 `discovery.fetch`。
  当时那一轮撞墙的直接原因是四路并发朝同一个出口压。）而 flat 拿不到播放量和发布时间
  （连 `youtubetab:approximate_date` 也不给）—— 这就是后路要打 `approximate` 标记的来由。

所以 RSS 没有退役：它是播放量和发布时间的唯一来源，404 只是让它这一轮交不出东西。
