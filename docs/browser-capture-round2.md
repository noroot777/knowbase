## 已修复的原功能问题

### 1. 待办可写性只有一份判据

- `writable(intent, item)` 统一检查条目存在、未排除、允许原文替换、非 X 观点及绑定的 key / 正文摘要 / 修订号 / 来源 / 原网址。
- 补抓页待办、扩展待办与保存前检查共用 `_refresh_status()`；创建请求的复用判断也调用同一判据。扩展无需先打开补抓页，即会剔除已失效请求。
- 扩展列表用一次数据库连接批量读取当前条目，按 key 去重；没有为每条待办单独打开数据库。
- 保存前检查在 `BEGIN IMMEDIATE` 内执行，原 UPDATE 的版本、来源、网址、类型和排除条件仍保留；提前检查不能替代事务内的最终拒绝。
- 这是原浏览器补抓功能的遗漏：`23f96aa` 中 `pending()` 已经只看内存状态，而 `save()` 已有条件 UPDATE。上一轮添加 `item_state()` 使不一致更明显，但不是其根因。

### 3. 常驻状态与一次性反馈分开

- 显示配对密钥失败、复制成功 / 手动复制指引、继续处理时回执变化的拒绝说明，均改走统一 `toast()`，不再改写轮询维护的 `#message`。
- `toast()` 使用 `textContent` 放入文案和详情，移除对主应用 `core.js` 中 `esc()` 的依赖。独立补抓页可以直接使用统一反馈，不加载会初始化主应用面板的整份 `core.js`，也不复制一份转义函数。
- 反馈由统一出口按原有时长和关闭按钮管理，不会被下一次状态轮询提前清除；复制失败时仍选中密钥并给出手动复制快捷键。
- 这处根因在 `23f96aa` 已存在：等待采集期间的 `poll()` 会调用 `display()` 重写 `#message`，而配对 / 复制提示也写在同一元素。故本轮处理该原功能问题，而不只为上轮新增的回执拒绝文案打补丁。

来源依据：`23f96aa:kb/static/js/browser_capture.js` 的网址默认值只在 `initialize()` 中赋值（原第 147 / 157 行）；其 `poll()` 仅在 pending 期间运行，期间网址字段禁用，且不写入该字段。上一轮修复提交 `db571bd` 为了跨标签、关闭页面后恢复回执，改为持续调用 `refresh()` / `render()`；在 `render()` 第 72–73 行新增按 pending / 空值回填网址，并在 `refresh()` 第 120 行安排无条件两秒轮询。本轮第 2 项报告的就是这次修复新带来的交互缺陷。
