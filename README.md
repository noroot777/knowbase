# Knowbase

个人知识库:把 obs vault 里的内容(绿泡泡公众号、YouTube 视频摘要)统一索引,
支持关键词 + 语义混合检索和意图问答。

## 免责与使用边界

**先读这一节再跑。**这个项目为了把公众号文章收进本地知识库,会在你这台机器上做下面
这几件事 —— 它们的影响范围比「一个检索工具」大得多:

- **请求 macOS 管理员授权,并以 root 运行 wxkey**(从固定源码构建)去提取**本机微信
  客户端的数据库密钥**。这个过程可能让微信退出或重启,并创建一份重签名副本。
- 用 **SQLCipher 只读打开解密后的消息库**,从里面发现公众号图文推送(私聊、群聊不作为
  文章采集)。
- 按推送里的文章链接**批量抓取公众号文章全文与图片**,存进本地 SQLite 和 Markdown。

### 边界

- **仅限你本人的微信账号,仅在你自己的本机运行。**不要拿它去读别人的微信,也不要
  在别人的机器上跑。页面上那个勾选框(「这是我本人的微信」)不是形式 —— 它就是这条
  边界本身。

- **使用者自行承担风险。**批量抓取和读取本机客户端数据库可能违反微信的服务条款,也
  可能触及你所在地的法律法规(著作权、计算机信息系统、个人信息保护等)。是否使用、
  怎么用,由你自己判断并承担后果。
- **本项目不提供任何保证。**按 [LICENSE](LICENSE) 的 MIT 条款,软件按「原样」提供,
  不保证可用性、正确性、数据不丢失,也不对任何直接或间接损失负责。采集依赖的上游
  工具和微信客户端版本随时可能变化,昨天能跑今天跑不通是常态。
- 维护者**不会**为规避平台风控、绕过授权或抓取非本人账号的内容提供帮助。

不接受上面这些,就别用这个项目 —— 只做索引和检索(不碰微信)的那部分可以单独用:
把已有的 Markdown 目录挂给它,见「[Docker 部署](#docker-部署)」。

## 没有鉴权:默认只听回环,别直接暴露到网上

**kb-web 不做任何身份验证** —— 全仓库没有一行鉴权代码:没有登录、没有 token、没有
API key 校验。它唯一的保护是**默认只绑在回环地址上**(`kb/server.py` 里 `KB_HOST`
默认 `127.0.0.1`)。

把 `KB_HOST` 改成 `0.0.0.0`、或者把 8787 端口映射出去之后,**任何能连上这个端口的人**
都可以读走整个知识库的全文与笔记、调 `/api/chat` 花掉你配置的模型 API key(账单记在
你头上)、触发采集管道、改配置、删库里的内容。

要从别处访问就走 **SSH 端口转发**(`ssh -L 8787:127.0.0.1:8787 …`)、私有网络,或者
在前面放一个**自己带鉴权的反向代理**,只让代理连本机端口。细节见 [SECURITY.md](SECURITY.md)。

## Docker 部署

安装 Docker Engine / Docker Desktop 和 Compose v2，在项目根目录运行：

```bash
docker compose up -d --build
# 打开 http://127.0.0.1:8787，配置供应商和各阶段模型
docker compose logs -f --tail 100
```

默认使用持久卷保存配置、索引、采集器数据、文章和模型缓存。已有文章目录可在
`.env` 中配置 `KB_VAULT_PATH`（参考 `.env.example`），再运行
`docker compose exec knowbase kb index --no-vector` 建立关键词索引。

**公众号采集只能在 Mac 本机跑。** 它读的是本机微信客户端已同步的推送,Linux 容器
碰不到那个库。推荐在 Mac 完成采集和导出,Docker 挂载导出的文章目录做索引和分析,
无需安装情报库 skill。镜像已包含应用和采集器依赖,首次向量索引会额外下载约 2GB 模型。
迁移、挂载和备份方法见 [Docker 部署说明](docker/README.md)。

## 架构

```
obs vault (事实来源, Markdown + frontmatter)
  ├── source/dr-gzh/          公众号文章 (collector/ 导出)
  ├── source/dr-youtube-dig/  YouTube 摘要 (自带 entity/topic 标签)
  └── source/gzh/             公众号实时保存 (gzh_saver)
        ↓ kb index                      ↓ kb extract
  SQLite (data/kb.db)           claude CLI (haiku)
  ├── documents / doc_tags     提取 entities/topics/summary
  ├── chunks + FTS5(jieba)       ├→ 入库 (可过滤可穷举)
  └── chunk_vec (sqlite-vec,     └→ --writeback 回写 obs frontmatter
      bge-m3 本地 embedding)
        ↓ kb search / kb ask
  FTS + 向量 → RRF 融合 → doc 聚合 [→ Claude 综合回答]
```

分工:**向量管"描述意图找内容"(语义模糊匹配),FTS+tag 管"精确命中和穷举"。**
标签提取(entity/topic)是搜索质量的大头,与是否用向量无关。

## 用法

```bash
uv run kb index                # 扫 vault,增量索引 + 补向量(首次下载 bge-m3 ~2GB)
uv run kb index --no-vector    # 只建 FTS(快,不依赖模型)
uv run kb extract --limit 20   # LLM 提取(公众号文章;youtube 自带标签免提取)
uv run kb extract --writeback  # 提取并回写 tag 到 obs md

uv run kb search "把书变成skill的工具"           # 混合检索
uv run kb search "画图" --tag topic/skill工具    # 带标签过滤
uv run kb search "xxx" --entity book-to-skill   # 按实体精确过滤
uv run kb search "xxx" --source dr-gzh --json   # 来源过滤 / JSON 输出

uv run kb ask "有没有能自动生成架构图的开源工具?"  # 检索+Claude 带引用回答
uv run kb stats

uv run kb-web                  # Web 界面: http://127.0.0.1:8787
```

## MCP(在 Claude Code / Desktop 里直接问知识库)

```bash
claude mcp add kb --scope user -- uv run --directory ~/code/knowbase kb-mcp
```

注册后对话里可用工具:`kb_search`(混合检索,支持 since/until 时间过滤)、
`kb_enumerate`(全量枚举实体/文章,穷举类问题用这个,不漏)、`kb_read`(读全文)、
`kb_entities`(列实体)。不提供 ask —— 调用方本身是 LLM,检索完自己综合。

## 问答的意图规划

`kb ask` / web 问答不是单纯 RAG:先用 haiku 把问题解析成查询计划——
- **穷举类**("最近一周都提过哪些开源项目")→ `mode=enumerate_entities`,
  SQL 全量聚合(时间/来源/实体类型过滤),一篇不漏,再由 Claude 分类整理
- **内容类**("X 怎么用/哪篇讲了 X")→ `mode=retrieve`,top-8 混合检索后综合
解析失败自动退回 retrieve,保底可用。

## 日常流程

web 界面(`uv run kb-web` → http://127.0.0.1:8787)的"管道"tab 一键搞定:

**抓取**(委托来源采集器,不在线则跳过)→ **导出**(采集器 → obs md)
→ **索引**(FTS + 向量,增量)→ **提取**(entity/topic/摘要,tag 自动回写 obs frontmatter)

抓取/导出两阶段只跟 `kb/collectors/` 的采集器契约打交道,知识库自身不认识
任何具体来源。公众号那一侧全在 `kb/collectors/wechat_local.py` + `collector/`:
推送怎么发现、反爬要等多久、文章先落哪个库都关在那里;换来源或换抓取方式只写
一个新实现,管道一行不改。

面板显示各阶段进度/待处理数/采集器健康状况(文案由采集器给,面板只渲染),
「管理公众号」弹窗可以添加、停用、移除订阅——采集器实现了 `TargetManager` 契约
才显示这些,没实现的来源自动隐藏。

**没有「同步前的准备」这一步。** 公众号采集读的是本机微信已同步的推送:不要凭证、
不起代理、不用在微信里逐个点开文章。添加公众号时的候选也来自本机的会话列表,
不登录公众平台。采集器是一次性 CLI,平时不占常驻进程——点"同步"时才起子进程,
跑完就退;唯一常驻的是 kb-web 自己。

所有操作走 `./kb.sh`(不带参数看命令列表):`sync` / `status` / `collect` /
`export` / `index` / `extract` / `graph` / `accounts` / `web start|stop`。
服务都是后台守护进程(自成会话),起完终端就能关,不占前台。

等价的 CLI:
1. `cd collector && ./.venv/bin/python -m cli collect` 抓新文章,再 `... -m cli export` 导出到 obs
2. `kb index` 增量索引新文档(内容 hash 判断,秒级)
3. `kb extract` 给新文章打标
4. 随便搜

### 公众号采集:读本机微信已同步的推送

通过 Rion Reader 只读本机微信客户端的公众号图文推送,提取文章链接后按链接抓正文。
不需要任何凭证、代理或逐号授权;首次在面板的「绿泡泡接入」窗口里检查工具、获取
数据库 key。日常同步读不到时如实报错,不自动重新获取密钥。

请先在 Mac 微信里订阅并同步需要采集的公众号——本机没有推送的号会显示为覆盖缺口,
不算请求失败;订阅之前的历史和未同步的消息不保证补齐。

发现和正文是两步:先增量更新本机文章索引,再按发布时间和所选公众号查询,去重后
只下载新文章和缺失的正文。「不限时间」查整个索引,指定区间含结束日全天。

同步范围(这次抓哪几个来源、哪些公众号)的手动选择保存在当前浏览器;「每日定时」
旁可单独设置定时范围。失败重试沿用上次运行的公众号和时间范围。文章按
`__biz + mid + idx` 去重并保留原档案 ID。

> 另一条采集方式(逐号文章凭证,靠 mitm 从 Mac 微信里截)在 `wechat-oa` 分支上,
> 不做推荐、不再跟进主干。两条分支始终并行,不打算合并。

首次同步批量索引本机已有的公众号图文推送；后续按每个消息分片/表的消息 ID 更新新增推送，公众号匹配静默进行。索引可包含未选公众号的文章元数据，但它们不会进入正文下载和知识库导出。修改时间范围或选择公众号时直接查询索引，不重新逐号翻历史。消息 ID 与文章发布时间分开，延迟同步的旧文章也能被发现；检测到库重建、消息数量或边界改变时会重新校验，读取失败不推进对应游标。

同步进度分为「发现文章」和「下载正文」，显示推送读取数、正文完成/总数、成功/失败、已有正文及等待重试数。批量正文请求保留节流；失败从 5 分钟开始退避，最长一天，原文明确不可用则一周后复查。正文失败不影响文章索引及已完成文章发现的公众号「最近采集」时间，下次到期后直接从索引重试；这类待补正文显示在「待处理明细」，不会误报账号失败或要求立即重跑整轮同步。导出阶段同样列出缺正文的待补明细，不会因为发布时间早就标为删除；用户主动删除的文章仍不会被重新采集。

不可解析的单条推送单独记录位置、内容指纹及可提取的文章 URL 归属线索，允许正常数据继续推进增量游标。后续只核对这些异常行，内容改变后自动再解析；能确认属于未选公众号的内容异常不进入同步提示。有不可读推送的所选公众号会在待处理明细中显示名称和现存条数，即使已有历史文章也会显示。已有覆盖的账号统一以本轮发现检查完成时间更新最近采集，不因是否有新文章或旧坏推送而采用不同口径；真正读取失败的账号保留原时间，新分片失败也按同一会话关联判断。仅能唯一匹配同名会话时明确标注归属待核实，不据此采集文章；同名冲突只在一条汇总中列出候选账号，条数不分摊给各号。完全无归属线索的异常仅汇总数量，不改变其他账号的覆盖状态。正常未同步账号仍只提示「在绿泡泡关注并同步后可采集」，不列入待处理明细；若同时有归属未明的推送，则提示「未匹配到本机推送」，说明仅在未关注或未同步时需要关注/同步，那批未知推送也可能来自这些账号。数据库读取或依赖故障仍作为错误报告，不会被当成坏消息跳过。

旧版本缺少 `chksm` 导致本地文章误退休时，可先运行 `python collector/scripts/recover_local_articles.py --db <采集器数据库>` 预览，再加 `--apply --backup <备份文件>` 复位。这只恢复重试资格，正文会在使用修复版本下次同步时补抓。

```bash
./kb.sh sync --channel wechat_local
./kb.sh collect --channel wechat_local --since 2026-09-01 --until 2026-09-15 --targets 公众号名
./kb.sh sync --channel wechat_oa

# 采集器 CLI 对应选项（用于直接排查）
cd collector
./.venv/bin/python -m cli status --channel local
./.venv/bin/python -m cli collect --channel local --targets 公众号名
```

默认复用 `${CODEX_HOME:-~/.codex}/skills/wechat-cli/scripts/reader.sh` 或已安装的 `rion-wechat-cli`，需要支持只读 `schema` / `sql`；也可使用「绿泡泡接入」准备的独立运行环境，无需安装 skill。自定义安装可通过 `RION_WECHAT_CLI_BIN` 指定可执行文件。升级后在 `collector` 运行 `uv sync --frozen` 安装压缩消息所需的 `zstandard`。文章元数据及读取游标保存在采集器私有 SQLite 的 `local_wechat_articles` / `local_wechat_sources` 表，不持久化原始推送 XML、私聊或数据库密钥；旧版 JSON 匹配缓存不再参与采集。

### 首次绿泡泡接入

首页「完成首次配置」、设置菜单「绿泡泡接入」和同步中心均可进入。先配置供应商和模型／智能体，再点「检查并接入绿泡泡」。获取 key 是独立的本机步骤，不使用供应商 API，也不向模型发送密钥。

1. 已有 Reader 配置可读时直接复用；已有 wxkey 材料则验证并导入，不覆盖旧配置和 Profile。
2. 没有 Reader 时，项目自动下载校验固定版本源码，用 uv 安装隔离的 SQLCipher / Zstandard 环境。多个账号必须在页面选择，不能自动合并。
3. 确实缺 key 时，自动构建固定版本 wxkey。页面说明进程访问、绿泡泡退出／重启及重签名副本的影响，勾选确认后点「自动获取 key 并验证」。管理员密码只在 macOS 系统授权框输入。
4. 获取前保存本机加密数据库和 sidecar 副本（活动文件副本不等于一致性备份），单次获取最多 600 秒，授权等待另有 180 秒。获取后自动验证、发布 Reader 配置并检查采集器实际使用的 Reader。成功后点「去同步公众号」。

当前自动获取限 macOS 本机访问，要求已登录自己的绿泡泡，以及 uv、Go、Apple Command Line Tools（LLDB）。Go 1.26.5 工具链可由已有 Go 自动下载。远程部署不能替浏览器所在电脑读取绿泡泡。系统授权、登录和版本不兼容不能保证无人值守完成。

独立工具位于 `~/.local/share/knowbase/wechat`，可用 `KB_WECHAT_RUNTIME` 更改（Web 服务和采集器需保持一致）；密钥与 Reader 配置仍位于本机私有配置目录，不回传页面。状态、构建收据和加密备份留在私有运行目录，备份可在确认不再需要后自行移除。关闭页面不取消后台工作；刷新页面恢复进度。获取失败保留上游恢复锁，不能自动重试或清除锁。已有配置失效时先修复配置，不因读取失败重新获取 key。

实现固定到 [Rion Reader `f7d60b6`](https://github.com/Rion-Wu-tech/wechat-intelligence-hub/tree/f7d60b6d94c70f09ad92b89215ce40b2dd752e7f/projects/rion-wechat-reader) 和 [wxkey `9b70eec`](https://github.com/r266-tech/wxkey/tree/9b70eecdde47a7172b19465c3f977c86b6050e8a)。下载文件校验 SHA256，wxkey 从固定源码构建并记录二进制 SHA256；系统授权路径以 root 调用并设置 `WXKEY_NO_ELEVATE=1`，该版本会跳过管理员密码 Keychain 路线，不启用修改原绿泡泡或关闭 SIP 的开关。兼容适配只修正“可读但未分类的辅助库被误计为未解密”的判断，真正读失败仍阻止接入。

**文章获取与 skill 的关系：** `wechat-intelligence-hub` skill 用于聊天情报、日报和商机分析，本项目采集文章不依赖它。数据库 key 用于读取公众号推送；全文及图片通过原文网页下载，不需要绿泡泡缓存图片的解码 key，也不保证补齐未同步到本机的历史。

## OpenAI 兼容协议

顶栏「设置 → API Key」的 OpenAI 兼容区域提供 **Responses → Chat Completions** 开关。
开启时，统一文本调用转为供应商的 `/chat/completions`；关闭时直接调用 `/responses`。
普通调用和问答流式调用使用同一配置，保存后即时生效，无需重启。原生 Responses 请求使用
`store=false`，不依赖供应商保存会话；问答上下文仍由知识库自己的提示词传入。

为保留升级前的行为，未配置开关的旧配置默认开启转换。配置保存在
`data/secrets.json` 的 `openai.protocol_conversion_enabled` 布尔字段；API 写入字段为
`POST /api/keys` 的 `openai_protocol_conversion_enabled`。Key 和 Base URL 的环境变量
优先级不变，协议开关仍可独立设置。模型列表继续通过 `/models` 拉取，不受开关影响。
这不是对外的 Responses 代理，不包含 Codex 工具调用协议转发。

## 设计决策备忘

- **obs md 是事实来源**,SQLite 只是索引(可随时删掉重建):换检索栈不锁死数据
- **中文 FTS**:FTS5 unicode61 不切中文词,入库/查询都过 jieba(`store.tokenize`)
- **RRF 融合**(k=60):不依赖两路打分量纲,免调参
- **doc 分 = 最高 chunk 分**:避免长文靠块数刷分
- **embedding 可换**:接口在 `kb/embedder.py`,换模型后 `kb index --reembed`
- **每个用到大模型的阶段各配各的**:问答回答/规划/研究、收藏分诊、提取打标、
  条目化 gate/拆条目、wiki 综述 —— 注册表在 `kb/llm_stages.py`,面板在 kb-web
  顶栏「模型」。选项按供应商分组,**选的是哪家就用哪家的 key**(同一个 id 在两家
  中转站都可能有,只存模型名就只能靠前缀猜,猜错是拿 A 家 key 打 B 家的站)。
  没配的阶段沿用注册表里的内置默认,也就是这套设置出现之前各文件里写死的那个 id。
- 规模预估 ~15 篇/天,5 年 ~20 万 chunk,sqlite-vec 精确搜索毫秒级,不需要独立向量库

## 大V观点与 RSS

左侧「信息来源」现有绿泡泡同步、大V观点、RSS 三个平级入口。大V观点首次导入 51 个 X 账号，RSS 首次导入 9 个订阅地址；支持增删改、停用、单源同步、内容阅读及独立定时。删除订阅保留已收录内容，重启不会恢复已删除的默认项。

手动或自动同步共用管道运行锁，完成采集、Markdown 保存和索引；单源失败独立退避，忙碌时定时任务顺延。自动同步默认关闭。RSS 内容不足全文时标注摘要；X 默认桥接依赖外部服务，可在界面更换全局模板或单账号专用 feed。

来源通过注册表与适配器扩展，本次不增加普通博客类别和 YouTube 采集。数据位置、同步限制、X 可用性与后续扩展方法见 [来源模块设计](docs/source-modules.md)。

**英文内容自动译成中文。** 订阅类来源(大V观点 / RSS)抓到的英文条目在导出进
vault **之前**先整篇翻译:标题和正文都译,专有名词保留原文,正文开头留一行
「本文由英文原文自动翻译」的提示,frontmatter 记 `lang: zh` / `translated_from: en`
(标题真的换了才另记 `original_title`)。放在导出前而不是阅读时,是因为 vault md
是事实来源——索引、提取打标、检索、日报读到的都得是中文,否则中文检索永远搜不到
这批内容。中文条目按字符判定(不花钱)直接跳过;**一个汉字都没有又有字母的一律算
外文,不管多短**——「Hello world」「Hello」「Great」这类短动态原来会被当成中文、
永远留在英文状态。产品名(「Bun 1.3」)该保留原文,靠的是翻译提示词里"产品名、
人名、代码、URL 保留原文"那条规则,不是把它当中文。
**一轮译不完的(成本上限 40 条/轮)不会先以英文落盘**,留到下一轮译完再写进 vault;
这期间它们在来源页面上标成「正在等翻译」,标题和正文都只写中文状态文案、也不给
「展开阅读」——库里还没有这一条,想看就点右下角的「原文」。只有重试三次仍然译不
动的、以及没配翻译模型的,才按英文原文导出(那时候英文总比这条内容根本进不了库强,
来源页面也就照原文显示)。**没配模型那阵子按原文入库的条目,补上模型之后标的是
「外文原文已入库,正在等中文译文覆盖」**:那一份英文此刻确实在库里,说它"暂未写入
知识库"反而是假的。标题和正文都译成中文才算一条译完——模型漏掉格式标记时会单独
补译一次标题,补不到就整条下轮重试,不会留下"正文中文、标题英文"的半成品。**升级前
已经留在库里的那批半成品**,下一次同步会自动清回队列、只补那一行标题(正文不重译);
在补上之前页脚如实写「正文已译为中文,标题还是原文」,不会假装整条译完了。阅读弹窗
有「看原文」可以切回英文。翻译模型在顶栏「模型」的「来源 · 英文内容翻译」阶段里配。
**补译会重写那篇已经导出过的 md,提取打过的话题/实体标签原样留着**——不留的话重索引
会按新文件重建标签、而提取完成时间还在(不会再打一遍),那篇文章从此按原话题搜不到,
再同步也不恢复。**翻译失败不会被说成同步成功**:这一轮有内容因为翻译出错没能入库时,
导出阶段判红、写明几条失败与原因,日报那头也照实记(试满三次按原文入库的不算失败,
那是设计好的出口;"这一轮只译得下 40 条、其余下一轮"算正常积压,和失败分开报)。
**已经按英文入过库的旧文章补译失败,同样不算同步完成**——库里躺的还是外文,这一轮
会写明「N 条补译失败(库里仍是原文)」;还没轮到补译的那些写「等待中文译文覆盖」,
不会说成"译完再入库"(它此刻读得到)。**同一轮里有译成的也有译不成的时候,译成的
那些照常入库**:能搜到、能进当天日报,失败的那几条单独扣着下轮重试。

## 每日日报

左侧「每日日报」:点「同步全部并生成」，或只用已入库的内容「直接生成」。日报按天写进
`<vault>/daily/YYYY-MM-DD.md`，可以直接在 Obsidian 里读。

- **覆盖的是「上一份日报的截止时刻 → 这一次的生成时刻」这段时间里发布的内容**，
  不是某个自然日。日报早上七点出，那它该覆盖昨天七点到今天七点 —— 按自然日算的话，
  昨晚七点之后的一切会掉进两份日报中间的缝里，再也不会被任何一份提到。上一份的截止
  时刻记在它自己的 frontmatter 里，所以链条自描述，删掉状态文件也能接上。页头写着
  这一份要覆盖哪一段，点「改区间」可以手工指定（补一份旧的、重算一段）。**没有「最长
  回溯几天」这种上限**：停服四天之后那一份就覆盖这四天，起点绝不往后挪——挪过去的
  那几天再也进不了任何一份日报。素材太多时按条数截断（日报里写明「窗口内共 N 条」），
  而不是把窗口本身砍短。
- **筛的是内容的生产时间(`published`)，不是抓取/入库时间(`indexed_at`)。** 两者差几天
  是常态（实测一批 RSS 发布于 26 号、29 号才抓进来）。按入库时间出日报，读到的是
  「今天抓到了什么」，而人想知道的是「这段时间世界上发生了什么」。
- **发布得更早、这一轮才抓进来的内容进「补录」**，单独一节、单独计数，不混进要点。
  不捡回来的话它永远进不了任何一份日报。
- **定时**:设一个时刻（默认关闭），到点自动跑一轮；可选跑之前先同步、同步哪些通道。
  一天出一份；遇到临时故障（模型 502 之类）当天会隔半小时补两次，出报成功、没有素材
  或者你自己按了停止就不再补。「没有上一份时回溯 N 天」只在一份日报都没有、接不上任何
  截止时刻时才用得上。
- **「同步所有内容」**是依次借用同一条管道（抓取→导出→索引→提取）把所选通道各跑一趟
  ——管道是单例（一把全局运行锁、kb.db 单写者），并发起只会互相拒绝。条目化和 wiki
  两个重活不跑:日报不读它们的产物。超过时间预算（默认 3 小时）就请求停下、拿已有内容
  出日报——"今天的日报没出来"比"日报少了两个来源"严重得多。窗口的截止时刻在同步**之后**
  才定下来，同步花掉的那几小时里产出的内容也算数。**你自己按「停止」是另一回事**：
  当前阶段收尾后这一轮就结束，不再生成日报（已同步进库的内容保留）。停止只管这一轮
  日报自己起的那一次同步（按运行编号认，不是"现在有同步在跑"就去停它——日报那一轮
  刚跑完、另一项同步紧接着开始时，认错就把别人的停了；同理，没拿到自己那一轮的结果
  时如实记成"成败未知"，不按成功记账）：日报在别人的同步后面排队等
  时按停止，只结束等待，不会把别人
  那一轮也掐掉。**已经在出稿（模型调用中）的时候停不了**，按钮会置灰并写明原因——那时
  模型钱已经花出去、文稿也是一次写完的，受理下来只是承诺一件做不到的事；这一份会照常
  保存，不想要可以生成完删掉。
- 勾了「先同步」却**一个同步范围都没选**时不会起跑：那样同步阶段什么都不做、界面却一路
  报成功，等于把「同步全部并生成」悄悄换成「直接生成」。只想用已入库的内容出报就点
  「直接生成」。
- **有来源没同步成功时，日报照样出，但三处都会说清楚**：完成提示写「N 个来源未同步成功
  （…）」、面板上留一条横幅（点得进同步进度）、日报文件本身也写进 frontmatter 和正文
  （所以复制出去、明天翻回来都看得见），历史列表那一行也标着。降级用已有内容出报是对的
  ——"今天的日报没出来"更严重——但一份"一个新来源都没同步到"的日报不能跟"全都同步到了"
  长得一模一样。
- **素材**取窗口内入库的原始来源（衍生条目树不算，hard 软广按同一份口径挡掉），
  一篇给模型一句摘要 + 来源 + 链接，综述里带 `[n]` 引用回原文。
- 这段时间没有任何内容时**不写空日报**，横幅上说明原因；已有的那天要重新生成会先问一次。
  日报不进 `kb/config.py` 的 `SOURCES`，不会自己把自己再索引一遍。
- 模型在顶栏「模型」的「日报 · 当日综述」阶段里配。
